# Squeal

Under Codex `squeal` is not on the PATH: wherever this skill and its references say `squeal`, run the command the SQUEAL primer names. That is the launcher `<plugin data>/bin/squeal`, in the plugin data directory where Squeal keeps a copy of each version; before the first copy, it is `node --disable-warning=ExperimentalWarning "<plugin root>/dist/cli/squeal.mjs"`, the plugin root being the directory that holds `skills/squeal/`. The last line of a FAIL report names it too. A plugin update deletes the plugin root of the version a session started on; this skill stays readable at `<plugin data>/versions/<version>/skills/squeal/`, the path the SessionStart message names.

Squeal runs this repository's tests in the background after every edit. It reports only changes, in messages that start with `SQUEAL ·`: a check that went `PASS -> FAIL`, `FAIL -> PASS`, or failed differently. It covers what the SQUEAL primer lists from `squeal.config.json`: the Vitest tests, the node:test tests of the `nodeTest` projects, the pytest tests of the `pytest` projects, and the slow test files `slow` marks; a test file you add that matches them is picked up too. Typecheck, build and anything else the repository checks are yours to run.

## Steps

1. **Keep working, and read the reports.** Results arrive with your next tool call, as SQUEAL messages. No message means nothing changed, not that everything passes; where the primer says no test group runs after each edit, nothing ran: use `squeal run <group> <path>... --wait 60000`. Running the test files beside your edit to learn sooner duplicates what Squeal is already running. Done when you have read every FAIL in every SQUEAL message that arrived.
2. **On a FAIL**, read its first error line and location. When they are not enough, run the message's last line, `Full output: squeal why '<name>'`, for the full output and history. Squeal re-runs a new failure once on its own, but not one from a forced run (`squeal run --all --force`, `squeal warmup`, a re-run), one already re-run at the same inputs, a slow file's, nor any when more than eight eligible test files fail anew in one tier; a passing re-run arrives as a PASS with the line `Flaky: FAIL -> PASS under the same tracked inputs`. So rather than re-running such a failure yourself to see whether it is flaky, let that re-run answer. After your fix the recovery arrives as `FAIL -> PASS`. Done when each FAIL is fixed or you can say why it stays.
3. **Wait only when you need a result before your next step**; otherwise results arrive with your next tool call. For files you just changed, `squeal status --wait 60000 <path>...` gives the verdict of the test files they select. Before saying the task is done, run `squeal status --wait 60000`, or `--wait 120000` on a busy host: it returns once the test files your edits re-keyed have results, or one of their checks changed, but not for slow files (step 4); `squeal run --all --wait` is a full-suite checkpoint. Done when the last line gives a verdict, `Returned on quiet` or `Returned on news`; on a timeout, wait again.
4. **Before you say the task is done, make the evidence current.** Where `squeal.config.json` marks slow test files, the header's second line starts `Slow tier:`. If the last one says `Stop waits`, they are required once you edit: while one is not current, run `squeal run --slow --wait 60000`. Without `Stop waits`, say how many are not current. Claim slow tests pass only once it says every slow file is current. Done when no check of your edits is pending, the slow tier is current or counted, and every claim about tests matches a line of `squeal status`. When a check stays pending after you waited again, say it is pending: `Known failures: 0; not current: …` means "no known failures yet".
5. **Run tests yourself only** when a header says no daemon is validating, a result is unknown, or the repository's own gate (CI, a pre-commit hook, the task) requires a run. A SQUEAL line `No result for <path>: no test Squeal runs reads it` means the same for that file: run whatever tests it yourself. Done when the suites the primer does not list have run as the repository says; a gate the repository requires is still yours to run.

## Reading a header

The registration and Stop's report start with a header like `Revision 21 (changed src/math.ts): 40 current (34 tests, 6 test files loaded), 3 pending (3 tests), 0 stale, 0 unknown.`, naming the files changed since your last report: what changed, not what caused a failure, which may be any earlier edit or none of yours. Other SQUEAL messages carry the news, those files and non-zero counts only.

## Reference

- `references/reports.md`: when reports arrive and what every header count and line means: pending, stale, unknown, inherited, `git-ignored`, the slow tier, no daemon validating. Read it when a header says something the steps do not cover.
- `references/commands.md`: what `squeal status`, `squeal why` and `squeal run` print, what the last line of each wait means, what a path selects, and red/green through the wait. Read it when a command's output is not what step 3 or 4 expects, or before a red/green check.
- `references/policy.md`: an edit denied after a regression, a Stop that keeps you going or waits for the slow tier, and every key of `squeal.config.json`. Read it when Squeal denies an edit or blocks a stop, or before changing the config.

# Squeal setup

`squeal setup` decides what to ask and writes every file: the harnesses, the Squeal block in the instruction files, the gate lines that run tests, the slow test files, the suites that test a build output, Codex trust. You ask the user its questions and pass the answers back as flags.

In Claude Code `squeal` is on the Bash tool's PATH; if not, run `"${CLAUDE_PLUGIN_ROOT}/bin/squeal"`. In Codex it is not: run `node --disable-warning=ExperimentalWarning "<plugin root>/dist/cli/squeal.mjs"`, the plugin root being the directory that holds `skills/setup/`. Below, `squeal` means that command.

## Steps

1. **Read the plan.** Run `squeal setup --plan --json` for the ids the flags take, then `squeal setup < /dev/null` for the questions: with no terminal it prints each question with its choices, the default first, writes nothing and exits 1. Done when you have each question and the flag that answers it (table below).
2. **Ask.** Do not ask again what the user already said ("take the defaults", "no block"). Ask the warm-up question with step 4's note on where it runs, and add one for the launcher (step 5). When the plan's `squealMentions` names a line, that file already holds Squeal instructions outside the block: show the user that line with the block question, since a block would repeat them. Show the user the plan's `not run:` and `run twice:` lines, each with its fix: no question or flag covers them. With `AskUserQuestion` (an interactive Claude Code session), ask the rest at most four questions a round, the default first and marked so; it takes four choices, so name any further ones in the question for a typed answer. Without it (`claude -p`, `codex exec`, Codex), print the plan's summary and each question with its numbered choices, say the user can reply with answers or "defaults", and end the turn without writing anything. 3. **Apply** with `squeal setup --yes --no-warmup` and one flag per answer:

   | Question | Flag |
   |---|---|
   | Set up a harness here? | `--harness claude-code`, `--harness codex`: each one chosen; `--harness none` when none |
   | Write or upgrade the Squeal block? | `--block <file>` for each file written; `--block none` when none |

   | Codex trust | `--no-trust` when declined |

## squeal reach

`squeal reach` says what one edit of each file re-runs, from the stores. You ask for it; no message pushes it. It needs no daemon, runs no test, and writes nothing. Use it when you want to know why an edit re-runs much of the suite, or which change would cut that. Every number is relative to this repository's own suite, recorded seconds and edits.

```text
Reach: what one edit of each file re-runs, of 1490 test files and 6696 s recorded.
Edits: 1523 from 2026-10-06 to 2026-11-07, every worktree's watch revisions in which HEAD did not move, of files this worktree has.

Files, by avoidable seconds per edit, then seconds re-run:
  1. src/core/state/slow.ts
     re-runs 85% of the suite: 959 test files, 5692 s; 6 edits in the window re-ran 34152 s
     coverage: loaded only 41%, called 29%, not loaded 25%, outside the test's process 5%; avoidable 3700 s
     paths: barrel 80%, runtime read 20%
     gateway: barrel through src/core/state/index.ts, for example test/a.test.ts → src/core/state/index.ts → src/core/state/slow.ts
     suggestion: import src/core/state/slow.ts from its own path in the files that use it, or split src/core/state/index.ts

Files, by seconds re-run over the window's edits:
  1. src/core/state/slow.ts: 6 edits re-ran 34152 s, 5692 s each; avoidable 3700 s; rank 1 above
```

The first part ranks files by their avoidable seconds per edit: the seconds of test files that load the file through their imports, or through the setup files that run in each test's process, but call none of its functions, or do not load it at all. Setup reached from the config or a global setup file runs outside the test's process, and its seconds are never avoidable. Where coverage cannot tell (coverage off, or a runner such as pytest that gives no records), the seconds on import paths count instead, and the entry says `on import paths with called unknown`. Then it ranks by the seconds one edit re-runs. Files that share a gateway and the same test files are one entry, such as `11 files in src/core/types/ through src/core/types/index.ts`. Each entry gives the share of the suite, the edits in the window, the coverage split (`called`, `loaded only`, `not loaded`, `unread`, `no record`, `outside the test's process`, `unknown`; `unread` also means the record cannot tell the file's top level from a function that starts with it), the path kinds (`setup`, `declared input`, `child process`, `runtime read`, `direct`, `barrel`, `test helper`, `transitive`, or `import` while import chains are not stored), the gateway with one example chain, and one suggestion. The gateway is that of the route with the most avoidable seconds, when the file has one. A suggestion is evidence and an option, not an instruction: a barrel's file that exports no runtime value can leave the tests' closure with `export type *`; a test helper is worth splitting only when some test file that loads the file through it never calls it, so with none there is no suggestion. When the module that imports the file also imports many of its sibling modules, such as a factory that loads every runner, and a barrel or helper comes before it on the chain, the entry names it as a `second gateway` with its own suggestion, which counts the test files that load the file through that module and never call it; when every one of them calls it, there is no such suggestion. Tests that start the program from source (`child process`, `runtime read`) get a note when their seconds outweigh the import seconds: Squeal re-runs them by design, and their seconds are never avoidable. A second, short list ranks the same entries by the seconds the window's edits re-ran, with each entry's rank in the first list; with no edits recorded yet, as in a repository that just installed Squeal, it says so in one line and ranks nothing. The last part ranks test files by avoidable pair-seconds: a test file's seconds times the source files it loads on import paths and never calls (`avoidablePairSeconds`), with the direct import that brings in most of the uncalled files.

`squeal reach <path>...` gives those files or directories in full: each path kind and gateway with its test files, their seconds and coverage, and one chain. Each list lists 10 entries and says how many more there are; `--limit <n>` lists `n`. In the named view, it bounds the routes of each file and the test files of each route the same way. `--json` gives every entry in a versioned object (`v`, `history`, `suite`, `window`, `coverage`, `absent`, `files`, `byEdits`, `testFiles`, `named`, `proposals`), or `--limit` entries when given. The lists hold only paths this worktree has: files of other worktrees or commits that tests read at run time are left out, and one line counts them (`absent`). Edits count only the paths this worktree has.

While no daemon has listed this worktree's test files, the whole answer is a proposal: `squeal start`, which lists them and looks up the results stored for their inputs in any worktree of the repository; under the default `baseline.onStart` it runs no test. With test files listed and no recorded result, the whole answer is `squeal warmup`, how many test files it runs, and its cost, about one run of the whole suite. Test files with no recorded seconds are left out of every share, and the report counts them. With coverage off, `called` reads `unknown`: the path kinds are only a proxy. The report then proposes the `squeal.config.json` key and `squeal warmup`, with the cost: every Vitest and node:test file runs once more, and each later run takes about a tenth more CPU. When some test files have no coverage record at their current inputs, it gives their share and names them: `squeal retry <test file>...` runs once each one that has no result at its inputs; a current result is re-run only by `squeal run --all --force`, which re-runs every test file, about one run of the whole suite. It never starts a run or changes the configuration. Exit 0 with an answer, the proposal included; 1 when there is no store; 2 on a usage error.

/**

export function primer(
  command: string = SQUEAL_COMMAND,
  coverage: Coverage = DEFAULT_COVERAGE,
): string {
  const names = runnersOf(coverage).map((runner) => runner.name);
  const groups = coverage.groups;
  // Spec 019 D6 (row 019-16): with check groups, the moments sentence says when each runs.
  const when = groups === undefined ? " after each edit" : "";
  // Row 019-49 (D6): with no test group at `edit`, silence between edits is not a pass.
  const quiet = groups?.noTestsAtEdit === true;
  // Review 0.1.411, B1: where D6's clause leaves no rendering within the cap, the same folds
  // run again with a compact clause that keeps the warning and is shorter than the edit one.
  const arrivals = quiet
    ? [
        ", but no test group runs after each edit, so silence between edits is not a pass; a SQUEAL message with your next tool call means a check changed;",
        ", but not after each edit, so silence between edits is not a pass; a SQUEAL message means a check changed;",
      ]
    : [
        `${when}; a SQUEAL message with your next tool call means a check changed, and passing results stay silent, so keep working;`,
      ];
  const most = Math.max(
    0,
    ...DESCRIPTIONS.map((runner) => projectsOf(runner.covered(coverage))?.length ?? 0),
  );
  let text = "";

        REVISION,
        covers,
        notCovered(coverage),
      ].join(" ");
    text = folded(sentences, coverage, most);
    if (text.length <= PRIMER_CAP_CHARS) return text;

/**
 * Fold the runners' projects first, then name the CLI less, until the primer fits;
 * the path wait joins only where it fits without folding more (task 005-68). Before the
 * CLI goes unnamed, the wait sentence drops its example, so a long CLI is still named at
 * the wait (task 004-78: a 217-character Codex CLI went unnamed and agents ran a bare wait).
 * Over the cap at every fold, the last one tried.
 */
function folded(
  sentences: (covers: string, naming: Naming, wait: WaitForm) => string,
  coverage: Coverage,
  most: number,
): string {
  let text = "";
  for (const naming of ["every", "first", "none"] as const) {
    for (let node = most; node >= 0; node--) {
      text = sentences(coversSentence(coverage, node), naming, "plain");
      if (text.length > PRIMER_CAP_CHARS) continue;
      const paths = sentences(coversSentence(coverage, node), naming, "paths");
      return paths.length <= PRIMER_CAP_CHARS ? paths : text;
    }
    if (naming !== "first") continue;
    for (let node = most; node >= 0; node--) {
      text = sentences(coversSentence(coverage, node), naming, "short");
      if (text.length <= PRIMER_CAP_CHARS) return text;
    }
  }
  return text;
}

/**
 * Spec 005 D6 as amended by the human (2026-10-17, task 005-68, issue 18):
 * which wait applies when. A path wait for the files just changed, with its
 * verdict line; the pathless wait and `run --all --wait` before saying the
 * task is done. An agent that knew only the pathless wait reported waiting
 * on most of a suite other work had re-keyed. What a path selects (005-67) is the
 * skill's: the primer is at its cap. Where it does not fit, `paths` off
 * gives the sentence it replaced, so no primer says less than before it,
 * projects and the CLI's naming included (the 005 coordinator, 2026-10-17).
 * `short` is that sentence in fewer words, for a CLI too long for it, so the
 * CLI stays named at the wait (task 004-78). Row 019-49 (019 D6): with no
 * test group at `edit` (`quiet`), the path wait becomes the narrow run, since
 * a path wait does not start a file its group's moment holds.
 */
function waitSentence(command: string, naming: Naming, form: WaitForm, quiet = false): string {
  if (form === "short") {
    return `Wait only when you need a result, as before you finish: \`${command} status --wait 60000\`.`;
  }
  if (form === "plain") {
    const wait =
      naming === "none"
        ? "`status --wait 60000` on the CLI SQUEAL messages name"
        : `\`${command} status --wait 60000\``;
    return `Wait only when you need a result before your next step, for example before saying the task is done: ${wait}.`;
  }
  // A Codex CLI is a long path: named in full once, as the path wait; unnamed, said once, up front.
  const full = naming === "every" && command === SQUEAL_COMMAND;
  const cli = (sub: string, first: boolean) =>
    naming !== "none" && (first || full)
      ? `\`${command} ${sub}\``
      : naming === "none"
        ? `\`${sub}\``
        : `the CLI's \`${sub}\``;
  const on = naming === "none" ? ", on the CLI SQUEAL messages name" : "";
  const finish = `before you finish, ${cli("status --wait 60000", false)} or a checkpoint, ${cli("run --all --wait", false)}.`;
  // Row 019-49 (D6): with no test group at `edit`, the path wait is the narrow run.
  if (quiet) {
    return `Before you rely on a result for files you changed${on}: ${cli("run <group> <path>... --wait 60000", true)}; ${finish}`;
  }
  return `Wait only when you need a result before your next step${on}: ${cli("status --wait 60000 <path>...", true)} for the verdict on files you just changed; ${finish}`;
}

/** D6's words for a moment, as the agent meets it; a `manual` group's clause names its run instead. */
const AT: Readonly<Record<Exclude<CheckMoment, "manual">, string>> = {
  edit: "after each edit",
  pause: "between your turns",
  stop: "at Stop, and Stop waits for them",
  commit: "when you commit",

/**
 * Spec 019 D6 (row 019-16): one clause per moment that has groups, naming
 * them, then the command that runs one group now (D6 "Command"). The
 * default `tests` group is said with what it holds, once: its name is the
 * one status and `after` use. For example: `Check groups: unit and tests
 * (the test files no group selects) after each edit; e2e at Stop, and Stop
 * waits for them; lint when you commit; parity waits for `squeal run
 * parity`; `squeal run <group> --wait 60000` runs one now.`
 */
function momentsSentence(command: string, naming: Naming, groups: GroupsCoverage): string {
  // A Codex CLI is a long path: named in full only where it is `squeal`, as the retry sentence does.
  const cli = (sub: string) =>
    naming === "every" && command === SQUEAL_COMMAND
      ? `\`${command} ${sub}\``
      : `the CLI's \`${sub}\``;
  const clauses = groups.moments.map(({ at, names }) => {
    const named = listed(
      names.map((name) => (name === "tests" ? "tests (the test files no group selects)" : name)),
      "and",
    );
    if (at !== "manual") return `${named} ${AT[at]}`;
