## Blockers

### B1. Proven: the e2e timeout reports the installer as Pi

Locations: `test/helpers/pi-wake-trace.ts:128`, `test/e2e/pi-fixture.ts:215`, `test/e2e/pi.test.ts:198`.

The brief requires the timeout to print the waiter's owning process, its PID and whether it lives. `PiE2E.run` passes the trace environment to `runPi`, which first runs `pi install` with that environment and then starts RPC Pi. Both are sibling child processes. The preload's owner variable is set inside each child, so each records a main-thread `start` in the same trace file. `describeTimeout` selects the first such record. That record belongs to the completed installer.

Independent proof: `pnpm exec tsx /tmp/00930-review-probe.mts` called the real `runPi` with an empty local Pi package, `trace.env`, one RPC prompt and a fake response. It then called `describeTimeout` on that trace. Output:

```json
{"proof":"installer selected as Pi","runExit":0,"processStarts":[{"pid":4191739,"command":"install"},{"pid":4191815,"command":"--no-context-files"}],"rpcPid":4191815,"reportedPid":4191739,"reportedInstallerAsPi":true}
```

The report selects PID 4191739 even though the `agent_settled` event identifies RPC Pi as PID 4191815. During an arm timeout it would say Pi is not running and exited with code 0 while the actual Pi can still be alive. Its arm summary also reads records across process owners. The stand-in test covers a descendant Node child, which inherits the owner and stays out; it does not cover these sibling launches.

Fix, one worker: distinguish installation from the actual Pi run in the test-side trace. Select the actual Pi owner and restrict its worker/event/exit records to that PID. Add a regression that runs an install followed by a still-live RPC process and forces only the helper's timeout. Assert the reported PID is the RPC PID, not the installer. Keep the fixture's optional-env contract.

### B2. Proven: timeout output prints home paths from raw stderr

Locations: `test/helpers/pi-trace-preload.mjs:57`, `test/helpers/pi-wake-trace.ts:156`, `test/helpers/pi-wake-trace.ts:104`.

The review brief requires that no secret or home path can reach a CI log through the printed facts. The wave brief says to write `~` for a home path. The preload copies stderr verbatim. The renderer prints its last 2,000 characters verbatim. A stack trace from the enabled `SQUEAL_DEBUG_CONTEXT` path can contain absolute repository or dependency paths under a home directory. The probe-error branch also renders arbitrary error text unchanged. Truncation and indentation do not sanitize either path.

The same throwaway probe passed a synthetic stderr record containing a fabricated home path and a fabricated `token=` value to the real renderer. It printed only these booleans, never a real credential or private path:

```json
{"proof":"raw diagnostic text reaches report","syntheticHomePathPrinted":true,"syntheticSecretPrinted":true}
```

This proves the new renderer has no redaction at that boundary. It does not claim that a real credential was present: `runPi` uses an isolated environment and a fake provider. The home-path disclosure alone breaks the requested output contract.

Fix, one worker: apply a single test-side safe-output policy to stderr, probe errors and other free-text diagnostics before rendering them. Normalize home paths to `~`. Retain only safe diagnostic text or redact sensitive values, including across stderr chunk boundaries. Add forced-timeout tests for a stack path and synthetic sensitive text. Keep the useful error kind and arm timing. Do not collect credentials to build a redaction list.

### B3. Proven: a worker terminated by the host has no recorded exit

Locations: `test/helpers/pi-trace-preload.mjs:61`, `test/helpers/pi-wake-trace.ts:143`.

The brief requires the waiter's exit code or signal and the times of each step. The research specifically names host deadline misses and worker replacement as possible causes. The preload observes `process.on("exit")` inside the worker. `Worker.terminate()` can stop that worker without running this listener. The timeout then prints that the waiter started, with no evidence of its termination or exit code.

Independent proof: `pnpm exec tsx /tmp/00930-review-terminate.mts` launched Node with the actual preload, started a worker, waited for a ready message, and awaited `worker.terminate()`. The host observed exit code 1. The trace contained a start and no worker exit:

```json
{"proof":"terminated worker diagnostic","termination":{"workerTerminatedWithCode":1},"starts":1,"workerExits":0,"printedExit":false,"traceKinds":["start","worker-start","worker-out","exit"]}
```

The existing helper test uses `process.exit(3)` inside its worker, so it does not cover this path. The product host's existing discard path uses `dead.terminate()`; this is a relevant failure mode, not an unrelated worker API exercise.

Fix, one worker: observe the worker's exit/error from the parent side in the test preload, with its owner PID and thread identity. Preserve the worker's original event delivery and reference state. Force a helper timeout after a host termination and assert the exit code and time appear. Keep an explicit unknown state for a process killed by a signal when no signal was observed; do not infer a signal from a missing record. No product change is needed to observe the host's worker exit event.
