# Research: Pi extension events for the Squeal adapter

Board row 009-01. Pi `@earendil-works/pi-coding-agent` 1.0.4, run 2026-10-14 on this host as the throwaway user `squeal-e2e`, with `PI_CODING_AGENT_DIR` redirected to a scratch directory, a scripted fake provider (`pi.registerProvider`, no credentials) and `PI_OFFLINE=1`. Probes and condensed logs: `probes/pi-extension-events/` (`results/<scenario>.txt`). Compared against spec 001 D9 and spec 002 D3.

## Questions answered

| # | Question | Short answer | Tag |
|---|---|---|---|
| 1 | Events and payloads | One order in `-p`, `json`, `rpc` and the TUI: `session_start` › per prompt `input` › `before_agent_start` › `agent_start` › per turn `turn_start`, `context`, provider request, per tool `tool_execution_start` › `tool_call` › `tool_result` › `tool_execution_end`, then `turn_end` › `agent_end` › `agent_before_settle` › `agent_settled` › `session_shutdown`. No event carries a session id: `ctx.sessionManager.getSessionId()` does. There is no run id. The `bash` tool sees `PI_SESSION_ID`, `PI_SESSION_FILE`, `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL`, `AI_AGENT=pi`, `PI_CODING_AGENT=true` and Pi's own environment. | verified by experiment |
| 2 | Mid-turn injection | Four surfaces reach the next request of the same run: `tool_result` content, a `turn_end` `custom_message` entry, `pi.sendMessage` with `steer`, and `context`. `turn_end` fires once per assistant message after every parallel result, so it is the batch boundary. `steer`, `followUp` and queued steers cost extra model requests. | verified by experiment |
| 3 | Deny | `tool_call` `{block, reason}`: the model gets an error tool result whose text is the reason, and the run continues. Writers: `edit`, `write`, `bash`. Extension tools keep their own names, MCP tools are `mcp__<server>__<tool>`, a package can replace `bash` itself. A throwing `tool_call` handler blocks the tool. | verified by experiment; read in docs and source |
| 4 | End of run | `agent_before_settle` with `continue: true` costs exactly one model request in `-p`, `json` and `rpc`; a silent handler costs nothing. Pi has no loop guard. RPC `abort` and TUI Escape skip `agent_before_settle`. Stdin EOF mid-run fires it after `session_shutdown`, and a continuation then still calls the model. | verified by experiment |
| 5 | Primer | A `before_agent_start` section (`systemPromptOptions.sections.squeal`) is in every request, survives compaction, is stored once per session, and passed at 200,000 characters. The alternatives are CLI-only, user-owned, accumulating, or load-on-demand. | verified by experiment |
| 6 | Failure modes and cost | Throws are reported and the run goes on. There is no timeout: a hung `tool_result` handler stalls the run for good, and `abort` does not recover it. A socket `error` with no listener crashes Pi. A socket left open keeps `pi -p` alive. Trivial handlers cost nothing measurable; a unix-socket round trip in `tool_call` and `tool_result` adds about 0.4 ms per tool call. | verified by experiment |
| 7 | Subagents and forks | Pi 1.0.4 has no built-in subagent. The shipped example spawns `pi --mode json -p --no-session`. That child process loads discovered extensions and has its own ephemeral session id. RPC `fork` and `new_session` rerun the extension factory in the same module, so module state survives, and they deliver `session_start` twice. CLI `--fork` is a new process with a new id. | verified by experiment; read in source code |

## Findings

**1. Events and payloads.** Recorded in `results/events-{print,json,rpc}.txt`; the TUI run has the same order (`results/tui.txt`). `session_start.reason` is `startup | new | resume | fork | reload`, and `session_shutdown.reason` is `quit | new | resume | fork | reload` (types in `dist/core/extensions/types.d.ts`). From `ctx` a handler gets the session id (UUIDv7), the session file (undefined under `--no-session`), `cwd`, `mode` (`tui | rpc | json | print`), `isIdle()` and `signal`. A run has no id. It spans `input`/`before_agent_start` to `agent_settled`. `turnIndex` restarts at 0 on every `agent_start`, including a settle continuation. `turn_end.messageEntryId` is a unique entry id. `tool_call` carries `toolCallId`, `toolName`, a mutable `input`, and `parentToolCallId` for nested calls. `tool_result` adds `content`, `details` and `isError`. `tool_execution_start` fires before `tool_call`. A `bash` command runs in the session cwd and inherits Pi's environment (a variable set on the Pi process reached it) plus the variables above, re-resolved per command (`docs/environment-variables.md`). `before_provider_request` did not fire because the fake provider does not call `onPayload`, so that event was not examined.

**2. Mid-turn injection.** Each surface was asserted by marker text in the fake provider's next request (`results/inject*.txt`, `parallel*.txt`):

| Surface | Next request? | Persisted as | Shown |
|---|---|---|---|
| `tool_result` returns `content` with text appended | yes, inside that tool result | the tool-result message | in the tool output, collapsed by default in the TUI |
| `turn_end` returns `entries: [custom_message]` | yes, after a turn with tool calls. On the final turn it waits for the next prompt unless `continue: true` | `custom_message` entry | TUI block headed `[customType]` (`results/tui-screen1.txt`); RPC `entry_appended` |
| `pi.sendMessage(…, {deliverAs: "steer"})` | yes | `custom_message` | as above |
| `deliverAs: "followUp"` | only after the run would end, and each adds one model request | `custom_message` | as above |
| `deliverAs: "nextTurn"` | held for the next user prompt, no extra request | `custom_message` | as above |
| `context` returns `messages` | yes, every request, rebuilt each time | not persisted | nowhere |

A custom message reaches the provider as a plain `user` message with the bare text. Pi adds no wrapper, so the text has user authority unless it names its source. With three parallel calls in one message, `tool_call` fired three times in message order before any result, `tool_result` three times in completion order (a 0.3 s `bash` came last), and `turn_end` once. Three steers queued in one batch were delivered one per request under the default `steeringMode: "one-at-a-time"`, which added two model requests after the model's final text (`results/parallel.txt`).

**3. Deny.** `deny_once` blocked the first `write` with a reason. The next request carried a tool result with `isError: true` and the reason as its text, and the second `write` in the same run succeeded (`results/deny.txt`). A blocked call fires no `tool_result` event. Its `tool_execution_end` has `isError: true`. A `tool_call` handler that throws also blocks: the model saw "probe throws in tool_call" as the tool error (`results/throw-toolcall.txt`, `docs/extensions.md` "fail-safe"). The built-in file writers are `edit` and `write`. `bash` (and `powershell`) can write anything. Extension tools fire `tool_call` under their registered names. MCP tools are `mcp__<server>__<tool>` (`docs/mcp.md`). Calls a tool makes through `ctx.executeTool` (codemode) fire `tool_call` with `parentToolCallId` (`docs/extensions.md`). Tool annotations (`readOnlyHint`, `destructiveHint`) are readable through `pi.getAllTools()`. The human's installed `@fractaal/pi-agentic-processes` registers its own `bash`, plus `bash_output` and `monitor_start` (read in its source), so a name alone does not say which implementation runs.

**4. End of run.** `settle_once` returned a `custom_message` and `continue: true` once. That produced exactly one more request carrying the text, then `agent_settled`, in `-p`, `json` and `rpc` (`results/settle-once-*.txt`). With no handler result: one request, no continuation (`settle-silent`). Entries without `continue` are persisted and seen at the next prompt (`settle-entry-only`). An unconditional `continue: true` looped through 2,716 requests in about two minutes until SIGKILL. SIGTERM did not stop it either, likely because the fake provider never yields to the event loop (inferred) (`results/settle-always.head.txt`). A continuation re-fires `agent_start` and `agent_end` but not `before_agent_start`. `agent_end` is notification-only and fires for every loop, including aborted ones. RPC `abort` and TUI Escape gave `turn_end` (outcome `aborted`) › `agent_end` › `agent_settled`, with no `agent_before_settle` (`results/settle-abort.txt`, `tui.txt`). Closing RPC stdin during a run fired `session_shutdown` first, then aborted the provider request, skipped `turn_end` and `agent_end`, and fired `agent_before_settle` with outcome `aborted`. Its continuation still sent a model request before `agent_settled` (`settle-eof.txt`, reproduced twice). The `turn_end` entries of an aborted turn are persisted and reach the next prompt.

**5. Primer.** In one RPC session (`results/primer.txt`), every request before and after a manual `compact` carried the `<squeal>` section, `--append-system-prompt` text, `AGENTS.md` (as a context file) and the skill's description. The skill body was absent: Pi lists only name, description and path (`docs/skills.md`). The section is stored once, in the session's single system message, and Pi sends deltas only when it changes. A 200,000-character section reached the provider unchanged (`primer-big`), so no Pi cap was observed below the context window. A `before_agent_start` `message` is persisted once per prompt and piles up (four copies after four prompts). `--append-system-prompt` is a CLI flag that Cezar already uses for its worker prompt (`cezarion/dist/core/pi-runner.js:605`). `AGENTS.md` is a user-owned file.

**6. Failure modes and cost.** A throw in `session_start`, `before_agent_start`, `context`, `tool_result`, `turn_end`, `agent_end` or `agent_before_settle` printed `Extension error (<path>): <message>` on stderr in `-p`. RPC emitted `{"type":"extension_error","extensionPath","event","error"}`, which Cezar turns into a note (`pi-runner.js:460`). Either way the run finished normally (`throw-*.txt`). Handlers are awaited in series, with no timeout. A 3 s `tool_result` handler delayed `tool_execution_end` by 3 s, and a 2 s `turn_end` handler delayed the next request by 2 s (`slow.txt`). A `tool_result` handler that never resolves stalled the run. `get_state` still answered, RPC `abort` got no response and did not unstick it, and closing stdin ended the process (`hang-rpc.txt`). Cost over 300 sequential `read` calls, three runs each (`timing.txt`), on a host loaded by other coordinators' evals:

| Handlers on `tool_call` and `tool_result` | ms between provider requests |
|---|---|
| none | 2.65, 3.09, 3.31 |
| trivial async no-op | 2.63, 2.79, 3.34 |
| one round trip each over a held unix socket | 3.14, 3.49, 3.75 |

A held socket is cheap but dangerous. `net.createConnection` to a missing or refused socket with no `error` listener crashed Pi with exit 1 on the unhandled `error` event, before any prompt ran (`dead-daemon.txt`). Pi isolates handler throws, not emitter errors. A socket left open after `session_shutdown` kept `pi -p` alive after its run until the peer closed, 120 s here (`socket-leak.txt`). Compare Codex, where a 2 s hook timeout bounds every call (002 D4). Pi gives no bound, so the extension must bound itself.

**7. Subagents and forks.** Pi 1.0.4 ships no subagent tool. `CHANGELOG.md` mentions only "the subagent example", and the installed Superpowers extension says "Pi does not ship a standard subagent tool". `examples/extensions/subagent` spawns `pi --mode json -p --no-session [--model] [--tools] [--append-system-prompt]` with the parent's environment. A nested `pi -p --no-session` run from the parent's `bash` loaded the probe from the agent extensions directory as a separate process. It had its own session id, `PI_SESSION_FILE` unset, and its `bash` saw its own `PI_SESSION_ID`, not the parent's (`nested.txt`). Extensions passed with `-e` are not inherited. The human's `~/.pi/agent/settings.json` has the keys `compaction`, `defaultModel`, `defaultProvider`, `defaultThinkingLevel`, `enabledModels`, `packages`, `steeringMode`; values were not read. The installed package directories are Superpowers, apptension `toolkit-dev` and `@fractaal/pi-agentic-processes`, and none of them registers a subagent tool (their `package.json` and extension sources were read). Cezar passes `--exclude-tools subagent` and maps `Subagent`, `SubagentSupervisor` and `SubagentWait` (`pi-runner.js:611-640`), so it expects some package to provide one. On forks and replacement (`sessions-rpc.txt`, `fork-rpc.txt`, `fork-cli.txt`): RPC `new_session`, RPC `fork` and a command's `ctx.newSession()` each fire `session_shutdown(new|fork)`. The default factory then runs again in the same module instance (a module-level counter went 1, 2, 3; the module was not re-imported), followed by `session_start(new|fork, previousSessionFile)`. Over RPC, `session_start` arrives twice for one replacement, because `rpc-mode.js` rebinds after `runtimeHost.newSession()` has already rebound (`dist/modes/rpc/rpc-mode.js:225-227, 334-339`, read in source code). `withSession` receives a context bound to the new session. CLI `--fork <file>` is a new process with a new id, `session_start` reason `startup` and the header `parentSession` set. `--session` and `--continue` keep the id with reason `startup`.

## Recommendation for Squeal

- Consumer key: `ctx.sessionManager.getSessionId()`, read on every `session_start` (its reason says whether the session was replaced) and on each event, never cached across `session_shutdown`. Registration must be idempotent, because RPC replacement delivers `session_start` twice. A subagent is a separate Pi process with its own id. If it loads Squeal, it is simply another consumer, and the parent cannot tell.
- Push: `turn_end`, returning one `custom_message` entry with the delta (customType `squeal`, `display: true`), without `continue`. It fires once per assistant message after all parallel results, is persisted, and shows in the TUI and on the RPC stream. It is 002 D3's PostToolUse and 001's PostToolBatch in one. Do not use `steer` or `followUp`: they add model requests. The text must name Squeal, since it arrives as a user message.
- Deny: `tool_call` on `edit`, `write`, and on any tool not annotated `readOnlyHint` where the policy asks, returning `{block: true, reason}` once per regression, as 002 D3 does. Leave `bash` unblocked. Never throw in `tool_call`.
- End of run: `agent_before_settle`. Return `continue: true` plus the entry only when there is news, `outcome === "completed"`, the session has not shut down, and Squeal has not already continued this run. Squeal owns that flag, the analogue of `stop_hook_active`, cleared at `input`. Otherwise return nothing, at no cost. Abort runs no settle, so treat `agent_end` with an `aborted` turn as 002's `Interrupt`, the end of the turn.
- Primer: a short `systemPromptOptions.sections.squeal` set in `before_agent_start` every run. It reaches every request including after compaction, costs no transcript growth, and needs no user-owned file or CLI flag.
- Never block: every daemon call in a handler needs an `error` listener, a timeout (001 D9 uses 100 ms) and `unref()`. Any socket must close in an idempotent `session_shutdown`. Reading the store with no held connection, as the Claude Code hooks do, avoids both the crash and the leak. Its per-call cost in Pi was not measured here.
- A board row's done-when: a fake-provider probe like this one asserts each delivery in the next request, a deny then continue, one continuation and then silence, the primer after compaction, and a dead daemon without a crash.

## Open questions

- Whether a real model treats a `custom_message` (bare user text) as Squeal's report rather than a user instruction is a dogfooding question.
- `turn_end` with `continue: true` on a final turn, and a hang inside `tool_call` under abort, were not tested.
- Whether `session_shutdown` fires on TUI Ctrl+D, SIGHUP or a kill belongs to the sibling topic. Incidentally, killing the tmux server after two Ctrl+C presses gave no `session_shutdown`.
- The doubled `session_start` over RPC, and the settle continuation that runs after `session_shutdown`, look like Pi bugs. Squeal should not depend on either being fixed.
