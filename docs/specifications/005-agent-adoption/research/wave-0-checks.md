## 1. Skills in Codex and Claude Code

- **Codex name.** A plugin's skills are listed "prefixed with plugin_name:" (developer instructions in `core/tests/suite/snapshots/..._astra_plugin_refresh.snap`). The namespace is the manifest `name` (`utils/plugins/src/plugin_namespace.rs`). cx1 listed `squeal:squeal — r1/squeal/0.1.131/skills/squeal/SKILL.md`. So D3's skill is `squeal:setup`. *verified by experiment, read in source code*
- **Codex invocation.** The docs say: "run `/skills` or type `$` to mention a skill" (learn.chatgpt.com/docs/build-skills). The mention sigil is `$`, and `:` is a name character (`skills/src/mentions.rs:226`). cx2's prompt began `$squeal:squeal`. Codex injected `<skill><name>squeal:squeal</name><path>/tmp/…/squeal/0.1.131/skills/squeal/SKILL.md</path>…` into the turn. *verified by experiment*
- **Codex finds the CLI.** The skills list gives each file through a roots table (`r1` = the plugin cache), and a mention gives the absolute path. In `fx/plain` (no Squeal config, so no primer), `command -v squeal` exited 1 (cx1). cx2 derived the root from the skill path and ran `node --disable-warning=ExperimentalWarning "/tmp/wave0-checks/codex/plugins/cache/hearsay/squeal/0.1.131/dist/cli/squeal.mjs" --version`, which printed `0.1.131`. The shipped skill's own rule produced that command: "the plugin root being the directory that holds `skills/squeal/`". *verified by experiment*
- **Claude Code finds the CLI.** "Files here are on the Bash tool's `PATH` while the plugin is enabled" (plugins-reference, Standard layout). Skill bodies also get `${CLAUDE_PLUGIN_ROOT}` substituted (same page). In `fx/plain`, cc1c ran `command -v squeal`, which gave `…/cache/hearsay/squeal/0.1.131/bin/squeal`, and `squeal --version` printed `0.1.131`. Its hooks printed nothing in that repository. The skill is `squeal:squeal` in `slash_commands`. *verified by experiment*
- **Claude Code question tool.** Under `-p`, `AskUserQuestion` is absent from the init event's 21 tools, inside the skill too. The model wrote `unasked` (cc2). Interactively in tmux, `/ask-probe` showed "Which colour should I use? ❯ 1. red 2. blue 3. Type something.", and the answer went back to the skill: `colour.txt` held `red` (cc7b). *verified by experiment*
- **Codex question tool** (not asked, but D3 step 3 interviews in both harnesses). `request_user_input` is offered only in Plan collaboration mode. Default mode needs `default_mode_request_user_input`, "UnderDevelopment", off (`tools/src/tool_config.rs:17`, `protocol/src/config_types.rs:700`, `features/src/lib.rs:1625`). No session tested it. *read in source code*

## 2. Shell tool timeouts

- **Codex.** `unified_exec` is Stable and on by default (`features/src/lib.rs:991`). `exec_command` takes `yield_time_ms` (default 10,000 ms, `handlers/unified_exec.rs:62`; clamped to 250 to 30,000 ms, `unified_exec/mod.rs:73-77`) and `timeout_ms`. In interactive mode `timeout_ms` is ignored: `ExecCommandLifetime::Interactive => None` (`handlers/unified_exec/exec_command.rs:313`). After the yield the process keeps running under a session id. `write_stdin` polls it, up to `background_terminal_max_timeout`, which defaults to 300,000 ms and can be configured. Only the one-shot fallback kills, at `timeout_ms` (default 10 s, no maximum found), and only managed requirements turn it on (`spec_plan.rs:1108-1116`). *read in source code*
- **Measured** (cx3, `logs/sessions-extract.txt`). Luna ran `date; sleep 75; date; echo finished` through code mode's `exec` tool. It called `exec_command({…, yield_time_ms:30000})`, which returned after 30.2 s with `SESSION_ID=65912`. Then `write_stdin` with a 30,000 ms yield, twice: 30.0 s with no output, then 11.3 s with `finished`. Exit 0, not killed. *verified by experiment*
- **Claude Code.** `BASH_DEFAULT_TIMEOUT_MS` defaults to 120,000 and `BASH_MAX_TIMEOUT_MS` to 600,000 (env-vars docs). A wait longer than 2 min needs the model to pass a larger `timeout`. *read in official docs*

So D5's `<ms>` has a hard bound only in Claude Code: under 120 s, unless the gate also has the model set the Bash timeout, and 600 s at most. In Codex any `<ms>` runs to the end. Each 30 s costs the agent one more poll turn.

## 4. `install.sh`

- **Hosting.** `hearsay-tools/squeal` is public: the API says `"visibility": "public"`, and anonymous `raw.githubusercontent.com/hearsay-tools/squeal/squeal--v0.1.131/README.md` returns 200 (`Cache-Control: max-age=300`). The hub `hearsay-tools/marketplace` is private: the API says `"private": true`, and anonymous requests to `github.com/hearsay-tools/marketplace` and its raw `main/README.md` return 404. So the hub cannot serve `curl … | sh` to anyone without access. The repository has no GitHub Releases (`releases?per_page=3` is empty, and `releases/latest/download/install.sh` returns 404). Its newest tags are `squeal--v0.1.131`, `squeal--v0.1.124` and `squeal--v0.1.121`. Fetched 2026-10-13 through this host's proxy (anonymous checks with `GH_TOKEN` unset). *verified by experiment*
- **The same fact reaches step 2.** `claude plugin marketplace add hearsay-tools/marketplace` clones a private repository, so it fails for a user without access. *inferred from the 404; not run against github.com*
- **`curl | sh`, measured** with this probe's own scripts on 127.0.0.1 (`logs/q4-curl-sh.log`):
  - A `read` in the script reads the script. In an 80 KB script, dash's `read` got `d 249 ......`, the middle of a later line (A2). bash's `read` took the next line whole, so that line never ran (A3). A small script was buffered whole, and `read` got EOF (A).
  - A cut download runs a prefix. A top-to-bottom script ran steps 1 and 2, then stopped on `Syntax error: Unterminated quoted string`, exit 2 (B). The same steps inside `main() {…}; main "$@"` ran nothing: `end of file unexpected`, exit 2 (C).
  - A 404 with `curl -f` runs nothing and the pipeline exits 0 (D). Exit 22 comes only under `bash -o pipefail` (D2), which POSIX `sh` lacks.
  - Under a pipe, `[ -t 0 ]` is false. `/dev/tty` is open from a terminal (E2) and absent without one (E). Arguments pass with `sh -s -- --uninstall --yes` (F).
- **Prior art.** beads' `scripts/install.sh` (`steveyegge/beads` at `f21e3a8`, read and not run) is bash with `set -e` and `main "$@"` as its last line. It is served unpinned from `main`, and it uses `sudo` for `/usr/local/bin`. *read in source code*

## 5. Scopes and versions in Claude Code

- **User scope satisfies project enablement.** `fx/enabled` commits `{"enabledPlugins": {"squeal@hearsay": true}}`, and the plugin was installed only at user scope. `claude plugin list` shows `✔ enabled` with the user entry `true`, absent, or `false`. With `false` it adds "Disabled in ~/.claude/settings.json but still loads — project settings enable it" (`logs/q5-list.log`). cc4, with the user entry absent, loaded `squeal@hearsay` 0.1.131 from the user install, with `squeal` on PATH. Docs: a project-only `true` fetches nothing that is not installed ("is enabled in project settings but isn't installed here", plugins/loading), so an install at any scope is what counts. *verified by experiment*
- **Side finding.** With the user entry removed and no project entry, the plugin did not load in `fx/plain` (cc1b, plugin list empty), although the docs say `defaultEnabled` defaults to `true`. *verified by experiment*
- **Which version a session loads.** The user install was 0.1.131 (installed first) and the project install in `fx/enabled` was 0.1.132 (`installed_plugins.json` holds both, `logs/q5-project.log`). cc5 in `fx/enabled` loaded **0.1.131** (init `plugins`, and `squeal --version`). With the two array entries swapped and timestamps unchanged, cc6 loaded **0.1.132**. So the session takes the first applicable entry in array order, not the project scope or the newest install. The docs do not say this (plugins/loading, fetched 2026-10-13). Not tested: three entries, a project entry for a parent directory, or whether `claude plugin update` reorders entries. *verified by experiment*
- **The launcher.** D3's rule ("a project-scope entry for the working directory first, then user scope", 005-05's `resolve.mjs`) runs 0.1.132 where cc5's session ran 0.1.131. Between harnesses: a newer hook steps an older daemon down, and an older hook never replaces a newer daemon (001 D10, measured in 005-05 question 2). Since 001-199 the key holds a key-format version, so a mismatch costs a daemon restart, not a re-key. *inferred*

- **What the rules miss.** This repository's plugin bundles come from `build:plugin` (`tsx src/harness/*/build.ts`), which no build-script rule reads. The `files` entry `plugins` is the only evidence for them. Cezarion's root `test:e2e` is `sh .ai/scripts/e2e.sh`, which no static rule resolves. Its slow unmarked Vitest files (`src/workflows/monitoring-turn.test.ts`, `pi-teardown.test.ts`) are left to the warm-up's 30 s rule, as D3 plans.
- **The gitignored-directory rule fired for nothing.** Neither checkout had a build: there is no root `dist` here and no `packages/cezar/dist` there. Built, it would fire for `packages/cezar/dist` (9 of 13 e2e files name it, such as `'../../dist/application-update/service.js'`). It would also fire for `web/dist` (2 files; `package-cli.test.ts` requires `web/dist/index.html` in the packed tarball). Here it would fire for root `dist` on false hits: `plugins/codex/dist/cli/squeal.mjs`, and fixture `dist/cli.mjs` strings in 4 of 10 files. So it depends on whether the worktree is built.
- **"The broader directory" is undefined for siblings.** `dist` against `plugins`, or `dist` against `web/dist` against `scripts`, are not nested.

## Recommendation for Squeal

- **005-19, the skill.** Name it `setup` in both plugins: `/squeal:setup` and `$squeal:setup`. Find the CLI with `squeal` in Claude Code (`bin/`, or `${CLAUDE_PLUGIN_ROOT}/bin/squeal` in the body). In Codex, use `node "<plugin root>/dist/cli/squeal.mjs"`, the root being the directory above `skills/setup/`, as `skills/squeal` already says. Interview with `AskUserQuestion` only in an interactive Claude Code session. Under `-p`, and in Codex outside Plan mode, print the plan and the questions and end the turn, as D3 says.
- **005-12 and D5's `<ms>`.** In Claude Code keep `<ms>` under 120,000, or have the reworded line also tell the model to set the Bash timeout, up to 600,000. Codex needs no bound. Say in the gate that the command keeps running and must be polled.
- **005-12, the slow and artifact candidates.** Count a node:test project as a slow candidate only when another rule agrees, or ask about it with "not slow" as the default: the cezarion `test/unit` case. Do not rank artifacts by the number of evidence lines: here the wrong `dist` had three and the right `plugins` one. Ask once per candidate directory with its evidence, or offer the union. Treat `files` entries as weak evidence, since they list sources (`scripts`) beside artifacts. Run the gitignored rule against `bin`/`exports`/`outDir`/`files` targets even when absent, and say "not built in this worktree".
- **005-14, `install.sh`.** Host it in this repository. Link it at a release tag, `https://raw.githubusercontent.com/hearsay-tools/squeal/squeal--v<version>/install.sh`, so what a user reads is what runs. The README's download, read and run steps carry the same URL. Write it as POSIX `sh` with `set -eu`, every step inside `main`, and `main "$@"` as its last line. Never `read` stdin. Take `--uninstall` through `sh -s -- --uninstall`. Expect a 404 to exit 0 silently under the pipe. Installing from the private hub is blocked first: see open question 1.
- **005-14, the launcher.** Follow Claude Code's rule rather than D3's project-first rule. Take the first entry of `installed_plugins.json["squeal@hearsay"]` that is user scope, or project scope for this working directory. When Claude Code and Codex hold different versions, run the newer one, because no hook of the older plugin can replace its daemon. Print both versions with `squeal update`.

## Open questions

1. **The hub is private.** Both `curl | sh` from it and `claude plugin marketplace add hearsay-tools/marketplace` fail for users without access. Making it public, or moving the marketplace files into this public repository, is the human's call.
2. How Claude Code orders `installed_plugins.json` entries after `claude plugin update`, with three entries, or with a project entry for a parent directory: not determined, untested.
3. Whether Codex's `request_user_input` works in Default mode with its feature flag on, and whether a `codex exec` turn ends its background `exec_command` processes: not determined, no session.
4. Whether `defaultEnabled: true` should load a user-scope plugin whose `enabledPlugins` entry was removed (cc1b did not load it): docs and behaviour disagree at 2.1.296.
