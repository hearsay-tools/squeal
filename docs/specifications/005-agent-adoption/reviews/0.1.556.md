## B1. Proven, blocking: Pi can lose every primer when the store appears after run start

Changed locations: `src/harness/pi/worker.ts:35`, `src/harness/shared/owed.ts:41`, `src/harness/shared/deliver.ts:74`.
Consumer path: `src/harness/pi/run.ts:33`, `src/harness/pi/extension.ts:176` and `:193`.

The review brief permits removing a duplicate primer at Pi's tool boundary, but requires: “confirm no path now has zero primers.” Spec 011 C8 also requires a first registration's primer. This path previously supplied it at the boundary.

1. A Pi session starts in a repository with `squeal.config.json` but no store. `startSession` ensures the daemon but returns no text while the store is absent.
2. The first `before_agent_start` happens before that daemon creates the store. `startRun` returns `{ primer: null, news: null }`. A fresh extension has `lastPrimer === null`, so it adds no system section.
3. The store appears before a later `turn_end` with tool results. This is the supported late-registration path: the tool boundary registers the consumer and returns its header and known failures.
4. The new harness-wide `registrationPrimer: false` makes `registerSaying` omit the primer. The boundary clears the owed registration after hand-over. The next boundary is silent.

Pi's `turn_end` handler returns message entries only. It does not install or refresh `lastPrimer`. `before_agent_start` runs at the user run's start, not after each tool batch. Thus there is no system-prompt copy beside this boundary's text, and the run continues with zero primers. This can occur on a new store or when a previously unreadable store becomes usable during the run. It does not require a killed start, artificial load or an expired consumer.

### Independent reproduction

An external Vitest file used the production `workerDeps`, `startSession`, `startRun` and `toolBoundary`, plus the existing `fakeRepo` and `squealRepo` fixtures. Its injected ensure returned immediately and created nothing. After the start and run calls, the test created the fixture store and seeded a known failure. This isolates store availability without starting or delaying a daemon.

The final probe also loaded `deliver.ts` and `owed.ts` from the base commit into external files. Relative imports were directed to the candidate's unchanged dependencies. Running the base boundary body through `withContext` returned a primer. The probe then removed that fixture consumer and ran the candidate boundary against the same store and failure.

Observed result:

```json

```

The final assertion required the candidate boundary to contain `PRIMER_OPENING`. It failed:

```text

expected 'SQUEAL · registered at revision 1\nRe…' to contain 'Squeal runs this repository\'s '
```

The returned registration contained the seeded `FAIL`. This is primer loss, not lost failure delivery or a silent hook error. The existing `registration-primer.test.ts:47` starts with a usable store and invokes the boundary directly. It proves absence from the boundary but does not establish that the run already received a system primer.

When no system primer was supplied, the first successful boundary registration must carry a fallback primer, or the adapter must supply the system primer before the next model request. Keep the normal successful run-start case at one primer. Do not restore unconditional duplication, change event deadlines, or treat daemon availability as proof that the host received a primer.

Add a regression for the complete event sequence: config without store, silent session start, run start with no primer, store creation, first tool boundary, next model request. Require a primer exactly once once registration becomes possible, a known failure delivered once, and no duplicate header at the next boundary. Retain the normal run-start/system-primer control and the killed or abandoned hand-over controls. Rebuild bundles in the coordinator's repair candidate.
