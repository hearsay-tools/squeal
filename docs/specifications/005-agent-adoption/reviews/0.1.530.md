## Blockers

### B1. Proven: late-state maintenance depends on whether this delivery may announce lateness

Locations: `src/core/delivery/edits.ts:143`, `:149`, `:156`, `:158`; `src/core/delivery/delivery.ts:346`, `:368`; `src/core/delivery/late.ts:108`.

Contract: wave 15 part 3, “A failure delivered during the delay ends the late state and no caught-up follows.” The same part requires one caught-up message after successful completion. Stop and the idle waiter must not announce either message; they still must maintain its state.

`lateNotes` is skipped when `boundary` is absent. Its `tell(failed)` is the only place that ends an open late state. `peek` does not read edit notes at all. Also, `editNotes` returns null at an unrefined revision with no counted files, even when a failure is about to be delivered. These paths acknowledge the failure but leave the late state open.

Proof, `pnpm exec tsx /tmp/squeal-review-530-probe.mts` (exit 0): use the same public store/sink/delivery setup as `test/delivery/late.test.ts`. Register with passing A and B. Edit A to key a2 and record its open re-key. Advance the clock 61 s and deliver the late notice. Leave A owed; fail B at its current key; deliver B through `onToolBoundary(C, {stop:true})` or `peek(C, {kinds:["pass-to-fail"]})`. Then finish A at a2. Both paths produce:

```text
FAILURE [ 'pass-to-fail' ]
NEXT SQUEAL · caught up at revision 1
Revision 1 (changed src/a.ts): the 1 test file your edits affect has run.
The 1 test file your edits affect has run at revision 1, with no new failure.
```

A normal non-Stop boundary has the same defect if a new revision is unrefined when B's failure is delivered: after refining it, the next boundary says caught up at revision 2.

The opposite failure uses the same missing state read: after late, let A pass and deliver an unrelated B recovery at Stop. `lateness` is null, so `ended` is true and `since` advances to 1. The late slot remains 1. The next boundary returns null because `revision <= since`; it can no longer deliver the caught-up notice it owes:

```text
STOP [ 'fail-to-pass' ]
NEXT null
STATE { late: '{"s1\\nmain":1}', edits: '{"s1\\nmain":{"since":1,"said":true}}' }
```

Fix scope: one delivery-state repair. Read and maintain the open late state independently of eligibility to emit late/caught-up text and independently of `readOwn` succeeding. Every delivered new failure must close it, including `peek`, Stop, idle delivery and an unrefined boundary. Other news must preserve its edit window until caught up can be said at a permitted boundary. Add public delivery regressions for the sequences above; keep Stop and idle text silent for late/caught-up.

### B2. Proven: the bound substitutes default tier size and file count for the scheduler's actual width

Locations: `src/core/delivery/late-timings.ts:24`, `:39`, `:62`; `src/core/delivery/late-bound.ts:50`.

Contract: approved design section 1 uses tiers of `runner.tierSize` and the runner's `tierWidth` in the scheduler's wall estimate. The done-when says results in normal time send nothing. The worker notes disclose this substitution; it is not safe to accept it as equivalent.

The hook always uses the default size 4 and width `tier.length`. Historical overhead makes the same width assumption using `run.durations.length`. Vitest can explicitly run at one worker: `src/runners/vitest/width.ts:13` returns 1 for ceiling 1. A configured policy can also have a different tier size.

Proof, `pnpm exec tsx /tmp/squeal-review-530-timings.mts` (exit 0), calling the real `tierWidth`, `wallEstimate` and `lateBoundMs`:

```text
WIDTH {
  runnerWidth: 1,
  schedulerBound: 80000,
  hookBound: 35000,
  actualNormalRunMs: 40000
}
```

Four measured 10 s files at one worker normally take 40 s. With no measured start or overhead, the approved bound is `2 * wallEstimate(40000, 10000, 1) = 80000`. The hook uses width 4, producing 35 s. It can therefore announce late during a normal run. Prior one-file runs with zero overhead do not compensate for this error.

Fix scope: one estimator-input repair. Supply the configured tier size and runner/project width, including serial runner parts, from facts recorded by their scheduler/runner owner. Use those inputs for both current tiers and historical overhead. Do not recover width by counting result rows. Add a one-worker Vitest case and a non-default tier-size case. Keep the hook's bounded read cost.

### B3. Proven: the 20-run window turns a later backlog start into the edit's first-start delay

Locations: `src/core/delivery/late-timings.ts:31`, `:35`, `:42`; `src/core/store/repos/runs.ts:66`.

Contract: approved design section 1 defines `start` as “edit to first start”, from recent edit runs. It is not elapsed time from an old edit to whichever backlog tier remains in the most recent 20 runs.

`recentTimings` limits by runs before `worktreeMedians` groups by revision. Once a revision has more than 20 completed tiers, its first start is absent. Taking the minimum of the remaining starts does not recover that fact. Backlog tiers retain the same revision (`src/core/scheduler/tiers.ts:196`).

The timing probe creates one watched revision at time 0, a completed 1 s file run starting at 1 s, then 20 completed runs of the same file/revision starting at 600 through 619 s. Each has its own stored result and a 1 s duration. Actual output:

```text
FIRST { startMs: 1000, overheadMs: 0 }
AFTER 20 LATER TIERS SAME REVISION { startMs: 600000, overheadMs: 0 }
PAST BOUND 10s AGE, 1s KNOWN FILE: expected true using first start 1s; actual false
```

The bound for a later edit of that 1 s file becomes 1,202 s instead of 4 s. Its machine and file timings did not become slower. The estimator silently lost the first-start fact, suppressing the required late notice.

Fix scope: one timing-sample repair. Preserve or query the actual first start per sampled edit revision before applying the sample limit. Keep later tier timings for overhead only. A checkpoint-null filter alone does not identify a first edit run. Keep the sample and hook work bounded; add a regression with more than 20 tiers at one revision and at least one subsequent edit.

### B4. Proven: the eval parser grades an explicit unknown caught-up result as pass

Location: `evals/lib/squeal-text.mjs:363`.

Contract: the brief requires parsers to round-trip real formatter outputs. Design section 4 requires the caught-up form with files that gave no result. Vision principle 2 forbids treating unvalidated state as a pass.

The new own-count parser hard-codes stale and unknown to zero. It does not read the unknown count in the caught-up sentence. Proof, `pnpm exec tsx /tmp/squeal-review-530-parser.mts` (exit 0): pass the real `formatDelta` output for `ownEdits: {files:1, owed:0}` and `caughtUp: {revision:7, files:1, unknown:1}` to `squealEvidence` as a PostToolBatch delivery, with zero preceding known failures:

`test/evals/own-count.test.ts` covers caught-up only with `unknown:0`, so the current green test misses this false pass.

Fix scope: one parser repair. Preserve the explicit unknown outcome in caught-up evidence, and do not infer that “all ran” proves every file has a result. Add the real formatter round-trip above with `unknown > 0`, as well as the ordinary news form after an unknown result. Keep no-count headers non-passing and retain support for old headers.

### B5. Proven: no-edit-group suppression applies only to the owed form

Location: `src/core/delivery/late.ts:158`.

Contract: the review brief says no late notice “with no test group at `edit`.” These groups intentionally wait for Stop, a commit or an explicit run.

`quietFor` checks `header.noTestsAtEdit` only when `late.kind === "owed"`. An unlisted or unread revision bypasses that condition.

Proof in the delivery probe: give the worktree this real policy before registration, with both listed test files under `src/**`:

```json
{"checks":[{"name":"unit","runner":"vitest","tests":["src/**"],"at":"stop"}]}
```

Record a watched edit, leave its revision unrefined and advance 61 s. `onToolBoundary` returns:

```text

```

This sends the new late notice even though its own real header says that no test group runs at edit. It also tells the agent that these files have not been queued as a result delay, although its policy intentionally postpones validation.

Fix scope: apply the no-edit-group suppression consistently to the late forms, while preserving status's unread/unlisted facts and existing liveness reporting. Add unlisted and unread delivery cases with the policy above. If the intended contract is instead the worker's narrower “no owed late” rule, that needs the coordinator's explicit amendment; this candidate has no such amendment.

## What fits

The recorded-but-unrefined same-call guard works in the existing test. The unrecorded same-call window remains the human's accepted limitation; this review does not claim to close it.
- A same-key confirmation run owes no new result. `edits-confirmation.test.ts` exercises the real ledger, rerun queue, sink and delivery in scheduler order. The re-key's open attribution ends on the first result at that key; a confirmation does not hide an outstanding edit key. Counting that file as run is correct. It does not claim that the confirmation passed.
- The news header's own set comes from the re-key record, not from the worktree's queue. A consumer with no counted edit gets no count; the parser's no-count case does not read as pass. The owed-counts exception remains. Full registration/Stop/status headers retain their existing counts. The old settled-line formatters are removed, and the shipped reports references describe the replacement. Old seed-copy drift disclosed in the worker notes predates this range.
- The new late sentences give the agent a named wait or a direct-test next step. Caught up states completion of the previously announced delay. New times use UTC. No new heartbeat or periodic clean message was added.
- The pure formula uses the scheduler's `wallEstimate`, one factor constant of 2, and median duration substitution. Its arithmetic examples pass. The faults are the inputs identified in B2 and B3.
- I would accept the `FEED_LATE_MS` stand-in when every timing input is zero, with an amendment: no measured baseline can distinguish a late result, and the existing 60 s change-feed interval is a startup fallback rather than a host-specific tuning. Likewise, the minimum for an unlisted revision avoids an immediate notice. This acceptance does not extend to the fixed width in B2.
- `RunRepo.recentTimings` is read-only, returns at most the caller's 20 runs, and reads per-run result durations through `results_by_run`. It excludes checkpoints, unfinished/crashed runs and other worktrees; the store test covers these filters and mixed test/file-check duration aggregation. Hook work can still grow with a run's result count and with the runs table scan. A read-only probe of this repository's live store found 16,125 run rows; the largest worktree had 1,164. Three calls returned 20 runs/1,007 file durations in 39.2, 25.4 and 20.5 ms. This does not show a 2 s hook-budget break. The query plan uses `runs_by_checkpoint` plus a temporary ordering tree; it is not an indexed top-20 lookup by worktree. Do not claim a constant scan cost.
- The two later commits add the requested prune validity case and explain it. The case calls the candidate's actual `recentTimings`; only a baseline without that method uses the independent row reader. It checks pruning, worktree isolation, checkpoint/running exclusion, order and limit, without changing production stored meaning. The separate store test covers duration aggregation. `test/keys/key-format.test.ts` is current/pass. `git diff 35b806131..HEAD -- src/core/keys/key-format.ts test/keys/validity/approved.ts` is empty: there is no `KEY_FORMAT_VERSION` raise and no `APPROVED_RAISES` entry.
