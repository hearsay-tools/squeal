## B1: proven, blocking. A failed clear is treated as a written clear, so Pi can still repeat the registration without a killed start

Location: `src/harness/pi/worker.ts:105`, `src/harness/pi/worker.ts:140`. Contract seam: `src/harness/shared/hand-off.ts:35`.

W1 says:

> The registration text reaches the session once; twice only when a start was killed between its output and its mark; never zero times.

The candidate waits on `handOff.sent()`. That promise resolves when the sent writes finish **or fail**. It deliberately never rejects. `HandedWrites` drops its pending state for either outcome and then starts the next handler. Therefore its completion does not prove that the registration clear is in the store.

Independent reproduction against the built Pi worker and a real daemon process:

1. Use `createFixtureRepo`, `spawnDaemon` and `waitReady` from `test/daemon/helpers.ts`, with `plugins/pi/dist/cli/squeal.mjs`.
2. Create the production `createDeliveryHost`. Its factory constructs a real `Worker` from `plugins/pi/dist/worker.mjs`, with the host's verdict slot and the fixture's environment.
3. Add a worker `message` listener in the factory, before the host attaches its listener. When request 1 posts its held start answer, send **SIGSTOP to the daemon only**. The host then receives the registration text and commits its verdict. No Pi session, start handler or delivery worker is killed.
4. Await the successful `start` answer. Immediately call `run` for that same session with the production 2,000 ms event deadline. Leave the daemon stopped until that call returns.
5. The start answer contains `registered at revision`. The run answer contains another `registered at revision`. It returns after **1,260 ms**, before the daemon resumes. Resume the daemon and clean up only after observing the result.

The write socket times out after its 1,000 ms bound. `HandOff.sent()` absorbs that failure, the gate opens, and `startRun` finds the old owed mark. A lease request to the stopped daemon also times out, so the hook can fall back to its direct store path and complete the replay. The host never reaches its event deadline. This is a duplicate with no killed start, not an unbounded wait or a missing registration.

Controls on the same built daemon path:

| Case | Next run | Time from request |
| --- | --- | --- |
| Gate removed from a temporary copy of the built worker; daemon resumed after 150 ms | Registration repeated | 164 ms |
| Candidate; daemon resumed after 150 ms | No registration repeated | 162 ms |
| Candidate; daemon killed at the held start answer | Registration repeated; call completes | 23 ms |
| Candidate; daemon remains stopped through the write deadline | Registration repeated; call completes before daemon resumes | 1,260 ms |

The successful-write repair is real. It does not cover the failed-write outcome required by the same once-only contract. The committed new tests release the daemon's pending clear or abandon the host verdict. Neither tests a committed verdict whose clear later fails.

Repair size: one Pi delivery worker task. Keep the distinction between text handed to the host and its clear persisted by the daemon. A failed clear must not let the same live worker replay a registration it knows it already handed over. Keep that suppression until the clear succeeds or that worker is lost; a lost start must still replay. If this needs a shared handoff outcome, change that interface explicitly and keep other prepared report kinds' failure behavior. Do not erase an owed registration before the host commits, and do not turn all failed reports into delivered reports.

Done when: a deterministic failed-clear test observes one registration across start and the next run with the same live worker, without exceeding the event deadline; the delayed-success and abandon/kill controls still pass. Exercise a tool boundary as the next request too, since it also reads an owed registration. Keep the idle waiter cancellable during the pending clear.

## S1: proven, nonblocking follow-up. OpenCode's separate bridge process does not remove the same race

Location: `src/harness/opencode/bridge.ts:220`, `src/harness/opencode/bridge-client.ts:145`, `src/harness/shared/owed.ts:49`.

The worker's reason for leaving OpenCode alone is not a correctness argument. A model round trip is a delay, not a write barrier. `handOver` settles the verdict without waiting for `handOff.sent()`. The bridge client resolves the held answer at the verdict. Its grace bounds the old process; it does not order a later bridge's reads after the daemon's write.

Independent deterministic probe used the real `register` and `after` handlers, `HandOff`, and `serveWrites` from `test/harness/daemon-writes-helpers.ts`. That helper serves the production daemon handlers and write desk over a real socket with a separate store connection; it does not launch a daemon process.

Register a fixture consumer with a handoff and verify its first header. Pause the daemon's writes, commit the handoff, and verify one held batch. Start `after` for a `read` tool before releasing that batch. Release after 100 ms. `after` returns another `registered at revision`. The next process can read the old owed mark before acquiring its write lease; a later successful lease does not undo that earlier decision to replay it.

Yes, a duplicate is reachable. It needs a separate OpenCode row. The row should order the next delivery's owed-mark decision after the prior accepted verdict's write, including a failed write, with the current hook deadlines. Test with two bridge processes and a held daemon clear. Appending an await inside the old bridge alone does not prove the required order while its client still resolves before that await completes.

This code is unchanged in the candidate. The brief asks for this judgment, but it is not a second blocker against the Pi row.
