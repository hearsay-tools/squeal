## B1. Proven, blocking: Pi and OpenCode can lose the registration and its known failure after the new early registration

Locations: `src/harness/pi/session.ts:43` and `:67`; `src/harness/pi/run.ts:39` and `:49`; `src/harness/opencode/bridge.ts:87`.

The review brief's decision C requires: “a boundary or prompt that finds the consumer registered with no mark delivers the registration text” and “Twice at worst ... never zero times.” Vision principle 1 also requires notification on the first observation of a failure.

Both adapters now commit registration before awaiting daemon startup. Unlike the shared Claude Code/Codex path, they register without `owesText` and never call `registrationSent`. Registration seeds the consumer view with the known failures. If its host kills it during `first.ensure()`, the view remains committed but the registration answer never reaches the host. Nothing records the lost answer.

Pi's next `before_agent_start` sees the consumer registered and calls `startTurn`; it returns no news because registration already seeded the failure. The next tool boundary also returns no news. OpenCode's next tool boundary likewise finds no delta and no owed registration. It can supply the system primer, but no failure text. A later OpenCode user message can retry registration; that does not deliver the missed failure at the first tool boundary.

The worker notes justify omitting the record because these adapters put the primer in the system prompt. That explains the primer's survival, but does not preserve the registration header or its known failures. The bug is introduced by moving registration ahead of the cancellable ensure; it is not a finding about pre-existing output handling.

### Independent proof

`pnpm exec tsx /tmp/review-541-other-kill.mts`, exit 0. The throwaway probe used production store, adapter and delivery APIs, with no product edits. For each adapter:

1. Create a private git-shaped worktree and store. Record one current known failure, `src/a.test.ts > known failure`, with summary `sentinel failure`. Record no live daemon.
2. Spawn a child process that calls the real Pi `startSession`, or OpenCode `register`, with a `HandOff`. Its injected `ensureDaemon` emits a marker and waits 30 seconds. This isolates the exact cancellable interval; it starts no test daemon.
3. Send SIGKILL two seconds after spawning the child. Confirm that it reached ensure and persisted its registration.
4. Read `owedRegistration` and the known state from a separate store connection. Record a fresh daemon heartbeat, as when startup completes.
5. For Pi call `startRun`, then `toolBoundary(..., false)`. For OpenCode call the real `after` handler with `tool: "read", primer: true`.

Actual output, with OpenCode's long primer reduced to its presence:

```json
{"harness":"pi","signal":"SIGKILL","registered":true,"childReached":true,"owed":null,"knownFailures":1,"runNews":null,"boundary":null}
{"harness":"opencode","signal":"SIGKILL","registered":true,"childReached":true,"owed":null,"knownFailures":1,"boundary":{"text":null,"primer":"present","stopWaitMs":0}}
```

The same cause also exists in Pi's registration at run start (`run.ts:49`): it can commit and then lose its answer during ensure, without creating an owed record.

### One-worker repair

Keep registration before ensure in all three sites. Record that the registration header is owed, independently of the system primer, in the registration transaction. Clear it only through the existing held handoff after the host accepts the answer. Let Pi's already-registered run-start path replay owed registration text before taking its ordinary delta. Shared tool-boundary/prompt recovery can then use the same record for these adapters. Keep each adapter's primer on its current system surface.

Add regressions for Pi session start, Pi's first run registration, and OpenCode registration: seed a known failure, lose the answer during ensure, and require the next eligible run or tool boundary to carry the registration and that failure once. Include failed handoff and successful handoff controls. Retain the two-second deadline and the first-registration-before-ensure ordering. Rebuild the committed bundles in the candidate's bundle/version commit.
