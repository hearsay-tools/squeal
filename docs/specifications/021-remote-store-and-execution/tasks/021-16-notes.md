# 021-16 notes: writes through the daemon

Worker notes for whoever continues (the follow-up row for import and the gate's kept files, row 021-17's measurement, and any later change to hook writes). Written 2026-11-12 at the end of row 021-16.

## The shape

While a daemon whose heartbeat is fresh serves the worktree, a hook or a writing command opens the store with a `SendingConnection`. It reads as `Connection` does and never writes (`PRAGMA query_only = 1`). Each outermost transaction's write statements are kept and sent, once it ends, to the daemon's socket as one batch; the daemon writes the batch in one transaction in its retried path (021-08's `DaemonWrites`). A per-worktree **write lease**, kept by the daemon's socket worker, stands in for SQLite's write lock between clients: a client holds it from its first write until its batch is written, and for a told report until the hand-off. A held report's batch is sent only after the host has the text; an abandon drops it, so the report stays owed.

With no daemon recorded, a daemon whose heartbeat is late (its main thread would write the batch late), a daemon that refuses the requests (before this row, stopping, another store schema), or no answer to a lease request, the client writes the store itself, as before: hooks through `HoldingConnection`, commands through `whileBusy` within D1's bound.

## Choices the spec did not settle

1. **Statements, not named operations** (coordinator, 2026-11-11, decision A). Hooks write from about 20 transaction sites inside shared delivery code; sending their statements keeps that code where it is. The daemon runs only `INSERT`, `REPLACE`, `UPDATE` and `DELETE` on the store's own tables, one statement each, no schema-qualified or `sqlite_` table (coordinator's guard; `node:sqlite` at 22.19 has no authorizer, and `prepare` silently drops a second statement). Each refusal has a test in `test/daemon/write-batch.test.ts`.
2. **The lease is per worktree, not per consumer.** Each consumer's told state lives in shared per-worktree JSON rows in `meta` (`delivery/slots.ts`), rewritten whole; two consumers deciding at once would overwrite each other's slot. Today's lock serialized the whole clone, so this is no regression. TTL 5 s, renewed by each write; it does not end while a write under it waits on a busy store. A batch written under a lease that ended is still written: its client told its host already.
2a. **A lease belongs to a process** (review 0.1.442 B3, repair R1). A lease request names the client's process (pid, `/proc` start time, PID namespace). Past `LEASE_TTL_MS` the desk asks whether that process lives (`leaseProcessAlive`): a live one, paused or not, keeps the lease for another TTL, as a process paused inside `BEGIN IMMEDIATE` kept SQLite's write lock, so a hook paused between deciding a report and its hand-off keeps the report its own. A process surely gone (missing, PID reused, zombie) loses it, so a dead client costs the next one at most one TTL. One that cannot be told (another PID namespace, no process named by an older client) ends at its time, as before. Without `/proc`, signal 0 on the pid tells. The desk's clock is monotonic (`performance.now`), so a host's sleep does not end a lease. A stopping daemon answers a lease request with the holder while one is held, not "stopping", so the next client waits instead of writing itself beside the held report. A live process could keep a lease it forgot for its whole life (a long-lived Pi worker or OpenCode bridge), so every path that gives a lease up ends it at the daemon: `settle` after a failed batch, a refused or failed write, an open hold at `close`. Residue: a daemon that restarts while a client holds a report has no record of the lease; that window is not closed.
3. **Reads during a hold.** A hook that holds a report reads on (Stop counts its hold after telling news). Its writes in `meta` are read back from the hold (`overlaidMeta`); other tables read the committed store. The 021-16 probe (all of `test/delivery` and `test/harness` with writes kept) found no other read of a kept write. A read while an unsent batch outside a hold is pending throws (`await sent()` missing): every write site runs in `HookContext.write` or a delivery method.
4. **A daemon whose heartbeat is late is not used.** Its main thread writes the batch; when it is blocked (the 2026-11-11 incident), the hook would wait. The hook writes itself instead, as before.
5. **Unanswered requests.** No answer to a `lease` or `release` (a hung socket, a stand-in) means no daemon takes writes: the client writes itself. A `write` left unanswered may have been taken, so it is an error, never written twice. A refused `write` (`ok: false`) or one the daemon failed is written here instead, where an SQL failure surfaces as before.
6. **`stop`'s mark** is written after the daemon's socket closed, so it is always written by `stop` itself. `start`'s writes go to a serving daemon; a stopping daemon refuses them and `start` writes itself.
7. **Hand-off.** `HandOff.take` gets the context's `sent`; `writeThenCommit` waits for the daemon's write before the hook process ends. The Pi worker and the OpenCode bridge call `HandOff.settle` and do not wait; their processes outlive the write.

## Left as it was, with reasons (coordinator, 2026-11-11, decision A)

- **`squeal import`** writes the store itself within D1's bound. Its transaction (1) creates the import tables when missing, with `conn.db.exec` DDL, which the guard refuses; (2) inserts checks new to the store and reads their ids back (`codec.ts` `ensureCheckId`), and a kept insert is not in the store yet, so it throws "check row missing after insert"; (3) is one transaction per bundle, tens of MB for a large bundle, past the write line limit.
- **The code gate's keeper** (`src/core/code/gate/keep.ts`) is unchanged. It writes only while no daemon holds the worktree lock, so with a daemon serving it already makes no direct write; sending its kept files to the daemon meets (2) above.
- The coordinator files a follow-up row: import and the gate's kept files as daemon-side requests (the daemon runs `importResults` and the keeper's rows itself), with spec 018's sliced import (D3) and spec 020's keeper.
- **`code.sqlite`** writes by hooks (told code news) stay direct: D15 names the store.

## Type changes (additive)

- `DaemonRequest` and `DaemonResponse` gain the four request and three response types of `types/daemon-writes.ts`.
- `HandlerContext` gains optional `requestWrite` and `storeSchema`; `DeskEvents` gains optional `requestWrite`; `DeskIdentity` gains optional `storeSchema`.
- `HookContext` gains `write` and `sent` (required: two test files that build a context by hand now set them). `HookDeps` and `ContextOptions` gain optional `writer`. `Prepare` gains optional `unit`. `HandOff.take` gains an optional `sent`.
- `LeaseRequest` gains optional `process` (`LeaseProcess`, review 0.1.442 B3); `WriteDeskContext` gains optional `alive`.
- `Busy` gains optional `leaseHolder`. `WriteWithinOptions` is now `CommandStoreOptions` (adds optional `writer`).
- Now async: `writeWithin`, `leaveStoppedMark`, `clearStoppedMark`, `endCommandHolds`, `denyCurrentTestCommand`, and `stopHolds` takes an optional `write`.

## Costs to watch (for 021-17)

- A write unit is a lease request, a write, one or more status polls and a release: four or more socket round trips of about 1 to 2 ms, plus the daemon main thread's time to reach the batch. A busy main thread delays a hook's write up to the hook's bound, after which the hook goes silent as it does on a locked store today.
- A registration sends one view per known state (about 1.5 MB at 15,000 states) through the socket worker and a structured clone to the main thread.
