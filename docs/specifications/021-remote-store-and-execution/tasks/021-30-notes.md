## Why the stored walk at the current key is not enough

`rekeyContent` moves the key of every test file whose closure names a changed path and commits it (`batch.ts:85-86`) before the runner part calls `affected`. So for every file the graph must judge, `readImportGraph(...).walk(ref)` at the current key finds no row; the row at the key the file held before the revision is still there until the runner part stores the new walk. That walk describes the files as they were before the revision; a content change moves no edge out of an unchanged file, so the set of test files that reach a changed path is the same before and after.
