## Why the stored walk at the current key is not enough

`rekeyContent` moves the key of every test file whose closure names a changed path and commits it (`batch.ts:85-86`) before the runner part calls `affected`. So for every file the graph must judge, `readImportGraph(...).walk(ref)` at the current key finds no row; the row at the key the file held before the revision is still there until the runner part stores the new walk. That walk describes the files as they were before the revision; a content change moves no edge out of an unchanged file, so the set of test files that reach a changed path is the same before and after.

## Step 2: the rule, as agreed

The coordinator (465c9044), 2026-11-12, on request b6baf9d3: "Rule: yes, as proposed", decisions A to D on my defaults.

The scheduler answers a revision's `affected` from the daemon's own data, without the runner host, only when all of these hold; otherwise the host walks, as before:

1. Every change of the revision is a content change: no add, no delete, no `.snap` path.
2. No changed path is an environment input, and the runner's view did not move: no project recreated, the environment and the listing not read again, no runner failure retried, no failed call earlier in the runner part.
3. Every listed test file is a Vitest file (`keys.runnerOf`) with a closure.
4. Each listed test file whose closure names a changed path (the reverse index, over closure paths) has a stored walk with its own entry, at the key it held before the revision.

Then a test file is affected when it is a changed path or its walk visits one (an importer or a target); direct when it is a changed path or its own entry imports one; the rest transitive.

Decisions:

- **A. The walk at the key before the revision**, not at the current key as spec 015 D11's read rule says (coordinator: accepted for this one reader, recorded in `status.md` and amended in D11 at integration). Reason: `rekeyContent` moves and commits the key of every file whose closure names a changed path (`batch.ts:85-86`) before the runner part asks, so the current key has no walk for exactly the files the graph must judge; the walk at the earlier key describes the files before the revision, and a content change moves no edge out of an unchanged file, so a test file reaches a changed path after the revision exactly when it reached one before.
- **B. Always when the rule holds**, not only for the first call after a reopen: answering only the first call would move the walk to the second edit.
