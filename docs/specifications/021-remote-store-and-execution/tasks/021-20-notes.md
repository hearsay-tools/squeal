# 021-20 notes: import in slices and through the daemon

Worker notes for whoever continues (row 021-17's measurement, later changes to import or the gate's keeper). Part one written 2026-11-12, landed in 0.1.448; part two (the keeper) written 2026-11-12 on main 22d1db3aa, after spec 020's row 020-28 landed in 0.1.447.

## The shape

An import is no longer one transaction over the bundle. `importSlices` yields short write transactions in the order the one transaction wrote: closure lists (500 files a slice), observed entries (one slice a project), start-up lists, then the re-keying (a read, after the lists committed), the import's file rows (500 a slice), the results (2,000 a slice, the results at one key never split), and last the environments with the import's own record. A driver runs each slice: `importResults` runs them here one after another (tests, sync callers); `importSliced` gives each to a `SliceRunner`, by default `retriedSlice` (001-422's `retryWhileBusy`, 250 ms tries, a bound from the slice's first try).

Three callers:

- The shared reader (`src/core/shared/reader.ts`, spec 018's file, agreed by both coordinators) awaits `importSliced` with `stopped` tied to its stop signal; the default runner, bound `BUSY_BOUND_MS`.
- `squeal import` with a daemon serving the worktree (fresh heartbeat): the `import` socket request; the daemon reads the file, checks the hash and the refusal, and imports through `DaemonWrites` with `within(BUSY_BOUND_MS, stopping)` per slice. The command polls `import-status`.
- `squeal import` with no daemon serving, or one that takes no imports: `importSliced` here, `retriedSlice(busyBoundMs)`.

## Choices the spec did not settle

1. **The import's record is written last** (018 coordinator's condition). The reader reads an export as held from `listImports`, and `ImportsSeen` rereads projects from the record's files. A record written first would make a half import look held. A stopped or failed import leaves results and file rows without a record; the next import adds only what is missing (keys already held count as `alreadyStored`).
2. **Each results slice takes its own record time** (`clock`, read inside its transaction). `StoredKeys` reads keys recorded since its last read less 120 s; one `now` for a long sliced import could fall outside that window for a late slice. The import's record, closures and environments keep the import's start time.
3. **A dry run stays one transaction** that rolls back: the re-keying reads the import's own lists, which separate rolled-back slices would not show. It holds the lock for the whole bundle, as before.
4. **The bound is per slice, not per import.** A slice that waits past `BUSY_BOUND_MS` (10 s) ends the import with exit 1 and the old busy text; a large import on a free store is not cut by its own length.
5. **The daemon reads the file itself**; the command sends its path and the SHA-256 of the bytes it checked. Other bytes are not imported ("changed after squeal import read it"). A bundle can pass the 32 MiB line limit, so the bytes do not travel on the socket.
6. **No answer to `import` means the command imports itself.** Unlike a sent write batch, an import is idempotent, so a daemon that took the request and went silent costs a second import at most. Once taken, a status request without an answer is an error (exit 1), as 021-16's writes do: the daemon may still be importing.
7. **The command still tells every daemon after a real import** (`tellDaemons`), the serving one included; the daemon does not tell itself.
8. **The D21 record**: the reader still clears it before the import and writes it on a refusal, outside the slices, as in 0.1.440.

## Part two: the code gate's keeper through the daemon

While a daemon holds the worktree's lock and its heartbeat is fresh, the keeper (`Keeper.#write`) writes through it; with the lock free it writes itself as 020-28 made it; with the lock held and no fresh daemon (a starting or hung one, or a daemon before this request), it keeps nothing and says "a daemon runs in this worktree, and it keeps its own", as before.

What moved and what did not:

- **The write tries moved, the wait did not.** `keepFile` takes a `KeepWriter` with two methods, one try each: the file's coverage record (`putParts`) and its results (`storeResults`). `writeHere` tries on the keeper's own connections with one busy slice, as before; `writeThroughDaemon` (`keep-sent.ts`) sends each try as a `keep` request. The flush after the report, the 30 s bound from the first refused try (`StoreWait`), the busy note naming the holder (from `/proc`, client side), the check of the file's inputs after each pause and before each write, and the notes at the end stay in the keeper, unchanged.
- **The daemon tries once** (`keepInDaemon`, `src/core/daemon/keep-request.ts`): `DaemonWrites.write` with `stopped` always true, so one try of one busy slice (250 ms) in the daemon's retried path, then `kept: true`, `kept: false` (busy) or `failed`. The keeper's loop pauses (`busyBackoffMs`), checks the inputs and the bound, and sends the next try. A daemon that retried for longer would write past an input change the keeper has not yet checked (review 0.1.444 B2).
- **What a request carries.** Coverage: the result key and the `CoverageRecord` as JSON; the daemon calls `shareRecord` and opens the code store per request (`openCodeStore` with its own policy and a 250 ms busy timeout). Results: the `ResultRecord`s the keeper built (it reads the previous checks itself), the file's stability paths for `healsUnheld`, and its project's environment files for `storeResults`' `unresolvedPreloads`. `storeResults` reads only `environmentFiles` of its keys, so the daemon passes a narrow stand-in (`Pick<WorktreeKeys, "environmentFiles">` asserted as `WorktreeKeys`); no scheduler file changed.
- **A refused `keep`** (an older daemon, a stopping one, another store schema) ends the flush with the 020-28 note; a daemon that took a try and stopped answering fails the files not yet written ("the daemon stopped answering").

Files: `src/core/code/gate/keep.ts` (`#write` picks the writer, `openCode`), `keep-write.ts` (`KeepWriter`, `writeHere`, `keepFile`, `sliced`), `keep-sent.ts` (`writeThroughDaemon`, `sentWriter`, `DAEMON_KEEPS_ITS_OWN`), `src/core/daemon/keep-request.ts`, `request-desk.ts`; wire types `KeepRequest`, `KeepWrite`, `KeepStatusRequest`, `KeepOutcome`, `KeepResponse`, `FailedOutcome` in `types/daemon-writes.ts`; relays `keep` and `keep-result` in `desk-messages.ts`, `front-desk.ts`, `desk.ts` (`DeskEvents.requestKeep`, a shared `relay`), `daemon.ts` `#openDesk`.

Tests: `test/code/gate/keep-daemon.test.ts` (a daemon socket served in the test process, its writes in an `AsyncLocalStorage` context so the counter tells them apart): two files kept through the daemon with 0 write transactions of the gate's own on `store.sqlite` and `code.sqlite`; a lock freed within the bound (holder named first, then the free note); a lock past the bound (both notes, nothing kept); an input moved during the wait; a late heartbeat and a daemon without the request both give the 020-28 note. The 020-28 tests (`test/code/gate/keep-busy.test.ts`, `keep.test.ts`, `test/cli/code-gate-keep*.test.ts`) are unchanged and pass.

## Repair R1 (review 0.1.450)

- **B1, line limit.** A line that starts `{"type":"keep",` gets the 32 MiB bound of a write line (`protocol.ts` `lineLimit`); past it the socket still answers "request too long". The gate's refusal note now names the daemon's reason ("the daemon refused the write: …"); only "unknown request type" or "this daemon takes no kept files" give the 020-28 note.
- **B2, lost answers.** `KeepRequest.id` is chosen by the gate. `RequestDesk` keeps a keep outcome under it (`idOf`, 1,024 remembered) and runs one id once. On a lost answer (timeout, closed connection) the gate asks `keep-status` by that id until `DAEMON_WAITS.reconcileMs` (10 s; answers 2 s each): a known id gives its outcome; an unknown id never ran, so the try is `lost` and `keepFile` tries anew after its pause and input check (at most 3 lost tries); no answer at all throws `KeepUnknown`, told by `perhapsKept` ("may not be kept … the next run reads it if it was kept"). A failed connect (ENOENT, ECONNREFUSED) proves nothing was sent: not kept. Tests may shorten the waits (`KeepOptions.daemonWaits`). Across a daemon restart the id is forgotten and a resent try runs again; its rows are the same rows at the same key (`INSERT OR REPLACE`, no flip), so nothing doubles.
- **B3, the keep payload.** `src/core/daemon/keep-protocol.ts` checks the whole request before the handler runs: a 64-hex key; a version 1 coverage record (paths, 40 to 64-hex blob ids, base64 bitsets, 5-number spans); or one file's results at the write's `key` (new field): test and file checks, `pass`/`fail`/`skip`, locations, errors with their known fields, one gate run's provenance (`gate-<uuid>`) in this worktree, no repeated check, no unknown field.
- Tests: `test/code/gate/keep-daemon-wire.test.ts` (B1, B3, real socket), `keep-daemon-lost.test.ts` (B2, a proxy socket that holds or drops one answer), `keep-daemon-kit.ts` (shared setup, moved out of `keep-daemon.test.ts`), the desk's id rules in `test/daemon/request-desk.test.ts`.
- Commits: B1 alone; B2 and B3 share the wire type change (the id, the results key), so the B2 commit typechecks only with the B3 commit after it.
