What each lead gave:

1. **Skip unchanged blobs.** Leaving `blob` out of the adopt's `SET` saved 4 to 7 ms (probe) and 10 to 15 ms in one test run, within noise. SQLite updates an index whose column a `SET` names, but most of the cost is the new and the removed rows, whose entries must move anyway. A correct form needs a second statement over the staged rows, which costs about as much. Not taken.
2. **A narrower index.** A prefix of the blob, with or without the worktree id first, saved nothing over the full blob: an index entry also carries the primary key, and the cost is per entry. A partial index of complexity states only saves the upkeep of every crap and uncovered state write (a coverage step's too) and a third of the removed delete's. Taken.
3. **Slice the writes.** The adopt must stay one transaction (row 015-48: a hook reads the old states or the new ones). The crap and uncovered states of the removed checks need not be in it: deleting them in a turn before the switch cuts the switch's rows from about 31,600 to 19,000 and its WAL from 7.3 to 6.1 MB, 18 to 25 ms. Taken.

Also: the code store's connections had SQLite's default 2 MiB page cache; the main store and the store process's writer (`store-process/writer.ts`) use `CONNECTION_PRAGMAS` (16 MiB, spec 024 D5). The 16 MiB cache saved 10 to 20 ms in the probe and the test. Taken. Deleting the removed checks by id instead of by `[path, name, occurrence]` would save about 10 ms more, but it needs the ids read during the staged parts and a change of `adopt`'s parameter type; not needed now, and the next lever if the line tightens.

Not taken: a trigger-kept table of blobs a file left, or a change counter. Each costs per state written as an index does, or does not pass `prune-keyed`'s B1 test, where a state names a blob no file ever named.

## The design

- `CODE_INDEXES.states_complexity_blob`: `CREATE INDEX states_complexity_blob ON states (blob) WHERE measure = 'complexity'`. A new name: a daemon of 0.1.570 or later tests its count rule with `s.blob = counts.blob`, which a partial index cannot serve, so under the old name its prune would scan `states` under the write lock.
- `CODE_RETIRED_INDEXES = ["states_by_blob"]`: a creating open drops it in the same `BEGIN IMMEDIATE` and second look as it makes missing indexes (`makeIndexes`, `open.ts`). A reader (`create: false`) neither makes nor drops. A store that has the new index and lacks the old opens with no write lock (the existing test "takes no write lock at a second open").
- The prune's count rule (`UNUSED_COUNT`, `prune.ts`) keeps a count that a live file or a kept **complexity** state names, tested by key under the write lock through `files_by_count` and `states_complexity_blob`. It needs both new indexes present (`hasIndexes`), or it waits, as before.
- `CodeStateRepo.removeOtherMeasures(worktreeId, checks, kept)` (new, additive): one statement deletes each check's states of every measure but `kept`. `quietEnd` calls it with the removed checks and `"complexity"` in a turn of its own before the switch, when any check was removed. The switch's `adopt` is unchanged and still deletes every measure's state of a removed check; it finds only the complexity ones by then. The edit pass's staged switch (`stage-edit.ts`) is unchanged.
- `openCodeStore` runs `CONNECTION_PRAGMAS` on every connection it opens, the daemon's, the hooks' and the CLI's, as the main store does.

## Older daemons on the same file (spec 015 D4)

`user_version` stays 1 and no table changes. An older daemon writes states as before; SQLite keeps `states_complexity_blob` current on its writes.

- A daemon before 0.1.570 never had `states_by_blob` and tests states in its prune's read only (as 0.1.568 did).
- A daemon of 0.1.570 to this row's base makes `states_by_blob` again at its next creating open (5.2 s on cezar's 5.4 M states, 021-33 notes), and its prune runs the count rule with it. A daemon of this branch drops it again at its own next creating open. While both run on one clone, each daemon start of the other kind rebuilds or drops it once. Without `states_by_blob` the older prune skips the count rule and keeps every count, which is safe. Test: `test/code/store-index.test.ts`, "replaces an older daemon's index of every state at a creating open, never at a reader's".
- One-time cost on a large store, not measured here (heavy work runs on boat.dev): building the new index reads every state and writes about a third as many entries as `states_by_blob` did; 021-33's 5.2 s for the full index suggests about 2 s on cezar's store, once per clone, at the first creating open of a daemon of this release.

## Decisions the spec did not settle

1. **The count rule keeps a count for complexity states only.** A pass reads a count by a state's blob in one place, `pass/bodies.ts` (`oldBodies`, `bodiesOf`), and only for complexity states; the coverage seed reads by a files row (`crap/seed.ts`, `#hadOf`), the coverage step by the files row too (`crap/step.ts`). A count only a crap or uncovered state names now goes after the retention. Test: `test/code/prune.test.ts`, "drops a count past the retention that only a crap or uncovered state names".
2. **A removed function's crap and uncovered states go one turn before the recount's switch.** For that turn a hook reads the old complexity states without those of the removed functions; it never reads them beside the new complexity states. Nothing writes them again in between: a coverage step judges a file's functions from the files row's count, at the new counter version since the pass's first transaction, and `dropKept` rewrites only states that exist. A crash before the switch leaves the cursor where it was, so the recount runs again and removes the complexity states then. Test: `test/code/pass/staged.test.ts`, "removes a renamed function's crap and uncovered states before the switch, never after it" (fails at main: the hook never reads the old states without them).
3. **Every code-store connection gets the 16 MiB cache**, readers too. The size is a ceiling, not an allocation; the main store does the same.
4. **Retired indexes are dropped at a creating open.** The brief asks that existing stores lose the old index. The cost is the rebuild and drop on a clone with daemons of both kinds (above).
