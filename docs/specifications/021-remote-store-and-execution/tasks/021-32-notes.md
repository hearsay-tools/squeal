## Rotation, and why the log stays bounded while one daemon runs for days

Mechanism: copy-truncate. When the file holds 4 MiB or more, it is copied
to `<log>.1`, over the previous copy, and then truncated in place to 0
bytes. Truncation keeps the inode. So every process that has the file open
(a daemon, the successor that a step-down spawns, the CLI's own writes
outside `log`) continues to write to the one file at the path. Because the
file is open with `O_APPEND`, each write goes to the new end, not to the old
offset.

Two places rotate:

1. The spawner (`openDaemonLog`) rotates before it opens the file. This
   bounds the log across restarts, also when the earlier daemon wrote only
   crash text outside `log`.
2. The daemon (`daemonLogSink`) checks `fstat(2).size` after each of its
   own lines, and every 60 s on a timer that is unref'd. The timer catches
   text that Node, a worker thread or a crash wrote to fd 2 outside `log`.

Bound: one file reaches at most 4 MiB plus one line, or plus what was
written outside `log` in one minute. The previous file has the same bound.
The constant is fixed and does not depend on the host.

Known gaps, accepted:

- Lines written between the copy and the truncate are lost. Both steps are
  synchronous in one process, so this window is microseconds wide.
- Two daemons of one worktree that rotate at the same moment (an old daemon
  that steps down and its successor) can copy twice. The second copy then
  replaces `.1` with a nearly empty file. Both daemons must reach the limit
  in the same instant for this to occur.
- The daemon's runner hosts and git children use pipes, not fd 2 (checked
  in `runner-host/channel.ts`, `fs/git.ts`), so they do not write to the log.

Cost to a hook: one `mkdir -p`, one `stat` and one `open` before the spawn.
A copy of 4 MiB occurs at most once for each 4 MiB of log, with
`copy_file_range` on Linux.

## Decisions the contract did not settle

- File mode `0o600`. The log names paths and test names of the project.
- The prefix is added only when fd 2 is this worktree's log file (same
  inode as `daemonLogFor` of the daemon's root). A daemon that a user runs
  in a terminal keeps its earlier output, with no prefix.
- The daemon finds the path from its `root` argument, with the same
  functions as the spawner (`resolveCommonDir`, `worktreeIdFor`). No
  argument and no environment variable is added (D11).

## Deleting a gone worktree's log

No code deletes a gone worktree's lock file. `stop-removed.ts` and
`ps/discover.ts` only read lock paths. Only `squeal remove` deletes the whole
`<commonDir>/squeal` directory, and the logs are deleted with it. So a gone
worktree's log stays, at most 8 MiB, until `squeal remove`. A later row can
delete both the lock file and the logs at the same place.
