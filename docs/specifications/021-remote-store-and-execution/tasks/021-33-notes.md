## What changed

- `src/core/store/prune-keyed.ts` (new): `deleteByKey(conn, rule)`. A read slice takes the next batch of keys that the rule's `search` finds, after the last key read, in a read transaction (WAL: no write lock). A delete slice then deletes those keys in one write transaction, where the rule is tested again per key (`recheck`, by an index; default `search`). A read that finds nothing ends the rule, so a rule with nothing to delete takes no write lock. The keys travel as one JSON parameter. `worktreeIdsOf` moved here from the code prune; `worktreeIdList` gives it as a JSON list.
- `src/core/code/store/prune.ts`: every rule is a `deleteByKey`. Dead worktrees go one id at a time (`worktree_id = ?`, so each read follows the key order with no sort); `transitions` is keyed by its index `(worktree_id, check_id, id)`. `checks` is tested again per key in `states` and `transitions` by worktree id and check id (one search per worktree id), and in `views`. Coverage records go 64 per transaction (`COVERAGE_BATCH`, see the probe).
- `src/core/store/prune-unused.ts` (new): the main store's `checkpoints`, `checks` and failure-text rules as `deleteByKey`. `checks` is tested again per key in `results` by its key, in `known_states` and `transitions` by worktree id and check id, and in `consumer_views`. Moved out of `prune.ts` to keep it near 300 lines (311; it was 325).
- `src/core/store/loaded-modules.ts`: `dropOrphanLoadedModules` is a `deleteByKey`, tested again per key by `results_by_key`.
- `src/core/daemon/clone-prune.ts` (new): `oncePerClone` and the mark `prune:last-at`. `src/core/daemon/lifecycle.ts`: the prune timer runs the main store's prune through it, and the code store's prune only when this daemon claimed the turn.

## Once per clone: a mark in the main store, not a lock file

The mark is the main store's meta row `prune:last-at`, the epoch ms when a daemon of the clone last claimed a prune. A daemon reads it outside the write lock, ten times per interval (`PRUNE_ASKS`, `lifecycle.ts`; the first 60 s after start). When it names a claim less than one full interval before the daemon's clock, the daemon prunes nothing and writes nothing. Otherwise the daemon claims it in one write transaction, by compare-and-set: it writes only when the mark is still the value it read, and it writes the clock as it is at the claim. A different value is a competing daemon's claim, newer or ahead of this clock, and this daemon prunes nothing. So of daemons that read the same mark, one claims, in either order and whatever their read times. The claimer then prunes the main store, then the code store (`lifecycle.ts`: the code prune runs only when this daemon claimed).

Recovery: a mark ahead of the clock when it is read (the clock moved back), or one that is unreadable, is due, so it cannot stop prunes. A claim whose prune never ran (its daemon stopped) is due one interval after it. There is no early slack (review 0.1.568 B2): a prune is never sooner than one interval after the last claim, and is at most a tenth of an interval later with a daemon running.

Why not a lock file under `<commonDir>/squeal/`: the claim must be atomic across processes. SQLite's write lock already gives that, with the busy handling of the prune driver (`SlicedPrune` retries a busy slice). A file needs an atomic create, a stale-file rule for a daemon that died, and mtime reads. The row is shared by every worktree, like `flaky-checks`, so `WORKTREE_META_ROWS` does not list it. An older daemon on the same clone does not read the mark and prunes as before.

`squeal prune` (the CLI) does not read or write the mark.

## Open: reads still block the daemon's event loop

A read slice holds no lock, but it runs on the daemon's main thread. The longest: the first read of `loaded_modules` (108 k rows, each with its module list; no index by `key`), 5.9 s on a cold cache and 0.5 to 1.2 s warm; the code store's `checks` and `counts` searches, 1.5 s. The base code did the same reads inside its write holds, so this is no regression, and `SlicedPrune` pauses after each slice. Paging those reads by key ranges, with the search per page, would bound each slice; it suits `loaded_modules` (its test is per row) but not `checks` (its `NOT IN` would be built again per page). An index `loaded_modules (key)` is a change of 022 D3's table shape, which needs the coordinator.

## Seam map for the next worker

- The daemon's prune: `lifecycle.ts` `startTimers` → `SlicedPrune.run(oncePerClone(... pruneSlices ...))`, then `pruneCodeSlicesAfter` when claimed.
- A slice is any `() => void`; a read slice is one too, and the driver pauses after it as after a write.
- To make another rule keyed: give `deleteByKey` the table, its primary key (or an index that names one row and whose order a cursor can follow), the search, and a recheck that uses an index. A search on a column the key does not lead with makes each read sort; split it per value, as the dead worktrees are.
- Tests: `test/store/prune-keyed.test.ts` (no write lock without a delete; a row live again before its delete stays; a rule without its index), `test/store/prune-results-race.test.ts`, `test/store/prune-plans.test.ts` (no scan under the lock), `test/daemon/prune-once.test.ts` (the mark; two daemons' real timers on one clone). `test/store/prune-race.ts` drives slices by hand and runs a change between a rule's read and its delete.
