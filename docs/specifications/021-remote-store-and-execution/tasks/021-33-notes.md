A read slice takes the next batch of keys that the rule's `search` finds, after the last key read, in a read transaction (WAL: no write lock). ## Once per clone: a mark in the main store, not a lock file

The mark is the main store's meta row `prune:last-at`, the epoch ms when a daemon of the clone last began a prune. At each timer firing, a daemon reads it outside the write lock. When it is fresh, the daemon prunes nothing and writes nothing. When it is stale, the daemon claims it in one write transaction that reads it again, so of the daemons that found it stale together, one prunes. That daemon then prunes the main store and the code store.

Why not a lock file under `<commonDir>/squeal/`: the claim must be atomic across processes. SQLite's write lock already gives that, with the busy handling of the prune driver (`SlicedPrune` retries a busy slice). A file needs an atomic create, a stale-file rule for a daemon that died, and mtime reads. The row is shared by every worktree, like `flaky-checks`, so `WORKTREE_META_ROWS` does not list it. An older daemon on the same clone does not read the mark and prunes as before.

"Fresh" means begun less than the interval before, less a slack of a tenth of the interval, at most a minute (57 minutes for the default hour). Without the slack, a daemon whose own timer fires a moment before the hour ends would skip its next prune, and the clone would prune up to two intervals apart. A mark ahead of the clock (the clock moved back) or unreadable is stale. The mark names the start, so a prune that a stopped daemon left half done continues at the next interval.

`squeal prune` (the CLI) does not read or write the mark.

## Decision the brief did not settle: the count rule's `states` test runs in the read only

A count stays while a kept state was judged on its blob (review 0.1.283 B5). `states` has no index on `blob` (5.4 M rows on cezar), so testing it per key under the lock is a scan: 1.0 s on the copy. Under the lock, a count is tested again on its own age and on `files` (`files_by_count`); `states` is tested in the read only. So a state written between the read and the delete, which names an old count that no file names, loses that count. The window is the read slice and one pause, normally under a second. A count is a cache of one blob's function counts. An index `states (blob)` would close the window; it is a code-store schema change and not this row's.

## Open: reads still block the daemon's event loop

A read slice holds no lock, but it runs on the daemon's main thread. The longest: the first read of `loaded_modules` (108 k rows, each with its module list; no index by `key`), 5.9 s on a cold cache and 0.5 to 1.2 s warm; the code store's `checks` and `counts` searches, 1.5 s. The base code did the same reads inside its write holds, so this is no regression, and `SlicedPrune` pauses after each slice. Paging those reads by key ranges, with the search per page, would bound each slice; it suits `loaded_modules` (its test is per row) but not `checks` (its `NOT IN` would be built again per page). An index `loaded_modules (key)` is a change of 022 D3's table shape, which needs the coordinator.

- A slice is any `() => void`; a read slice is one too, and the driver pauses after it as after a write.

A search on a column the key does not lead with makes each read sort; split it per value, as the dead worktrees are.
