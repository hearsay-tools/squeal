## Choices the brief did not settle

1. **What "on PATH" means.** A file that is executable and is a regular file in a directory of `PATH`, as `harnesses.ts` `onPath` checks it, plus the regular-file test (a directory is executable too). The same test runs on the remote as a `node -e` script, so the two cannot drift; `required-commands.test.ts` runs both on one `PATH`. A name must be a bare command: no `/`, no leading `-`, no space. Windows `PATHEXT` is not handled.
2. **Here, the check runs on the daemon's own `PATH`**, which its test runs get. Not the CLI's: `squeal status` from another shell may have another `PATH`. It runs at start and when `squeal.config.json` changes. A line is written only when it changes: missing names, then `tests need git, python3; all found on PATH here` once they are found, or `tests need no command (requires.commands is empty)`.
3. **On the remote, the check is one more `ssh` call at each connect**, after the bundle check and before the host starts, so a refused remote gets no tree. It runs only when `requires.commands` is not empty. Folding it into `bundle.ts`'s `CHECK_SCRIPT` would save that call, but that file is not this row's.
4. **A missing remote command is a refusal, not a loss.** `startRemoteHost` throws `RemoteRefusal`; the lane's connect `catch` calls `down(text, true)`. Status: `remote <target> refused: tests need python3; not found on PATH there; running here` (or `; N files not run`). The lane tries again after its backoff (30 s to 10 min), so a remote that gets the command back is used again without a restart.
5. **The split.** A background tier's `needsRepository` files run here first, while the tier still holds its local permits (`permits.back` without `away` answers the workers it holds), in `<logDir>/repository`. The rest then go remote as before. The two reports are joined with the composite runner's `merge`, failures prefixed `here:` and `remote <target>:`. A tier of only such files is a plain local run. A `squeal stop` after the first part starts no remote part, as the composite runner does.
6. **The guard.** It reads a proven remote report only. A file whose failed test, file error or setup failure carries Git's own fatal line for a missing repository (R1 below; it was any `not a git repository` substring before) loses every per-file field of the remote report (`withoutFiles`), runs here at once in `<logDir>/here`, and stays here for the life of the lane (in memory; a daemon restart forgets it, and the guard catches it again). It runs here also under `whenLost: "not-run"`: D19.2 says these files always run here. Topic `remote-lane:repository` names every file it holds: `remote box: test files that failed on the remote as not a Git repository run here: test/git.test.ts; add each to remote.needsRepository in squeal.config.json` (the first five, then how many more).
7. **A setup failure with Git's text** (a `globalSetup` that runs `git`) flags every file of that run, since none of them can run there. The hint then names each file; a hint about the setup file would read better, and is left for later.
8. **Git missing on the remote is not the guard's case.** `git: not found` is a missing command: `requires.commands: ["git"]` refuses such a remote. The guard is only for Git's own text, when Git is there and `.git` is not.

## R1: review 0.1.457

Repair round on `cand/0.1.457` (`47c8faed2`), 2026-11-12. The review is `../reviews/0.1.457.md`.

- **B1 and B2, one recognizer.** `lane-repository.ts` `missingRepository(error)`: a line of the error's message, or of one of its `causes`, that starts with Git's `fatal: not a git repository` and goes on with one of Git's own continuations: ` (or any ` (the parent directories, or a mount point), `: ` (a named directory, with `GIT_DIR` set), or the end of the line. Case-insensitive, for older Git's `Not`. The line's end is not required, because a cause keeps only its first line, capped at 200 characters (`results.ts` `causeChain`). It applies to a failed test's errors, each file error and the setup failure. The stack is no longer read: it repeats the message, and a stack alone is no evidence. So Vitest's `expected 'not a git repository' to be 'invalid input'`, an assertion on the whole fatal line, a cause that quotes it, and `git: not found` all stay remote failures, run nothing here, and are not remembered.
- **Cause depth.** A cause that is an `execFileSync` error keeps only `Command failed: git ...`, its first line; Git's line in its second line is lost there, and such a failure stays a remote failure. A test that throws its own error with Git's stderr as the cause, as the review's probe does, is recognized.
- **B3, deferral.** A report holds one setup failure. In a split tier the local part runs first; if it failed to start, the remote part does not run, and its files join that failure's `testFiles` (`deferredTo`). The scheduler's `failStartup` then blocks the files of the failed project and queues the others again, so the remote part runs in a later tier, with its own setup outcome. Likewise the guard does not rerun a file here beside a setup failure the remote report keeps: the file joins it, is remembered, and runs here in a later tier. A remote setup failure after a local part that started is kept as before, beside the local part's results. A stop after the local part still starts no remote part.
- **Tests.** `lane-guard.test.ts`: the recognizer's four Git forms, a capped cause, five quoting controls; through the lane, a cause-wrapped test failure, file error and setup failure each lose every remote per-file field, run here, are named and stay here; each quoting control stays a remote failure and is not remembered. `lane-setup.test.ts`: the deferral, the remote-only setup failure, the guard beside a remote setup failure, the stop, and a scheduler regression over the real lane and an in-process remote with two projects and two setup errors: setups `a` and `b` both fail with their own text, neither file stays queued, both are unknown. Against the candidate's code, 11 guard tests and 3 setup tests fail; the scheduler one records project `a` alone, as the review saw. `test/e2e/remote-lane.test.ts` adds two real Vitest controls on the container: an assertion that quotes the words on the remote alone stays a failure there, and a thrown error whose cause is the fake Git's stderr runs here and is named.
