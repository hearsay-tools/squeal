## 1. D22.5 audit: code-store transactions that read inside themselves

A daemon's code-store transaction now runs in a deferred read transaction on its own connection (`SendingConnection`), records its writes as statements and sends them as one batch. So inside one transaction (a) a read does not see the transaction's own earlier writes, (b) `run` returns 0, and (c) a decision taken from a read may be stale when the batch is written, if another process wrote between. Batches of one daemon are written one at a time and the daemon's main thread waits for each (section 3), so a read in a later transaction sees every earlier batch (precondition P).

## 3. The bound (the coordinator's condition, 2026-11-19)

The main thread waits for a batch at most the time a direct write would wait for the lock: the connection's `busy_timeout`, or the caller's busy slice when shorter (`boundOf`: 1,000 ms for the code pass, 250 ms for the coverage writer and `keepInDaemon`'s slice). Then:

- `written`: done.
- `not-taken` or `unknown`: written here under the mark with the rest of the bound as busy timeout. The mark settles an `unknown` batch: a store process killed after its commit left the mark at the batch (`superseded`, nothing written); one killed before left it below (written here).
- No answer within the bound (`late`): written here under the mark with busy timeout 0. A free lock settles it the same way, and the store process later finds the mark and skips it. A held lock throws SQLite's busy error, as a direct write would after its timeout; nothing was written here, and the store process may still write the batch, once. While a late batch is unanswered, later batches are written here at once (no second wait).

So the main thread never waits longer than today, and no batch is written twice. Tests: `relay.test.ts` "waits no longer than the busy timeout, then settles the batch by its mark, written once" (bound 200 ms, a lock held by another connection: waited < 350 ms, `late` 1, the store process wrote it once afterwards, `direct` 0); `processes.test.ts` "leaves a batch it was killed in to the client, written once within the bound" (300,000 rows, `kill -9` at 0.4 s, all rows once, mark set, under 10 s).

## 4. Deviations and decisions the spec did not settle

- **The daemon waits for each batch.** `design.md` section 6 says a client's send returns at once. Today's code-store callers are synchronous and read what they just wrote, so the relay keeps them as they are and waits within the bound above. An asynchronous send would need every caller to await `sent()` first. Busy-handler waits are 0; the wait for the queue is not.
- **Busy waits are counted by construction.** `node:sqlite` exposes no busy-handler counter. The test counts the daemon's own writes (`direct`, `superseded`): 0 means it never asked for the write lock, and a WAL reader never runs the busy handler. The control test without a store process counts `direct` > 3.
- **Not routed in this slice:** the code-store prune (`prune-main.ts`, a `PRAGMA` vacuum and reads outside its statements; run once per clone per interval since 021-33) and the index build at open (021-35). Both write directly; SQLite's lock is the safety net. The queue's `prune` kind exists and is tested; no caller uses it yet.
- **A busy store-process write is not retried there.** It fails the batch; the client writes it under the mark. A stray writer (an older daemon) costs a direct write, not a corruption.
- **Marks of gone worktrees stay** (one `meta` row each, `store-process:<id>`). A later prune rule can drop them.
- **Older clients:** a write without `seq` is refused, so a client of another release writes directly.
- **No relay script, no relay:** from the sources without a loader, or a bundle built before the two entries, `codeStoreOptions()` is empty and the daemon writes with a plain `Connection`, exactly as before.
- **Two daemons that start one at once start two processes;** the one that does not take the lock exits at once (`lost-lock`, exit 0). This is the daemons' own mechanism (spec 001 D10).
