## 1. D22.5 audit: code-store transactions that read inside themselves

A daemon's code-store transaction now runs in a deferred read transaction on its own connection (`SendingConnection`), records its writes as statements and sends them as one batch. So inside one transaction (a) a read does not see the transaction's own earlier writes, (b) `run` returns 0, and (c) a decision taken from a read may be stale when the batch is written, if another process wrote between. Batches of one daemon are written one at a time and the daemon's main thread waits for each (section 3), so a read in a later transaction sees every earlier batch (precondition P).

32 write sites in `src/core/code/**` and `daemon/keep-request.ts` were read (a background read of the code, then each change checked by hand). Sites not listed below only write, or test their condition in their own statements (`ON CONFLICT`, `WHERE`), or touch only the worktree's own rows (one daemon per worktree, batches in order).

## 3. The bound (the coordinator's condition, 2026-11-19)

The main thread waits for a batch at most the time a direct write would wait for the lock: the connection's `busy_timeout`, or the caller's busy slice when shorter (`boundOf`: 1,000 ms for the code pass, 250 ms for the coverage writer and `keepInDaemon`'s slice). Then:

- `written`: done.
- `not-taken` or `unknown`: written here under the mark with the rest of the bound as busy timeout. The mark settles an `unknown` batch: a store process killed after its commit left the mark at the batch (`superseded`, nothing written); one killed before left it below (written here).
- No answer within the bound (`late`), or the store process lost (`unknown`): **settled first** (review of 0.1.571, B2 and B2b; this replaces the earlier rule that threw busy while the store process could still write the batch). The relay sends `write-cancel`: a batch the writer has not begun is withdrawn and never written (`cancelled`); one it began is waited for until it ends (`written` or `failed`). When the store process cannot answer (gone, stopped, the batch unknown there), the batch is written here under its mark as soon as the lock is free; the store process skips it later by the mark. Only then is a batch not written there written here (busy timeout 0) or reported to its caller as busy. So a batch is never written after its caller saw it fail, and the worktree mark never passes an unsettled batch. The wait past the bound lasts as long as the store process's writer holds the batch (at most its 1 s busy timeout when another process holds the lock), or until the lock frees; past 30 s (`SETTLE_MS`) the caller gets a busy error, and the batch stays pending: every later batch first settles it under its mark, or fails without being written.

So the main thread never waits longer than today, and no batch is written twice. Tests: `relay.test.ts` "waits no longer than the busy timeout, then settles the batch by its mark, written once" (bound 200 ms, a lock held by another connection: waited < 350 ms, `late` 1, the store process wrote it once afterwards, `direct` 0); `processes.test.ts` "leaves a batch it was killed in to the client, written once within the bound" (300,000 rows, `kill -9` at 0.4 s, all rows once, mark set, under 10 s).

Today's code-store callers are synchronous and read what they just wrote, so the relay keeps them as they are and waits within the bound above. - **Busy waits are counted by construction.** `node:sqlite` exposes no busy-handler counter. - **A busy store-process write is not retried there.** It fails the batch; the client writes it under the mark. A stray writer (an older daemon) costs a direct write, not a corruption.
- **Marks of gone worktrees stay** (one `meta` row each, `store-process:<id>`). A later prune rule can drop them.

### Deviations and decisions the spec did not settle

- **A refused batch is written here at once** (D22.4 lists "it refused the schema" among the proofs). A refusal because the store process is stopping is waited out instead: the batch goes to the next process, or here once the lock is free.
- **`hungMs` 10 s** (D1's bound) for the ping. A store process that answers pings but whose writer never ends a batch is not "hung" by D22.4's definition: its batch waits, and its callers' `sent()` waits with it; the daemon's main thread does not.
- **Holder lookup**: the relay ends only a pid learned from the store process's own ping, or the lock holder whose command line says `store-process`; it never ends `squeal remove`, which takes that lock too.
- **A failed batch fails the rest of its connection's epoch**: a code pass's later batches were decided on rows the failed one left out. The epoch moves when the caller is told (`surfaced`), so batches posted after that are written.
- **Daemon stop**: `CodeRelay.close` waits up to 5 s for the thread to settle what it holds. Past it, batches are left to the store process that holds them, or lost as at a crash; no caller is left to retry them.
- **A relay thread that died** rejects every later batch (previously: written on the main thread). The main thread never writes, and a dead thread may have left batches at the store process.
- **The store process's `write-cancel` and `batches.ts`** stay but no client sends a cancel any more. Removing them touches `types/daemon-writes.ts`, `write-protocol.ts` and `write-desk.ts` (outside this brief); a follow-up can.
- **Test pause point `store-written`** added to `daemon/test-pause.ts`'s union (one member, outside the brief's list), for the B5 proof with real processes.
