## Who reads `imports` (searched at `02e286d10`)

Every graph write takes `imports` from the closures the runner just fetched, never from `#runnerClosures`:

- `revision.ts` `resolveClosures`: `setClosure(closure)`, then `storeClosures(context, resolved, { closures })` with the same objects.
- `revision.ts` `keyRunnerRetry` / `storeRunnerRetry`: `retry.closures`, the same objects, to `storeClosures`.
- `refinement.ts` (`applyRunnerPart`): `part.closures` to `setClosure`, then `bindWalks(part, ...)` to `storeClosures`. A walk changed meanwhile is carried in a fresh part, which the runner fetches again.
- `import-rewalk.ts` `apply`: fresh closures from the runner to `recordImportGraph({ closures: kept })`. `keysAlike` compares `paths` only.
- `record-tier.ts` `storeClosures(context, refs)`: no fetched part, so no graph write.

In `keying.ts`, the kept closures are read for `testFile`, `paths` (`assembleClosure`, `runtimeApplication`) and `packages` (`#dependencySegment`). `KeyIndex` gets the assembled `Closure`, which has no `imports`. `ci/export.ts` keeps its own closure map, in a one-shot command, not in the daemon. The map's type now omits `imports`, so a new reader of the kept copy fails the typecheck.

## Decisions the spec did not settle

1. **When to drop `imports`:** at `setClosure`, not after `recordImportGraph`. The kept copy is never read for them, and the graph writers read the caller's object, which keeps them until the part is done. Dropping at the write would need `keying.ts` to know about graph writes.
2. **A copy, not a mutation:** `kept` copies the closure without `imports`; it does not delete the field from the caller's object, because that object is the fetched part the graph is written from, sometimes later (`bindWalks`, `storeRunnerRetry`).
3. **`keptClosure(ref)` is public** for the test. No product code calls it.
