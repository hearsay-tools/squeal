## Blockers

### B1. Proven: the new keep payload exceeds its socket contract

Locations: `src/core/code/gate/keep-sent.ts:36`, `:55`, `:57`. Boundary: `src/core/daemon/protocol.ts:25` and `server.ts:112`.

021-20's done-when: “Both write through the daemon when one serves.” Spec 020 D17.3 requires the completed file's coverage record and results at its key.

The new request carries the whole coverage record, or all result records, in one JSON line. `lineLimit` gives only requests beginning `{"type":"write",` the 32 MiB allowance. A `keep` request retains the ordinary 64 KiB limit. On a large line, a socket data chunk without the terminating newline exceeds that limit and the server answers `request too long`. The keeper replaces this refusal with the old “a daemon runs ... and it keeps its own” note and stops saving its files. Coverage records with many loaded sources, or result lists with many checks or long failure text, can exceed 64 KiB without violating a gate limit.

The independent probe sent a valid record with 10,000 unread module paths through `writeThroughDaemon` to `createDaemonServer` and `createHandlers`. It used the real `keepInDaemon` and stores. The transport rejected it before `requestKeep` ran. A control stored exactly that record through `keepInDaemon` successfully:

```text
LARGE_RECORD {"bytes":209095,"largeError":"a daemon runs in this worktree, and it keeps its own","daemonRequests":0,"direct":{"kept":true}}
```

Fix scope for one 021-20 worker: give keep records and result lists a supported, bounded transport. Extend the applicable line contract or use chunking/a file handoff with content verification. Preserve request size protection. Do not turn a payload-size refusal into an older-daemon explanation. Add real-socket regressions with coverage and results above 64 KiB, including fragmented input, and assert both the stored record and keyed results with no client store write.

### B2. Proven: a committed keep loses its answer on client timeout and is reported as not kept

Locations: `src/core/code/gate/keep-sent.ts:37`, `:42`; `src/core/daemon/request-desk.ts:64`. Report: `src/core/code/gate/keep.ts:255`.

The brief explicitly requires “a kept answer is never lost on a client timeout (no duplicate rows, no lost record).” The vision requires trustworthy state and evidence for claims.

Both the initial request and each status request have a two-second socket timeout. A rejection escapes the writer immediately. The keeper reports the remaining files as not kept. Nothing reconciles a committed result after a lost reply. For the initial request, the only request id was generated by the daemon and was inside that lost reply; the client cannot even ask for the stored outcome. A server may finish the write before a delayed or interrupted connection times out.

The probe placed a forwarding Unix socket between a real `Keeper` and the real daemon handler. It forwarded the coverage request normally. For the results request it forwarded the request immediately, let the daemon commit, then delayed only its answer for 2200 ms. No SQL failure, fake outcome or shortened client timeout was injected. After `Keeper.flush()`:

```text
LOST_KEPT_ANSWER {"notes":["1 completed test file was not kept in the stores: no answer from <temporary proxy socket> in 2000 ms"],"storedRows":1,"storedOutcome":"pass","delayedReplies":1}
```

The row survived and was not duplicated in this probe. The proven break is the lost committed-write answer and the false not-kept statement; this does not claim that SQLite lost a committed row. A timeout of the earlier coverage reply also stops the keeper before it sends the file's results.

Fix scope for one 021-20 worker: make a sent keep identifiable before acceptance, retain its outcome, and reconcile transport failures through that identity. Repeating the same request must not run its mutation again. Retry status for an accepted request without creating a new write. Distinguish a proved refusal from an unknown outcome if the daemon cannot be reached. Keep recovery bounded and preserve the input recheck before a genuinely new write attempt. Add delayed/lost initial-reply and status-reply tests through the socket; assert one mutation, both stored artifacts, and truthful notes. Merely raising `ANSWER_MS` leaves this failure intact.

### B3. Proven: keep accepts rows the gate cannot produce and poisons keyed-result reads

Locations: `src/core/daemon/write-protocol.ts:169`, `:175`; `src/core/daemon/keep-request.ts:68`.

The brief requires that “the daemon's keep handler cannot be used to write outside the gate's rows.” The `ResultRecord` contract in `types/store-records.ts:134` excludes unknown keyed results: “Crashes and timeouts are not stored here.” `RunOutcome` is `pass | fail | skip`.

The parser checks only that each record is a non-null object, then asserts `ResultRecord[]`. The daemon forwards that unchecked data to `storeResults`. The store's SQL schema requires text for `outcome`, but does not restrict its values. With a new key and no prior flips, the transaction commits an `unknown` outcome and returns `kept: true`. A subsequent normal keyed-result read throws when its decoder validates the outcome. Thus the new socket can persist rows outside the keeper's result contract, rather than refuse them with no write.

The independent probe sent an otherwise complete file-level result through the real keep socket, with `outcome: "unknown"`. It polled the returned request id, checked the stored SQL row, and called `store.results.byKey(key, 0)`:

```text
OUTSIDE_GATE_ROWS {"outcome":{"kept":true},"persisted":{"outcome":"unknown"},"readError":"squeal store: outcome has unexpected value unknown"}
```

Fix scope for one 021-20 worker: validate the complete keep payload before any mutation. Admit only the result/check kinds and outcomes the keeper writes, with valid keys, locations, errors and provenance, and the single-file/key relationships of one keep. Validate coverage records too; an object assertion is not that contract. Refuse invalid payloads without changing either store. Add socket tests for `unknown`, an invalid check kind, mixed files/keys, malformed coverage and a valid gate payload. Continue to use the existing store operations; this finding does not call for a generic SQL interface or a new authorization system.
