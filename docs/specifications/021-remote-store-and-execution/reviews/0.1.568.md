## Blockers

### B1. Proven: a state written after the count read loses its count

Location: `src/core/code/store/prune.ts:137`, especially the `search` at line 141 and `recheck` at line 143.

Requirement: row 021-33 done-when (3), “a row that stops matching between the read and the delete is kept.”

The old count delete tested all three conditions under the write lock: age, absence from `files`, and absence from `states`. The new outside-lock search still tests all three. Its write-side `UNUSED_COUNT` omits `counts.blob NOT IN (SELECT s.blob FROM states s)`.

Reproduction through the real `pruneCodeSlices` and code-store repositories:

1. Store count `(old, typescript, 1)` at `NOW - 8 days`; no file or state references it. Set retention to seven days and live worktrees to `["w1"]`.
2. Run through the yielded read of `counts` keys. Before its delete slice, call `code.states.upsertMany` with a complexity state in `w1` whose `blob` is `old`.
3. Finish the slices. The state remains, but the count is deleted.

Probe output:

```json
{"inserted":true,"stateRows":1,"countsRemoved":1,"count":null}
```

This is a lost retention guarantee, not just an extra cache miss: `src/core/code/pass/bodies.ts:39` reads the count at the state's judged blob to recover its function body hashes. The current file can already name a different blob. The worker notes acknowledge the race, but no approved amendment waives done-when (3). The passing race test covers a new **file** reference only.

Fix scope: restore the state-reference test under the lock through an indexed lookup. An additive index on `states(blob)` in `CODE_INDEXES` can support that without raising `user_version`. Add a race test for a new state reference, including when no file names that blob. Do not fix this by restoring a whole-state-table scan under the lock.

### B2. Proven: reversed claim order lets two daemons prune one interval

Location: `src/core/daemon/clone-prune.ts:45`, `:51`, `:52`; the future-mark handling at `:23` to `:25`.

Requirement: row 021-33, “a daemon skips its prune when another pruned within the interval,” and done-when (2).

The claim transaction is atomic, but it compares the current mark with the invocation's captured `at`. A second invocation can begin later and claim first. The earlier invocation then treats the newer mark as a clock rollback and claims again. `SlicedPrune` pauses between the first read and the claim; separate daemon processes can reach these writes in either order.

Deterministic probe with two real store connections on one clone, an empty mark and a one-hour interval:

```ts
const make = (store, at, name) => oncePerClone(
  store, at, 3_600_000, () => [() => ran.push(name)], () => {},
);
const first = make(a, 1_000_000, "a");
const second = make(b, 1_000_001, "b");
first.next().value();  // a reads stale
second.next().value(); // b reads stale
for (const slice of second) slice(); // b claims and prunes
for (const slice of first) slice();  // a also claims and prunes
```

Actual output: `{"ran":["b","a"],"mark":"1000000"}`. Both prune, and the older invocation overwrites the newer mark. The existing simultaneous-reader test gives both invocations the same timestamp and runs their claims in start order, so it misses this failure.

The same mechanism also needs its interval boundary corrected: `slackMs` permits a second prune after 59 minutes for the default hour. The existing test explicitly expects this. That is earlier than the brief's “within the interval” rule; there is no recorded amendment accepting it.

Fix scope: distinguish a mark changed by a competing claimant from a mark that was already ahead of the clock when read. Compare the observed mark again atomically and use a current claim time, with a clock supplied as a callable if needed. Preserve expiry after an abandoned claim and recovery after real clock rollback. Test different captured times, both claim orders, a delayed claim, and the full interval boundary. Remove the early-expiry slack to meet the stated interval.

### B3. Proven: the new write-side rechecks still scan whole tables

Locations: `src/core/store/prune-unused.ts:56`, `src/core/code/store/prune.ts:166`, and `src/core/store/prune-unused.ts:27`.

Requirement: row 021-33 outcome, “no prune slice scans a table while it holds the write lock.” The helper's contract also requires indexed rechecks (`src/core/store/prune-keyed.ts:12`).

The target keys are bounded, but these predicates build an unbounded reference set inside each delete transaction:

| Actual delete rule | Write-side predicate | Actual `EXPLAIN QUERY PLAN` detail |
| --- | --- | --- |
| Main-store unused checks | `id NOT IN (SELECT check_id FROM consumer_views)` | `SCAN consumer_views USING COVERING INDEX sqlite_autoindex_consumer_views_1` |
| Code-store unused checks | `id NOT IN (SELECT check_id FROM views)` | `SCAN views` |
| Ended checkpoints | `id NOT IN (LAST_COMPLETED_CHECKPOINTS)` | `SCAN w USING COVERING INDEX sqlite_autoindex_worktrees_1` |

The probe opened real stores with their current indexes, seeded an unused check and an old checkpoint, and drove `dropUnusedChecks`, `dropEndedCheckpoints`, and `pruneCodeSlices`. A `Connection.run` wrapper captured each actual delete and its parameters while `observeWrites` showed that `BEGIN IMMEDIATE` held the lock. It ran `EXPLAIN QUERY PLAN` on those exact statements. The target lookups were `SEARCH checks USING INTEGER PRIMARY KEY (rowid=?)` and `SEARCH checkpoints USING INDEX ... (id=?)`; the scans above remained as list subqueries under that lock. Scanning a covering index still visits the whole reference table. No invariant bounds the number of view rows.

Fix scope: make both view-reference tests indexed per candidate. Additive indexes by `check_id`, or searches over the full view-key prefixes, can support this. For a checkpoint, re-test its own worktree's latest completed checkpoint by `checkpoints_by_worktree`, rather than rebuilding the latest checkpoint of every worktree. Preserve every keep condition. Add query-plan or equivalent bounded-work evidence for these write statements, with populated reference tables. A low observed duration on one copy does not establish absence of a scan.
