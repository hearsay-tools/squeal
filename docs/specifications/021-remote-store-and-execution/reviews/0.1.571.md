## Blockers

### B1. Proven, coordinator-found: `squeal remove` cannot stop the new store process

Locations: `src/core/store-process/paths.ts:29`, `src/cli/remove.ts:239`, and the removal call at `src/cli/remove.ts:82`.

The new process holds `locks/store-code.sqlite` for its life. `holdDaemonLocks` treats every `.sqlite` lock except `waiter-*` as a worktree daemon lock. Removal asks the recorded worktree daemons to stop, then waits on this extra lock. It never asks its store process to stop. The process can remain in its five-minute grace after the daemons end. Removal returns nonzero and says a worktree daemon did not stop.

Evidence: the coordinator reported the failing `test/cli/remove.test.ts` and requested that it be listed as B1. Its repair was already in progress. This reviewer did not repeat that proof. The exact source trace above independently explains the regression introduced by the new lock.

Required repair: include the store process in removal's stop-and-lock sequence. Keep the exclusion that prevents deletion while a writer still uses the file. Test removal with a live store process, not only a different lock filename.

### B2. Proven: a timeout leaves a batch live after throwing retryable BUSY, so later work can lose or duplicate it

Locations: `src/core/store-process/relay.ts:224` and `:245`, `src/core/store-process/guard.ts:95`; retry contract: `src/core/store/busy.ts:51`.

D22.4: "A batch is written once: the client learns whether a lost batch was written before it writes again." D22.3 also requires per-worktree order. D2 requires retrying busy writes. Here, `#write` throws BUSY when its late direct attempt cannot take the lock, while the relay/store process still owns the original batch. The next transaction gets a new sequence. While the first is in flight, it can write directly and move the high-water mark beyond that unresolved batch.

Two probes demonstrate both outcomes. Both warm a real relay first and use a 200 ms client busy timeout.

**Loss/order trace:**

1. Stop the store process with `SIGSTOP`. A plain connection holds `BEGIN IMMEDIATE`.
2. `store.meta.set("first", "1")` times out and throws BUSY. The store process has not resolved that job.
3. Release the SQLite lock. `store.meta.set("second", "2")` writes directly while the first is still in flight. Its later mark commits.
4. Resume the store process. Wait until a subsequent batch is acknowledged through the relay.
5. `second` is `"2"`; `first` is **null**. The server treated the later mark as proof that the earlier batch was written. The assertion failed: `expected null to be '1'`.

**Duplicate/retry trace:**

1. A plain connection holds `BEGIN IMMEDIATE`.
2. `store.transitions.append([t])` throws BUSY at the client bound. `t` is one `first-seen-fail` transition for `src/a.ts::f` at revision 1.
3. Release the lock. The original sent job commits. Wait until history contains that one transition.
4. Retry the same failed write closure, as a busy-write caller does. It gets a new sequence and appends it again.
5. History contains **two** equal transitions. The assertion failed: `expected ... to have a length of 1 but got 2`.

The mark correctly deduplicates a *single sequence*. It does not establish that every lower sequence committed, nor preserve identity across a caller's retry. The existing timeout test waits for the late job before its next write. The kill test uses idempotent meta upserts. Neither excludes these failures.

Required repair: give unresolved writes one owner and stable identity through recovery. Do not advance a worktree's committed prefix past an unresolved predecessor. A retryable BUSY must mean that attempt cannot later commit, or the retry path must explicitly settle that same pending batch. Preserve the main-thread wait bound. Add both non-idempotent retry and unresolved-predecessor tests.

### B3. Proven: schema shutdown drains old-schema writes instead of refusing them

Locations: `src/core/store-process/server.ts:133`, `:160`, `:203`; `src/core/store-process/writer.ts:82`.

D22.2 requires exit when the file's schema is newer. The server also promises to refuse queued work on stop. `stop` changes the phase, then waits for `pumping` to finish. The pump never tests that phase. It runs every queued batch and every remaining slice before the queue can be drained as refusals. The writer does not re-read the file's schema after taking the SQLite lock.

Probe with a real writer thread:

1. A plain connection holds `BEGIN IMMEDIATE`.
2. Send numbered old-schema writes 1 and 2. Write 1 waits for the lock; write 2 queues.
3. A schema-plus-one request triggers `stop("newer-schema")` and is refused.
4. While still holding the lock, set `PRAGMA user_version` to `CODE_SCHEMA_VERSION + 1`, then commit.
5. The process ends as `newer-schema`, but **queued old-schema write 2 committed** after the upgrade. Expected no `old:2` meta row; actual `{ value: '1' }`.

Required repair: stop taking queued jobs/slices as soon as stopping starts, and reject the remainder. Check schema under the write lock before executing a job, so a job already waiting for that lock cannot write against an intervening upgrade. Test both queued and lock-waiting jobs. Complete server/thread cleanup before releasing the singleton lock.

### B4. Proven: a relay thread that exits before shutdown makes daemon shutdown hang

Locations: `src/core/store-process/relay.ts:160` and `:188`; `src/core/daemon/daemon.ts:1338` and `:1390`.

The constructor discards worker errors and retains no exit state. `close` attaches a new `once("exit")` listener. If the thread already exited, that event never occurs again. The one-second timer calls `terminate()` but ignores its already-resolved result, then waits forever on the missed event.

Probe: construct `CodeRelay` with a missing relay module to inject a worker startup/load failure; wait 200 ms for it to exit; race `close()` against 1,500 ms. Actual result was **false** for closed. Expected true. This tests the thread-failure path; it is not a claim that candidate packaging omitted the module.

Precise daemon consequence: shutdown awaits `relay.close` before runner close, escaped-child cleanup, main-store close, socket close and singleton-lock release. `#step` catches rejections but puts no deadline on a pending promise. Thus a handled relay startup error can leave the daemon and its resources alive after stop.

Required repair: retain the worker's lifetime/exit promise from construction. Let `close` join an exit that already happened, and await forced termination when needed. Close the local port too. Test a failed/previously exited relay and a healthy relay with a late job.

### B5. Proven: D22.6 reports a failed fallback as a completed local write

Required repair: count committed outcomes separately from fallback attempts. Attribute a mark-confirmed/late remote commit to the remote writer. Count failed local attempts and unresolved jobs explicitly. Add a log assertion while the local transaction fails, not only on successful direct fallback.

### B6. Proven: guarded writes bypass D3's long-write log

Required repair: preserve the observer around the guarded lock hold, and forward writer-thread long-write events to the process log with the batch's operation identity and row count.
