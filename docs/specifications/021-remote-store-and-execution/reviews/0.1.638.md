## Nonblocking upgrade note

**N2, plausible: a very long or suspended old prune can outlive its index check.**
`src/core/code/store/prune.ts:205` drops `states_by_blob`. In the base's prune,
the `hasIndexes` decision is made once before the count rule, outside its
later write slices. Independent SQL plans confirm that the old unrestricted
`s.blob = counts.blob` test uses `states_by_blob` while it exists and becomes
`SCAN s` after removal. The new partial index cannot serve that old query.

The shared `prune:last-at` claim prevents ordinary overlapping prunes inside
one interval. A prune paused beyond the interval could resume after another
daemon claimed and dropped the index. That lifecycle was not reproduced;
there is no demonstrated routine overlap or measured hold regression here.
It is not a blocker. If long-lived old prunes become an observed problem, a
bounded follow-up should defer retirement while such an old prune is active
and cover the paused-generator sequence. Do not weaken the keyed recheck.

## What fits

- **Count readers.** Audited all product `counts.get` calls. `pass/bodies.ts`
  reads a state blob, but both callers supply complexity states: `oldBodies`
  and `stage-edit.ts:117`. Coverage seed `#hadOf` uses its saved file row;
  the step uses the current file row. Seed handles an aged-out saved count
  as unknown and seeds quietly. Delivery evidence/line readers, reach and
  CLI code reports also use file rows. No count reader was found that uses
  a crap or uncovered state's blob.
- **Keyed prune.** The count predicate is repeated in the keyed DELETE under
  the write lock. The independent plan for that DELETE with only the new
  index is `SEARCH counts USING PRIMARY KEY`, `SEARCH f USING COVERING INDEX
  files_by_count`, and `SEARCH s USING COVERING INDEX states_complexity_blob
  (blob=?)`. The only scan is the input `json_each`. The populated-table plan
  tests and the race tests in `prune-keyed` passed unchanged in purpose.
- **The early-delete window.** The new transaction removes only other measures
  of removed checks in that worktree. It emits no transition and does not
  advance the cursor. Complexity adoption and meta still switch together.
  Existing `staged.test.ts` observes complete old or new complexity snapshots
  and observes the intended earlier omission of retired coverage states.
  `planCodeDelta` requires a removal transition before telling a removal, so
  absence alone cannot manufacture a recovery/removal notification.
- **Interruption and store-process order.** An independent probe injected an
  interruption at `sent()` after the early delete became durable and before
  adoption. A separate reader saw old `f,g` complexity, no removed coverage
  state, file counter version 2, and cursor counter version 1. Retrying the
  version-2 pass produced `f,h`, cursor version 2 and zero false transitions.
  The same probe passed through the real store process: 23 batches sent,
  zero direct writes. This verifies failure/retry at that boundary, not an
  operating-system crash test. In production, `createCodePass` serializes
  passes and runs coverage only after `runPass` returns; a nudge cannot start
  a concurrent step there. `store.sent()` before adoption drains the staged
  writes and early delete; the relay preserves worktree batch order.
- **Older daemons.** No table, column or `user_version` changes. Older writes
  maintain the partial index through SQLite. Versions 0.1.570 through
  0.1.637 can recreate their separate full index at a creating open. Their
  prune uses it when present and skips the count rule when it is absent at
  its guard. Pre-0.1.570 code had no dependency on that index. The new prune
  alone retires it, with a second check under the lock; creating and reader
  opens leave it in place. The regression tests prove coexistence, preserved
  rows and an unchanged schema version, plus no write lock for an already
  absent retired index. Old-version rebuilds can recur about once per clone
  prune interval during overlap, not on every new-version creating open.
  The notes' 5.2-second old-index rebuild and estimated new-index startup
  cost on the large store are not new measurements of this candidate.
- **Reader memory.** Every open now receives `cache_size=-16384` and
  `temp_store=MEMORY`, readers included. This is a page-cache target, not an
  eager 16 MiB allocation or a process memory limit. A separate-process probe
  scanned 60,000 synthetic states with 256-character blobs: the 2 MiB cache
  reader grew from 56.93 to 58.93 MiB RSS; the 16 MiB reader grew from 56.94
  to 73.31 MiB. About 14.38 MiB extra RSS is therefore a real possible cost
  per busy reader. Temporary query storage and JS allocations are additional.
  Hooks use `withCode` and close the connection on completion, or at the
  held delivery's commit/rollback. This does not reserve that memory for
  every idle hook. The pending benchmark must supply aggregate workload
  evidence; this probe does not claim that typical hooks fill the cache.
- **CI isolation and guard.** Neither import test belongs to `UNIT`; both use
  the `isolated` project at `vitest.config.ts:107`. Vitest 5.0.3 defaults to
  `pool: forks` and `isolate: true`. Its pool shares a runner only when both
  tasks have isolation disabled; it terminates an isolated runner after
  its file. Thus this helper's `process.env` deletion cannot reach the parent
  or another test file under this config. Checked the marker list against
  installed std-env 4.3: omitted provider markers are non-CI providers. A
  throwaway copy that omitted `GITHUB_ACTIONS`, run with that marker true,
  exited 1 with `test/ci/no-ci.ts: Vitest still reads CI; a CI variable is
  missing from CI_MARKERS, or Vitest's node API loaded before this module`.
  This simulates a newly recognized CI marker missing from the list. The
  four real matrix runs prove that the current helper loads early enough.
  Other `CI: ""` uses under `test/` are key/environment assertions, not this
  record/export mismatch pattern.
