## Blockers

### B1. Proven: an old hook can delete a newer `--until-start` stop

**Location:** `src/core/delivery/stopped.ts:55`, `:93` and `:104`; the null-tree update at `:97` uses the same unprotected read/update pattern.

**Contract:** 011 C9, row 011-254: "No tree print, edit, Git operation or daemon heartbeat clears it ... only `squeal start` does". Wave 12's done-when 4 also requires preservation of the R2 start/stop race rule.

The hook reads the file after Git returns, compares that value with its original mark, then unlinks the pathname. Another process can replace the file after that read and before the unlink. The comparison protects only replacements that finished before the read. Atomic rename prevents a partial JSON read; it does not make the read, comparison and removal one operation.

**Reproduced schedule, on the exact clean candidate:**

1. Create a real Git fixture and store, with no daemon or worktree row. Leave a plain file stop with `at: 1000` and `tree: "old tree"`.
2. Read that mark and call `stopHolds(store, { id, root }, mark)`. Git returns a different tree.
3. Let `readStopFile` perform its real `readFileSync` and obtain the old JSON. Pause the hook before it uses those bytes.
4. Run the shipped `plugins/claude-code/dist/cli/squeal.mjs stop --until-start <fixture>` in a separate process. It exits 0 and writes a new file with `untilStart: true`.
5. Resume the hook with the bytes it already read. Its comparison passes. `removeStopFile` unlinks the newer stop, and `stopHolds` returns `false`.

The scheduling control wrapped the built-in read, using `syncBuiltinESMExports`. It returned the real bytes without modification. The competing stop used the actual bundled CLI, not a replacement implementation. The relevant wrapper was:

```js
const originalRead = fs.readFileSync;
let armed = true;
fs.readFileSync = function (path, ...args) {
  const value = originalRead(path, ...args);
  if (armed && String(path) === stopPath) {
    armed = false;
    execFileSync(process.execPath, [
      cli, "stop", "--until-start", root,
    ]);
    // originalRead(stopPath, "utf8") now contains untilStart: true.
  }
  return value;
};
syncBuiltinESMExports();
const holds = await stopHolds(store, { id, root }, mark);
```

**Impact:** the boundary is allowed to ensure a daemon after a successful `stop --until-start`. Later boundaries also find no mark. The command's success message promises a state the hook has erased without any explicit start.

**Why the green tests miss it:** `test/harness/stopped-file.test.ts:78` replaces the mark while Git is pending. That replacement precedes the final file read, so the comparison sees it. No test puts a competing mutation between that read and the file update.

**Fix, one repair row:** give all file stop mutations one shared per-worktree serialization rule. Include `leaveStoppedMark`, `clearStoppedMark`, and the hook's compare/fill/remove operation. Read and check the mark inside that rule before changing it. Keep this independent of the shared `store.sqlite` write lock. One more read before unlink leaves the same race. Atomic rename of the writer's temp file alone also leaves it.

Add a controlled two-process regression for the schedule above. Check both the returned hold decision and persistence of the newer `untilStart` mark. Cover the null-tree fill under the same rule, so it cannot overwrite a newer stop or restore a mark after an explicit start. Keep the existing idle-linked-worktree, held-WAL-lock, legacy-clear and fresh-heartbeat checks green.
