## Blockers

### B1. Proven: a failed hold write still starts the command and returns success

Location: `src/cli/hold.ts:93`, especially the busy-only return at line 94 and command start at line 111.

D1: "No one-shot command reports success after a failed store write." The review brief also requires that hold never starts its command unstored.

Only `not: "busy"` stops execution. `writeWithin` also returns `not: "failed"` for a rejected write. That branch prints a warning, sets `held` to null, and starts the command. A write failure such as a full disk therefore still runs the command without its hold and returns the command's success code.

Probe: create a fresh git repository and Squeal store; install a SQLite `BEFORE INSERT ON meta` trigger with `SELECT RAISE(ABORT, 'review write rejected')`; close that connection; call `holdCommand(['--', 'touch', ran], io, { ask: async () => null })`.

```text
HOLD_FAILED_WRITE {"exit":0,"ran":true,"stderr":"squeal: nothing is on hold: its Squeal store could not be written (review write rejected)\n"}
```

Fix scope, 021-07: distinguish the established no-store fallback from an attempted write that failed. Return `HOLD_NOT_STARTED` before spawning for the latter. Add a non-busy write-failure test that checks both the exit code and absence of the command's side effect. Preserve the bounded-busy tests.

### B2. Proven: socket writes can fail after the free-lock check and are not retried

Locations: `src/core/daemon/busy-writes.ts:49`; `src/core/daemon/daemon.ts:1066`.

D2: socket requests that write "use the sliced, retried path ... instead of one 5 s wait"; goal 2 forbids a busy write left unretried.

`writable()` retries an empty transaction, releases its lock, then the actual scheduler request runs outside the retry and slice. Another process can acquire the lock in that gap, or during an awaited scheduler operation. This is not a reservation of the write lock.

Probe: start a real fixture daemon. Wrap `DaemonWrites.prototype.writable` only to acquire a second SQLite connection's `BEGIN IMMEDIATE` immediately after the original method resolves. Arrange rollback on a 100 ms timer. Send `run-group` for `tests`, then read `run-group-status`. The actual unsliced write blocks that timer for about 5 s and fails; after rollback the request retains the error rather than being retried.

```text
SOCKET_POST_PREFLIGHT_BUSY {
  "status":{"ok":true,"type":"run-group","group":"tests",
    "requested":null,"unknown":false,"error":"database is locked","holder":null},
  "elapsedMs":5212
}
```

The first probe's `retry` variant also left the stored request unclaimed after a 5 s wait. That retry record remains available to a later reconciliation; the group request above proves the unretried request failure.

Fix scope, 021-08: make the actual socket operation's persistence retryable, retaining its pending state and memory changes between attempts. Retry the commit or a safely repeatable request stage; do not blindly repeat queue/checkpoint creation. Test contention acquired **after** preflight and verify both the eventual answer and event-loop progress between slices. The existing test holds the lock before preflight and cannot catch this gap.

### B3. Proven: an unlimited test timeout removes the host deadline too

Location: `src/core/runner-host/proxy.ts:219`.

D6: "Every request has a deadline the daemon sets." D7 requires a host that misses one to end the run incomplete and be replaced.

`timeoutMs: null`, a supported runner policy, becomes a null protocol deadline. `HostConnection.request` installs no timer in that case. A host hung in a transform or adapter call stays live forever if its process does not exit. The tier never reaches `unknown`, and the recovering runner has no reason to replace it.

Probe: serve a fake adapter whose `run` never resolves. Start the proxy with `runMarginMs: 20` and `callMs: 20`; run with `timeoutMs: null`; inspect it after 100 ms, then kill it for cleanup.

```text
UNBOUNDED_RUN {"settled":false,"killed":false,"gone":false,"elapsedMs":100,"runMarginMs":20}
```

Fix scope, 021-11: give the host request a finite watchdog even when the test policy has no timeout. Keep test timeout and transport/liveness policy distinct. Add a null-timeout hung-host test that reaches `timed-out`, stores no results, and permits replacement. Worker notes describe the current null behavior, but `status.md` contains no accepted exception to D6 for it.

### B4. Proven: EOF during startup leaves the adapter that finishes later unclosed

Locations: `src/core/runner-host/host.ts:103`, `:133`, `:252`.

D6: "When its input ends, the host stops its run and its workers and exits."

`start` awaits `options.build` before setting `adapter`. EOF during that await calls `stopAll`, which sees null, resolves immediately, and permanently settles its memoized shutdown. `start` can then assign and return the late adapter without checking `ending`. No code closes that adapter. A worker it created before the factory returned can survive the host's exit.

Probe: use `serveRunnerHost` through the stream-pair helper. Block the adapter factory on a gate; give the adapter a live child and a `close` that kills it. End input after the factory begins, await `served`, then release the factory. The child was explicitly killed by the probe afterward.

```text
EOF_DURING_START {"served":true,"adapterClosed":0,"workerAlive":true}
```

Fix scope, 021-11: account for the pending factory in shutdown. An adapter obtained after shutdown begins must close and must not become a live host instance. Bound that cleanup and retain the worker-stop guarantee. Add a start/EOF test with a factory that has not resolved, in addition to the existing EOF-after-run test.

### B5. Proven: opening a new code store can still wait inside the main-store hold

Locations: `src/core/delivery/held-connection.ts:134`; `src/core/delivery/code-source.ts:129`. The boundary they leave unguarded is `code-source.ts:63`, before `openCodeStore` constructs the holding connection.

D3: "Whatever it reads from the code store, it reads before it takes the write lock." The accepted amendment still requires that the code-store lock inside the main hold never waits.

The new zero-timeout rule applies only to `HoldingConnection.hold()`. Opening `code.sqlite` precedes that call. `openCodeStore` can migrate a schema-0 file under its configured busy timeout before it creates `HoldingConnection`. If another daemon is initializing that new file, `codeLockFree` times out before the main hold and swallows the error. The code delivery then opens the file again inside the main hold and waits for the same migration lock a second time.

Probe: create a new WAL `code.sqlite`, user version 0, with another connection holding `BEGIN IMMEDIATE` and an uncommitted initialization table. Make a holding code source with a 100 ms timeout. Run `codeLockFree(source)`, take the main store's `HoldingConnection.hold()`, then call `withCode(source, ...)`.

```text
CODE_MIGRATION_INSIDE_HOLD {"codeSchema":0,"currentSchema":1,"mainHeld":true,"elapsedMs":101,"busyTimeoutMs":100,"result":null}
```

Fix scope, 021-09: apply the no-wait rule to the entire code-store open path when any main hold exists, including WAL setup and migration, or carry a fully prepared code access into the hold. If open cannot complete without waiting, omit the code part and keep it owed. Add the initialization-lock case to `hold-code-wait.test.ts`; its current-schema fixtures bypass this path.

## Should-fix

### S1. Plausible: native stdout without a newline can hide the next protocol frame

Location: `src/core/runner-host/protocol.ts:172`; related stdout interception at `src/cli/runner-host.ts:113`.

`takeStdout` redirects JavaScript `process.stdout.write`, but a native write or a test child with inherited fd 1 bypasses it. `LineReader` accepts the marker only at the start of a newline-delimited line. A partial stray write followed by a protocol frame becomes one unmarked line and discards the valid reply. That can cause a needless host timeout. The worker notes acknowledge inherited-stdio output; no complete failing Vitest scenario was run here, so this is not blocking.

Fix scope: harden framing or isolate the protocol descriptor. Add a protocol case with stray bytes lacking a newline immediately before a frame. Keep diagnostics off the protocol channel.
