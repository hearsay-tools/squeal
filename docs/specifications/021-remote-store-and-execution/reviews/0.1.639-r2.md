### B1 resolution: one lock covers the final read and file change

**Contract:** spec 011 C9: "No tree print, edit, Git operation or daemon heartbeat clears it ... only `squeal start` does". Wave 12 done-when 4 preserves the start/stop race rule.

`src/core/presence/lock-events.ts:124` adds `withStopFileLock`: a separate per-worktree `<lockFile>.stopped.lock` SQLite file, `BEGIN EXCLUSIVE`, a synchronous callback, then rollback and close. The default busy wait is 2000 ms. This does not take the shared `store.sqlite` write lock.

The production mutation callers use that same lock:

- `src/cli/stopped-mark.ts:70`: read the kept mode and write the new mark under the lock.
- `src/cli/stopped-mark.ts:101`: clear an existing file under the lock.
- `src/core/delivery/stopped.ts:60`: after Git answers, read, compare and fill or remove inside the locked callback. `fileOutcome`, at line 101, has no await. A lock failure returns a hold decision. Legacy store work occurs after releasing the file lock.

The new five-test two-process regression passed. It covers a newer stop landing before the hook takes the lock, a CLI stop waiting behind a held lock, null-tree fill preserving a newer stop, null-tree fill leaving a start-cleared mark absent, and a busy lock holding the stop. Existing file, mode, legacy clear, held-WAL and fresh-heartbeat tests in the focused run also passed.

The independent probe placed contention at the first review's exact vulnerable boundary, after the hook's real file read returned old bytes but before its comparison and mutation:

1. Create a real Git fixture and store with no daemon or worktree row. Write an old plain file stop.
2. Wrap `fs.readFileSync`, using `syncBuiltinESMExports`, to pause that final read after obtaining the real bytes.
3. Spawn the actual bundled CLI with `stop --until-start <fixture>`. A preload signals immediately before and after the child's real `BEGIN EXCLUSIVE`.
4. Wait for the child's lock attempt. Keep the hook paused another 100 ms and verify the child has not acquired the lock. Return the old bytes to the hook.
5. Let the hook finish and release its lock. Require CLI exit 0, a surviving `untilStart: true` file, and a holding decision at the next boundary.

Run this for edit-clear and null-tree fill. Actual output, omitting generated fixture paths:

```text
tree=old tree: CLI waits while hook has already read old bytes
tree=old tree: hook holds=false; CLI exit=0; final untilStart=true; next hook holds=true
tree=null: CLI waits while hook has already read old bytes

```

The edit-clear decision can precede the concurrent stop. The important change is that the stop cannot complete between the hook's read and mutation. Its later mark survives. If the stop takes the lock first, the regression verifies that the hook sees and honors it. Both mutation orders now obey B1's contract.
