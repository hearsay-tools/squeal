## B1: busy GC can run while a tier is active

**Proven, blocking (021-29).** `src/core/daemon/idle-gc.ts:179-185`, and the missing running-tier input to `busyGcDue` at lines 47-67. The brief requires that the busy GC cannot run during a tier. The existing `#running` guard protects only `idleGcDue`. The busy branch checks the remembered end of any tier and does not check whether another is active.

Two ordinary sequences reach the GC with one active tier:

1. Tier A ends, setting `#tierEnded = true`. Tier B starts before the lifecycle check. The check sees A's end and collects during B.
2. A and B run together in different lanes. A ends. The check collects while B is still running.

The fake-clock probe used `IdleGc` itself, a heap reader initially at 100, and an injected GC that records an independent active-tier count and resets the heap to 100. The clock advances only 1 s, so the idle trigger cannot fire. For the first sequence, the essential calls are:

```ts
idle.ready();               // heap reader: 100
idle.started();             // A
now += 1_000;
idle.ended();               // A
idle.started();             // B
heap = 301;
idle.check();               // injected GC called with B still active
```

For the second, call `started()` twice before `ended()` and do not start B afterward. Actual probe output:

```json
{"probe":"busy-gc","overlap":false,"gcs":1,"collectedActive":1}
{"probe":"busy-gc","overlap":true,"gcs":1,"collectedActive":1}
```

The existing long-tier test consumes `#tierEnded` with a check before starting the long tier. It therefore proves only the case where no earlier tier end remains pending. The real-daemon test waits for settled tiers before making the heap large. Neither excludes these sequences.

**Repair for one worker:** make the active-tier count part of the busy eligibility rule. Do not collect while any tracked run remains active. Check after the final tier ends, keep the one-minute limit across both kinds of GC, and preserve the idle behavior and shutdown guard. Add fake-clock regressions for both sequences above. They must fail on this candidate and pass after the repair.

## B2: removed source paths can accumulate in the loader-set cache

**Proven, blocking (021-31).** `src/core/code/crap/cache.ts:142-148`, with `src/core/code/crap/loader-map.ts:88` and `99-109`. This breaks the review brief's requirement that the retained map's memory is bounded. Cleanup of `LoaderMap.#sets` is skipped based on the size of a different cache, `StepCache.#conditions`.

When the test listing changes between empty and nonempty, `LoaderMap.end` reports `moved = "all"`. `StepCache.#forget` clears conditions, signatures and early signatures. It does not clear loader sets. A source with no loaders has no slot to remove it through `#spread`; its `"no-loader"` set therefore survives. After the current sources' conditions are rebuilt, their count does not exceed the current source count, so `keep` returns before calling `#map.keep`.

Reproduction through real `StepCache` and `LoaderBuild`, without private-field access:

1. Keep one current source path, `src/renamed-0.ts`. List one test whose closure contains only itself. Read the loaders, call `cache.condition(source, loaders)`, then `cache.keep([{ path: source }])`. This caches that source's `"no-loader"` set.
2. Remove the last listed test and rename the source to a new path. Invalidate, read, compute the current source's condition, and call `keep` again. The listing change clears conditions. The old source's set survives.
3. Add the test back, rename the source again, and repeat the same operations. The listing change again clears conditions. Cache the new path's set.
4. Repeat 1,000 reads, alternating one listed test and none. Only one source remains current after each read. Capture the actual map passed to the `LoaderBuild` constructor. After the reads, wrap its public `of` method to count calls. Call `map.set` for the 500 former source paths that had a nonempty listing. All return `"no-loader"` with **zero** calls to `of`, proving all 500 obsolete entries remain cached.

Actual output:

```json
{"probe":"removed-source-loader-sets","oldPathsRetained":500,"currentSources":1,"recomputed":0}
```

The loop can continue with new paths and no growth in the current source or loader population. This is retained path storage for the daemon's life, not a temporary allocation peak. The new cleanup test covers only conditions growing past the file count; it does not cover clearing conditions before deciding whether the independent loader-set cache needs pruning.

**Repair for one worker:** decide whether the loader-set cache needs pruning from its own occupancy or source membership. Do not gate its cleanup on condition count. Preserve the fast common case without an unconditional closure walk. Add a regression that changes listing emptiness while renaming/removing no-loader sources and proves obsolete set entries are dropped or their total stays bounded by the current source population. Keep the existing incremental-update and fresh-map comparisons.

The latter preserves the pending tier end while any tier runs. `ended` queues one deferred check when the final tier ends. That callback reads the active count again, so starting another tier before it runs does not permit collection. The next final end queues a new check. One callback is kept even if several tiers end before the event loop turns.
