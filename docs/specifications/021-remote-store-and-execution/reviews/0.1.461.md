## Blocker B1: reopening does not wait for the idle host's teardown

**Proven.** `src/core/daemon/runner.ts:100-106`, `123-127` and `249-256`. Violates D20.3, "A planned close is not a crash", and the brief's requirement to avoid races between the idle timer, a starting call and close.

`park()` clears `inner`, retains only the adapter and its environment in `parked`, and starts `current.close()` without retaining its promise. The next call therefore reaches `options.create()` while the old host can still be running its global setup teardown. This is ordinary asynchronous cleanup, even though no adapter call remains in flight. The old and new instances can hold the same exclusive resource. The wrapper's final `close()` also clears `parked` and only waits for `creating` and `inner`, so it returns while the old close is still in progress.

### Reproduction and result

The temporary probe used `createRecoveringRunner` around `createHostedVitest(SOURCE_LAUNCH, "0.1.461", { root })`, with `gone: runnerHostGone` and `idleMs: () => 100`. `SOURCE_LAUNCH` is the source launch in `test/runner-host/process-helpers.ts`; this did not use a stale build. The fixture held one passing test and this global setup, with the three paths replaced by absolute paths in its private ignored fixture:

```ts
import { closeSync, existsSync, openSync, rmSync, writeFileSync } from "node:fs";

export default function setup() {
  closeSync(openSync(resource, "wx"));
  return async () => {
    writeFileSync(teardownStarted, "");
    while (!existsSync(release)) {
      await new Promise((resolve) => setTimeout(resolve, 20));
    }
    rmSync(resource, { force: true });
  };
}
```

The actual probe bounded the teardown wait to 20 s and released it in `finally`. It performed these steps:

1. Call `runner.testFiles()` and `runner.run(refs, options)`. The first run passes.
2. Wait until idle close writes `teardownStarted`. Verify the resource still exists.
3. Call `runner.run(refs, options)` again before releasing the old teardown.
4. Await `runner.close()`, then check whether the old teardown still holds its resource.
5. Write `release`, wait for resource removal, and remove the fixture.

The failure is caused by a planned idle close with unchanged test and setup bytes. A service listening on a fixed port has the same lifetime conflict. It is not a hypothetical interleaving: two real source-host processes overlapped and the second returned a crashed run with a structured setup failure.

### Fix for one worker

Keep the planned close promise as part of the recovering runner's state. Await it before creating or using the replacement host, and await it during final close even when `inner` is null. Preserve the environment snapshot and the distinction from `replaced`. Recheck the permanent `closed` state after any awaited close barrier so shutdown cannot start a replacement. `LaneInstance` in `src/core/daemon/slow-instance.ts:158-175` already uses a closing promise for these two lifetime boundaries.

Add regression coverage with a gated asynchronous close: reopening must wait; final close must wait; releasing the gate must permit the next run without a note, unknown check or extra recreation. Include close during a queued reopen and concurrent callers so only one replacement starts.
