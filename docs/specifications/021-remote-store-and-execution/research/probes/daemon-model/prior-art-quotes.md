## 1. Bazel persistent workers (and multiplex workers)

- **Unit.** One process per worker key, with a pool of processes per key: "Each combination of mnemonic and start-up flags is combined into a WorkerKey, and for each WorkerKey up to worker_max_instances workers may be created." (persistent). Multiplex keys include the execution root: "Bazel uses the key's hash code (composed of environment variables, the execution root, and the mnemonic) to determine which WorkerMultiplexer to use." ... "each unique mnemonic can only have one WorkerMultiplexer and one worker process." (multiplex). Each worker gets its own working directory: "Each worker instance is assigned (but not chrooted to) a separate working directory under <outputBase>/bazel-workers." (persistent)
- **Transport and message shape.** "The Bazel server communicates with the worker using stdin/stdout. It supports the use of protocol buffers or JSON strings." "Each protocol buffer is preceded by its length in varint format". "JSON requests and responses are not preceded by a size indicator." (creating). A worker "reads WorkRequests from its stdin" and "writes WorkResponses (and only WorkResponses) to its stdout." (creating). The request carries `arguments`, `inputs`, `request_id`, `cancel`, `verbosity` and `sandbox_dir`. The response carries `exit_code`, `output`, `request_id` and `was_cancelled` (proto). Concurrency: "If request_id is 0, this WorkRequest must be processed alone (singleplex), otherwise the worker may process multiple WorkRequests in parallel (multiplexing)." (proto)
- **Inputs and proof.** A request includes "a list of path-digest pairs representing the inputs the worker can access (this isn't enforced, but you can use this info for caching)" (creating). The digest is advisory: "The format of the contents is unspecified and the digest should be treated as an opaque token. This can be empty in some cases." (proto) "a digest is passed along with each input file. Thus the compiler or the wrapper can check if the input is still valid without having to read the file." (persistent) The paths are local: "either a path relative to the execution root (the worker process is launched with the working directory set to the execution root), or an absolute path." (proto) There is no input-content transfer. The worker reads the host's files.
- **Cancellation.** Opt-in: "add supports-worker-cancellation: 1 to the execution-requirements field ... and set the --experimental_worker_cancellation flag." "Each non-cancel WorkRequest message must be answered exactly once, whether or not it was cancelled." "The server may send cancel requests for requests that the worker has already responded to, in which case the cancel request must be ignored." "Once a response has been sent for a WorkRequest, the worker must not touch the files in its working directory." (creating)
- **Health and versioning.** The fetched protocol has no ping or heartbeat message. Capabilities are declared per action rather than negotiated: `"supports-workers" : "1"`, `"supports-multiplex-workers" : "1"`, `"requires-worker-protocol" : "json"` (creating, persistent). Forward compatibility: "JSON workers must tolerate unknown fields in these messages, and use the protobuf defaults for missing values." (creating). The same binary must also work one-shot: "only make itself persistent if that flag is passed, otherwise it must do a one-shot compilation and exit." (creating)
- **Crash and fallback.** "For actions that do not support persistent workers, Bazel falls back to starting a tool instance for each action." The docs recommend a local fallback: "this example includes specifying local as a fallback to the worker strategy: bazel build //my:target --strategy=Javac=worker,local" (persistent). For racing: "the experimental dynamic strategy, which races a remote execution and a worker execution" (persistent). "Using dynamic strategy requires workers to be sandboxed." (persistent). The fetched pages do not describe what happens when a worker process dies mid-request.

## 2. Bazel Remote Execution API (REAPI v2)

- **Unit.** One action. The client does not address a particular worker: "The server MAY choose to execute the action on any worker satisfying the requirements, so the client SHOULD ensure that running the action on any such worker will have the same result." An `Action` "captures all the information about an execution which is required to reproduce it." The proto defines only client-facing services (`Execution`, `ActionCache`, `ContentAddressableStorage`, `Capabilities`). It defines no service between the scheduler and the executor. The executor side is internal to each server.
- **Transport and message shape.** gRPC (with HTTP annotations). `rpc Execute(ExecuteRequest) returns (stream google.longrunning.Operation)`. Stage metadata goes through `CACHE_CHECK`, `QUEUED` ("awaiting a free machine to execute"), `EXECUTING` and `COMPLETED`. Output streaming: "the client can use this resource name with [ByteStream.Read] to stream the standard output".
- **Inputs and proof.** Inputs are uploaded first and named by digest: "the client must first upload all of the inputs, the [Command] to run, and the [Action] into the [ContentAddressableStorage]. It then calls `Execute` with an `action_digest` referring to them." `input_root_digest`: "The files in the directory tree are available in the correct location on the build machine before the command is executed. The root directory, as well as every subdirectory and content blob referred to, MUST be in the [ContentAddressableStorage]." Missing inputs fail with a precise error: "`FAILED_PRECONDITION`: One or more errors occurred in setting up the action requested, such as a missing input or command or no worker being available." The server "SHOULD additionally send a [PreconditionFailure] error detail where, for each requested blob not present in the CAS, there is a `Violation` with a `type` of `MISSING`". Canonical form: "The input `Action`'s fields MUST meet the various canonicalization requirements ... so that it has the same digest as other logically equivalent `Action`s."
- **Cancellation.** Optional and delegated to the Operations API: "`CANCELLED`: The operation was cancelled by the client. This status is only possible if the server implements the Operations API CancelOperation method". "The server NEED NOT implement other methods or functionality of the Operations API." Per-action timeout: "A timeout after which the execution should be killed." `DEADLINE_EXCEEDED`: "The execution timed out."
- **Health and versioning.** "The Capabilities service may be used by remote execution clients to query various server properties, in order to self-configure or return meaningful error messages." `ServerCapabilities` carries `low_api_version` ("Earliest non-deprecated RE API version supported") and `high_api_version` ("Latest RE API version supported"). Transient load: "`UNAVAILABLE`: Due to a transient condition, such as all workers being occupied ... the action could not be started. The client should retry." Retries: "any call may return an error with a [RetryInfo] error detail ... clients SHOULD respect the information provided."
- **Disconnect and crash.** The client can reattach to an operation by name: "Wait for an execution operation to complete. When the client initially makes the request, the server immediately responds with the current status of the execution." On a lost operation: "`NOT_FOUND`: The operation no longer exists due to any of a transient condition ... The client should call `Execute` to retry." Execution is at-least-once: "The server MAY execute the action multiple times, potentially in parallel. These redundant executions MAY continue to run, even if the operation is completed." The proto itself defines no fallback to local execution. That is the client's choice (see Bazel's dynamic strategy above and Buck2 below).

## 3. Buck2

- **Unit.** "By default, there is 1 daemon per project root, you can run multiple daemons in the same project by specifying an isolation dir." The daemon is started on demand: "The first time that a Buck2 command is run, Buck2 starts a daemon process for the current project." (daemon). Opt-in sharing is experimental: "BUCK2_SHARE_DAEMON=true lets tenants in different isolation directories share a daemon while retaining separate output and cache state." (daemon). Persistent workers are per build command: "Workers are shared across actions within a single build command and are terminated when the command completes — they do not persist across separate invocations." (persistent_workers)
- **Transport.** Between the client and the daemon: "The Buck2 CLI runs in a client process, which sends commands to the Buck2 daemon via gRPC." (architecture). For workers there are two protocols: "Local workers use a Buck2-specific gRPC protocol over Unix domain sockets. Buck2 passes the socket path in the WORKER_SOCKET environment variable." "Remote workers use the Bazel persistent worker protocol (length-prefixed protobuf over stdin/stdout)." (persistent_workers). Remote execution: "Buck2 can use services that expose Bazel's remote execution API in order to run actions remotely." (remote_execution)
- **Inputs and proof.** The daemon watches files itself: "While it runs, the Buck daemon process monitors the project's file system for changes." (daemon). Remote execution uses REAPI digests: "Buck2 uses SHA256 for all its hashing by default." with `cas_address` and `action_cache_address` (remote_execution).
- **Cancellation.** Only tenant eviction is described: "buck2 kill evicts the selected (project root, isolation directory) tenant from the daemon and cancels its work. Eviction waits for cancellation and cleanup before returning." (daemon). The fetched pages say nothing about cancelling a single action.
- **Health and versioning.** "You can see detailed information about the status of the daemon by running buck2 status." Startup settings are checked on connection: "It is part of the daemon configuration checked on connection. Changing it restarts an unshared daemon." "Daemon groups require compatible startup configuration and binary versions. An incompatible invocation fails without restarting the group's daemon." (daemon)
- **Crash and fallback.** Mixed local and remote execution is a platform setting: "remote_enabled - set to True. local_enabled - set to True if you also want to run actions locally. use_limited_hybrid - set to False unless you want to exclusively run remotely when possible." (remote_execution). Worker fallback: "WorkerRunInfo bundles a worker with a fallback command for when workers are disabled". "Without workers (fallback): The final command is WorkerRunInfo.exe followed by the positional arguments." (persistent_workers). Restart: "The Restarter can automatically restart Buck2 when Buck2 detects that it hit a condition that may be recovered by restarting the Buck2 daemon." (restarter)

## 4. Gradle: build daemon, Worker API, Develocity Test Distribution

- **Unit (daemon).** The daemon is reused by compatibility, not tied to one project root: "*Gradle reuses an existing daemon only if its Java home/version and JVM args (e.g., org.gradle.jvmargs, GRADLE_OPTS) are identical." "Gradle starts a new Daemon if no idle or compatible Daemons exist." Its registry is per user and per version: "These logs are stored in the Gradle User Home directory under daemon/<gradle-version>/". Each build sends its project: "The Gradle Client sends the Gradle Daemon build information such as command line arguments, project directories, and environment variables so that it can run the build." (gradle_daemon)
- **Transport (daemon).** "Communication between the client and the Daemon happens via a local socket connection." (gradle_daemon). The message format is not documented on the fetched page.
- **Inputs (daemon).** The daemon watches files: "Watching the file system to calculate exactly what needs to be rebuilt before you run a build". It also keeps "in-memory caches of build data, such as the hashes of task inputs and outputs for incremental builds." (gradle_daemon)
- **Health and versioning (daemon).** "`gradle --status`" lists PID and IDLE or BUSY. "Currently, a given Gradle version can only connect to Daemons of the same version." Compatibility "is based on exact matches of these values": Java version, JVM attributes, JVM properties and Gradle version. Self-health: "When a memory leak exhausts available heap space, the Daemon: Finishes the currently running build. Restarts before running the next build." Auto-stop: "Available system memory is low" and "Daemon has been idle for 3 hours". (gradle_daemon)
- **Worker API isolation modes.** `noIsolation()`: "the work should be run in a thread with minimal isolation". `classLoaderIsolation()`: "run in a thread with an isolated classloader". `processIsolation()`: "run with a maximum isolation level by executing the work in a separate process. ... the process will be a worker daemon that will stay alive and can be reused for future work items with the same requirements." Worker daemons are matched by spec: "When a unit of work for a worker daemon is submitted, Gradle will first look to see if a compatible, idle daemon already exists. If so, it will send the unit of work to the idle daemon, marking it as busy. If not, it will start a new daemon." Parameters are serialized: "For processIsolation(), Gradle also serializes the parameters to transport them to the worker daemon process." Lifetime: "Worker daemons will remain running until the build daemon that started them is stopped or system memory becomes scarce." (worker_api)
- **Cancellation (Worker API).** "custom tasks should react to interrupting their executing thread. The same is true for work items submitted via the worker API. If a task does not respond to an interrupt within 10s, the daemon will shut down to free up system resources." (worker_api)
- **Test Distribution: unit and transport.** "The tests and their supporting files are transferred to each agent and executed, with their logging and results streamed back to the build in real time." "The build and Test Distribution agents connect to the Develocity server using a WebSocket connection." Agents dial out: "since the connection to the Develocity server is initiated by the agent, it can be deployed to an internal network and doesn't need to be addressable from machines running builds." (agent manual)
- **Test Distribution: agent requirements.** "The agent requires at least Java 21 to run and supports Linux, macOS, and Windows." "The agent itself needs about 128 MiB of memory". "The agent uses a local file cache to store JAR files and other artifacts that are required to execute tests." Authentication: "The agent sends the registration key to the Develocity server when starting up and once every hour to renew its registration." (agent manual). Builds must authenticate: "Unauthenticated usage of Test Distribution is prohibited due to the inherent security implications of such a remote code execution service." (user manual)
- **Test Distribution: inputs.** Inputs are sent from declarations: "The test runtime classpath and any additionally declared file inputs are transferred to the agents." "All inputs declared on the test task are tracked by Test Distribution and will be transferred to remote executors." Undeclared files are a known failure: "If your tests are expecting any other resources to be locally available, such as a running database, the test agents must also provide the resource or the tests will fail." Outputs: "After finishing execution of a test partition all output files that are registered on the test task are transferred back from remote executors to the build." (user manual). The fetched pages do not say whether inputs are content-addressed. The agent cache and the advice on reproducible archives ("minimise the number of input files transferred") suggest it, but that is not stated.
- **Test Distribution: capabilities.** "Requirements are matched against the capabilities of the agent pool those agents belong to." "Local executors are assumed to provide all required capabilities." (user manual)
- **Test Distribution: crash and local fallback.** "If there are no remote agents available, tests can still be executed locally on the build machine." "When an agent disconnects during the build, the plugin reschedules the affected test partition on another local or remote executor." "when the connection to the Develocity server is closed unexpectedly, the plugin attempts to reconnect and reschedules the affected test partitions." "As long as local executors are configured the build can always progress and thus won't time out." "If enabled, remote executors are tried first, falling back to local ones after waitTimeout expires." On the agent side: "If the connection is lost, e.g. when the server is restarted, the agent will periodically attempt to reconnect." (user manual, agent manual)

## 5. Pants (pantsd and remote execution)

- **Unit.** pantsd state lives under the build root (`pants_subprocessdir` "default: <buildroot>/.pants.d/pids"). The daemon runs one command at a time: "Because pantsd currently does not support parallel runs, any prior running Pants command must be finished for the current one to start." (global-options, `pantsd_timeout_when_multiple_invocations`)
- **Purpose.** "pantsd can significantly improve runtime performance by lowering per-run startup cost, and by memoizing filesystem operations and rule execution." (global-options). "Work is broken down into many small units and kept warm in a daemon so that as little work as possible needs to be re-done when files change." (how-does-pants-work)
- **Transport (client to daemon).** "The port to bind the Pants nailgun server to. Defaults to a random port." (`pantsd_pailgun_port`). The fetched pages do not describe the message shape.
- **Inputs.** The daemon watches files itself: `watch_filesystem` "Set to False if Pants should not watch the filesystem for changes. pantsd or loop may not be enabled." Restart triggers: "Filesystem events matching any of these globs will trigger a daemon restart. Pants's own code, plugins, and --pants-config-files are inherently invalidated." (`pantsd_invalidation_globs`)
- **Remote execution.** "'Remote execution' allows Pants to offload execution of processes to a remote server that complies with the Remote Execution API standard ("REAPI")." Platform match is required: "Pants requires that the server's operating system match the client's operating system." Workers are chosen by properties: "The REAPI execution service selects a worker for a process by consulting the 'platform properties' that are passed in a remote execution request." (remote-execution). Deadline: "Overall timeout in seconds for each remote execution request from time of submission" (default 3600). Maturity: `remote_execution` "Enables remote workers for increased parallelism. (Alpha)".
- **Cancellation, health and fallback.** The fetched pages do not describe cancelling a remote process, a pantsd liveness check, or falling back to local execution when the REAPI server is unreachable. A cache-only mode is offered: "you can use [GLOBAL].remote_cache_read and [GLOBAL].remote_cache_write to still run everything locally, but to use a remote cache."

## 6. Vitest custom pool (v5.1.0)

- **Status.** "This is an advanced, experimental and very low-level API." (pool docs)
- **Unit.** One `PoolWorker` per worker in one project. Reuse is gated: "This is called on workers that already satisfy certain constraints: - The task has the same worker name - The task has the same project" (`canReuse`, types.ts).
- **Interface.** `PoolRunnerInitializer { name; createPoolWorker(options: PoolOptions) => PoolWorker }`. `PoolWorker` has `on`, `off`, `send(message: WorkerRequest)`, `deserialize`, `start()`, `stop()`, an optional `canReuse(task)`, and optional `reportMemory` and `cacheFs` (types.ts). The transport is left to the implementer: "Your CustomPoolRunner will be controlling how your custom test runner worker life cycles and communication channel works. For example, your CustomPoolRunner could launch a node:worker_threads Worker, and provide communication via Worker.postMessage and parentPort." (pool docs)
- **Message shape.** `WorkerRequest` is one of `start` (poolId, workerId, environment, `config: SerializedConfig`), `run` or `collect` (`context: WorkerExecuteContext`), `stop` and `{ type: 'cancel' }`. `WorkerResponse` is one of `started`, `stopped`, and `testfileFinished` with `usedMemory`. `WorkerExecuteContext` has `files: FileSpecification[]` with `filepath: string`, `testNamePattern`, `testIds` and `testLocations`, plus `invalidates?: string[]` (types.ts, types/worker.ts, runtime/runner/types.ts). Listing goes through `collect`: `collectTests: (state, traces) => runBaseTests('collect', state, traces)` (pool docs).
- **What the worker needs locally.** The worker side is a Node module that imports Vitest: `import { init, runBaseTests, setupEnvironment } from 'vitest/worker'` (pool docs). The built-in forks worker loads its entry from the local install: `resolve(options.distPath, 'workers/forks.js')` (forksWorker.ts). Test files are named by path (`filepath: string`). Modules are transformed in the main process and fetched over birpc: `project._transformService.fetch(url, importer, environment, cacheFs, ...)`. Some results are `externalize` results that the worker imports itself ("builtins and network urls are already resolved inside the worker"). With `cacheFs`, the worker reads transformed code from disk: "the transformed code is already stored on disk either by the forks pool (`cacheFs`) or by `fsModuleCache` — the worker can read the file itself instead of fetching each module separately." (rpc.ts)
- **Remote machines.** The fetched docs and source do not mention running a pool worker on another machine. *Inference*: the interface is transport-neutral, but a remote worker would need a Vitest install, the same `node_modules` for externalized modules, the test files at the same `filepath` (or a path translation layer), and `cacheFs` off.
- **Cancellation.** `{ type: 'cancel' }` in `WorkerRequest`. The runner forwards a cancel reason over RPC: `this._offCancel = vitest.onCancel((reason) => this._rpc.onCancel(reason))` (poolRunner.ts). Reasons: `'keyboard-input' | 'test-failure' | ...` (runtime/runner/types.ts). Forced stop in forks: "If process running user's code does not stop on SIGTERM, send SIGKILL." with `SIGKILL_TIMEOUT = 500` (forksWorker.ts).
- **Health and versioning.** There is no version field in `WorkerRequest`. Start and stop are bounded by `START_TIMEOUT = 60_000` and `STOP_TIMEOUT = 60_000`, and a timeout surfaces as "[vitest-pool-runner]: Timeout waiting for worker to respond" (poolRunner.ts). The RPC has no per-call timeout (`timeout: -1`).
- **Crash.** An unexpected exit becomes an error naming the files that were running: "Worker exited unexpectedly ${errorDetails}during ${this._state} state${testFileDetails}" (poolRunner.ts). The fetched code shows no fallback to another pool.

## 7. Language Server Protocol 3.17

- **Unit.** One server per tool: "The protocol currently assumes that one server serves one tool. There is currently no support in the protocol to share one server between different tools." Workspace scope is fixed at start and can change later: `workspaceFolders` holds "The workspace folders configured in the client when the server starts." `workspace/didChangeWorkspaceFolders` informs "the server about workspace folder configuration changes."
- **Transport and message shape.** "The base protocol consists of a header and a content part (comparable to HTTP)." The header is `Content-Length`, "The length of the content part in bytes. This header is required." "The content part of a message uses JSON-RPC to describe requests, responses and notifications." Channels: "stdio: uses stdio as the communication channel.", "pipe: use pipes (Windows) or socket files (Linux, Mac)", "socket: uses a socket as the communication channel.", "node-ipc: use node IPC communication between the client and the server."
- **Inputs.** Open documents are pushed by the client (`didOpen`, `didChange`, `didClose` are mandatory). File watching on disk is preferably the client's job: "The watched files notification is sent from the client to the server when the client detects changes to files and folders watched by the language client". "Servers are allowed to run their own file system watching mechanism and not rely on clients to provide file system events. However this is not recommended". Reasons given: "a client usually starts more than one server. If every server runs its own file system watching it can become a CPU or memory problem." There is no content proof. Stale results are reported: "if a server detects an internal state change (for example, a project context changed) that invalidates the result of a request in execution the server can error these requests with ContentModified."
- **Cancellation.** Notification `$/cancelRequest` with `CancelParams { id }`. "A request that got canceled still needs to return from the server and send a response back. It can not be left open / hanging." Error code: "it is advised to set the error code to ErrorCodes.RequestCancelled." Servers should not drop work on their own: "servers should therefore not decide by themselves to cancel requests simply due to that fact that a state change notification is detected in the queue."
- **Capability negotiation.** "A development tool and the language server announce their supported features using capabilities." Handshake: "The initialize request is sent as the first request from the client to the server." "Until the server has responded to the initialize request with an InitializeResult, the client must not send any additional requests or notifications to the server." Requests sent before initialize fail with `-32002` (`ServerNotInitialized`).
- **Liveness and shutdown.** There is no ping. The server watches its parent instead: `processId` is "The process Id of the parent process that started the server. ... If the parent process is not alive then the server should exit". "To support the case that the editor starting a server crashes an editor should also pass its process id to the server. ... The command line argument to use is --clientProcessId." Shutdown takes two steps: `shutdown` "asks the server to shut down, but to not exit (otherwise the response might not be delivered correctly to the client)", then `exit`: "The server should exit with success code 0 if the shutdown request has been received before; otherwise with error code 1."
- **Crash.** "if a client notices that a server exits unexpectedly, it should try to restart the server. However clients should be careful not to restart a crashing server endlessly. VS Code, for example, doesn't restart a server which has crashed 5 times in the last 180 seconds." There is no fallback. The client restarts the same server.
