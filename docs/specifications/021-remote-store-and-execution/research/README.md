## Rules for findings documents

- Length: 1 to 4 pages. Structure: Questions answered (a table), Findings per question, Recommendation, Open questions for the human, Sources.
- Mark every finding `verified by experiment`, `read in official docs`, `read in source code` or `inferred`. Name the commit you read source at and, for outside tools, the version and the retrieval date.
- Sources: official docs and source repositories of the tools this brief names. Do not search the open web beyond them. Where a named product's own site does not answer a question, the answer is "not determined, because".
- No outside actions: no accounts, sign-ups, cloud spend, pushes, CI runs or GitHub settings. A trial that needs any of these is proposed as a later row with its cost, not run.
- Experiments on this host: in a fresh clone or fixture under your own `$TMPDIR`, never in the main checkout or another worktree. A remote host is a throwaway container on this host (`docker` is installed; if you cannot use it, say so and fall back to a second directory). SSH keys, `known_hosts` and every tool's state directory live under `$TMPDIR`: run tools with `HOME` set to a directory there, so nothing reaches the real HOME, `~/.ssh` or `~/.mutagen`. Download a tool's release binary into its own empty directory and verify its checksum. Stop every daemon you start (`squeal stop`, `mutagen daemon stop`), remove every container and clone before you finish. No full test suite, no `squeal run --all` in this repository's worktrees. Never run agent CLIs (Claude, Codex, Pi, OpenCode) against your real HOME.
- Load: this host is shared with other coordinators. Make no load on purpose. Skip any timing measurement when the one-minute load average is above the CPU count (24), retry it later in your session, and if it never drops, report the timing as not measured with the load you saw. Report the load during every timing you keep.
- Throwaway scripts live under `research/probes/<topic>/` with a README that says they are throwaway. `node_modules` stays out of git.
- Do not design the feature. Answer, measure, recommend; the coordinator writes the spec.
- Touch nothing outside `docs/specifications/021-remote-store-and-execution/research/`.

3. "A more performant store than SQLite for the remote path." Measure the batched lookup and the bulk import against two or three candidates in containers on loopback, with the round trip added by arithmetic as 018-03 did.
4. Is SQLite a bottleneck anywhere today? From existing measurements (`../../011-core/research/load-slowdown.md`, the store sizes in 018-03 Q2, `src/core/store/`): does any local store operation cost enough to matter? Keep the answer to evidence; the local store is not this topic's to replace.
5. An existing protocol. Could Squeal speak the REAPI action cache and CAS, or the Turborepo API, so a team reuses a server it already runs? Map a Squeal result (check identity, key, outcome, duration, failure text, closure) onto it and name what does not fit.
6. Fit and scope: vision principle 8, secrets in failure text, what a team pays. Does a live store belong in Squeal, in a Hearsay service, or nowhere? Recommend the smallest useful form beyond the git-ref route, or say the git-ref route is enough and why.

## Topic: store-contention

The local store is one SQLite file per clone (`<git common dir>/squeal/store.sqlite`, decision 0002). Every daemon of every worktree, and short CLI and hook processes, write to it. SQLite allows one writer at a time. Here the local store is in scope.

1. Inventory. Every lock failure on record: open issues #176, #138, #162, #158, #108; closed #1, #86, #186 (`gh issue view`, read-only); board rows 011-104, 011-113, 011-126; `../../001-core-loop/research/issue-8-contention.md`; and any other you find in `docs/` or the issues. For each: which process held the write lock, which operation waited or failed, the busy timeout it used, what the user saw, and whether it is fixed. Group them by cause.
2. The writers today, from source (`src/core/store/`: `open.ts`, `connection.ts`, `busy.ts`, `repos/`, `schema.ts`; every `openStore` caller in `src/cli/` and `src/core/daemon/`): which processes open the store for writing, the transaction mode (deferred or `BEGIN IMMEDIATE`), the busy timeouts, the longest write transactions and what they hold, WAL checkpoint settings. Measure on copies of this repository's and cezar's stores (copy to `$TMPDIR`; never open a live store for writing): table sizes, WAL size, and which tables are shared across worktrees and which are per worktree (`../../018-ci-and-shared-results/research/remote-store.md` Q2 has a first split).
3. Reproduce. In a small fixture clone under `$TMPDIR`, start several daemons (no more than 6, one per worktree) and drive edits and CLI reads, while recording lock waits and failures (SQLite's busy handler, the daemon logs). Name which of the issues in 1 reproduce. Only when the one-minute load is below 24, and short: this proves the mechanism, not a load test.
4. Options, compared on correctness first, then cost: (a) keep one file and fix the use: shorter transactions, `BEGIN IMMEDIATE`, retries, checkpoint policy; (b) split the file: a store per worktree for local state plus one shared file for content-keyed results (for example through `ATTACH`), and how cross-worktree reuse (decision 0002) survives; (c) one writer process per clone that the daemons send writes to; (d) another engine on the same machine: SQLite's `BEGIN CONCURRENT` branch, libSQL and Turso's rewrite (concurrent writes), PostgreSQL as a local server, LMDB. For each: which failures in 1 it removes, what code changes, the dependency it adds (native modules, size, platforms), migration of existing stores, and what a user must run. Read each engine's official docs or source at a named version.
5. Fit with the remote path. Which option would also make a remote or shared store (`store-service.md`) simpler, or harder? One paragraph; do not reopen that topic.
6. Recommendation: the smallest change that removes the failures in 1, with evidence, and what it would not fix.

## Topic: runner-split

The human wants Squeal's own test runs to execute on another machine over SSH, with the agent, the code and the daemon staying local. `../../019-run-triggers/research/remote-runner.md` found that the Vitest instance (Vite server, transforms, module graph) runs inside the daemon process, with workers that import `node_modules` by absolute `file://` path, so moving runs means moving the whole runner adapter. `remote-execution.md` (this folder) adds the rules a remote result must meet: a remote blob-id check of the run's closure as proof of the revision (Mutagen's `flush` is not one), an `equal` environment descriptor (spec 018 D1), and a deadline on every step. This topic finds where to cut and proves it with a prototype.

1. The cut. From `src/core/types/runner.ts` (`RunnerAdapter`) and `src/runners/vitest/` (`index.ts`, `adapter.ts`, `load.ts`, `run.ts`, `observe.ts`, `coverage.ts`): which members need the project's files or `node_modules` (listing, closures, module graph, runs, observed inputs, coverage) and which do not. Name the candidate cuts: the whole Vitest instance in a remote process that the daemon drives over a stdio protocol through SSH; or the Vite server local and only workers remote (019-04 says the `file://` contract forbids it; confirm or refute from Vitest's source). Say what crosses the connection for each member, and how large it is.
2. Paths and keys. Which values hold absolute paths (observed inputs, closures, coverage, failure locations), how they map between the local root and the remote root, and whether keys stay equal when the remote root differs (`result-import.md` Q1).
3. Prototype. A throwaway remote host process in a container over SSH (the setup of `probes/remote-execution/`, `HOME` under `$TMPDIR`): it loads the project's Vitest with `createVitest`, runs the files a local driver names over stdin and stdout, and returns results and observed inputs. The tree goes by rsync of named paths or a git tree (019-04 Q2), then the remote blob-id check. Use a small fixture and, if it fits, this repository at a fixed commit. Show one edit, one run, one result with its proof.
4. Time from save to verdict, by step (sync, proof, run, return), local against the container, with real round trips added by arithmetic at 1, 20 and 80 ms. Take timings only when the one-minute load is below 24; otherwise say not measured.
5. node:test and pytest: they start a process per file or batch (`src/runners/process/group.ts`). Is the cut `ssh` around the same command, and what of their graph files, temp directories and environment?
6. Failure: a dropped connection mid-run, a hung remote, a remote with another Node version or install. What the daemon records (never a pass, never a test failure), what status says, and what is retried.
7. Prior art for the protocol, one paragraph each, read in source or official docs: Vitest's own worker RPC (`birpc`), Bazel's remote execution API, Gradle Develocity Test Distribution. Recommend the cut, the protocol shape and the smallest first slice, with what it costs a user.

## Topic: daemon-model (third angle, the human, 2026-11-11)

The human: "Add a third angle - one daemon per project + multiple runners (local or remote) + store options. Looking for a good primitive that could contain this properly." This topic looks for one process model that holds the store question (`store-contention`), the remote runner (`runner-split`) and the host's load together, instead of three separate fixes. It runs beside those two topics and does not read their files; it may cite their questions as boundaries. Earlier file: `../../011-core/research/daemon-scope.md` (row 011-52, 2026-10-21): it rejected one daemon per repository on memory alone (0.8 to 1.1 GiB saved; the memory is per-worktree Vite graphs; a crash or hang reaches every worktree; one old session holds back every upgrade; Vitest needs `process.cwd()` at the root). Extend it; do not repeat it. Also read `../../011-core/research/load-slowdown.md` and `remote-execution.md` Q1 in this folder.

1. Today's model, from source (`src/core/daemon/`, `src/core/scheduler/`, `src/core/store/`, `src/core/types/runner.ts`): what one daemon owns (watcher, revisions, hashing and keys, scheduling, runner instances, store writes, delivery to sessions), what is already per clone (the store, locks), and what each worktree's daemon repeats. Which of the open lock issues (#176, #138, #162, #158, #108) come from several processes writing one file, and which would remain with one writer.
2. Candidate primitives. Name each by what it owns and where its boundary is. At least: (a) a project daemon per clone that owns the store as its only writer, the scheduler and one CPU budget for the host, with worktrees as clients and runner hosts as separate processes, one per worktree and runner, local or over SSH (011-52's design (c), widened); (b) daemons per worktree as today plus one store broker per clone; (c) daemons per worktree as today plus a shared pool of runner hosts per host. 3. The runner host as a primitive. What a process that hosts one runner for one root must offer the scheduler (list, closure, run, observe, cancel, health), so that the same interface serves a local child process and a remote host over SSH. Compare with the protocols other tools use for this: Bazel persistent workers (the worker protocol) and remote execution executors, Buck2's daemon and remote execution, Gradle's daemon, worker API and Test Distribution agents, Pants' `pantsd`, Vitest's custom pool API, and the Language Server Protocol's process model. Read each in official docs or source at a named version.
4. Scheduling across worktrees. With one scheduler per clone or per host: one CPU budget against the slowdown knee (`load-slowdown.md`: 14 to 16 busy vCPUs), priority of edit tiers over background tiers across all worktrees, and fair shares. From the stores (copies) and sar history: how much background work would a host-wide budget have deferred or dropped in the last week, and what would it have done to edit-tier latency? Make no load to measure it.
5. Store under each primitive. With one writer, what changes for SQLite (no writer contention; readers in CLI and hooks), and whether another engine is then needed at all. With remote runner hosts, where results are written. One paragraph per primitive; the engine comparison belongs to `store-contention`.
6. Migration. From today's layout to the recommended primitive in steps that each ship and each work alone, and what a user with several worktrees sees during the move.
7. Recommendation: the primitive, its boundaries and its interface in outline, what it fixes and what it does not, and the smallest first slice. Where the honest answer is that today's model with targeted fixes is better, say so with the evidence.
