## Adapter decisions that changed, and how the `adapter:pytest` kind reads them

1. **Closure.** After a run, a test file's observed paths, its `closure()`, the store's `pytest.observed.<project>` key and its stored closure hold what its child Python processes found. Before, they held only what the pytest process imported. 011-48's closures case (`tests/test_child.py` runs `python -m pkg`) shows it: its keys differ, which the kind reads as a re-key.
2. **`affected`.** A test file is `direct` for a path its child found. Before, such a path did not affect it at all.
3. **Session.** The rule "an importer never imported in-process joins the session" now reads in-process `import` edges only. Old inputs give the same result, since no `spawned` record existed before.
4. **Run environment.** `SQUEAL_PYTEST_FILE` is removed from the pytest process's environment, and a test sees it, its own file's real path, while it runs.

## The raise to `PYTEST_ADAPTER_VERSION` 3 (coordinator decision (b), 2026-10-22)

The kind folds every step's closure and `affected` into keys (011-48 notes, decision 14), so decisions 1 and 2 read as a re-key, and a re-key asks no raise. A raise needs a case that stores a different outcome under equal keys (task 011-37 D6). The case "a test sees its own file in SQUEAL_PYTEST_FILE while it runs" is that case: its test reads the variable, which decision 4 sets, so it passes here and fails at the last release. Its `why` also names the reason for the raise: results stored before this change sit at keys whose closures lack child-process imports, and only the raise re-keys them.

The case "a child Python's failed imports, an old-protocol finder, an unwritable events file, a sitecustomize after the hook and a bare script" runs the hook's remaining branches in child processes, on both Pythons. Three defensive branches no process can reach were removed; their behaviour stays the same. A finder held off `sys.meta_path` asks no other finder. A hook whose directory is not on `sys.path` chains nothing. `_record` cannot raise.

**Option (c), for a row.** The `adapter:pytest` kind reads each step's closure as a key, so a change that grows a closure only after a run counts as a re-key and asks no raise. The scheduler finds a result stored before such a change at the key the first step computes, which the change leaves equal, so that result stays current until its file runs again. The verdict could compare the steps before the first run as keys, and count a later step whose keys grew at equal earlier keys as a reason to raise.

## Repair of review 0.1.268 B2: a script that imports nothing

The hook recorded `__main__.__file__` inside `find_spec`, so a script that imports nothing, or only modules cached at start-up, asked no finder and was never recorded: an edit kept its test's pass current. Now `_record` records `sys.argv[0]` at start-up when it names a file. Python 3.8 and later set `sys.argv` before `site` runs (PEP 587; checked on 3.10 and 3.13): `python tool.py`, `./tool.py` and an absolute path give the script, `-m` and `-c` give `-m` and `-c`, stdin gives `-`. No `__main__.__file__` fallback at exit was added: every other way to run a file as `__main__`, `-m`, a directory, a zip's `__main__.py`, asks a finder, so such a fallback would record nothing the start-up record and the finder do not. Regressions: the hook test "records a script that imports nothing", the live scheduler test over `outcomes/test_spawn_tool.py` (its `tool.py` only prints; an edit to print something else re-keys the file, runs it and fails it) on both Pythons, and a bare script in the `adapter:pytest` children case. `PYTEST_ADAPTER_VERSION` stays 3: no release carries 3 yet, so no stored result sits at a key this repair changes.

## Known gaps

- **Stored results from before the change** are re-keyed by `PYTEST_ADAPTER_VERSION` 3, so each pytest file runs once after the release that carries it.
- **The `direct` mark lives in memory only.** The store keeps spawned paths with the other observed paths. So another worktree, or this one after a daemon restart, finds the test file as `transitive` until it runs there. The verdict stays right: the closure holds the path, so an edit still re-keys the file. To make the mark persist, add a meta key beside `pytestObservedMetaKey` (`src/core/types/runner.ts`) and its read and write in `src/core/daemon/pytest-runners.ts`. Both are outside this row's files.
- **Not observed:** a process started with an explicit `env` that drops `PYTHONPATH` or the variable, or started with `-I`, `-E` or `-S`. Also every process of a project whose own `PYTHONPATH` entries, which come before the runtime directory, hold a `sitecustomize`: that one shadows the hook. A module found by a finder of the old `find_module` protocol is not recorded either. A `multiprocessing` fork child was already observed, because it inherits the pytest process's wrapped `__import__`.
- **Expected failures in this tree:** the four "bundles exactly as the build produces them" tests, because worker trees do not build.

## Cost

Without the variable, the hook takes about 1 ms per Python start (3.10 and 3.13, bytecode cached), most of it importing `importlib.machinery`. The pytest process pays this once. With the variable, each import pays one delegation through `sys.meta_path`, plus one `realpath` for each new file found.
