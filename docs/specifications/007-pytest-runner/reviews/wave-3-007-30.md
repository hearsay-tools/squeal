## Blockers

### B1, proven: regrouping grants a third run after the same file and key were withheld twice

`src/core/scheduler/stability.ts:114` to `117`; call and application at `src/core/scheduler/scheduler.ts:515` and `527`.

007-30 requires: “A second withhold of the same file and key in a row leaves it `unknown` and adds a daemon note naming the touched path.” 007-31 check 1 explicitly asks that the second withhold produce only the note and normal unknown state.

`Withholds.retry(files)` returns one boolean: `true` if **any** member is new at its key. `recordTier(..., installMoved || retry, ...)` then re-queues **every** member of that tier. The per-file map therefore bounds a fixed tier, but does not enforce the promised per-file bound when the queue changes its grouping.

Deterministic reproduction using `test/scheduler/claims-fixture.ts`:

```ts
const { main } = claimRepo(3);
const a = side(main, { count: 3, tierSize: 2, backlogTierSize: 2 });
a.runner.during = files => {
  for (const file of files) {
    const path = join(main, file.path);
    writeFileSync(path, readFileSync(path));
  }
};
await a.scheduler.start();
await a.scheduler.idle();
expect(a.runner.ran(fileName(0))).toBe(3); // observed defect; contract requires 2
```

All three files have stable content and keys, and no revision is created. The first tier withholds `f00` and `f01` and puts them behind the untouched `f02` already queued. The second tier holds `f02` and `f00`. `f00` is now withheld twice at its original key, but `f02` is new to the map, so both are re-queued. `f00` runs a third time in the fourth tier. The second-tier note says it “runs once more”, rather than leaving `f00` unknown then. The final note incorrectly says two runs when `f00` has run three times. Nothing from these runs is stored, and the finite fixture eventually stops, but both the retry budget and the second-withhold note/state contract are broken. With more fresh files joining withheld tiers, the excess grows.

Fix sized for one core worker: classify first and exhausted withholds per file and key, then pass that classification into recording. Queue only first-withheld files, preserve their previous state, and mark exhausted files unknown without re-queuing them. Keep withholding every result from the report; do not store the other files' results as a shortcut. Emit retry and exhaustion notes for the corresponding subsets. Add this three-file/two-file-tier regression, requiring exactly two runs per unchanged key and the exhausted file to stop at its second withhold even when it shares a tier with a fresh file. Keep existing single-file, slow-tier, provenance and claims tests.

## Should-fix

### S1, plausible: final provenance cannot catch transient publication by a withheld run

`test/integration/stamps-repo.ts:180` to `187`, and `test/scheduler/withheld-retry.test.ts:47`.

The changed checks read `results.listForCheck` only after the later run has finished. This is not retained history of every run: `results` has primary key `(check_id, key)` (`src/core/store/schema.ts:116`), and `putMany` uses `INSERT OR REPLACE` (`src/core/store/repos/results.ts:78`). A first-run record published and then replaced by a later same-key record disappears from this query. An external store probe verified that publishing `withheld-first`, then `later-retry` under one check/key makes the final `listForCheck` return only `later-retry`. The helper's `not.toContain(ran[0])` would accept that final provenance.

This is a test gap, not evidence that the candidate leaks results: the changed recording path bypasses storage correctly. The 001-168 barrier's reason is precisely that a transient false PASS must never be available for delivery or inheritance, so final correctness alone is weaker than its safety contract.

Fix in the B1 test row: wrap or spy on the test store's `results.putMany` and reject any record whose provenance names a withheld run; alternatively hold the retry before its report returns and assert the store remains empty for the withheld check/key there. Keep final provenance assertions as well. Use a previously validated file too, and assert that its prior state survives the first withhold while its retry is pending. These checks must distinguish old legitimate rows from new withheld-run rows.
