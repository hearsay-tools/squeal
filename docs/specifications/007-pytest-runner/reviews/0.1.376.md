## Blockers

### B1 (proven): the commands can create an external environment instead of `.venv`

Location: `src/runners/pytest/environment/states.ts:55`.

The new note says the two commands "create `.venv` there" and rewrite
`.pdm-python` to that `.venv`. The refusal tests only `python.use_venv = false`;
it does not require PDM's `venv.in_project` setting to be true. A valid local
configuration can therefore reach this note:

```toml
python.use_venv = false
[venv]
in_project = false
location = "/absolute/path/outside-the-project"
```

Independent probe, using the installed PDM 2.29.4, an empty dependency list,
`requires-python = ">=3.10"`, and an existing `__pypackages__` directory:

```text
PDM_USE_VENV=true pdm use -f     -> exit 0
PDM_USE_VENV=true pdm install    -> exit 0
.venv/pyvenv.cfg exists          -> false
.pdm-python                     -> <outside>/outside-<hash>-3.12/bin/python
pdm.toml unchanged              -> true
environmentState(root, project) -> state: "none", command: null, same note
```

The probe isolated PDM config and cache paths, used the stdlib venv backend,
and removed active-environment variables. The failure does not need an active
virtual environment or missing packages. With the same fixture and PDM's default
in-project setting, both commands succeeded, `.venv/pyvenv.cfg` existed, and
`environmentState` returned `ready`. These were scratch probes outside the tree.

PDM source confirms the cause: `Command.do_use` delegates to
`Project._create_virtualenv`, which passes `config["venv.in_project"]` to the
backend. `PDM_USE_VENV` does not override that separate setting. Squeal rejects
the resulting external `.pdm-python` during ordinary discovery.

This breaks the row's outcome, "the note tells the user how to get one today",
and the review requirement that the note be true in every refusal state.

Fix for one worker: make the note require or explicitly select an in-project
environment. Do not state that the current commands always make `.venv`.
If adding `PDM_VENV_IN_PROJECT=true`, verify interpreter selection too: a
selected existing virtual environment can bypass PDM's creation branch.
Keep `command: null`, discovery, states and keys unchanged. Add a regression
for the non-default PDM placement setting and update text/JSON expectations.

### B2 (proven): the note ignores a missing explicitly declared interpreter

Location: `src/runners/pytest/environment/states.ts:55`.
Relevant unchanged contract: `src/runners/pytest/environment/discover.ts:49`.

Set the project's Squeal `python` to `envs/test/bin/python`, leave that path

and save its interpreter in `.pdm-python`. Squeal still returns the same
`state: "none", command: null` note. Discovery returns immediately for the
missing declared path; it never checks `.venv` or `.pdm-python` in this case.

The independent probe reused the real `.venv` created by the successful default
case above and called the candidate's `environmentState` through `pnpm exec tsx`:

```text

```

Both calls used the same files. The second note still says "To get one today"
and "Squeal then checks that environment as usual". Its new instructions do
not resolve the refusal or identify the remaining declared-path requirement.
This is a counterexample to the brief's working stand-in outcome and the
explicit review requirement to check every state where this note can appear.

Fix for one worker: explain that a missing declared interpreter must point to
the new `.venv/bin/python`, or that the declared environment must be created
instead. Keep the choice with the user and keep `command: null`. Add a case
with a missing non-default `python` path. Do not change discovery to fall back
past an explicit declaration.
