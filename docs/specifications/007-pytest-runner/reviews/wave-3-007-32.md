## Blockers

### B1, proven residual: a forced exhausted file remains queued and runs a third time

Changed call site: `src/core/scheduler/scheduler.ts:536` and `542`. Existing contracts it calls: `src/core/scheduler/tiers.ts:384` to `386`, `src/core/scheduler/ledger.ts:339` to `347`.

007-32 requires: “Queue only first-withheld files and keep their previous state. Mark exhausted files `unknown` and do not re-queue them.” The review brief explicitly asks whether an exhausted file can ever run again from the whole-tier re-queue. It can when the queue entry is forced.

`recordTier(..., installMoved || again, ...)` takes its install-moved branch when any member needs its first retry. That queues every member and preserves each tier file’s `forced` flag. The new `ledger.markUnknown(held, ...)` corrects the exhausted subset only for ordinary entries: `markUnknown` intentionally removes an entry only when `!this.queue.isForced(file.ref)`. Thus the exhausted forced file stays queued. `startTier` accepts forced work without a result lookup, and runs it again.

Deterministic reproduction using the existing real-store scheduler fixture:

```ts
const { main } = claimRepo(3);
const a = side(main, { count: 3, tierSize: 2, backlogTierSize: 2 });
await a.scheduler.start();
await a.scheduler.idle();
const before = [0, 1, 2].map(i => a.runner.ran(fileName(i)));
const keys = [0, 1, 2].map(i => a.keyOf(fileName(i)));
const revision = a.store.revisions.latest(a.worktreeId)?.number;
a.runner.during = files => {
  for (const file of files) {
    const path = join(main, file.path);
    writeFileSync(path, readFileSync(path));
  }
};
const puts = vi.spyOn(a.store.results, "putMany");
await a.scheduler.requestFullSuite({ force: true });
await a.scheduler.idle();
expect([0, 1, 2].map(i => a.runner.ran(fileName(i)) - before[i]))
  .toEqual([3, 2, 2]); // observed break; required [2, 2, 2]
expect([0, 1, 2].map(i => a.keyOf(fileName(i)))).toEqual(keys);
expect(a.store.revisions.latest(a.worktreeId)?.number).toBe(revision);
expect(puts.mock.calls).toEqual([]);
```

After tier 2, the note says `f00 stays unknown until an input changes`. It nevertheless runs in tier 4, and gets the same second-withhold note again. All writes are same-byte touches. There is no intervening request, revision, key change, install change or claim takeover. This is the original per-file budget and note contract breaking through the repair’s new recording seam, not a new scope of review. The checkpoint honestly ends abandoned and no withheld run publishes a result; those guarantees do not repair the extra run.

Fix sized for one core worker: let `recordTier` accept the subset that needs a withhold retry, as an additive parameter, so it never temporarily queues exhausted files. Preserve install-moved behavior, existing forced-request semantics, and legitimate queued work for a newer key. Avoid changing `markUnknown` globally merely to erase forced entries, since that rule protects independent forced work. Add this forced-checkpoint variant beside the ordinary three-file regression; require `[2, 2, 2]`, no withheld writes, no pending exhausted entry, and one exhaustion note per file.
