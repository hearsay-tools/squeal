Topic `python-environments` of `research/README.md`. ## Findings

### 1. Interpreter discovery

- **In-tree `.venv`** (uv, PDM, plain `venv`). `pyvenv.cfg` holds `home`, `implementation`, `version_info` and, for uv, `uv = 0.12.2`; site-packages is `.venv/lib/python3.X/site-packages`. uv writes only the minor version (`version_info = 3.10`) and `home` names uv's minor-version directory (`cpython-3.13-linux-x86_64-gnu`), a link whose real path carries the patch (`cpython-3.13.14-...`); `realpath(.venv/bin/python)` gives it (`out/1-uv-layout.txt`, `out/4-env-hash.txt`). For a system interpreter the real path (`/usr/bin/python3.12`) carries no patch at all, so a distribution upgrade in place is invisible to files (inferred). Asking the interpreter costs 26 ms, 16 ms with `-I -S` (`out/6-managers.txt`). *verified by experiment.*
- **uv.** `uv run` syncs before running, so in a fresh worktree it installed 8 packages; `uv run --no-sync` still created an empty `.venv` and then failed `No module named 'app'`. `uv run --frozen --no-sync python -c pass` costs 63 ms against 26 ms for the interpreter directly (`out/2-uv-discovery.txt`). `UV_PROJECT_ENVIRONMENT` moves the environment; an absolute path is used as-is and "the environment will be overwritten by invocations in each project" (uv docs, below). *verified by experiment; read in official docs.*
- **PDM** writes `.pdm-python` (an absolute interpreter path, read before `.pdm.toml`, `pdm/project/core.py` `_saved_python`) and a `.venv` in the project. `pdm info --python` costs 420 ms and, in a fresh worktree, created a virtualenv as a side effect (`out/6-managers.txt`). *verified by experiment; read in source code (PDM 2.29.2).*
- **Poetry** puts environments in `<cache>/virtualenvs/<name>-<h>-py3.X`, `h` the first 8 characters of urlsafe-base64 `sha256(realpath(cwd))` (`poetry/utils/env/env_manager.py` `generate_env_name`), unless `virtualenvs.in-project` (global config, `poetry.toml`, or `POETRY_VIRTUALENVS_IN_PROJECT`) puts it in `.venv`. Two worktrees got `app-a6Ube3HM-py3.12` and `app-U8PTQ08u-py3.12`. `poetry env info -p` exits 1 in a fresh worktree; `poetry run` there created the environment. *verified by experiment; read in source code (Poetry 2.5.1).*
- **Hatch** puts environments in `<data>/hatch/env/virtual/<project>/<id>/<env>`, `<id>` from a sha256 of the project path (`hatch/utils/fs.py` `Path.long_id`); nothing is written into the project. `hatch env find` prints the path even when it does not exist (fresh worktree: `exists: no`). *verified by experiment; read in source code (Hatch 1.18.1).*
- **pyenv** selects a version from `PYENV_VERSION`, then `.python-version` in the current or any parent directory, then its global file; it names an interpreter, not an environment. uv reads `.python-version` too. **conda** environments live in `<base>/envs/<name>` or a prefix, named by `environment.yml`'s `name:`; activation exposes `CONDA_PREFIX`, which uv's discovery reads second, after `VIRTUAL_ENV`. *read in official docs.*
- **An inherited `VIRTUAL_ENV`.** An activated shell's `python` resolved to the other worktree's environment and code. `uv run` ignores a mismatching `VIRTUAL_ENV` with a warning unless `--active`. Running the worktree's own `.venv/bin/python` by path imported the right code under the other activation, but a test's `subprocess.run(["python", ...])` ran the other worktree's 3.13 interpreter and code from a 3.10 parent (`out/7-inherited-env.txt`). *verified by experiment.*

### 2. Worktrees

- **Fresh worktree, no environment.** Nothing can run; every wrapper that could run creates or syncs one (above), which is the agent's or human's call, not a validator's.
- **Nested worktree** (`.ai/cezar/worktrees/<id>`, defect 12's layout). Python never searches for a `.venv`. uv's project commands stop at the worktree's own `pyproject.toml` (`Found project root: .../b`), but `uv python find` in the same worktree returned the parent checkout's `.venv/bin/python3` ("virtual environment" search walks to "the nearest parent directory", uv docs). A daemon that walks up from the worktree, or asks `uv python find`, gets the parent's environment. *verified by experiment.*
- **Shared environment.** With `UV_PROJECT_ENVIRONMENT` shared, each `uv sync` rewrote `app.pth` to the syncing worktree's `src` (first `.../c/src`, then `.../main/src`). With worktree c using main's environment (a `.venv` symlink, or an inherited activation), c's edited `app` was not imported: the test that expects c's edit failed, `APP_FILE .../main/src/app/__init__.py` (`out/3-editable-crossing.txt`). A `pythonpath = ["src", ...]` entry in `[tool.pytest.ini_options]` put c's own code first and the test passed: the project's pytest config can mask the crossing. *verified by experiment.*
- **Detection from files.** Every editable install has `<dist>.dist-info/direct_url.json` with `"dir_info": {"editable": true}` and `url` the project directory, for uv_build, setuptools (static `__editable__.*.pth` path, and the import-hook finder whose `MAPPING` names the source directory) and hatchling (`_editable_impl_*.pth`) (`out/3-*.txt`). Installers MUST write it for a direct URL and MUST NOT for an index install (PEP 610). A probe comparing each editable `url` with the worktree root flagged both of main's packages `OUTSIDE`. The `.pth` and the finder name the import root, `direct_url.json` the project; the second is enough for the worktree check. *verified by experiment; read in official docs.*

### 3. Environment hash

- **Changes the verdict** (`out/4-env-hash.txt`, 4 tests): `PYTEST_ADDOPTS='-p no:pytest_mock'` and `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` turn one pass into an error; `PYTEST_PLUGINS=pytest_mock` restores it; `PYTHONPATH` to a shadowing `app` fails 3 of 4. A `pytest-mock` downgrade behind the lock's back changed the installed set with `uv.lock` unchanged. A `.python-version` change and `uv sync` replaced the venv (new interpreter inode, 8 to 11 dists on 3.10: `exceptiongroup`, `tomli`, `typing_extensions`). *verified by experiment.*
- **pytest 9.1.1 reads** `PYTEST_ADDOPTS`, `PYTEST_PLUGINS`, `PYTEST_DISABLE_PLUGIN_AUTOLOAD`, `PY_IGNORE_IMPORTMISMATCH`, `TOX_ENV_DIR` (cache directory), `PYTEST_DEBUG_TEMPROOT`, `CI` and `BUILD_NUMBER` (assertion truncation, so failure text only), and colour and theme variables (`PY_COLORS`, `NO_COLOR`, `FORCE_COLOR`, `TERM`, `PYTEST_THEME*`, output only); it sets `PYTEST_VERSION` and `PYTEST_CURRENT_TEST`. *read in source code (`grep os.environ _pytest/`).* Python itself reads `PYTHONPATH`, `PYTHONHOME`, `PYTHONSAFEPATH`, `PYTHONNOUSERSITE` and others; `PYTHONHASHSEED` was not probed. *inferred from Python's documented variables, not checked here.*
- **Changes only the installed set.** A lockfile edit without a sync left the fingerprint identical; a sync then changed it. A no-op `uv sync` moved no mtime or inode. User site-packages is off in every probed venv (`ENABLE_USER_SITE False`), as `site` documents when `include-system-site-packages` is false; when it is true, system site-packages join `sys.path`. `.pth` lines starting with `import` run at startup (`_virtualenv.pth`, setuptools' finder), and Python 3.15 adds `name.start` entry points. *verified by experiment; read in official docs.*
- **Fingerprint cost.** A Node script reading `pyvenv.cfg`, the interpreter's real path, the site-packages listing, every `.pth` and every `direct_url.json` took 1.1 to 2.0 ms in-process (8 to 12 dists; 93 ms with Node startup). Hashing every `RECORD` too (280 KB for numpy and pandas) took 1.3 to 3.7 ms. *verified by experiment.*
- **During a sync.** uv holds an exclusive `flock` on `.venv/.lock` for `uv sync` (153 of 154 polls) and `uv pip install`, and a sync waited 2.8 s while another process held it (`out/5-sync-window.txt`). `uv sync --check` exits 0 when synced, 1 when behind `uv.lock` or with an extra package, writes nothing, 51 ms (`out/8-sync-check.txt`). Poetry, PDM and Hatch were not probed for a lock. *verified by experiment.*

### 4. Setup

From files: a lockfile (`uv.lock`, `poetry.lock`, `pdm.lock`), `pyvenv.cfg` with `uv =`, `.pdm-python`, `poetry.toml` `in-project`, `[tool.hatch.envs]`, `environment.yml`, `.python-version`; whether `<root>/.venv` exists and its editables lie inside the worktree; pytest config presence (the sibling topic). Not from files: Poetry and Hatch out-of-tree paths without their CLIs, a conda environment by name, which of several environments (Hatch matrices, tox) the human means. *inferred from 1 to 3.*

## Recommendation for Squeal

1. **Discovery order**, never walking above the worktree root (001 D1): a declared interpreter or environment in `squeal.config.json` (relative paths resolve inside the worktree); else `<project root>/.venv` (uv, PDM, venv, Poetry in-project); else `.pdm-python` when it points inside the worktree; else nothing, with one note naming the command that would create it (`uv sync`, `poetry install`). Do not take `VIRTUAL_ENV`, `CONDA_PREFIX`, `python` on `PATH` or `uv python find` implicitly: the probes show each can be another worktree's. Poetry and Hatch out-of-tree environments, and conda, only when declared (Poetry's path differs per worktree, so a declared absolute path would be wrong in every other worktree). Never call `uv run`, `poetry run`, `pdm` or `hatch` to discover or run: each wrote an environment.
2. **Run environment.** Spawn `<env>/bin/python -m pytest` with `VIRTUAL_ENV=<env>` and `<env>/bin` first on `PATH`, removing an inherited activation (`VIRTUAL_ENV`, `CONDA_PREFIX`, `PYTHONHOME`, another env's `bin`), so subprocesses the tests start resolve the same environment (`out/7`).
3. **Environment hash**, beside 003 D1's: the interpreter's real path plus `sys.version`, implementation and `cache_tag` asked once (16 ms, `-I -S`) and again when the binary's stat changes; the `pyvenv.cfg` bytes; the sorted site-packages entry names; every `.pth` and `.start` file's bytes; every `direct_url.json`; optionally every `RECORD` (under 4 ms); allow-listed variables `PYTHONPATH`, `PYTHONHOME`, `PYTHONSAFEPATH`, `PYTHONNOUSERSITE`, `PYTEST_ADDOPTS`, `PYTEST_PLUGINS`, `PYTEST_DISABLE_PLUGIN_AUTOLOAD`, `PY_IGNORE_IMPORTMISMATCH`, plus policy `env.allowlist`. Not the lockfile: it changes nothing until a sync. With `include-system-site-packages = true`, the system site-packages listing joins it.
4. **Worktree rules.** No environment: every check `unknown`, one note, nothing stored, re-checked when `.venv/pyvenv.cfg` appears. An editable `direct_url.json` outside the worktree: refuse to run, one note naming the package and the path, nothing stored, since the verdict can be wrong in either direction (`out/3`). A sync in progress (`.venv/.lock` held, or the fingerprint differs before and after a run): store nothing from that run and recompute, which is defect 12's rule applied to Python. After the fingerprint changes, restart any runner process (spec 007's choice) before the next tier. Environment behind `uv.lock` (`uv sync --check` exit 1): results stay valid for the installed set; one note says the environment is behind.
5. **Fixture tests that would prove it**: a nested worktree with the parent's `.venv` and none of its own reports `unknown` and never runs the parent's interpreter; a worktree with `.venv -> ../main/.venv` refuses with the editable-outside note; an activated `VIRTUAL_ENV` from another worktree in the daemon's environment changes neither the interpreter nor a test's child `python`; `uv pip install pytest-mock==3.14.0` re-keys every file and `uv lock` alone re-keys none; `PYTEST_ADDOPTS` in the daemon's environment re-keys; a run overlapping `uv sync` stores nothing; a `.python-version` change plus `uv sync` re-keys and restarts the runner; the same suite on 3.10 and 3.13 environments keys differently.

## Open questions

1. Taking `.venv/.lock` costs Node a native `flock` it lacks (the bundle has no native addons): spawn `flock(1)` (util-linux, not on macOS), ask the project's Python (`fcntl.flock`), or rely only on fingerprint before and after. Holding the lock through a run would block the agent's own `uv sync` for that run. Not determined, because no option was probed beyond `flock -n` from the shell.
2. Crossing with `pytest-runner-api` 4: how `pythonpath`, `rootdir` and `--import-mode` change which `src` a test imports, and so whether the editable-outside rule can be relaxed when config already puts the worktree's `src` first (`out/3` shows it can mask the crossing).
3. Crossing with `python-module-graph` 1 and 2: the static resolver needs the same `sys.path` (site-packages, `.pth` roots, finder `MAPPING`) this hash reads; who computes it once. And whether an import of an installed package keys by that package's `RECORD` (per-package keys, as 001 D3 scheme B) or the whole fingerprint.
4. Poetry, PDM and Hatch locks during install, and Windows and macOS layouts (`Scripts\`, `bin` names, case folding in Hatch's id): not determined, because not probed.
5. Whether a declared Poetry or Hatch environment should be resolved by Squeal calling their CLI once per worktree at setup (684 ms, 170 ms), a tool call with possible side effects (in a fresh worktree `poetry env info -p` exited 1 and created no environment; `poetry run` and `pdm info --python` created one). Not determined, because it is a policy choice for the spec.
6. `PYTHONHASHSEED` and other Python variables were not probed for verdict changes. Not determined, because no fixture test depends on hash order.
