## Blockers

### B1 — Proven: a FileHandle's numeric descriptor escapes read and time-change tracking

Locations: `src/runners/vitest/ci-runtime/descriptors.cjs:103` to `:110`, `:144` to `:155`. A numeric open populates `fds`. A promise open populates only `handles`, although its public `handle.fd` can be passed to every numeric descriptor API. Those APIs look only in `fds`.

Item 1 requires hashing again at reads through an already open read-only descriptor or FileHandle. Item 3 requires descriptor timestamp changes to count as writes. D9 requires evidence of the content read and no intervening write. These are ordinary Node filesystem calls through a handle opened after the hook loads.

Minimal hook reproduction, with `v` initially `GOOD` and the CI hook preloaded:

```js
const h = await fs.promises.open("v", "r");
execFileSync("sh", ["-c", "printf BAD! > v"]);
const bytes = Buffer.alloc(4);
fs.readSync(h.fd, bytes, 0, 4, 0);
console.log(bytes.toString()); // BAD!
await h.close();
```

The only evidence for `v` is `671246b06c57aadc1e9daef1e43984c40e094184`, the blob of `GOOD`. No `BAD!` hash or write cancellation appears. Controls using `fs.openSync` plus `fs.readSync`, or `fs.promises.open` plus `handle.readFile`, record both hashes and lose evidence as intended.

One complete record/export proof establishes the consequence:

1. Commit a scratch Vitest fixture with a plain passing test and `test/handle-fd.test.ts`. Ignore `data/` and `node_modules/`. Set `maxWorkers: 1`. The input `data/value.txt` initially holds `BAD!`.
2. In the second test, open the input with `await open(file, "r")`, read `BAD!` with `readSync(handle.fd, bytes, 0, 4, 0)`, then write a readiness marker. Poll that same descriptor every 5 ms, for up to 1500 ms, until it reads `GOOD`; close the handle and require `GOOD`.
3. Record a wrapper around Vitest. On the marker, the wrapper uses `sh` to write `GOOD`. After Vitest ends, it uses `sh` to restore `BAD!`. No change is made and undone inside a single read. The test reads the temporary content through Node's wrapped `readSync` entry point.
4. Record exits 0: both files and both tests pass. The part's only evidence for `data/value.txt` is `2d44917b56c83488042edd88a44fd34eaae0764f`, the blob of `BAD!`.
5. Export exits 0: `Exported 2 test files, 4 results`. It includes both file and test `pass` rows for `test/handle-fd.test.ts` at key `26c8406f9f2a1c0031b070376507f5dbc2c3e407ed6f01a7034a54f98b1405d0`. Its closure includes `data/value.txt`; the input was not lost from the closure.
6. At the same clean fixture content, the same test run independently exits 1: `expected 'BAD!' to be 'GOOD'`. The plain control remains exportable.

The same map split breaks item 3 without an outside writer. Open `v` read-only through `fs.promises.open`, call `fs.futimesSync(h.fd, 1, 1)`, then close. The probe confirms `mtimeMs === 1000`, while evidence still retains the original hash and contains no cancellation. `FileHandle.utimes` and descriptors returned by `fs.open` pass their committed tests.

Worker-sized fix: share the descriptor registration for handles and numeric opens, including cleanup when a handle closes and when a descriptor number is reused. Numeric reads and `futimes` must find a handle's descriptor too. Alternatively, conservatively cancel evidence for these consumers. Add mixed-API read and timestamp regressions, including the complete false-export case above. Keep unchanged reads exportable and keep the daemon recorder untouched.

### B2 — Proven: a different recording variable exempts an unobserved child without cancelling parent evidence

Locations: `src/runners/vitest/ci-runtime/children.cjs:66` to `:68`; `test/runners/vitest/ci-evidence-children.test.ts:40` and `:68` explicitly retain the affected path.

Item 2 permits following a child with a replaced environment or dropping that shard's files when the child cannot be observed. It does not permit retaining earlier parent evidence after a child writes the input. D9's write-cancellation rule applies even when the bytes stay equal.

The new `carried` function immediately returns an environment with any different `SQUEAL_CI_RECORD` value. It does not require that the value describe a recording, that its hook is loaded, or that its writes reach the parent's evidence directory. It emits no signal to withhold the parent's run.

The hook probe reads `v` as `GOOD`, then successfully runs this Node child:

```js
execFileSync(process.execPath, ["writer.cjs", "v"], {
  env: { SQUEAL_CI_RECORD: "{}" },
});
```

`writer.cjs` writes `GOOD` back to `v`. The child has no `NODE_OPTIONS`. The parent evidence retains the `GOOD` hash with no write cancellation. The current committed test deliberately expects this result for `foreign.txt`, so its green result does not establish item 2 for this branch.

The independent matrix also uses valid, different evidence settings naming a second output directory. Both an `execFileSync` child and a Worker with that replacement environment write the input successfully. Neither output directory receives the child's write; parent evidence still retains `v`. Settings alone do not load the hook. The ordinary `env: {}` cases, including a Worker with empty `execArgv`, do cancel writes.

This is a proven write-cancellation break within item 2. Only B1 has a complete false-export proof; no second complete export proof was run for B2. Preserving a nested recording's settings is reasonable, but it does not prove the enclosing recording's inputs stayed unchanged.

Worker-sized fix: preserve a child's separate recording if needed, while also carrying its writes into the parent recording, or conservatively withhold the parent's shard when this branch starts an unobserved Node descendant. Replace the test's retained-`foreign.txt` expectation with the safe outcome. Cover both child and Worker replacement environments and keep the daemon's observation-equality test.
