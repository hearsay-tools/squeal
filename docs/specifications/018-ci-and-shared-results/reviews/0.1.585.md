## Blockers

### B1. Proven: an imported value named `type` is discarded as a type-only binding

Location: `src/runners/node-test/graph/type-imports.ts:74`, reached through `bindingsOf` and `droppedImports` at lines 25 to 47. Row 018-62 b2 requires that a dropped import never hide a module Node loads.

An import specifier can name the exported value `type` and rename it. The regular expression `/^type\s+\S/` reads `type as Value` as a type-only marker. It gives this import no bindings. `droppedImports` then drops the whole import without checking its runtime use.

Reproduction, in an ESM fixture with default tsconfig options:

```ts
// dep.ts
console.log("LOADED_DEP");
export const type = 2;

// a.test.ts
import { test } from "node:test";
import assert from "node:assert/strict";
import { type as Value } from "./dep.ts";
test("value", () => assert.equal(Value, 2));
```

Build the graph with `createNodeTestGraph({ root, cwd: root, argv: ["--import", "tsx"], testFiles: ["a.test.ts"] })`, then run `node --import tsx --test a.test.ts` in that root. Actual results:

```text
Node: exit 0; LOADED_DEP printed
graph.closure("a.test.ts"):
  paths: ["a.test.ts", "package.json"]
  complete: true; incomplete: []
graph.affected(["dep.ts"]): { direct: [], transitive: [] }
dep.ts changed to export const type = 4:
  Node: exit 1
```

This is a new static-graph omission. The old graph kept this static import. Observed module loads may recover the dependency after a run; that does not make this static closure or its affected-file answer correct. This review does not claim an end-to-end stale imported pass from this probe.

Repair for one worker: distinguish a value binding named `type` from the inline type modifier. On an ambiguous clause, retain the import. Add a real tsx comparison for `import { type as Value }` and a negative control with `import { type Value }`.

### B2. Proven: division is mistaken for a regular expression and hides real dependencies

Locations in the changed code: `src/runners/node-test/graph/type-imports.ts:43` and `:94`; `src/runners/node-test/graph/parse.ts:87` to `:91`. Both now trust `codeAt` to remove dependencies. The faulty guess is in `src/runners/node-test/graph/code-ranges.ts:102`: `}` always permits a regex; a property name such as `return` is treated as the keyword.

The helper existed before this wave. The new import-elision and literal-require filters turn its wrong guesses into new missing edges. It can mark the text between two division operators as non-code.

Real tsx fixtures used a module that prints `LOADED_DEP` and exports `Value = 2`, then these expressions:

```ts
import { Value } from "./dep.ts";
const result = ({ return: 8 }).return / Value / 2;
assert.equal(result, 2);
```

```ts
import { Value } from "./dep.ts";
const result = { valueOf: () => 8 } / Value / 2;
assert.equal(result, 2);
```

A CommonJS fixture used:

```js
// dep.cjs: console.log("LOADED_DEP"); module.exports = 2;
const { test } = require("node:test");
const assert = require("node:assert/strict");
const result = { valueOf: () => 8 } / require("./dep.cjs") / 2;
test("value", () => assert.equal(result, 2));
```

All three real `node --import tsx --test` commands exited 0 and printed `LOADED_DEP`. In each case the graph omitted the dependency, reported `complete: true`, and returned `{ direct: [], transitive: [] }` for its change. Replacing the exported 2 with 4 made each real command exit 1. The old literal-require scan did not apply this filter.

Repair for one worker: make removal conservative when `/` can mean division. A tokenizer that reports uncertainty must keep the dependency there. Fix both callers, with real tsx and CommonJS regressions for object-literal division and a keyword used as a property name. Keep the existing string, comment, template-expression and regex controls. B1 and B2 can share the 018-62 repair row, but both mechanisms need coverage.

### B3. Proven: an unreadable `--parts` path still crashes instead of returning exit 2

Location: `src/core/ci/parts.ts:465`. Row 018-63 requires a one-line refusal and exit 2 for a path that is neither a directory nor a part file. The coordinator explicitly confirmed ELOOP is within this repair's scope during review.

`statSync(path, { throwIfNoEntry: false })` only suppresses missing-entry errors. An ELOOP error escapes `readPartsIn` and the CLI. Reproduction from any git worktree:

```sh
scratch=$(mktemp -d)
ln -s loop "$scratch/loop"
node plugins/claude-code/dist/cli/squeal.mjs ci export --parts "$scratch/loop"
```

Actual result: exit 1, `Error: ELOOP: too many symbolic links encountered, stat ...`, followed by the Node stack through `readPartsIn`, `partsOrExit` and `ciExportCommand`. Before this change, the initial `existsSync` treated that path as absent.

Repair for one worker: turn filesystem failures while inspecting a named path into `readPartsIn`'s refusal result, so `ci export` returns exit 2 with a concise reason. Cover ELOOP and keep the valid file, missing path, malformed part and empty-directory behavior.

## Should-fix

### S1. Plausible: the hashing deadline does not bound the CLI process lifetime

Locations: `src/core/ci/endpoints.ts:168` to `:190`; `src/cli/index.ts:14`. D30 and D20.2 require a stall to let the command run without Squeal failing the CI step.

At the deadline the promise resolves, and `clock.over` prevents new reads. A filesystem request already in flight remains live. The CLI sets `process.exitCode`; it does not force an exit after part writing. A genuinely stuck OS request can therefore hold the process open after the user's command and part writing finish. Enough such requests can also occupy the libuv pool and delay later work. The worker's 018-61 notes state this limitation. The tests use unresolved JavaScript promises, which do not keep Node alive.

No stuck regular-file or network-filesystem case was reproduced here. This is plausible, not blocking. A worker-sized follow-up should give endpoint hashing an execution boundary that can be abandoned and test the outer process exit, not only the return of `ciCommand`. Until then, describe the bound as a bound on waiting for a round, not a guarantee of CLI termination during an OS-level stall.
