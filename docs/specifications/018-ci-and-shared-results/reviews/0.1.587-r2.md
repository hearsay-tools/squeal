## S1 resolved on Linux, proven

The hashing child now leads its own process group. The timeout ends that group. A lost IPC parent causes the child to end its own group. An exit without a result also triggers group cleanup. The stalled git joins the group rather than surviving the endpoint process that owned its timer.

Re-ran the first review's bundled-CLI proof: a git wrapper delegates ordinary commands and makes `ls-tree` a Node process that records its pid and waits forever. At the real 10 s floor, the command runs and passes, the part lacks endpoint hashes, `ci record` exits 0, and `ps` shows no remaining git process. This directly closes the old live `Sl` process result.

A second probe kills `ci record` once the stalled git has started. Its git disappears as the endpoint child handles the IPC disconnect. The first version of this probe exited 1 because its own cleanup called `kill` after git had already disappeared, producing `ESRCH`. Its earlier liveness snapshot was stale. Corrected the probe to allow cleanup to settle and inspect the process state again; it exits 0 and finds no live git. This was a probe race, not a candidate failure. The committed `record-exit.test.ts` also passes its timeout and lost-parent tests, with bounded polling and zombie handling.

Windows uses `taskkill /T /F` with a 5 s call timeout. That path was read but not run. A process in an uninterruptible kernel read can still retain a pending SIGKILL until the read returns; the parent does not wait for it. These are stated limits, not blockers in this Linux re-review.
