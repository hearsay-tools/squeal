## 1. Where the export can be made, and what it costs

**What cezar's step does today** **[exp][src]**. Job `vitest`, matrix shard 1 to 4, `ubuntu-24.04`, step `npm test -- --shard=N/4 --maxWorkers=4` (`vitest run --project server --project contract --project api-client --project web`), plus `--coverage.enabled` (cezar's own v8 coverage) on `pull_request_target` and dispatch only. Main pushes skip the suites when `queue-proof` finds the merge-group run for the same SHA, so the tests run in `merge_group` (`ci.yml` jobs `queue-proof`, `vitest`). Across 20 merge-group runs (80 shard jobs, 2026-11-07 to 11-09), the test step took p50 650 s, mean 600 s, p90 796 s. That is 2,399 s summed per run. The shard jobs took p50 682 s and p90 831 s (n 392, 98 runs). Vitest's own line for shard 1 of run 42607624919: `Duration 570.36s (transform 23.66s, setup 78.02s, import 197.80s, tests 1878.21s, environment 54.50s)`.

**What Squeal needs from a run** **[src]**. Per test file: the results, and a key. The key needs the environment (resolved config, Node, dependencies, setup files), the closure from Squeal's own transform walk (`src/runners/vitest/graph.ts` `importClosure`), and the observed reads of that run (the recorder, `src/runners/observe/recorder.cjs`, through `NODE_OPTIONS`). The export (`src/core/store/transfer.ts` `exportResults`) holds results, closure lists, observed entries and environment descriptors. Vitest's blob report holds results and the module graph the run loaded (4.1.10 `BlobReporter.onTestRunEnd`). That graph covers only the modules the run loaded, so it does not replace Squeal's walk, which follows imports that do not run **[inf]**.

cezar already has this shape for coverage: each shard uploads `vitest-coverage-shard-N`, and `vitest-coverage-merge` (`needs: [vitest]`) merges them into one artifact. `verify` does not depend on it **[src]**.

With B1 and C, the keys come from a Squeal Vitest instance with Squeal's options, not from the run's own config. The run's results then stand for a config that differs from Squeal's in the fields of question 3, plus `includeTaskLocation` (Squeal passes `true`) and coverage (Squeal's marker against none, or cezar's v8 on PR runs) **[exp]** (`probes/ci-step/out/config-diffs.txt`, last block per version). `includeTaskLocation` only adds the test's location to its record. Coverage on or off should not change a pass. Both are **[inf]**.

## 2. Shards

- Vitest "splits your _test files_, not your test cases, into shards" **[docs]** (`docs/guide/improving-performance.md` at v4.1.10). cezar balances the shards with its own sequencer (`.github/scripts/ci-test-sequencer.mjs`, measured durations) **[src]**.
- With Squeal's options, `--shard=1/4` changed no project field in 4.1.10. In 5.0.3 it changed `coverage.coverageFilesDirectory` from `<root>/coverage/.tmp` to `<root>/coverage/.tmp-1-4`, with coverage off as well **[exp]**. `canonicalConfig` replaces the coverage options with a marker only when Squeal's provider runs. Otherwise it keys them as they are, relativized **[src]**. So under 5.0.3 a shard's key differs from a local key unless the coverage options are the marker or are left out of the key **[inf]**. Recommendation 2 needs the same rule.
- Combining: the parts hold disjoint test files, so the export for a commit is their union. Each project's environment descriptor should be equal across the parts. If they differ, keep each part's own record, or refuse the part, and do not merge them into one record **[inf]**. In 36 of 36 shard jobs (9 runs) all 4 shards ran Node v26.13.0 **[exp]**. cezar's own comment on the browser job says "Runner images can cache different LTS patch versions" (that job sets `check-latest: true`; the Vitest job does not), so shards can differ in principle **[src]**.
- A missing part: when a shard fails or is cancelled, `verify` fails the merge group, and the SHA never becomes main. So an export that is published for a main commit has all of its shards **[src][inf]**. The observed sets of the parts are merged by the rule that topic `key-rules` owns.
- Vitest's own `--merge-reports` merges blob reports into one test report. It does not merge Squeal's closures or observed reads **[docs][src]**.

## 3. `CI=true`: which resolved fields differ

**std-env 4.3.0** (both Vitest versions) **[exp]** (`isci.mjs`): `isCI` is `!!env.CI || provider.ci`. `CI=true`, `CI=false`, `CI=0` and `GITHUB_ACTIONS=true` alone all give `isCI: true`. Only an unset or empty `CI` with no CI service variable gives `false`. Squeal's `sawCi` (`src/core/keys/environment-descriptor.ts:103`) says that `"false"` is std-env's "not CI". The experiment shows otherwise. It is a hint for the difference text only (in no hash) **[src][exp]**.

**Every field that differs in the dist** **[src]**: `defaults` (`allowOnly: !isCI`, `watch: !isCI && stdin.isTTY && !isAgent`, `open: !isCI`; 5.0.3 also `reporters` with `github-actions` from `GITHUB_ACTIONS`), config resolution (`snapshotOptions.updateSnapshot`: `none` under CI without `update`; `browser.headless ??= isCI`; `browser.ui ??= headless ? false : !isCI`; `browser.screenshotFailures ??= !preview && !ui`; `includeTaskLocation ??= true` when `browser.ui`; 4.1.10 adds `github-actions` reporter when `GITHUB_ACTIONS=true`), and terminal output only (`isTTY`, `canClearScreen`, a cache hint in 5.0.3).

**Measured** **[exp]** (`dump.mjs`, `createVitest`, one node project and one browser-mode project; `out/config-diffs.txt`):

| Field (project `serializedConfig` unless root) | Unset → `CI=true` | Under Squeal's options | Keyed by Squeal | Equal for an imported pass? |
|---|---|---|---|---|
| `allowOnly` | `true` → `false` | differs | yes | **Yes.** In CI a file with `.only` fails ("focused: failed", exit 1, 4.1.10 and 5.0.3), so no pass is exported. A file without `.only` runs the same tests **[exp]** |
| `snapshotOptions.updateSnapshot` | `new` → `none` | equal (`update: "none"`) | yes | Equal under Squeal. A plain run with `CI` removed writes a missing snapshot and passes (exit 0, file written), where `none` fails (exit 1) **[exp]**. Never export from a run with `new` or `all` |
| `watch` | `undefined` → `false` (`true` with a TTY) | differs | yes | **Yes.** In a worker it is read only to keep an inspector open (`inspector.*.js` `shouldKeepOpen`) **[src]** |
| `browser.headless`, `browser.ui`, `browser.screenshotFailures` | `false/true/false` → `true/false/true`, in node projects too | differs | yes | **Yes when `browser.enabled` is false**: only browser-mode code reads them **[src]**. **No for a browser-mode project**: headed runs one file at a time (`getThreadsCount`), and `ui` scales the tester iframe to the UI (`orchestrator` `transform: scale(…)`), so layout can differ **[src]**. A config that sets `browser.headless` has no difference |
| `includeTaskLocation` (browser project) | `true` → unset | equal (Squeal passes `true`) | yes | — |
| `open`, `reporters` (root) | differ | — | no: not in `serializedConfig` | — |
| `isAgent` (4.1.10), `disableColors` (5.0.3) | not from CI; agent variables such as `CLAUDECODE` | — | dropped by Squeal already | — |

Neither cezar nor this repository has a browser-mode Vitest project. cezar's `e2e` project uses `environment: 'node'` and drives a real browser through a CLI (`packages/web/e2e/vitest.config.ts`) **[src]**.

**Removing the variables in the existing step costs more than tolerating them** **[docs][src]**. GitHub: "You can't overwrite the value of the default environment variables named `GITHUB_*` … Currently you can overwrite the value of the `CI` variable. However, it's not guaranteed". So only `env -u` in the shell removes `GITHUB_ACTIONS`. `CI=false` still means CI to std-env. cezar's `vitest.config.ts` adds its `github-actions` job-summary reporter only when `GITHUB_ACTIONS === 'true'`, so removing the variable loses that summary.

## 4. Node

- cezar today **[exp]** (`out/nodever.tsv`): Vitest shards and browser shards run `lts/*`, v26.13.0 in all 72 sampled jobs. "Unit, build, and package" (node:test) runs `'24.21.0'`. `engines.node` is `>=24.21.0`. There is no `.nvmrc`, `.node-version` or `devEngines`. The trial job pinned 24.22.1, this host's version.
- Squeal keys `process.version` exactly (`src/core/keys/environment.ts:45`). node:test also keys `execPath`, which topic `key-rules` owns **[src]**.
- What a project must pin: one exact version in one file that both sides read. setup-node's `node-version-file` reads `.nvmrc`, `.node-version`, `.tool-versions` or `package.json` (`volta.node`, then `devEngines.runtime`, then `engines.node`) **[docs]** (setup-node `docs/advanced-usage.md` at v7.0.0 `8207627`). `lts/*` and a range float. cezar's vitest job would change `node-version: lts/*` to `node-version-file`. Its developers would use the same file through nvm, fnm or volta **[inf]**.
- What Squeal should say: today the difference line is `Node v26.13.0 in the export, v24.22.1 here` (`describeDifferences`) **[src]**. Because every file of the project misses at once, one line per export that names both versions is enough, with the remedy: pin one Node version for CI's test step and this machine **[inf]**. Whether a key should accept the same major version is a decision for the human (open since 2026-10-31).

## 5. The merge-group run as main's export

- GitHub: for `merge_group`, `GITHUB_SHA` is the "SHA of the merge group". When the checks pass, the queue merges the temporary branch `gh-readonly-queue/main/pr-N-<base>` into main **[docs]**.
- Measured **[exp]** (`out/main-commits.tsv`, `out/mgjobs.tsv`): each of cezar's last 100 main commits (2026-11-07 06:47Z to 2026-11-09 12:00Z) is the `head_sha` of a successful merge-group run. 98 of the 100 ran all 4 Vitest shards there. The other 2 skipped the suites: both are docs commits (#3084, #2937). Their PR-reuse job did not set `source`, so the skip came from another rule, most likely the docs-only surface **[exp][inf]**. Over 362 merge groups, `main-results.md` counted 13% that reused a PR run. cezar's own `queue-ci-proof.cjs` looks up the merge-group run by the main push SHA **[src]**.
- Of 106 passed merge-group SHAs in the window, 105 are on main. `aed9fc54` (pr-3032, 2026-11-08 16:10Z) diverged from main, so a passed merge group is not proof that its SHA landed **[exp]**.
- Safe attribution **[inf]**: name the export by `merge_group.head_sha`. Treat it as main's export only when that SHA is an ancestor of the default branch, because the queue can drop a group after its checks pass. The results are keyed by content, so an export of a SHA that never landed is still correct for its keys. Its risk is trust, not correctness. The run uses the workflow file of the merge-group commit. cezar checks `ci.yml` at base and head before it reuses a PR run (`pr-test-proof.cjs` `matchingWorkflow`) **[src]**.
- Commits whose merge group skipped the suites (docs-only) or reused a PR run have no merge-group test run. A docs-only commit re-keys only the tests that read the changed docs, so the nearest earlier export covers the rest (topic `transport`) **[inf]**. A merge group that reused a PR run has none either. Its PR run tested an equal tree (`sameTree`), on `pull_request_target`, with cezar's own coverage enabled. So it has another environment and a weaker source **[src]**.

## Recommendation for Squeal

1. **Keep the project's runner in the test step.** Add only the recorder and a results file to the existing `vitest run --shard` (B1), at about +3% CPU. Do not make Squeal schedule the suite in CI (A) **[inf]**.
2. **Leave Squeal's coverage provider out of the CI step**, and have the key treat coverage options as equal for imported passes. Imports carry no coverage record anyway. This saves 5 to 12% CPU per shard. The rule belongs with `key-rules` or the spec **[inf]**.
3. **Compute the keys and write one export per commit in a job after the shards** (C). Use cezar's existing coverage-merge pattern, and keep it out of `verify`'s `needs` **[src][inf]**.
4. **Tolerate `CI`. Do not ask projects to remove it.** For imported passes, treat `allowOnly`, `watch`, and `browser.*` of non-browser projects as equal. Keep `browser.*` keyed for browser-mode projects. Refuse an export made with `updateSnapshot` other than `none` **[exp][src]**.
5. **Node**: require one exact version in a version file. Name both versions once per export **[docs][inf]**.
6. **Merge group**: export at `merge_group.head_sha`. Count it as main's only when the SHA is an ancestor of main. Leave commits with no merge-group test run without an export of their own **[exp][inf]**.
