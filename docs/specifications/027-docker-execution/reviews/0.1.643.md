## Blockers

### B1. A declared container project runs on the host without consent

**Proven.** Changed entry point: `src/core/daemon/policy-containers.ts:116`, reached from `src/core/daemon/policy.ts:156`. Callers: `src/core/daemon/node-test-runners.ts:122` and `src/core/daemon/pytest-runners.ts:92`.

Spec 027 D4.2 says that without a matching enabled local consent entry, container-configured projects' files “stay `unknown` with one actionable note.” Row 027-04 also requires the actionable consent note. The new policy loader accepts and retains a valid `container` reference, but no daemon caller reads the consent loader or routes that project to the container manager. Existing runner factories receive the new project unchanged and start the host adapter. Zero Docker commands alone does not satisfy the unknown-state rule.

Reproduction through public interfaces:

```js
// squeal.config.json in a temporary project
{
  "containers": { "blocked": { "image": "nonexistent/no-pull:643" } },
  "nodeTest": [
    { "name": "blocked", "include": ["*.test.cjs"], "container": "blocked" }
  ]
}
// proof.test.cjs
const { test } = require("node:test");
test("host proof", () => {
  require("node:fs").writeFileSync(__dirname + "/HOST_RAN", "yes");
});
```

Load that policy. Read consent with an empty temporary `XDG_CONFIG_HOME`. Pass `policy.nodeTest` to `createNodeTestRunners`, as the daemon does, with the temporary root, temp directory, tier size 1, and a note collector. Call `testFiles()` and then `run(files, { runId, logDir, timeoutMs: 10000 })`. Close the runners afterward.

Actual output:

```text
policy problems: []
containerConsentFor(...): null
listed: blocked / proof.test.cjs
HOST_RAN exists: true
report.end: completed
report.failure: null
result outcomes: [pass]
notes: no unconsented note
```

This both executes in the wrong environment and admits a host pass for an explicitly container-targeted file. The missing image is never consulted. Pytest follows the same unguarded factory path; the executable proof above uses node:test only.

**One-worker fix:** guard every container-configured project before any local or remote execution fallback. Until the container route and key space exist, leave its results unknown with the actionable consent/unavailable note. Do not let the parsed field silently retain host execution. Add a daemon-facing test with absent, disabled, and wrong-target consent that asserts no host test process starts and no pass is admitted. Full container keying and visibility can remain in row 027-06.

### B2. The Jest graph uses tsx file precedence and misses the module Jest loads

**Proven on Jest 29.7.0 and 30.5.2.** `src/runners/jest/graph/index.ts:85` and `src/runners/jest/graph/index.ts:96`; the selected resolver is defined in `src/runners/js-graph/resolver.ts:64`.

Spec 028 D3.3 requires the pre-run closure and `affected()` to model Jest's static imports. Reusing the parser and graph is appropriate. Selecting `rules: "tsx"` also selects tsx's `.ts`-before-`.js` resolution and `.js` extension aliases. Jest's default file precedence differs. The `.jsx` fallback in the new mapper does not correct a successful resolution to the wrong file.

Temporary project:

```js
// helper.js
module.exports = "js";
// helper.ts
module.exports = "ts";
// case.test.js
const subject = require("./helper");
test("actual JS", () => expect(subject).toBe("js"));
```

Create the graph with `{ root, rootDir: root, testFiles: ["case.test.js"] }`. Run the file with the project's real Jest, `testEnvironment: "node"` and `transform: {}`. The real test passes on both majors, proving Jest loaded `helper.js`.

Actual graph output on both majors:

```text
closure.paths: [__snapshots__/case.test.js.snap, case.test.js, helper.ts, package.json]
closure.complete: true
affected([helper.js]): { direct: [], transitive: [] }
```

The initial key omits the source Jest reads, and pre-run affected selection misses an edit to that source. Later runtime observations cannot satisfy the explicit pre-run contract.

**One-worker fix:** separate shared graph parsing from runner resolution rules. Configure Jest's extension order and aliases from its resolved `moduleFileExtensions`, without changing node:test's tsx behavior. Add a regression with coexisting `.js` and `.ts` files, plus an explicit `.js` import, that compares closure/affected results with real Jest on both majors. Preserve the mapper, setup-file, and workspace-link behavior already covered.

### B3. A failing global teardown is reported as a clean completed run

**Proven on Jest 29.7.0 and 30.5.2.** `src/runners/jest/run/results.ts:247` and `src/runners/jest/run/run.ts:241`.

Vision principles 2 and 7 require truthful state and actionable failure evidence. Spec 028 goal 4 requires honest streaming results. `ending()` returns `{ end: "completed", failure: null }` as soon as all file results exist. It ignores an abnormal batch exit in this branch. The reporter has already flushed those results when Jest runs `globalTeardown`.

Use the passing test from B2 and configure:

```js
// jest.config.cjs
module.exports = {
  testEnvironment: "node",
  transform: {},
  globalTeardown: "<rootDir>/teardown.cjs"
};
// teardown.cjs
module.exports = () => { throw new Error("TEARDOWN_PROOF_643"); };
```

Invoke `runJest` with this config, one explicit test file, a fresh log/cache directory, and a 10-second deadline. The normal injected runtime and reporter were enabled.

Actual output on both majors:

```text
run.json batch exit: { code: 1, signal: null, error: null }
stderr contains TEARDOWN_PROOF_643: true
report.end: completed
report.failure: null
report.completedFiles: [case.test.js]
report.results: [[actual JS, pass]]
report.fileErrors: []
```

The failure exists only in the stderr log. Consumers receive a clean result. The existing tests cover syntax/load errors and per-case failures, but not a failure after all file completions.

**One-worker fix:** distinguish expected nonzero exits explained by mapped failures from abnormal batch termination or teardown errors. Consume terminal evidence and surface the latter through a core-consumed error or withheld-result path even when every file flushed. Keep completed case evidence for diagnostics and preserve Kit K8 cancellation behavior. Add real Jest 29/30 tests for throwing global teardown and abnormal exit after the last file, plus a normal failing-test case to avoid double-reporting ordinary exit 1.

### N2. Container lifecycle tests do not prove runner-host crash cancellation

**Unverified behavior; proven coverage gap.** `test/runner-host/container/lifecycle.test.ts:124` proves real Docker mounts, UID ownership, and removal, but fakes the Node preflight. The file never starts a real runner host or batch. It does not exercise cancel RPC, EOF, killing `docker exec`, or killing the owning daemon, which Spec 027 D5.4 names and row 027-05's done-when includes. The earlier research supports the mechanism, but is not a candidate-level regression check.

**One-worker follow-up:** use an already-local Node 22.19+ image when available, skip clearly otherwise, and drive a real protocol start plus a hanging test with a child process. Cover the four stop paths and inspect for remaining processes/managed containers. The supplied passing lifecycle test is useful evidence of the narrower checks it actually runs.

### N3. Container reuse has no configuration or mount identity check

**Plausible integration risk.** `src/core/runner-host/container/manager.ts:132` reuses on PID, running state, and image label alone, before checking the new mount paths. Spec 027 D5.1 also says the mounts must match. A later caller that retains the same `(worktree, target, pid, image)` while changing the bundle/cache/log paths, target env, or network will receive the old container. Root mount proof cannot detect a stale bundle mount or env value. No live daemon container integration exists yet, so a user-facing stale result from this path was not proved.

**One-worker follow-up:** define one effective launch stamp, including mounts, network, and env, and require it for reuse, or make the integration close the old container on any stamp change. Add a same-image configuration-change test before row 027-06 wires this manager into active execution.
