## Blockers

### B1. The daemon mounts only the CLI directory, excluding required runner assets

**Proven.** `src/core/daemon/daemon.ts:489`. Consumers: `src/core/runner-host/container/index.ts:137`, `src/core/runner-host/container/manager.ts:101`, `src/runners/jest/run/run.ts:314`, `src/runners/pytest/run/run.ts:426`, `src/runners/observe/runtime.ts:37`.

Spec 027 D5.1 requires mounting the Squeal bundle read-only; D5.3 requires the runner host to work inside the container. Normal installed launch paths are `<plugin>/dist/cli/squeal.mjs`. `dirname(launch.cli)` is `<plugin>/dist/cli`, while Jest's runtime, pytest's runtime/grammars, node:test's runtime and the input recorder sit in sibling directories under `dist`. The other three mounts do not cover an installed plugin outside the project.

Cheap reproduction: copy only `plugins/claude-code/dist/cli` into a temporary `dist/cli`, as the daemon-selected mount exposes it. Call `jestRuntimeDir`, `pytestRuntimeDir`, and `observeRecorder` with the URL of that copied `cli/squeal.mjs`.

```text
jest: jest runtime files not found ... tried <scratch>/dist/jest/, <scratch>/dist/runtime/
pytest: pytest runtime files not found ... tried <scratch>/dist/pytest/, <scratch>/dist/runtime/
observe: null
```

Thus the shipped daemon route cannot run those adapters with their required assets. The new real-container test passes `BUNDLE = .../dist` directly, so it does not test the daemon's directory selection and would not catch this defect even on a provisioned image.

**One-worker fix:** derive and mount the complete runtime bundle root for installed launch layouts. Include the source/development launch case or refuse it explicitly. Add a daemon-wiring regression that resolves every required runtime/grammar path within the effective mounts. Exercise the installed bundle outside the test worktree, not a hand-corrected `ContainerPaths` value.

### B2. Completed container runs are attributed to the host machine

**Proven.** `src/core/runner-host/container/runner.ts:345`. Contract consumers: `src/core/scheduler/record-tier.ts:186` and `src/core/runner-host/remote/remote-key.ts:113`.

Spec 027 D7 keys results under the inside-container environment. `environment()` attaches the container's Node/platform/arch, but `run()` returns the proxy report without `executedCore` or `fileCores`. The ordinary runner host does not add these fields. The scheduler explicitly treats an untagged report as a run on its own host (`HERE`).

Reproduction: use `createContainerRunner` with the same fake Docker and in-process protocol pattern as `runner.test.ts`. Make the probe report container Node `v22.19.0`, return a completed file from the inner adapter, and run on this host's Node `v26.13.0`.

```json
{"keyedNode":"v22.19.0","executedCore":null,"fileCores":null,
 "schedulerInfersNode":"v26.13.0","sameMachine":false,
 "completedFiles":[{"project":"app","path":"a.test.js"}]}
```

`recordCompleted()` consequently takes `storeOtherMachine()`: it stores under a host-machine variant of the container key and leaves the requested container key unknown. Any normal host/container Node-version difference triggers this. When the versions happen to match, the missing provenance is hidden.

**One-worker fix:** stamp every completed container report with the actual live container core, following `tagReportCore`, before returning it. Preserve that field through composite merging. Add a scheduler-facing regression with different host/container Node versions that proves the completed result becomes current at the container key and no host-machine variant receives it.

### B3. CI exports never enter the new container key space

**Proven.** New key boundary: `src/core/runner-host/container/key.ts:153`. Its only active application is `src/core/runner-host/container/runner.ts:333`. Relevant existing exporter: `src/cli/ci-export.ts:195`.

Spec 027 D7.2 says that `squeal ci record` / `squeal ci export` inside a separately built container produces a matching descriptor under the same `build-content` policy. Row 027-06's done-when explicitly includes Spec 018 export/import parity.

`applyContainerEnvironment` adds the mandatory `container` config field only on the developer daemon's managed-container route. The CI exporter constructs plain node:test/Vitest adapters, without applying this descriptor. Running that same code inside a container does not change this branch. No CI path calls the new helper or gathers the matching container inputs.

Reproduction: create a committed temporary project with one `*.test.cjs`, `nodeTest: [{name:"unit", include:["*.test.cjs"], container:"backend"}]`, and a default `build-content` backend target. Record `node --test` with Squeal's CI reporter, then export it through the public `ciCommand`. Both commands exit 0. Decode the bundle and compare its environment descriptor with the same adapter environment after the new container wrapper is applied. Keep Node/platform/arch identical so machine differences cannot explain the mismatch.

```text
record/export: 0 0
Exported 1 test file, 2 results
exportHasContainer: false
localHasContainer: true
hashesEqual: false
```

The absent config field alone guarantees different environment hashes, even with identical packages, Dockerfile inputs and machine. Import cannot make these CI passes current under the container environment. The key unit test compares two manually wrapped descriptors; it never traverses this export path.

**One-worker fix:** provide one container descriptor contract shared by managed execution and CI recording/export inside the image. Obtain the declared target's build-content inputs without requiring a nested Docker daemon. Add an export/import round-trip test that compares the real exported key with the managed adapter's key and proves reuse. Keep ordinary host exports outside this key space.

### B4. An imported Jest config dependency can change without invalidating its environment

**Proven on Jest 29.7.0 and 30.5.2.** `src/runners/jest/environment.ts:280` and `src/runners/jest/adapter.ts:134`.

Spec 028 D2.3 requires deterministic identity from the resolved Jest config and its config file chain. The live adapter caches that resolved config. It reopens only when a changed path appears in `configFiles()`. That function collects conventional filenames and path values in the resolved config, but not modules imported while evaluating the config. An imported helper that exports scalar options is absent from both the environment files and the test graph.

Temporary fixture with the already-installed Jest linked into `node_modules`:

```js
// jest.config.cjs
module.exports = {
  testEnvironment: "node",
  testMatch: ["<rootDir>/*.test.js"],
  ...require("./options.cjs")
};
// options.cjs, before
module.exports = { testTimeout: 1000 };
// options.cjs, after
module.exports = { testTimeout: 9000 };
```

Open `createJestAdapter`, read `environment()`, edit `options.cjs`, call `invalidate([{path:"options.cjs",kind:"change"}])`, then read the environment again. Open a second adapter on the changed files as the control.

```text
Jest 29 and Jest 30:
watched(options.cjs): false
invalidate: { recreatedProjects: [] }
live resolvedConfig unchanged: true
fresh adapter resolvedConfig differs: true
```

The cached environment and its file hashes cannot reflect this edit. Tests are not selected through the helper either. A change to `testMatch` or `moduleNameMapper` in the same helper also leaves the adapter's listing/graph at the old configuration, while later Jest processes load the new one.

**One-worker fix:** capture the config's worktree dependency chain when reading it, then hash and watch those paths. Rebuild the project when they change, including recovery when a dependency caused config loading to fail. Add both-major regressions that compare a live adapter after an imported config edit with a freshly opened adapter, including a changed test listing or mapper.

### B5. A live container runner ignores target changes and consent withdrawal

**Proven.** `src/core/daemon/container-guard.ts:164`, `src/core/daemon/container-guard.ts:187`, and `src/core/runner-host/container/runner.ts:274`.

Spec 027 D4.2 says that without enabled matching consent Squeal never executes Docker commands for the target. D5.1/N3 require the effective launch configuration to match. The new guard reads the live target and consent when creating a runner, but a healthy container adapter retains that target object. Its later invalidations inspect only the old image reference. They do not call `routable()` or re-read consent. The runner-set stamp covers the project entry, not the separately declared target.

Reproduction through `createContainerGuardRunner`: supply an isolated `XDG_CONFIG_HOME` with enabled consent, a live `containers()` callback, fake Docker, and an in-process runner host. Open the runner with image `old`, env `MODE=old`. Replace the callback's target with image `new`, env `MODE=new`, leaving the project entry unchanged. Invalidate `squeal.config.json`. Then disable consent, invalidate again, and request a run.

```text
target reload:
  recreatedProjects: []
  inspected references: [old]
  started containers: [{image: sha256:old, MODE: old}]
  environment's container ENV: [[MODE, old]]
consent withdrawal:
  recreatedProjects: []
  inspected references: [old, old]
  completed test files: [app / a.test.js]
```

The manager's launch stamp does not help because the updated target never reaches `ensureContainer`. Consent withdrawal also leaves the target executing and reporting ready.

**One-worker fix:** reconcile effective target configuration and local consent before each batch, before Docker inspection and reuse. On target changes, close the old host/container, start the replacement, and recreate/re-key the project. On withdrawn consent, stop execution and expose the unconsented state with no new test run or Docker inspection. Retain managed-only cleanup. Test target image/env/network/key-mode changes and the allowed-to-denied transition through the daemon-facing guard, not just direct manager calls.

## Nonblocking notes

### N1. Container status entries have no removal path

**Plausible.** `src/core/status/container-status.ts:78` and `src/core/daemon/daemon.ts:496`. `containerSummaries()` can set entries but cannot remove them. Runner-set reconciliation closes removed projects without notifying this accumulator. Removing the last container project, or moving it to another target, appears able to leave the old `ready` target in `squeal status` until restart. A rendered daemon-reload reproduction was not run, so this is not a blocker.

**One-worker follow-up:** reconcile the summary against active configured projects and clear retired entries. Test removing the last target/project and changing a project's target in a live daemon.

### N2. Ordinary failing checks lack an explicit container provenance field

**Plausible.** `src/core/runner-host/container/runner.ts:345`. The wrapper appends `in container <target>` only to a non-null batch `failure`. An ordinary failed test can have `failure: null` and carry its failure in `results`; that path returns the report unchanged. Spec 027 D7.3 asks for container provenance on failures. This review did not run the rendered failure/status path, so it does not claim that every consumer loses the target.

**One-worker follow-up:** run one ordinary assertion failure through the managed route and inspect status, push delivery and retained run provenance. Record the target where execution is known, and test its rendering without changing check identity or error fingerprint semantics.

- The manager's deterministic `org.squeal.config` stamp includes mounts, network, workdir and launch env. Reuse checks the stamp as well as owner/image/running state. Its direct same-image replacement test covers the intended N3 helper contract.

- Mount proof refuses missing or mismatched `dev:inode`; image rebuild checks replace the host/container and report project recreation before reuse. Refusal paths return unavailable environments with no host fallback.
- Jest resolves through the strict dependency chain, reads config in a child, normalizes worktree paths, and returns unavailable states for missing/unsupported installs. The real both-major adapter/environment tests and kit file are current passes.
- Policy registers Jest, rejects Jest names colliding with configured node:test/pytest projects, validates container references, and suppresses the default Vitest route for a Jest-only policy. Composite ownership still rejects duplicate runtime project names.
- Host protocol/build/proxy wiring includes Jest. All five plugin trees contain its runtime files, including the separate OpenCode build path. An independent build reproduces the committed bundles without drift.
- Status and ps additions are additive. Managed-container listing is bounded and tolerates unavailable Docker. The selected status/ps and runner-boundary tests pass.
