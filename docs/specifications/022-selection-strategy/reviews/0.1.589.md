Assertions checked the empty result, exactly 625 delete transactions, no delete above `DELETE_BATCH`, retention of the empty table, and no scan of `loaded_modules` in the write-side query plan. `observeWrites` timed each transaction from lock acquisition through commit. These are one sandbox's observations, not a timing guarantee.

The absent-table case yielded no slice and took no write transaction. A second connection then created the old table; the next prune handled it. A row inserted after an emptying was removed on the next prune. A row inserted behind the cursor between the read and delete remained until the next prune, which removed it. That delay is consistent with D3's accepted coexistence with older daemons; one pass does not promise to beat a writer that keeps inserting.
