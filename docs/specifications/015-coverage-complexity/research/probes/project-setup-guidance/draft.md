# Draft guidance used in the probe

Throwaway research text, not an installed skill or approved product behavior.

1. Read the installed version, runner config, package scripts, existing Squeal config and project instructions. Run `squeal setup --plan --json` and `squeal setup < /dev/null`. Keep the plan's source of test counts: a static estimate is not a runner listing or a test result. Resolve `not run`, `run twice` and unresolved scripts before making claims about scope.
2. List the candidate paths and read their imports and purpose. Separate runner-listed tests, test-only helpers, fixtures and product code. A test glob does not establish the purpose of its parent directory. Keep ambiguous paths included and ask the owner. Use narrow, explicit coverage exclusions for confirmed test support. Show every matched path and check that product paths remain included. Preserve existing exclusions. Distinguish runner exclusions (tests not run), coverage exclusions (no CRAP or untested check) and complexity exclusions (no count).
3. Explain the installed defaults and the current project choices. In 0.1.359, complexity and coverage default on; coverage is not opt-in at this version. Where coverage is off, enabling it is a separate proposed choice. Coverage needs complexity. Vitest and node:test can supply records; pytest cannot. Child processes and user worker threads are not measured. Inspector imports, shared isolation and provider failure can leave coverage unavailable. `untested` means no measured in-process run, not proof that no test exists. CRAP combines complexity and measured lines; it is not an instruction to add assertion-free tests. Inspect lint only if configured: it uses the project's ESLint, is independent of complexity and defaults off.
4. Present a config diff, matched-path table, any separate instruction diff, checks outside Squeal and expected cost. Switching coverage on or off re-keys covered results once; collection adds CPU and storage. Warm-up runs every test file and requires its own resource choice. Do not enable gates, change thresholds, remove exclusions or alter project instructions without authorization covering that exact change. Existing explicit authorization remains valid. If approval is missing, stop at the proposal.
5. After authorized application, read the config back, run `squeal setup --check`, and inspect the diff. Then use affected `squeal status --wait 60000 <changed-source>...` and `squeal code <source>...` to inspect current results and measurement limits. Run uncovered checks as the project requires. A setup check only validates setup; it proves no tests or coverage. Record the actual verdict, pending/unknown checks and checks not run. No routine full suite.
