## Blockers

### B1. Proven: a rename while its listing is pending loses D2 identity and tells two false changes

Changed boundary: `src/core/code/pass/listed.ts:107`, `holdUnlisted`, and `src/core/code/pass/pass.ts:88`. The hold removes a new destination from the work set but keeps the old path's `gone` entry. The pass removes the old function before the destination can participate in matching by body hash. At the next listing it judges the destination as a new function.

D2: "When a revision removes a function and adds one with the same body hash, the new check takes over the old one's state and every delivery view's entry for it. ... Nothing is delivered."

Reproduction through the existing `worktree`, `open`, `fakeCounter` and `pass` helpers:

```ts
const tree = worktree();
const store = open(tree.commonDir);
const counter = fakeCounter();
tree.write("src/old.ts", "moved 25 same-body\n").revise();
await pass(tree, store, counter);
tree.listed = 1;
tree.remove("src/old.ts").write("src/new.ts", "moved 25 same-body\n").revise();
const held = await pass(tree, store, counter);
tree.listed = 2;
const released = await pass(tree, store, counter);
```

Actual result at the candidate:

```text

released: revision=2, moved=0, transitions=1
expected: one move, zero transitions
```

A second probe used the existing delivery rig. It registered a session, crossed the threshold at `src/a.ts`, delivered that failure, then renamed the file with its body unchanged while the listing lagged. The two passes delivered:

```text

FAIL complexity: f (src/b.ts:1) is 3, over 2 (ESLint rule)
```

The same direct-pass scenario at base `94c683a1f` records one move and zero transitions. Its second pass is null. This establishes a regression in the candidate, rather than an old identity defect. Probes used a synthetic counter to isolate the hold and judgement, not parser behaviour.

Fix for one repair worker: retain the identities and provenance needed to match a held destination with its original function. Do not resolve the original before the listing can settle the move. Apply the rule both to a file deletion and to a function removed from a file that remains. Keep complexity, CRAP, uncovered, views and transition history together. Add a regression through delivery for a told crossing, and for a crossing not yet told. A rename of an unchanged body must remain quiet and preserve Stop/status history.

### B2. Proven: the new listing gate releases a test file after an unsuccessful listing

Changed boundary: `src/core/code/pass/source.ts:60`, `listedRevision`. It returns `refinedMetaKey` as if that proved the runner successfully listed the revision. It does not. A normal `runner.testFiles` rejection is handled by `tryRunner` in `src/core/scheduler/refinement.ts:135`; the runner part still commits its refined revision. The new `onRefined` nudge then releases every held file for that revision against the old test list. The worker's notes name whole-refinement exceptions and install waits as limits, but no D1 amendment accepts judging test files on those paths. The reproduced case needs neither a whole-refinement exception nor an install wait.

D1: "These are never counted: test files (any file a runner lists)." The row's outcome also says a session is never told a code line about a test file's functions. The repository styleguide requires recording a fact where it is known, rather than deriving it from a value that does not prove it.
