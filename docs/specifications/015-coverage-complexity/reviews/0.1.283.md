## Blockers

### B1. Proven: corruption during a code query disables healthy test status and registration

Location: `src/core/delivery/code-source.ts:71`; callers in `src/core/status/code-status.ts:27` and `src/core/delivery/code-deliver.ts:118`.

Contract: the brief requires a corrupt code store never to fail a hook, status or Stop (011 C8, C13). The separate code store must not take the test channel down.

`openCodeStore` handles corruption detected while opening. A file can have a readable header and schema and a corrupt data page. `withCode` handles only busy errors from its callback. It rethrows `SQLITE_CORRUPT` from a later query. `withStatusStore` then turns that code-only error into an unavailable result for the whole main store. A hook suppresses its whole registration.

Reproduction:

1. Create a healthy main store and a code store with a counted function. Close the connections so WAL data is checkpointed.
2. Query `sqlite_master` for the `states` root page and `PRAGMA page_size` in `code.sqlite`. Close that connection.
3. Change only the first byte at `(rootpage - 1) * page_size` to `0xff`. Leave the main store, code header and schema unchanged.
4. Call `withCode(source, ({ store }) => store.states.list(worktreeId))`, `readStatus(root)`, and the Claude Code `session-start` entry with an alive daemon stub.
5. Turn complexity off and repeat status and the same hook.

Observed:

```text
CORRUPT {"opened":true,"error":"Error: database disk image is malformed","errcode":11}
STATUS_CORRUPT {"schemaVersion":1,"available":false,"reason":"store-unreadable","message":"status unavailable, store unreadable: Error: database disk image is malformed"}
HOOK_CORRUPT {"stdout":"","stderr":"","exitCode":0}
STATUS_OFF_AVAILABLE true
HOOK_OFF {"exitCode":0,"stdoutBytes":1516,"stderr":""}
```

The `opened:true` mark was set inside the callback. This proves the error happens after a successful open. This is physical SQLite page corruption, not a mocked error or an invalid JSON record.

Worker-sized fix: handle code-store corruption across the complete code operation, not only its open. Omit the unavailable code part and keep the test result and registration. Add a regression with a corrupt data page and a healthy main store. Check status, registration, delivery and Stop. Do not run a full integrity scan inside a hook.

### B2. Proven: a body-preserving move loses a failure's transition provenance

Location: `src/core/code/store/states.ts:149`, read by `src/core/delivery/code-since.ts:71` and `src/core/delivery/code-delta.ts:136`.

Contracts: D2 says a move takes over the old state and every delivery view; goals 3 and 6 require failure delivery to survive without a new move notification. D7 requires an opted-in Stop to count functions that failed since registration.

`states.move` moves `states` and `views`, but leaves `transitions` on the old check id. The current check then has no last transition. `wentOverSince` omits it. A consumer that had not received the crossing also loses that notification: its moved view still says `pass`, but `planCodeDelta` silently seeds the current `fail` because it cannot find the explaining transition.

2. At revision 2, change it to CC 3 with body hash B. Deliver to the first consumer only.
3. At revision 3, remove it from `a.ts` and add `b.ts:f` with the same body hash B and CC 3.
4. Read `wentOverSince(..., 1)`, `codeStopReason` with `blocking:true`, and `tellCode` for both consumers.

Observed:

### B3. Proven: a missing closing brace creates a judged failure instead of unknown

Location: `src/core/code/pass/judge.ts:194`.

Contract: D3 says a function in a parse error's range is `unknown` and delivers nothing.

The real parser represents a missing token as a zero-width error. At a missing final brace, this point equals the function's end. `overlaps` uses strict end-exclusive comparisons, so it excludes the error from that function. The pass then judges its incomplete body and can record a failure or recovery.

Real input, at threshold 1:

```ts
function f(x) { if (x) return 1;
```

Real `countFile` output followed by `judge`:

```text
errors: [{startLine:1,startColumn:33,endLine:1,endColumn:33}]
function range: {startLine:1,startColumn:1,endLine:1,endColumn:33}
complexity: 2
outcomes: ["fail"]
transitions: ["first-seen-fail"]
```

Expected: `unknown`, no transition. This is an ordinary incomplete edit, not an exceptional counter failure. The test in `test/code/pass/states.test.ts` supplies a non-empty fake error range and misses the parser/pass boundary.

Worker-sized fix: give missing-token points their owning function, including a point at its end, without marking an adjacent healthy function unknown. Add real-parser tests for missing braces and other EOF tokens. Check that an existing fail is not recovered by such an edit.

### B4. Proven: the details command hides parse errors with no affected function

`notJudged` infers parse errors only from `unknown` function states. It never reads the stored count's `errors`. A file with a parse error outside every function, or with no function, has no such state and disappears from the report.

Neither malformed file is named under `files`. B4 is independent of the zero-width error in B3: the error in `const x = ;` has non-zero width.

### B5. Proven: an edit that overtakes a count loses the first-edit notification

Location: `src/core/code/pass/pass.ts:63` and `src/core/code/pass/pass.ts:173` (`oldBodies`); retry path in `src/core/code/pass/blobs.ts:63`.

Contract: goal 5 and D6 require the first edit to a standing failure to be told once. D4 requires a file whose bytes moved after its stat to be retried without losing its previous state.

The pass replaces the `files` row before it verifies or counts the blob. If the disk already holds the next edit, it retains the old state but leaves the file row pointing to the uncounted intermediate blob. On retry, `oldBodies` reads that file row rather than the blob on the retained state. It cannot find the old body. `judge` therefore cannot record the function as edited.

Reproduction with a shared retry set and real `runPass`/`tellCode`:

1. Count a function at CC 3, body B, threshold 2. Register a consumer by count.
2. At revision 4, put CC 4/body C in the source's stat map, but overwrite the disk with CC 5/body D before the pass reads it. This represents a second edit before the watcher records its next revision.
3. Run the pass. It skips the moved bytes and keeps the failure.
4. At revision 5, update the stat map to D and run the pass again. Deliver to the consumer.

Observed:

```text
revision 4: {mode:"edit", files:1, counted:0, transitions:0, moved:0, edited:[]}
revision 5: {mode:"edit", files:1, counted:1, transitions:0, moved:0, edited:[]}
current state: fail, value 5, changedAt 2, countedAt 5
tellCode: null
```

The function's body changed twice after registration and remained over throughout. It should receive one `STILL FAIL` line. This also loses the old body needed to match a later move on the retry.

Worker-sized fix: retain the body provenance of the last judged state across skipped or failed counts. Keep pending file progress separate, or resolve old bodies from the retained state's blob. Test two edits that overtake a count, then verify one first-edit delivery and a quiet second delivery.
