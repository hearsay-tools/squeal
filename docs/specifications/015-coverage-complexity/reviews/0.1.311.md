## Blockers

### B1: proven, a rename during a partial start seed produces a false first-seen failure

**Location:** `src/core/code/crap/seed.ts:103`, particularly the name/occurrence intersection at line 104; its snapshot is retained by `src/core/code/crap/cache.ts:55`.

**Contract:** D2: "When a revision removes a function and adds one with the same body hash, the new check takes over the old one's state ... Nothing is delivered." D9: "A function present when coverage starts ... is seeded pending, so its first judgement records no transition; a function an edit added is a first-seen fail."

**Reproduction on the exact candidate, through the daemon's code pass:**

1. Count 96 sorted files, `src/m000.ts` through `src/m095.ts`, with coverage off. Each has one function, `old`, CC 3, a unique body hash `b0` through `b95`.
2. Store one current loader whose closure names all 96 sources, with a whole empty coverage record. It loads the files and runs none of their functions.
3. Turn coverage on. Make each count read advance the fake clock by 2 ms. Nudge the code pass and await `idle()`. Exactly 32 files now have pending coverage states. No file has been judged.
4. Before the next slice, rename `old` to `renamed` in `src/m095.ts`, preserving body hash `b95`. Store the revision and nudge the same code pass. This is a move recognized by the complexity pass, not a new body.
5. Advance the fake timers to finish the chain. The function ends with `uncovered fail`, correctly, but its history contains `uncovered first-seen-fail renamed`. The expected history is empty. The daemon reports no error.

`Seed` still holds the file's original blob. `functionsOf` compares current function keys against the original count's names and occurrences. `renamed` does not match `old`, so it gets no pending coverage state. There was no earlier coverage state for `states.move` to move, because this file was beyond the first seed slice. The coverage judge therefore treats the renamed function as new and appends a false failure transition.

The worker's decision 3 documents this limit, but the spec does not accept an exception to D2 or D9 for a rename during a seed. A function that was already there is reported as a new failure solely because of the slice boundary. This is a proven contract break, not a timing hypothesis.

**One-worker repair:** make the partial seed follow the function moves recognized by the complexity pass, so an unchanged body present at seed start keeps its quiet first judgement. Keep genuinely added functions eligible for first-seen failures. Add regressions through `createCodePass` for a same-file rename and a cross-file move before either source is seeded, plus the passing case where the source was already seeded. Preserve the seed budget and immediate result/record cache invalidation. Do not repair this by seeding every current function after every edit; that hides new failures.
