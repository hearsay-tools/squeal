## Blockers

### B1. A real called function at line 1, column 0 reads as loaded only

**Proven.** `src/core/reach/read.ts:96`–`98` treats every hit function beginning at `[1, 0]` as the module's top level. An ordinary function can start there too. D11 requires `called` when “a function of the file other than its module top level ran.”

Reproduction:

1. Write `src/answer.mjs` with these exact bytes:

   ```js
   function answer() { return 42; }
   export { answer };
   ```

2. Write a node:test file that imports `answer` and asserts `answer() === 42`. Run it with `node --test` and `NODE_V8_COVERAGE` pointing to an empty directory.
3. Pass the test process's real payload through `ownRecord(root, payload, "sha1")`. Store the encoded record at the listed test file's current result key, provider `COVERAGE_PROVIDER_VERSION`. Give its trusted closure the source and its result a 2,000 ms duration.
4. Call `readSnapshot`, then `buildReport`, or call `reachCommand(["--json"], io)` against that fixture store.

Actual evidence:

```text
V8 module: name "", startOffset 0, endOffset 52, count 1
V8 function: name "answer", startOffset 0, endOffset 32, count 1
Stored source.functions: [[1,0,1,31,1],[1,0,2,18,1]]
File: coverage {"loaded only":1}, avoidableSeconds 2
Test file: sources 1, called 0, avoidableSeconds 2
```

The test calls the function, but both ranked lists treat its cost as avoidable. This changes the main ranking and gives false coverage evidence.

**Repair, one worker:** identify the module top level from evidence that distinguishes it from a function at the same start position. Do not discard a hit by its start coordinate alone. Keep an uncertain case explicit rather than declaring it uncalled. Add a regression from a real coverage payload for a called first-line function, plus a load-only control. Preserve the existing key and record contracts.

### B2. Identical importer bytes overwrite edges from another resolution context

**Proven.** `src/core/store/import-edges.ts:33`–`40`, `172`–`185`; `src/core/store/import-graph.ts:83`–`92`. The sole edge identity is `(path, hash)`. The writer replaces the targets at that identity. The reader checks the importer's stat/blob but has no project or resolution provenance. Importer bytes do not determine Vite's resolved targets.

Reproduction used two real `createVitestAdapter({ root })` instances. Both roots contained the same test and these same source bytes:

```ts
// src/gateway.ts
export { value } from "@leaf";
```

Root one configured `resolve.alias["@leaf"]` to its `src/a.ts`; root two configured it to its `src/b.ts`. Both files existed in both roots. Each adapter's real `closure()` result was persisted through `writeImportGraph` into one shared store, with each root's actual file hashes and stats.

Actual evidence:

```text
REAL_CLOSURE one: sha1 4fa54e30410a28e27868bc6cf525a3f9156e5705, static ["src/a.ts"]
REAL_CLOSURE two: sha1 4fa54e30410a28e27868bc6cf525a3f9156e5705, static ["src/b.ts"]
readImportGraph(store, rootOne, "one").targets("src/gateway.ts"):
  {static:["src/b.ts"],dynamic:[]}
readImportGraph(store, rootTwo, "two").targets("src/gateway.ts"):
  {static:["src/b.ts"],dynamic:[]}
```

Root one's bytes and config did not change. It now reads root two's edges as current. Its trusted closure still names `a.ts`, but its gateway walk follows `b.ts`. The same conflict can arise between projects with different aliases in one worktree. D11's content-sharing assumption needs a resolution identity as well as an importer identity to preserve the reader's “direct targets ... at its current bytes” contract and the vision's provenance rule.

**Repair, one worker:** retain content sharing only for compatible resolution contexts. Bind stored variants and reads to the relevant project/environment or other recorded resolution evidence. If the current port cannot express that context, return not recorded for ambiguous variants instead of accepting the last writer's variant. Coordinate any `ImportGraph` contract change with the report caller. Cover two worktrees and two projects with identical importer bytes and different aliases. This must not change result keys, `KEY_FORMAT_VERSION` or the main-store `user_version`.

### B3. Setup and config import edges never reach persistence

**Proven.** `src/runners/vitest/adapter.ts:517`–`518` exports edges only from the test file's import walk. `RunnerEnvironment` carries the flattened environment file list, and `recordImportGraph` stores that list, but no environment walk's edges. The consumer in `src/core/reach/chains.ts:88`–`96` needs those edges to find setup/config roots and chains.

D11 requires setup suggestions to “name the chain from the setup file,” and config-import suggestions to name the config import and offer loading it by path. The research and wave brief name these as central cases.

Reproduction extended the real Vitest fixture above:

- `test.setupFiles` named `test/setup.ts`.
- `test/setup.ts` imported and called `init` from `src/env.ts`.
- `vitest.config.ts` imported `Reporter` from `src/reporter.ts` and set `test.reporters` to `[new Reporter()]`.
- The test file imported neither setup source nor reporter.

After `adapter.environment()` and `adapter.closure()`, persist their real outputs as the scheduler does. Actual evidence:

```text
environment.files:
  ["src/env.ts","src/reporter.ts","test/setup.ts","vitest.config.ts"]
closure.imports paths:
  ["test/a.test.ts","src/gateway.ts","src/a.ts"]
graph.targets("test/setup.ts"): undefined
graph.targets("vitest.config.ts"): undefined
setupWalk(graph, environment).chain("src/env.ts"): ["src/env.ts"]
setupWalk(graph, environment).chain("src/reporter.ts"): ["src/reporter.ts"]
```

The walk treats imported leaves as roots. The report then calls a reporter or setup dependency itself a setup file and gives the generic “keep its imports leaf-only” suggestion. Re-running the test cannot supply edges that only the environment walks visit. `test/reach/command.test.ts:242` manually supplies config edges, so its passing setup assertion does not cover this producer/consumer seam.

**Repair, one worker:** carry diagnostic edges from setup/global-setup walks and config imports through the runner/core boundary and persist them with the environment evidence. Keep their existing environment hash inputs unchanged. Add a real-adapter-to-store-to-report regression that proves `test/setup.ts -> src/env.ts` and `vitest.config.ts -> src/reporter.ts`, including the config suggestion. Where a config edge cannot be recorded, state that the chain is unavailable; do not invent a root from the flattened list.

## What fits

- No result-key implementation, `KEY_FORMAT_VERSION`, hash code or main-store schema change appears in the range. The key-format and version-sensitive test files are current and passing. The added optional runner field is not consumed by key assembly.
- The three graph tables are created on the first graph write. Existing schema statements do not name them. Source inspection and the store test support older-daemon compatibility at the unchanged `user_version`; no historical daemon binary was run.
- A changed importer's stat or blob causes a fresh graph reader to return `undefined` until edges for that blob exist. The tests cover an edit before and after the daemon hashes it, and reject a walk of other bytes. B2 is a separate resolution-context hole.
- `reachCommand` uses store readers and has no daemon-start or test-run call. On the disposable current-schema fixture, it exited 0 with no daemon. Hashes of both closed `store.sqlite` and `code.sqlite` were identical before and after the command. The missing-store path is also covered by a targeted test.
- Coverage off and pytest produce `unknown`; an absent current-key record produces `no record`; an unconfirmed source produces `unread`. Missing coverage on a setup, declared-input, child-process or runtime-read pair produces `outside the test's process`.
- Avoidable seconds are added only for import-path pairs whose coverage is loaded only or not loaded. Child-process and runtime-read routes have no subtraction suggestion and use the by-design note. B1 can still give an import pair the wrong coverage state.
- Manual groups are left out. Partial durations, explicit paths, limits, JSON, exit codes, the no-history proposal and the coverage-off cost text have targeted coverage. The forced command for current results without records is `run --all --force`; the report does not start it.
