## Blockers

### B1, proven: a threshold change never invalidates the CRAP judgement

**Where:** `src/core/code/crap/step.ts:105` and `:159`; status presents the new threshold at `src/core/code/crap/status.ts:34`.

**Contract:** D1: "A policy change that alters ... the states (threshold ...) re-counts the files that need it." D9 makes `crap.threshold` configurable and suppresses crossings caused only by its change. That requires updating the state, not retaining the old judgement.

**Proof:** Using `coverageRig`, count `cold 6 c1`, store a current loader result and a record that never calls it, then call `step()`. Its CRAP is 42, `fail` at threshold 30. Call `step({ threshold: 50 })` with the same source and loader key. The output is:

```text
{ judged: 0, transitions: 0, wakeAt: null, more: false }
crap state: cold fail 42, threshold: 30
expected: cold pass 42, threshold: 50
```

The signature contains only the source blob and loader keys. A real policy revision reaches the step, but takes this same cache hit. Status reads the current policy and can thus say the function is over 50 while its score is 42. The existing threshold test changes the loader key too, so it misses this case.

**One-worker repair:** include the judgement's policy inputs in its validity check. Re-judge on a threshold-only change, keep the threshold-only crossing quiet, and test both raising and lowering the threshold without replacing a result or record. Do not make this depend on another test run.

### B2, proven: a counter recount can strand states pending or emit a false crossing

**Where:** `src/core/code/crap/step.ts:106`, `:127`, `:200`; `src/core/code/pass/index.ts:212` passes `reseed` for a recount.

**Contract:** D9: "A function present when coverage starts, or brought by a complexity recount, is seeded pending, so its first judgement records no transition." D1 delivers the recount as one summary. Goal 11 permits judgement when all loaders are current.

**Proof, cache:** count `cold 6 c1` and judge its current record. Recount the identical source with a version-2 fake counter that names the function `newName`, CC 8. The complexity pass removes the old state. `step({ reseed: true })` sees the unchanged blob and loader keys and skips judgement. It then seeds the new coverage states:

```text
{ judged: 0, transitions: 0, wakeAt: null, more: false }
crap: [ 'newName pending -' ]
expected: [ 'newName fail 72' ], with no transition
```

All records are current, yet subsequent steps keep the same cache hit. The signature omits the counter version and `reseed` does not bypass it.

**Proof, quiet rule:** start with `cold` at CC 3 and no hit (CRAP 12, pass). Recount it at CC 8 with the same body. Give the loader a new current key and record so the cache does not hide the problem. `step({ reseed: true })` produces:

```text
crap: [ 'cold fail 72' ]
transitions: [ 'crap pass-to-fail cold' ]
expected transitions: []
```

`seed()` skips every function that already has a CRAP state. Its old judged state reaches `judgeFiles`, so the recount records a per-function transition. A delivery probe also read the recount summary while the new loader was queued. After the record arrived, the next step and delivery told this line despite no source edit:

```text
FAIL CRAP: cold (src/a.ts:1) is 72, over 30 (CC 8); no in-process test that Squeal runs reaches it
```

**One-worker repair:** invalidate judgements when the count's meaning changes. Carry a quiet-recount marker until the affected functions are actually judged, including those waiting on records. Seed or otherwise suppress the recount's existing functions as well as new identities. Test a changed name, a changed CC at a retained name, a loader ready at recount, and a loader whose record arrives later.

### B3, proven: another worktree's closure can bypass this worktree's queued loader

**Where:** `src/core/code/crap/loaders.ts:104` to `:119`; the empty loader set becomes ready in `src/core/code/crap/file.ts:35`.

**Contract:** goal 11 and D9: each state is pending "until every test file that loads the function's source has a current result with a coverage record." The vision requires results tied to the current code state.

**Proof:** in worktree A, count `src/a.ts` with `cold`, CC 6. Store `test/a.test.ts`'s closure as `[test/a.test.ts, src/a.ts]`, and its worktree-A key as `this-branch`, `pending: queued`, with no record. The step correctly leaves `src/a.ts` pending. Then have worktree B replace the shared `testFiles` row with its branch's closure `[test/a.test.ts, src/other.ts]`, `updatedBy: wt-other`. Do not change worktree A's files, key or pending flag. The next step gives:

```text
src/a.ts summary: { state: 'judged', ... }
crap: [ 'cold fail 42' ]
expected summary state: pending
```

The global newest closure no longer names `src/a.ts`, so the reader never even asks whether A's loader is queued. Once coverage has started, this can also record and deliver a false crossing. The worker's residue names the shared-closure limitation, but it breaks the current-loader gate; it is not just a cache miss or lost optimisation. D9's "stored closure" amendment does not make the other branch's closure current for A.

**One-worker repair:** supply the pass with closures from this worktree's current reverse index, or retain a closure snapshot tied to the worktree/key that it judges. If that snapshot cannot be confirmed, preserve uncertainty. Do not treat a missing or foreign snapshot as proof that no test loads the source. Add a two-worktree regression with different imports and A's loader still queued. This needs an explicit seam from the daemon, not a read of the global newest row.

### B4, proven: lazy field arrows are reported as run on Node 22 and Node 24

**Where:** `src/core/code/crap/join.ts:141` to `:148`.

**Contract:** D9's `uncovered` fails "when no current test runs the function in the test's own process". The review brief specifically requires real Node 22 and 24 records, including lazy functions absent from V8's inventory.

**Proof:** use `covering()`, `openFixture('own-provider', ...)`, `buildRecord`, `countFile`, then `joinCoverage`. The source is:

```ts
export class Never { a() { return 1; } b() { return 2; } }
export class Fields { a = () => 1; b = () => 2; }
export function outer() { const inner = () => 1; return inner; }
```

The test only imports the module and asserts `typeof mod.outer === 'function'`. It constructs no class and calls no source function. The expected set of functions run is empty. Actual results from the shipped provider:

```text
Node 22.23.3: ran = [ 'Fields.a', 'Fields.b' ]
Node 24.21.0: ran = [ 'Fields.a' ]
Each listed function: lines 1, covered 1, coverage 1, runBy [0]
```

V8 has a zero-hit class/field-initializer range, but no separate entry for each uncompiled arrow. The fallback credits the executed declaration line to an absent function. The ordinary multi-line fixture from `test/code/crap/fixture.ts` passes on both engines; that fixture does not test this ambiguity.

**One-worker repair:** do not infer a function hit from a line also executed outside its body. Preserve enough range/call evidence to resolve an absent entry, including an enclosing zero-hit range, or represent an unresolved join as unknown. Test unconstructed field arrows and constructed-but-uncalled field arrows on both Node versions. Keep the passing arrow, nested callback, early-return and class-method cases.

### B5, proven: the recount-revision filter hides a real too-big edit

**Where:** `src/core/delivery/code-deliver.ts:236` (`f.revision !== recount?.revision`); the pass rewrites every file row during a recount in `src/core/code/pass/pass.ts:84`.

**Contract:** D6: "The first time in a session that an edit changes an included file over complexity.maxFileBytes, the session gets one line." The brief explicitly asks that the recount revision rule cannot hide a real edit made at that revision.

**Proof:** use the pass rig with `maxFileBytes: 64`. First count a 108-byte `src/big.ts` containing `'run 1 b1\n'.repeat(12)`. Register the session. Edit it to `'run 1 b2\n'.repeat(12)`, store the next revision, and run the pass with `fakeCounter(2)` so that revision also recounts. `delivered()` gives only:

```text
Complexity counted again by a new counter: 0 functions over 20; squeal code lists them.
```

There is no `src/big.ts is ...` line, now or at the next delivery. An unchanged file rewritten by the recount and the genuinely edited file have the same row revision, so the new filter cannot distinguish them. A policy change and a file edit in one watcher revision has the same path. The notes call this an accepted limit, but the brief requires this exact case and D6 has no such exception.

**One-worker repair:** retain the file's actual edit revision separately from the recount's row-write revision, or otherwise read the revision's changed paths and blob difference. Suppress recount-only rows; deliver a real edit once even when its revision also recounts. Test both in the same recount, and retain the resume and once-per-session cases.

## Should-fix

### S1, proven: an overdue record deadline polls while the writer is busy

**Where:** `src/core/code/crap/loaders.ts:94` returns the expired `until` while `writing` holds; `src/core/code/pass/index.ts:247` schedules it with a zero delay.

A loader with a current result recorded at 1,000, no record, `now = 100,000`, and a busy writer stays pending. Its `wakeAt` is still 37,250. The daemon's timer repeatedly schedules a pass at delay zero. A focused `daemonPass` probe counted **76 coverage steps in 100 ms**, without a revision, result or record change. It kept `writing()` true for that interval, then closed the pass.

This is a cost finding, not an additional blocking spec failure: D10 sets no numeric CRAP-pass budget. A busy writer is ordinary during a large coverage batch, and a deliberately uncovered inspector file can already have an expired deadline then. Use a bounded future retry or an explicit writer-idle signal. Do not schedule a past deadline indefinitely. Preserve the writer callback and its 100 ms coalescing.

An independent steady-state sample with 650 sources, 12 functions per source, 1,040 loaders and 35-path closures took 15.5 to 27.4 ms wall and 20.8 to 40.3 ms process CPU per no-op coverage step (five samples, host load about 8 to 10 on 24 CPUs). It judged zero files each time. This supports the worker's order-of-magnitude cost note. It is synthetic, not the required dogfood CPU-per-edit result.
