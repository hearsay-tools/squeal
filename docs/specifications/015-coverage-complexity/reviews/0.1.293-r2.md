### N1. A held edit can report a crossing caused only by a later threshold change (proven)

Locations: `src/core/code/pass/failed.ts:98`, `src/core/code/pass/pass.ts:82-104`.

D1 says a policy change delivers "one summary line, never one transition per function". The worker names this case in the R2 notes. I reproduced it on the clean candidate:

1. At revision 1, the function is CC 3 and passes threshold 20.
2. At revision 2, an edit changes it to CC 4. Its count throws at time 2,000. The failure has edit origin, with no quiet flag.
3. At time 3,000, a threshold recount lowers the threshold to 2. It holds the failed edit because the retry is not due. The old judged state remains pass at threshold 20.
4. At time 7,000, the retry compares CC 4 against threshold 2 and the stored pass. It records and delivers `pass-to-fail`, revision 2, from value 3 to value 4, threshold 2.

Both values pass the old threshold and fail the new one. The code edit caused no crossing under either policy. The policy change caused the FAIL. With complexity blocking enabled, `wentOverSince` can also treat that transition as a session regression.

This is a new case beyond round 1's failed first-count/recount reproductions. The reviewer skill bounds re-review to the prior blockers and directs other findings to notes. It therefore does not block this verdict. The coordinator must decide its next row.

Suggested repair scope: preserve enough policy provenance on a failed edit to separate its own crossing from a later policy-only crossing. Keep genuine edited crossings reportable. Add delivery and session regression tests for CC 3 to 4 with threshold 20 to 2, plus a genuine CC 3 to 23 edit as the control. Do not make all edit-origin retries quiet.
