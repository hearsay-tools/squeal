## Resolved finding

### B1 — proven repaired: each notification revokes the cached inputs at once

**Location:** `src/core/code/pass/index.ts:309`, `src/core/code/crap/cache.ts:89`; regression tests in `test/code/crap/notify.test.ts:88` and `:109`.

**Contract:** D9 judges the current records. R9 makes the record-stored notification the one owner of decoded-record validity. It must revoke validity synchronously on every notification, including one during a pending coalescing timer. The timer delays only the work.

`soon()` now calls `cache.invalidate()` before the timer guard. Invalidation clears cached loader, condition and signature data and advances the record epoch. It performs no record read or decode. Those stay inside the coverage step and its budget. The timer sets `coverageDue` and calls `nudge()`. All four shipped daemon bundles contain this same order.

I repeated the round-2 probe unchanged through actual `createCodePass` and `soon()`, with the real code store and real timers. One current loader reaches a function with CC 6. Each record read advances the injected pass clock by 60 ms, exhausting the 50 ms step budget before judgement. The paced successor becomes due before the 100 ms coalescing timer. Before the replacement, the stored state is `pending`. SQL still reads the real record bytes. Both directions now judge the replacement correctly, with two record reads and no errors.

I extended that probe for a second notification during the same timer window, in both directions. The first notification leaves the bytes unchanged. The paced successor reads them again and exhausts its budget. While state is still `pending`, the probe stores the opposite record and calls `soon()` again. That second call occurred 60.99 ms and 61.02 ms after the first call, while its 100 ms timer was pending. Each sequence reads the record three times and judges the replacement correctly.
