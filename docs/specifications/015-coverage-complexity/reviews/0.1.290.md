## Blocker

### B1 — proven: resuming a session misses its new daemon's catch-up

**Location:** `src/core/delivery/code-since.ts:34-37` (`seenUpTo`). Callers: `codeSeenUpTo`, `codeSince`, and `consumerSince` in the same file. The existing registration lifecycle that makes this reachable is `src/core/delivery/registered.ts:153-162` (`back`) and `src/harness/shared/session.ts:66` (registration after resume).

**Contract:** amended D6 says a change made while no daemon ran “is taken into the view by count and never told”, and the review brief requires P2 to be fixed. D7 excludes a function already failing when the consumer registers from blocking Stop.

`seenUpTo` looks only at `r.since + 1`. A session resumed within the parked-registration retention period keeps its original `since`. A resumed session whose new daemon has not scanned yet has no `scanned` marker, but its new `start` revision can be much later than `since + 1`. The bound therefore misses that catch-up. Its transition has a time after the new seed and a revision after the old bound. Delivery tells it as the session's `FAIL`. Status, `squeal code --changed`, and blocking Stop also include it.

**Reproduction, verified with public store and registration functions on the candidate:**

1. Register consumer `{ worktreeId: "probe", sessionId: "s", agentId: "main" }` at revision 0. Let its first daemon record start revision 1. Record a real session change at revision 2.
2. End it using `park(main, consumer, 15000)` and `main.consumers.unregister(consumer)`.
3. Change a different function from pass to fail while no daemon runs. Resume the same consumer before its new daemon scans: register the consumer, call `tellRegistered(main, consumer, 2, { at: 16000, scanned: null })`, and `registerCode(source, consumer, 16000)`.
4. Record the resumed daemon's catch-up as start revision 3 and its `pass-to-fail` state/transition at time 17000, as the pass does. Call `tellCode(source, consumer, 18000, () => codeSeenUpTo(main, consumer))`.

The probe uses real SQLite stores, `park`, `tellRegistered`, `registerCode`, `tellCode`, `readCodeReport`, and `codeStopReason`. It supplies the start revision and the pass's state/transition through their store APIs; it does not claim a second live-daemon run. It prints:

```text
registration = {"since":0,"gaps":[]}
startRevision = 3
bound = 1
news = [["offlineResume","pass-to-fail"]]
changed = ["offlineResume","own"]
stop = Squeal policy complexity.blocking is on and 2 functions went over the complexity threshold 20 since this session started: offlineResume (offlineResume.ts), own (own.ts). `squeal code --changed` lists them.
```

`own` is the earlier session change. `offlineResume` must not be delivered or counted as a session change. This is distinct from the accepted one-revision registration count lag. It also does not require a plugin update, a commit batched with an edit, or an edit during startup.

**One-worker repair:** handle the latest registration/start-scan boundary on resume, rather than deriving every catch-up from the original `since + 1`. Keep delivery, status, Stop and `--changed` on the same rule. Preserve eligible changes from before the pause; simply raising the whole session's bound can hide them. Add a park/resume/start regression test plus the fresh-registration case. Verify that the catch-up is seeded by count, a later session edit still delivers, and blocking Stop never names the offline function. Own the code-registration/bound seam and its delivery tests; amend a shared type only if the representation needs it.
