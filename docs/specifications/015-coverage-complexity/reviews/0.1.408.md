## Blockers

### B1. The first coverage summary is still required before the new fallback can show a reason

**Proven.** `src/cli/code-coverage.ts:150`, behind the summary guard at lines 131–132; called from `src/cli/code-report.ts`.

The row's outcome says: "`squeal code` never shows a listed function with complexity but no CRAP and no reason while coverage and CRAP are on." Its fallback says a file with no summary entry reads `the coverage step has not judged this file's current bytes yet`.

Before the first coverage step, complexity can already be counted while the worktree has no coverage summary. D4 expressly runs coverage in a later turn. The new fallback only runs after `readSummary` succeeds. The null-summary return still drops every coverage field. This is an incomplete acceptance case for the new behavior, rather than a claim that the old guard was introduced in this range.

Reproduction with the existing rig:

```ts
const rig = coverageRig(); // coverage and CRAP enabled
await rig.edit({ "src/a.ts": "double 2 d1\n" }); // count, no coverage step
expect(readSummary(rig.store.meta, WT)).toBeNull();
const report = readCodeReport(rig.main, rig.store, WT,
  { threshold: 20, maxFileBytes: 524288 },
  { paths: ["src/a.ts"], changed: false, shell: null, root: rig.tree.root });
```

Actual JSON function has `complexity: 2`, `outcome: "pass"`, and no `coverage` key. Actual text:

```text
Complexity: 1 function in src/a.ts, threshold 20
  src/a.ts:1  double  CC 2 (if 1), at or under
```

The assertion expecting `coverage.crap` to contain `outcome: "pending"`, `value: null` and the not-judged reason failed with `Received: undefined`.

**One-worker fix:** give the report reader the effective coverage/CRAP policy, so it can distinguish "on, no summary yet" from coverage off. Apply the new pending fallback in the first case. Keep exclusions, CRAP off and coverage off silent as required. Add text and JSON tests before the first step, including those off/excluded controls. Do not seed or change stored judgements to solve a display gap.

### B2. The recovery command is unusable as printed in harnesses that need an absolute command

**Proven.** `src/cli/code-crap-reason.ts:47`.

The row requires: "Where `squeal status` already names a recovery command for that condition ... the reason names the same one." The review brief explicitly asks to judge the fixed `squeal` against status's supplied command.

`pendingWords` hardcodes `squeal run --all`. `src/cli/status-command.ts:19` selects a harness command; Codex deliberately uses an absolute launcher because its CLI is not on PATH (`src/harness/codex/command.ts:7`). Pi and OpenCode also have their own invocation. The new reason ignores that selection in both text and JSON.

The probe passed `/home/agent/.codex/plugins/data/squeal-hearsay/bin/squeal` to `coverageStatusLines` for one file waiting for runs, and compared `pendingWords({ state: "pending", blob: "b", reason: "run", waiting: 1 })`:

The assertion that the reason contains the same executable command failed. The status assertion passed. The existing reason tests pin only the bare command, so they do not detect this break.

**One-worker fix:** resolve the command at the CLI boundary using the same mechanism as status and pass it to reason creation for both JSON and text. Preserve the generic `squeal` default for shells where it applies. Add a CLI test for Codex and parameterized tests for the other supported command forms.
