## What fits

### The bound discriminates for the defect

**Proven by source inspection:** `writer-feed.test.ts:118` starts `TurnLog` before `writer.collected` and stops it only after `writer.idle`. Thus the window includes the maps that pacing can put outside the reconciliation pass itself. `longestWork()` measures the main thread's CPU use, not the worker thread's CPU use. `mapTime()` measures the read, parse, map and encode on that same thread. The new assertion compares the most work in a long turn to half of this calibration.

The injected defect used the writer's existing `worker: null` option. `threadMapper` maps one whole payload synchronously inside `Pace.measure`. Pacing delays the next job; it cannot divide the current map into turns. This recreates the main-thread map whose cost the test guards. The broader storage window also catches a map when the reconciliation pass fits between paced jobs.

I ran the timing case exactly twice locally, both as fallback probes. An external Vitest config used a Vite transform to replace only `worker: TS_WORKER,` with `worker: null,` in this test. The second run added a reporter to retain console output and the skip note. Neither run changed a repository file or bypassed the load skip. Each command was:

```text
npx vitest run --config /home/agent/projects/squeal/.ai/cezar/t/76355d71/squeal-review-015-60-r3cg_k9s/red.config.mjs test/code/coverage/writer-feed.test.ts --maxWorkers=1
```

Run 1: exit 0, one file passed, one test skipped, duration 8.76 s. Detailed timing output was not captured.

**Proven numerical discrimination in the probe:** 237 ms exceeds 147 ms by 1.61x. ### The CI margin is measured in the new unit

The notes list 89 old CI measurements: the whole pass alone took at most 0.34 of one payload's map wall time. That supports replacing the noisy wall-time ratio. It does not alone prove a bound on thread CPU time: the old logs did not record that time. The notes label this inference correctly.

**Proven on the exact candidate:** CI run `40258232216`, Node 22 shard 3/3, logged this at 2026-10-26T02:21:41Z:

```text
reconciliation pass over 2000 tracked paths: 53 ms alone, 155 ms beside 12 payloads of 219 ms each (thread 208 ms); most work in a turn 0 ms, bound 104 ms; load average 2.8; no turn over 50 ms
writer-feed.test.ts: 1 test passed, 4485 ms
```

`0 ms` means that `TurnLog` retained no interval over its 50 ms wall-time cutoff; it does not mean that the thread did no work. The 104 ms bound is more than twice that cutoff, so this run has margin. The old ratio was 155 / 53 = 2.92, close to its 3x limit even in this passing run. The new bound therefore keeps the discriminating fallback result above it while the candidate's worker mapping stays below it. One CI run does not establish a future failure rate.

**Read in the installed Node type documentation:** `process.threadCpuUsage` is available since Node 22.19.0 (`node_modules/@types/node/process.d.ts:1503`), the package's minimum Node version. CI used Node 22.19; the local probes used Node 24.21.0. Both executed the API successfully. The helper uses this API when present, so it measures thread CPU time on both supported Node lines.
