## Blockers

### B1 — proven: a record update during a chain can produce a false pass

**Location:** `src/core/code/crap/cache.ts:58`, `:82`; the judgement reads it at `src/core/code/crap/step.ts:162`. The code pass calls `invalidate()` after a stored record at `src/core/code/pass/index.ts:313`.

**Contract:** D9 joins the coverage records of the current results. The review brief requires that records changing cannot leave a stale judgement. A result key names inputs, not immutable coverage bytes: the existing `CodeCoverageRepo.put` upserts the record at that key.

`invalidate()` drops loaders, conditions and signatures but keeps every decoded record. During a long chain, another whole run at the same key can replace a record. This can happen with timing-dependent tests or a forced rerun. A following step reads the old decoded record despite the writer's `onStored` nudge.

**Reproduction:** I used the real code store, `StepCache` and `runCoverageStep`, with one source, one function, and one current loader. The first step decoded a hit record. Its coverage read advanced an injected clock by 60 ms, so the step exhausted its 50 ms budget before judging. I replaced that record at the same key with a zero-hit record, then called `cache.invalidate()`, as the code pass does after a record update. The next step judged the function from the old hit. No concurrency timing is needed to reproduce this ordering.

```text
first-step { judged: 0, transitions: 0, wakeAt: null, more: true }
cached-record-after-invalidate 1 stored-record 0
next-step { judged: 1, transitions: 0, wakeAt: null, more: false }
uncovered-state [ 'pass' ]
after-settle { judged: 0, transitions: 0, wakeAt: null, more: false }
uncovered-state [ 'pass' ]
```

The stored current record supports `uncovered=fail`. The false pass survives the chain ending: the summary now holds the unchanged blob, counter, threshold and loader-key signature, so the next step skips the file. This finding is about a record replaced **before its first judgement** in this chain; it does not rely on the pre-existing handling of a record replaced after a file was judged.

**Worker-sized fix:** make a record write invalidate the decoded bytes it replaces before a resumed chain can judge from them. Keep the distinction between a result/loader change and a record-content change if required to preserve cache progress. Add the deterministic decode → replace → notify → continue case. Check both hit-to-no-hit and no-hit-to-hit. No provider-version or record-format change is needed.

### B2 — proven: a worker exit after reading a payload loses its record

**Location:** `src/core/code/coverage/map-worker.ts:60` deletes the payload at line 62 before asking for sources or returning a record. `src/core/code/coverage/writer.ts:112` refuses fallback once that payload is absent.

**Contract:** the review brief says, “A failed worker loses no record.” D8 requires a record for the completed whole test file; the test run in this case has completed and has a result key. This failure is in the new mapping worker, after the test run.

**Reproduction:** I ran the actual candidate `dist/core/code/coverage/map-worker.js`. A temporary Node import hook exits with code 9 when the worker receives its `sources` reply. At that point the candidate worker has parsed and deleted the payload but has not sent its record. I queued two files. The first record was absent. The second mapped through fallback and was stored. `idle()` resolved.

```text
records [false, true]
coverage: the mapping worker failed (Error: the coverage worker exited with code 9); mapping on the main thread
coverage: test/0.test.ts: Error: the coverage worker exited with code 9
```

The fallback test in the candidate throws at worker startup, before the payload is read. It does not cover this case. The record cannot be recovered from the completed job because both the payload and worker memory are gone.

**Worker-sized fix:** retain the payload until the parent has accepted the encoded record. Let the parent own successful cleanup, or add an acknowledgement before worker cleanup. On worker failure, remap the retained payload, and close any failed worker. Test an injected exit after the read with the real worker. Both records must be stored and the worker-failure message must appear once. Also retain the existing shutdown cleanup checks.

## Should-fix

### S1 — proven: the first loader read still holds the main thread for over a second

**Location:** `src/core/code/crap/step.ts:92`. The newly cached loader read still calls all of `readLoaders` synchronously before the budget can yield.

The amended D9 includes loader reads in the step budget. The review brief specifically calls out the first cold loader read. The incident-store probe above measured 1,043 and 1,201 ms for that call. Starting the budget before it accounts for elapsed time, but does not split that turn. A cached read also repeats after invalidations; the warm calls here took 114 and 122 ms. This agrees with the worker's own residue note.

This is a proven remaining long turn. I do not use the loaded measurements as proof of an unloaded 100 ms timing failure or a failure of the 3× reconciliation bound. The writer's large-payload turn has improved.

**Worker-sized follow-up:** build the loader map in budgeted slices, including result lookups and closure traversal. Keep the intermediate state private until the map is complete. Measure the cold path on the incident-size corpus, not only a synthetic main store with cheap reads.

### S2 — plausible: two separate pacing budgets do not cap their combined main-thread share

**Location:** `src/core/code/coverage/writer.ts:87` and `src/core/code/pass/index.ts:129` each create a separate `Pace`.

D10 caps coverage work at about half the daemon's main thread. The writer and coverage judge each yield their own time. One can consume the interval that the other yields. For example, two 50 ms producers can alternate at 0–50, 50–100, 100–150 ms while each follows its own 50 ms wait. The fallback writer makes this scenario more likely. The new timing tests exercise writer work and judging separately; the reconciliation test runs beside the writer only.

I did not reproduce a combined-share violation in a running daemon. This is not a blocker. A combined writer-plus-judge probe should decide whether both need one shared coverage budget before the half-thread claim is used as a guarantee.

## What fits

- The payload read, JSON parse, source-map work and record encoding moved into the worker in shipped builds. The 26.9 MiB probe measured a 34 ms longest turn. Sources are sent on demand.
- `buildRecord`, the mapping algorithm, encoding and provider version remain unchanged. The only change in `record.ts` exports `scriptPath`. The worker produces the same encoded bytes, including through all four committed bundles.
- A worker stops after an empty queue and the next run starts another worker. The direct two-run probes verified storage and byte identity after that restart.
- The loader map, conditions and signatures have explicit invalidation for revisions, result/record notifications and timed wakes. The decoded-record lifetime is the exception in B1.
- The continuation now uses a timed wait. Fake-clock tests cover the chain and `soon()` pacing; the writer has a separate pacing test. Both are easier to reason about than repeated `setImmediate` work.
- Coverage-off does not create a mapping worker: construction is lazy in `mapperNow`, reached only for a collected payload. `soon()` remains a no-op with coverage off. Existing coverage-off output and key tests remain relevant.
- The changes leave the watcher and scheduler source trees alone. Version 0.1.305 and all four plugin bundles agree. The new worker ships in each bundle, and the build has no drift.
- The incident analysis identifies the post-writer load: repeated loader reads, record decompression and signature work in the coverage chain. The new record cache and decode budgeting address that repeated work, subject to B1.
