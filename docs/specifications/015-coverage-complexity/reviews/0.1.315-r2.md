### B2: repaired, proven by independent reproduction and source inspection

Failed `testFiles` leaves the fact unchanged even when the revision becomes refined. A whole-refinement throw sets `ledger.listingFailed`, so the next runner part must list again before it can advance the fact. An absent fact is null; it does not classify revision-zero files as source.

The independent real-scheduler/code-pass probe fails `runner.testFiles`, adds a test and a source, and observes that neither is counted despite the revision becoming refined. Once the installed lockfile appears, `handleBatch` runs the normal baseline, which lists, commits the fact, and invokes `onListed`. No permanent hold exists on this healthy path. ## Scheduler conditions and recovery

- The listing meta write is inside `Ledger.#write`'s existing store transaction, beside the refined revision. A commit with `listed` cannot take the quiet branch. Refined and pending semantics remain separate.
- `onListed` runs after `ledger.commit` returns, for the baseline and applied runner parts. The scheduler catches a hook throw and forwards it to `onError`. The hook cannot undo the committed listing. `on-listed.test.ts` checks the visible committed fact, pending boundary, failed listing, whole-refinement recovery and hook errors.
- `test/scheduler/runner-work.test.ts` and `model-scheduler.test.ts` have no candidate diff. Both passed in the independent full run; neither declares a skip guard.
- Restart reads the persisted waiting record. A successful baseline writes a fresh main-store fact even if a 0.1.314 store has none. A code store without this version's record is read as unseen, so the first pass checks the listing rather than returning at an unchanged cursor. Candidate tests cover restart of a held source and cleanup of a test counted by an older daemon.
- A recount returns before writing its cursor when it would hold files. The next listing therefore retries the recount. `wasOff` survives that wait. The initial failed-listing test verifies a single quiet first count after recovery; the threshold-change test verifies one summary including the released source, with no per-function transition.

## Notes and limits

No additional blocking finding was proved in the repair delta.

The implementation notes accurately describe the cost of a long-broken listing. Never-counted files wait. While any waits, all nonquiet removals wait, including unrelated deletions. Stored failures can therefore remain visible after deletion until classification recovers. A policy or counter recount can retain the previous policy while it waits; a fresh worktree can remain uncounted. Ordinary edits to already counted files proceed unless a recount is due. Each pass reads changes since the oldest wait plus deferred paths. A new listing releases the work together. These are functional tradeoffs, not measured timing bounds.

**Nonblocking documentation drift, proven in the fetched status:** the W1 amendment still names `onRefined` and treats a runner-part commit as the release boundary. R11 now uses a distinct successful-listing fact and `onListed`, and introduces missing-fact and recount waits. The coordinator should record those decisions and costs in the status/spec when folding this review. No product repair is required by this note. The task brief explicitly asks this review to assess these deviations.

The repair does not promise that a broken runner will recover without any later scheduler work. Recovery evidence here is a healthy baseline, a restart, a later edit or a same-revision runner-only refinement. No performance conclusion is drawn from a loaded full run or skipped timing guards.
