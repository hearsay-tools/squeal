## Remaining blocker

### B2-R3. A stale runner part can become the permanent walk of a newer, current result key

**Proven.** `src/core/store/import-edges.ts:110` and `179`; the changed seam at `src/core/scheduler/refinement.ts:254` and `259`; reader `src/core/store/import-graph.ts:65`.

The approved rule is: a test file's walk is read only at its current result key, and the report is exactly as valid as the results. The writer selects that key when it applies the runner part, after concurrent content edits may have moved it. It no longer checks the bytes the transform read. The scheduler already identifies closures changed meanwhile, but still passes those closures to the graph writer. `ON CONFLICT ... DO NOTHING` then prevents the corrective walk from replacing the stale one.

A deterministic real-scheduler reproduction:

```ts
// src/leaf.ts
export const value = 1;

// src/a.ts
export { value } from "./leaf.js";

// src/gateway.ts, initially
export { value } from "./a.js";
export { value as other } from "./leaf.js";

// test/gate.test.ts
import { it, expect } from "vitest";
import { value } from "../src/gateway.js";
it("g", () => expect(value).toBe(1));
```

1. Start a real scheduler with a real Vitest adapter and run this fixture's baseline.
2. Append a comment to `gateway.ts` and deliver its watch batch. Wrap `closure()` to hold its answer after the actual adapter has read and returned the old imports.
3. While that answer is held, remove the direct `leaf.js` export from `gateway.ts`, leaving only its `a.js` export. Deliver a second watch batch.
4. Release the held answer. Await `scheduler.idle()` and read the graph at the worktree's current key. Compare with a fresh real adapter closure.

Both source versions have the same closure path set: `a.ts` imports `leaf.ts` in either version. Thus the carried corrective walk uses the same new key as the stale part that was applied first.

The probe's assertion that stored and fresh direct targets match failed. The graph retains a direct import absent from the current source after refinement has fully caught up. A chain to `leaf.ts` can bypass `a.ts`, and the report can name the wrong gateway. This is a stale-edge failure in B2's repaired mechanism, within this round's explicit stale-read check. It is not Step 0 (B): the scheduler did re-walk the test and its results are current for the final bytes.

**Repair scope, one worker if the human authorizes further work:** let the scheduler's existing runner-part freshness decision govern which walks may be bound to a key. Do not publish a changed-meanwhile walk under a key computed from later content. Keep that walk unrecorded until the carried fresh part supplies it. Handle environment walks under the same freshness contract. Add the overlapping-refinement case with an unchanged closure path set, and assert correctness after the scheduler is idle and the results are current. Simply overwriting every keyed row would let a stale writer replace another worktree's valid walk; simply retaining the first write causes the demonstrated failure. Preserve the one-owner rule, result keys and main schema version.
