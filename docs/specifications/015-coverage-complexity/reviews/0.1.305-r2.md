## Blockers

### B1 — proven, still blocking: the notification delays invalidation until after an old-record judgement

**Location:** `src/core/code/pass/index.ts:308`, `:313`, with its paced continuation at `:201`; `src/core/code/crap/cache.ts:61` and `src/core/code/crap/step.ts:173`.

**Contract:** D9 judges the current records. Round 1 required that a record write invalidate the decoded bytes before a resumed chain can judge from them. This is still an overwrite **before the first judgement**, not row 015-44's overwrite after a completed judgement.

R8 makes `StepCache.invalidate()` work: it advances an epoch, reads the record again, and decodes it again when its digest changed. My independent direct-cache probes pass in both directions. But the writer notifies through `CodePass.soon()`. That method waits 100 ms before it calls `cache.invalidate()`. An existing `more` continuation can run first. It then judges with the old decoded bytes and ends the chain. The later invalidation cannot repair that first judgement because the summary signature now matches the source blob, counter, threshold and loader key.

**Own probe:** I used the candidate's actual `createCodePass`, real code store, real timers, and one source with CC 6. The main-store facade supplied one current loader. I injected 60 ms into the pass's clock when the first coverage record was read. The SQL read still returned the real stored bytes. This spends the first step's 50 ms budget before judging and schedules its successor about 60 ms later. No product file or return value was changed.

After `await code.idle()`, the function's `uncovered` state was still `pending`. I stored the opposite-hit record at the same key and immediately called `code.soon()`, the writer's actual notification route. After the continuation and coalescing timers had run, the stored judgement still described the first record. There was only one coverage-record read in each case, and no code-pass error.

```text
record change  state before notification  state after notification       record reads
hit -> no-hit  uncovered pending          uncovered pass; CRAP pass 6    1
no-hit -> hit  uncovered pending          uncovered fail; CRAP fail 42   1
```

The correct states are `uncovered fail; CRAP fail 42` in the first row and `uncovered pass; CRAP pass 6` in the second. The direct-cache probes, which call `invalidate()` immediately, each read the record twice and produce those correct states. That difference isolates the missing invalidation at the notification boundary.

The committed B1 regression test calls `cache.invalidate()` directly. It verifies the new epoch/digest implementation, but bypasses the 100 ms delay that leaves this failure reachable in the daemon.

**Worker-sized fix:** revoke cached input validity synchronously when the notification arrives, before any pending continuation can use it. Coalesce the work, not that invalidation. Handle repeated notifications while a `soon` timer already exists too. Add a test through `createCodePass` and `soon()`, in both directions, where the continuation becomes due before the coalescing timer. Keep record reads and decodes inside the step budget. Do not rely on row 015-44 to repair a wrong first judgement later.

## Resolved finding

### B2 — proven repaired: a post-read worker exit keeps the payload for fallback

**Location:** `src/core/code/coverage/map-worker.ts:60`, `src/core/code/coverage/mapper.ts:148`, `src/core/code/coverage/writer.ts:110`.

The mapping worker no longer deletes the payload. The parent deletes it after the worker answers. If the worker exits first, `mapOf` can map the retained payload on the main thread.
