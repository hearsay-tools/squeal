## Blockers

### B1. A first-count retry reports untouched code as a new failure (proven)

Location: `src/core/code/pass/pass.ts:61-85`, especially adding `due` paths at line 69; `src/core/code/pass/failed.ts:13-23` retains no first-count or recount provenance.

D6: "A change at or before the revision the session counts from is taken into the view by count and never told." D5/D6 also make first counts quiet and policy changes one summary, with no transition per function. This is a break of goals 3 and 4's delivery model, not just an extra internal transition.

Reproduction on the candidate's clean `npm run build` output:

1. Revision 1 contains `src/old.ts`, with one function at CC 23. Its first count throws once at time 1,000. The pass advances the cursor to revision 1 without a state for that file.
2. A session registers at revision 1, before the retry.
3. At time 2,000 only `src/new.ts` changes, producing revision 2.
4. At time 6,000 the retry counts the unchanged `src/old.ts`. The pass uses revision 2 and `quiet: false`. The delivery planner for `{ since: 1, gaps: [] }` tells a first-seen FAIL for the old function.

Actual output, using `runPass`, a counter that fails once, the real code store, and `planCodeDelta`:

```text
first:          revision 1, mode first, counted 0, transitions 0
unrelated edit: revision 2, mode edit,  counted 1, transitions 1
retry:          revision 2, mode edit,  counted 1, transitions 1
old transition: kind first-seen-fail, revision 2, at 6000, toValue 23
old delivery:   kind first-seen-fail, revision 2, value 23
```

No bytes of `src/old.ts` changed after registration. Its failure should enter the view by count. With `complexity.blocking` on, this false attribution also makes the standing function count as a session regression. The new daemon test asserts `edit 1 1` on a retried first count but never inserts another revision or checks delivery attribution.

Repair: preserve the failed blob's first-count/recount origin through its retry and adoption from another worktree. Seed that blob quietly when it has not changed. A later edited blob must still get normal transitions. Test the sequence above through delivery and the session regression query, plus a retry after a policy recount. Do not make every retry quiet: retries of actual session edits must still report crossings.

### B2. A transient store lock removes the only retry timer (proven)

Location: `src/core/code/pass/index.ts:123-139` and `:146-165`.

D4: a failed count "is tried again 5 s and then 60 s later, three times in all". The row must recover a counter that throws once without requiring a blob change. This case leaves it pending indefinitely after a transient store error clears.

The timer callback sets `timer = null`. A thrown `runPass` skips the only `retryLater` call, which sits after the successful pass. The catch logs the error and leaves no timer. No further edit means no further count.

Reproduction used `createCodePass` with a counter that throws once, an in-memory clock/timer driver, and a real second `node:sqlite` connection holding `BEGIN IMMEDIATE` on `code.sqlite` during the retry. The write failed with `database is locked`. The lock was then released:

```text
after first failure {"calls":1,"timers":1}
after busy retry and lock release {"calls":1,"timers":0,"errors":["database is locked"]}
while idle later {"calls":1,"timers":0}
explicit nudge recovers {"calls":2,"timers":0}
```

The failed count's record stays due. This is not a spent budget and the counter can recover, but the daemon has no timer to call it again. A shared store write lock is an expected condition; D4 explicitly uses WAL and busy retries.

Repair: retain a bounded wake after an aborted retry pass. Re-arm outside the success-only path, with a positive backoff for an overdue retry so a persistent lock cannot cause a zero-delay loop. Keep the count attempt budget unchanged until an actual count is attempted. Add a test that releases a real store lock after an aborted timer pass and observes recovery without `nudge` or a file edit.
