# Research wave: existing coverage selection tools

## R1 — 015-96

Use /researcher. Shape: research. Find a practical way to reduce Squeal’s test runs using existing coverage-selection tools or their methods, preserving the vision’s honest state and adapter boundaries.

Read docs/vision.md, 015 Non-goals/D8–D10/status, 011 C3/C4/C7/C10, and research/line-level-selection.md as a limited baseline, not a verdict. Start with testmon’s structural blocks: trace selection in its pinned source before adapting any probe.

1. Compare actual algorithms, assumptions, invalidation and reliability evidence in pytest-testmon, Wallaby, StrykerJS, and relevant tools their official sources reference. Separate marketing, source facts and experiments.
2. Can Squeal use them directly, embed their libraries, or adapt their methods? Check licenses, maintenance, headless/local APIs, runner compatibility, dependencies and provenance. Name integration costs.
3. Run an available real tool on ordinary edits and adversarial cases; prototype the strongest transferable JS/TS method in isolated research code. Compare selected tests with exhaustive results in bounded fixtures. Measure runs avoided, missed failures and overhead; cover structural changes, data/children/reflection and stale evidence without treating lexical blanket fallback as proof.
4. Recommend a concrete reduced-run path, applicability limits, fallback and honest status contract. Prioritization alone does not answer the request.

Own research/selection-tools.md and research/probes/selection-tools/**. Leave product, board and existing findings unchanged. Use sources below and their official links; no paid services or uploads. No repository full suite. Commit reproducible evidence; report gaps at two hours.
