## Blockers

### B1. Proven: shallow shards cannot run the validity self-tests

**Location:** `.github/workflows/ci.yml:27`, `:61`, and `:199`; incomplete guard at `test/ci-shard.test.ts:47` and `:106`.

The workflow now fetches history only for shard 1. It pins direct history readers, but misses tests that call `comparisons()` from `test/keys/validity/self-test.ts`. That helper unconditionally calls `lastRelease()` and extracts its tree in `beforeAll` (`self-test.ts:95`). `lastRelease()` runs `git describe --tags --abbrev=0 --match squeal--v* HEAD` (`trees.ts:33`). A depth-one candidate checkout has no reachable release tag and throws:

```text
no squeal--v* tag is an ancestor of HEAD: run `git fetch --tags` (a shallow clone needs its history too)
```

The candidate's actual duration partition gives these assignments:

| Test file | Node 22 shard, of 6 | Nightly shard, of 3 |
| --- | ---: | ---: |
| `test/keys/key-format.test.ts` | 3 | 1 |
| `test/keys/validity/adapters.test.ts` | 3 | 3 |
| `test/keys/validity/pytest.test.ts` | 6 | 1 |
| `test/keys/validity/reach.test.ts` | 5 | 3 |
| `test/keys/validity/lock.test.ts` | 3 | 1 |

Thus the push suite fails in shards 3, 5, and 6, and the nightly suite also has broken history readers. The new green guard cannot exclude this failure: it searches each `.test.ts` file's text for direct calls, without checking the shared helper. Also include `test/e2e/codex-migration.test.ts:28` in the history inventory: it archives `squeal--v0.1.367` and lands in shard 4 when enabled, though ordinary CI skips it without Codex.

This breaks G4, "every `cand/*` push and every main code landing gets the full suite," and row 010-35's requirement to preserve history-dependent tests while using shallow shards.

**One-worker fix:** restore full history on every shard, or pin all direct and indirect history readers to shard 1 for both shard counts. Extend the guard to cover helper callers and explicit tag archives. Verify the affected files in the same checkout conditions CI uses; a local checkout with full history cannot establish the shallow-checkout contract.

### B2. Proven: adding a source file does not invalidate the shared CLI build

**Location:** `test/helpers/build-inputs.ts:176`; caller `test/daemon/helpers.ts:99` and recipe at `:79`.

`current()` hashes only `stamp.inputs`, the previous build's input list. `cliRecipe()` includes options and config contents, but no current source membership. `tsconfig.build.json` includes all of `src`. After the first cached build, adding a new source module without changing an old input therefore reuses the old output. The new module is neither compiled nor included in the observed input list. Previously each `buildCli()` call compiled the current source tree.

A direct probe used the real `sharedBuild` and `observeBuildInputs`. Its builder discovered `src/*.ts` and emitted one output per input. It built `a.ts`, added `b.ts`, then called `sharedBuild` with the same recipe and live run directory. Both source files were older than the cache's one-second settle window. Output was:

```json
{"builds":1,"newSource":true,"newOutput":false,"outputs":["a.js"]}
```

This is a concrete stale-build scenario in a warm Squeal run: a newly added CLI module is absent from later private builds. A new compiler error can also bypass compilation. It breaks row 010-36's preservation of current compiled inputs and Spec D13's "input observation ... stand" contract. The vision requires that an old result never pose as current evidence.

**One-worker fix:** validate the current compiler input set as well as the prior input contents before accepting a hit. Include input membership in the recipe or stamp, accounting for config exclusions. Add a regression that builds, adds a source file, and builds again in the same run directory. Keep unchanged-input reuse, observation on every hit, and per-test output ownership. Existing tests cover edits to known inputs but do not cover this addition case.

### B3. Proven: the non-isolated unit project loses shared cleanup hooks

**Location:** `vitest.config.ts:62`; affected helper contract at `test/store/helpers.ts:17`.

`test/store/helpers.ts` registers `afterEach` at module evaluation and keeps a module-level cleanup list. `tempDir()` appends directory removals; `open()` appends store closes. Many unit-project files import this helper directly or through status helpers.

With `isolate:false`, the first file that imports the helper registers its hook. Later files in the same worker reuse the cached module, but do not register that hook in their own suite. Their cleanup functions accumulate instead of running after each test. This leaves temporary directories and open SQLite stores alive across files. Moving only the six `vi.mock` users into a separate project does not address this shared state.

The two-file proof used the existing helper unchanged. Each file called `tempDir()` in one test and checked directory removal in `afterAll`. With `isolate:false` and one worker, Vitest reported:

```text
FAIL b.test.ts
AssertionError: tempDir was cleaned after the test: expected true to be false
Test Files  1 failed | 1 passed (2)
Tests       2 passed (2)
Duration    277ms
exit: 1
```

Both test bodies passed; the second file failed because its imported helper's cleanup never ran. All probe files and leaked directories were removed. This breaks row 010-36's instruction to use isolation when a file leaks shared module state and regresses the helper's documented per-test resource lifetime.

**One-worker fix:** retain isolation for affected consumers, or make cleanup registration execute for each file without relying on first module evaluation. Audit other cached helpers that register hooks. Add a two-file, one-worker regression using the real helper; a single-file test or a green suite without cleanup assertions misses this defect.
