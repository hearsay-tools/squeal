## Should-fix

### S1. Proven, pre-existing: a result arriving after membership lookup can lose its coverage record

Location: `src/core/code/store/prune.ts:161`, especially the fixed deletion list at lines 166 to 167. Regression-test home: `test/code/coverage/prune-main.test.ts:73`.

Contract: W2 says to “keep the rule that a coverage record stays while its key has a result.” Spec 015 D8 says it is “adopted with the result ... and pruned with it.” This candidate does not establish that invariant across concurrent result writes. **The base already has the same defect, so this does not block 011-315**, per the coordinator's explicit scope instruction during review.

Concrete sequence, using separate main-store and code-store writer connections:

1. Coverage key `racing` has an old record; the main store has no result at that key. This can exist after main-store pruning and before code-store pruning.
2. Prune reads the main store and finds no result.
3. Another writer stores a result at `racing`, then refreshes its coverage record.
4. Prune deletes that record using the earlier membership answer. The result remains.

The same probe ran against an extracted base and the candidate. Only the intercepted lookup method differs. Both the record-refresh and result-only variants produced these results:

```text
base 6eb3c3a0a: method=keysSince,       removed=1, resultCount=1, coverage=null
candidate:     method=keysWithResults, removed=1, resultCount=1, coverage=null
```

The new protection works for a newly introduced key, which the committed test covers. It does not protect a refreshed record at an already-enumerated key. A result committed during the gap can also be lost from the retention decision without a record refresh.

One-worker follow-up: add the controlled interleaving test below, then make result membership and the corresponding coverage deletion one coordinated, bounded operation. Re-reading without coordination still leaves a gap; guarding record identity alone covers refreshes but not result-only writes. Keep C7's short transactions, the 256-row deletion budget and the absence of a schema change. Scope: code-store prune/main bridge and their result-query contract/tests.

Regression core, using the existing test's `main`, `code`, `at`, `RECORD`, `NOW`, `result`, and `testCheck` helpers:

```ts
code.coverage.put(at("racing"), RECORD, NOW - DAY_MS);
const results = {
  ...main.results,
  keysWithResults: (keys: readonly string[]) => {
    const kept = main.results.keysWithResults(keys);
    // Use second store connections here to model the independent writer.
    writer.results.putMany([
      result(testCheck("racing"), "racing", { recordedAt: NOW }),
    ]);
    otherCode.coverage.put(at("racing"), RECORD, NOW);
    return kept;
  },
};
pruneCodeStoreAfter({ ...main, results }, commonDir, ON, NOW);
expect(main.results.byKey("racing", 0)).toHaveLength(1);
expect(code.coverage.get(at("racing"))).toEqual(RECORD);
```

At the candidate, the last assertion fails with `null`. At the base, intercept `keysSince(since)` after its real call and perform the same writes before returning the saved answer; the last assertion fails in the same way. Also run the regression without `otherCode.coverage.put` to cover result-only arrival.
