## Blocker

### B1, proven: the lint-group wait still ends on a busy store

Locations: `src/cli/wait/table.ts:261-266`, `src/cli/wait/reads.ts:230-257`, and the lint branch at `src/cli/wait/wait.ts:54-55`.

Decision 4 item 1 says: **"A busy read is skipped and read again."** It applies to the run waits, including the lint-group row. The candidate adds that rule only to the checkpoint and test-group worktree reads. The lint row still maps every failed `withLint` read to `counts: "unread"`, which wins before its deadline and returns immediately. Notes decision 6 acknowledges this omission because the shared reader loses the distinction between busy and damaged. That explains the gap; it does not fulfil the approved behaviour.

Reproduction on the clean candidate:

1. Make a private worktree fixture with lint enabled, eslint in group `lint` at `stop`, a fresh daemon record, and one pending lint state.
2. Close the seed lint connection. On a separate `DatabaseSync(lintStorePath(commonDir))`, run `PRAGMA locking_mode=EXCLUSIVE; BEGIN EXCLUSIVE`, then read `sqlite_schema` to establish the lock.
3. Call production `runWait` for that lint group with a 60,000 ms deadline. Give it a stepped clock whose first pause releases the lock, so the next read can succeed.

Actual output:

```json
{"case":"busy lint store","outcome":{"kind":"unread"},"pauses":[],"elapsedMs":1010,"line":["has no verdict: the lint store cannot be read",3]}
```

The wait never reaches the pause that would release the lock. A short competing lock ends a minute-long wait after about one second. The busy timeout also remains the lint reader's default, rather than being bounded by the wait's remaining time. This is missing work within the approved busy-read cell, even though the old lint reader also behaved this way. It is not a request to fix unrelated pre-existing lint behaviour.

Repair as one focused row: retain the distinction between a busy lint read and an unreadable store, bound each read as `readBound` does, and represent retry/final-unavailable in the existing lint table and loop. Keep the existing unreadable-store outcome for genuine read failures. Add a real-lock loop row that releases on the first pause and gets the next read's verdict; add a final-read busy row. If exposing the busy reason requires a core lint-reader change, obtain the coordinator's ownership decision as W1 requires. Do not retry every generic `failed` indefinitely, since that would also hide damaged rows. No key-format change is implied.

### Lint presence adds one conditional worktree read

At `reads.ts:153-159`, creating the lint reader now derives the worktree ID before the counts read. This is an extra filesystem identity lookup, including on off/unread/ended branches; it opens no store. `presenceOf` constructs its watch lazily.

Only a pending lint group before the deadline reaches `presenceRead`. That opens the worktree store in a separate bounded read transaction, reads the worktree record, then `stoppingOf`, and asks the watch. The watch may consult lock marks, reread a cleared record on its own connection, or ask the socket in the background, exactly as the status watch does. It does not reopen the lint store or reread lint counts. Off, unread, completed and deadline outcomes avoid this presence-store read. This added read is needed to replace the old ping and is within decision 4 item 2. A missing/busy presence store is `unread` evidence about the daemon, so the wait continues; it is distinct from B1's failed lint-count read.
