## Blocker

### B1. Proven: a failed sync can present an old pass as current

Location: `src/cli/status-paths.ts:91–95`, especially the `current.state === "unsupported"` arm. `syncDaemon` uses `unsupported` when no socket listens, the socket errors, the daemon predates sync, or its pass failed (`src/cli/status-sync.ts`). The new snapshot treats all these as sufficient freshness evidence while the stored heartbeat is fresh. A fresh heartbeat proves neither that the latest edits were stored nor that the sync succeeded.

Contract: design 011-24 section 1.5 says, “When the sync did not reach the store's revision, the line says `results are as of revision N; the daemon has not stored its pass over the latest edits` and gives no verdict.” R3's done-when says, “a snapshot after an edit the daemon has not stored says so and gives no verdict”; its “most likely false” line expressly forbids a stale exit 0. Vision principle 2 also forbids an old result posing as current.

Verified twice with the committed 0.1.233 Claude Code CLI bundle, a real daemon, and throwaway `/tmp/sq-r233-*` repositories, each with private `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` and `XDG_RUNTIME_DIR`. The fixture is gh-44's 25-file node:test project under `baseline.onStart: "lookup-only"`. Reproduction:

1. Initialize and commit the fixture. `squeal start`; `squeal status --wait 60000` for discovery.
2. Append a passing test to `test/f01.test.mjs`; `squeal status --wait 60000 test/f01.test.mjs` returns 0 at revision 1.
3. Read the daemon PID with a `ping` on its private Unix socket, then `kill -STOP <pid>`. Append `test("broken", () => assert.equal(3, 4));` to that same file.
4. While the stored heartbeat is still fresh, rename the socket aside to model a lost endpoint. Ask `squeal status test/f01.test.mjs`.
5. Restore the socket, `kill -CONT <pid>` and `squeal stop`; no daemon is left running.

Observed on `/tmp/sq-r233-es4hxxoz/repo` (867 ms process elapsed), and again in `/tmp/sq-r233-ofh3sbfn/repo` (944 ms):

```text
exit: 0
Revision: 1 · 493d53d5 + 1, dirty
Selected: test/f01.test.mjs
Named test files at revision 1: no known failures; 1 test file, each with a current result. Worktree: known failures 0; not current: 24 of 25 test files (24 unknown)
```

The failing edit has never been read by the suspended daemon. The result is the old passing revision. No malformed store, forged sync reply or product edit is involved. A socket lost during shutdown or a sync pass that fails has the same `unsupported` branch; those natural variants were not separately reproduced.

Fix sized for one CLI worker: require a successfully stored sync at or before the read revision before issuing a named snapshot verdict; give unsupported/failed sync an honest no-verdict reason and exit 3. Keep the named wait's existing fallback separately if needed. Add a socket-level regression with a fresh stored heartbeat and current passing rows but an unavailable/failed sync, alongside the existing pending-sync test. Do not promote, change core, or raise key format to fix this.

## Should-fix observation

### S1. Proven measurement, nonblocking: the process outlives the bounded read

Location: `src/cli/status-paths.ts:57,73` and its existing sync helper. With the real daemon suspended but its socket still present, `status --json test/f01.test.mjs` correctly returned code 3 with `named.waitedMs: 766`, but the process exited after **2,097 ms** (second run: **2,146 ms**). The in-flight ping retains a referenced socket/timer until `CLI_SOCKET_TIMEOUT_MS` (2,000 ms); `sync.stop()` only sets a flag and cannot cancel it. The read bound is working, so this measurement is not counted as a second blocker. Consider cancellation or a deadline-aware CLI sync so an agent's shell call also ends near the advertised 750 ms bound. Pin process completion, not only `main()` or an injected `DaemonSync`'s return time.
