## Should-fix proposal outside this change

### S1. Plausible production failure: a non-abort error permanently stops priority lowering

Pre-existing code: `src/core/daemon/low-priority.ts:77-110`, especially the unconditional catch at line 108. This is not a regression or blocker for 011-409.

The catch's behavior is **proven** by source and the old-walk experiment: an error returns while the abort signal remains live. A production path is **plausible**: `EscapedChildren.carriers` can reach `escaped.ts:514`'s `snapshot`, whose top-level `readdirSync("/proc")` is unguarded. A transient read failure such as descriptor exhaustion can reject that look. Most per-process disappearance and permission failures are already caught. This review did not force a real production `/proc` failure.

This merits a proposed row. The styleguide says, "Never swallow an error silently; either handle it or let it surface." The priority contract in 011 C10 also expects looks to continue until the run settles. A transient scan error should not disable all later lowering without a note.

One-worker scope: distinguish signal cancellation from other errors at the per-look boundary; report a non-abort failure with context through the daemon's existing note path and retry on the existing cadence. Keep the cancellation prompt and the shared scan cap. Do not add an immediate retry loop or widen this test-only repair.

Done when: a controlled `carriers` rejection on one look, and a controlled walk exception on another, each leave the loop active and allow a later child to reach nice 10; diagnostics identify the failure without repeating every look; signal abort still resolves quietly. Preserve lane filtering and PID/start guards. The coordinator should propose this row for approval rather than treating it as already authorized.
