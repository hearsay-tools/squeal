## Inputs for the coordinator and next wave

### Proven residual: the pool's refresh and duration need their own row

The brief explicitly asks whether this is visible. **Yes.** `PoolWaits.refused` compares the calendar reading to `#publishedAt` (`src/core/scheduler/pool-wait.ts:130`); `#live` compares to `last` (`:156`); `granted` subtracts `since` (`:142`). These methods are unchanged from the base. Stamping fixes row identity, not these intervals.

Probe: start at 10,000,000, refuse with gate `busyCores=20, grants=12`, advance 1s, set back 1h, then refuse every 2s for 12s with `busyCores=21, grants=11`. The public reader still returned:

```json
{"busyCores":20,"cpus":24,"hostSlots":12,"grants":12,"since":10000000}
```

The normal 10s refresh elapsed, but the stored fields did not change. The reader accepts that old row because its stamp is ahead of the rolled-back calendar. `next-step.ts:352` prints those fields in the named wait's host-busy explanation. A subsequent grant logged:

```text
the pool granted the test lane's tier after -3587 s of waiting for CPU
```

This is a user-visible residual honesty defect, not just bookkeeping. It predates this range; row 011-386 asks for valid publication identity without changing row shapes or readers, and that requirement passes. It does not block this candidate.

Proposed separate scope: make pool-wait refresh, refusal continuity and grant duration count elapsed time, while retaining calendar `since` for published text and the daemon-start stamp for identity. Test repeated refusals across both steps, changed gate fields after 10 elapsed seconds, positive grant durations, a genuine 30s refusal gap, and predecessor rejection. Keep this out of the capacity/permit ownership work.

### Proven residual: a step before lint first sees an edit still moves its quiet

The code and worker notes disclose this precisely. The probe first observed revision 1, advanced 4s, created revision 2, advanced 1s, stepped the calendar, then called the lint callback for the first time on revision 2. Quiet was 3s. Actual output:

```text
set back 1h: left=3602000, elapsed-time remainder=2000
set forward 1h: left=0, elapsed-time remainder=2000
```

This is a real remaining delay or skipped quiet. It falls outside the explicit first-sight contract the brief asks this implementation to use, and the old lint path already had it. A scheduler that already observed that edit can do better; merely sharing a steps instance does not guarantee that either reader saw the revision before a step. Full correctness for that window needs an observation tied to revision creation, or equivalent provenance. Do not widen this landing to add that interface. Retain the disclosure and let the coordinator decide whether to propose a separate row.

The changed owner-to-reader tests cover publication identity, not refresh after a row was already written. The new lint tests cover a step after the edit was observed and a new edit after a step; they do not cover an unobserved edit before a step. The probe above establishes these limits without weakening either test's useful guarantee.
