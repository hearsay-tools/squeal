## Nits

### N1. Proven: the helper reads the default slow activity twice when no lane waits

Location: `src/core/scheduler/scheduler.ts:656` and `:659`.

Scenario: no group has a stored waiting activity. The helper first calls `readSlowActivity`. It then scans `GroupTiers.lanes(policy)`, which includes the default `slow` lane. `readGroupActivity(..., "slow")` calls `readSlowActivity` again. Thus even a policy without configured groups reads the same row twice in one re-walk answer.

The combined `slowWaiting` fact remains lazy and memoized once per answer. This duplicate read changes no decision or published state, so it does not block either row. One-worker fix: retain the default-first check and skip the default `slow` lane in the following scan. Preserve the halt-before-read order and the single combined fact.

## What fits

### 1. Proven: both design differences were real

Locations: `test/scheduler/admission-runner-work.test.ts:53`, `test/scheduler/admission-rewalk-lanes.test.ts:76`.

Both original tests fail with only the source fixes reverted. The runner-work case places the batch through the real mutex watcher, not a timer. `Mutex.run` queues tasks in call order. A touched-unchanged batch queues runner work without advancing the revision, so preemption does not hide the gap. The asserted order observes both invalidation and the actual run.

The re-walk case controls its load input and CPU count; it creates no host load. Stored walks are removed, so a chunk remains. The configured group publishes its real load wait under its own activity key. The idle-barrier variant also fails before the fix and passes after it. No uncontrolled timing race is needed to expose either defect. The committed re-walk test still uses a bounded 500 ms observation window, rather than that stronger barrier.

### 2. Proven: runner work refuses every group lane, then the drain retries it

Locations: `src/core/scheduler/admission.ts:212`, `:303`; `src/core/scheduler/slow-tier.ts:411`, `:626`; `src/core/scheduler/scheduler.ts:1064`, `:1337`, `:1451`.

The new refusal order is stopping, runtime gone, held, runner work, then the lane's `after` rules. It applies to default slow and configured groups, including `after: []` and explicit requests. Fast selection already refuses runner work. The table now checks lint, e2e and slow; existing halt tests plus the direct branch order establish precedence.

Selection reads the admission inside its lock task. A refusal returns `null`; `#launch` releases the unused slot and returns `"again"`. `#groupLanesNext` returns true, so the pump continues directly to `#drain`. While draining, it waits for an event rather than repeatedly selecting the lane. Drain completion clears `#draining` and calls `#notify`; `#nextEvent` also checks the latched `#woken` flag. Completion before registration therefore does not lose the wake. The next pass asks the lane again. The integration test reaches its run and `idle()`, rather than merely proving a refusal.

This guard reads queued work (`size`), as the fast path does. It does not add a rule for a refinement already shifted into its runner phase. That boundary is unchanged and disclosed in the notes.

### 3. Proven: waiting activity now covers configured lanes and remains lazy

Locations: `src/core/scheduler/scheduler.ts:646`, `:654`; `src/core/scheduler/admission.ts:227`; `src/core/slow/state.ts:79`.

The scheduler supplies one deferred `slowWaiting` callback. The admission calls it only when `rewalk` is requested, after stopping/runtime checks, and caches its boolean for that answer. Existing table tests cover repeated access and a halt that must read no activity.

The helper checks the default slow row, then the current policy's lane names through the existing `readGroupActivity(store, worktreeId, group)` contract. It uses the same names and keys as publication. A missing entry, missing row or invalid activity reads as null, hence not waiting. Any waiting reason holds the chunk; this is not limited to load. N1 concerns a repeated underlying read, not the lazy callback or coverage of lanes.

### 4. Proven: status, messages, keys and lane budgets keep their contracts

Locations: `src/core/scheduler/admission.ts:217`, `:317`; `docs/specifications/019-run-triggers/status.md:52`.

`LaneAnswer.waits` still uses only the lane's prior `after` rules. Its publication callers and activity writers are unchanged. The new runner-work refusal introduces no published reason or status field. The re-walk consumes existing activity without changing it. No formatter, CLI shape, message text or key source changed. Key-format and version-sensitive have current passing results.

The spec 019 amendment states that starting beside fast work means beside fast tiers, not before pending runner work, whatever the group's `after`. This matches the approved row and 011 C4's no-selection-before-runner-work rule. Guard budgets, explicit-request bypass, slot limits, pool grants, width and the same-turn launch check are unchanged. Intended user effects are the later safe start of a group and the re-walk yielding while that group waits.
