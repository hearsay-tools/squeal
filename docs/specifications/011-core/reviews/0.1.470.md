## The five order quirks

**Proven:** each design quirk holds.

1. **Lock per busy attempt, except behind runner work.** `#perTry` puts `lock.run` inside `#request` (`request-intake.ts:179`). The `always` branch puts retries inside `afterRunnerWork` (`:138`); the deferred full-suite branch does the same for recovery keys and stage (`:186`). The table's two lock-order rows and the retained real runner-recovery race pass.
2. **Full suite wakes all lanes before the lock.** Its declaration uses `wake.allLanes` with the required reason (`checkpoint-requests.ts:168`); `#take` calls it at `request-intake.ts:111`, before `#locked`. An install-wait abandonment does not move this wake after the transaction.
3. **Group marks its lane requested inside the stage.** `groups.get(group)?.request()` precedes `queueGroup` (`request-intake-requests.ts:124`). `SlowTier.request` still sets the request and calls `preempt`. The declaration names why the usual wake step is skipped.
4. **No final pump after a throw.** The async intake pumps only after the awaited locked answer (`request-intake.ts:112`); synchronous refresh pumps only after its successful store callback (`:96`). The pre-existing `afterTier` pump that admits runner work is still necessary before a narrow request can answer or fail. It is not a new pump after a failure.
5. **Fresh delivered pass, then the install's pass.** `start.afterPass`, `#afterPass` and `installWait.passFirst` retain that order and the delivered-number comparison (`request-intake.ts:106`, `:118`; `checkpoint-requests.ts:134`). The table and retained `full-suite-pass.test.ts` pass.

## Judgment of the three reported shifts

### N1: Proven, intentional: failed stages no longer leave new progress asks

Locations: `request-intake.ts:214`, `request-intake.ts:224`, `checkpoint-requests.ts:160`; unchanged consumers `request-progress.ts:33`, `ledger.ts:795`, `daemon/lifecycle.ts:311`.

Successful stages return the same covered `FileState` objects. Recording follows the outer transaction commit, in the same synchronous mutex task. No tier-record task can end a file between those operations. A retry records only its claims; group and narrow requests still pass all their selected/group files, with `RequestProgress.ask` filtering to queued or running; a checkpoint uses its own `record.testFiles`. Successful-request progress and idle activity remain the same.

A stage that throws now records nothing, as the design expressly requires. This is a real bookkeeping difference on failure. In the base, an ask made before a later stage failure could survive ledger restoration because restoration keeps the file object. If that file was already queued or running, its later independent accepted end could count as request progress. The new failed request creates no such ask. A temporary real-ledger/progress probe reproduced **one later end versus zero**. The daemon's unchanged lifecycle converts a changed progress count to activity and use, so this can remove an idle-period extension that the failed request formerly caused. An earlier independent ask for the file remains effective.

The request's rejection and the absence of its final pump are unchanged. This shift follows the approved record-after-commit rule. It is not a blocker, but “nothing changes” must not be expanded into a claim that failed-stage progress or resulting idle activity is identical. A full-suite warm-up failure after queueing but before `warmUp.start` finishes belongs to this same exception.

### Proven: moving the narrow lane wake preserves successful answers

`narrow-run.ts:137` still queues the same selection and adds the same lane asks under the mutex. `narrowAnswer` reads selection, policy and ledger state, not lane wake state. The intake records, then wakes that lane before releasing the mutex. `SlowTier.preempt` updates its preemption/deferral state; it does not synchronously run a tier. There is no new interval for another mutex task to observe half a successful request, and no new progress activity.

On an exception after the old wake position, the base could already have preempted the lane, whereas the new stage reaches no wake. Do not claim equality of that failed-stage side effect. The move is consistent with applying the common record/wake steps only after a committed stage; no changed request answer or new work after failure was found.

### Proven: reading narrow install-wait state before selection is equivalent

`request-intake.ts:141` reads the reason before the awaited plan. The writes to `#awaitingInstall` and `#reinstalled` occur under the same scheduler mutex, at start, reconciliation and reinstall (`scheduler.ts:405`, `:447`, `:577`). `selectNarrow` changes neither flag. Holding that mutex through selection therefore preserves the reason the base read afterwards. Unknown-group and lint decisions still precede an install-wait answer. A close can cancel work but does not independently change those install flags.
