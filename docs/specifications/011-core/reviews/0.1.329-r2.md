## Limits and disposition

### N1. Proven: after 120 s of busy release, the claim remains

`full-check.ts:155` and `:236` bound the release retry with monotonic time. If the store remains locked, the code logs the failure and allows shutdown to proceed with the claim still present. The next start can skip that day's full check. It never records a successful full check.

The external probe held a real SQLite write lock, stopped a held check, advanced the observed monotonic clock past `RELEASE_WITHIN_MS`, and verified that stop settled, the claim remained and the log named the 120,000 ms busy limit. This tested the deadline branch, not a two-minute wall-clock wait. A final slice and backoff can add a small amount beyond the nominal bound. The bound starts when release begins; it is not a bound on all shutdown work or on an unresponsive child.

This is acceptable bounded failure handling for a store that cannot accept a write. It is not an unconditional guarantee of returning every stopped claim. Keep this limit explicit in the coordinator's amendment record. It does not reopen the original loss of a release obligation after an ordinary busy wait.

### N2. Plausible ordering difference, acceptable: a crash can change the fallback handover group

The known R2 limit is acceptable for this repair. The first commit preserves the pending obligation and writes the current startup revision into its row. If the file has no persisted open move, the next start can use that newer row revision as `handover`'s fallback. Its group or order can differ from an uninterrupted start. This review did not run a separate group-difference probe.

This affects priority after a crash, not whether work survives, whether a result is current, or whether the second lookup may avoid the run. Existing open-move information remains the input where it exists; the bounded review does not require a new durable queue-order format for a file with no recorded move. Record the limitation. Do not promise exact order through this crash boundary.
