## Blockers

### B1 — proven: a failed OpenCode output can commit after an early verdict

Location: `src/harness/opencode/bridge.ts:197` through the commit at line 202; `src/harness/opencode/bridge-verdict.ts:48` and its `cancel` at line 58.

011 C8 says: “a hook stopped, killed, cancelled or past its deadline before that rolls back, so the report stays owed and the next eligible boundary delivers it”. Design section 2 says OpenCode abandons without hand-off; `handOver` also documents abandonment “when the write fails”. The brief explicitly asks to test stray SIGUSR2 and failed hand-offs.

`awaitSignal` starts before the output write. A signal settles its promise to `true`. If the output later rejects or times out, `handOver` calls `verdict.cancel()` and continues. Resolving an already settled promise to `false` does nothing. The next line reads the earlier `true` and commits the report despite the failed write.

Reproduced through the real `runBridge`, real `after` handler, real store and real child process. No stdout reached its reader. The stdout shim only retained the attempted text in a private marker and returned `false` without invoking the callback. After that marker appeared, the probe sent one SIGUSR2. The bridge's own 1 s `ack.by` bound then expired; no external kill was needed. Actual final output:

```text
stray outcome {"stdout":"","view":"fail","next":0}
AssertionError: expected 'fail' to be 'pass'
Test Files  1 failed (1)
Tests       1 failed | 13 skipped (14)
```

The recorded `view` is from before the next boundary. The bridge exited 0. The report contained `PASS -> FAIL`, but no host received it; the consumer was marked told and the next boundary had no transition. This requires an early signal plus an output failure; it is not a claim about its frequency in use. The existing stray-signal test covers a silent ping without a held report and cannot detect this case.

Reproduction recipe for a regression in `test/harness/opencode/held-answer.test.ts`:

1. Use `failedSince()` and the existing stalled `bridgeEntry` for `after`. Give the child a private HOME and runtime directory.
2. Spawn that entry directly, capture stdout and its exit, and send `{ kind: "after", ...about(r), tool: "read", stallMark: freshMarker, ack: { by: Date.now() + 1000 } }` to stdin. Use a fresh marker for every run.
3. Wait until the marker exists. It proves the report reached the intercepted write and the verdict listener is installed. Then `child.kill(VERDICT_SIGNAL)` once.
4. Let the bridge reach its own bound and exit. Assert stdout is empty, view is still `pass`, another writer can take the lock, the next boundary contains one `PASS -> FAIL`, and the following boundary contains none. Candidate instead has view `fail` and zero at the next boundary.
5. Also cover a write callback that reports an error after the early signal. Both failures must abandon.

Worker-sized fix: in `handOver`'s write-failure catch, cancel the listener, **abandon and return unconditionally**. Do not let an already true verdict override the failed write. Keep listening before the write, since a valid host verdict can race its write callback. Extend the held-answer test with the above timeout/error cases; retain normal, deadline and stray-ping controls. No schema, key, output, timeout or protocol change is needed for this repair.
