## Blockers

### B4: setting the gather aside also hides the record's active reads

**Proven; blocking in the added slot-gather/no-hidden-work scope.** `src/core/scheduler/slot-records.ts:86` subtracts the flight's tracked count while awaiting the gather. But `src/core/scheduler/record.ts:141` has already started `#ended(...)` before it calls `SlotRecords.record(ended)`. Those reads run beside the gather without a separate count. `#ended` awaits the warm-up read, stability reads, install stamp, runtime check and merge-hold check. They are scheduler work, not a held runner or a timer wait.

The design requires that rest resolve when “no tracked work is open”; it sets aside a runner's run and requires that “its end does not” count as rest (`research/scheduler-step.md`, “The wake loop”). The extension asks that setting aside the gather hide no work. With one ended backlog slot, a resting pump and record reads still pending, the new aside drops the count to zero. Rest resolves after its immediate check even though the record's reads have not ended. The existing new test covers fast reads and misses this overlap.

The following probe uses the public scheduler and the same real-store fixture as `scheduler-rest.test.ts`. The gate models one asynchronous read already in progress. It creates no host load and does not depend on a timed race:

```ts
import { expect, it } from "vitest";
import { WarmUp } from "../../src/core/scheduler/warm-up.js";
import { RUN_MISSING } from "../helpers/baseline.js";
import { virtualClock } from "../helpers/virtual-clock.js";
import { catchUpRepo, catchUpSide } from "./catch-up-fixture.js";

it("counts record reads beside a pending gather", async () => {
  const files = [{ path: "test/a.test.ts", ms: 1, imports: ["src/a.ts"] }];
  const repo = catchUpRepo(files);
  const clock = virtualClock(Date.now());
  const side = catchUpSide(repo, repo.main, {
    files, hostSlots: 2, policy: RUN_MISSING, backlogSlot: () => 1,
    scheduler: { clock } as never,
  });
  const original = WarmUp.prototype.read;
  let release = () => {};
  const gate = new Promise<void>((resolve) => { release = resolve; });
  let entered = false;
  let ended = false;
  WarmUp.prototype.read = async function (...args) {
    entered = true;
    await gate;
    ended = true;
    return original.apply(this, args);
  };
  try {
    await side.scheduler.start();
    await expect.poll(() => entered).toBe(true);
    let rested = false;
    let reasons: string[] = [];
    side.scheduler.rest().then((r) => {
      rested = true;
      reasons = r.wakes.map((w) => w.reason);
    });
    await new Promise<void>((resolve) => setImmediate(resolve));
    await new Promise<void>((resolve) => setImmediate(resolve));
    console.log({ readEntered: entered, readEnded: ended, rested, reasons });
    expect(rested).toBe(false); // Receives true on the candidate.
  } finally {
    release();
    WarmUp.prototype.read = original;
    clock.advance(25);
    await side.scheduler.idle();
  }
}, 20_000);
```

**Worker-sized fix:** keep the ended-read promise counted independently while the flight sets its gather wait aside. Preserve the current overlap of reads and gather; serializing them would change timing. Keep the ordinary future-gather rest and post-advance record/pump assertions. Add a gated-read case: rest stays pending while the reads are open; after releasing them it reports the still-future gather; after advancing it waits for record and pump completion. This can be contained in the record/slot-record accounting seam and its tests. No timer, key, tier or output change is needed.
