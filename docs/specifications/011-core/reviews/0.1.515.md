## Blockers

### B1. Proven: runner work can discard a consumed install change before its refresh

**Where:** `src/core/scheduler/scheduler.ts:1317` and `:1156`; `src/core/scheduler/step.ts:180-183`, `:197-204`.

**Contract:** wave 101 W1 requires “No tier, order, width, status payload, note text, CLI output or key change.” The design requires reads before a tier starts. The existing install rule (`install-stamp.ts:59-64`, task 001-109) specifically requires a package folder added without a lockfile rewrite to refresh environments before the next tier. This delta loses that rule under a normal content batch.

The sequence is:

1. The scheduler has checked stamp A before. A package folder appears, so the next stamp is B. No watched lockfile changes.
2. `#carryAfter(read-install)` calls `takeChange(B)`. That advances the remembered stamp and returns `changed: true` only in the current `Reads`.
3. An ordinary source batch takes the lock before the next step and queues its runner refinement. This is possible while the asynchronous install check is in progress or after it returns and before the next lock turn.
4. The next step reaches `drainRunnerWork` before `readInstallStamp`. It decides `drain` and returns `event`. The pump clears `Reads` because the wake is not `reads`.
5. After the drain, the next install check still sees B. `takeChange(B)` now returns false. No `refresh-install` decision is made. Ordinary refinement does not refresh environments unless its project was recreated, the content changed an environment input, or a runner failure is being retried (`refinement.ts:122-130`).

Thus an installed-package change can leave the scheduler using its prior environment and keys. A later tier can run on that stale environment state. The probe proves the skipped refresh; it does not claim that its fake runner demonstrated a wrong real-runner result. The baseline always queues `refreshInstall` immediately after consuming a changed stamp, so this is introduced by the step boundary. Released merge-hold paths avoid the same loss because `#released` persists outside `Reads`.

**Reproduction:** use `catchUpRepo` with one test importing `src/a.ts`, `writeInstall` with one package, and `catchUpSide` with a wrapper counting `runner.environment()`. Start and await idle. Touch `src/a.ts` and precompute its `statCandidates`. Add a second package folder without changing the hidden lockfile. Wrap `InstallStamps.prototype.takeChange` so that its first real `true` queues the precomputed watch batch synchronously:

```ts
const changed = original.call(this, check);
if (changed && consumed++ === 0)
  queued = h.scheduler.handleBatch({ trigger: "watch", paths });
return changed;
```

Wake the pump with an empty interval batch; await idle and the queued batch. Assert that the stamp changed once, the batch ran, and the environment read count increased. On the candidate it stays `1 -> 1` and fails. With baseline `scheduler.ts` the same assertion passes. Use a private home and fake runner; no host load or sleeps are needed.

**One-worker fix:** retain a pending install-refresh obligation independently of disposable iteration reads, or consume the changed stamp only when its refresh is safely scheduled. Clear that obligation only after the refresh succeeds. Add this interleaving as a permanent scheduler test. Do not fix it by allowing stale disk reads to survive every wait. Preserve fresh reads before starts, runner-work priority and the busy-store retry behavior.
