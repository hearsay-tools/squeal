## Blockers

### B1. Proven: a stopped or unrun check can keep the day's claim

Location: `src/core/daemon/full-check.ts:166` and `:185`.

The brief and worker contract require a check that cannot run or is stopped to give its claim back. `release` catches a busy error, logs it and gives up. The stop path sets `ended = true` before this attempt. Neither it nor the completion callback retries the release. Shutdown then proceeds toward closing the connection.

Proof on the built candidate: start a held full check, take `BEGIN IMMEDIATE` from a second connection, then call the returned stop function. After its 5 s wait, release the writer. `META_FULL_CHECK` still holds the cancelled check's start. Call `startFullCheck` again after the writer released: the run counter remains **1**, so the next start launches no check. Log:

```text
full integrity check claim not given back: Error: database is locked
```

The old claim now suppresses the check for 24 h although that check never finished. The unrun outcome uses the same release path and has the same fault.

Fix scope: the full-check owner must retain the release obligation across busy errors, retry without holding the event loop, and complete it before closing the store on normal shutdown. Keep the compare against the claimed value, so a later claimant is not erased. Test both stop and unrun with the store busy at release, then unlock it and prove a subsequent start can claim. This and S1 belong in one repair of claim ownership and its lifetime.

### B2. Proven: interruption between startup commits loses handed-over work

Location: `src/core/scheduler/bootstrap.ts:187`; the handover is not applied until `:225` and the following enqueue loop.

C4 requires every start, under either policy, to queue the files the predecessor left `queued` or `running`, unless lookup finds a result at the new key. The first lookup has `queueMisses: false`. The early commit writes these misses with `pending: null` before handover restores their queue entries. Only the running process retains `previousKeys`. If it dies during the closure recheck, the next start cannot recover that predecessor's queued work. The old single-commit path leaves the predecessor's rows intact until handover is ready.

Clean-candidate external proof, using `claimRepo`, `side` and `fileName` from `test/scheduler/claims-fixture.ts`:

1. Run one file under `RUN_MISSING`, close its scheduler and leave its row `pending: "queued"`, as a predecessor's unfinished work.
2. Start a successor under `lookup-only` with adapter version `2`. Its first lookup misses, and its stored closure triggers the recheck.
3. Inside that recheck's `runner.closure`, assert that the persisted pending phase is already `null`. Save a consistent SQLite image with `VACUUM INTO` before returning the closure. This image is what survives a process death at this boundary.
4. Let this successor finish as a control: it hands the file over and runs it once.
5. Close its connection, restore the captured image and start another successor with the same version `2` and `lookup-only` policy.

The final successor runs the file **zero times**, leaves its phase **null**, and has **zero current passing checks**. The adapter change makes the previous result stale, so no valid hit accounts for the omitted run.

Fix scope: the scheduler owner must preserve the pending handover durably through the early commit, then settle and clear that obligation with the second commit. Keeping it only in `previousKeys` is insufficient. Preserve the rule that a recheck hit is not queued at its first key. Add a restart-from-first-commit test for predecessor queued and running rows, including a case whose second lookup hits.

### B3. Proven: the inode recorded at startup can belong to the replacement store

Location: `src/core/daemon/open.ts:179`; compare `src/core/daemon/full-check.ts:228`.

The amendment requires every daemon on a condemned store to exit at its heartbeat, including when another start has already moved that store and its mark aside. The new inode comparison is intended to cover this. But `openDaemon` gets the inode by statting the pathname after it opened the database and prepared its scratch directory. Recovery in another worktree can replace that pathname between the open and the stat. The connection then points at the old store, while `storeFile` names the new store. With the mark moved aside, `storeCondemned` returns `null` at every heartbeat.

Clean-candidate external proof: seed a store with `meta["belongs-to"] = "old"`. Wrap `prepareScratch` so that, after preparing scratch and before returning to `openDaemon`, it performs the interleaving of another daemon: `markStore`, then `openStore({ checkIntegrity: "quick" })` to recover the store. No store or heartbeat function is mocked. After `openDaemon` returns, all these assertions hold:

```text
opened.store.meta.get("belongs-to") === "old"
opened.storeFile differs from the old file's dev/inode
opened.storeFile equals storeFileOf(commonDir)
storeCondemned(commonDir, opened.storeFile) === null
```

Thus the connection still reads the moved store, and its heartbeat accepts the replacement inode. The injected recovery gives a deterministic order to a real cross-process race; the per-worktree daemon lock does not exclude another worktree's recovery.

Fix scope: the store/daemon owner must bind the recorded file identity to the database connection that opened it. Serialize identity capture with recovery, or detect and retry a changed pathname during the open. A later pathname stat alone is insufficient. Add this open-versus-recovery interleaving to the tests, and prove the stale connection either never serves or is condemned at its next heartbeat.

## Should-fix

### S1. Proven delay, unverified effect on callers: taking the claim holds the main thread for five seconds

Location: `src/core/daemon/full-check.ts:159`; caller `src/core/daemon/daemon.ts:730`.

The new claim runs a synchronous `BEGIN IMMEDIATE` after the phase becomes `ready`, with a 5,000 ms busy timeout. It uses neither a short busy slice nor an asynchronous retry. With another connection holding `BEGIN IMMEDIATE`, a zero-delay timer scheduled before `startFullCheck` fired **5,018 ms** later. No child started; the log said `full integrity check not claimed: Error: database is locked`.

This proves a main-thread stall, not a hook timeout. The shipped socket runs in its own worker (`desk.ts`), and ping and nudge answers do not need the main thread. The probe did not prove an agent-facing failure. Treat this as a note, not a blocker. The spec's C8 busy-write policy favors short waits for retryable work after start. Use that mechanism for the claim, retaining its atomic transaction, and test an actual shipped socket alongside the held writer before making latency claims. The TypeScript-source fallback serves its socket on the main thread and is not evidence about shipped hook behavior.
