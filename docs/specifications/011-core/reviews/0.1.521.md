## Notes

### N1, plausible: hold the new SIGKILL case's check before killing its daemon

`test/daemon/sigkill-children.test.ts:190-203` waits for ready, finds the check
child, reads the claim through another store connection, then kills the daemon.
The check can finish between finding its pid and killing the daemon. On that
schedule the daemon correctly keeps an answered claim, so replacement takeover
is not expected. Killing the child can also report ESRCH. A faster disk or a
descheduled test process can widen this test's exposure. The 300,000-row fixture
gives time, but does not establish the required ordering.

The case passed in this review. No failing schedule was reproduced, so this
is a nonblocking timing risk, not a proven product defect.

**One-worker change:** freeze the check before reading the killed claim, as the
preceding case does, and verify the holder row still names the daemon. Register
the check's cleanup immediately. Then kill the daemon and the frozen orphan
before starting the replacement. This would test an unanswered claim without
depending on the fixture's check duration.
