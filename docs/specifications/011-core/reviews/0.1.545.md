## Row 011-391

FAIL 011-391: two proven breaks of the amended store-failure contract.

### B1. Proven, blocking: the identity check and mark write can straddle recovery

Locations: `src/core/daemon/store-fault.ts:37` and `src/harness/shared/context.ts:232` (mark written at line 235). The shared `markStore` writes by pathname. Neither new caller holds the recovery lock over its identity check and write.

Spec 011, store failures, 2026-11-18: **"A mark is not written over one already there, nor beside a file other than the one its writer opened."**

A permitted cross-process order is:

1. A hook or daemon handles corruption of store A. It sees no mark and stats A at `store.sqlite`.
2. Another writer marks A. A starting daemon acquires `store-recovery.sqlite`, moves A and its mark aside, and creates store B. It can store new results in B and release the recovery lock.
3. The first writer resumes. Its already-passed identity check names A, but `markStore` writes beside B.
4. B's daemons stop. The next start moves the healthy B aside and loses its new baseline.

The existing test replaces the file *before* the classifier runs. It does not cover replacement between the last stat and the write.

The deterministic probe used real candidate open, mark and recovery functions on temporary databases. For the hook, its supplied `now` callback ran the competing recovery after both guards and before the write. For the daemon, a `statSync` barrier returned A's real stat after running that same recovery. These barriers model another process running while the writer is descheduled; they do not change the classifier's decisions or its file writes. Recovery put `fresh=keep` in B. Each path then marked B, and the next real `openStore({ checkIntegrity: "mark" })` discarded that row:

```text
hook: identity changed before mark; fresh store marked; next start discarded fresh=keep
daemon: identity changed before mark; fresh store marked; next start discarded fresh=keep
```

A minimal hook reproducer, after building, uses these exports from `dist/`:

```js
const old = storeFileOf(commonDir); // A exists and is closed
markCorrupt(commonDir, old, "A's damage", () => {
  markStore(commonDir, { at: 1, problem: "A's damage", found: "daemon" });
  const b = openStore(commonDir, { checkIntegrity: "mark" });
  b.meta.set("fresh", "keep");
  b.close();
  return 2;
});
// storeFileOf(commonDir) differs from old, but readStoreMark() says hook.
const next = openStore(commonDir, { checkIntegrity: "mark" });
// next.meta.get("fresh") is null: a second recovery discarded B.
```

**One-worker fix:** give both new marking paths one store-identity-aware operation that serializes with recovery. Check identity and mark absence, then create the mark, under the same exclusion used by move-aside. A hook must fail quietly within its existing budget if it cannot acquire that exclusion. Keep the first mark. A second stat before the write alone leaves the same race. Tests must pause at the last identity check, let a competing recovery finish, then resume the old writer; B must retain its results and remain unmarked. Include concurrent mark writers and an unwritable/busy lock path.

### B2. Proven, blocking: a hook's setup read can throw corruption before the marking catch exists

Location in the changed range: `src/harness/shared/context.ts:121`. It calls `open()` without a catch and only marks the returned `"corrupt"` sentinel. `withContext` calls `openContext` at `src/harness/shared/hook.ts:107`, before its `try` and the new `faulted` call at line 124.

Concrete seam: `open()` calls `openSentStore`. After `openStore` succeeds, `src/core/delivery/sent-store.ts:87` reads `store.worktrees.get(worktreeId)` to decide whether writes go to the daemon. Corruption in that row throws from this read. It is neither an open failure returned as `"corrupt"` nor an error inside the context's protected callback. No mark is written. The outer hook still goes silent, but the other daemons keep serving and the next start sees no condemnation mark.

Spec 011: **"A hook whose open, read or write throws corruption writes the same mark when it can and stays silent; it never moves the store."**

The probe created a real store and a real worktree row whose `root` was 200,000 bytes. After closing it and `PRAGMA wal_checkpoint(TRUNCATE)`, it selected `pgoffset, pgsize` from `dbstat` where `name = 'worktrees' AND pagetype = 'overflow'`, then overwrote those 48 pages with `0xab`. The header and schema still opened. Calling real `withContext` for that worktree threw `errcode: 11` from the initial `worktrees.get`; its callback never ran. The mark directory was writable.

```text
hook setup: 48 real worktrees overflow pages damaged; open succeeded; initial worktrees.get threw SQLITE_CORRUPT; callback never ran; mark=null
```

**One-worker fix:** protect corruption from the entire main-store context-opening path, including that initial read, with the same identity-aware, best-effort marker as B1. Close the partially opened connection when setup fails. Preserve the current hook silence and normal handling of non-corruption errors. Add a real-page-damage regression on the worktree row; assert a hook mark, no move-aside and no output. Do not route code/lint setup errors to the main-store marker.

### S1. Plausible, nonblocking: the accepted prepared-code-commit case still lacks store provenance

Location: `src/harness/shared/hook.ts:124`. The brief explicitly accepts the worker notes' two narrow cases for this review. The broad catch can receive a failure from `prepared.commit()`. `src/core/delivery/prepared.ts:173` commits held code-store writes there; its error can escape the normal `withCode` catch. The new catch classifies an `errcode: 11` or 26 from that commit as damage of the main store. This would conflict with **"Corruption of the code or lint store marks nothing."** A damaged code-store COMMIT was not reproduced; this remains a plausible note, not a third blocker. The startup-wide classifier is the other documented narrow case; current code/lint/coverage stores open lazily and have separate error paths.

If this boundary is widened later, preserve which database raised the error or handle its corruption at that database's own boundary. A regression should fail a held code-store commit and assert that the main store stays unmarked. This can fit beside B2 if its worker needs to distinguish main-store setup from other setup, but it is not required to settle the two proven blockers.
