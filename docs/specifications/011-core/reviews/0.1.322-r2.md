## Blockers

### B2 remains. Proven: a legacy request loses its guard even when the new writer sees it before trimming

`src/core/retry/records.ts:95` calls `writeRetries` before adding only the **new** request's fact. Neither that path nor the retained-record returns at lines 208 and 210 import a legacy request into `retries-asked`. `src/core/retry/kept.ts:54` adds only the record passed to it. A request made before upgrade, or by a released writer, has no marker.

C15 still forbids a second ask at a held key. Its accepted retention exception keeps the fact while a worktree holds the key or for 7 days after the last request, up to 4,096 entries with unheld entries dropped first. The coordinator confirmed the design agreement `c40bf8e3` conditions (a) to (c): no mixed-writer exception was accepted. This failure reaches none of those bounds.

The isolated proof uses the released `squeal--v0.1.323` request function and a fresh SQLite store:

1. A worktree holds `test/a.test.ts` at key K, unknown and unqueued. The released writer stores a request at K and ends it with `unknown`. There is no `retries-asked` row.
2. The candidate's `askNamedRun` reads the retained request and correctly returns `asked`. It preserves no fact in the new row.
3. Seed 1,023 other ended requests to reach the existing 1,024-record limit. The candidate's `askRetry` stores one more request at a different key. Its new trim drops the original ended request. The ledger contains the newly added key only.
4. The original file remains at K. `askableFiles` selects it again, and `askNamedRun`, with the actual repaired eligibility predicate, returns `queued`. A second request at K is stored.

All times are current; the key stays held; fewer than 4,096 facts exist. Replacing the candidate trim in step 3 with the released writer's actual trim gives the same result. Thus this is not only an old writer deleting data before the candidate could see it: the candidate observes the fact and then discards it itself. The ordinary retained-history guard works only until that trim.

The new tests miss this order. `test/retry/asked-keys.test.ts:81` and line 92 create the first requests with the new writer, so they already have markers. The CLI case at `test/cli/status-wait-ask.test.ts:240` also uses the new writer before clearing the log. It proves that an old writer cannot erase a **new writer's** marker. It does not prove the claim that a request made by an old writer keeps its guard. The missing-record test correctly preserves uncertainty for the existing wait, but does not prevent a later wait from asking again when neither row keeps the old fact.

One-worker repair scope: preserve visible legacy request facts in the same transaction **before** any new-writer trim, including the facts found on retained `asked` or `joined` answers. Batch that import so it does not rewrite and scan the ledger once per request. Add ended and cancelled legacy fixtures with no ledger row, then use the candidate's actual trim and check that a second wait asks nothing. Include a released-writer trim after the candidate has observed the record. Also define a conservative mixed-version rule for a released writer that creates and removes a request before any new reader sees it; an empty ledger cannot prove that no request existed. A broader compatibility exception needs the human's decision and a dated amendment. Do not silently infer never-asked from missing legacy data.
