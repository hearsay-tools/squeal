## Blocker B1: current daemon claims do not prove that retained rows are unchanged

**Proven.** Primary location: `src/core/store/states-marker.ts:117-122`.
Also `statesMark`, line 107; `src/core/store/closure-writes.ts:50-54`;
the reuse branches in `src/cli/wait/every-state.ts:53-61` and
`src/cli/stored-closures.ts:53-55`.

Row 011-45 requires: "A state write between polls is found on the next
poll, and its news and quiet equal a full read's." Row 011-44 requires
that the retained selection equal a full read after a closure write.
Spec goal 3 requires current truth; C6 says the fallback ends on any
check's news. Both rows also promise to preserve the waits' outcomes.

The trust check describes only daemons registered **at this read**.
It neither records a writer that came and went between reads nor covers
an older CLI writing without a daemon. Such writes change the data but
not the new markers. Both caches then accept an unchanged, trusted marker
and retain rows from before the write.

### The documented registration/write/exit case

The private-store probe used this sequence:

1. Register and claim W's current daemon; leave X with no daemon. Give W
   and X the same key for `a.test.ts`. W has a current failing check.
   Record its closure without `source.ts` and move the closure marker.
2. Prime `readEvery` and a `StoredClosures` selection for `source.ts`,
   each in a read transaction. They retain the failure and zero readers.
3. Register X as an older daemon, without a marker claim. Confirm that
   `statesMark(W)` is null while X is registered.
4. Through the base version's repositories, write W's recovered state and
   replace the closure with X's closure containing `source.ts`. The keys
   still match, so that closure is valid for W. Commit the writes.
5. Clear X's registration before W reads again, as a clean exit does.
6. Compare retained and full reads in the same read transaction, three
   times. Both markers equal their values before step 3, and
   `everyDaemonClaims` is true again.

Each of the three reads printed:

```json
{"trusted":true,"markerChanged":false,"keptState":"fail","fullState":"pass","keptNews":0,"fullNews":1,"namedKept":0,"namedFull":1}
```

The final probe's store sequence and three reads took 6.7 ms. This measures
the store operations, not a real daemon's startup/run/shutdown time.
No real older daemon's lifetime was timed. The stale-read counterexample
is proven; the frequency of that lifecycle ordering on a live host is
unverified. A poll interval supplies no maximum bound on the time between
reads, so startup taking over one second would not establish safety.

### A writer that needs no registration or short lifetime

There is also an existing production route from an older CLI:
`core/code/gate/keep.ts` takes **its worktree's** daemon lock, then
`keep-here.ts:33-35` calls `storeResults`. Its shared-key recovery calls
`sink.refresh` for W (`scheduler/store-results.ts:48-61`). X need not have
a registered daemon. These files are unchanged by this candidate;
the new retention rule exposes the missed write.

The probe exercised `storeResults` and its real sink with the base
repositories, a fail-to-pass result at the shared key, and X unregistered
throughout. W's marker stayed unchanged and trusted. Then it compared the
**actual candidate and base `editPoll`** on the same store. Both started
with the failure and an unrelated `b.test.ts` still pending, with a sync
that returns unsupported. After the recovery, their deadline reads gave:

```json
{"olderGateWriterWithoutDaemon":true,"trusted":true,"markerChanged":false,"keptState":"fail","fullState":"pass","keptNews":0,"fullNews":1}
{"realEditPollComparedToBase":true,"candidateOutcome":"timeout","baselineOutcome":"news","candidateTransitions":0,"baselineTransitions":1,"candidateSnapshotFailures":0,"baselineSnapshotFailures":0}
```

This second case needs no registration to fall between polls. The final
snapshot is fresh, but the wait's reason and transition count differ from
the base because its decision used retained states. Existing tests only
leave the unclaimed daemon present for the next read, or write through
repositories that already bump; neither catches these cases.

### Fix, sized for one repair worker

Repair the shared invalidation contract for both caches. Reuse must be
supported by evidence that also detects relevant writes from older
clients, including clients with no daemon. A check of the current daemon
set, or only of `lastDaemon`, is insufficient for the gate case. Options
include invalidation enforced by the database for all writers, or a
retained database-change observer with a safe ordering relative to each
read. Fall back to full reads wherever that evidence is absent.

Add regression cases for both sequences above. Compare the candidate
poll's outcome and transition count with an uncached read, with unrelated
work still pending. Compare the named selection after the older closure
writer adds and drops the source path. Keep the unchanged-poll counting
tests. Do not change gate behavior to compensate for a reader's trust
error. Recheck key-format without a raise and measure any added write cost.
