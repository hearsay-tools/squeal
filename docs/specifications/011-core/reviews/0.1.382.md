## Blockers

### B1. Proven: worker-pool contention is reported as a busy slow slot

Location: `src/core/retry/text.ts:105`, through `src/core/retry/waits.ts:46`, `src/cli/retry.ts:252` and `src/core/status/outstanding-text.ts:255`.

Row 011-272 requires a known blocker or an explicit unknown. Its brief says: “Stop and report instead of widening when the blocker cannot be read without a new scheduler field; then the words say ‘queued’ and ‘blocker unknown’ only.” The styleguide says: “Record a fact where it is known; never infer it later from something that does not prove it.”

The scheduler publishes `{kind: "waiting", for: "slot"}` for two different resources. `src/core/scheduler/slow-tier.ts:260` publishes it when the shared worker pool refuses capacity. Line 296 publishes it when the slow slot is unavailable. `retryWaitOf` copies either to `{kind: "slot"}`. The new `holdText` always renders “the slow tier waits for the slow slot”. Spec 004 D2 distinguishes the slow slot from the per-user worker pool.

**Reproduced on the candidate:**

1. Start a real scheduler with one fake slow file. Let its first run fail, with automatic failure reruns disabled.
2. Give the scheduler a private worker pool with `hostSlots: 1` and a separate private slow slot with one permit. Take the pool's only permit using another owner.
3. Store an environment retry and call `scheduler.requestRetries()`. Wait for the published `waiting: slot` activity.
4. Successfully acquire and release the slow slot as a third owner. The slow slot is free; the shared pool is full; the slow retry has not started.
5. Read status and issue a joining environment retry from another session. Both print the false blocker:

```text
queued and not started: the slow tier waits for the slow slot
it has not started: the slow tier waits for the slow slot
```

The status group's JSON has `waits: {kind: "slot"}`. Text and JSON share the same ambiguous input; that agreement cannot establish which resource blocked execution. The existing new tests cover an occupied slow slot, but never the free-slot/full-pool case.

**Bounded fix:** keep the scheduler unchanged. Render the existing ambiguous state without selecting one resource, for example “waiting for capacity; whether the slow slot or shared worker pool holds it is not known”. Alternatively report an unknown blocker. Use the shared renderer for receipt and status. Add the free-slot/full-pool regression and retain the occupied-slot, failure-count and JSON assertions. No new scheduler field is needed.

### B2. Proven: pending acceptance falsely denies existing slow results

Location: `src/cli/run-slow.ts:77`; assertion repeated in `test/cli/run-slow-accept.test.ts:149`.

The new timeout line says “the daemon has not taken slow tier request s1 yet, **so no slow file has a result**”. A request's pending acceptance establishes no fact about results already in the store. This breaks the vision's requirement for trustworthy state and stated uncertainty, and the styleguide's rule to record a fact where it is known.

**Reproduced on the candidate:** create the existing `repoWith([], [SLOW_FILE])` fixture. Its slow file has a current result. Declare that file slow in its private repository's policy. A scripted socket returns the supported `run-slow` response with `requestId: "s1"`, `requested: null`, `error: null` for the initial request and its polls. Call `main(["run", "--slow", "--wait", "1"], io)` with the fixture's root and clock. The command exits 3 and prints “so no slow file has a result”, while the stored slow state remains current. The probe asserts both facts.

This is reachable when acceptance is delayed and some slow files are already current, or a slow run finishes independently while acceptance is pending. The candidate's new regression fixes the false sentence as the expected output, so green tests preserve the defect.

**Bounded fix:** describe only the request: it is pending and this command has no acceptance/result verdict for it. Remove the statement about every slow file's results. Keep the request ID, timeout exit 3 and next command. Add a pending-acceptance case with an existing current slow result. No daemon or scheduling change is needed.
