## Blocker

### B1. Proven: a real timing-write failure can roll back the whole start and strand the file

Locations: `src/core/scheduler/edit-timings.ts:88`, `src/core/scheduler/edit-timings.ts:123`, `src/core/scheduler/tiers.ts:214`. Relevant existing boundary: `src/core/store/connection.ts:57` and `:61`.

Contract need 2: **“a failed write loses at most the sample.”** The row's done-when requires **“a competing writer strands no launch and loses at most the timing sample.”** R1 question 1 explicitly asks whether an error kind can still abort the whole start.

The savepoint fixes the original competing-writer gap. It does not isolate SQLite errors that automatically roll back the whole transaction. A real `SQLITE_FULL` during the new timing write ends the outer transaction too. The nested transaction's `ROLLBACK TO` then fails because its savepoint is gone. `recordEditTier` catches that exception and returns, but `startTier`'s outer `COMMIT` fails with `cannot commit - no transaction is active`.

By then, `startTier` has removed the file from the in-memory queue, set its running key and taken its claim. Those moves are not undone. `act` never receives its tier, so `startNext` never calls `fly`. The stored run and phase writes rolled back. This leaves an in-memory running file with no flight or committed run to finish it. It breaks launch ownership and contract need 2.

**Independent proof.** I copied the existing `tier-start-fixture.ts` into a scratch directory, changed its relative imports to absolute imports, and replaced only the Vitest-dependent store helper with a private `openStore`. The production `Ledger`, `Connection`, `startTier`, `startNext`, recorder and SQLite writes stayed real. Each case queued the same forced edit file. I limited the private database with `PRAGMA max_page_count = page_count + 10`. A long but valid runner-part string made the optional record need more pages than that limit. This is fault injection to produce a real SQLite error cheaply, not a claimed normal part size or a measurement of disk consumption. No actual disk was filled.

The control runs the same `startTier` without the new timing callback under the same limit. It commits and hands off one tier. The candidate's `startNext` path runs the new timing callback and fails:

            message="database or disk is full", db.isTransaction=false
candidate: flown=0, failure="cannot commit - no transaction is active",

The following temporary test reproduces the same boundary using the committed fixture. Imports are from `test/scheduler/`; use the repository config and a timeout. Its assertions describe the defect, not the desired behavior:

```ts
import { afterEach, expect, it } from "vitest";
import { connectionOf } from "../../src/core/store/store.js";
import { declareTraits } from "../../src/core/types/runner-traits.js";
import { startNext } from "../../src/core/scheduler/tier-start.js";
import { candidate, closeStores, listPlan, setup } from "./tier-start-fixture.js";

afterEach(closeStores);
it("a real SQLITE_FULL in the sample loses the launch", () => {
  const { context, ledger, files } = setup(2);
  const picked = files("a");
  Object.assign(context.runner, {
    traits: declareTraits({
      tierWidth: () => 1,
      tierPart: () => "vitest:" + "x".repeat(200_000),
    }),
  });
  const db = connectionOf(context.store).db;
  const pages = Number(db.prepare("PRAGMA page_count").get()!.page_count);
  db.exec(`PRAGMA max_page_count = ${pages + 10}`);
  let flown = 0;
  expect(() => startNext(context, ledger,
    listPlan([candidate(picked, { kind: "edit" })]),
    { fly: () => { flown++; } },
  )).toThrow("cannot commit - no transaction is active");
  expect(flown).toBe(0);
  expect(ledger.queue.has(picked[0]!.file.ref)).toBe(false);
  expect(picked[0]!.file.runningKey).not.toBeNull();
  expect(db.prepare("SELECT count(*) AS n FROM runs").get()!.n).toBe(0);
});
```

The existing “disk I/O error” test throws an ordinary JavaScript `Error` before SQLite executes the write. The transaction remains open, so its savepoint can roll back. Its passing result does not cover a real SQLite automatic rollback. I did not inject an actual I/O fault; that error family's effect remains **unverified**. `SQLITE_FULL` alone proves B1.

The notes acknowledge whole-transaction errors and classify them as exposure shared with the old start writes. The control shows why that does not settle this row: the old start's writes succeed and the new optional sample alone introduces the failing write. The contract did not exempt that error kind.

**One-worker fix scope:** the launch/timing boundary in `tier-start.ts`, `tiers.ts`, `edit-timings.ts` and its regression. Ensure an optional timing failure cannot lose launch ownership, including a transaction-ending SQLite error. Recording captured facts after a flight has ownership is one option allowed by the brief. An in-transaction solution must also restore/retry the in-memory start when SQLite has rolled it back; catching the sample's exception alone cannot do that. Keep the original action stamp and grant, preserve the existing competing-writer regression, and add a real automatic-rollback case. Do not broaden into pool or busy-resume changes. If the design changes the lock turn, measure that final path again.
