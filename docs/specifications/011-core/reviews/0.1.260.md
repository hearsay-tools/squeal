## What fits

- **Close before the pass.** `src/core/scheduler/slow-tier.ts:193` checks
  `host.closed()` before reading the preemption count. The check and the read
  have no asynchronous boundary. A close before entry returns `"again"`
  without selecting candidates or starting a guard wait. The scheduler's
  pump then exits on its closed flag.
- **Close during selection or a wait.** A close after the count was read
  changes it through `preempt()`. The existing comparison after selection
  returns `"again"`. During a wait, `close()` still aborts its controller;
  the abort returns `"preempted"`. The closed check before starting a tier
  remains in place. An open pass follows the same path as before. The
  existing load-wait cases and their teardown passed.
- **The regression discriminates.** In a disposable snapshot of this
  candidate, removing only the new closed check made the new test fail at
  `test/scheduler/slow-slot-fair.test.ts:189`: expected `"closed"`, received
