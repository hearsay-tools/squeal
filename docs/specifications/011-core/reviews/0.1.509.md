## What fits

1. **Turns, proven by source and passing targeted tests.**
   `write-turns.ts:23` owns `max(10, ceil(heldMs))`. The daemon's main and
   code prunes use it in `sliced-prune.ts:69`; import uses it in
   `transfer-import.ts:95`. Every delete batch, parts batch and vacuum
   step yields one transaction before the driver pauses. A retry stays on
   that slice. No production caller uses the synchronous prune or import
   wrappers; those remain test helpers over the same slices.

2. **Same prune, proven by the diff, existing prune/parts tests and the
   scratch proof.** The SQL predicates, keys, table order, 256-row budget,
   vacuum page budget, counts and store format stay unchanged. The old
   synchronous entry points consume the same generator and return the same
   report. The daemon chains the code prune after the main prune through
   the same driver. `iterator.return()` reaches the code generator's
   `finally`, which closes its connection on stop and failure as well as
   completion. The injected failure logs `code prune failed`. Main-prune
   failure still reaches its continuation unless stopped.

3. **Busy handling, proven by source and the scratch proof.** Each yielded
   write uses `withBusySliceSync(BUSY_SLICE_MS, next.value)`. The code
   connection's `Connection.transaction` applies that context to its own
   `BEGIN IMMEDIATE`. Vacuum now also enters through that transaction.
   A refused delete leaves its count unchanged and retries that closure,
   rather than opening and repeating the whole prune. `SlicedWrites` no
   longer coalesces the code prune with the other timer groups; one
   `SlicedPrune` prevents overlapping prunes, and the shared `BusyWaits`
   still groups active waiters and names this one `pruning`. Failure labels
   stay distinct. No user-visible status or result meaning changed.

4. **Import, proven by source and passing import tests.** The daemon
   (`import-request.ts:74`), shared reader (`reader.ts:276`) and CLI
   (`import.ts:169`) all call `importSliced`. Its timed wrapper assigns the
   hold only after `slice.run()` returns; failed attempts and async retry
   delays cannot become the measured hold. The pause follows each
   successful slice, including the last. The generator resumes after that
   pause. The stop check remains before each slice; committed slices stay,
   and an interrupted import has no final record. A stop during the final
   pause can still return success, correctly, because its record committed.

5. **Tests: positive behavior proven; negative discrimination plausible
   from the worker's recorded experiments.** The waiter is another thread,
   with its own connection and a 250 ms busy slice. TEMP triggers sleep
   while the holder owns the lock. Each test compares landings at its first
   and last hold, so a write before or after the loop cannot satisfy it.
   Neither asserts a host-specific write count. The 30 s timeout is an
   outer test bound, not the fairness assertion. The notes report the prune
   failing 14/15 times without a pause and import failing 10/10, with both
   passing 5/5 when paced. They also name rare genuine lock-free gaps. Thus
   the negative prune test is not deterministic; the report does not claim
   that it fails on every no-pause run. I did not repeat those mutations.
   The injected-pause test separately confirms that every import slice
   calls the pacing rule.

6. **Row 011-318, proven unchanged in kind.** `prune.ts:202` still reads the
   coverage keys, asks the main store for held results, then deletes using
   that saved absent-key list at line 212. No lookup moved into the delete
   transaction and no new guard was added. Pauses extend the time over
   which a result and refreshed record can arrive for a previously absent
   key. They also admit same-process callbacks between slices. The
   lookup/delete race already existed across processes; its predicate and
   lost-record outcome are unchanged. It remains the separately planned
   row, not a new blocker for this wave.
