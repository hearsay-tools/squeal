## Blockers

### B1, proven: the group's full-list command omits group members

**Location:** `src/core/delivery/failure-groups.ts:105`, especially the limit at line 111.

**Contract:** C5, row 011-109: "one `squeal failures` command whose selection and limit list each of them". The brief also requires mixed errors to stay separate and the command to list each grouped check.

The command selects test files or their common directory. Those paths can contain other failures and historical failing rows. Its limit is only the group size, or the default 20 for a smaller group. `readFailures` lists all selected stored failures, newest first, not only this group's members (`src/core/status/failures.ts:98`; query in `src/core/store/repos/failures.ts:66`). Other selected rows therefore displace group members. This can happen in one mixed-error delivery; it does not require a race after delivery.

**Proof:** a standalone Node probe used the candidate's built `formatDelta`, real store and real CLI `main`. It stored 91 target failures across seven `tests/components` files, plus 25 newer failures with a different error in the same files. It rendered the target group and ran the exact command from `Full list:`. Output:

```json
{
  "command": "squeal failures tests/components --limit 91",
  "code": 0,
  "header": "Failures in this worktree for tests/components (newest 91 of 116, newest first):",
  "targetListed": 66,
  "otherListed": 25,
  "stderr": ""
}
```

The command succeeds but omits 25 members. The existing evidence test puts the other failures in `tests/api`, outside the selection, so it does not test this case. The worker notes acknowledge displacement by a newer failure; the amended C5 sentence still promises every member.

**Bounded fix:** one delivery/CLI worker must make the generated selection and limit include every group member even with other selected rows. Do not bound a broader selection by the group size. Add a real-CLI regression with unrelated failures in the same selected files/directory, including repeated historical rows for the same check. Keep one command and the current notice cap. No deny-once change is needed.

### B2, proven: a runtime-lost tier still applies its startup failure and drops queued work

**Location:** `src/core/scheduler/scheduler.ts:883`, where the runtime-lost tier's unfiltered report is passed to `recordTier`. The receiving seam is `src/core/scheduler/tiers.ts:735` and `src/core/scheduler/setup.ts:81`.

**Contract:** C11, row 011-106: "A tier during which the daemon's own runtime went stores nothing either: its files are queued again". C9 requires files to remain queued. The brief says no missing recorder is stored as a FAIL.

The new requeue set governs per-file `storeDecision` only. After those files are requeued, `recordTier` still calls `failStartup` for `report.startupFailure`. That call records a setup FAIL and blocks/removes queued files in the affected project. Vitest uses this report shape when a run rejects before a test file is queued (`src/runners/vitest/startup.ts:30`). Thus a setup or pre-file startup error during runtime deletion bypasses the new protection. The same seam can apply a setup recovery from a report whose test results were rejected.

**Proof:** a standalone Node probe created a real repository, store, state sink and scheduler with an existing `runtimeDir`. Its runner removed that directory during `run` and returned a crashed report with no completed files and this startup failure:

```js
startupFailure: {
  projects: [""],
  testFiles: [{ project: "", path: "a.test.ts" }],
  setupFile: "setup.ts",
  error: {
    name: "Error", message: "Cannot find module recorder.cjs",
    stack: null, location: null, diff: null, phase: "setup"
  }
}
```

The scheduler sent the runtime-gone note naming `squeal start`. After its close, the real store contained:

```json
{
  "runs": 1,
  "keys": [{ "file": "a.test.ts", "pending": null }],
  "states": [{
    "check": { "kind": "setup", "project": "", "testPath": "setup.ts" },
    "outcome": "fail",
    "summary": "setup failed: Cannot find module recorder.cjs"
  }]
}
```

This is the first interruption, so the once-per-key limit is not involved. The claimed recovery command will not find the file queued.

**Bounded fix:** one scheduler worker must reject the runtime-lost report's setup outcomes as well as its per-file results. Preserve run accounting and resource release, the queued files and the once-per-key rule. Do not fail, recover or block a project from this rejected tier. Add a startup-failure regression with another queued file in the same project and verify successor recovery. Keep normal setup failures outside runtime loss unchanged.

### B3, proven: a slow tier starts after its runtime disappears during the load wait

**Location:** `src/core/scheduler/scheduler.ts:696`, with the unchecked slow-start path at lines 724 to 727. The wait and selection seam is `src/core/scheduler/slow-tier.ts:208`.

**Contract:** C9, row 011-106: "before each tier ... when [the directory] does not [exist], it starts no tier". The queued-work done-when explicitly requires no tier to start.

The runtime check happens before `await this.#slow.next()`. That call can wait for the load guard, normally for up to `slow.maxDeferMs` (600,000 ms by default). When the runtime is removed during that wait, `next` still selects a tier and the scheduler calls `#fly`. The next runtime check is after the unnecessary run ends. In that interval the new missing-runtime rule does not hold.

**Proof:** a standalone probe used the real scheduler, store and state sink, one slow `a.test.ts`, trigger `idle`, one slow permit and an isolated slot directory. The runtime existed at the pre-tier check. The injected load reader removed it on its first read and returned high load; its next read returned low load. The runner recorded whether its runtime was absent at entry. Output, omitting only the full note:

```json
{
  "runs": 1,
  "ranWithRuntimeMissing": true,
  "loadReads": 2,
  "keys": [{ "file": "a.test.ts", "pending": "queued" }],
  "states": []
}
```

Post-run requeue works in this case, but the tier must not have started. This is a deterministic wait boundary, not a speculative filesystem race.

**Bounded fix:** one scheduler worker must check runtime availability after the slow guard wait and before starting the selected tier. Integrate the guard at the slow selection boundary, or safely unwind any selected but unrun tier. Leave files queued, release any acquired slow slot, capacity lease and claim, persist the note once and take the existing `reinstalled` exit. Add a regression that deletes the runtime while the guard waits and requires zero runner calls. Preserve normal slow-slot fairness and cancellation.
