## Blockers

### B1. Proven: the new observer can defeat a restart from an older hook

**Location:** `src/cli/wait-liveness.ts:122` and `:165`. The affected existing decision is `src/core/daemon/open.ts:105`, through `servedElsewhere` and the last-version check at `:118` after a lock wait.

**Failure scenario:** a newer daemon served a worktree with an older plugin session still registered, then stopped on SIGTERM. Its record is cleared; its last version stays recorded; there is no handoff or serving successor. The older session's resumed hook starts its own daemon. With the singleton free, that daemon takes it on its first attempt and serves. If a wait's new probe holds the singleton at that attempt, the spawn takes the vacant-lock path. That path gives up when the last recorded version is newer than its own. It returns `lost-lock`, without a serving daemon or a restart. Even if the probe releases before the next attempt, the post-wait last-version check can reach the same result.

The private probe above demonstrates both paths through production `openDaemon` and the real `lockHeld`. An ordinary same-version spawn retries; the older-version case does not. The existing `test/daemon/vacant-wait.test.ts` deliberately proves the version rule for a real daemon handoff, but does not test an observer as the temporary holder. `test/cli/wait-locked.test.ts:85` proves that a lock can be acquired after a completed probe; it does not exercise a daemon that meets the probe.

**Contract:** wave 52 W1 requires a resumed session to get a validating daemon at its first wait, or the reason it cannot to be fixed. C9 permits sessions of older plugins and describes hook restart after a signal stop. Its new observation must not turn a previously successful restart into a losing daemon. F4 and board row 011-251 name the concern, but the C9 amendment does not accept a lost restart as a limit.

**Comparison with status:** `daemonGone` uses the same take/release operation. Its production callers do not probe this cleared-record state: `withDeath` returns when `record === null`; `withStopping` routes a null record to `claimed`, which reads no lock. The new wait probe therefore adds contention to the signal-restart window that those status paths leave alone. It is not just another invocation in the same state.

**One-worker repair:** replace the contending observation with a source of start/stop state that does not take the singleton, or replace this probe with the spawn-state design carried by 011-251. Add a deterministic regression with a cleared record, a newer last version, no live claim and an older spawning daemon. Pin both controls: a real newer holder must still defeat that older contender; an observer must not. Preserve nonblocking reads, the deadline, named exit 3 / JSON reason `lapsed`, and pathless exit 0. Changing only the new daemon's retry code is insufficient for sessions that still run old installed bundles.
