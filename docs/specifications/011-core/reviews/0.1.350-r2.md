## Should-fix / nonblocking notes

### N2. Proven: a poll can mix a cleared-record snapshot with a mark removed after registration

**Locations:** `src/cli/wait-liveness.ts:124`, `src/core/daemon/daemon.ts:468`; callers `src/cli/status-wait.ts:304` and `src/cli/status-wait-paths.ts:253`.

**Scenario:** a settled poll's read transaction sees the cleared record while the new daemon is starting. The daemon then commits its registration and removes its start mark. The poll reads the filesystem afterward. Its WAL snapshot still has `record === null`, but `startMarked` now returns false. `judge` returns down/stopped. With no higher-priority news, either wait can return `no-daemon` even though the daemon has registered and still holds the lock. All later store reads in that poll retain the old snapshot, so they cannot correct the decision. C9's explanation that the wait reads the record once the mark goes does not hold for a poll already inside its read transaction.

The private snapshot probe above proves the observation through the actual store and judge. The production sequence follows because `withStatusStore` uses deferred `BEGIN`; a WAL reader does not prevent the daemon's registration commit. The probe did not run a concurrent serving daemon or measure the frequency. The existing regression tests pin a mark held through a poll and the state after registration, but not this boundary between the two reads.

**One-worker follow-up:** before concluding stopped from a cleared record and an absent mark, retry that decision in a fresh store read transaction. A second read inside the old transaction is insufficient. Keep the existing deadline and noncontending observation. Add a deterministic regression that commits registration and removes the mark after a poll pinned the cleared record; cover named and pathless outcomes. This is a new repair-delta note under the bounded re-review rule. It does not reopen B1's resolved lock contention or block this verdict.
