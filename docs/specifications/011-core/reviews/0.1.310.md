## Blockers

### B1. Proven: a write after the hash read is lost across a stat-cache reload

**Location:** `src/core/revision/reconcile.ts:122` through the cache update at line 131. The persistence boundary is `StatCache.flush`/`StatCache.load` in `src/core/hash/stat-cache.ts`; the caller is `WorktreeKeys.bootstrap` in `src/core/scheduler/keying.ts:179`.

**Contract:** goal 3 says, "Everything the agent is told is true at the moment it is told". C2 says, "Anything the watcher missed becomes a revision then. This bounds the damage of a lost event to latency, never to a false 'current'." The brief also requires no lost change without a following batch and a write after the read to be a change on the next pass.

The new update stores the hash read before a write beside the stat taken after that write. It marks the pair racy, which repairs it on the next pass of the same cache. The racy mark is not persisted: `StatCache.load` constructs entries with an empty racy set. A daemon restart before the next pass therefore makes the pair trusted. Its stat agrees with disk, so line 104 skips the hash on startup and on every later pass. No revision or new key exposes the write. A result at the old key can remain current.

**Reproduction, with real filesystem writes and a real scratch SQLite store:**

1. Commit `src/a.ts` containing `export const a=1;\n` and a test that names it. Bootstrap `WorktreeKeys` and compute the test's key. The freshly seeded source entry is racy.
2. Reconcile its unchanged candidate stat. A wrapper calls the real hasher, then appends `// post-read write\n` before returning that hash. The new post-read stat sees the append. No watcher batch follows.
3. Close and reopen the store, construct a new `WorktreeKeys`, then call `bootstrap` and assemble the same closure and environment.
4. The candidate returns no revision, retains hash `8cfc2f...`, and computes the unchanged key. The real disk hash is `fb4460...`. An assertion that the loaded hash equals disk fails. A separate direct `StatCache.load` probe remains stale through three passes.
5. The same tests pass with only `reconcile.ts` restored from the range base. That source stores the earlier stat, so the append's changed size and ctime force a read after reload.

This is introduced by the later-stat pairing. It does not depend on the pre-existing same-size, same-timestamp-tick reload limitation: this append changes size, and the old code detects it. A normal daemon death or step-down between the pass and the next batch/pass is sufficient to cross the persistence boundary.

**Bounded fix for one worker:** make the uncertainty survive reload, or conservatively re-read potentially mismatched persisted entries at startup. A stable verified stat/hash pair is another valid design. Keep the no-following-batch behavior that the first discarded-entry repair broke in `linked-start.test.ts`; simply leaving the entry untouched is not sufficient. Add a regression that performs the post-read append, flushes, closes/reopens the store, and bootstraps without a watcher batch. It must record the change and move the key. Retain both new stat-pairing regressions, the ordinary touch contract and the no-batch linked-start case. No existing-table column may be added under an unchanged schema version (C7).
