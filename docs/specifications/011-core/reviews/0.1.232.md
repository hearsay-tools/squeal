## Blockers

### B1. Proven: the Vitest comparison can approve changed stored failure fingerprints

Locations: `test/keys/validity/harness/vitest.ts:26-33`, especially the result projection at line 31, and `test/keys/validity/verdict.ts:117-135`.

C3 defines stored meaning as "the checks it stores, and per check its outcome and its fingerprint as `sameFingerprint` reads it". C14 requires each adapter to use that rule under its own version. `storedOf` retains only each result's check identity and outcome, and reduces a file error to the file's path. `ranFiles` compares that reduced data. Neither test failures nor file failures retain the fingerprint that `recordsForFile` actually stores. The canned `rows` cases do not repair this seam: their reports do not come from the adapter under test.

A scratch probe ran `compareTrees` against the candidate's sources on both sides, with one `adapter:vitest` fixture. Its sole test writes `$STARTED`, waits while `$HOLD` exists, then runs `expect(1).toBe(2)`. It has no touched paths, so both sides complete the file and would store its failed test. The candidate overlay changes this line in `src/runners/vitest/results.ts`:

```ts
name: error.name ?? "Error",
```

to:

```ts
name: "ChangedAssertionKind",
```

The comparison returned:

```text
fired components: ["vitest"]
keysEqual: true
outputsEqual: true
uncovered: []
failures: []
```

The existing projection at both sides was the same completed file, `outcome: "fail"`, and no file-level load error. A diagnostic capture in the scratch harness, before the projection, passed each real failed result's errors and location through `describeFailure`, exactly as `recordsForFile` does. It observed:

```text
AssertionError: expected 1 to be 2 // Object.is equality @ test/a.test.ts:4:230
ChangedAssertionKind: expected 1 to be 2 // Object.is equality @ test/a.test.ts:4:232
```

These fingerprints differ under `sameFingerprint`, including independently of the differing source columns. This changes a stored value that C3 treats as meaning, with unchanged adapter version and keys. Coverage does not catch it: the added failing case runs the changed line on both sides, yet the comparator has discarded the evidence. Adding a case alone therefore cannot satisfy the alarm's contract.

As a sensitivity check, the scratch harness added each failed test's derived fingerprint to its existing result projection. The identical fixture and overlay then produced no uncovered lines and correctly failed with:

```text
adapter:vitest case "failing result fingerprint": equal keys, different outputs at same tree and the candidate (run 1, :test/a.test.ts: completed at the last release, completed at the candidate, its other outputs differing); raise VITEST_ADAPTER_VERSION (src/runners/vitest/version.ts)
```

**Repair sized for one worker:** project the rows the real adapter reports would store, including test and file-level check identities, outcomes and fingerprints, and compare fingerprints through the candidate's `sameFingerprint`. Keep duration, summary and other wording outside meaning. Preserve the accepted completion/withholding direction rule. Add a failing-test case, a file-error case and an overlay regression that changes a fingerprint without changing identity, outcome or completion; it must ask for `VITEST_ADAPTER_VERSION`. Retain a wording-only regression that passes when fingerprints remain equivalent. Do not repair by requiring a raise for every textual error change.
