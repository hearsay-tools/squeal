## Blockers

### B1. Proven: a fresh heartbeat no longer bypasses the stop mark

Location: `src/core/presence/decide.ts:169`; caller `src/harness/shared/ensure.ts:73`.

The old `delivery/stopped.ts` `heldStop` returned `null` immediately for `live.state === "alive"`. The replacement combines that case with the cases that return the stored mark:

```ts
if (heartbeat.state === "alive" || mark === null || mark.untilStart === true) return mark;
```

Reproduction: use `scratch({ heartbeat: -2000, stop: { at: -30000, untilStart: true } })` and `at(0)` from `test/presence/fixture.ts`. Call the old and new stop readers and then each `ensure` with an injected `ensureDaemon` returning `alive`, and hook version `0.1.400`, equal to the recorded daemon. Actual output:

```text
oldHeldStop: null
newStopHeld: { at: 1793779170000, tree: "t", untilStart: true }
old ensure: alive; ensureDaemon called
new ensure: stopped; ensureDaemon not called
```

The same wrong mark is returned for a plain stop beside a fresh heartbeat. If Git cannot print the tree, `stopHolds` honors that mark and the new hook returns `stopped`; the old hook reaches its normal ensure path. This also introduces a Git call on a path that previously skipped it.

This state is allowed: C9's `--until-start` amendment explicitly allows a daemon spawned in the stop's window to validate until it exits. The mark remains stored while that daemon heartbeats. The row and research brief require the hook's decisions to stay unchanged. A newer hook also skips its handoff path when the new early return fires.

Fix sized for one worker: restore the fresh-heartbeat `return null` before returning a mark. Add explicit expected stop-view outputs for fresh heartbeats beside both stop modes, with marks before and after the heartbeat. Cover the hook boundary too. `test/presence/presence.test.ts:58` currently compares `stopHeld` with `presence.stop`, two results from the same helper; it cannot catch this error. The existing stop rows contain cleared or stale records, not this combination.

### B2. Proven: the shared fact reader adds unrelated store and lock-mark I/O

Location: `src/core/presence/facts.ts:81`, `:90` and `:95`; callers `src/harness/shared/deliver.ts:95`, `src/harness/shared/ensure.ts:73` and `:172`, `src/cli/start.ts:158`.

The brief requires: "I/O is unchanged: no reader probes the lock, reads the socket or the store more often or at a different moment, above all on the hook paths." `readPresenceFacts` eagerly reads every meta mark and both lock marks before a narrow view can return. Only the lock acquisition and in-flight runs are lazy.

The probe spied on `store.meta.get` and the named `node:fs` `readFileSync` export while evaluating the old edit-line expression and the candidate's exact replacement expression. It used a recorded daemon with no shutdown mark or note, at `at(0)`:

| Heartbeat | Base meta reads, in order | Candidate meta reads, in order | Base mark-file reads | Candidate mark-file reads |
| --- | --- | --- | --- | --- |
| `at(-2000)`, fresh | None | notes, exit, handoff, short handoff, rest, stop, feed | None | `.starting`, `.spawned` |
| `at(-12000)`, stale | exit, notes | notes, exit, handoff, short handoff, rest, stop, feed | None | `.starting`, `.spawned` |

The returned edit-line value agrees with the base in both cases. The I/O does not. The stale case is the normal input to the "Not validated" line, so the issue does not depend on a fresh-heartbeat race. Reading a valid start mark can also read `/proc` to check its process.

Other moved paths have the same cause:

- The hook's old stop check read only its stop mark, and skipped even that when alive. The new call reads all facts and lock marks before the stop check. If it continues, `spawnStartCurrent` reads the marks again at the old later point.
- The hook's handoff path now reads rest, stop, feed and lock marks even though it needs the record, short handoff, claim and, only for a stale heartbeat, shutdown evidence.
- `start`'s old `shortOf` read one short-handoff meta key. Its replacement reads a worktree row and the other facts too.
- `wait-liveness.ts`'s stopping read now collects unrelated facts. The public `daemonStart` facade also reads `.spawned` when a live `.starting` mark already settled the old reader.

The worker's decision 4 preserves the absence of a lock-acquisition probe on the hook stop/edit paths. It does not preserve their store and mark reads. No new socket call or lock acquisition was found on those two paths; the proven breach is the added reads and their timing.

Fix sized for one worker: keep all presence rules inside `presence/`, but collect only the facts the requested view needs, at the caller's existing read boundary. Make unused facts and decisions lazy, or provide narrow fact readers for hook stop, edit line, handoff and `start`. Keep once-only reads within one view without forcing unrelated reads. Preserve `daemonStart`'s short circuit after a live start mark. Add boundary tests for read counts/order, zero lock probes on the hook stop/edit paths, and the existing early-return cases. Repairing only `lockFree` does not fix this finding.
