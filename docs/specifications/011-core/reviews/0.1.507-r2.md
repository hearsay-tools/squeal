## Note

### N1. Proven: `startNext` is not a general frame for every former selection write

Locations: `src/core/scheduler/scheduler.ts:1112`, `src/core/scheduler/tier-plan.ts:221`, `src/core/scheduler/tier-start.ts:64`.

The repair commit's explanation says this frame "holds every write selectTier made." That is too broad. JavaScript evaluates `this.#plan(context, ledger)` before entering `startNext`. The `Plan` constructor calls `steps.next()` immediately, so initial lookups and any `endPass` commit reached before the first yielded candidate happen without a `startNext` frame. Generator continuations invoked by `afterRefusal`, `afterUnstarted` and `afterStart` run inside it, as do act/start transactions.

This does not block the three repaired injection sites: they target the runnable edit's `startTier` transaction as described above. No code fix is required. For later tests that target an empty, fully settled or refused selection, select the actual write boundary instead of assuming `startNext` encloses construction of the first candidate. A one-worker documentation follow-up can narrow the explanation to these start transactions if it is repeated elsewhere; a future test needing broader injection should assert its chosen transaction explicitly.
