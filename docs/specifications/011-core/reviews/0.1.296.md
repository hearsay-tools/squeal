### B1. Proven: the protected module's end does not recheck an unchanged tier

**Where:** `src/core/scheduler/yields.ts:208`, `:329`; integration boundary `src/core/scheduler/scheduler.ts:409` and `src/core/scheduler/tiers.ts:545`. The new `named` decision has no bound. The existing file-end callback calls `#recheckTiers` only when `tier.changes.size` is nonzero. A tier starts with an empty change set. Neither a promotion nor a file end adds a revision change to it.

**Contract:** C4 step 5 says a promoted file counts when it ranks before every file of the tier "that has not ended". C15 requires the line to say whether that tier yields. The worker's notes at line 20 assert that a file's end checks the tier again. That is false for this common case. This is a new dependency on the existing guard, within this range's changed scheduling boundary.

**Reproduction:** Use test 1's four-file tier, each estimated at 200 s, and queued P. Before the tier starts, wrap the fixture runner's `run` to capture `options.fileEnded` for that run. Move its clock to 40 s. Promote `[A, P]` for 60 s and establish `named`. Call the captured callback with A while the other three files remain in flight. Wait the fixture's 1.5 s settling period. The tier is still not cancelled and still publishes `named`. Now P ranks before every unfinished file, since A is ended and the other three have no open wait. Repeating `promote([P], 60000)` immediately cancels the tier and publishes `yields`.

**Impact:** P waits behind unrelated long-running modules after the reason for protecting the tier has ended. Text and JSON continue to present the expired reason as current. With a short remaining estimate, this also bypasses the overrun timer that should be restored once the protection is gone. The seven new tests cannot catch it because their fake runner reports no module ends.

**One-worker fix:** Recheck a tier's named-wait rank when a module ends even when no revision has touched that tier. Keep the existing supersession, claim, cut-once and backlog-turn checks. Add a scheduler regression that reports A ended while another module stays in flight and proves P makes the tier yield without a new edit or promotion. Keep already-ended evidence under the existing recording rules. Correct the notes' event claim.

### B2. Proven: an expired earlier wait can keep a later waiter behind an overrun tier

**Where:** `src/core/scheduler/yields.ts:208`, `:303`, `:327`; `boundOf` at `:397`. `named` removes the tier's bound. Rank lookup excludes expired promotions, but no timer asks it again when a protecting promotion expires. Notes line 20 says no check is needed because nothing then waits. That ignores a later wait with a later deadline.

**Contract:** C15 Rank protects files selected by the same or an earlier **open** wait. C15 Lifetime ends promotion at its deadline. C4's exception is therefore gone when the last protecting earlier wait closes. The unchanged overrun rule must apply to the still-open queued promotion. Vision principle 2 and C15 also require the reason to describe the current state.

**Reproduction:** Use the four-file tier with a 20 s estimate. Move its clock to 55 s, already 35 s past the estimate. Promote only A for 3 s. Then promote only P for 60 s. The earlier wait on A makes the later P wait read `named`. Let more than 3 real seconds pass with no edit, new promotion or module end; the probe waits 1.5 s, then 2.5 s. The tier remains uncancelled and publishes `named`, although no open wait selects any file of the tier. P remains promoted. Repeating its promotion immediately cancels the overrun tier. This expiry proof uses real elapsed time, not just a moved clock.

**Impact and bounds:** A later wait can time out pending when it should have run after the earlier wait expired. The CLI's `--wait` still ends at its own deadline. A normal Vitest run also has `runner.timeoutMs` (600 s by default) plus its cancellation grace. `timeoutMs: null` removes that runner deadline. In either case there is no remaining estimate-plus-30-second guarantee once `named` goes stale. C4 permits that delay while a protecting wait is open; it does not permit an expired wait to keep it. A quiet reconciliation is no repair guarantee: Vitest has no runner `recheck`, so an unchanged pass returns without `host.applied` and never calls the tier check.

**One-worker fix:** Arm a recheck at the earliest promotion deadline that can change the protected unfinished files' minimum rank while queued promoted work remains. A bounded rank recheck is also possible if its delay is stated and tested. At that check, refresh ranks and claims, restore the unchanged remainder/overrun rule and replace the published reason. Do not cancel merely because a deadline passed if a different open wait still protects an unfinished file. Add distinct-deadline regressions, including an already-overrun tier, a later P-only wait, and a case where protection correctly remains. Amend the notes' no-deadline-check claim.
