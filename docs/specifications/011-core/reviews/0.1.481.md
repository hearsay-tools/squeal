The real-daemon test proves that a worktree without dependencies prints the reason with and without `--wait`, rather than the empty/current sentence. Its exit codes stay 0 and 3 respectively. The intake table proves both `AWAITING_INSTALL_REASON` and `REINSTALLED_REASON` reach the answer; the CLI tests and independent probe prove both print correctly. Its waited receipt fixture has no store, so its exit 3 proves rendering and code stability only; the real install-wait test supplies the daemon evidence.

### Request order: proven

The two new `afterPass: true` declarations call the unchanged rule at `request-intake.ts:123`. It records the number of passes already started, awaits the next queued pass, then requires a delivered pass numbered above that count. `change-feed.ts:176` joins only a pass not yet started. Its pending slot is cleared before that pass starts; a request during a running pass queues another. Delivery is recorded after `onBatch` completes. Thus an already running pass cannot satisfy the new request by itself.

The intake rows begin with a current file, then store its edit in the requested pass. Both answers use the edit's revision and queue the edited file. The real-daemon regression repeats the research order with an in-process command: a failing edit gives exit 1 for the group, then a passing edit gives exit 0 for the narrow run, each at a revision above the previous one. `fullSuiteRequest` and its pass rule are unchanged.

### Who now waits, and for how long: proven in source

| Client | New wait | Existing client budget |
| --- | --- | --- |
| Group or narrow CLI, including without `--wait` | One pass before taking the request | Request phase: 10 s without `--wait`; supplied milliseconds with it; no finite deadline for bare `--wait` |
| `run --slow` | Same group request, before queuing slow files | Same 10 s / supplied / unbounded choices; daemon discovery precedes this clock |
| Lint group's release | One pass before `releaseLint`; the existing later pass is still requested without awaiting it | Same CLI choices as a test group |
| Stop's waiting entry | The scheduler takes its group request after a pass too | The entry awaits only the initial request-id answer, not scheduler acceptance. Requests share at most `min(2000 ms, remaining Stop budget)`; the overall wait retains its configured bound, capped at 3,540,000 ms |

Yes, group, narrow, slow and lint commands can now spend time waiting for a pass where they did not before. These are client budgets, not a fixed maximum duration of a pass. `#afterPass` has no timer. The feed queue, filesystem work, scheduler lock or busy-store retries can delay it without a finite daemon-side bound. A disconnected client does not cancel its queued request. Existing request-loop details remain: a 50 ms socket floor; slow requests also use fixed 100 ms pauses, so a numeric deadline can be exceeded by that scheduling overhead. The research's 0.06 to 0.23 s is a measurement, not a bound.

The notes' “not awaited” description of Stop refers to scheduler acceptance: `requestGroups` itself does await the initial socket replies (`stop-wait.ts:86`). The daemon's group and slow handlers return request ids without awaiting their scheduler promises. The new pass does not force Stop to await that promise. It can postpone actual validation and consume the existing overall Stop allowance.

`NO_PASS` is reachable during normal failure handling: a Git/filesystem/pass error that is not recovered, or closure before delivery. The real-feed probe exercised both. A busy-store pass retries until delivery or closure; it need not fail at the first refusal. During shutdown a client may instead observe the daemon stopping or its socket disappearing before it polls the stored error. Stop does not poll that request error, so its existing result/deadline handling decides what the agent sees.
