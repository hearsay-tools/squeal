## Blockers

### B1. Proven: rollback publications are rejected as a predecessor's, hiding live waits

Changed sites: `src/core/scheduler/quiet.ts:104` and `promotions.ts:224`, reached through `scheduler.ts:1411`. Reader seam: `quiet.ts:310`, `promotions-row.ts:63`, and `src/core/status/standing.ts:131`.

The Design promises that status sees a quiet wait's end republished in the new calendar. `BacklogQuiet.shift` does publish that end, but also stamps the row with the rolled-back `at`. `publishedWaits` rejects any row whose `at < daemonStartedAt`. The stored daemon start did not move. `Promotions.shift` republishes through a fresh calendar reading and hits the same rule in `publishedBatches`.

Reproduction, with real public owners/readers:

1. Start a virtual clock at 10,000,000; initialize the stepped clock; retain that calendar reading as `daemonStartedAt`.
2. Wire `BacklogQuiet`'s publication to `publishQuiet`, and its step listener to `quiet.shift`. Start lane `a`'s 20s wait. `publishedWaits(..., daemonStartedAt, now).backlog.size` is 1.
3. `shiftCalendar(-3_600_000)` and read the stepped clock. The owner still waits, with 20s left. Its row is `{"at":6400000,"lanes":{"a":6420000}}`.
4. Read the same public status reader. Its backlog map is empty because 6,400,000 is before the stored daemon start.
5. Repeat with `Promotions`, wired to `publishPromotions`, and one queued file. The owner's rank remains 0, but `publishedBatches` returns no batch.

Actual probe output:

```text
quiet status {"before":1,"ownerStillWaiting":true,"after":0,
  "row":["{\"at\":6400000,\"lanes\":{\"a\":6420000}}"]}
promotion status {"before":1,"ownerRank":0,"after":0}
```

This happens whenever a rollback puts a publication before that daemon's start. It is not restricted to a change inside a scheduling step. For a daemon younger than 1h, a 1h rollback meets the condition. The wait's status reason or batch position disappears while the daemon still enforces it. The reader guard predates this range; the new shift publication now immediately crosses it. This breaks the row's published-fact seam and C15's wait explanations.

Fix scope for one worker: make the changed wait publications and their status freshness rule agree across a rollback, while still rejecting a predecessor's row. Do not remove the guard without an equivalent identity check. If this needs a stored/public contract change, route it through the coordinator before implementing it, as W1's seam requires. Add owner-to-public-reader tests for rollback with a real daemon-start value, for quiet and promotions, plus rejection of a genuine predecessor. The current tests inspect raw republished values and miss the reader.

### B2. Proven: a step between decision and wake conversion can hold a 60s wait for 3,660s

Changed mechanism: `src/core/scheduler/calendar-steps.ts:96` and `scheduler.ts:1422`; affected owner: `slow-release.ts:135`.

`SlowRelease.arm()` computes a calendar `wakeAt` in `#decide()`, then takes a second reading in `wakeAt - this.host.now()`. If that second reading detects a rollback, the new listener shifts `#endedAt`, but cannot shift the already-copied `wakeAt`. The wake loop receives a delay with the whole rollback added. Its elapsed timer then faithfully waits that long. No next scheduling turn is needed or guaranteed to repair this timer.

Reproduction with the real owner and wake loop:

1. Wrap a virtual clock with `steppedClock`; wire steps to `release.shift`.
2. Open one idle slow lane. Call `release.ended(lane)` with no earlier release timer armed.
3. Set the wrapper to roll back 1h on the third calendar read in that call: the first stamps the end, the second decides `wakeAt`, and the third subtracts now when arming.
4. Advance 60,000ms of elapsed time and await `wakes.rest()`: nothing releases. Its next wake is still 1h away.
5. Advance another 3,600,000ms: the lane finally releases.

```text
slow release at 60s {"released":[],
  "rest":{"next":{"reason":"slow-release","at":10060000},
          "wakes":[{"reason":"slow-release","at":10060000}]},
  "step":-3600000}
slow release at 3660s {"released":["slow:x"]}
```

The two-read arm predates this range. Row 011-377 explicitly takes ownership of making this idle bound count on elapsed time, and the new shift path does not close this case. The notes' known limit is therefore a user-visible residual defect, not merely one decision corrected a few milliseconds later. A runner instance can retain setup resources for the extra hour. A clock step must land between those reads; the window is small, but its frequency on real hosts was not measured.

Fix scope for one worker: derive the delay and the bound from one consistent reading/generation, or retain the delay on elapsed time. Inspect the other changed owners' conversions too: `scheduler.ts:#eventOrAt` and `TierYields.#arm` also copy a calendar end before a reading can re-anchor its owner. Those two are **plausible related cases**, not additional proven blockers. Add the discriminating clock wrapper above, in both directions. An ordinary step after the wait was armed does not test this seam. Keep row 011-372's one decision reading.

## Should-fix

### S1. Proven: a pause between the two samples is detected as a calendar step

`src/core/scheduler/calendar-steps.ts:96`. The notes bound reading jitter by Date's millisecond resolution. The pair is not atomic: the host can deschedule the thread or pause it between `clock.now()` and `clock.elapsed()`.

The probe initialized the wrapper, then made `elapsed()` advance the virtual clock's calendar and elapsed sides together by 200ms before returning, once. It never called `shiftCalendar`. Two successive `now()` calls reported:

```text
sampling pause with no calendar change {"told":[-200,200]}
```

This proves that ordinary time passing between samples can cause false step notifications and publication writes. It contradicts R1 check 2's claim that jitter never reads as a step. The 100ms threshold is a portable policy choice rather than a host measurement, and its notes explain the intended Linux/NTP model. They do not bound sampling latency. NTP configurations and non-Linux clock-rate behavior were not independently tested.

Nonblocking: the probe proves false detection, not a separate lasting scheduling failure or its rate on real hosts. A fix should reject an uncertain pair, for example by bracketing the calendar sample with elapsed readings and checking the pair's width. Add a delayed-sample test; do not solve this by tuning the threshold to this host. Document the limits of the NTP assumptions.
