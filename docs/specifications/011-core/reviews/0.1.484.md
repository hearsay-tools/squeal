## Nonblocking note

### N1, proven: clock calls are not literally unchanged

Locations: `src/cli/wait/wait.ts:224`, `:271`, `:278`; `src/cli/wait/named.ts:73`; `src/cli/wait/presence.ts:29`. Worker notes decisions 5 and 6 disclose both changes.

The base read the monotonic clock once for `final`, then again for the busy-timeout remainder. `readBound` now uses one reading for both. A deadline crossed between the old two calls could use a slightly smaller remainder; with a long process deschedule between them, the difference need not be nanoseconds. The final-read classification still uses the first reading, as before. No different outcome was reproduced, and the full deadline busy-read tests pass.

The named wait also constructs its wall-clock deadline before `pollStatus` starts the monotonic clock. The base started the monotonic clock first. This can shift measured duration and the relative promotion lifetime by setup time. It adds no store or socket read, changes no priority, and supplies no proven break of the wait's goal. Treat strict clock-order equivalence as qualified, as review 0.1.469 did for its clock-only differences. If exact ordering later becomes required, restore those two reads and construct the deadline after the monotonic start in one focused timing change.
