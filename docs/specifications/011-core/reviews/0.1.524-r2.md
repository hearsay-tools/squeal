## Prior findings and what fits

### B1: closed, proven for the public publication/read seam

`src/core/scheduler/calendar-steps.ts:111`, `scheduler.ts:169`, `scheduler.ts:1437`, and `ledger.ts:200` implement the agreed publication rule. Quiet and promotions use `max(reading, this daemon's stored start)`. The scheduler accepts a daemon record only when `daemonIncarnation(record)` matches `SchedulerOptions.incarnation`, then caches that start. A mismatching successor record cannot supply its start to a predecessor. The production daemon passes the same incarnation derived from its registration.

The five B1 cases in `calendar-steps-seams.test.ts` pass. They use real stores with daemon records, real wait owners, and the public `publishedWaits`/`publishedBatches` readers. Both rows remain visible while their owners enforce the wait, across a 1 h set-back and set-forward. The predecessor case writes after the successor started, following a rollback; its own earlier start remains below the reader's guard and both rows are rejected.

No row shape or reader changed. The publication's `at` is deliberately clamped after a rollback; the published ends stay in the new calendar. Without a step it retains the ordinary reading.

Coverage limit, **unverified by a dedicated integration test**: these owner-to-reader cases inject the start callback directly. The scheduler's incarnation lookup and cache are verified by source inspection, rather than an end-to-end test that changes daemon records while that scheduler runs. No failure was found there.
