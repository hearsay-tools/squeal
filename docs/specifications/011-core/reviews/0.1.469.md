## Nonblocking notes

### N1, proven: the clock is read on early-return branches

At `src/cli/wait/table.ts:179` and `:210`, `late` is in the initial reads. `wait.ts:74` reads all those fields before deciding. The old checkpoint poll returned moved or abandoned before calling `Date.now()`. The old lint loop returned off or unread before calling it. Store reads and outcome priority are unchanged, and the extra clock value cannot affect those winning branches. This is not the expensive eager-read problem of review 0.1.403 B2 and does not block the row's behavior goal.

The notes' claim that all initial fields were always read before is too broad. One small docs correction can name these four cheap clock exceptions. If exact clock-call parity is required later, stage `late` after those early outcomes while keeping it before the old hold/verdict reads.

### N2, proven: no permanent unbounded late-socket loop row

The notes explicitly defer this row in decision 8. `request-loop.test.ts` covers bounded unanswered sockets, but not an `ask` throwing for the unbounded run-all/run-slow rows. `run-loop.test.ts` likewise lacks a throwing checkpoint ping. Source still calls the same uncaught socket operation; the temporary probe confirmed the request-loop throws. There is no proven behavior break.

For 011-327, add deterministic port tests for a throwing request and a throwing checkpoint ping before changing the socket cell. Then change those expectations to the new deadline/busy outcome. This can be one focused test step with that row; a real 2 s sleep is unnecessary.

### Complexity 27 in `holds`: no action needed for this row

`src/cli/wait/decide.ts:72` is a flat switch over the typed condition vocabulary. Each arm is a short predicate. Rule order and read sequencing remain in the table and evaluator, not hidden in nested branches. Splitting this switch to satisfy the numeric threshold would not remove a decision or improve this review's evidence. No blocker or should-fix from the complexity count.
