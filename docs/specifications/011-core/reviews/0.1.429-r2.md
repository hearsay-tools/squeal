## B1 closure and what fits

`src/harness/shared/stop-required.ts:145` now returns an open-check hold
only when checks are open **and** the daemon is not stopped by request.
A stopped daemon falls through to `failingLines` even with another open
check. Thus a current required failure retains its hold. A stopped daemon
with no failure still holds nothing for the open checks.

The new tests exercise the quick entry through both real hook adapters
and the waiting entry after an explicit turn handoff. Each entry and
harness has a pending-check case and a no-pending control. They assert
the existing `lint.blocking` reason and a counted hold. The quick-entry
cases also assert no later hold after the budget is spent. Their passing
candidate results and four failures under the old conditional show that
they detect B1 rather than only exercise the path.

For a live or crashed daemon, `stoppedByRequest` remains false. With an
open check the old and new conditionals both return the same `open` step
before reading failures. With none open both reach the same failure
decision. The no-edit early return, transaction boundary, failure rules
and hold budget are unchanged. Existing mixed-group and crashed-daemon
cases have current passing results.

The restricted delta has one production conditional, its comment, the
regression tests, eight shipped copies of that same conditional, and four
changed Codex manifest hashes. No other production behavior changed in
`src`, `test` or `plugins`. Registration storage, Git reads, keys and
scheduling are unchanged from R1.

### Commit-boundary report: plausible timing failure, no causal change found

The parent reported a FAIL then PASS 9 s later at the same key for
`test/commit/boundary-daemon.test.ts:85`, with load 53 on 24 CPUs, in a
worktree whose product matches this candidate. That history and load are
parent-reported evidence. This worktree now has a current passing result
for the file, as recorded above.

The assertion requires the daemon's commit report immediately after a
tool boundary. `src/core/commit/boundary.ts:19` caps the boundary's sync
wait at 500 ms; `syncOnHeadMove` returns when that deadline expires even
if the report is not stored. A late pass under load can therefore produce
the reported `seen === undefined`. This timing explanation is
**plausible**, not proven by a reproduction.

The new `registrationHead` read runs inside `register` only when the
consumer was not registered. This test registers at SessionStart, then
edits and commits before the failing PostToolBatch. Its `deliver` path
uses the already-registered branch and never calls that read there. The
extra field writes only registration metadata; it does not change the
revision commit or commit-report `seen` that `headMovedSinceLook` reads.
Those paths are unchanged, and the B1 repair is Stop-only. I found no
causal path from this row's change to the missing report. The transient
observation does not establish a new wave defect. If it recurs, inspect
whether the 500 ms deadline passed before the daemon stored the report.
