## Blockers

### B1. Proven: the eligibility check and the request write are separate transactions

`src/cli/status-wait-ask.ts:160` calls `askNamedRun` with the file and key selected by an earlier read. The write transaction at `src/core/retry/records.ts:184` checks retry records only. It does not read the file's current key, class, pending state or another worktree's claim again.

C15's 011-207 amendment says the file "has nothing queued, has no claim of its key by another worktree" and "the check and the write are one transaction". The isolated SQLite probe reads an eligible unknown file, then commits a live other-worktree claim of that key before calling the exact write function. `claimantOf` now finds the claim, and `askableFiles` would refuse the file, but `askNamedRun` returns `queued` and stores the request. The CLI has no intervening eligibility check. A file can likewise become queued, current or re-keyed between its decided read and this write. The new request can force work that the exception did not authorize. The existing claim test installs its claim before the first read and misses this order.

One-worker fix: decide eligibility and insert under the same `BEGIN IMMEDIATE`, including on each busy retry. Recheck that the row is still at the requested key, stale or unknown, unqueued and unclaimed before creating a request. Return a distinct no-write answer when that no longer holds. Preserve the pending/ended/cancelled record guards. Add deterministic cases that commit a claim, queue, current result or new key after the first read and before the write; none may store or report a new ask. Keep source-path selections, `--check` waits and unnamed files outside this path.

### B2. Proven: the one-run guard disappears when the retry history is trimmed

`src/core/retry/records.ts:185` makes the new never-asked decision from `readRetries` alone. `writeRetries` keeps only the latest `RETRIES_KEPT` requests, 1,024. That bounded operational history cannot prove that no request was ever stored at a key.

C15 says "no request ever stored at its key, pending, ended or cancelled"; row 011-207 requires that a second wait at the same key asks no second run. The probe asks the file once, ends it with `unknown`, then stores 1,024 requests at other keys. Its first record is gone. Asking the original file/key again returns `queued` and writes a second request. The file need not change key or gain a result in this sequence. The retained-history pending, ended and cancelled cases do pass. A single command naming more than 1,024 askable files can also evict its first still-pending requests before it tells the daemon. `askedEnds` then assumes a missing record ended (`src/cli/status-wait-ask.ts:181`), although eviction proves no such end.

The 1,024 limit predates this range. The break introduced here is using that lossy history as the new permanent one-run guard and as proof that this wait's request ended.

One-worker fix: keep the fact that a file/key was asked independently of the capped request history, transactionally with each relevant ask. Keep unresolved requests available until they actually end. Do not infer completion from absence in a trimmed log. Test an ended and a cancelled request after enough later requests to pass the retention limit, plus an unresolved request crossing that limit. These tests must keep the same key and must not rely on a current result suppressing the second wait.

### B3. Proven: busy refusals are reported as asked runs in both JSON fields

`src/cli/status-wait-ask.ts:96` makes `waitAsked` present for `answer: "busy"` and retains that entry. `askedPayload` at line 81 removes the answer, so the JSON cannot distinguish a refused write from an asked run that is no longer pending.

C15 requires `asked` to contain "one ... per file the wait asked" and to be "present only when it asked". The full CLI probe has one stale/unknown file and an ask boundary that returns the real busy-refusal shape. No request exists. The text correctly says `Run not asked`, and the command exits 3. Both `selection.asked` and `wait.asked` nevertheless say:

```json
[{ "project": "", "path": "test/a.test.ts", "pending": false }]
```

The committed busy test at `test/cli/status-wait-ask.test.ts:266` explicitly expects this contradiction. A machine sees a requested run where none was stored. This breaks the vision's requirement to report recorded facts and the amendment's explicit field contract.

One-worker fix: keep refusal data for `Run not asked`, but serialize `asked` only for requests actually asked under the agreed contract. Omit the field when every write was refused. In a mixed success/busy case, include only actual asks and keep both text lines. Update both JSON alias assertions without changing `schemaVersion` or the central result/reason/exit decision.

### B4. Proven: shutdown can finish while the timer's slow-instance teardown is still running

`src/core/scheduler/slow-release.ts:84` starts the due close with `void this.#due()`. `close()` at line 91 clears only a future timer. It does not await a close that already started. That new detached path meets `withSlowInstance`'s existing `drop` (`src/core/daemon/slow-instance.ts:34`): `drop` clears `slow` before awaiting the saved `closing` promise. A later `runner.close()` sees `slow === null`, gets an already-resolved promise from `drop`, and waits only for the fast instance.

The probe opens a fake slow instance, fires the candidate's actual `SlowRelease` timer and holds the slow instance's `close()` at a teardown gate. It then calls `SlowRelease.close()` and `runner.close()` in shutdown order. `runner.close()` resolves while the slow teardown is still blocked. Releasing the gate completes it afterward. The daemon's real shutdown calls scheduler close and then runner close before child cleanup, scratch removal and store/socket closure (`src/core/daemon/daemon.ts:939`). No intervening wrapper waits for the detached release.

This violates the requested no-leaked-instance shutdown check and C9's shutdown order: the awaited runner close must complete the project's teardown before the daemon tears down its environment. The old drain-only release ran inside the tier's awaited `flight.done`; the new timer makes this race reachable outside the pump. This is a new seam failure, not a request to repair unrelated old code.

One-worker fix: ensure shutdown awaits any slow close already in progress, even after `slow` was cleared. For example, make the runner's close include its saved `closing` promise, or track and await releases in the scheduler. Keep the no-close-during-selection and no-close-during-run guards. Add a gated teardown test: timer release begins, shutdown starts and must stay pending, then the gate opens and shutdown completes with exactly one teardown.
