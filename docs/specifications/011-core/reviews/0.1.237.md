## Blockers

### B1. A forced run can yield repeatedly at the same file and key

**Proven.** `src/core/scheduler/yields.ts:100`, especially line 103. C4 step 5: “A file that a yield cut is marked until its result lands or its key moves, and a tier holding a marked file does not yield.”

`queueFullSuite` queues a forced run without clearing an existing `FileState.resultKey` (`checkpoint-requests.ts:78`). After that run yields, `#forget` treats that pre-existing result as a result that just landed. It deletes the mark at the next check. No new run needs to finish. The next promotion can therefore cancel the same file at the same key again. A stream of named waits can repeat this and prevent a forced checkpoint from completing. A forced rerun is not a supersession exception.

I reproduced it through the real scheduler, store and pool in a scratch candidate tree. The existing `catchUpSide` fake runner supplied fixed durations and a held run. A 120 s known failing file ran first in `run --all --force`; two 1 ms files stayed queued. Promoting the first short file cut the held file. After the short file stored, the held file ran again. Promoting the second short file cut it a second time. Its key never moved and its new result had not landed.

```text
$ node node_modules/vitest/vitest.mjs run test/scheduler/review-fairness.test.ts --maxWorkers=1
{"firstCancelled":true,"againCancelled":true,"oldResultWasCurrent":true}
AssertionError: expected true to be false
 Test Files  1 failed (1)
      Tests  1 failed (1)
   Duration  4.21s
[exit 1, expected regression failure]
```

A direct decision probe gave the same result. With `resultKey: null` as a control, the first tier cancelled and the second did not. With `resultKey === key` already set before the first cut, both cancelled.

**One-worker fix:** clear a mark on evidence that a result was accepted after the cut, or on a key move. Equality with an old `resultKey` is insufficient. Keep the mark through an incomplete forced rerun. Add the scheduler regression above, plus checks that an actual accepted result and a key move each release the mark. Preserve forced checkpoint attribution and the current result while the forced run is pending.

### B2. Completed files prevent the required supersession cancel

**Proven.** `src/core/scheduler/yields.ts:128`, with the stated approximation at lines 49–50; `remainder` at line 177 uses the same whole-tier set. C4 step 5: “Any fast tier in flight in a lane whose runner cancels (Vitest) is cancelled by a revision that changes an input of every file of it whose module has not ended.” The first rule has no 30 s threshold, fairness-mark restriction or backlog-turn exception.

`superseded` tests every selected file. Once A has completed, a revision that re-keys every unfinished file B still fails the predicate if A's input did not change. The fallback yield cannot replace the first rule: it refuses a remainder at or below 30 s, a marked tier and the backlog's turn. The unfinished files then keep running results that the stability check will discard.

The scratch scheduler probe ran two files with 20 s known durations. A finished at once; B remained in flight for 60 s. A revision edited only B's test file. The tier did not cancel. An explicit stop then returned exactly A in `completedFiles`, confirming the finished/unfinished split. The low known duration intentionally excluded the threshold-based fallback.

The current runner interface exposes completion only with its final report. That explains worker decision 1, but does not implement the amended rule. It also means the remainder and new marks include completed files, contrary to the unfinished-file wording.

**One-worker fix:** expose module completion to the scheduler for this decision, and use the unfinished set for supersession, the remainder and new cut marks. Keep result storage behind the existing completion barrier and stability checks. Add the completed-A/re-keyed-B regression with a short remainder, a marked rerun and the backlog's turn. If the coordinator wants the conservative whole-tier rule instead, obtain the human's spec amendment before accepting this deviation.

## Should-fix

### S1. Some new tests still depend on short wall-clock windows

**Plausible, nonblocking.** `test/scheduler/tier-yields-fixture.ts:44` uses `expect.poll` without a timeout, so a held tier must start within Vitest's default 1 s. This helper is used by tests 1–6 and 8. The 120 s test timeout and 30 s cancel poll do not extend it. The text test also accepts only a 10–20 s reported remainder from an initial 20 s duration (`tier-yields-text.test.ts:88`); a scheduler delay over about 10 s can fail the assertion although the correct branch is still “does not yield.”

These are unnecessary load risks on the shared host. Use the explicit long poll budget and an injected clock or a range bounded by the rule, rather than a narrow positive remainder. No failure from these windows was established by the source inspection alone. The 1.5 s negative-case pause follows an awaited revision/promotion whose abort decision is synchronous under the scheduler lock; it does not hide an async cancel decision in the candidate. The real Vitest case uses explicit 60 s polls and a 120 s held-test deadline. It depends on marker ordering, not a sub-second performance target.

## What fits: contracts and blast radius

- **Cancel no longer means backlog.** `startTier` sets `kind` for every production tier. `busyLanes` now identifies backlog tiers by `kind`, so a cancellable Vitest edit tier still occupies its lane. node:test/pytest slots retain `kind: "backlog"`, a cancel handle and `slot: true`; their adapters still ignore the per-tier cancel and respond to the shared stop. Their edits have no per-tier cancel. The special turn slot retains the old backlog-slot behavior. `#editPending` tests `kind !== "backlog"`, so an edit tier and Vitest backlog turn still block the slow lane. The optional fields serve only the validity harness's old tier literal.
- **Completion and claims.** `executeTier` combines the per-tier signal with the unchanged shared stop signal. `storeDecision` already distinguishes incomplete cancelled files from completed ones. Only incomplete files requeue uncounted; completed files still pass through the same touch barrier, run-end reads, observed-input handling and stability predicate. `ledger.setRunning` and the queued/current commit release incomplete claims. Superseded keys still cannot overwrite newer running/current results. Promotion does not bypass another worktree's claim. A claim-blocked promotion can waste one cut; the ordinary bound limits that cost, subject to B1.
- **Classes.** The requeue preserves `forced`, `recent` and `catchUp`. Promotions remain in `Promotions` while a selected file is running or queued and before the wait deadline. Recomputing the within-group priority does not move a recent/catch-up/promoted file out of its specified class.
- **Stop and step-down.** Both still abort `#stop`, including a close already in progress. That signal reaches slow tiers and non-cancelling runners as before. The daemon still applies its stop grace and child sweep. No stop path infers backlog from `tier.cancel`. A normal departure still lets the run store.
- **Published yields.** The row is keyed by worktree, then run id. Status ignores it without a live daemon, before that daemon's start, or without its matching open run. `ended` deletes the tier on normal record and error requeue and removes the row when empty. The registry entry in `WORKTREE_META_ROWS` gives existing worktree removal/prune its exact prefix. No suffix-based removal or schema migration was added. An older daemon publishes no row, so the old wording remains. The stored remainder is explicitly worded as what it “was,” rather than a live countdown.
- **Release.** All eight release paths carry 0.1.237: package, lockfile, installer, Claude manifest and package, Codex manifest, Pi package and OpenCode package. Rebuilding all four plugin trees left no tracked drift. `KEY_FORMAT_VERSION` remains 20. The independent `test/keys/key-format.test.ts` guard passed. No key-format raise is needed for this candidate.

## The reported slow-slot-fair failure

The supplied coordinator evidence places the same teardown timeout before this row, on 0.1.236 at `61a80133`, and reports three isolated passes on this candidate. I treat that history as supplied evidence, separate from my independent result above.

The candidate's `slots.ts` change preserves the slow lane's behavior: a slow tier previously had `cancel: null` and was treated as an edit for lane occupancy; it now has `kind: "slow"` and is still treated that way. `slow-tier.ts` changes its `startTier` argument from `false` to `"slow"`; that still creates no per-tier cancel and no backlog slot. This fixture marks every file slow, so there is no new cancellable fast tier. `TierYields` skips its slow tier. Neither edit changes `slowSlotHeld`, its wait ownership, the load guard, slot handover or fixture cleanup. The timeout at `claims-fixture.ts:249` waits for `scheduler.close`; a delayed old slow pump can remain alive and increment the module-wide `probes.count` during a later test. The diff gives no changed state transition that causes that delay. Added bookkeeping can affect timing under load, but the supplied prior failure rules out attributing the symptom to this row from timing alone.
