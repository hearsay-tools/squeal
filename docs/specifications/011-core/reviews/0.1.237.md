## Blockers

### B1. A forced run can yield repeatedly at the same file and key

**Proven.** `src/core/scheduler/yields.ts:100`, especially line 103. C4 step 5: “A file that a yield cut is marked until its result lands or its key moves, and a tier holding a marked file does not yield.”

`queueFullSuite` queues a forced run without clearing an existing `FileState.resultKey` (`checkpoint-requests.ts:78`). After that run yields, `#forget` treats that pre-existing result as a result that just landed. It deletes the mark at the next check. No new run needs to finish. The next promotion can therefore cancel the same file at the same key again. A stream of named waits can repeat this and prevent a forced checkpoint from completing. A forced rerun is not a supersession exception.

I reproduced it through the real scheduler, store and pool in a scratch candidate tree. The existing `catchUpSide` fake runner supplied fixed durations and a held run. A 120 s known failing file ran first in `run --all --force`; two 1 ms files stayed queued. Promoting the first short file cut the held file. After the short file stored, the held file ran again. Promoting the second short file cut it a second time. Its key never moved and its new result had not landed.

A direct decision probe gave the same result. With `resultKey: null` as a control, the first tier cancelled and the second did not. With `resultKey === key` already set before the first cut, both cancelled.

**One-worker fix:** clear a mark on evidence that a result was accepted after the cut, or on a key move. Equality with an old `resultKey` is insufficient. Keep the mark through an incomplete forced rerun. Add the scheduler regression above, plus checks that an actual accepted result and a key move each release the mark. Preserve forced checkpoint attribution and the current result while the forced run is pending.

### B2. Completed files prevent the required supersession cancel

**Proven.** `src/core/scheduler/yields.ts:128`, with the stated approximation at lines 49–50; `remainder` at line 177 uses the same whole-tier set. C4 step 5: “Any fast tier in flight in a lane whose runner cancels (Vitest) is cancelled by a revision that changes an input of every file of it whose module has not ended.” The first rule has no 30 s threshold, fairness-mark restriction or backlog-turn exception.

`superseded` tests every selected file. Once A has completed, a revision that re-keys every unfinished file B still fails the predicate if A's input did not change. The fallback yield cannot replace the first rule: it refuses a remainder at or below 30 s, a marked tier and the backlog's turn. The unfinished files then keep running results that the stability check will discard.

The scratch scheduler probe ran two files with 20 s known durations. A finished at once; B remained in flight for 60 s. A revision edited only B's test file. The tier did not cancel. An explicit stop then returned exactly A in `completedFiles`, confirming the finished/unfinished split. The low known duration intentionally excluded the threshold-based fallback.

Their edits have no per-tier cancel. The special turn slot retains the old backlog-slot behavior. `#editPending` tests `kind !== "backlog"`, so an edit tier and Vitest backlog turn still block the slow lane. The optional fields serve only the validity harness's old tier literal.
- **Completion and claims.** `executeTier` combines the per-tier signal with the unchanged shared stop signal. `storeDecision` already distinguishes incomplete cancelled files from completed ones. Only incomplete files requeue uncounted; completed files still pass through the same touch barrier, run-end reads, observed-input handling and stability predicate. `ledger.setRunning` and the queued/current commit release incomplete claims. Superseded keys still cannot overwrite newer running/current results. Promotion does not bypass another worktree's claim. A claim-blocked promotion can waste one cut; the ordinary bound limits that cost, subject to B1.

- **Published yields.** The row is keyed by worktree, then run id. The registry entry in `WORKTREE_META_ROWS` gives existing worktree removal/prune its exact prefix. No suffix-based removal or schema migration was added.
