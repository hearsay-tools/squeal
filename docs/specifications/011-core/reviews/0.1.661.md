## Blocker B1: a failed claim can be mistaken for another hook's claim

**Proven under an injected write rollback.** `src/harness/shared/ensure.ts:194-208`, particularly the recovery at line 207 and the identity check at line 227.

Contract: spec 011 C9 requires **one successor per handoff**, and says a hook spawns only when the claim is its own. Row 011-434 must preserve that rule when the write throws. The new read-back compares only the old incarnation, destination version and millisecond timestamp. Those fields are not a unique hook identity.

The probe used the existing `stepping`, `recording` and `squealRepo` helpers from `test/harness/handoff.test.ts`, two real store contexts, and a fixed `now()` value of `1_800_000_000_000`. It forced this order:

1. Hook B reads no claim and asks the old daemon to step down.
2. B's write callback runs inside an enclosing real store transaction. The real `claimHandoff` attempts B's claim. The probe throws before the enclosing transaction commits, so B's claim rolls back.
3. Before B's asynchronous write rejects to `handOver`, the wrapper verifies no claim is stored, then lets hook A call the real `ensure`. A stores its claim and starts one lock-waiting successor. Both hooks use the same version and clock value.
4. B's context wrapper rethrows the write failure.
5. B's catch finds A's matching `from`, `to` and `at`, returns `claimed`, and starts a second lock-waiting successor.

The decisive wrapper and assertion were:

```ts
write: async <T>(work: () => T | Promise<T>): Promise<T> => {
  try {
    await second.write(() => second.store.transaction(() => {
      expect(work()).not.toBeNull();
      throw failure; // Roll back B's actual attempted claim.
    }));
  } catch (error) {
    if (error !== failure) throw error;
    expect(readHandoff(r.store, r.worktreeId)).toBeNull();
    expect(await ensure(location, deps, first)).toBe("spawned");
    throw error;
  }
  throw new Error("rollback did not run");
}
// After ensure(location, deps, wrappedSecond):
expect(successors()).toHaveLength(1); // Actual: 2.
```

This proves the recovery's ownership error at the public `ensure` boundary with an injected failure and rollback. It does not claim an observed real daemon/network occurrence or measure its frequency. The existing lost-ack test covers only a hook whose own claim remains stored, so it misses this branch. The initial joined-result probe alone was weaker: a read-only join sends no claim-write acknowledgement to lose. The rollback variant removes that ambiguity.

**Repair scope:** one worker in `src/harness/shared/ensure.ts` and `test/harness/handoff.test.ts`, plus the claim's stored contract and its writers if a unique attempt token is used. For an uncertain write result, require evidence that identifies this hook's claim attempt, or decline ownership. Preserving a known joined result alone does not fix the rolled-back-write case. Add the forced order above as a regression, and keep the own-claim/lost-ack and busy-store cases passing. Amend C9 if the stored identity or recovery rule changes; rebuild bundles in the coordinator's version commit.

## What fits

- Row 011-433 retries an early empty wait at most three times after its first attempt. The remaining count is passed into each retry; a new idle/settle starts its own budget. A successful answer does not retry.
- Pi and OpenCode compare the completed wait with the current wait before acting. A cancelled old answer cannot schedule a retry or deliver into the replacement wait. Cancellation during the pause clears its timer. Shutdown/stop and session removal use the same cancellation path.
- Both retry pauses use unreferenced timers. Pi's worker and OpenCode's background bridge already have separate process-lifetime rules. The new pause introduces no referenced timer.
- A wait that lasts `WAIT_BOUND_MS` does not retry. Tests pin both copied bounds to their worker/bridge `IDLE_WAIT_MS`. The 008 and 009 D5 amendments match the retry count, pause, cancellation and expiry behavior.
