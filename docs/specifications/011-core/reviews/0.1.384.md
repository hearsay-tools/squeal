## Blocker

### B1. Proven: an already-current file keeps a completed wait's priority alive

Locations: `src/core/scheduler/promotions.ts:107` and `:227`; caller `src/core/scheduler/scheduler.ts:664`.

Wave 62 W1 rule 3 says: **"A group lasts until each file has a current result at its key, its key moved, or it left the queue."** Rule 4 requires that nothing else about order changes. The worker also explicitly preserves early settlement: once each selected file had its turn and settled, the wait ends. C15's existing current-file exclusion is not replaced by the new delayed-queue rule.

`seen` starts with only queued or running files. An already-current selected file is therefore indistinguishable from a file still waiting to be queued. `#settle` keeps the whole wait while any selected id is unseen. The CLI sends all own-path selections, including current files (`status-wait-paths.ts:387`); the scheduler forwards them without a current-state filter. After the other files settle, the current file keeps the old wait alive until its deadline. A later edit can rejoin that finished wait.

Reproduction with the real scheduler, store and private pool:

1. Start four fast files A, B, C and X, each importing its own source. Use last-known durations of 10 ms, four host slots and a `run-missing` baseline. Wait until all are current.
2. Edit B's source and hold B's run. Promote `[A, B]` for 600,000 ms, as a named wait over current A and pending B does.
3. Release B and wait for idle. Assert that both A and B are current. The named wait has its answer. The promotions row nevertheless retains `[A, B]` with an empty `batch.files`.
4. Edit X's source and hold X's short run so the lane stays busy without a yield. Edit B's and C's sources. Promote only C for 600,000 ms. Release X and drain the scheduler.
5. Repeat with the first wait naming only B. This control changes nothing else.

Actual output from the paired probe:

```text
first wait [B]:
  after B settles: promotions row = null
  later runs: [["test/c.test.ts"], ["test/b.test.ts"]]
  assertion that C goes first: PASS

first wait [A, B], with A already current:
  after B settles: promotions = [{ files: [A, B], batch: { files: [] } }]
  later runs: [["test/b.test.ts"], ["test/c.test.ts"]]
  assertion that C goes first: FAIL
```

This is a scheduling change after a completed wait, not merely unused row retention. The current A lets the old group overtake the new C group. It is not the accepted memberless-takeover limit: no handover occurs.

**One-worker repair:** give `Promotions` enough lifecycle facts to distinguish a selected file still awaiting its first queue entry from a file already current or otherwise settled. End the group once all selected files have settled. Preserve the earlier place for an actually pending, unqueued retry until its deadline. Keep this decision in `Promotions`; do not restore the CLI re-send or add another ordering mechanism. Cover both an initially current file beside a queued file and a selected unqueued file that becomes current through a shared result. Repeat the paired next-wait ordering assertion. Do not change retry priority, slow eligibility, tier selection, keys or verdicts.

The added `named-wait-late.test.ts` early-settlement test includes only a file that was queued. It cannot distinguish the current A case from an unqueued retry. Extend that coverage through the scheduler, where current-at-key state is known.
