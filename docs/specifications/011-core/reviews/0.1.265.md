## Blockers

### B1: replacement order is used as failure-time order

**Proven, blocking.** Locations: `src/core/status/replaced-failures.ts:95` and `src/core/status/why.ts:264`.

C6 says: “`--per-check` lists each selected check once, at its newest selected failure”. R3 test 2 requires the retained flips “all kept, newest first”. The formatter also labels the `why` block “newest first”.

`keepReplaced` appends when the passing replacement arrives. That order need not match the failing run's `recordedAt`: worktrees can retry different keys of the same check in either order. `selectReplaced` reverses insertion order and deduplicates before `mergeFailures` sorts. The newest failing entry can therefore be discarded before that sort. `replacedOf` uses the same reverse without a sort.

**Reproduction:** seed one check failing at k1/time 100/run `old-fail` and k2/time 200/run `recent-fail`. Replace k2 with a pass at 300, then k1 with a pass at 400, using `failingAt` before `results.putMany` and `keepReplaced` afterward in each transaction. Read both failure modes and `why` with the exact printed check name.

```text
all failures: ["recent-fail", "old-fail"]
--per-check: ["old-fail"]
why.replacedFailures: ["old-fail", "recent-fail"]
expected --per-check: ["recent-fail"]
```

This is a wrong result under a supported selection, not only a display order issue. If a stored failure's time lies between 100 and 200, the same early deduplication can select that stored failure and miscount how many selected checks are replaced.

**One-worker fix:** order selected retained entries by the failing provenance's `recordedAt` before per-check deduplication. Use the same ordering for `why`. Define a stable tie rule. Add the reverse-completion test to `failures-replaced.test.ts` and `why` coverage, including a stored failure between the two retained ones. Keep the 4/1,024 retention caps and keyed-result semantics.

### B2: prune leaves a retained failure that `why` cannot resolve

**Proven, blocking.** Location: `src/core/status/why.ts:258`, the new `replacedOf` path, whose entry guards at lines 76 to 95 still require an old source of check identity.

C6 says that `why` lists “the check's replaced failures with their runs and logs”. C7 keeps their failure text, run and log until expiry. W1 explicitly keeps an entry after its worktree is removed. The new history source is omitted from both exact-name recognition and partial-name candidates.

**Reproduction:** register main and linked worktree B in a real temporary store. A check that main has never observed fails in B. A pass in B replaces it and `keepReplaced` retains the failure. Remove B's `.git` entry and prune one second later, well before the seven-day cutoff. Prune correctly removes B and the last result row; the retained entry remains. From main, read `failures --all-worktrees`, then `why` using `formatCheck` of exactly the listed check.

```text
failures.total: 1
results.listForCheck(check, 20).length: 0
why.found: false
expected why.found: true, with the kept failure
```

`known` checks only this worktree's state, its transitions and stored results. `resolve` checks only this worktree's states and held failures. Neither can reach the retained entry. The failure list's instruction to use `why` therefore leads to no match while the promised evidence is still kept.

**One-worker fix:** include retained failures in exact check recognition and in the intended candidate resolution. Match through the existing check identity and printed-name rules. Keep partial candidates bounded and distinct. Add a removed-worktree/prune test that checks exact and partial lookup, log and stack, without a state or result in main. Do not change result storage or protect unrelated result rows just to make lookup work.

### B3: the UNKNOWN cap evicts a still-standing state's run and invents its writer

**Proven, blocking.** Locations: `src/core/store/repos/unknown-runs.ts:57`, `src/core/status/why-unknown.ts:47`, and `src/core/store/prune.ts:108`.

C7 states: “While that UNKNOWN stands, prune keeps the run and its run log, past the cutoff too.” C6 names an older daemon only when it recorded the UNKNOWN without its run. Vision principle 2 requires truthful provenance.

`recordUnknownRuns` truncates all worktrees' records to the last 1,024 files without testing whether evicted records still stand. Unlike replaced-failure history, C7 provides no expiry or cap exception for a standing UNKNOWN. One crashed tier can produce hundreds of file records; several worktrees share this cap. Fallen records also consume it until prune, so even 1,025 simultaneous UNKNOWNs are not necessary.

**Reproduction:** register a live worktree. Start and finish `unknown-run` as crashed, eight days before now, with a check's known state UNKNOWN at revision 7 and summary `worker died`. Record that file's run through `recordUnknownRuns`. Add 1,024 other file records afterward (the probe also seeded their UNKNOWN states). Prune with seven-day retention. The original state remains UNKNOWN at revision 7.

```text
knownState.outcome: "unknown"
unknownRun: { runId: null, revision: 7, error: "worker died", missing: "older-daemon", ... }
store.runs.get("unknown-run"): null
expected: the standing UNKNOWN still names unknown-run, and prune keeps it
```

The writing daemon is this candidate, not an older release. A read is already false as soon as the cap removes the record; the next prune then loses the run. W1's note that the cap can read as `older-daemon` records this limitation but does not amend the unconditional C6/C7 contract.

**One-worker fix:** retain provenance for every standing UNKNOWN until the state changes. Drop fallen records before considering any bound; do not silently evict a standing one. Keep this separate from keyed results and from the replaced-failure cap. Test more than 1,024 file records across worktrees and the first prune past retention. Also cover a large set of recovered records followed by one new UNKNOWN. A record written by this release must not be labelled an older daemon's.
