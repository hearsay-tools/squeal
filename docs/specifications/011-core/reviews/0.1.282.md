## Blockers

### B1 (proven): An unknown top-level importer layout silently removes every bare import from the key

**Location:** `src/core/keys/pnpm-lockfile.ts:70` to `:79`, especially `:77`; consumed by `PnpmGraph.#fromImporters` at `src/core/keys/pnpm-graph.ts:135`.

**Contract:** 011 C11: “any line the reader does not know keep[s] the whole fingerprint.” Design 1.4: “a line it does not know ... returns nothing ... a split, never a wrong key.” Row 011-165 requires the unknown-line reader case. The review brief also requires no reuse across a pnpm bump that changes a package loaded in the test's own thread.

At a top-level pair with a nonempty value, the reader clears `section` and continues. It does this for `importers` too. Thus this valid YAML layout, which the line reader does not implement, returns a graph with an empty `importers` map rather than `null`:

```yaml
importers: {'.': {dependencies: {vitest: {specifier: '^4.0.0', version: '4.0.0'}, a: {specifier: '^1.0.0', version: '1.0.0'}}}}
```

The snapshots and integrities still read normally. All snapshot folders exist. The trust check sees no importers to inspect and calls the install trusted. Bare `require('a')` is keyed as absent, as is the environment's bare `vitest`. A bump of `a` then changes the real load and the whole fingerprint but leaves both scoped key parts unchanged. This is a false reuse that the old whole-fingerprint definition avoids.

**Reproduction:** write two fixtures with root imports `vitest: 4.0.0` and `a: 1.0.0` / `a: 2.0.0`, and matching snapshots. In each fixture, replace only the block between `importers:` and `packages:` with the one-line flow map above, using its own `a` version. Keep `packages` and `snapshots` in the written block layout. Read each install, then call `dependencyKeys` with environment imports and runner imports both `[{ from: '', name: 'vitest' }]`, and empty builtins. Compare `keys.environment` and `keys.of({ imports: [{ from: 'test', name: 'a' }], builtins: [] })`. Load `a` with Node's `createRequire` rooted in that fixture.

Observed output:

```text

equal whole fingerprints: false

```

**Worker-sized fix:** validate the value/layout of the three read sections at their headers. Return `null` for a nonempty representation that the reader cannot read, rather than treating that section as ignorable metadata. Audit the other skip branches against the same rule; keep known ignored metadata explicit. Add a reader rejection and an install/key regression for the flow importer case above. The install must fall back to the whole fingerprint, and the bump must change its key. Keep the key-validity cases current.

### B2 (proven): A missing importer link lets the graph key a different package from the one Node loads

**Location:** `src/core/keys/pnpm-install.ts:95` to `:102`; the assumed resolution is at `src/core/keys/pnpm-graph.ts:135` to `:140`.

**Contract:** 011 C11: “A package is found as Node finds it”; a name that does not resolve must key as absent. Row 011-166 and this review brief require a missing entry to be stale with one note. The review brief requires no reuse across a bump that changes an in-thread package, beyond C11's listed misses. This case uses a declared literal `require`, not an undeclared package edge or a hand-built path.

The snapshot loop checks the real package folders. The importer loop only enumerates entries that exist. It never checks whether each required declared link exists. With root `a@2.0.0` and workspace `packages/app` declaring `a@1.0.0`, delete only `packages/app/node_modules/a`, leaving both snapshot folders present. The install remains trusted, with no note, and retains `formerPnpm`. Node now resolves the workspace's `require('a')` to root `a@2.0.0`; the graph still resolves it to `a@1.0.0`. It remains wrong even after a fresh read/start.

A bump of the root's `a` to 3.0.0 then changes what the test loads but keeps its new scoped key. The old whole fingerprint changes, so this is a regression from the previous definition.

### S1 (proven, nonblocking): pnpm types-only identities retain their version

**Location:** `src/core/keys/pnpm-graph.ts:172`; resolved-edge identities at `:151` also retain type-only child refs.

C11 says a types-only package “keys as a constant ... so `@types/node` re-keys no file that keeps its own segment.” The implementation emits `${id}@types-only`, and `id` includes the version. A direct types-only `@types/x` bump from 1.0.0 to 2.0.0 changes the file segment in a trusted fixture. Each snapshot contained only `index.d.ts` and its manifest; the environment remained fixed. There is no false reuse here, only extra invalidation. Design section 2 explicitly proposed `<id>@types-only`, so this is also a conflict between accepted design text and C11, not a reason to block these rows independently of B1/B2.

**Next action:** the coordinator should settle the intended constant identity and its treatment in parent edge identities. If C11 remains authoritative, one small graph/test row should ensure a pure types-only bump preserves the file key, while a manifest import still re-keys. Do not replace the marker alone and overlook parent edge refs.
