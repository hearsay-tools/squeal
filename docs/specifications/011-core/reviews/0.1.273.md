## Blockers

### B1: proven: a prepared record ignores a merge hold that starts during its busy wait

Location: `src/core/scheduler/scheduler.ts:1047`, `:1073`, `:1083`, `:1105`, `:1128`.

Spec 011 C9, unresolved merge (`spec.md:261`): “A run recorded then stores nothing for that key. The file stays queued, and that withhold counts toward no withhold limit.” The preceding sentence includes a key whose closure or project environment names an unmerged path.

The new retry caches more than the observations and counted withholds. `#prepare` computes the current merge-held files, their setup exclusions and `again`. After the first busy error, `#record` reuses that entire object. `#write` never adds files that have become held since preparation. A reconciliation pass can publish a new hold while the record waits. The retry then stores a result for the held key and clears its running phase rather than leaving it queued. The current hold is known; this is not a watcher delay or an unreported file edit.

I reproduced this through `openHarness`, the real Vitest adapter and store. On the first record transaction after a passing source edit, the probe:

1. Confirms that the new key has no stored result.
2. Marks `src/math.ts` unmerged in the index without changing its bytes, using the existing `unmergeIndex` helper.
3. Queues an interval pass and throws `errcode: 5` before the record transaction begins, the same boundary at which a busy `BEGIN IMMEDIATE` gives up.
4. Lets the pass publish the hold, then lets the record retry and waits for `idle()`.
