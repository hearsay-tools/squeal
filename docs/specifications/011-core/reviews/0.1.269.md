## Blockers

### B1. Proven: a slow runner starts after the command hold settled

Location: `src/core/scheduler/scheduler.ts:491`, `:839`, `:885`. The slow host supplied at `:239` also omits the hold from `halted`.

C9: "While either holds, no tier starts in any lane of the worktree, slow and backlog included." R3 also requires that a node:test or pytest file in flight finishes and none starts after it.

The pump checks the hold before it calls `await this.#slow.next()`. That call can wait for the slow load guard. A command hold during that wait only cancels the flights already in `#inFlight`. It does not preempt the pending slow selection. When load falls, `SlowTier.#select` sees `host.halted()` as false, selects a tier, and the pump calls `#fly` without checking the hold again. A cancellable runner gets a pre-aborted signal, but a non-cancelling runner gets no hold controller and runs its new file during the hold.

A clean-tree throwaway probe used the existing `catchUpRepo`, `catchUpSide`, `heldFiles`, `hold` and `liveProcess` fixtures:

1. One 3 s file, slow policy `{ ...DEFAULT_POLICY.slow, include: ["test/**"], quietMs: 0, maxDeferMs: 10000 }`.
2. Slow options use a private slot directory, `recheckMs: 50`, `cpus: () => 1`, and `load: () => [load]`, initially `load = 10`.
3. Start the scheduler and wait for `readSlowActivity(...).kind === "waiting"`. No runner call has started.
4. Add a live command entry. Await `scheduler.commandHold()`. It returns `true`.
5. Set `load = 0`, then wait 500 ms. The command entry is still live.

Observed:

```text
cancels=true:  before=0 after=1 active=0 cancelled=true completed=[]
cancels=false, backlogSlot=()=>1:
               before=0 after=1 active=1 cancelled=false completed=[]
AssertionError: expected 1 to be +0
```

This is a controlled sequence, not a timing conjecture. It lets validation compete with the wrapped gate after the wrapper was told the hold settled. The same probe also shows an unnecessary cancelled Vitest tier starts after settlement.

Fix for one scheduler worker: preempt a pending slow selection when a command hold begins, and include both hold causes in the slow selection's start guard. Guard selection and launch, and return any selected claims and permits correctly if a hold intervenes. Do not stop the scheduler or discard its queue. Add a regression for the load-guard sequence with both cancelling and non-cancelling runners. Preserve the passing in-flight slow-cancel behavior.

### B2. Proven: overlapping holds repeat the wrong start and lose the other hold's transitions

Location: `src/core/delivery/hold-told.ts:31`, `:58`, `:79`; consumed at `src/core/delivery/delivery.ts:206`.

C8: "a hold's start and end are told as liveness is, once per change and in one line each". The task also requires one start and one end per consumer. C9 explicitly permits two command holds at once.

`holdsChange` notices any change in the complete label array, but `holdChangeOf` always returns the *first remaining hold* as a new `on-hold` message. It does not identify which entry started or ended. Command text alone is also not a holder identity.

A clean-tree probe registered a consumer against a live fixture worktree, then used the command-row writer and delivery API:

```text
add live hold A (command "gate A"); tool boundary
add live hold B (command "gate B"); tool boundary
remove B;                            tool boundary
```

Observed `delta.hold` commands:

```text
on-hold gate A
on-hold gate A
on-hold gate A
```

B's start and end are never named. A's unchanged start is delivered three times. A merge hold with a command hold behind it has the same first-entry problem. If an old hold is replaced by another with the same command between boundaries, equal text labels can suppress that change altogether.

Fix for one delivery worker: retain enough stable hold identity and previous hold data per consumer to compute added and removed entries. Deliver each actual change once, name the changed hold, and say validation resumes only when no hold remains. Preserve registration seeding and daemon-down suppression. Add tests for A then B then B's removal then A's removal, merge plus command, two holds with the same command, two independent consumers, and hold changes first seen at Stop. The shared `HoldChange` payload and formatter may need an additive extension to carry more than one change.

## Should-fix

### S1. Proven, non-blocking: status suppresses `expired` when the holder is also gone

Location: `src/core/status/holds.ts:72`; compare `src/core/scheduler/command-hold.ts:108`.

C6's new amendment defines `gone` as each recorded process being gone and `expired` as `until` having passed, so readers need not judge either again. `readHolds` tests `!gone && entry.until <= now`; therefore an entry that satisfies both facts carries only `gone: true`. The daemon's prune instead gives the passed deadline precedence and records reason `until`.

A probe recorded a process, waited for its exit, added an entry with a positive 1 s bound, and read status at a clock 2 s later. Output contained `gone: true` and no `expired`; an assertion for both failed. Both implementations still end the hold, so this does not block the wave's scheduling or notification goals.

Fix in the delivery/status worker: calculate the two factual flags independently, and use the daemon's reason precedence when rendering a single explanation. Add one gone-and-expired case beside the existing live and gone cases.
