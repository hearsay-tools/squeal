## Process-state diagnosis

**Proven by source and an independent experiment:** signal 0 can succeed for a child that has stopped executing but has not been reaped. `src/core/daemon/terminate.ts`'s `statOf` returns null for a missing process, a zombie (`Z` or `X`), or `PF_EXITING`. `src/cli/stop-removed.ts`'s `processEnded` polls that same start identity after the socket closes. A successful signal 0 therefore does not contradict this stop's completed process wait.

The probe spawned a child, waited for readiness, sent SIGKILL, and held the parent's event loop in a bounded synchronous raw `/proc/<pid>/stat` read until the child was a zombie. With the child still unreaped, signal 0 succeeded and `statOf` returned null:

```json
{"zombie":{"killZeroSucceeds":true,"rawState":"Z","statOf":null}}
```

The CI log does not prove whether its particular process was a zombie or in kernel exit. The reproduced distinction and the source support the coordinator's race diagnosis. They do not establish a product claim made while the stand-in still executes. A zombie cannot execute application code. `PF_EXITING` is kernel exit, not a promise that the PID has been reaped or that all kernel teardown has finished. The stop separately checks its marked children before it says no process it started still runs.

To avoid relying only on the same helper in the test and implementation, the independent probe ran two detached daemon stand-ins through `stopCommand` after removing their roots. Assertions read raw `/proc` state without calling `statOf`, checked both were running before stop, required exit 0 and the no-process-remains message, and checked both had entered exit before return. The child's SIGTERM handler imposed its delay after the stop request. Actual output:
