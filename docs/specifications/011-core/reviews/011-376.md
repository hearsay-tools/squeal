## Should-fix

### S1. Proven: an early test error leaves the probe interval running

Locations: `test/code/coverage/writer-turns.test.ts:53`, `:57`, `:62`; `test/code/coverage/turns.ts:25`; cleanup at `writer-turns.test.ts:26`.

`watchTurns` creates a referenced 5 ms interval. Only `turns.stop()` clears it. If creating the second payload link throws, or the test times out before reaching `stop`, its cleanup removes the payloads but never stops the probe. It also does not close the writer. This does not meet R1 check 3's cleanup condition. Ordinary record-count and timing assertion failures are safe: both assertions follow `stop` and `close`.

Proof: in scratch, replace only the second `own.file(...)` expression with an injected payload-link I/O error. Capture the interval handle when created and inspect it in `afterEach`, before the probe's own explicit cleanup. The test failed with `EIO: injected payload link failure` and printed:

```text
review early-failure probe: interval active=true, referenced=true
```

The probe then cleared that exact handle, so this review left no interval running. This proves the early-error leak; timeout cleanup is inferred from the same missing lifecycle cleanup. It does not prove a missed regression or a failure on an ordinary run, so it is nonblocking under the reviewer skill.

One-worker fix: give the timer and writer test-lifecycle cleanup that runs on early errors and test timeout, before deleting their fixtures. Preserve the current stop-before-assert ordering. A `finally` around an indefinitely pending `idle()` alone would not handle Vitest's timeout.

## What fits

1. **Proven, regression guard:** the whole-map fallback and the parse-only mutation fail. The parse mutation fails on both Node 26 and the supported minimum Node 22.19. `threadCpuUsage` measures the calling thread, not the mapping worker. A synchronous CPU-heavy parse cannot allow the interval callback to run inside it; the next callback includes its CPU cost.
2. **Proven on the tested runs, work-derived bound:** the budget is half a parse of the same bytes in this process. It has no host-speed constant. Removing descheduled time avoids the prior wall-clock failure mode, and the checks run rather than skip at high load. Cold parsing and main-thread GC can change the calibration, but neither caused a false failure or a missed parse in these probes. Universal margin across machines remains **unverified**; no contrary failure is proven.
3. **Proven by source, conservative sampling:** `watchTurns` measures CPU between callbacks, not one sample per event-loop turn. A 5 ms window can contain several short turns, which can raise the maximum; it cannot divide a single blocking synchronous turn. The initial 30 ms wait and final 50 ms drain give the probe callbacks before and after the writer. Main-thread GC and other work in the Vitest worker count. Other threads' CPU does not. The wall and CPU maxima may come from different windows. Cleanup on an early error is S1.
4. **Proven, existing D8 design:** `writer.ts` opens the store and calls `coverage.putParts` on the main thread. Spec 015 D8 Mapping says: "the main thread gives it the sources the payload names and stores the record." A slow synchronous store write does delay a user's daemon, but this candidate neither introduces that delay nor violates the mapping design. The worker's 240 ms wall/10 ms CPU observation does not establish whether disk wait or descheduling caused the gap. This test intentionally does not bound synchronous I/O latency. No product repair is justified by this diff.
