## Nonblocking notes

### N1. Plausible: a reused pid can keep a failed spawn in the starting outcome

`src/cli/start-ready.ts:33` identifies the spawned process through `pidRuns(pid)`, which uses `kill(pid, 0)`. If the child exits and that pid is reused before the next observation, the new process can keep `lives()` true. With no answering daemon, the command then waits to the bound and returns 3, saying its daemon is still starting, instead of 1 for the ended child. The new `EnsuredDaemon` record retains no child exit state or process birth identity. This is a plausible race, not an observed pid reuse, and does not block the wave.

One-worker follow-up: preserve the spawned child's exit/error state or its process identity for the explicit-start wait. Keep the string-returning `ensureDaemon` interface for hooks and the probe after the liveness check, so an exited loser still succeeds when the winner serves. Add a deterministic case in which the original child has ended but a different process has the same numeric pid.

### N2. Proven: C9 omits its retained answer-at-bound exception

At the candidate, `docs/specifications/011-core/spec.md:268` says exit 0 is once the daemon "answers and the store records it". `status.md:191` explicitly retains the old exception: "A daemon that answered but is not recorded at the bound counts as served, as before." `src/cli/start-ready.ts:69` implements that exception. The isolated wait probe confirms it. The CLI reference says exit 0 once a daemon answers, so the product's documented command behavior and accepted deviation agree. C9 alone lacks the exception. This is documentation drift, not a new product regression.

One-worker fix: add that bound exception to C9. The coordinator reports that it already made that docs edit after the candidate SHA; it is outside this pinned review. Do not remove the implemented fallback as a side effect of this note.
