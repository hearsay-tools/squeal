## Blockers

### B1 — Proven: the table's daemon column is a parallel decision path

Locations: `src/core/run-evidence/run-evidence.ts:260`, `test/run-evidence/fixture.ts:152`, `src/core/scheduler/tiers.ts:851`, `src/core/scheduler/record-tier.ts:98`.

The brief requires that the table's daemon column describe the daemon's own path, rather than a copy that can drift. The row also requires both callers to take their store decision from the module.

`decideFiles` composes hold precedence, the barrier, `runEnd`, and `storeDecision`. Its only production caller is `keepDecisions`; the daemon never calls it. The fixture labels a direct call to `decideFiles` as `daemon`. The real daemon instead constructs requeue and a possibly modified startup report in `TierRecords.#write`, calls `recordTier`, and calls `storeDecision` in `recordFile`. The new `runEnd` wrapper only forwards to `tierEnd`; it does not connect the daemon to the table's per-file decision function.

The paths already return different decision kinds for identical touch evidence. The table returns `touched` on every invocation. The real daemon passes a first touch through `Withholds` into `requeue`, and an exhausted touch into `unknown` (`record.ts:303-350`). Likewise, the daemon folds merge-held files into requeue and re-reads the hold at a write retry, while the table returns `held` from its initial evidence. `touched` and `held` are useful evidence labels, but they do not establish that this table exercises the daemon's store decision. The existing daemon actions remain correct; the required shared path and its proof have not been completed.

**One-worker fix:** make the module's decision preparation be the function the daemon actually consumes, and exercise that function in the table. Supply caller-owned retry, hold and ledger facts explicitly; keep `Withholds`, its counting, lock order and writes with the daemon. Keep `store-decision.ts` and the record write unchanged. Distinguish evidence labels from final store decisions in the test and notes. Merely adding a daemon call whose answer is ignored would not resolve this finding.

### B2 — Proven: observed-read evidence still bypasses the required owner

Location in the new code: `src/core/run-evidence/run-evidence.ts:146`. Evidence: `src/core/scheduler/observed.ts:214-226`; disclosed at `tasks/011-319/notes.md:67`.

The row's explicit done-when is: "No file outside the module calls `snapshotInputs`, `changedSince`, `barredByTouch` or `prepareObserved` to decide a store."

The new module delegates to the unchanged `prepareObserved`. That function still snapshots the observed paths and calls `changedSince` outside the module. Its output directly supplies changed and touched evidence to the store decision. Having a single caller does not satisfy the required ownership. This finding concerns the incomplete move in this range, not a defect in the pre-existing helper.

The mock is not proof that the exception is necessary. `busy-withhold.test.ts` wraps `prepareObserved` with `vi.fn(real.prepareObserved)` and counts calls. A compatibility wrapper can retain that name and one call while the module owns the evidence computation. Being a key-alarm entry is also not permission to leave a stated done-when unmet; the alarm must verify an equivalent move without a version raise.

**One-worker fix:** move the snapshot and change computation into the module. Retain a thin compatibility entry if needed for the unchanged scheduler test. Verify the call boundary, scheduler tests and key alarm again. If this ownership exception is preferred, the coordinator must resolve it against the approved row before treating the row as complete.

## The five requested checks

### 1. Keeper equivalence — Proven for valid reports and the stated sources

The old and new candidate gate is the same: only completed files with a non-null record reach evidence gathering (`keep.ts:163-169`). A runner-withheld file is absent from `completedFiles` by the `RunReport` contract (`types/runner.ts:553`); the new decision therefore introduces no extra exclusion for a valid candidate.

For each candidate the old predicate is exactly: no observed growth, no environment load beyond its project's keyed environment, and no changed or touched named input. The new ephemeral file state is held at its run key, with no requeue, cancel, runtime identity check or ledger supersession. `keeps` accepts only `store` at `ran`. Under these conditions that is the same conjunction. Growth produces `grown` or `first-seen`; missing environment inputs produce `environment`; moved bytes produce `unstable`; touches produce `touched`. All are rejected. Combined evidence changes the reason's precedence, not which files are kept. The 41 comparisons support this source proof rather than proving every possible runtime state by themselves.

**Proven listing claim:** a listing path has no regular-file stat-cache entry. `createFsHasher.stat` returns null for the directory, including a linked directory reached by a trailing slash. The old `changedSince` therefore produces neither a change nor a touch for that path (`revision/reconcile.ts`, `diffCandidates`). Leaving it out in `movedInputs` changes neither filter. Listing hashes live in `Listings`, not the stat cache. The temporary trees included such an input.

`stillAsRead` still filters only changed bytes, as old `steadyOf` did; it does not introduce a touch rejection after the run. Its only changed input selection is the same inert listing omission. The record-null check and the write-time `InputCheck` are unchanged.

### 2. Daemon behavior — Proven preserved; table path claim refuted by B1

The diff preserves `#ended` and `#focused` ordering; their `unstableInputs` calls pass the same tier and hasher. The moved implementation removes listing paths exactly as before.

Under the same scheduler lock, `#prepare` still calls environment re-key, observed preparation, scratch instability, touched union and sort, then the merge hold, in that order and with the same arguments. `#heldNow` still applies the current hold plus the prepared hold. `#barrier` passes the same free files, report, touched paths and growth to the same helper. Its `Withholds` operations are untouched. `recordTier` calls the forwarding `runEnd` with the same arguments formerly passed to `tierEnd`. `record-tier.ts`, the decision function, transaction nesting and write order are unchanged. The unchanged targeted scheduler tests pass.

This proves the move did not alter the daemon's behavior by source equivalence. It does not make `decideFiles` the daemon's path.

### 5. Deviations — Judgment

The notes actually list four bullets under "Where the design's calls did not hold", not three.

1. **Proven, not acceptable as completion:** leaving observed-read snapshot/change computation outside the module violates the explicit done-when (B2).
2. **Proven, reasonable behavior-preserving deviation:** keeping `rekeyEnvironments` whole preserves its `seeStartup` write, read order and scheduler-lock boundary. It also preserves the existing mock's call count. This does not break the row's named done-when, but it means the new module performs re-key side effects, contrary to the design's proposed read-only boundary. Record this limitation if accepted; do not describe the entry as only reading evidence.
3. **Proven, justified retention:** keeping the per-lookup CLI cases avoids claiming that a no-write, no-daemon table tests lookup and persistence. Retain them. This is a subtraction-boundary correction, not a behavior change.
4. **Proven coverage limit, nonblocking:** the scratch row reaches `Tier.changes`, but there is no independent revision-only row. "A content change also moves the bytes" is not a general justification: revisions retain changes after restoration, and ordinary directory-listing changes need not change any named file's bytes. No regression is shown: the unchanged `tierEnd` still consults `tier.changes`. A direct row for an ordinary listing change would make that source explicit.
