## B1 closed: uncertain writes cannot adopt another hook's claim

**Proven by source and independent fault injection.** `src/harness/shared/ensure.ts:190-206` and `:223-233`; `src/core/presence/events.ts:184`; `src/core/presence/stored.ts:127` and `:145-155`.

Each hook generates a UUID before attempting the claim. The transaction writes that UUID into the claim and records its own result in `ran`. Recovery preserves a known `joined` or `none` result. Otherwise, it returns `claimed` only if the stored claim carries this attempt's UUID. A failed read returns `none`. The old incarnation/version/millisecond tuple no longer establishes ownership.

The independent probes reused the existing socket and store fixture setup, but rebuilt the fault order and asserted the intermediate results. Both hooks used the fixed clock `1_800_000_000_000` and the same version.

1. **Join, then acknowledgement throw.** B first reads no claim. Its write wrapper lets A call the public `ensure`, claim and request its successor. B then calls its real `write` and verifies that the callback returned `joined`, before throwing an acknowledgement error. B returns `alive`; the recording dependency receives exactly one call in total, A's lock-waiting successor. This checks preservation of the known join, including absence of a fallback spawn call.
2. **Rollback, intervening claim, then reject.** B's real `write` runs the real callback inside an enclosing store transaction. The probe checks that it returned `claimed`, reads B's attempt ID from the actual store, then throws a sentinel to roll back the enclosing transaction. It verifies no claim remains. Before rejecting B's write, it lets A call `ensure`, claim and spawn. A's claim has the same incarnation, version and time, but a different UUID. B's recovery leaves A's UUID intact and requests no second lock-waiting successor. Exactly one such successor is recorded.

The candidate's committed tests at `test/harness/handoff.test.ts:291-355` cover both orders too. The existing own-claim/lost-ack test still passes: recovery can recognize this hook's persisted claim and start its successor. The busy-store test still leaves ownership to the next claimant.
