## Blockers

### B1. Proven: an edit keeps an expired waiter reservation fresh

`src/core/capacity/pool.ts:442` (refresh), `src/core/capacity/pool.ts:365` (expiry).

R3 requires that a waiter forget its age 30 seconds after its last look. A refused acquisition records `#idleSince`. Starting an edit preserves the pending demand and starts the refresh timer. That timer updates only CPU and the mark's timestamp. It neither expires the waiter nor rebuilds its demand. The mark can therefore reserve permits for the whole edit after the last pool look is more than 30 seconds old.

Failure scenario: on two slots, A holds both permits. B's `acquire(2, "fast", 2)` is refused. B starts a long edit in the same lane and makes no further pool look. After 31 seconds, A releases both permits. C cannot take even one free permit because B's fresh mark still reserves both through `least: 2`. B cannot use them while its edit runs. A long edit can thus stop unrelated backlog work with every permit free.

Proof: a standalone probe used the public pool API, an injected CPU reader, a 200 ms refresh, and a real 31-second wait. It changed no product file. Output:

```text
holder grant 2
waiter acquire null
edit start: want 2, grant 0, since T, least 2, cores 1
31 s after last look, after refresh: want 2, grant 0, since T, least 2, cores 1
new daemon after holder releases both permits null
```

Control: starting one more edit calls `#republish`, which applies the expiry. The mark then reads `want 0, grant 0, since null, cores 1`; the same one-permit request succeeds. An injected-clock probe gave the same result.

Fix scope: in the refresh path, expire idle waiter state and publish the resulting demand and age while keeping the active edit's CPU mark. Add a regression that refreshes past expiry while an edit remains active, then lets a newcomer acquire a free permit. Clearing only `#since` in memory is insufficient if the timer writes its previous `#mark` unchanged.

### B2. Proven: the first edit writes no CPU mark when the pool directory is absent

`src/core/capacity/pool.ts:242` (`running`), `src/core/capacity/pool.ts:422` (failed initial publication).

C10 requires an edit's daemon to write its CPU mark while the edit runs. `acquire` prepares and checks the pool directory. `running` does neither. Its first write gets `ENOENT` on a new pool directory, and `#republish` suppresses that error. The refresh also cannot create the directory.

Failure scenario: a Linux daemon uses `baseline.onStart: lookup-only`, has no slow work, and has not acquired a backlog permit. Its first edit runs before `$XDG_RUNTIME_DIR/squeal` exists. No edit mark appears. Another daemon creates that directory in `acquire` and admits backlog work without counting the active edit until a later refresh. This loses the required conservative CPU count before the edit's first measurement.

Proof: two standalone public-API runs used `hostSlots: 2` and a CPU reader whose initial measurement is unavailable. Only directory creation differed:

```text
directory prepared false: edit.running(4) leaves no mark
backlog.acquire(2): grant 2

directory prepared true: edit.running(4) writes want 0, grant 0, since null, cores 4
backlog.acquire(2): grant 1
```

The second run is C10's half-slots gate. The first admits an extra backlog worker solely because the edit's mark was lost.

Fix scope: prepare and check the directory before the first edit mark, using the same private-directory rules as `acquire`. Keep the edit independent of permit acquisition and retain its nonblocking failure handling. Add a regression that starts an edit before any acquisition with a missing pool directory and checks both its mark and the next daemon's gated grant.

### B3. Proven: an unused non-isolated sibling forces an isolated tier to width 2

`src/runners/vitest/width.ts:71` and `src/runners/vitest/width.ts:72`.

R3 says the floor of 2 applies only to `isolate: false` projects. Row 011-97 requires an isolated project at grant 1 to run one worker. `#rootFloor` instead becomes 2 if any project reading the root width is non-isolated. `floorOf` then gives that floor to isolated siblings, including when the non-isolated project has no file in the tier.

Failure scenario: projects A and B both use `extends: true` and omit `maxWorkers`. A is isolated; B sets `isolate: false`. Only A's two files need validation, and one permit is available. A's width hint is 2 at grant 1, so the scheduler's `fewest` asks for 2 and waits. A could run correctly on the available permit. With `hostSlots: 1`, that isolated backlog cannot start at all.

Proof: a standalone real-adapter fixture used that configuration and selected only A's files. It called `run` with `workers: 1`. Output:

```text
listed [ 'a:a1.test.ts', 'a:a2.test.ts', 'b:b1.test.ts' ]
isolated a width at grant 1 2
isolated a only: failure null results [ 'pass', 'pass' ]
isolated a only: worker ids [ '1', '2' ]
```

W6's notes identify the shared root floor as a decision. It prevents one mixed-project width mismatch by widening the rule beyond the accepted design. The existing mixed-project test gives B its own `maxWorkers: 3`, so it does not cover this shared-root case.

Fix scope: keep isolated projects' minimum at 1 when sizing and reporting widths, while retaining the floor for a selected non-isolated project and the mixed-tier no-throw guarantee. Add the shared-root fixture above, an isolated-only run at grant 1, and a mixed run at grant 2. The scheduler must not ask for 2 permits merely because an unused sibling is non-isolated.
