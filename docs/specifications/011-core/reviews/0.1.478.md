## Blocker

### B1: Proven: pruning ignores a covered file queued again

Location: `src/core/store/covered-files.ts:83-94`. Contract: “kept while any of its files is queued or running, and at least 10 minutes after” (`research/request-intake.md`, Covered files, condition 3; board row 011-325).

The writer reads only records with `idle_since IS NULL`. Once it marks a record idle, no later write checks that record's files again. The delete then removes every expired idle record without checking whether a file is queued or running now. A later run can therefore lose a record while a covered file is pending. It can also lose the record less than 10 minutes after that later run ends.

The worker notes explicitly choose never to clear `idle_since`, on the ground that a later run is not the original request's. The agreed condition says any covered file, and the record contains neither per-run identity nor a different agreed retention rule. That choice does not satisfy the contract. The existing lifetime test covers one queued-to-idle transition only.

Reproduction through the real intake, real ledger and real store, using `request-intake-probe.ts`:

1. Create `p = probeHost()` and retain `start = p.state.now`.
2. Take `groupRequest(TESTS_GROUP, p.groups, undefined)` and retain its `coveredId`. B is queued.
3. Complete B with `p.ledger.applyResults(file, keyOf(B), [], null)` and `p.ledger.commit()`.
4. Set the clock to `start + 60_000`; take `retryRequest()`. The old record is now marked idle and is still readable.
5. Set the clock to `start + 2 * 60_000`; call `p.ledger.enqueue(file, 0, true)` and commit. Take `retryRequest()`. B is queued again and the old record remains readable.
6. Set the clock to `start + 11 * 60_000`; take `retryRequest()`. Assert `file.phase === "queued"`, which passes. Assert `readCoveredFiles(p.store, id) !== null`, which fails: it returns `null`.

The probe used existing public ledger operations, not a substitute pruning implementation. It changed no product source. The failure is deterministic clock arithmetic, not a load timeout.

**One-worker repair:** prevent deletion whenever a covered file is pending, and restart the grace interval after later pending activity ends. Do not treat the first idle observation as terminal. Examining idle records too and clearing their timestamps on observed re-entry closes this reproduction; also account for activity between prune calls when establishing the next grace interval. Test queued and running re-entry, then the 10 minutes after the later end. Keep the write and prune in the request transaction. No CLI or key change is needed.

The ImportsSeen tests cover repeated `false`, success, an overlapping call and a thrown request.

`daemon.ts:416` is unchanged. It still calls synchronous `refreshObserved(): boolean`; the narrowed lifecycle declaration writes no store and retains its closed/install-wait `false` answers.

## Should-fix and qualifications

### N1: Proven, nonblocking: a narrow install-wait answer now waits for a write

Location: `request-intake.ts:153-162`. Previously, after selection, this branch returned its install-wait answer without a transaction. It now holds the scheduler mutex while it retries the record transaction. A write lock can delay `squeal run <group> <path>` until released; a daemon stop during busy retry rejects it with the named busy-store error; a non-busy record-write error also rejects it. A bounded CLI wait can reach its deadline before that answer is taken.

This follows the new requirement to record the install-wait decision and is disclosed in W2's notes, decision 4. It is not an accidental integration loss and is not a blocker. The coordinator should record this observable timing/failure qualification when folding the row. Preserve the busy retry, no progress ask and no lane wake on this branch. Do not describe all failure exits as unchanged.
