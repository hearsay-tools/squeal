## What fits

### B1: overlapping requests have a positive source of truth

`src/core/scheduler/scheduler.ts:355` publishes all three sets in one row: narrow asks, exact commit asks and group names whose lane has `requested` set. `src/core/state/groups.ts:202` reads these through `publishedLaneRequests`. It no longer uses lane activity to decide that a whole-group request exists or that a narrow ask excludes it.

The real scheduler tests distinguish these cases:

| Case | Observed result |
| --- | --- |
| Narrow A only | B stays on request and does not run after A finishes. |
| Whole group only | No file is on request; both run. The published whole-group request disappears when the queue empties. |
| Narrow A, then whole group while A runs | B leaves on-request classification and runs without another request. |
| Whole group, then narrow A | B stays runnable and both files run. |

The status tests exercise the real text/JSON formatter. A published request preserves queued counts; mere lane activity does not. `kept-header.test.ts` verifies request metadata starting and ending with unchanged keys makes the kept part rebuild. The old narrow-row and re-key tests still pass.

### Request publication follows the owner through its lifecycle

The only writes to `#requested` are its false initializer and `#setRequested` (`src/core/scheduler/slow-tier.ts:158`, `:278`). The setter calls `requestsChanged` after a change. `request()` sets it; `#candidates` clears it when no file is queued or its group is absent (`:524`); `retire()` clears it (`:845`). Both `CommitAsks` instances call the same callback on add, prune, follow and clear. Thus every successful mutation republishes the aggregate row; repeating a value needs no write.

The supplemental retirement probe first held a real whole-group run open, added a narrow ask, and asserted the row held both. A policy reload then removed that lane. `GroupTiers.#sync` retired it before deleting it; all its asks and the whole-group request disappeared, leaving no row. The ordinary drain test verifies the other clearing path. Completing the commit/narrow/whole combination also deleted the row.

The restart probe put all three request kinds in a predecessor row, registered a second scheduler with a later daemon start, and started it over the same store. The reader rejected the predecessor row. Both queued files stayed on request, and the new scheduler ran neither. The rejection uses the existing timestamp rule: a row stamped before the registered start is ignored. Publication still uses `CalendarSteps.stamp`.

The wire shape preserves `{ at, asks }`, including `asks: []` for a row containing only whole-group or commit asks. The exact old parser reads only narrow asks and safely ignores the extra fields. The new parser reads an old `{ at, asks }` row with empty commit/requested sets. The existing `publishedNarrowAsks` API still returns only narrow asks. None of these readers confuses a whole-group or commit ask with a narrow ask.

### Commit asks are exact per file and key

`GroupTiers.commitAsks()` publishes `SlowTier.asks`, not every queued file in an active lane. `onRequestFiles` compares the file id and its current key against that map, just as `SlowTier.#trigger` calls `asks.has`. Commit asks do not follow an edit to another key; narrow asks do. The pruning callback republishes removals.

This matches the held-group behavior used by spec 023, including its D7.3 narrow per-group requests and rows 023-67/023-79. A request for a selected file does not release unrelated files. The actual trigger contract for groups at `commit` is spec 019 D5.1: "For each check of a group at `commit` whose file the commit changed ... queue it now". It never makes a commit a request for the whole group.

The supplemental probe edited A and B but committed only A's source. While A's run was held open, the published commit map contained only A at its current key. B remained on request. Adding a narrow request for B and then a whole-group request preserved all three request kinds correctly. The permanent commit-group tests also verify partial commits, exactly-once execution and an edit re-keying an asked file before it runs.
