## Blockers

### B1. Proven: the batch budget can hide an under-grant from the fallback

Location: `src/core/scheduler/tiers.ts:435`, `narrowerThanEdit` at line 519;
the preceding budget check is at line 398.

Design D1 and C15 require: "The batch never starts later or narrower than an
edit's tier would". An under-grant must return its lease and start at most
`runner.tierSize` batch files without a permit, as wide as an edit's tier.

Reproduction: queue and promote six files of 500,000 ms each, with the default
`tierSize: 4`, `timeoutMs: 600000`, and a pool offering and granting three.
The batch's `BacklogWall` admits three files. Its fourth would exceed the
600,000 ms budget at three workers. `narrowerThanEdit` then compares the grant
with those **three already trimmed files**, so three appears sufficient.

Actual probe output:

```text
tierSize: 4, timeoutMs: 600000, fileDurationMs: 500000
batch: files [slow00, slow01, slow02], leased: true, grant: 3
pool: takes: 1, released: 0
comparison edit: files [edit00, edit01, edit02, edit03], leased: false
```

The batch starts fewer files at once than the same work in an edit's tier.
The existing under-grant test uses short durations, so its wide pick retains
all six files and does not expose this case.

Fix sized for one worker: determine the edit-sized batch candidate and its
width independently of the pool-budgeted wide pick. Compare the grant with
that candidate, return an inadequate lease, and select the permit-free tier.
Add the long-duration, low-offer regression above. Preserve runner ceilings,
claims and the ordinary wide-grant path.

### B2. Proven: a batch grant does not end an earlier wait in its lane

Location: `src/core/scheduler/tiers.ts:430`, through
`src/core/scheduler/capacity.ts:77`.

C10 requires a log line "when the wait starts and one, with its seconds, when
it is granted". Notes item 4 and `PoolWaits.granted` define a grant in the
lane as the end of its wait.

Reproduction: a normal Vitest backlog tier is refused and records a wait.
A named wait then promotes those files. Capacity becomes available, and the
batch gets a six-worker grant in the same lane. Every batch passes
`waitsIn: null`, so `TierCapacity` skips both refusal **and grant** reporting.

Actual probe output with a real pool:

```text
backlog refusal: no tier; published lanes: [vitest]
log: the pool refused the vitest lane's tier: it waits for CPU (...)
batch grant: six files, leased: true, grant: 6
published lanes: [vitest]
log: still only the refusal line
```

The grant neither drops the wait row nor writes the required end line. A
subsequent refusal within 30 s can also retain the old `since`, spanning a
grant that should have ended it. Suppressing a new wait for a batch that
falls back is correct; suppressing the end of an existing wait is not.

Fix sized for one worker: distinguish suppression of a batch's refusal from
notification of a grant in a lane with an existing wait. End and publish
that wait on the grant, without logging a wait for the refused fallback.
Add a scheduler/capacity test for backlog refusal, promotion, then batch
grant, and assert the end log and removal of the published lane.

## What fits

- The ordinary refused six-file batch selects four files, then two, with no
  lease. `executeTier` calls `running(files.length)` and ends that mark in
  `finally`. Under-grants that the comparison detects return the lease
  before recursion. In the `asEdit` pass no acquisition occurs, so this new
  fallback cannot recurse again on a capacity refusal.
- A sufficient grant keeps the wide tier. The batch retains `kind: backlog`,
  `promoted: true`, `batchStarted` and the existing post-batch turn and yield
  rules. The fallback does not become an edit for cancellation or fairness.
- D2 text, deadline text and JSON carry the same pool fields. Named JSON
  entries and outstanding standings include `pool`. Grouping includes the
  wait's `since` value.
- Wait start, refresh at 10 s on continued refusal, grant and close are
  covered in isolation. The row is registered for worktree removal. Readers
  ignore missing, malformed, incomplete, predecessor and older-than-30-s
  rows. An older daemon without the row keeps today's output. B2 is the
  missing integration path between these working parts.

## Requested judgments and inputs for the repair

**Notes item 3, per lane.** The implementation is per lane, as stated. Status
adds `pool` only to queued, unpromoted files with no open tier in that lane;
holds and quiet waits take precedence. A refused backlog tier prevents its
lane's backlog from starting, so extending the explanation to that queued
backlog is reasonable. A turn refusal can still let an edit's tier start;
then the open tier supplies the behind reason. This is no additional blocker.
Record the lane-level scope in C15 if retained, as the worker notes request.

**Notes item 5, the waiter mark after fallback.** The batch still asks the
pool, so a refusal can leave a waiter reservation while the permit-free tier
runs. It holds no lease. Its CPU is recorded through the same `running`
path as an edit's. This is a fairness cost of the approved ask-first policy,
not a proven breach of D1. The notes' unconditional "up to 30 s" needs care:
the existing `LockFilePool.#forget` skips forgetting while another lease is
held. With no lease it forgets the waiter after 30 s from the last look;
another lane's lease can retain it longer. Do not replace the pool's shared
waiter state as part of either repair without accounting for other lanes.

Repair inputs: keep `runner.tierSize` as the fallback's file bound, with the
runner's own width and ceiling; return the inadequate grant before starting
the unleased tier; preserve the batch flags and post-batch turn. For wait
reporting, a batch refusal must create no new CPU wait, but a grant must end
an existing wait in its lane. Keep the current text/JSON contract, 2 s
rechecks, 10 s refresh and 30 s row freshness. Add B1 and B2 regressions to
the affected tests. Read Squeal's results and pending CI at the repaired SHA;
do not run a local full suite or build under this task's host policy.
