## B1: Proven remaining blocker: replacing a file state loses its exit history

Contract: condition 3 of `research/request-intake.md`, Covered files: a record is “kept while any of its files is queued or running, and at least 10 minutes after.” The repair brief also names activity that begins and ends between writes.

Locations: `src/core/store/covered-files.ts:143-146`, `src/core/scheduler/covered-files.ts:75`, and the file replacement at `src/core/scheduler/ledger.ts:263-274`.

`leftPendingAt` belongs to a `FileState` instance. Removing a file removes that instance, and adding the same reference creates another with `leftPendingAt: null`. A restored file can take a cached result without ever entering pending in the new instance. The writer then has no evidence of the old instance's later pending activity. Its first-write bound is still the ledger's earlier first write, so the old idle timestamp wins and the record expires early.

The worker notes name this case as an untested limit. The independent probe proves that it violates the condition; it is not only a plausible race.

### Reproduction

The disposable test used the real intake, ledger and store from `request-intake-probe.ts`, plus `recordedBy` from `claims-fixture.ts` to seed a real stored passing result. Times are offsets from the probe's scheduler clock; no wall-clock sleeps are needed.

1. Take `groupRequest(TESTS_GROUP, p.groups, undefined)` and retain its `coveredId`. B is queued.
2. Seed B's pass at `keyOf(B)` with `recordedBy(p.store, p.context.worktreeId, B.path, keyOf(B))`. Apply those stored results to B and commit.
3. At minute 1, take `retryRequest()` to write another record. The original record becomes idle and remains readable.
4. At minute 3, change B's key in `p.state.keys` to `"f".repeat(64)`, settle B and commit. Assert B is queued. There is no record write.
5. At minute 5, call `p.ledger.removeFile(b)` and commit. B leaves the queue and the listing. There is no record write.
6. At minute 6, add B again, restore its original key, settle and commit. Assert the new state has the original `resultKey`, `phase === null` and `leftPendingAt === null`: the real cached pass was inherited without a run.
7. At minute 11, take `retryRequest()`. Assert `readCoveredFiles(p.store, id) !== null`. This fails: the result is `null`, only six minutes after B left queued work.

The helper's cached result is an actual results-table row, not a stubbed answer. The probe writes no replacement retention logic and changes no product source.

### A user can meet this sequence

A user runs a group once, edits a test, then deletes and restores it while its changed version is still queued. A hold, a manual group, or load-deferred work can keep that version queued. Restoring the original bytes can reuse the earlier pass. The next explicit request within the failed grace interval prunes the record.

The production path supports this sequence: `revision.ts:318` removes files absent from a successful listing; `:321` adds restored references as new states; `Ledger.settle` takes a stored hit through `applyResults`. Reconciliation and edits do not themselves write covered-file records, so both listing changes can occur between record writes. The record's identity remains its test-file reference, which is the same after restoration.

**Proven scope:** the core sequence and early deletion were reproduced through production ledger/store/intake operations. **Unverified scope:** no real CLI/daemon session was launched to time deletion and restoration on disk. No unsupported mutation or impossible intermediate state is needed for the core failure.

**Bounded repair input, subject to the human's decision:** keep pending-exit history for the covered reference across removal and re-addition, rather than only for the current file object, or use a conservative bound when that history is lost. Preserve rollback and the handoff bound. Extend the existing lifetime table with removal/restoration from a real cache hit and a grace assertion after the removal. No reader, response or key change is indicated. Inspect the lifetime owner before another repair to the same mechanism, as process step 6 requires.

The passing handoff row preserves an idle record through minute 14 after a first new-daemon write at minute 9, then permits deletion at minute 19. The bound is conservative even if that first attempt rolls back: it still begins after the previous daemon's exits. There is no claim that an in-memory exit timestamp itself survives the handoff.
