### B1. Proven: a replacement's live start mark does not suppress a stopped-daemon delivery when the old record remains

**Changed locations:** `src/core/status/stopping.ts:48` and `src/core/status/died.ts:45`. Caller: `src/core/delivery/liveness.ts:237`, with the silence decision at line 249. The latter file is a caller of the changed boundary, not an unrelated pre-existing defect.

**Contract:** C9's 011-251 amendment says, "A boundary that spawns a daemon gives no news while its spawn is marked" and "With a stale record a start mark is a start and no death." Wave 53's outcome requires the hooks to name a starting daemon as starting. The brief repeats the approved silence rule in check 4.

**Failure scenario:** a consumer was told its daemon was alive. That daemon dies without clearing its record, as SIGKILL does. Once its heartbeat is stale, a hook spawns a replacement and writes the spawn mark. The replacement takes the real daemon lock and writes a live start mark before opening the store or registering. This is an ordinary startup state: `openDaemon` marks the acquired lock before `openStoreFile`, and only `#register` replaces the old record.

`withDeath` now recognizes the replacement's live mark, so status and the delivery header say starting. `livenessChange` calls `withStopping` alone. That function returns through `withShort` at line 49 because the killed predecessor left no shutdown mark. It never reads the replacement's mark in this branch. Delivery therefore emits a down transition during the marked start. Its title and header disagree:
