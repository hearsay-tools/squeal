## Should-fix

### S1. Proven, nonblocking: a pause between readings causes two extra writes without a calendar step

Changed sites: `src/core/scheduler/pool-wait.ts:143`, `:156` and `:197`. `refused` reads calendar time, then elapsed time, and compares their difference with the difference at the last write. A host pause between those readings changes this sampled difference although both clocks advanced together. It bypasses the sampling guard already present in `CalendarSteps.observe`.

The probe used the real stepped clock and normal production publication callback. It initialized a wait at 10,000,000, advanced 2,000ms, then simulated one 200ms thread pause immediately before the separate elapsed reading by advancing both sides of the virtual clock. It never called `shiftCalendar`. After another 2,000ms it refused again with no pause. Actual output:

```json
{"samplingPauseWithoutCalendarStep":{"elapsedMs":4200,"writes":3,"expectedWithoutStep":1,"calendarStepsTold":[],"writeTimes":[10000000,10002000,10004200]}}
```

The delayed pair records an offset of -200ms; the next ordinary pair records 0ms. Each difference crosses 100ms and writes the row, before the 10s refresh is due. The established step detector correctly tells no step. `calendar-steps-sample.test.ts` tests that detector's guard, but it does not exercise this new subtraction in `PoolWaits`. The unchanged pool-wait tests omit `elapsed`, so their single fake time cannot expose it either.

This qualifies R1 check 2's "no extra write" claim. It repeats the sampling issue from review `0.1.524.md` S1 at a new call site. It is nonblocking for the same reason: the proven effect is extra status writes. The probe proves no wrong wait, negative duration, false status, self-sustaining loop or persistent scheduling failure. Its frequency on the real host is unverified.

Fix scope for one worker: keep interval accounting on elapsed time, but use an accepted calendar-step observation for the immediate rewrite, or reject an uncertain sample with the existing bracketing rule. Do not tune the threshold to this host. Add a pool-owner test with both clocks advancing during the sample and no `shiftCalendar`; it must keep one start write until refresh is due. Retain immediate publication after a real step and the existing row shape/readers.
