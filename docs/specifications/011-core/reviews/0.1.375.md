## What fits

### Negative remainder preserves the overrun yield (proven by source and targeted checks)

`yield-sooner.ts:69` returns true when no cut file sorts ahead of the candidate. With known durations ahead and a negative remainder, its later comparison can return false. That helper case does not remove a yield that row 011-107 allowed through today's rank guard:

- An overrun yield is eligible only at estimate + 30 s (`yields.ts`, `byRemainder`). Last-known durations are nonnegative, so the tier has then run at least 30 s.
- From 30 s, `rankToBeat` takes the least live rank of every unfinished file (`yields.ts:427`). `runsSooner` rejects a candidate at that rank or later before it calls the new helper (`:392`). A running file that could sort ahead therefore already blocked that yield under row 011-184.
- A candidate that passes this rank check sorts before every cut file. The new helper takes its immediate true branch, including with a negative remainder. Unknown and zero durations do not change this argument.
- Before 30 s, a negative remainder cannot yet satisfy the old overrun threshold. Suppressing a yield then loses no eligible overrun. Crossing 30 s only tightens rank eligibility; it cannot create a missed eligible yield.

The review probe put a known 5 s running file under an earlier promotion, queued a later promoted file without a new edit, and checked at elapsed 35 s. The tier stayed running. Its earlier promotion expired at elapsed 40 s; one timer recheck then aborted the tier with reason `yield` and left zero timers. A separate probe at 35 s with no running promotion yielded immediately to the queued promoted file. Thus both the protected and eligible overrun paths were exercised without the edit shortcut in `hasRecentAfter`.

### The new early deadline bound rechecks without a loop (proven by source and targeted checks)

`rankToBeat` reads all unfinished ranks against the decision's one clock reading and takes their earliest deadline before 30 s (`yields.ts:417`). `Promotions.rankAt` returns only promotions with `until > now` (`promotions.ts:109`). Each bound is therefore future at the decision reading. If it passes during the check, the existing timer arms at zero; the next reading excludes the expired promotion. A later promotion of the same file then supplies its own later deadline.

The review probe gave a running 308 s file two earlier promotions, expiring at 11 s and 12 s, then queued a later 1 ms promoted failing file at 10 s. There was one timer. At 10.999 s there had been no recheck. At 11 s there was exactly one recheck, no yield, and one rearmed timer. At 12 s there were exactly two rechecks, the tier yielded, and zero timers remained. No edit or file end occurred between checks. The candidate's integration test separately covers one pre-30 s expiry in the real scheduler. The existing clock tests pass with deadlines crossing during a decision.

A file end can also change this decision: rejected candidates stand `named`, and `Scheduler.#fileEnded` rechecks tiers with that standing. The candidate preserves this path.

### Queue and ledger reads do not silently skip a valid candidate (proven by source and targeted checks)

`RunQueue.hasPromoted` calls the predicate only for entries in its current fast-entry array (`queue.ts:354`). The predicate and `priorityOf` run synchronously without an await. `priorityOf` reads the same entry map by the same `testFileId`; it uses `??`, so the failing class `0` is preserved (`queue.ts:312`). The review probe queued priority `Priority.failing`, confirmed that exact value, and observed the overrun yield.

Normal callers pass a registered `FileState` to `Ledger.enqueue`; `Ledger.file` reads its ID from the ledger map. Removing a file removes its queue entry before deleting the ledger state (`ledger.ts:247`). The new undefined/null guards therefore do not reject a normal queued candidate. Focused demand still uses its separate fallback in `waitedFor`; it does not require a whole-file queue entry to pass this helper.

This also rules out an empty-tier loop for valid policy values.
