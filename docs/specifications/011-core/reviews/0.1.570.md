## Blockers

### B1: missing lint rows allow a complete zero-findings commit line

**Proven, blocking, P1.** Locations: `src/core/commit/lint-tally.ts:116`, `src/core/commit/lint.ts:28`, `src/core/commit/lint.ts:159`, and `src/core/commit/text.ts:64`.

The tally visits stored states only. The commit's released paths without states are added to `waiting`, but never to the per-tool totals or incompleteness. `withNotRun` returns immediately when any tool has a counted file. The formatter then presents the existing subset as complete.

Reproduction through the real lint pass and store:

1. `lintTree()` holds `src/a.js` with `ok`. Revise it, nudge a `FakeProvider` pass and await `idle()`. The file has a current clean ESLint result.
2. Add `src/b.js` with `bad no-undef`, revise and commit both files. Do not nudge the lint pass yet, so the new file has no lint state.
3. Read `committedBlobs`, then call `commitLint` with both paths in `changed`, no differing files, and a lint group at `commit`.
4. Format that result with `commitReportText`.

Observed:

```text
lint.counts.tools:
  [{ tool: "eslint", files: 1, findings: 0, running: 0, notDetermined: 0 }]
lint.waiting includes src/b.js at its committed blob
Commit <sha>: 0 known failures; lint (eslint): 0 findings in 1 of 1 file
```

After the pass keys and lints the new file, the same commit has `files: 2` and `findings: 1`. The incomplete first line was therefore not evidence of a clean commit within ESLint's scope.

This breaks wave 123 W4, "puts the zero only on complete evidence", and gh-237's approved done-when: "Pending, unknown, missing or stale-config results for changed files remain explicitly not determined in commit summaries". Spec 017 D8 says the finding count leads only when every file is complete. The existing count rule cannot establish that when listing is still behind. Worker notes 017-32 decision 7 identify the omission but leave it for a follow-up; that does not satisfy this row's completeness goal.

One-worker repair: carry listing uncertainty and released paths missing a state into each affected tool's report. Do not claim every released path is lintable before the provider establishes that. Either count known lintable missing files as incomplete or explicitly qualify the tool's incomplete listing and suppress the complete zero. Preserve ignored/docs-only handling and tools with different progress. Add a mixed regression with an already-current clean file and a newly added failing file before listing, plus the after-listing result. Cover the initial report and its one update.

### B2: the surviving beside tier claims two active tiers after the original ends

**Proven, blocking, P2.** Locations: `src/core/scheduler/overrun.ts:205`, `src/core/scheduler/overrun.ts:235`, and `src/core/status/tier-text.ts:119`.

`Tier.beside` records how a tier started. `Overruns.check` treats its presence as proof that two tiers still run in that lane. `ended` removes the pair flag from survivors only when the ending tier was the beside tier. Ending the original does not clear it; a later check reconstructs it from the surviving tier's immutable `beside` flag.

Reproduction uses `hungTier(5, 4)` from `test/scheduler/overrun-fixture.ts`:

1. Hold the original and beside runs. Advance `OVERRUN_FLOOR_MS` twice, settling after each step. Both tiers are reported as overrunning.
2. Release `hung`, the original tier, and settle. Keep the beside gate held.
3. Count active runs and read `overrunsOf` and `classLines(read(...))` for a beside file.

Observed:

```text
active runs: 1
published overruns: one, for test/q0000.test.ts through test/q0003.test.ts
published overrun.beside: true
... it runs beside another tier, so the lane's next tiers wait for one of the two to end ...
```

There is no other active tier. The JSON also retains `beside: true`, whose new type contract says the lane holds two tiers. The existing new test covers the opposite end order only.

This breaks 011's goal that everything told is true when told, and row 011-405's paired-lane wording. C6 defines this field as present "while its lane holds two tiers" and absent otherwise. It is a reporting defect; the probe establishes no result corruption or extra instance.

One-worker repair: derive current lane occupancy from the live tiers rather than treating historical beside admission as occupancy. Update publication when either tier ends. Keep the admission bound separate: merely removing the paired wording must not falsely promise that a surviving second instance can start another beside run. Give that survivor accurate wait text under the existing admission rule. Test both end orders, the first tier ending before the second reaches its threshold, and status plus named JSON after publication. Do not add a third instance or change stored results.
