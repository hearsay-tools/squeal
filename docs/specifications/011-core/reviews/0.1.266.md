## Blockers

### B1: another worktree's heal makes a held key current

**Proven, blocking.** Changed policy locations: `src/core/scheduler/ledger.ts:684` and `src/core/scheduler/hold.ts:249`. Missed caller: `src/core/scheduler/store-results.ts:40`, especially its `sink.refresh` at line 51.

C9 says: “While the hold holds, a key that names an unmerged path [...] takes no stored result, from this worktree or from other worktrees' keys.” The held file must remain queued. Vision principle 2 requires an honest current state.

The new store view is used only by `Ledger.#refresh`. A FAIL-to-PASS replacement in another worktree also refreshes this worktree, directly through a plain `createStateSink(store)`. That path reads the held key's newly stored pass. It writes a current PASS while the merge row still stands. A queued file row alone does not prevent this: the sink classifies a matching result as current before considering pending phase.

**Regression steps**, based on `merge-hold-fixture.ts` and test 7 of `merge-hold-records.test.ts`:

1. Create `mergeRepo()`. Start main with `holdSide(repo)`, then wait for its baseline to finish.
2. Run the conflicting merge and hand the helper's batch to the scheduler. Write valid resolved bytes, `helperReturning(7)`, to the helper and send that batch too. Do **not** stage it. The index still lists the helper unmerged. Main's importers are queued with no current result.
3. Start the other worktree with `holdSide(repo, repo.other)`. Make its fake runner fail A and B through its `beforeRun` hook. Copy main's resolved helper bytes there and send its batch. It stores FAIL at exactly main's held keys. Assert the keys match.
4. Change only the other runner's outcome knob to pass. Call `other.scheduler.requestFullSuite({ force: true })`, then `idle()`. This models a flaky failure's same-key recovery; there are no conflict markers in these resolved bytes.
5. Read main's hold, file row and known states before any further main batch. Expect the hold to remain, A and B to stay queued, and neither to have a current outcome.

```text

main current outcomes: ["pass"]

```

This is a missing part of the new hold contract, not a separate complaint about the pre-existing healing feature. The worker's notes identify this gap but no spec amendment accepts it.

**One-worker fix:** make the cross-worktree refresh honor the target worktree's merge hold, as well as the ledger refresh. Preserve pending states and suppress transitions for held keys. Keep normal healing for unaffected keys, including unrelated files in the same worktree. Decide the target file's hold in scheduler orchestration before invoking the normal sink; do not change key equality or store a special result. If the repair changes code covered by the validity alarm, supply its discriminating validity case and follow C3; avoiding the alarm is not a reason to leave this caller unsafe. Add the steps above as a permanent regression, with a control that an unaffected file still heals.

### B2: a withheld setup failure makes held importers UNKNOWN and loses their queue

**Proven, blocking.** Fix location: `src/core/scheduler/scheduler.ts:908` to `:962`, where held files enter the requeue set but the report's setup outcomes still pass to `recordTier`. The called setup branch is `src/core/scheduler/tiers.ts:748` to `:755`, then `src/core/scheduler/setup.ts:90`.

R1 test 6 requires: “Nothing is stored for the importers. They stay queued, and no `unknown` follows a second such withhold.” C9 also requires the held queue to resume when the index clears, without another edit.

`heldFiles` adds the affected files to `again`. Their individual store decisions requeue them. But `setups` checks only runtime loss. With an ordinary merge hold it stays true. A `startupFailure` then reaches `failStartup`, which blocks the project's queued files, removes them from the queue and writes a current setup FAIL. The held importers become UNKNOWN after the **first** withheld run. Clearing the index does not unblock them.

**Regression steps**, using the existing files-before-index race test as the starting point:

1. Create `mergeRepo()`, start `holdSide(repo)`, and finish its baseline.
2. Save the fake runner's original `run` method. Wrap the next run so it calls `unmergeIndex(repo.main, HELPER)` after selection. Return a valid `RunReport` with no completed files or results and `startupFailure: { projects: [""], testFiles: files, setupFile: HELPER, error: <setup parse error> }`. This models a global setup, or its dependency, failing on the conflicted path while the index lands after selection.
3. Write changed helper bytes and send its watch batch, so both importers start through the still-clear pre-tier check. Wait for `idle()` after recording. The ending check sees the unmerged helper.
4. Assert both importers remain queued, no setup failure is applied from the held report, and neither importer is UNKNOWN. Assert no result was stored at their run keys.
5. Restore the original runner, stage the helper, wait for the merge row to disappear, then `idle()`. Expect the importers to run without a new edit and become current. Repeat a held setup report to prove it consumes no withhold budget.
