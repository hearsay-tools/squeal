## Should-fix

### S1, proven: the worker's two-paused-daemon limit is incorrect

Location: `tasks/011-49/notes.md:36`.

The notes say two paused daemons can hold the snapshot for `2 x 750 ms`.
`src/core/daemon/ensure.ts:99` returns the recorded socket whenever its ping
is anything except `absent`. A timeout is `unresponsive`, not `absent`, so
the runtime socket is not pinged. The independent two-socket probe confirms
one recorded ping, no runtime ping, and exit after 768 ms from connection.

Fix sized for one worker: correct the notes' known-limit paragraph. Explain
that fallback happens only for an absent recorded socket. No daemon lookup
or product change is needed. This does not break the row's done-when.

## Nits

### N1, proven: the deadline does not settle every sync at that instant

Locations: `src/cli/status-sync.ts:64`, `src/cli/status-sync.ts:165`,
`tasks/011-49/notes.md:21`.

The description says the sync is then `unsupported`. The socket requests
are bounded, but the sleep between sync-status polls is not shortened.
A cheap helper probe used a 300 ms deadline, a 1000 ms poll, and an immediate
pending sync answer. At 400 ms `current()` was still `pending`;
`answered` settled as `unsupported` at 1009 ms. The daemon saw only `ping`
and `sync`, so no request started after the deadline. Load: 6.21, 8.09,
11.21 on 24 CPUs. Candidate sources and worktree stayed unchanged.

Fix sized for one worker: clarify the function comment and notes to say the
next loop step settles `unsupported`; the deadline bounds network requests,
not `answered`. A later consumer that needs settlement at the deadline must
also cap the poll sleep. No change is required for this row: the sleep is
unref'd, and the snapshot reads and ends on its own deadline.

   defaults to infinity, so each request still gets the same 2000 ms timeout.
   Named and edit waits keep their three- and two-argument calls. The snapshot
   calls `options.sync(root, pollMs, sources)` with exactly three arguments

   confirms the unbounded sync remains pending when the bounded one ends.
   New stop checks can suppress a further request after a wait has stopped;
   they do not alter a live wait's outcomes.
3. **Request deadline and honesty, proven for the changed request paths.**
   `syncOnce` checks the remaining budget before lookup and after it, and
   again after each poll. Ping, sync and sync-status use that budget capped
   at 2000 ms. At expiry no further sync request is sent. A late sync or
   sync-status answer no longer holds the process open. Both `pending` and
   `unsupported` fail the snapshot's readiness test: its table has no settle
   fallback. An answer after the bound does not give a verdict. The helper's
   eventual state is qualified by N1; the claimed two-paused limit is false
   as S1 records. The deadline is a socket budget, not a bound on synchronous
   store reads or host scheduling.

   on stop **or** a bound at the snapshot deadline. `requestDaemon` takes no
   abort signal. Keeping `stop()` as a flag leaves the named/edit waits'
   existing socket tail, but leaves no uncovered snapshot case named by this
