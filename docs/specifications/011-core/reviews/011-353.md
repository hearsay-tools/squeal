## Blocker B1: advance discards a crossing inside its timer callback

**Proven.** `test/helpers/virtual-clock.ts:60`, in the new combination of `advance`, `jump` and `CrossingClock.now` (`:156`). W1 requires that the model's `cross`/`uncross` reading jumps move onto the virtual clock. The design requires the same plans and properties. A forward crossing must remain in effect after the decision that reads it; the old `ModelClock.advance` kept that reading.

`advance` captures `until` before invoking callbacks. A callback can read `CrossingClock.now()`, which calls `jump` and moves time past `until`. The final `now = until` then undoes that jump. The clamp before `due.fire()` does not protect the time after that call.

Minimal reproduction using the real wake loop, with imports from the candidate:

```ts
const clock = new CrossingClock();
const start = clock.raw();
const loop = new Wakes(clock);
const fired: unknown[] = [];
loop.slot("yield-bound", at => {
  fired.push(["first", at - start, clock.now() - start]);
}).at(start + 10);
loop.slot("slot-gather", at => {
  fired.push(["second", at - start]);
}).at(start + 30);
clock.cross(1, 60_000);
clock.advance(10);
let rested = false;
void loop.rest().then(() => { rested = true; });
for (let i = 0; i < 3; i++) {
  await new Promise<void>(resolve => setImmediate(resolve));
}
console.log(JSON.stringify({ fired, raw: clock.raw() - start, rested,
  armed: clock.armed,
  wakes: loop.wakes().map(w => ({ ...w, at: w.at - start })) }));
loop.close();
```

Actual output:

```json
{"fired":[["first",10,60010]],"raw":10,"rested":false,"armed":1,"wakes":[{"reason":"slot-gather","at":30}]}
```

The first callback sees the crossing at +60010. The clock then returns to +10. The loop has rearmed the now-due second wake with a zero delay at the crossed time, but the prompt turn finds the clock back at +10 and cannot fire that timer. No later host turn moves virtual time. The gather and `rest()` stay pending until another explicit advance. A simpler probe with the crossing at the first wake's entry also observed a wake reading +60010 followed by a raw reading of +10.

This breaks the new clock's forward-jump semantics and its ability to settle due work. It is not a claim that the passing fixed seeds currently hang: the three inspected prefixes did not show the reversal. It is a concrete failure of the clock on which the model and the new harness option now depend.

**One-worker fix:** preserve a forward jump made during an advancing callback, including a callback reached by the prompt turn. Keep jump callbacks deferred to a host turn. Add regression cases to `model-harness-clock.test.ts` for a crossing inside a fired callback and for the due second wake above; require that the crossing remains, the second wake fires and `rest()` resolves. Scope: `test/helpers/virtual-clock.ts` and that test. No product-code repair is needed.
