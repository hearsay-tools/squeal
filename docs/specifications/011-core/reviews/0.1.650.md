## Blockers

### B1. Proven: a whole-group request is lost from the on-request classification while a narrow ask exists

**Location:** `src/core/state/groups.ts:212` and `:213`, in `onRequestFiles`.

**Contract:** wave 128, contract 1: "`queued` counts only files that will run by themselves." The outcome reserves "on request" for files no request asked to run. The notes explicitly include a whole-group request as queued work.

Reproduction with a manual `browser` group owning A and B:

1. Start `heldSide` with A and B, each importing `src/core.ts`. Edit that source so both files are pending.
2. Call `requestGroupPaths("browser", [A])`. Hold A's runner open using the fixture's gate.
3. While A is running, call `requestGroup("browser")`. This asks the whole group to run, including B.
4. Read `onRequestFiles` with the store's actual keys and the same group policy.
5. Release the gate. Check that B starts without any further request.

Observed output:

```text
activity: running test/browser/a.test.ts
keys: a.test.ts running; b.test.ts queued
onRequest: [test/browser/b.test.ts]
ran-without-another-request: [test/browser/a.test.ts, test/browser/b.test.ts]
expected onRequest [], received [test/browser/b.test.ts]
```

The scheduler's `SlowTier.#trigger` combines `#requested`, commit asks, narrow asks and checkpoint coverage with OR. A narrow ask does not cancel a whole-group request. The reader instead treats the existence of any narrow ask as evidence that the lane cannot have a whole-group request. Its `narrow` condition disables the activity exception and puts B in `onRequest`.

The shared set then makes the headline, tests clause, affected counts, pending lists, registration and news classify automatically runnable B as "on request" and remove it from `Queued:`. Centralizing the set correctly propagates the wrong answer to all these readers. This is a current-state honesty break, not just a missing test.

**Worker-sized fix:** give the shared rule positive evidence of the lane's whole-group request, independent of narrow asks. Publish/read that request state from its scheduler owner rather than infer mutual exclusion from activity. Preserve narrow-only behavior: unasked B remains on request when only A was asked. Add overlap tests in both request orders, through the scheduler and real status formatter; include the kept-header reader so metadata changes with unchanged keys invalidate its part. The existing ownership list needs the scheduler's publication seam added for this repair.

Minimal reconstruction using the existing fixture:
