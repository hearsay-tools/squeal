## Blockers

### B1: the pump prevents rest while a runner is held

**Proven; blocking.** `src/core/scheduler/scheduler.ts:1108` tracks the entire pump, including its waits at line 1122 and the other `#nextEvent()` sites. `src/core/scheduler/wakes.ts:190` refuses rest while that tracked promise is open. Setting the flight's run aside at `scheduler.ts:1246` removes the flight's count, but leaves the pump's count. The pump cannot finish until the runner finishes or an event arrives.

This breaks the design's explicit contract: “a runner's `run` is set aside, so a held run counts as rest and its end does not.” It also prevents rest during a future quiet, capacity or claims wake, when the pump waits with no work it can do now. This blocks row 011-353's move from real-sleep settling to `Scheduler.rest()`.

Reproduction uses the existing `catch-up-fixture.ts`, not a mock scheduler:

1. Make one file `{ path: "test/a.test.ts", ms: 100, imports: ["src/a.ts"] }` with `catchUpRepo` and `catchUpSide`, `hostSlots: 2`, `policy: RUN_MISSING`.
2. Call `side.runner.hold()`, then `await side.scheduler.start()`; wait until `runner.active === 1`.
3. Call `scheduler.rest()`, recording whether it resolves. After 100 ms the value is still false. No release or event occurred.
4. Release the runner and await `scheduler.idle()`. The same rest promise resolves. Output: `heldRest=false, afterRelease=true`.

Worker-sized fix: count the pump's runnable work, excluding its event/time waits, and restore its count before event-driven continuation. Keep runner work, records and queued/running lock work counted. Cover the public scheduler with a held run and a future wake, then release/end the event and prove that its continuation must finish before rest resolves. The existing standalone `Wakes.aside()` test does not exercise the pump and cannot catch this break.

### B2: rearming adds the time already spent in the pass

**Proven; blocking.** `src/core/scheduler/wakes.ts:257` passes the pass-start reading to `#rearm`; line 274 uses that old steady time to compute a relative delay, then line 278 arms the delay after callbacks have finished. Time spent in the callbacks is added to the next owner's wait a second time.

This breaks R1's timing requirement: no wake earlier or later than its owner's old timer beyond the named timing differences, and the row's one timer at the earliest wake. This is separate from Node being unable to run a timer while another callback is busy: after the callback returns, an overdue independent timer can run immediately; this loop schedules another delay.

The probe uses a controllable `Clock` with `now()` and `ticks()` both returning `time`, and `arm(ms, fire)` recording `time + max(0, ms)`. It creates a command-hold wake at 50 and a claims wake at 100. When the first wake fires at 50, its callback moves the clock to 150 to model elapsed synchronous work. No host load is made. The next arm is at **200**, when it must be immediate at **150**. The assertion `expect(armed.at).toBe(150)` receives 200.

Worker-sized fix: retain the pass's single reading for owners, but subtract elapsed steady time when converting the remaining deadline to the next arm's relative delay. Do not reset existing deadlines. Add the probe's case, plus a case where the next deadline remains in the future after the callback. Keep the one-reading and fixed-`now`/virtual-clock behavior intact.

### B3: a policy reload does not update slow-lane wake order

**Proven; blocking on the written-order done-when.** `src/core/scheduler/slow-tier.ts:187` assigns every configured lane rank 0. `src/core/scheduler/wakes.ts:75` then orders equal-time lanes by their immutable creation sequence. A reload can reorder retained groups or insert a new group ahead of them; their slots retain the old order.

The design requires “each slow lane in the configured order (the default `slow` last).” Existing `GroupTiers.lanes(policy)` correctly returns the new policy order; this is a regression in the newly added wake-slot ordering, not a finding against the unchanged group owner.

The probe constructs a real `GroupTiers` with real `SlowTier` objects on a `Wakes(virtualClock())`. Each host's `pump` records its group name. A wrapper around the public `Wakes.slot` captures each lane's slot. It syncs policy `[alpha, beta]`, then `[beta, alpha]`, states all captured lane wakes at 100 and advances to 100. `lanes()` returns `[beta, alpha, slow]`; the wake callbacks run `[alpha, beta, slow]`.

Today the callbacks only ask the pump to run, so the experiment does not prove a changed tier order or user-visible result. It does prove a break of this row's explicit ordering contract, which the later step must be able to rely on.

Worker-sized fix: give retained slots their current configured rank when policy order changes, preserving each lane's state and pending deadline. Keep the default slow lane after every configured lane. Add reorder and insertion-on-reload cases. A repair may need a narrow ownership grant for `group-tiers.ts` to supply the current policy order; do not recreate whole lane owners and lose their state.

## Should-fix

### S1: the promise guard treats a retained variable as evidence of tracking

**Proven guard gap; nonblocking.** `test/scheduler/untracked-promises.test.ts:85` exempts handlers on a promise identifier without checking where that promise is awaited or tracked. The fixture at line 104 explicitly permits `const kept = this.#release("d").catch(() => {})`, although `kept` is never used. Splitting a detached call into `const p = start(); p.catch(report);` also passes this syntax rule. A retained reference alone does not make the scheduler's work visible to `rest()`.

The guard catches the two direct spellings it tests. I found no additional current product call that loses work through this exemption, so this is not another proven scheduler break. The two named exceptions remain justified: the mutex Set deletion is synchronous, and the lint pass owns its separate work.

Worker-sized improvement: add a negative fixture for an assigned-but-unconsumed promise and require an await, return or tracking handoff for locally started work. Preserve handled rejection marks whose underlying promise has an actual consumer. If a syntax-only guard intentionally cannot establish this, name that narrower guarantee rather than treating assignment as proof of ownership.
