## B1: the runner ceiling bypasses the grant's budget

**Proven, blocking, P2.** Location: `src/core/scheduler/tier-width.ts:55`, with the new `budgetAt(grant)` at line 56; `tier-pick.ts:57` and `tier-pass.ts:203` supply the distinct offer and runner width.

Wave 125 W2 requires: "The trim at a grant below the offer uses the grant's share." C4 step 5 now says the same. The guard still requires `grant < Math.min(pick.width, pick.offer)`. A runner's configured `maxWorkers` can make `pick.width` smaller than the pool's offer. A grant equal to that width is below the offer, but bypasses the new budget.

Reproduction through the public tier plan:

1. Use `tableOf` from `test/scheduler/tier-plan-table.ts` with 250 backlog files, each last known to take 2,000 ms, `offer: 3`, `fullWidth: 9`.
2. Set `view.tierWidth = (_, grant) => Math.min(2, Math.max(1, grant))`, the shape of a runner capped at two workers.
3. Call `planTiers(view, asks).first`, then its `width.atGrant(2)`.

Actual output:

```text
offer 3; want 2; grant 2; picked 39; kept 39
wallEstimate(39 * 2000, 2000, 2) = 40000 ms
budgetAt(2) = 120000 * 2 / 9 = 26666.667 ms
```

The grant should retain at most 25 such files: their bound is 26,000 ms. It instead keeps the offer's 40,000 ms tier. With an offer of nine and the same runner cap, this path can keep the whole 120 s budget. This defeats the promised re-pick interval at a narrower grant. The guard predates this range, but the new grant-dependent budget makes its unchanged condition insufficient. The new tests use a runner whose width always equals its grant, so they miss the seam.

One-worker repair: apply the grant's budget whenever a scaled backlog tier's grant is below its offer, including equality with the runner's requested width. Keep the existing runner-width wall estimate, first-round progress and batch behavior. Add the capped-runner case above and retain the existing 9-to-1 and 9-to-3 grant cases. This does not require changing the full-width denominator.

## B2: file completion leaves an old overrun published

**Proven, blocking, P2.** Changed boundary: `src/core/scheduler/tiers.ts:314` records progress, and `src/core/scheduler/overrun.ts:251` can withdraw the report only when checked. The missed caller is `src/core/scheduler/yields.ts:352`.

The amended C4 and C6 require that "a file end withdraws the report" until the tier again has no progress for the threshold. The worker notes assume every queued `file-ended` step calls `Overruns.check`. `yieldReach` actually returns `none` unless the tier has later input changes or stands for a named wait. An ordinary tier meets neither condition.

Reproduction with the existing `hung()` fixture from `test/scheduler/overrun-fixture.ts`, which reports real `RunOptions.fileEnded` callbacks through the fake runner:

1. Hold the edit tier containing H and its three mates, and hold its lane's beside tier. All files have 5 ms last-known durations; there are no later edits or named waits.
2. Advance 60,000 ms and settle. One overrun is published and one beside tier starts.
3. Advance 5,000 ms. Report all three mates ended through the fixture's `end` callback, then settle.
4. Read `overrunsOf(side)` and capture `scheduler.onStep` decisions after the file ends.

Expected: no overrun until 60 s after the last end. Actual: the original overrun remains, still listing H and all three ended mates, with `at = start + 60000` and `laneWaits: either`. The queued step's decisions are `[]`: there is no `check-yields` decision. Both repetitions fail here before any calendar shift. The file-end history write republishes the existing overrun map; it does not recompute it.

Once published, that tier has no pending overrun bound. With both runs held, it need not receive another event that corrects the report. This breaks the row's explicit withdrawal behavior and the vision's requirement that status describe the current state. Before this row, progress did not withdraw an overrun; this range introduces that contract without connecting its event path.

One-worker repair: make a relevant file end reach overrun recomputation under the scheduler's lock, even when the tier has no changed input and no named standing. Use the existing event/check owner rather than a second status-only withdrawal rule. Re-arm the threshold from the new progress, withdraw the published row, and leave the running beside tier alone. Add the sequence above, assert the report returns at last-end plus threshold, and assert no third instance opens. Cover a progressing beside tier as well. Keep existing hold and busy-store rules.

## S1: extra synchronous tree reads need a bounded cost check

**Plausible, nonblocking should-fix.** Locations: `src/core/capacity/pool.ts:454`, `pool.ts:475` and `pool.ts:487`; the reader is `src/core/capacity/cores.ts`, `ProcTreeCpu.read` and its child walk.

It is **proven by source** that a permit-returning shrink or a lease release beside an active tier now synchronously resets and reads the process tree. It walks the daemon's descendant processes and their thread child files, not all host processes. A tail that returns permits at several file ends can repeat this work in a short interval. The more frequent backlog-gate read can also walk the tree once its window is 1 s old. Neither cost was measured independently here.

The benchmark comparison is one run per version on the same Ryzen 9 9950X model:

| --- | --- | --- | --- |
| ref | 78 to 68 | 0.8 to 1.3 | 0 to 2 |
| wt-3 | 70 to 60 | 2.5 to 4.9 | 3 to 7 |
| load-50 | 56 to 64 | 2.4 to 1.3 | 4 to 3 |

All correctness checks passed. No cell fell by the process's 15-point repeat threshold. The base is 0.1.575 rather than the brief's 0.1.572; this isolates these rows from 021-36, which is useful for this review. It is not a last-release comparison.

**The new per-release walk does not directly explain sustained idle CPU after all tiers end.** `#release` deactivates the pool when no tier remains, and no idle timer was added. In raw `ref`, the checkpoint reports all 500 files current, zero running and zero queued before the 60 s idle window. In `wt-3`, the other two daemons are started immediately before that window; their first status counts are still zero, so the window can include startup/listing work. It is not proof of three quiescent daemons. Deferred startup or record work and run-to-run noise remain possible explanations, not established causes.

Follow-up sized for one worker: first count and time tree reads during active permit returns, and distinguish startup/drain from settled idle in a boat.dev comparison when authorized. If repeated synchronous baselines are material, coalesce or otherwise bound that work while retaining the immediate held-worker fallback and a correctly started measurement window. Treat this as a should-fix investigation of active cost. A product optimization, attribution of the idle increase to these walks, and a causal explanation of the long store writes are **unverified**. The current benchmark does not justify an idle-CPU code repair or block this candidate.
