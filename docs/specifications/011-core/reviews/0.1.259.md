## Blockers

### B1, proven: claim recovery stops working once the old heartbeat is stale

Location: `src/harness/shared/ensure.ts:117`, through `asksStepDown` at line 189. Coverage gap: `test/harness/handoff.test.ts:68`.

Row 011-32's done-when says: "past the claim's bound and after a timed-out wait the next boundary spawns". Spec 011 C9 says the claim ends at registration, successor timeout or its bound: "After that, the next boundary claims again."

`handOver` rejects a stale heartbeat before it reads or renews the handoff claim. A stepping daemon stops its heartbeat at shutdown. Its normal 5 s interval therefore expires long before the successor's 120 s wait or the claim's 130 s bound. A boundary then falls back to an ordinary ensure; a stopping socket still answers its ping, so no successor is spawned. This affects both an expired claim and a claim that `lockWaitTimedOut` cleared. The retry tests hide it with a one-hour heartbeat interval.

Probe sequence at one incarnation, with the heartbeat fixed at T and `heartbeatIntervalMs: 5000`:

```text
T: first boundary
  successors: 1
  claim: { from: <old incarnation>, to: "0.1.259", at: T, boundAt: T+130000 }
T+130000: boundary at the expired claim
  successors: 1
  requests so far: ["step-down", "stop"]
  claim still has at: T
T+120001, independent timeout case: clearHandoff, then another boundary
  successors: 1
  requests so far: ["step-down", "stop"]
  claim: null
```

Expected: a second successor call and a fresh claim in each retry case. Observed: neither. This is a break of the row's explicit recovery requirement, not a claim that every normal upgrade fails.

One-worker repair: separate the eligibility for a first step-down from recovery of an existing stopping incarnation. Read the claim/shutdown state before rejecting an old heartbeat; join a live claim and claim/spawn after expiry or timeout while retaining version and session protections and the busy-store fallback. Add both retry tests with a normal 5 s heartbeat that stays stopped. Keep the concurrent six-boundary test.

### B2, proven: a wait reports a stopped daemon during a live handoff

Location: `src/cli/wait-liveness.ts:93`, at the seam with the new `src/core/status/stopping.ts:59`. Callers: `src/cli/status-wait.ts:291` and `src/cli/status-wait-paths.ts:350`.

Spec 011 C9 requires status, a wait and the header to use the stopping reading: "A stopping daemon is neither alive nor down." Before its bound a wait goes on; after the bound it returns without a daemon and names `squeal start`.

The new `withStopping` correctly reads a live claim plus a held lock as a handoff after the old daemon clears its record. `watchDaemon` only receives the nullable record and immediately calls a null record stopped. A wait that polls in this shutdown window therefore returns without waiting for the successor, and its verdict contradicts its own stopping snapshot. This window exists in the real shutdown order: clear record, close store, close socket, then release lock. The successor can also hold the lock while it opens and registers. The new status test covers this window, but the wait tests all retain the old daemon record.

Probe: set a live claim at T with bound T+130000, hold the worktree's daemon lock, clear its daemon record, then read at T+20000. `waitForStatus` used a 200 ms deadline and zero settle time to make its first decision visible; the normal settle time only delays the same decision if the window persists.

Expected: continue waiting through this live handoff, or reach the caller's deadline with a handoff timeout description. Observed: an immediate stopped verdict while the snapshot says an unexpired handoff holds the lock.

One-worker repair: give the wait's liveness decision the same claim/lock-based stopping reading that the status transaction uses, including the record-cleared window. Keep the wait going before that bound; after it, return the handoff reason and recovery command. Add plain and named wait tests that start with or poll across a cleared record and a live claim, then either observe successor registration or expire the bound. A genuinely free lock with no live handoff must still return no-daemon.
