## What fits

### Forced state follows the tier's key or a live strict hold

`Ledger.staysForced(file, key, forced)` (`src/core/scheduler/ledger.ts:543`) requires that the tier entry was forced. It keeps that force at the tier's key, or while `checkpoints.covers([file.ref], true)` still holds the file. A non-strict checkpoint does not extend it. A completed strict file does not extend it either: coverage requires that the file remain in the checkpoint's remaining set.

All changed call sites pass the key captured in the tier entry, not the file's new key: cancel/install requeue (`tiers.ts:665`), not-started files passed to `failStartup` (`tiers.ts:672`), timeout split (`tiers.ts:676`, `timeout-split.ts:11`), and discard (`ledger.ts:529`). The timeout signature and its sole caller agree on argument order. `failStartup` still blocks the project whose setup failed and queues the other projects' not-started files. No new transaction boundary was added.

The helper does not promote an ordinary run to forced. `RunQueue.add` can retain a newer forced request through its existing OR behavior; the changed requeue code does not erase that request. Before the force short-circuit, `settle` still ends a pending automatic rerun whose key moved and releases an agent retry's old-key claim. The old tier can no longer put forced back at the new key without a strict hold. At an unchanged key, a cancelled rerun still skips its own stored failure. This preserves 001-171 and 001-348's distinct purposes.

### Strict checkpoint progress requires its run

The new `strict` branch (`ledger.ts:283`) applies to a file still held strict whose running key differs from its current key. It takes neither a stored-result lookup nor the `resultKey` shortcut. It queues the file forced even when the caller asked only to adopt stored results (`queueMisses: false`). No lookup can count as the strict checkpoint's own tier in this path.

The committed regressions check both relevant orders. A strict run at a key that moves to another stored pass does not advance checkpoint progress at the lookup. It runs again at the new key and completes. A forced file moved while queued starts at that moved key; a revert during its run cannot leave the checkpoint open with no queued work. One forced run at the restored key completes it. The tests check run count, pending phase and checkpoint end, not just a current status header.

A non-strict `run --all` keeps the former lookup at a moved stored key. Its new regression checks completion before the held run is released. The existing 011-118 `checkpoint-lookup.test.ts` checks completion on return to `resultKey`. The strict test does not weaken either non-strict path.
