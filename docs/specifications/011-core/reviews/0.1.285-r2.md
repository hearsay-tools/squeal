**Proven resolved.** `src/core/scheduler/accept.ts:78` now compares `readAt(key, found.keys)`, not just the current key. `readAt` joins the current key and ordered compatibility keys. Real keys are SHA-256 hex strings, so the space separator is unambiguous. The memo is still indexed by test-file identity and records only that file's last read identity. A copy error still leaves it unmarked, because the assignment follows `copyNewest`.

When the shared closure names a branch-only absent path and the own closure removes it, the current key stays equal while the old keys move. The new identity permits the second read. An unchanged list, even in newly allocated arrays and objects, has the same identity and is skipped. Once a row exists at the current key, `acceptedAt` does not enter the compatibility read at all, including for a held foreign failure.

I repeated the original reproduction with the repaired source. The old row's record time is 1,000, outside the 120 s recent-store overlap.
