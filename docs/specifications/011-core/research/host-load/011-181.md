# 011-181: who runs tests outside Squeal on this host, and why

Row 011-181, wave 32 R2 (`../../tasks/wave-32.md`). Transcripts read for 2026-10-23 14:00Z to 2026-10-24 14:00Z; the sampler runs from 2026-10-24 14:06Z for 24 h. Code and docs read at `60bc1a946` (squeal) and cezar `origin/main` `e2882a245`. This session's worktree (`1bf0bde9`) is out of every count. The probe is `../probes/host-load/011-181/`; one line per run is in its `runs-2026-10-24.tsv`.

**Verdict.** Friction with Squeal is almost none of the test load outside Squeal: 3 of 593 runs, 232 of 69,391 wall seconds (0.3%). Three quarters of the wall is load the repositories' own processes require. The largest part is the reviewers' locked full runs: 27 in 24 h, about 1,350 s each, one at a time. The next largest is runs made before Squeal could answer: 326 runs, 18% of the wall. Most of them (213) ran a file at most a minute after the session edited it (146), or in the same command as the edit (67). Squeal's results do not lag on this host; the agents do not wait for them.

## Method

`extract.py` reads each transcript changed since the window's start and keeps the shell commands that start a test runner. It does not count a runner named in a here-document body or in quoted text, but it does count one in an `sh -c '…'` body. It notes the session's last SQUEAL hook message, its last `squeal status`, `why`, `run` or `retry` output, and its last edit (an edit tool, or a command that writes a file). `classify.py` applies the first rule that matches:

1. **Required by the repository's process.** A squeal reviewer's run in the candidate: the reviewer skill bars Squeal's results ("never Squeal's checkpoint in its place"). A squeal coordinator's `key-format.test.ts` with `version-sensitive.test.ts` after integration (`docs/process.md`, "Test runs on a shared host"). A cezar red or green proof in a disposable tree or a scratch `--config` (cezar `AGENTS.md`, "For a source fix" and "For a test-only fix").
2. **Not covered by Squeal.** A tree outside any Squeal worktree (`/tmp`, a mutated copy). A scratch config. `test/e2e` in squeal (`squeal.config.json` excludes it). pytest or `node --test` in squeal (it covers Vitest only). A coverage run. A run that rewrites a baseline (`*_UPDATE=1`). A run that checks process leftovers.
3. **Squeal had no current answer.** The command edits a file before it runs. Or the session edited after Squeal's last statement. Or that statement was not current: pending, stale or unknown checks, or a revision whose runner part was pending. Or the tree is an integration tree that no daemon validates. Or the session stopped Squeal first.
4. **Squeal had an answer, friction.** Squeal's last statement came after the last edit, and it named a current result for the run's files, or said every check was current.
5. **Load made on purpose.** A test run repeated in a loop (timing, flake reproduction, mutation), and every eval subject's run.

Session role comes from the first prompt: the skill (`/worker`, `/reviewer`, `/researcher`), "Coordinate", a coordinator's `t/<id>/int*` tree, cezar's `/dev-flow`, "Fix GitHub issue" or "Handle main CI failure" (worker), and "check-code-quality" (reviewer). Wall is the time from the command to its result; it includes lock waits, and a run in the background gives only the time to start it (5 runs).

## Recommendation for Squeal

1. **Do not build anything against class 4.** Three runs and 232 s in 24 h. Each one re-ran a file Squeal had just reported as failing, to read the failure. `squeal why` already gives that text.
2. **The large lever is the reviewers' full runs, and it is a process choice.** About 10 h a day of a locked `--maxWorkers=4` suite. Two cheaper forms are possible: a reviewer re-review after a repair runs only the files the repair changed, plus CI's full suite; or the locked run uses Squeal's results as a second witness and re-runs only the files whose key changed. Both change the reviewer skill, which is the human's call (the 2026-10-23 decision kept the reviewer's run as one of the two full-suite checks).
3. **Class 3 is about waiting, not lag.** Runs start a median 13 s after the edit, before any runner could answer. A sentence in the worker skill could say that the red step's run is Squeal's edit tier, read with `squeal status --wait 60000 <file>`. That would remove most of 162 duplicates. This is repo-local guidance for the squeal project; cezar's `AGENTS.md` already says it.
