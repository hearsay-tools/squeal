## 1. The 57%

Row 011-395's run A (1,200 files, 1,143 s, 6.0 of 12 busy CPUs) put 57% of Squeal's extra time into the backlog phase, 1,000 s at 6.4 busy cores. It named three causes and could not split them. Here is what the records give for each.

- **Grant width (the D18 ceiling).** Row 021-19 ran the same edit on the same VM four times, alternating `capacity.backgroundShare` 0.75 and 1.0. Share 1.0 finished in 974.5 s against 1,032.9 s, **−5.7%**, six times the spread between repeats. CPU was the same (6,858 against 6,906 CPU-s). Mean busy CPUs were 7.15 against 6.8, and backlog tiers ran 3.7 against 3.5 files at once. Even at 1.0, 5 of 12 CPUs stayed idle on average. *Verified by experiment (021-19); its attribution inferred by 021-19.* So the ceiling explains about 6 points of 011-395's 55% overhead, or roughly one sixth of the backlog phase's idle cores. *Inferred.*
- **Vitest start per tier.** In A the 11 backlog tiers (871 files, 968.6 s of lane wall) had 11.9 s of gaps between them, 0.6 to 1 s each (`results/A.timeline.json`). Each test file runs in its own forked process in both Squeal and a plain run. Squawk's projects keep Vitest's default `forks` pool with `isolate` on, and Vitest 4.1.10 forks one `PoolRunner` per file task and stops it after (`cli-api` `Pool.schedule`, line 3427 onward). So per-file import (790 s of a plain run's 5,890 file-s) is paid per file, not per tier. *Verified by experiment (011-395 records); read in source code.* The fixed work at a run's start (reporters' `onTestRunStart`, coverage start, sequencer sort, `groupSpecs`) and at its end (cache write, coverage generation) falls inside each tier's wall. It was not timed apart. *Read in source code; size not determined.*
- **Waiting for each tier's slowest file.** The backlog tiers ran 2.9 files at once on average (summed file seconds over tier wall; per tier 0.95 to 4.57). Experiment B held 5.1 permits on average over its run (`lslocks`). The tier with 0.95 at once (11 files, 95 s) is one long file holding the lane. A plain `vitest run` of the same files kept (4,869 test s + 1,021 s of import, environment, setup and transform) / 509.5 s = **11.6 of 12** workers busy. *Verified by experiment (records); the comparison inferred.* The gap of about 2 permits out of 5 is barrier tail plus each file's own non-test time plus workers below one core. Splitting it needs `probes/.../workers.mjs`, which counts live fork workers each second. **Not determined, because the lab VM was withdrawn on 2026-11-19.**
- **A large tier budget (arms T and TS).** The 120 s budget is a constant (`backlog.ts:15`, `BACKLOG_TIER_BUDGET_MS`), at most half of `runner.timeoutMs`. `runner.backlogTierSize` caps only the file count. In A only the first 3 of 11 backlog tiers reached 200 files; the 120 s wall budget cut the other 8. A tier's grant is fixed when it starts and only shrinks (`tiers.ts:190`, `:307`). So one large tier would also fix the backlog's width at whatever the pool offered at selection. That cuts barriers but can freeze a narrow grant. *Read in source code; inferred.* Measured: **not determined, because the lab VM was withdrawn on 2026-11-19.** The probe runs it as a VM-only patch of that one constant (README, "The budget patch").
- **Run-loop held.** With an agent mid-turn, squawk's `run-loop` group (`at: pause`) does not run (`slow-trigger.ts` `momentHolds`, `consumersIdle`). So its tiers of 4 add neither CPU nor busy CPUs against the backlog's gate. In A those were 311 of the 1,200 files and 2,230 of 5,097 recorded file-s. Expected direction: the backlog gets a wider grant and its 889 files finish sooner, while the 311 wait for the agent's pause. *Inferred from source and A's records.* Measured: **not determined, because the lab VM was withdrawn on 2026-11-19.**

## 2. Selecting affected tests: the runner part

**Phases, from 011-395's daemon logs** (`results/A.timeline.json`, `B.timeline.json`; Squeal logs every store write lock held over about 250 ms with its caller and row count). *Verified by experiment.*

| Revision | Content re-key (`reconcileBatch`, lock held) | No lock: invalidate, affected, closures, edit cut | Closures applied (`storeClosures < applyRunnerPart`, lock held) | First tier |
|---|---|---|---|---|
| A, 1,297 files, warm daemon | 864 ms, 37,615 rows, at 1.1 s | 1.4 to 21.4 s | 1,004 ms, 5,172 rows, ends 22.4 s | 22.5 s |
| B edit 1, same, freshly started daemon | 982 ms, 42,135 rows | 1.4 to 44 s | 1,012 ms, 6,166 rows, ends 45.0 s | 45.6 s |
| B edit 3, same file again, beside tiers | 868 ms, 25,293 rows, at 601.2 s; a 229 ms last-resort GC at 602.8 s (heap 1,834 MiB) | 601.6 to 622.2 s | 1,027 ms, 5,172 rows, ends 623.2 s | 623.8 s |
| B edit 2, one test file, beside a backlog tier at load about 7 | 344 ms, 393 rows | to about 9.6 s | not logged (under 250 ms) | 9.6 s |

**What runs in the 20 s.** `fetchRunnerPart` (`refinement.ts:89-206`) calls `runner.invalidate`, `affected` (or the stored import graph, row 021-30), then **one `runner.closure(ref)` per re-resolved file, in a `for … await` loop** (`refinement.ts:169-177`), then the edit cut. The re-resolved files are every file whose content key moved, plus the affected set. Each closure call crosses to the runner host and runs through `#part` (`adapter.ts:370`). The runner host has one call at a time in its "part" lane, beside the "run" lane in the same process (`gate.ts:12-15`). So under a running tier, closure calls share one event loop with the tier's Vite transforms. Each call walks the file's import graph (`importClosure`), its resolution inputs, module globs and per-file import hashes (`adapter.ts:540-574`). *Read in source code.* No tier starts until the runner part is applied (`runner-work.ts:53`, "no tier is selected while any is left").

**What grows with files, what is fixed.** *Inferred from the table and the E4 runs; the split inside the unlocked part is not determined.*

- Grows: the closure calls. 20 s for 1,297 files is **about 15 ms a file** on a warm daemon. A freshly started daemon took 43 s, **about 33 ms a file**. The likely cause is a cold Vite module graph in a fresh runner host. Row 011-394's E4b, on the same repository on a quiet VM with no run open, refined revisions of three edited files one after the other every **20 to 22 s** (revision 3 at 22 s, then 4 at 07:22:43, 5 at 07:23:05, … 13 at 07:25:53), with 774 files queued. The closure store write grows with files (about 4 rows a file) but stays at 1 s.
- Fixed per revision: the content re-key (0.3 to 1.0 s; its rows follow the worktree's key count), `affected`, the edit cut, the apply. Bounded by the small revisions: one central edit with 105 files queued was refined within **6 s** (E4, revision 1 at 07:19:42, refined by the 07:19:48 sample), and one test file took **9.6 s** beside a running tier.
- **"Listing about 21 s per revision" is not a listing.** `testFiles` (Vitest's `globTestSpecifications`) runs only for a revision that adds or deletes a path, after a recreate, or after a failed listing (`refinement.ts:129-132`). E4b's edits added nothing, so its 21 s per revision is the closure loop above, repeated for every revision of the stream. *Read in source code; E4b verified by experiment.* No record times a real listing: **not determined, because the lab VM was withdrawn on 2026-11-19.**
- **A restart is much faster.** In E4c the daemon was stopped mid-stream with revision 14 of 22 refined. The new daemon refined revision 23 (765 queued) **within about 5 s of its start** (07:26:18 start, refined by the 07:26:23 sample). That is a quarter of one in-stream revision. Whether it fetched fewer closures (a catch-up revision, or the stored graph answering), or the same closures faster, is **not determined**. The CPU profile of `q2.sh` would show it. *Verified by experiment (E4c); the cause not determined.*

## 3. One Vitest, many workers

What Vitest 4.1.10 allows, *read in source code* (`dist/chunks/cli-api.BK8pd4xc.js`):

- **No barrier inside a run.** `executeTests` queues every file task of a group at once, and each finished task calls `this.schedule()`, which takes `this.queue.shift()` for the freed worker (line 3427). The order comes from `sequence.sequencer` (`BaseSequencer.sort`: longest and failed first). Between `sequence.groupOrder` groups there is a barrier.
- **Width is fixed for a run.** `groupSpecs` reads `resolveMaxWorkers(project)` (line 3765: `project.config.maxWorkers`, else `vitest.config.maxWorkers`) and calls `pool.setMaxWorkers` once per group (line 3696). Changing the config between runs takes effect at the next run; Squeal relies on this (`src/runners/vitest/width.ts:146-155`). Nothing changes it during a run. The `Pool` lives inside `createPool`, whose returned object has only `name`, `runTests`, `collectTests` and `close`.
- **Files cannot be added to a run.** `runFiles` does `await this.runningPromise` and then sets a new one (lines 13576-13582). A second `runTestSpecifications` waits behind the first run; it is neither merged nor refused. Reporters' `onTestRunStart` and coverage's `onTestRunStart` fire before that wait, so during the earlier run.
- **Cancel keeps the instance.** `cancelCurrentRun` (line 13731) cancels the pool's queued tasks and awaits the run; `this.pool` stays and the next run resets the flag. Squeal keeps one instance across tiers (`adapter.ts:84`, `:384-404`).

So "one long-lived run whose `maxWorkers` follows the grant, fed files as workers free" cannot be built on the public API of 4.1.10. Inside one run, the dispatch it wants already exists. Two ways need neither Vitest internals nor a new API: a run started at a fixed width and never resized, or runs restarted at each grant change, which are today's tiers. *Inferred from the source above.*

How much a barrier-free run would clear faster: the plain run of A's 1,192 files kept 11.6 of 12 workers busy at 12 workers (509.5 s). Squeal's backlog tiers ran 2.9 files at once on 5.1 permits held. At equal width, the gap between those two use rates is the upper bound of what removing barriers can return. The long run at the grant width that would measure it: **not determined, because the lab VM was withdrawn on 2026-11-19** (`plainw.sh`).

## 4. A cap on measured CPU across daemons

**The rule today** (0.1.563), *read in source code*:

- **Backlog tiers.** A permit is taken only while `max(Σ marks' cores + own, host busy CPUs) < min(hostSlots, ceiling)`, one core added per permit taken (`cores.ts` `gatedPermits`, `gatedCores`). The marks' cores are each daemon's measured process tree; the host's busy CPUs come from `/proc/stat` and include other users' work (`pool.ts` `#busy`, rows 011-98, 011-182, 021-18). On top of that comes each daemon's max-min fair share of `hostSlots` (`share.ts` `fairShares`) and the count of `hostSlots` permit lock files. So the backlog is already gated on measured total CPU. The slots add a per-daemon division and a count cap.
- **Checkpoint tiers** (`run --all`): cores below `hostSlots`, or grants below half of them. **Edit tiers** take no permit; their CPU counts only in the marks (`pool.ts` `running`).

**Where it can overshoot the machine:** a grant is fixed for its tier's life and only shrinks at the tail (`tiers.ts:307`). A permit not yet measured counts 1 core. Marks refresh every 10 s (`MARK_REFRESH_MS` = 30 s / 3). Edit tiers are not gated. The floor gives one background tier its fewest workers even above the bar. **Where it can under-use:** a permit counts one core, while fewer files ran at once than permits were held (011-395: 2.9 files at once on 5.1 permits; 021-19: 3.5 to 3.7 files at once with 6.8 to 7.15 busy CPUs, the daemon's 0.75 included). One daemon's tier tail keeps its lane waiting, even though the tail permits go back to the pool for other daemons. And a slot setting below the ceiling turns into a busy-CPU bar. *Read in source code; the use figures verified by experiment (011-395 and 021-19 records).*

**Recorded evidence of under-use.** On this host the user config `hostSlots` 6 made `min(6, 18)` the bar for 4.5 days. Background work was held 205 daemon-hours, **137 of them while the host was below 18 busy CPUs**. Backlog p90 was 66 min, against 40 min replayed for a bar of 18. The host's time above 20 busy CPUs barely moved (11.4% to 10.3%), because other load alone made those samples. *Verified by experiment (021-19 records), attribution inferred by 021-19.* That is one daemon population on one host. It does not compare the two rules.

**Two and three daemons, slot rule against CPU cap:** throughput, overshoot (time at or above 11.5 busy CPUs, runnable tasks above 12) and under-use (idle cores while files wait) are **not determined, because the lab VM was withdrawn on 2026-11-19**. `q4.sh` runs it: the slot rule with `hostSlots` 11 and share 1.0, and a CPU cap with `hostSlots` 48 and share 0.92, which is 11 busy CPUs.

## Recommendation for Squeal

Inferred. For the coordinator to design from; nothing here is a design.

1. **Re-run the probes when a quiet machine is available**, in this order of value for VM time: the question 2 profile (`q2.sh`, about 10 min), arm T against H0 (question 1, about 35 min), the long run (question 3, about 20 min), then the daemon pairs and triples (question 4, about 35 min).
2. **The runner part is a per-file loop, and an edit stream pays it per revision.** About 20 of a broad edit's 22.5 s is one closure round trip per re-resolved file. Store writes add 2 s. An edit stream repeats the whole loop for each revision (E4b: 13 revisions in 4 min, 20 to 22 s each, no tier meanwhile). A restart refined the newest revision in 5 s, so fewer or cheaper closure calls are possible on this repository. That is where the selection time goes. *Inferred.*
3. **Of the idle CPU, the ceiling is the smaller part.** Share 1.0 returned about 6% of the wall time and no CPU. Gaps between tiers cost about 1%. The larger part is inside the tiers: 2.9 files running on about 5 permits, against 11.6 of 12 in one plain run. Barrier tail and the one-core-per-permit count are the candidates. Their split needs the worker sampler. *Inferred.*
4. **Vitest 4.1.10 fixes a run's width and file list at its start.** A design that wants no barrier and a moving width must either run at a fixed width or depend on Vitest internals. *Read in source code.*
