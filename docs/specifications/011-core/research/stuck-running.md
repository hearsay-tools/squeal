# Research 011-394: why a test file stays "running" and focused requests wait until a restart

The three stall shapes do not share one cause. Two mechanisms carry most of them. First, one hung or slow test file holds its whole Vitest tier and lane. After one yield it can no longer yield, so only the run timeout ends it (900 s per round in the reporters' repository). Second, a stream of edits has every revision listed in turn, at about 21 s each on squawk's repository, and no tier starts meanwhile. Both mechanisms keep their state in daemon memory or in the runner host, so a restart clears them. Three smaller defects and gaps add to the delay: a `run <group> <path>` request does not move a known queued file ahead, a worktree-wide "not listed" condition returns exit 3, and status gives no "stuck" signal. The cross-worktree claim wait of #179 was **not reproduced** on 0.1.563 in four attempts.

| 1 | Shape 1, a file stays "running": state and what a restart clears | The file sits in a tier with a hung file. The whole tier stays `running` until the run ends; the lane runs nothing else. A yield ends the tier 30 s past its estimate, but only when promoted work or an edit's work waits. Once cut, a file's next tier never yields (`decide-yields.ts:226-227`), so `runner.timeoutMs` ends it. A timed-out tier splits in halves and re-runs. A restart kills the runner host, drops the in-memory cut marks and re-queues the `running` rows (`daemon.ts:546`). A deterministic hang re-hangs in the new run. | verified by experiment (E1, E1b, E2) and read in source code, 0.1.563 |
| 1 | Shape 2, focused requests expire while a revision is listed | (a) No tier starts while runner work is queued, promoted or not (`step.ts:233-237`). Every revision's listing is queued and done in turn, each with one closure call per re-keyed file (`refinement.ts:168-177`, `runner-work.ts:265-271`). On squawk's repository, an edit every 3 s for 60 s made 20 revisions. They were listed at about 21 s each, with no tier for over 4 min while 774 files waited. One edit alone listed within 16 s. A restart lists only the newest revision, in 5 s. (b) `run <group> <path>` on a known, already-queued file leaves it in its queue place and says "which run now": no run in 80 s while ~800 others ran. (c) "each of its calls bounded at 966 s" is fixed text; 966 = `runner.timeoutMs` 900 s + 66 s. (d) "what holds it is unknown" means the scheduler lock was free, as it is during the listing's runner phase. | (a) verified by experiment (E4, E4b, E4c) and read in source code; (b) verified by experiment (E1, E1b) and source; (c, d) read in source code |
| 1 | Shape 3, a wait on another worktree's run, and #232 | A claim is another worktree's `running` row with a heartbeat at most 10 s old. The requester waits at most `timeoutMs` + 6 s from its first sight, which only daemon memory keeps. A requester restart starts that bound again. Status recomputes "at most until" as now + bound on each read and reads the claim from the store, so it can name a claim the daemon no longer waits on. In four attempts (an edit's work, a 12-path catch-up revision, a restart, a narrow ask after a missed edit), B ran the key at once beside A's live `running` row. The `run` non-promotion and the worktree-wide exit 3 are separate code paths. | inferred from the experiments and source |
| 3 | What can Squeal know at the time? | The file's past duration and its tier's estimate (E1b: 0.2 s estimated, 121 s run, about 600×). Whether a yield is still possible: known in memory, not said. The run deadline: known, not said. Heartbeat age: a stopped daemon read "heartbeat is late" when sampled at 77 s, and a killed one still reads "alive" for 6–8 s. ## Experiments

Probe: [`probes/stuck-running/`](probes/stuck-running/README.md). Fixture `syn`: 1,200 Vitest files that import `src/shared.ts` and sleep 60 ms, plus `test/hang.test.ts`, which blocks its worker in `Atomics.wait` while `hang.on` exists. No CPU is used, and Vitest's test timeout cannot stop it, just as it cannot stop a synchronous loop. `runner.timeoutMs` is **120 s** there, scaled down from 900 s. Tiers hold 4 files, with 4 workers. Baseline: `run --all`, 1,201 files in 69.5 s, at load 0.3.

**E1, shape 1 with a named wait** (load 1.8–3.1). One edit re-keyed 1,201 files; edit tiers of 4 ran about 12 files/s. The hung file read `in the vitest tier of 4 test files running since …, 1 of them ended`. A `status --wait 60000` on another file promoted it. The hung tier yielded 31 s into its run ("to a promoted file; 30 s past its estimate"), and the named file passed after 12.5 s. `squeal run tests test/gen/f0009.test.ts --wait 60000` answered "1 queued, which run now" and then exited 3 after 60.2 s. f0009 never ran before the daemon stopped 80 s later, while the done count rose from 32 to 824. A new test file was listed within about 1 s and ran at once. `status --wait 1000` on a current file exited 0. After `stop` and `start` with the marker still present, the new daemon ran the hung file in a new tier, which hung again.

**E1b, shape 1 with nothing promoted** (load 4.8–7.7, from 011-395). The hung tier of 4 ran 48 s. It yielded only when a new test file arrived ("to an edit's work"). The hung file then ran alone from 06:52:01 and **timed out at 121.1 s**; its result became `unknown`, "timed out after 120 s". For those 121 s the lane started nothing: 1,198 files stayed queued, the new file waited the full 121 s, and `run tests f0011 --wait 60000` exited 3. Revision 6 was listed at once (`runnerPartPending: false`), so this hang did not block listing. Status meanwhile said only `running since 07:52:01 in the vitest lane; a yield at 07:52:00 cut 1 file after 48 s …`. It named no estimate, no deadline, and nothing about yields being over.

**E2, shape 1, daemon lifecycle** (load 5.1–9.4). After `SIGSTOP` for 75 s, status said: "the daemon's heartbeat is late: the last one was 1 min 17 s ago …; the daemon may be busy or stopped". The file read `running in the vitest lane`, with no start time. After `SIGKILL`, for 6–8 s status said the daemon was alive and the file was "in the vitest tier … running since". The runner host and its workers exited with the daemon, so no process was left. The killed daemon's run row stays open in `runs` (`ended_at` null) and is ignored by status. `start` re-queued and re-ran the tier.

**E3–E3d, shape 3** (load 2.4–9.5). A's hung tier held `hang.test.ts` at key K; its four rows read `running` in the store. B reached K in four ways: an edit while live (E3b), 12 keyed paths in one revision (E3c), restarts of B (E3b, E3c), and an edit missed while stopped followed by `run tests` (E3d). Each time, B ran K within 1–5 s and stored a pass. No claim wait occurred. E3 found something else: an edit made while B's daemon was stopped left the file `stale, nothing queued it (the baseline is lookup-only)` after `start`, and only an explicit request ran it.

**E4 to E4c, shape 2 on the real fixture** (squawk's repository at `c11e4edf`, 1,931 test files; load 1.0–2.4, with 011-395 idle).
- **E4:** on a fresh store, a lookup-only start took 41.2 s. One comment appended to `packages/contract/src/index.ts` was listed within 16 s (not yet at 5 s). `run tests` for `packages/cezar/src/delegation/settled-observation.test.ts` (a file from #181; on this fresh store it had no result yet) then passed in 4.9 s. **One large edit lists quickly.** Limit: with no stored results, the edit queued only the 97–105 files that the edit cut keeps, not about 1,300.
- **E4b, an agent-like stream:** 20 edits to two central modules, one every 3 s for 60 s, made revisions 3 to 22. The daemon listed them **one at a time, about 21 s each** (listed revision 3 at 07:22:21, 4 at :43, 5 at 07:23:05, … 10 at 07:24:52). No run was open and the 774 queued files waited throughout. `status --wait 60000` on that file during the stream and `status --wait 180000` after it both exited 3, with the incident's exact words: `revision 22 is not listed yet (774 test files queued): … it waits for the run in flight, each of its calls bounded at 966 s`. No run was in flight. When the daemon stopped, 4 min 11 s after the first edit, revision 14 was the last one listed.
- **E4c, restart:** `start` on that store listed the latest revision (23, the revert) **within 5 s**. It did not list revisions 14 to 22 one by one. The named file had its verdict after 42.4 s. Without the restart, the nine unlisted revisions alone would have taken about 3 min more at the measured rate.

So the shape-2 waits do not need a slow test. Each revision of a stream of edits is listed in turn, at full cost, and no tier starts until the newest is listed (`runner-work.ts:265-271`, `step.ts:233-237`). A restart replaces the queue with one listing of the newest revision. The "(run …)" words are fixed text (`next-step.ts:286`).

## What a restart clears (shapes 1–3)

**Read in source code, 0.1.563.** Memory only: the cut marks and yield history (`yields.ts:120-128`, `yield-history.ts:1-9`), the runner-work queue and `#refining` (`runner-work.ts:54-58`), queue order and promotions, run requests, and claim first-sight (`claims.ts:34`). In the runner host: the hung Vitest instance and its workers, which die with the daemon (E2). In the store, but trusted only from the live daemon's start: open runs, published yields, quiet waits and pool waits. In the store and lasting across a restart: `running` rows, which the next start sets to `queued` (`daemon.ts:546`), and an unlisted revision, which the next start lists again. A restart therefore ends any stall whose holder is the current Vitest instance or in-memory state. It does not end a test that hangs every time (E1 stage D). After a restart, a queued file can read "queued; no run is open and nothing recorded holds it" until the new daemon publishes its own waits (`standing.ts:133-145`).

## Bounds the reporters' settings give (inferred from source, not run at 900 s)

With `runner.timeoutMs: 900000` (squawk's `squeal.config.json`), one round of a hung tier lasts 900 s plus at most 6.5 s of cancel graces (`run.ts:96-138`). The host's own deadline is 1,200 s (`proxy.ts:73-76,255-257`). A timed-out tier re-queues its unfinished files with `cap = max(1, floor(incomplete/2))` (`store-decision.ts:85-94`). An edit tier of 4 with one hung file therefore costs 1 round when its three mates end (E1b), or 2 rounds at 15 min each. A 200-file backlog tier can split 8 times (200, 100, … 1). That gives up to 2 h, with the hung file `running` throughout. The reported 10–53 min fits one to three rounds. The claim bound is 906 s; listing calls are bounded at 966 s each, with no total.

## Recommendation for Squeal (evidence, not design)

The design should weigh:
- A tier that cannot yield and runs far past its estimate. E1b measured 600× the estimate with no word in status. Squeal knows the estimate, the cut mark and the deadline at that moment.
- `run <group> <path>` saying "which run now" while it does not reorder (E1, E1b).
- Listing every revision of an edit stream in turn, which blocks every tier until the newest is listed (E4b). A restart lists only the newest (E4c).
- Exit 3 from a worktree-wide "not listed" condition when every named file is current (#232).
- The claim text, which reads the store and not the waiting daemon.

Measure duration overrun against the per-file estimate, not the tier's, since a tier's estimate covers its mates. A slow test and a hung one differ by the worker's CPU only for a blocked hang. A busy-loop hang was not measured.

## Open questions

- What makes a real squawk test hang under Squeal and not in plain Vitest? Not determined, because the incident workload (four worktrees, run-loop tests that kill process groups) was not replayed, and no incident left a run log or process tree.
- Why B never waited on A's live claim (E3–E3d)? `claimOf` and `peekClaim` exempt only forced and edit-recent files (`claims.ts:141-182`). Not determined in the time budget. Compare the 0.1.430 scheduler-level reproduction in [issue-179.md](issue-179.md).
- Whether a hung run blocks listing when the listing needs a recreate (`gate.ts:43-62`, `adapter.ts:489-494`)? Not exercised: E1b's listing needed no recreate.
- The ended count read "1 of them ended" for 48 s in a 4-file tier whose 3 other files take 60 ms each. Not explained.
