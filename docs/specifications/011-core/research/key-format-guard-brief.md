# Research brief: when should a check key change across releases?

Use /researcher. Shape: research, read-only on the product. Decided by the human on 2026-10-20: "We need to have a way to determine if the key should change or not. Imagine real users who have to re-run everything every time we make a minor improvement. It will kill this project's purpose." Today `KEY_FORMAT_VERSION` was raised at 0.1.222, 0.1.223, 0.1.224, 0.1.225 and 0.1.226, and each raise re-keys every check in every worktree.

Read first: 011 C3, the "Key format version" bullet (tasks 001-199, 001-203); `src/core/keys/key-format.ts`; `test/keys/key-format.test.ts` and `test/keys/key-sources.ts` (what is guarded, what is exempt and why); the adapter versions (`src/runners/*/version.ts`, 011 C14/D4); `../../001-core-loop/research/fresh-worktree-reuse.md`; `research/issue-47.md` finding on the key format moving between releases.

Questions, each tagged (`verified by experiment`, `read in source code`, `read in official docs`, `inferred`):

1. **History.** For each raise from 10 to 17, sort the guarded diff that forced it into: (a) changes what a key is computed from or how; (b) changes what a stored result means or whether one is accepted (the stability check, withheld runs, store rows); (c) neither (ordering, tiers, lifecycle, handoff, wording, comments). Give the files and counts. How many raises had any (a) or (b)?
2. **The path that decides validity.** Map the code from inputs to key to stored row to lookup to "accepted". Which modules are on it, and is that set separable from the scheduler and daemon code around it? What would move to make it so?
3. **Mechanisms.** Compare, each with what it catches and what it misses: (a) a guard over a computed import closure of the key and acceptance entry points instead of all of `src/`; (b) golden keys: fixed fixture repositories whose computed keys and accept/reject decisions are pinned, so a raise follows from changed output, not changed source; (c) per-component format versions like the adapters'; (d) reading results stored under an older format when that format's key code is unchanged; (e) combinations. Prior art in official docs: Bazel's action cache key, Gradle's build cache key, Turborepo and Nx hashes, Jest's transform cache key, ccache: does each include the tool's own version, and how do they avoid invalidating on their own upgrades?
4. **Safety.** For the recommended mechanism, which change could still trust a stale result, and which test would catch it.
5. **Effect.** Under the recommendation, how many of the raises from 10 to 17 would have happened?

Own only `research/key-format-guard.md` and throwaway probes under `research/probes/key-format-guard/`. Edit no board, spec, status, test or product file. Experiments (computing a closure, keys over a fixture) run in a throwaway `git worktree` under `/tmp` at a SHA, with `HOME` and `XDG_*` there, only while the one-minute load is below the CPU count; no full suite, no build. Done when the findings answer the five questions with tags, name the mechanism the evidence favours with its numbers, and state the limits; commit. Budget: about ninety minutes; then write what you have.
