# What the intermittent CI failures have in common (row 011-428)

Researcher, 2026-11-27, wave 129. Brief: `../tasks/wave-129.md`. Squeal at `5fca81f09`. Research only. Probes and data: [`probes/ci-flake-census/`](probes/ci-flake-census/README.md).

**Recommendation.** Two test-side rules remove most of the re-runs: a test never asserts wall-clock or CPU time on the shared runner (G1), and a test never acts on the first sign that a process is ready (G2). Together they cover 132 of the 189 runs with an intermittent failure, and 33 of the 55 main runs that needed a re-run had no other cause. Three product repairs follow: the Pi and OpenCode waits re-arm after a deadline miss (G5), a hook stores its handover claim before it says "claimed" (G6), and the store process handles SIGTERM before it prints `serving` (G2, reproduced).

## Census

`gh run list --workflow ci.yml` from 2026-10-27 00:08Z to 2026-11-27 18:39Z on `main` and `cand/**`: 1,230 runs, 1,156 of them completed (575 main pushes, 550 candidate pushes, 31 nightlies). The 334 runs started at 2026-11-17 11:24Z are left out: a re-run of old branches, all red. 318 completed runs had a failed job; 472 failed jobs in all, read through their check-run annotations (`census.csv`).

A failure counts as intermittent when the same job passed on the same commit (149 test failures in 105 runs), when the same test has such a pass elsewhere in the window, or when a board row names it. Runs where three or more jobs failed with no same-commit pass are left out as real breakage (23 runs, for example `cand/0.1.600` 45070829138 with 10 files over 6 jobs), except runs a board row cites.

**Release friction.** 55 of 575 main runs (9.6 per 100) went green only on a re-run of the failed jobs; 48 of 550 candidate runs did the same. Every release waits on green exact-main CI, so each of those 55 cost one re-run before a release could use that commit.

Rates are runs with a sighting per 100 completed runs. Node 22 runs the whole suite on every push; Node 24 and 26 run only the version-sensitive files per push and the whole suite nightly, so the Node split below is not a per-version rate.

## Findings per group

**G1, time on a shared runner.** The bounds are of four kinds. (a) CPU of the longest main-thread turn, which counts garbage collection: `writer-turns.test.ts:76` (under half a `JSON.parse` taken just before, whose garbage is collected inside the window) and `chain-load.test.ts:225` (250 ms; the only `process.env.CI` scaling, `:55`); both through `test/code/coverage/turns.ts:14,20` and `test/code/pass/turns.ts:42,47`. (b) Wall time against a constant: `keep-early.test.ts:98` (2,600 ms), `busy-requests.test.ts:83` (750 ms gap), `departure.test.ts:181` (3,000 ms, includes Vitest teardown), `backlog-slots.test.ts:118,120,209`, `prune-vacuum.test.ts:82` (300 ms a slice), `ci-map-client-clock.test.ts:76`, `graph-cost.test.ts:149` (a wall ratio under 1, beside work counts at `:141-147` that already prove the claim). (c) Vitest's 5 s default over real work: `retry/records.test.ts:127` makes 1,025 transactions, each rewriting the whole list; `not-current` and `why-unknown-standing` are synchronous SQLite work. (d) Short waits against a cold `tsx` start or a product deadline: `status-paths.test.ts:156` (the CLI's 750 ms settle, `src/cli/wait/status-table.ts:31`), `status-at-now-daemon.test.ts:160` (3 s since `a7f4c980b`, all 7 sightings after it), `warmup.test.ts:220` (`maxDeferMs: 6000`), `status-wait-paused` and `run-group`, `stop-slow-wait`, `stop-group-mixed` (policy `slowWaitMs` 5,000 equals Vitest's timeout), `environment-growth-siblings.test.ts:152` (shortest-first order learned from real durations). `slow-node-test` is placed here **inferred**: a slow file ran inside the turn (`test/e2e/slow-shape.ts:120,127`); not read to the line.

The shared amplifier is the machine, not one helper: `scripts/ci-shard.mjs:186` runs Vitest with its default workers on 4 vCPUs, and the load gate `LOADED = loadavg()[0] > 8` (`test/daemon/helpers.ts:48`) is read once and not scaled by CPU count, so on 4 vCPUs it skips only at twice saturation. Main CI 45710459569 (row ci-45710459569) shows one stall, not five bad bounds: backlog-slots twice, stop-slow-wait twice, stop-group-mixed three times and hung-daemon's 120 s wait failed in one job; three more jobs paired two G1 files each (`groups.txt`). Repaired in the window and quiet since: `daemon/lifecycle` (`3eff92c8f`), `backlog-tiers` (`c7e13fca2`), `wait-stale-start` (`17f51c374`), `wait-reads` (`97200af06`), `lanes-stored-rerun` (`69864034f`). Raising a bound moved these failures; it did not remove them (writer-turns failed at 117, 235, 183, 257, 119, 320 and 131 ms against 100).

**G2, readiness before state.** **verified by experiment** for ci-46051074967, Node 26.13.0 and 22.19.0: `src/core/store-process/server.ts:245` writes `store process: serving` inside `startStoreProcess`; `src/cli/store-process.ts:49` registers the SIGTERM handler only after that promise resolves. The test sends SIGTERM as soon as the line shows (`test/store-process/logs.test.ts:126`). With the store process's main thread held 1.5 s right after the line, SIGTERM kills it by the default action and the log holds only the `serving` line, the CI symptom; SIGTERM 1 s later, or at once without the hold, gives the `stopping (stopped)` line (`probes/ci-flake-census/store-process-sigterm/output.txt`). This one is a product order: the process says it serves before it can stop cleanly.

The rest are test-side, **read in source code**: `hand-off.test.ts:159` polls `existsSync(marker)` but the child's `writeFileSync` creates the file before it writes; `test_hang.py:10-13` (pyrun, row ci-43589305691 item 2) writes its pid in two steps, and `Number("")` gives pid 0, which `kill(0, 0)` always finds alive; `stop-at.test.ts:130` checks a killed child before it is reaped; `handover.test.ts:124` counts a forked child that still shows the successor's command line; `handover-gap.test.ts:44` and the keeper tests read `/proc/locks` once, which the product's own comment says can miss a moving lock (`src/core/store/lock-holders.ts:46-50`); `code/store.test.ts:163`'s lock holder commits with no busy timeout; `seed-failed.test.ts:122`, `group-lanes-moments.test.ts:113` and `tier-yields-overrun.test.ts:249` read state after an idle point that counts runner calls, not row writes. Repaired in the window: `handover-batches` (`c3f73a9b2`, the largest, 16 sightings), `ci-record` (`e12ee8b48`), `keep-busy`/`keep-daemon` (`3f22e3cc6`), `scratch-identity` (`32492e1a9`), `low-priority` (`e22c75649`, row 011-409). `optimizer-start.test.ts:170` stays **not determined**: `36c776cdf` made the shim's claim atomic, yet two sightings on 2026-11-26 still show a second append; the next step is a shim that logs each call's pid and arguments.

**G3, removal beside a live writer.** `removeTree` (`test/helpers/remove-tree.ts:35`) and `awaitGroups` (`test/helpers/process-groups.ts:152`) from row 011-336 exist, but three call sites use them. `launcher-one-node`'s cleanup (`test/harness/bundle-helpers.ts:165-169`) has no retry; the daemon's store process is detached in its own group (`src/core/store-process/spawn.ts:48-50`), lives up to its grace, and `squeal stop` does not wait for it (`src/cli/stop.ts:117-118`); **inferred** as the late writer. `stopStrays` (`test/daemon/helpers.ts:365-378`) already waits for daemons, hosts and store processes, but only daemon tests use it. 28 of 33 failed tests are on Node 22, as `enotempty-cleanup.md` finding 1 predicts.

**G4, the busy loop.** The fixture loops forever with no timeout (`test/fixtures/node-test/edge/test/busy-loop.test.ts:3-5`). The product marks a stream the signal made as `signalled` (`src/runners/node-test/run.ts:108-113,231,263,392`); the premise check reads only `completed` (`test/runners/node-test/run.test.ts:56-73`, asserted at `:123,163`), and `fixtures.test.ts:206` expects no `test:complete` for the busy loop. A test assumption, not a product defect. 9 of 15 failed tests on Node 26; 9 runs in the last 7 days.

**G5, a deadline miss that drops news.** `src/harness/pi/extension.ts:151` still returns on `text === null` without re-arming; row 009-30 landed diagnostics only. OpenCode's idle bridge has `stop.waitMs + 500 ms` (`src/harness/opencode/hooks.ts:15,127-129`); `turns.ts:231` returns on a `null` answer. Pi's `tool_call` gate misses its 2,000 ms deadline and lets the edit through (`extension.ts:8,218-224`; row ci-43528167215). `integration/node-test.test.ts:209,286`: the hook prints nothing when the store stays busy past `STATUS_BUSY_TIMEOUT_MS = 1_000` (`src/core/status/open.ts:14`, `src/harness/shared/context.ts:113-139`) while live daemons write; **inferred** for these sightings. The product promise is "push transitions": a slow machine that drops a transition is a user-visible defect, not only a flaky test.

**G6** and **G7** are as in the table. G7's Node 26 job on 2026-11-17 (44098099705) timed out every e2e baseline with no `runs` folder, the same hour as the Node 22 `ENOTCACHED`; **inferred** as the same install gap.
