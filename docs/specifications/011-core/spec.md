## Scope

The harness-neutral and runner-neutral subsystem: worktrees, repository and store, the watcher and revisions, content keys and closures, scheduling and validity, known states and delivery views, status, the daemon's lifecycle, policy and capacity, error handling, and the two adapter contracts every runner and harness implements. Excluded: any hook event name, plugin manifest or packaging (012, 002, 008, 009); anything that reads Vite's module graph or calls `createVitest` (013); the slow tier's rules (004); node:test (003) and pytest (007); wording 005 owns; evals (006); CI (010).

## Problem

<!-- 001 spec.md@cdd72a91 lines 7 (Problem) -->
Coding agents validate synchronously or not at all. They forget to run tests, run the wrong command, miss failures that were already there, and discover at the end of a task that an early edit broke something a later edit built on. Watch-mode tools exist for humans but not in a form an agent harness can consume: event-driven, revision-aware, machine-readable, and honest about what has and has not been checked.

<!-- 001 spec.md@cdd72a91 lines 9 (Problem) -->
Squeal v1 proves the interaction model from `docs/vision.md`: push transitions, pull state. One test ecosystem (Vitest), one harness (Claude Code), one repository with any number of git worktrees.

**Note (2026-10-17).** "One test ecosystem (Vitest), one harness (Claude Code)" describes v1 as shipped on 2026-10-06. Since then: Codex (002), node:test (003), slow suites (004), pytest (007), OpenCode (008), Pi (009). The interaction model is unchanged.

## Goals

<!-- 001 spec.md@cdd72a91 lines 13 (Goals) -->
Each goal is testable.

<!-- 001 spec.md@cdd72a91 lines 15-21 (Goals) -->
1. An agent editing a Vitest project learns about a `PASS -> FAIL` transition within one tool call of the result being known, inside the same turn, without running tests itself.
2. The matching `FAIL -> PASS` arrives the same way. Nothing arrives for `PASS -> PASS` or for a failure that is still failing with the same diagnostic.
3. Everything the agent is told is true at the moment it is told: a delivered state is the current known state, labelled with the revision it was validated at and whether the current revision is still pending for that check.
4. A new worktree of a repository that already has a baseline inherits every result whose inputs are byte-identical, without running them, and reports them as inherited.
5. `squeal status` answers, for the current worktree and revision: known failures, counts of checks current, pending, stale and unknown, whether a full-suite run exists for this revision, and whether the daemon is alive.
6. No Squeal hook ever blocks the agent for more than its configured timeout (2 s default), and a dead or hung daemon degrades to "status unavailable", never to a stall.
7. One shared store per repository serves several worktrees and several agents at once without lost writes or corruption.

## Design

### C1. Workspace, repository, store

<!-- 001 spec.md@cdd72a91 lines 38 (D1) -->
A **worktree** is one git working tree: the nearest ancestor of a path that is a git top level. Every worktree has its own daemon, revision counter, Vitest instance and file hash cache. A directory below a worktree root that contains its own `.git` entry is another worktree, or a clone or submodule, and is opaque to the parent: never watched, never validated.

<!-- 001 spec.md@cdd72a91 lines 40 (D1) -->
A **repository** is the set of worktrees sharing one git common directory. The **store** is `<git-common-dir>/squeal/`. In a normal repository that is `<main worktree>/.git/squeal/`, so it lives in the main worktree, is never watched, and cannot be committed. Layout:

<!-- 001 spec.md@cdd72a91 lines 42-44 (D1) -->
- `store.sqlite`: the shared database (D8).
- `locks/<worktree-hash>.sqlite`: one exclusive-lock database per worktree, the daemon singleton (D10).
- `runs/<run-id>/`: full runner output per run, referenced from results, pruned with them.

<!-- 001 spec.md@cdd72a91 lines 48 (D1) -->
The unix socket for liveness is `<runtime dir>/squeal-<worktree-hash>.sock`, never under the worktree, because socket paths are limited to 104 bytes on macOS and nested worktree paths exceed that. Without a runtime directory, or when that path would pass the bind limit, it lives in `/tmp/squeal-<uid>`, the per-user directory D10's temp directory also uses, created mode 0700 and checked for owner and mode, never a fixed name in a shared directory. It is never under the inherited `TMPDIR`, which another tool may reap and which differs between the processes that start hooks, so the daemon, every hook and the CLI compute one path. Hooks and the CLI pick the socket by one rule: the one recorded in the store first when its heartbeat is fresh and a daemon answers there, else the computed one.

### C2. Watcher and revisions

<!-- 001 spec.md@cdd72a91 lines 52 (D2) -->
The watcher sits behind one internal interface with two backends: chokidar 5 on Linux, @parcel/watcher on macOS. The Linux choice is the only backend that passed every correctness scenario in research; the macOS choice avoids per-file descriptors and reports dropped events. Node's recursive `fs.watch` is excluded: it loses writes after an atomic save.

<!-- 001 spec.md@cdd72a91 lines 54 (D2) -->
Watcher events are hints. Each debounced batch (100 ms quiet, 500 ms maximum) is reconciled: every reported path is re-stat'ed and, if `mtime`, `size` or inode changed, re-hashed with the git blob hash. Paths whose hash is unchanged are dropped. If anything remains, the worktree's **revision** increments by one and the revision records the changed paths with old and new hashes, the time, `HEAD`, and whether the tree is dirty. The `git status` a revision runs for its dirty flag also gives the worktree's unmerged paths (codes `DD`, `AU`, `UD`, `UA`, `DU`, `AA`, `UU`), for the merge hold (C9; amended 2026-10-21, the human, row 011-61). A revision is never created by a touch or a no-op save. Such a batch still reaches the runner: each path whose stat moved since it was hashed and whose bytes hash as before (a no-op save, a revert and its restore inside one batch, a build that rewrites its output unchanged) is handed to the runner's `invalidate` as a touch, with the batch's revision or in a runner part of its own, before the next tier (D4, task 001-159). Before a tier is recorded, the inputs its keys name are re-stat'ed against the stat cache as the tier was selected: a touch found there, whose batch has not arrived, withholds the files whose keys name it (amended 2026-10-20, 013 row 013-01, D2) and is reconciled at once (the completion barrier, D4, task 001-168). A racy entry re-hashed on the stat it was hashed with was not written, and a path that appeared and went within the batch (an atomic save's temp file) was never known; neither is a touch. A path shaped like an atomic save's temp file (`<file>.tmp.<pid>.<random>`) that exists and is not tracked is held out of batches and reconciliation passes for 5 s from its first sighting, then rechecked once: gone, it was never known; still there, it is a new file. No other path waits, so a real add is never delayed (task 001-216: Claude Code's create and rename fell ~550 ms apart, in separate batches, at load ~35). Creating a revision never waits on the runner: the store work (revision row, stat cache, content re-key, queued phases) completes within the debounce window even while a tier is running, and the runner-dependent refinement is queued separately, applied in revision order beside the tiers in flight (D5 step 5, task 001-140), and never holds the revision path. A runner that serializes its calls behind its own run waits for it; Vitest's adapter answers its runner part during its run, and waits only to recreate its instance (D5 step 5, task 001-150). The last revision whose refinement was applied is recorded, and headers, status and every wait treat a revision ahead of it as pending, so a test file added during a tier is never reported as nothing pending.

<!-- 001 spec.md@cdd72a91 lines 56 (D2) -->
Ignore rules come from git, in three layers: at watch time, exclude `.git`, nested worktree roots, and the output of `git ls-files --others --ignored --exclude-standard --directory`; at batch time, run the paths through one `git check-ignore --stdin`, except a path beyond a symlinked directory below the root, which git refuses and can never track: it takes the class of the outermost link above it, which git accepts. The link's subtree is ignored when git ignores the link's own path or would ignore a directory at that path (a linked `node_modules` under `node_modules/`, which never matches the link itself, a file to git); the second is asked as `L/` through one `git check-ignore --no-index --stdin` with the worktree's git directory against a scratch work tree under the daemon's temp directory (D10), reused, holding only copies of the `.gitignore` files above the link, so `info/exclude` and `core.excludesFile` apply too. Any other symlinked directory is a project directory: its descendants are candidates, the watcher watches its target and reports each event under the link's path, and every reconciliation pass walks it, since git status never lists what is behind a link; links inside it are not followed, and a link to the root or above it, or to another repository, is not observed. Amended 2026-10-12 (task 001-300, `research/nested-worktree-watch.md` R3): the watch of a target leaves out the directories below it that git would ignore under every link to it were the link a directory, asked as `L/dir/` through the same scratch tree, which copies the target's own `.gitignore` files through the link, and those that hold their own `.git` entry; it recomputes them on each reconciliation, on a `.gitignore` event in the target and for each directory that appears there. The descendants keep the link's class, so a reconciliation pass still walks those directories and finds a change there, which the watch does not report. A batch git refuses anyway is split until the path it names stands alone and counts as ignored, so one path never fails the batch (tasks 001-111 and 001-118, `lessons.md` defect 21, `reviews/wave-11f.md` B1). Recompute the watch-time list when any `.gitignore` changes or a `.git` entry appears under the root. Gitignored files that appear in a known closure (generated code) and the installed-dependency lockfile that the environment hash reads are added to the stat cache and watched individually, so a change to them creates a revision like any other input, even though the ignored tree around them is not watched; the installed lockfile is read and watched through a linked `node_modules` the same way. A gitignored path the stat cache holds from an earlier daemon is watched again at start. Once the environment is read, one that no closure, environment file, lockfile or observed read names is dropped from the stat cache and no longer watched, with no revision. A kept one is judged again when a closure that named it is replaced or its test file is removed, or when the environment is read again; a dropped path that a closure names later is hashed and watched again (amended 2026-10-23, row 011-36). A test file is never keyed while any of its closure paths is untracked by the stat cache.

<!-- 001 spec.md@cdd72a91 lines 58 (D2) -->
A reconciliation pass runs every 30 s when idle, on daemon start, and after every update of the watch, from a batch's hints (a new ignored directory, a `.gitignore` or `.git` entry change) or from a change of the extra files (row 011-187): `git status --porcelain` plus a re-stat of every file in the hash cache. The last is because a backend that replaces its watcher can drop an event in flight: chokidar's old watcher closed before its stat of an edit returned, and the new one attached after it (row 011-183). Anything the watcher missed becomes a revision then. This bounds the damage of a lost event to latency, never to a false "current". @parcel/watcher 2.6.0 erases an event added between copying and clearing its pending events (task 001-235), from the watch of an excluded directory's extra files and, on macOS, from the root watch too. Both recover it by one rule, reading no content: beside the files a batch names, each file whose mtime or ctime is no older than the previous batch less the 2 s racy window is reported, so a same-size rewrite inside one tick is too, and the reconciler drops a duplicate (tasks 001-236, 001-253). An extras batch checks every extra file of its directory, with one exists bit per file so an erased removal or creation is reported by its kind; a root batch re-stats the directories its events name, at most 1,024 stats and 4,096 directory entries read (task 001-250). An erased root event that this does not find (a removal, a write in a directory the batch does not name, an entry past either budget) waits for this pass, so its bound is 30 s after the watcher goes quiet.

Amended 2026-10-15 (task 001-406, the human's choice): headers, `status` and `why` show a revision beside its commit, `revision N · <sha> + K`, where `K` counts the revisions since `HEAD` last moved, with `dirty` when the tree differs from `HEAD`; a partial commit reads `+ 0, dirty`, and a repository before its first commit shows the number alone. A commit leaves the revision number unchanged, so an agent can keep referring to it. The display is derived from the `HEAD` and dirty flag each revision already records, and a newer same-revision `HEAD` move decides the dirty flag, a move back to the revision's commit included (review 001-417 B4). ### C3. Keys and closures

<!-- 001 spec.md@cdd72a91 lines 64 (D3) -->
Results are keyed by what produced them, never by where or when. The commit SHA, revision and worktree are provenance, stored beside each result and shown to agents, never part of the key. (ADR 0002; research, result-fingerprinting-prior-art R1 to R4.)

<!-- 001 spec.md@cdd72a91 lines 66-67 (D3) -->
- **File hash**: the git blob id of the bytes on disk, `sha1("blob <len>\0" + bytes)` (SHA-256 in `objectFormat=sha256` repositories). It is read from the git index only when git reports the file clean and no `eol`, `text` or `filter` attribute applies to it; otherwise the bytes are hashed. One definition everywhere.
- **Environment hash**, per Vitest project per worktree: the key format version and the runner-adapter version, Vitest and Node versions, platform and arch, the resolved Vitest config, the contents of the root's config file, the project's own config file and the `configFileDependencies` of these two, never a sibling project's (task 011-85: Vitest loads each `projects` entry as its own config; as for a sibling's `globalSetup`, a sibling config's effect on Vitest's shared process is not keyed), the closure of every `setupFiles` and `globalSetup` entry, with every unresolved import's target path and resolution candidates as a test file's closure has them (task 001-424: a setup file's failed import fails every test file of the project and lies in no test file's closure, so only these re-key the project when the target is added), the installed dependencies every test file can load (below), and allow-listed environment variables. Policy-declared `inputs` enter closures, not the environment hash, so they are never counted twice. npm's hidden lockfile `node_modules/.package-lock.json` stands for the install only while npm itself would trust it: every package folder in the `node_modules` hierarchy (the root's and each listed workspace's, recursively) is listed in it, every folder it lists exists, and none is newer than it, workspace links compared with `lstat` and never followed. Otherwise the fingerprint hashes the package folders instead (each folder's path and its `package.json` name and version, each link's path and target), so an install that bypassed the file still re-keys, and one daemon note, recorded once each time it changes and not again by a later daemon start that finds it unchanged, names the first unlisted, newer or missing folder of each kind (tasks 001-104, 001-105, 001-109). pnpm's installed `lock.yaml` stands for the install under C11's rule for it (task 011-162).

Incremental maintenance follows Bazel, Nx and the git index: a stat cache `path -> (mtime, ctime, size, inode, hash)`, a reverse index `path -> test files`, and re-computation only of the keys that reference a changed path. Adding or deleting a file re-resolves closures of test files that import from the affected directory, because module resolution can change without any closure file's content changing. Most such test files are also reported by the runner's `affected` (D4) or by an absent resolution candidate in their closure; only the `package.json` rule reports the importers of a directory whose `package.json` was added, deleted or edited, because the manifest is in no closure and in no module graph. It re-resolves every closure with a path below that directory, since the entry the manifest names, or named, may lie below it (`"main": "lib/entry.ts"`) (tasks 001-72, 001-79). The root `package.json` re-resolves every closure, since its `imports` and the package imported by its own name can resolve anywhere (001-81).

### C4. Scheduler and result validity

<!-- 001 spec.md@cdd72a91 lines 96 (D5) -->
Validity is per check, not per run. A stored result is **current** for a check in a worktree at a revision when its key equals the key computed for that check at that revision. Otherwise the check is **stale** (an older result exists under another key) or **unknown** (no result at all). **Pending** means a run that will produce a result for the current key is queued or running.

A focused result (C15) has no validity: it is never current, stale, unknown or pending, and it never says whether a check passes at a key (amended 2026-10-23, the human, row 011-135).

<!-- 001 spec.md@cdd72a91 lines 98 (D5) -->
On each new revision the daemon:

<!-- 001 spec.md@cdd72a91 lines 100-104 (D5) -->
1. invalidates changed paths in the runner and updates the stat cache and reverse index;
2. computes the affected test files and recomputes their keys;
3. looks each new key up in the store. A hit is promoted to current for this worktree with its provenance intact. No run is needed. A key with no result is first read at the formats and the former definition C3 reads as one, once per file, key and keys read as one in a daemon: a closure change can move the keys read as one while the key stays, as a path with no file leaving the closure moves only the key before 011-158 (task 011-158, review 0.1.285 B1), and the file is read again at the keys it moved to, and the keys other worktrees stored since the last read are matched at those formats too (task 011-37). This is the inheritance path for new worktrees and the de-duplication path between worktrees that have identical files. A file whose key has no result here is looked up again when other worktrees store results: each reconciliation pass and each tier selection read the keys recorded since the last read, with an overlap for stores that commit late, and settle this worktree's files at those keys as above. Provenance is kept and an unconfirmed fail stays held (C5); nothing is queued that policy did not queue, so under `baseline.onStart: "lookup-only"` a stale file becomes current without a run (amended 2026-10-20, row 011-23, the human chose reading on each pass over a push by the storer; cezar, 2026-10-19: 664 of a second worktree's 747 stale files had results from the main checkout at their keys; `research/catch-up.md`). Under `"lookup-only"`, now the default (001 D11), a file whose result at its key is another worktree's held failure (001 D6, task 001-170) is still queued once, for the local run that confirms or clears it, so a known failure shows in a worktree that runs nothing else; no other miss is queued (amended 2026-10-23, the human, row 011-159, `research/main-daemon.md` 5: cezar held 30 such failing rows that no run confirmed);

**Holds** (amended 2026-10-21, the human, row 011-61, gh-68 and gh-49, `tasks/011-61/design.md`). ### C15. Named demand

Added 2026-10-17 (row 011-03; issues 14, 17, 23, 24; accepted by the human as drafted in `tasks/011-03/design.md`, with promoted files ranked first in the edit-caused group and source paths not promoted). It revises 005-11's "reads only, no reordering" (the human, 2026-10-13); 005 D2 points here. Code rows 011-11 and 011-12.


A named wait (`squeal status --wait <ms> <path>...`, 005 D2) tells the daemon which files the agent is waiting for, and the daemon runs them sooner. It changes only the order in which queued files are taken. It does not change which files run, their keys, or whether a result is current, so the verdict is the same as without promotion (principle 2). A focused request (below) runs part of a test file first, and its outcome is never a result (C5), so the same holds with it (amended 2026-10-23, row 011-135).

**What is promoted.** A path that selects a listed test file by itself promotes that file. A source path's selection is not promoted: it reaches every consumer of the path (79 to 83 files on cezarion, `issue-17.md` 2), which is the queue's ordinary work. A file that is current, running, or not queued is not affected. A promoted file that becomes queued while the wait is open (an edit during the wait) is promoted too.

**Rank.** A promoted file counts as work an edit caused (C4 step 4, first group) and goes before every other class in that group, failing files included. Among promoted files, the earlier request goes first, then C4's order. It still obeys every rule that keeps tiers honest. It joins a tier only when the lane is free. A tier that is not the backlog's shares only with files of comparable duration (001-184), so a promoted file leads its own tier and never shares it with a file that a yield cut past its estimate (C4 step 5, row 011-112). It counts toward the four first-group tiers after which the backlog gets its turn, so a stream of named waits cannot starve the backlog. A promoted file queued behind a running tier makes it yield as C4 step 5 says: once per file and key, when its estimated remainder exceeds 30 s, never the backlog's turn, and, once the tier has run 30 s, only when the tier runs no file that the same or an earlier open wait selected (row 011-184). A promoted file that waits on another worktree's claim of its key (C7: not forced, not work an edit caused, no result stored at its key) makes no tier yield, as the cut would run nothing sooner, and its wait names the claim (amended 2026-10-23, row 011-55). While it waits, a tier in flight that such a yield could cut (not a slow tier, not a backlog slot, not a tier whose runner runs each tier to its end) is checked again each second: a result the claimant stored is taken with no run, and a claim that ended with no result (its heartbeat lost, or the waiter's bound passed since it first saw the claim) makes the tier yield as above, with no new edit or request (amended 2026-10-23, review `reviews/0.1.271.md` B1, row 011-123). Otherwise it waits for the tier (amended 2026-10-21, the human, row 001-381).

**Lifetime.** Promotion lasts until the wait's deadline or until none of the selected files is queued or running, whichever comes first. A wait's last read judges its files as of its deadline, so a wait that times out still says its files were promoted and what they wait behind (amended 2026-10-21, row 011-63, gh-51). A file waiting for another worktree's claim of its key stays queued here, so promotion holds through the claim; emptying the queue (an install) drops it. The request carries the deadline as the time left of the wait, which the daemon adds to its own clock (task 011-11), so a killed CLI leaves promotion in place for at most its own `<ms>`, and no cancel message or lease is needed. Promotion lives in the daemon's memory, and a successor daemon does not inherit it.

**Constraints that still bind.**
- *A claim* (C7): a file whose key another live worktree is running keeps waiting for that run, which will store the result this wait needs. Promotion does not start a duplicate run.
- *A slow file* (004 D2): it leads its own tier's order when the tier runs. Promotion does not make the slow tier eligible while a consumer is in a turn; `squeal run --slow` does.
- *An unlisted revision* (C4, the runner part): no tier starts until the revision is listed, promoted or not.

**What the wait says while a constraint holds a file.** For every selected file that is still pending, the named line gives one reason with its bound when one is known; the verdict line names at most five reason groups and summarizes the rest by count, while the class lines and `--json` keep every file's own (review wave-1.11 S1, task 011-13):
- running since HH:MM:SS in its lane;
- queued, promoted, behind the `<lane>` tier running since HH:MM:SS, then `; the tier yields` or the reason it does not (`queued, promoted` with no tier running in its lane; the tier yields when C4 step 5 will cancel it, and the reason names its remainder, the time a tier past its estimate yields at (row 011-107), a file already cut, the backlog's turn, a file this wait or an earlier one selected (row 011-184), or a runner that runs each tier to its end (node:test, pytest, a backlog slot); amended 2026-10-21, rows 001-381 and 011-51): the daemon publishes its live promotions in one `promotions:<worktree>` meta row, rewritten on each change and dropped when none is left, and the CLI says promoted only while that daemon lives, the row is no older than its start and the deadline has not passed; an older daemon writes none, so its files read `queued` (task 011-13);
- waiting for `<worktree>`'s run of its key, at most until now plus C7's bound, since the waiter's bound runs from when its daemon first saw the claim, which only that daemon knows, and the claimant's own policy bounds its run; only a claimant whose daemon heartbeats is named (review wave-1.11 B1, B2); a queued file with a result stored at its key reads no claim, as selection holds no such file on one, and reads what it waits for instead; a file an edit caused or a forced file still reads the claim, as the queue's classes are only in the daemon's memory (amended 2026-10-23, row 011-124; the rest is row 011-125);
- slow, run when the agent pauses or on `squeal run --slow`;
- revision N not listed yet, because the runner part waits for the run in flight, each of its calls bounded at N s, followed by `; the run yields` when a selected file is promoted and C4 step 5 cancels the run (amended 2026-10-21, row 001-381) (gh-17 finding 2, the `runner.timeoutMs` + 66 s bound of C4; the store keeps no call's start, so no countdown: review wave-1.11 B3).

- a file a hold keeps queued reads `queued, on hold for the unresolved merge (git lists <paths> unmerged)` or ``queued, on hold for `<command>` (pid N) until it exits`` (amended 2026-10-21, the human, row 011-61).

Status counts the checks of a file whose run is open as running, even after a re-key queued it under its new key (gh-17 finding 3: `queued 10, running 0` with the run open).

**Older daemons.** The CLI sends the promotion as a new request (`promote` with the test files selected by their own paths and the time left). It sends it once, beside the first read whose selection is decided (the daemon's sync pass stored and the revision listed), and only while the wait is still open (task 011-11). A promoted fast file that is queued counts as an edit's work for the slow tier too, so the slow tier waits for it as for an edit's work. A daemon that does not know the request answers unknown, and the wait reads only, as before. Nothing breaks, and the order is simply the old one.

**Measured by** a scheduler test from `issue-14`'s probe: with A running, then B and Z queued, a named wait on Z makes Z start before B, and B still runs. Also: a source-path wait reorders nothing, a claimed key waits for its claimant, and the fairness turn still comes after four first-group tiers.

**What status and the named line say about each file** (issues 23 and 24, folded in by the human on 2026-10-17). A named wait that times out lists the selected paths still pending by class, names the selected failures and the known pass or fail outcomes without a `why` call, and every `wait.testFiles` entry of its JSON carries `current`, `pending`, `stale` or `unknown` and a verdict when one is known; counts alone are not enough once more than a few files are selected. Both JSON forms, the snapshot (`status <path>... --json`) and the wait, also carry the whole selection payload under `selection` (outcome, waited time, code, test files, unmatched paths and verdict), the older `named` and `wait` keys kept, so one filter reads either form (amended 2026-10-21, row 011-63, gh-65 option 2; `schemaVersion` unchanged, the field is additive). A file shown `unknown` keeps the reason it became so where one is known (a withheld run, a failed setup, a key that never ran, a claim another worktree holds), and `no reason was kept` is said only when that is the truth of the store, never as the default for files the daemon has not yet listed. Status tells initial discovery (the daemon still listing or keying files) from idle work that is queued but not scheduled, and names the command that advances each.

Amended 2026-10-20 (the human, row 011-24; gh-38, gh-39, gh-40, gh-41, gh-43, gh-46; `tasks/011-24/design.md` section 3, Q3 option 1, Q5 (a)): every selected file without a verdict names the command that advances it, or says that none does and why: `squeal retry <file>` runs once a stale, never-run or timed-out file (the last with the load when it is at or above the CPU count), `squeal run --slow` a slow one, a claim, or a running tier that does not yield (C4 step 5), is waited for and nothing runs it sooner, a file in a run of several files is said to be in that run and not running, a file queued with nothing recorded holding it says so, and a running slow file whose project has a global setup names `squeal retry <file> --reason environment` as its one-file rerun. The class lines group the files by reason with that step, and the verdict line gives each of its reason groups its command. A group of up to three files names its command with every path; a larger one names `squeal retry <test file>...` and how many files `squeal run --all --wait` would run; `retry` takes no source path, since a source path's selection is the queue's ordinary work. An unmatched path names the directory it was resolved against and, when the same path from the worktree root is a listed test file, that file; it never selects it.

**Focused checks.** Added 2026-10-23 (the human, row 011-135, gh-64; `tasks/011-135/design.md`, Q1 to Q6 (a)). `squeal status --wait <ms> <path>... --check <text>...` asks the daemon to run first, alone, the checks of each test file selected by its own path whose full name holds one of the texts. The full name is the check's identity within its file (013 V4); the path and project are not matched, and a text that begins with the file's printed prefix (`[project] <path> > `) is read without it. A source path selects no focus. Once the daemon listed the revision, `--check` with no test file named by its own path is a usage error (exit 2), whatever the paths select (review 0.1.286 B4). The CLI sends `focus` (those test files, the texts and the time left of the wait) once, beside `promote`. The daemon keeps a focused entry per file until the deadline, in its memory, and runs it as C4 says. A completed run that selected no check reads `No check of <file> holds "<text>" at revision N (the run collected M checks)`; a run that ended crashed or timed out reads `no outcome: the focused run ended <end>`.
