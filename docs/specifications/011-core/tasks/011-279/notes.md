## 011-279: the updater lock test (`test/harness/codex/runtime-update/lock-process.test.ts`)

- **The acknowledgement already existed.** `lock-owner.ts` sends `held` only after `acquireLock` returned, and `acquireLock` returns only after `writeAtomic` wrote the owner hint. So the fixture needed no new acknowledgement message. The old test failed because it required the PID from the two losers' results, and a loser can read before the holder wrote its hint.
- **Three contenders.** Still exactly one `held` and two `busy`. A loser's PID is now `0` (unknown owner) or the holder's PID; any other PID still fails. After all three answered, the test process attempts once in process and must read `busy` with the holder's PID: this is the check that waits for the acknowledgement.
- **The deterministic case.** The test process takes the lock with a `now` callback. `tryLock` calls `now` once, inside `BEGIN EXCLUSIVE` and before the hint. The callback runs one real contender synchronously (`execFileSync`), which must answer `busy` with PID `0`. After `acquireLock` returned, a second real contender must answer `busy` with the test process's PID. If a future `lock.ts` called `now` before `BEGIN EXCLUSIVE`, the first contender would answer `held` and the test fails; it does not pass silently.
- **Fixture mode.** Without an IPC channel `lock-owner.ts` attempts once, releases what it took, and prints its result as JSON on stdout. With IPC (fork) it behaves as before.
- **Timeout.** The deterministic case blocks the event loop for two `tsx` process starts. It has a 40 s test timeout and a 15 s timeout for each child; the other two tests keep Vitest's default.
- **Killed-owner recovery** is unchanged: its PID check already follows the owner's `held` message.

## 011-280: the step-down test (`test/daemon/step-down.test.ts`)

- **One test, two phases, per daemon.** The equal and newer daemons still start together. Each is first held in its start window, then released and checked once settled. This costs two daemon starts, as before, not four.
- **Holding the start window without a product change.** No pause point (`src/core/daemon/test-pause.ts`) is in that window: `store-open` comes before the socket and the record, and a SIGSTOP would also stop the socket worker. So a test preload, `test/daemon/start-hold-preload.mjs`, replaces `fs.rmSync`. At the daemon's first removal of its `.starting` mark, which `clearStartMark` does after the registration commit, it writes `<prefix>.held` and sleeps in `Atomics.wait` steps of 20 ms until the test writes `<prefix>.release`, 60 s at most. The socket worker still answers pings. This is the research probe's mechanism, with a release file in place of its fixed 2.5 s hold, so a slow hook cannot outlast the window. It depends on `start-mark.ts` removing the mark with `rmSync` from `node:fs`; if that changes, the test fails at "the daemon registered, its mark kept" after 60 s. It does not pass silently.
- **Start-window assertions.** The ping names the spawned process's PID and the daemon's version; SessionStart and PostToolBatch ask `ensureDaemon` nothing (`[]`); the start mark still names a live daemon after both hooks, which proves they ran inside the window; and no other `daemon <root>` process exists.
- **Settled assertions.** The test waits for the record at the daemon's version, a heartbeat that `daemonLiveness` reads as alive, and no start mark. The brief named the record and the mark. I added the live heartbeat: after a long hold the record's heartbeat can be older than two intervals until the next tick, and then PostToolBatch would call `ensureDaemon` a second time. Then `["alive"]`, the same PID and version after 1 s, no successor, and no step-down note, as before.
- **Failure evidence.** Both hooks run with `SQUEAL_HOOK_DEBUG=1`; their stdout and stderr are the message of the `ensured` assertions.
- **Kit additions** (`test/daemon/step-down-helpers.ts`, additive): `run` returns a hook's result (`hook` now calls it and still returns its duration), and `startHold()` returns the preload's environment, the `held` path and `release`. The handover tests that share the kit are unchanged.
- **Older-daemon cases** (`cancelsItsTier`, `stepsDownAfterItsTier`) are unchanged.
