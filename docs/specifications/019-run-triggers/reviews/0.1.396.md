## Blockers

### B1. Proven: one group's load wait blocks a different group that may run now

Locations: `src/core/scheduler/scheduler.ts:1383`, `src/core/scheduler/slow-tier.ts:287`, `src/core/scheduler/group-tiers.ts:39`.

D3 says: "a running tier in one lane never holds back another lane". Goal 3 says: "A long group never holds back another group's results." Row 019-10 requires independent group lanes and their optional limits.

`#groupLanesNext` awaits `lane.next` in a serial loop. `next` awaits that lane's complete load-guard wait. Sorting unguarded groups first does not isolate two groups that both have guards with different bounds. A guard's wait can consume its entire `maxDeferMs` before the next group is even considered.

Reproduction uses `groupSide(groupPolicy(...))` from `test/scheduler/group-lanes-fixture.ts`:

1. Configure `strict` at `edit`, selecting `test/e2e/c.test.ts`, with `deferUnderLoad: { maxLoadPerCpu: 1, maxDeferMs: 5000 }`.
2. Configure `tolerant` after it in the list, at `edit`, selecting `test/b.test.ts`, with `deferUnderLoad: { maxLoadPerCpu: 20, maxDeferMs: 5000 }`. Neither group has `after`.
3. Let the baseline finish at load 0. Set the fixture load to 10 per CPU. Edit both `src/core.ts` and `src/other.ts`.
4. Wait until `strict` publishes `{ kind: "waiting", for: "load" }`. After 300 ms, inspect the new run log. `tolerant` should already have run: its own load bound permits it.

Actual clean-candidate output:

```text
REVIEW lanes while strict waits:
{"vitest":[["test/a.test.ts"]],"node-test":[["nt/test/d.test.mjs"]],"pytest":[["py/tests/test_f.py"]]}
expected undefined to deeply equal [ [ 'test/b.test.ts' ] ]
```

Fix for one scheduler worker: make each lane's guard wait independent of the shared pump. Publish the wait, retain that lane's remaining budget, and let the pump inspect the other lanes. Keep a lane's selection serialized and retain preemption, hold and slot checks. Add this two-guard case; also cover a second lane becoming eligible while the first remains deferred. Preserve the default slow group's width and budget behavior.

### B2. Proven: an unstaged lint config is accepted as commit evidence

Locations: `src/core/commit/lint.ts:42`, `src/core/commit/lint.ts:49`. Key contract: `src/core/lint/pass/keys.ts:133`.

D5 step 2 requires keys "from the committed blobs" and says that a differing working-tree blob makes a check "not determined for this commit". Row 019-13 owns that computation, including partial staging.

For file-local lint, `lintCounts` accepts a current judged result when the source file's blob equals the committed source blob. It does not establish equality of the lint config and its closure. It consults other differing paths only for whole-program checks. The existing lint key does include config files, their closure and the computed config. Equality of the source blob alone therefore does not prove equality of keys.

Concrete case: the committed ESLint config enables a rule that rejects `src/a.ts`. Leave a config edit disabling that rule unstaged, let file-local lint finish under that edited config, and make a commit that keeps the source blob unchanged. The current working-tree pass belongs to the edited config. The committed tree has no such passing evidence.

The clean-candidate probe supplies that valid current local-lint state to `lintCounts`: `stale: false`, `outcome: "pass"`, judged source blob equal to the committed source blob, a key from the unstaged config, and `differing = new Set(["eslint.config.js"])`. Actual:

```text
REVIEW lint counts with unstaged config: {"findings":0,"notDetermined":0,"running":0}
expected +0 to be 1
```

The worker's notes and the comment at `lint.ts:26` acknowledge this limit; neither is an amendment authorizing attribution to the wrong commit.

Fix for one commit/lint worker: record the config and other key inputs where lint computes its key, then compare their blobs with the commit. If that evidence is absent, report not determined. A conservative fallback may mark local lint not determined when equality cannot be established. Do not reuse an opaque working-tree key as proof. Test both an unstaged rule change and an unchanged config, through the lint store and the report.

## Follow-up items accepted for step 2a

Do not call the complete feature or its diagnostics finished until 019-16 lands. Under scope `user`, the old slow paths remain unchanged.

019-16 should use `slotFiles(group, scope).dir(base, commonDir)` and group-aware holder reads. Test a real held repository-scoped slow permit and a configured-group permit. Require the old output under scope `user`.

### S2. Proven: stored commit reports have no completion update yet

Locations: `src/core/scheduler/head-move.ts:62`, `src/core/scheduler/head-move.ts:68`, `src/core/commit/report.ts:17`.

D5 step 3 requires one update when commit groups finish. A report stores only counts. Once `HEAD` is unchanged, `reportHeadMove` returns without recounting; a previously reported SHA reuses its old report. There is no completion callback that updates it.

Printing the stored report alone will not implement the update. The coordinator must assign the refresh together with commit-group triggering, with keys or a safe recount tied to the same SHA. Test an initial report with running checks and exactly one later update after those checks finish, including an intervening edit. No commit group runs automatically in this candidate.

## Plausible notes

- **S3, plausible:** `src/core/scheduler/head-move.ts:103` counts only the current worktree's `testFileKeys`, and `src/core/commit/compute.ts:83` iterates that list. A test that still belongs to the commit but was deleted only in the working tree may disappear from the report rather than count as not determined. The worker notes name this limit. A real runner relisting such a deletion was not probed here. Add that partial-staging case when repairing commit attribution; it is not a separate blocker in this review.
- **S4, plausible:** the generalized scheduler gives `SlowRelease` a maximum end time over all groups (`src/core/scheduler/group-tiers.ts:76`, scheduler constructor), while `SlowRelease` still has one shared selection flag and timer. A lane with queued work that cannot start may retain its instance beyond its own 60 s bound while another lane keeps ending tiers. Per-lane creation and direct release are covered, but this multi-lane timeout case is not. Check it with a fake clock before claiming independent idle release. The known closed-Vitest retention issue assigned to 019-19 is separate and is not a new finding here.

## What fits

These are source and test-contract observations. They do not replace the pending affected checks or CI.

- D1/D2 ownership routes through `groupOf` and the policy-scoped group view. Default `tests` lanes stay the runner's, default `slow` lanes stay `slow:<runner>`, and configured lanes use `group:<name>:<runner>`.
- The no-`checks` fixture has recorded start/edit tier logs and checks slow starts after fast completion. `pytest[].slow` now participates in the common classifier, including globs. The additional pytest slow lane is the intended defect fix.
- Default slow activity keeps `slow-tier:<worktree>`. Configured activity uses the single `group-tier:<worktree>` map agreed in 019-10's notes; readers must use `readGroupActivity` rather than the older draft key per group.
- Low priority reaches tier kind `slow`, which `TierYields` does not cancel on an edit. Selection narrows low-priority width when normal work is pending or the group's load bound is exceeded. Normal priority uses kind `edit` and the existing cancellation rules. B1 concerns a waiting guard, not the direct run-isolation test.
- `RunOptions.priority` is set by `newTier`, passed by `executeTier`, and read by `afterEachRun` through `runPriority`. `lowerWhile` chooses idle I/O from that value. Tests cover explicit low in a configured lane and explicit normal in a slow lane; nice 10 remains shared.
- `withSlowInstance` creates and releases by the full group lane string. The integration fixture checks that a configured Vitest group runs in its own instance, with no run in the fast instance.
- Slot identity hashes the repository id stored under the common dir. All worktrees sharing that common dir share the identity. Two repositories get separate directories by default. The shared host pool stays in the user base. Private base and repository directories are checked by the new slot test. Scope `user` keeps `slow.lock`, numbered slow permits and the old waiter prefix; configured groups use `group.<name>.<i>.lock`. Pool priority retains the older mark's `slow` flag, and an absent flag remains fast. This is compatible with older marks; it does not make an older user-scoped daemon adopt the new repository scope.
- The commit-report path runs no validation and installs no git hook. The boundary reads `HEAD` without spawning, asks for `sync` only on a detected move, and catches socket failure. The default socket wait is bounded at 100 ms, not the reconciliation pass's duration. The report may therefore become available at a later boundary. There is no new block or denial branch. Plain, partial, amended, rebased and hooksPath commit cases exist in the scheduler tests. B2 limits the lint attribution claim.
