## Nonblocking should-fix

### N1. A hung normalization command holds the scheduler lock for 30 seconds

**Proven, pre-existing in the first reviewed candidate.** `src/core/commit/stored.ts:38`, through `src/core/scheduler/head-move.ts:141`, `batch.ts:57` and `scheduler.ts:385`.

The diagnostic put a Git shim on PATH after fixture setup. It delegated every command except `hash-object` to the real Git. For `hash-object` it recorded one call and used `exec /bin/sleep 90`, so the real `runGit` timeout killed that process without leaving a child. A stable edited source made normalization eligible. While the interval pass waited, a later watch batch could not take the scheduler lock. Both settled after 30,054 ms, and the report kept the source's reader not determined. With only `differingPaths` replaced by its unchanged function extracted from `a9170ad10` (0.1.400), neither operation was pending at the 400 ms observation point, and the shim received no normalization call.

Thus the candidate does add latency relative to 0.1.400. It is not a zero-cost path, and the timeout does not run outside the lock. The repair leaves the first reviewed candidate's Git call, 30 s timeout and scheduler await unchanged. The parent clarified the brief on 2026-11-04: this re-review gates on no new or longer stall relative to `5f70bfcd4`, rather than equal latency to 0.1.400. Under that clarified scope, N1 is nonblocking. No claim of a total pass deadline follows from this per-command timeout; other Git reads have their own bounds.

**Worker-sized follow-up:** give normalization a short bound, for example 2 s, and keep every path different when it expires. Prefer doing the call outside the scheduler lock, while preserving the cached-hash and stat proof before any result is applied. Add a regression that holds normalization and shows another edit can progress. This needs its own approved scope; it is not part of B1's repair.
