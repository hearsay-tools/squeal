## Blockers

### B1. The lint-group wait reports a stale pass as completed

**Proven.** Location: `src/cli/run-lint-group.ts:181` to `:187`, especially the outcome-only classification at `:185`.

Contract: 019-22 requires `squeal run <lint group> --wait` to give the group's verdict. Vision principle 2 forbids an old result posing as current. A whole-program lint file retains `outcome: "pass"` with `stale: true` after another program file changes; this is a normal state, defined by `LintKnownState` and covered in `test/lint/pass/program.test.ts`.

Reproduction through the public CLI `main` and real lint store:

1. Configure enabled ESLint and `{ "name": "lint", "lint": true, "at": "commit" }`.
2. Store one valid earlier passing state for `src/a.js`, with its judged key, blob and revision, and `stale: true`.
3. Call `releaseLintGroup` for the group. It correctly returns **1** waiting check. Use a daemon socket that acknowledges that request but has not completed the lint pass.
4. Call `main(["run", "lint", "--wait", "300"], io)`.

Observed in **10 ms**, while the stored state remained stale:

```text
exit 0
Group lint completed: no lint findings in 1 file
Group lint requested at revision 3: 1 lint check queued; they lint now.
```

The request path selects both pending and stale checks. The verdict reader selects only `outcome === "pending"` as unfinished. It discards stale passes with `continue`, so the first poll can declare completion before the requested rerun starts. A stale failure is likewise treated as a completed current failure.

Small fix: give stale checks precedence over their old outcome in the lint-group verdict reader. Treat a released stale check as outstanding, and an unreleased stale check as having no current verdict. Count current findings only after staleness clears. Add stale-pass and stale-failure cases, holding the lint pass across the first poll, then completing it; assert exit 3 while unresolved and the actual 0/1 afterward. Keep the request and verdict readers on the same definition of outstanding work.

### B2. Unasked predecessor files can starve a commit's requested group forever

**Proven integration break.** New selection: `src/core/scheduler/commit-moment.ts:83`. Boundary: `src/core/scheduler/slow-tier.ts:436` and `src/core/scheduler/scheduler.ts:1453`.

Contract: D5 step 1 and 019-22 run the commit groups for changed closures. The review brief explicitly requires that held commit asks cannot starve. The new selective commit asks meet an older `after` check that counts every queued predecessor file, including files that this commit did not ask to run.

Reproduction with a real repository, scheduler, store and the existing fake runner:

```json
"checks": [
  { "name": "first", "runner": "vitest", "tests": ["test/a.test.ts"], "at": "commit" },
  { "name": "second", "runner": "vitest", "tests": ["test/b.test.ts"], "at": "commit", "after": ["first"] }
]
```

The closures contain `src/a.ts` and `src/b.ts` respectively. Start with both files awaiting their first commit-time result. Edit and commit only `src/b.ts`; send the reconciliation pass and wait for scheduler idle.

Observed: **zero runs**, `slowPending() === true`, and a report with **one running file and one unknown file**. The only report wait names `test/b.test.ts`. The `first` group's queued file was not asked at this commit and cannot run; `second` nevertheless waits for it. Repeated pumping cannot change that condition. An explicit `requestGroup("first")` runs `a`, then `b`, which confirms the cause.

A second probe made `first` own both `a` and `c`, then committed changes to `a` and `b`. The predecessor ran `a` to completion, but `second` still never ran `b`, because unchanged `c` remained queued and unasked. An explicit request for `first` again released the obstruction. Thus the problem also occurs after the predecessor has completed all work selected by this commit.

The all-queued predecessor check predates this range. This finding concerns its new coupling to selective automatic commit asks, which leaves legitimate commit work unable to run or complete its report.

Small fix: make commit-moment ordering consider the predecessor's eligible commit work and in-flight work, rather than its unasked held backlog. Preserve ordering when both groups have eligible asks, explicit group requests, and behavior without `checks`. Add the above case and a case where both groups are selected: only the changed group runs in the first case; both run in order in the second. Assert the report's one update after completion.

### B3. The lint-group path still spends the fixed discovery timeout before its short wait

**Proven.** Location: `src/cli/run-lint-group.ts:64`; compare the repaired test-group call in `src/cli/run-group.ts:89`.

Contract: wave 3 item 019-24.3 and the review brief require `run <group> --wait` to stay within its wait on a stalled daemon. The new lint-group path duplicates the transport loop and calls `daemonSocket(root)` without the remaining budget.

Reproduction: configure the same lint group; listen at its daemon socket; accept connections but never answer `ping`. Call `main(["run", "lint", "--wait", "300"], io)`.

Observed: **2006 ms**, exit **3**, empty stderr, with `Group lint has no verdict: the daemon did not answer (... in 1 ms)`. Discovery had already spent its default 2000 ms; only the subsequent request used the exhausted deadline. The exit code and wording are handled, but the wait budget is still broken. The added lint socket test answers `ping`, so it does not cover this path.

Small fix: pass the remaining deadline budget to lint-group discovery, as the test-group path now does. Use the shared bounded transport helpers for both paths; also bound the lint request-status sleep. Add a silent-discovery-ping case for lint groups, with a short wait and the same timing tolerance used by the test-group stall tests. Keep exit 3 and the worded no-verdict result.
