## What fits

### The helper preserves behavior

**Proven by source comparison and focused tests.** `src/core/lint/pass/commit-entry.ts:127` and `src/core/lint/pass/records.ts:262`.

Before the change, the non-held branch called `store.meta.get(committedKey(scope))` and, only when its result was not `null`, called `store.meta.delete(committedKey(scope))`. It now passes the same `store.meta` and `scope` to `forgetCommitted`, which performs those exact synchronous operations in that order. It retains the same condition, key builder, receiver and return behavior. It adds no transaction, await, catch, or state mutation beyond that delete. `markHeld` remains before it; the held branch still runs `releasedNow` before `committedNews`.

The metadata repository is a stable object with synchronous `get` and `delete` methods (`src/core/lint/store/store.ts:30`). Moving the call does not change its receiver or transaction context. The pass tests retain commit-held and edit-time behavior, commit news, request-only quiet releases, and the prior B1 cache-hit cases. The registry test passes without being weakened. Its source scan matches `.meta.get/set/delete(...)`; moving this lint-store record operation to its existing record owner removes the inline expression that the scan rejected.

This preserves D5's commit-report behavior and row 019-43's requirement to tell the agent a committed finding once. The extraction does not consume commit provenance on the held path.

### The reset is a peer-close error, and the assertions still apply

**Proven mechanism; historical timing inferred from the log.** `test/commit/boundary.test.ts:51`, `src/core/commit/boundary.ts:86`, `src/core/daemon/client.ts:98`, and `src/core/daemon/server.ts:106`.

`gh run view 41819844757 --log-failed` reports an uncaught `Error: read ECONNRESET`, `{ errno: -104, code: 'ECONNRESET', syscall: 'read' }`, attributed to `test/commit/boundary.test.ts`. Its last named test is `stops waiting after 500 ms when the pass does not end, well inside the hook's 2 s`. This agrees with the brief. The log alone does not identify the exact scheduling order.

The production client destroys its socket on both settlement and timeout. Each status request near the boundary's deadline has only the remaining milliseconds to answer. A server can write its answer while a busy client has not read it; the client's timeout can then destroy that socket with the answer unread. The real server handles all socket error events by destroying the socket. The fixture previously had no error listener.

A throwaway `node --input-type=module` probe reproduced the precise error with the same Unix-socket request/`socket.end` topology. The server ran in the parent process and used the fixture's pending-sync JSON reply. A child client set a 40 ms destroy timer, wrote one `sync-status` request on connect, and stayed busy for 100 ms before it could read. The server recorded:

```json
{"clientExit":0,"answered":1,"serverErrors":[{"code":"ECONNRESET","syscall":"read"}]}
```

The probe asserted successful child exit and the server's `ECONNRESET`/`read`, and exited 0. Its temporary socket directory was removed. This proves the named timeout/unread-reply mechanism can produce the nightly error; it does not claim to replay the nightly schedule.

An earlier one-process probe used the actual `requestDaemon` with fifty 2 ms requests and a 5 ms busy server callback. It got fifty client timeouts and server `EPIPE` write errors. Its assertion requiring `read ECONNRESET` failed (exit 1). That diagnostic showed a different ordering of the peer-close race, not a candidate test failure. Separating the busy client from the server produced the read-side error above. Both probes left the candidate tree clean.

The added listener handles only the accepted socket's `error` event. It does not catch JSON parse errors, exceptions from `answer`, assertion failures, or listener setup errors. Request recording still occurs before the response. The completed-pass test still checks the exact `sync`/three-`sync-status` sequence. The pending-pass test still checks the 500 ms lower bound, its outer upper bound, and the status-request types. Refusal/forgotten-request cases still check their exact sequences. Hook tests still check request suppression after the report, exit codes and absence of a block. Transport failure is already tolerated by `syncOnHeadMove` as its documented fallback to the daemon's later pass; the listener changes no such contract. No meaningful assertion was removed or bypassed.
