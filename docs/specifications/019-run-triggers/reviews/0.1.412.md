## Blocker B1 — the printed source-path command does not run all the files it says it runs

**Proven.** `src/cli/status-wait-groups.ts:75` retains the original source paths, while `:121` renders the promise using the entire left-file count and list. In particular, `:134` says the narrow command “runs them now and waits for their results”; `:136` makes the same promise for a required stop group.

A named wait selects every valid closure reader of a source (`src/cli/named-selection.ts:97`). A narrow run intentionally selects the source's edit work (`src/core/scheduler/narrow-run.ts:52`), which can be fewer files. Passing the same path to these two operations does not establish the same selection.

Independent reproduction:

```json
{
  "checks": [{"name":"browser","runner":"vitest","tests":["test/**"],"at":"manual"}],
  "runner": {"tierSize":1}
}
```

Three test files directly import `src/core.ts`: `test/core.test.ts` (30 ms), `test/x.test.ts` (10 ms), and `test/z.test.ts` (50 ms). All wait for the manual request. A real `waitForNamed` for `src/core.ts`, followed by `namedText`, reports all three left files and prints:

```text
3 browser test files wait for `squeal run browser`, which this wait does not hold for: test/core.test.ts, test/x.test.ts, test/z.test.ts; this repository does not require them before you finish; `squeal run browser src/core.ts --wait 60000` runs them now and waits for their results
```

The probe supplied `node <absolute candidate bundle>/cli/squeal.mjs` as the CLI name, extracted the command from that output, and executed it unchanged with `/bin/sh -c` in the same worktree. The socket used production `groupRequests` and `requestGroup` with the real scheduler. Result:

```text

```

The runner log contains only `test/core.test.ts` and `test/x.test.ts`. `test/z.test.ts` remains non-current. The narrow command itself follows D6 correctly; the new status guidance makes the false promise. This violates the brief's command-as-printed check and the vision's requirement for trustworthy state. The added text tests use test-file paths, so they do not check this seam.

**Repair sized for one worker:** keep the approved original-path command and the narrow command's edit rule. Change the clause to state that this command runs and waits for the paths' edit work, without claiming that it covers the entire left-file list. Keep the whole-group command as the explicit way to cover the rest, and keep the stop requirement for all required files. Add a source-path case with a namesake, more direct readers than `tierSize`, and a reader left over; execute the printed command and assert both the work it does and the limits the status text states. If exact equality with the left-file set is required instead, that conflicts with reusing source paths under the existing edit rule and needs a spec decision before changing either selection contract.

## Should fix S2 — discarding a report can still cause a random missing-coverage failure

**Proven helper behavior; plausible remaining CI flake, non-blocking.** `test/keys/validity/coverage.ts:47` now skips JSON parse failures. The safety claim is correct for the coverage proof: `unrun` at `:114` requires a positive count in at least one complete report. Removing a report cannot create a positive count or cover a previously uncovered line. It can only preserve or enlarge the set of unrun lines. It therefore cannot cause a false coverage pass. This does not mean the check becomes strictly harder on every skip: redundant coverage can leave the result unchanged.

It also does not prove the random failure is gone. The independent probe wrote a complete report that alone covered line 1 of `x();`. `unrun(..., coverageOf(...), [1])` returned `[]`. Truncating that report made `coverageOf` skip it and `unrun` return `[1]`. For a changed runtime line covered only by a killed process, the symptom can move from `SyntaxError` to “changed lines no case runs” (`test/keys/validity/verdict.ts:260`). This review did not reproduce that race naturally in CI, so it is not a proven failure of 011-305's done-when.

The worker's notes identify the writers and explain the terminal partial-file case. `sides.ts` waits for driver close, and nonzero driver exits fail the comparison. No new wait was added. The precise cause of the original CI file's truncation remains inferred; a parse error alone does not prove that every writer had ended. A terminal partial file cannot be repaired by waiting longer.

**Follow-up sized for one worker:** make required coverage from deliberately killed children deterministic, for example by recording it before the deliberate kill, and keep the skip as a fallback for terminal partial reports. Add a regression in which the discarded file is the sole positive report for a required line. Do not weaken the unrun-line gate or count malformed coverage as evidence.

## Requested note — production hashing still pays configured filter costs

**Proven mechanism, pre-existing and non-blocking.** The new `test/hash/git-index.test.ts:16` hooks set `GIT_CONFIG_NOSYSTEM=1` and `GIT_CONFIG_GLOBAL=/dev/null` for each test; `vi.unstubAllEnvs()` restores the prior values afterward. This aligns production calls inside the tests with their already-isolated fixture Git calls. It is a valid test isolation repair.

Production `readCleanIndexHashes` still invokes `git status` before excluding converting attributes (`src/core/hash/git-index.ts:55` and `:83`). `runGit` preserves user and system config, and these calls give it no timeout. A clean filter can run for a path whose index hash Squeal will discard afterward.

The independent probe committed `big.lfs` under `*.lfs filter=lfs` with the fixture's isolated config, then called production `readCleanIndexHashes` with a temporary global clean filter that records a call, sleeps 200 ms and passes stdin through. The filter ran once; the call took 226 ms; `big.lfs` was correctly absent from the returned map. This proves the cost remains on a user host with such a filter. It does not prove an actual Git LFS call caused the original CI timeout, nor that ordinary LFS startup takes five seconds.

This is a product performance follow-up worth recording, not a regression in this test-only repair. One worker can add a slow-filter fixture and bound or avoid conversion-filter work in the index shortcut, while preserving the rule that converting files are byte-hashed. Do not copy the test's global/system-config suppression into production: production must still honor the user's conversion settings for correctness.
