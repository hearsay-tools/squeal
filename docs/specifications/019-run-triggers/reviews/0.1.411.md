## Blockers

### B1. Proven: the no-edit primer can exceed its cap

Location: `src/harness/shared/primer.ts:82` and `:107` to `:120`.

D6 requires: "The primer stays within `PRIMER_CAP_CHARS` and its folding order." The longer no-edit opening can leave no fitting rendering. The final `return text` then returns the over-cap `none/plain` form.

Reproduction through the existing `repoFor` and `sessionStart` helpers:

```json
{
  "checks": [
    { "name": "lint", "lint": true, "at": "stop" },
    { "name": "unit", "runner": "vitest", "tests": ["test/unit/**"], "at": "stop" },
    { "name": "node", "runner": "vitest", "tests": ["test/node/**"], "at": "stop" },
    { "name": "browser", "runner": "vitest", "tests": ["test/browser/**"], "at": "manual" }
  ],
  "slow": { "include": ["test/browser/**"] }
}
```

List only `test/browser/core.test.ts`, project `""`, with `replace: true`. Thus no listed file belongs to the default `tests` group. The legacy slow declaration is valid even though the named group owns that file. Actual hook output:

```text
REAL_PRIMER claude-code 1590 cap=1500 narrow=false
REAL_PRIMER codex 1522 cap=1500 narrow=false
```

Both exceed the cap. Neither keeps the narrow-run example. A pure-renderer control with the old edit wording fits at 1,471 characters; the same coverage with the no-edit flag is 1,570. This is a regression introduced by the new text, not a request to repair arbitrary old oversized policies. `trailingPrimer()` refuses a primer over the cap, so hook text cutting also loses its guarantee to preserve the whole primer.

One-worker fix: give the no-edit text a bounded rendering that fits this existing slow-tier combination while preserving the specified folding order and warning. Extend the primer matrix across slow settings, coverage folding and long Codex CLI names. Keep the edit-policy output byte-identical. Do not solve this by slicing off sentences.

### B2. Proven: a selected unknown file is reported as current

Location: `src/cli/run-group-narrow.ts:131` and `:140`; producer: `src/core/scheduler/narrow-run.ts:95` to `:108`.

The renderer computes `current = selected - queued`. A file excluded from queuing because its key is absent or its runner is blocked is unknown, not current. This violates the vision's state-honesty rule and the styleguide rule to record a fact where it is known.

The probe used a real scheduler, a manual `browser` group and one file, `test/browser/a.test.ts`. Its runner's `closure()` threw `Error("closure failed")` during startup. After startup and idle, `requestGroupPaths("browser", [file])` selected it and queued zero files. No run occurred, and `side.current(file)` was false. Passing that actual answer to the CLI renderer produced:

```text
Group browser at revision 0: these paths select 1 test file, current; none runs again.
```

This affects the command without `--wait`, which can give the agent only that false current claim and exit 0. With `--wait`, the store verdict can correctly say unknown, but the same false line is still appended. The existing tests cover current passes and failures, not a selected file that could not be queued.

One-worker fix: remove the inferred current claim, or carry an explicit classification from the scheduler in the narrow answer. Name files that could not be queued and their reason. Add a CLI/scheduler regression for a failed closure or environment call, plus the mixed case with a current file and a blocked file. Preserve `--wait` exit 3 for unknown results.
