## Blockers

### B1. Proven: typed lint files bypass the pause and Stop hold

Location: `src/core/lint/pass/run.ts:89`, `:92`, `:97`, `:109`.
The changed boundary gives `lintParts` a hold and also passes its unfiltered
program feed. The existing `parts.ts:215` takes `ctx.feed` before the held
queues; `lint-part.ts` then lints and judges those files. The new moment
contract does not cover this entry path.

019 D1: “at `pause` an edited file waits and is linted when the agent
pauses; at `stop` the same”. Wave 9 test 1 requires that an edit lints
nothing before the pause.

Reproduction, separately at `pause` and `stop`:

1. Use `FakeProvider` with `program = ['src/a.js']` and
   `wholeProgram.add('src/a.js')`. Give the lint group that moment.
2. Lint the initial `ok` file while paused.
3. Set `pauseIn` to 60000, edit the file to `bad no-undef`, and run the pass.
4. Expected no lint call and a pending check. Actual output for both moments:

```text
calls: [ [ 'src/a.js' ] ], state: { 'src/a.js': 'fail' }
expected [ [ 'src/a.js' ] ] to deeply equal []
```

This is the new pause/Stop path through a pre-existing feed seam, not a
finding against unrelated old code. It defeats the row's purpose for typed
projects: edited program files still lint while the agent works.

Fix sized for one worker: make the moment hold govern the program feed as
well as pending/stale queues. Keep changed program bytes available for the
eventual released call, so the fix preserves 017 D5's worker-byte and key
contract. Do not discard the feed to suppress this call. Add these two
tests, then verify the program-feed and commit regression tests.

### B2. Proven: lint finished before Stop can exceed `stop.maxHolds`

Location: `src/harness/shared/stop-slow.ts:330` through `:337`, together
with `src/harness/shared/stop-decide.ts:240` through `:249` and
`src/harness/shared/stop-lint.ts:58` through `:65`.

019 D1 requires more lint holds only under `lint.blocking`, “within
`stop.maxHolds`”. D4 step 3 makes that the number of holds per consumer and
turn. The waiting entry now holds for a settled lint failure, but the quick
entry still treats that same required failure as a general lint-policy
block. It sets `held` only for open checks. A settled lint block consumes
no hold, so the waiting entry later spends the full budget again.

Reproduction in **both Claude Code and Codex**:

1. Group `lint` at `stop`, `lint.blocking: true`, `stop.maxHolds: 1`.
2. Start a turn; edit `src/a.js` from pass to `bad no-undef`.
3. Explicitly release/run `lint` and let it finish before Stop.
4. First quick Stop blocks with the lint-policy reason and the FAIL line.
   `readStopHolds` is **0** after that block.
5. Next quick Stop with `stop_hook_active: true` is silent. Its waiting
   entry blocks again for the same lint failure and calls this the last hold.

Actual: **two blocks at a configured limit of one**. The finding is the new
settled-lint hold combined with the quick entry's existing policy route;
the original route alone did not add this second waiting-entry block.

Fix sized for one worker: give required lint failures one decision and
budget owner across both entries. A quick-entry block for a required lint
failure must consume the same turn budget, or that reason must be handed
to the waiting entry when it owns required checks. Keep general lint
blocking for tools outside the required groups. Add precompleted lint
cases for limits 1 and 2 in both harnesses, including completion at a pause
and after `squeal run lint`, and verify the untrusted-waiting-entry path.

### B3. Proven: display truncation can hide the only required lint failure

Location: `src/harness/shared/stop-lint.ts:86` through `:94`.

`untoldLintFails` decides whether Stop must speak by reading only
`readLintNews(...).news.entries`. That list is capped at five across all
tools (`LINT_LISTED_MAX`); it is a presentation list, not the complete
required-failure set. Entries from another group's tool can fill it.

019 D1 says Stop waits for the lint and tells its findings by 017 D8.
017 D8 says an untold lint change is news at Stop by itself. The vision
requires delivery of new failures without silently losing the last edit.

Reproduction in **both Claude Code and Codex**, with `lint.blocking: false`:

1. Enable ESLint and oxlint. Put ESLint at `pause`, oxlint at `stop`.
2. Start a turn over six initially passing files `src/a0.js` through
   `src/a5.js`. Edit the first five to findings of `no-undef`; edit the last
   to a finding of `other-rule`. The fake oxlint disables `no-undef`.
3. Quick Stop ends the turn silently while the held lint is pending.
4. While idle, finish both lint passes before the waiting entry decides.
   There are six ESLint failures and one oxlint failure, all untold.
5. The waiting entry returns silence. The first five news entries are all
   ESLint's, so `untoldLintFails` finds no Stop-group entry.

Actual output, independently for each harness:

```text
quick: {}, waiting: {}
news: { v: 1, entries: [five ESLint entries], more: 2 }
expected undefined to be 'block'
```

The follow-up read proves news remained untold after Stop; another tool
boundary would be needed to deliver it. This is not an overflow-count
delivery: neither Stop entry delivered a count or a finding.

Fix sized for one worker: decide from all relevant untold failures before
the display cap, then cap the rendered delivery as usual. Preserve the
read-only decision and acknowledgement-after-delivery contract. Do not
advance the lint view just to inspect failures. Add this mixed-tool case
and a case where the Stop group's only failure lies beyond the display
cap. Verify one delivery and silence on the next Stop.
