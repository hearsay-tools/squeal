## Nonblocking follow-ups and limits

### 1. Merge hold's delayed edit note: pre-existing mechanism

**Proven pre-existing mechanism; plausible explanation of the worker's uninstrumented 1-in-14 failure.** The ordinary merge scenario passed once on each actual Codex runtime. That alone does not clear a rare race.

The controlled probe ran that fixture on each runtime, waited for the conflicted edit and pending test, temporarily set `refinedMetaKey(worktreeId)` to the previous revision, and called the first tool boundary. It got the merge hold and no edit note. It then restored the recorded refined value and called the next boundary. **Both 0.1.399 and 0.1.400 emitted `Squeal saw your edit and queued 1 test file; results arrive ...` without a hold line.** The probe's first attempt used a guessed meta key and failed its setup assertion; the corrected attempt used the exported key function and passed both cases.

This matches a hold row being visible before runner refinement. `hold.ts:175` publishes independently; `edits.ts:134` withholds the edit note until refinement. `delivery.ts:287` records the hold as told, but `delivery.ts:308` later permits an edit note by itself without checking a continuing hold. These mechanisms are unchanged in this range. With no HEAD move, the new commit-boundary wait is not entered. The changed fixture exposes current runtime behavior that the seed tests could miss. **Judgment: not a regression introduced by this candidate.** The original failing run's exact interleaving remains unverified.

Not fixed here, as requested. A separate worker can add the hold-before-refinement ordering case and make edit-note delivery describe or defer to an active hold, while preserving the single hold-change delivery.

### 2. Part A's initial lint assertion races its independent listing

**Proven test synchronization gap, pre-existing.** The coordinator reported one concurrent-run failure at `test/e2e/run-triggers.test.ts:85`: lint files/pending were 0/0 rather than pending 3; 11 of 12 tests passed. This review's required direct run passed both legs.

The baseline at line 83 waits for `e2ePending(s) === 2`. `settleEdit` (`run-triggers-support.ts:197`) waits for the edit test groups and runner refinement only. It does not wait for lint. The daemon nudges its separate lint pass without awaiting it (`daemon.ts:769`, `daemon.ts:810`). The assertion and its predicate are identical in 529d3b01b. Thus the observed 0/0 snapshot is permitted before lint lists its files; it does not prove that the product failed to list them eventually.

One test worker can extend this baseline's acceptance predicate to require the fixture's exact lint file and pending counts, **3 files and 3 pending**, with zero failures, before the assertion. Keep this local to the baseline; later moments intentionally have different lint states. No product change is indicated by the reported evidence.
