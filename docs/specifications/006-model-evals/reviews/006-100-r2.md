- `evals/lib/prepare.mjs:123` retains the runtime and writes the update hold. `holdCodexUpdates` at line 145 writes a whole schema-1 `runtime/update.json` whose next check is 59 minutes away. This is within the updater's accepted one-hour interval. Both `scheduleRuntimeUpdate` and `updateRuntime` read that state; they schedule nothing or return `not-due` without transport calls.

## The two requested limits

**An explicit `squeal update` inside the session is not a blocker.** It deliberately bypasses the scheduling hold. If it publishes a newer runtime, the final check rejects the cell before grading. If it finds no newer runtime, the cell's measured runtime has not changed. Such a rejected cell costs a session and must be reported as failed, never as a valid measurement of the pin.

**A timeout near an hour is not a blocker.** The hold is finite, and the repair does not promise permanent update suppression. The default per-turn timeout is 900 seconds; every turn renews the hold. If a longer turn or another startup after expiry permits a new runtime to be retained or selected, the final check rejects the cell. This can waste a long run, but it does not reproduce B1's falsely attributed grade. No test or review claim should call the runtime immutable under every explicit action or arbitrary duration; the guarantee here is that a cell with detected runtime movement is not graded.
