## Blockers

### B1. Proven: the final count turns an unknown write into a definite not-kept claim

Location: `src/core/code/gate/keep.ts:111` and `:116`, with `src/core/code/gate/keep-write.ts:234` (`keptCount`). Evidence: `test/code/gate/keep-daemon-lost.test.ts:109` to `:131`.

D17.5 requires the final line to say how many completed files are kept and what the next run runs. Vision principle 2 requires stated uncertainty. The existing lost-answer path correctly says the file may be kept. The new final line then contradicts it.

The targeted test "says the file may be kept when the daemon took the write and stopped answering" passes on this candidate. Its proxy lets the daemon write the results but holds that answer and drops later requests. It asserts both:

- `notes[1]` is `0 of 1 completed test files are kept in the stores; the next run on the same bytes runs it`;
- `resultsAt(at.commonDir)` is `1`, with the comment "The daemon wrote it: the next run reads it."

`writePass` retains only `written` for the totals. `KeepUnknown` reaches the earlier warning, but its uncertainty does not reach `keptCount`. The last line is therefore false even in the candidate's own passing test. A warning on the previous line does not make that definite final claim true.

**One-worker fix:** carry an unknown file outcome through the pass and keeper totals. The final line must distinguish confirmed kept, confirmed not kept, and unknown, and describe the next lookup conditionally for unknown files. Reconcile by file identity if an early uncertain write is later confirmed. Change this lost-answer test to reject the definite zero-kept/rerun claim while retaining its store assertion. Keep the definite no-daemon/no-write case and normal count forms covered. JSON, verdict and exit code stay unchanged.

### B2. Proven: a successful part of a daemon reads merge does not reset the bound

Location: `src/core/code/gate/keep-seen.ts:151` to `:159`. The called boundary is `src/core/code/gate/keep-sent.ts:132` to `:137`.

D17.5: "each write that lands (a file's coverage write, its results write, the reads merge) starts it again." The new callback runs only after the whole `writer.seen(seen)` call succeeds. The daemon writer splits that call into 4 MiB writes. When one part succeeds and a later part is busy, it returns `busy` without reporting the successful part. `keepSeen` can then spend the quiet bound while writes have landed.

A temporary protocol probe used the real `writeThroughDaemon`, `partsOf`, `keepSeen`, `InputCheck` and `StoreWait`. A local socket server supplied the outcomes; no SQLite behavior was simulated beyond those protocol acknowledgments. The payload contained 45,000 distinct paths (`src/${i}-${"a".repeat(90)}.ts`) in one file's `add` list and split into two parts. The fake clock and responses were:

1. First attempt's first part: busy at 0 ms. This starts the wait.
2. Retry's first part: confirmed kept at 29,000 ms.
3. Retry's second part: busy at 31,000 ms.

With `boundMs: 30000` and `runMs: () => 60000`, `pnpm exec tsx /tmp/s508-probe.mts` exited 0 and printed:

```json
{"parts":2,"requests":3,"writes":[29000],"signals":0,"clock":31000,"outcome":"spent","stop":"quiet","msSinceWrite":2000}
```

The quiet limit stops just 2 s after a confirmed write. The ceiling has not expired. The temporary script and socket directory were removed; the candidate tree stayed clean.

**One-worker fix:** report progress at the individual reads-write boundary, before a later part can return busy or fail. For example, pass the landed callback through `KeepWriter.seen` to each confirmed part, or move part iteration to the layer that owns that callback. Preserve one signal for a local merge and no signal for a refusal, lost request or absent merge. Add a two-part regression with the timing above; assert that the later busy response does not stop the quiet bound. Retain the independent total ceiling and input rechecks.
