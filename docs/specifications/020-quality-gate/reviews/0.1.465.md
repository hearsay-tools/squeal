### S1 — proven, non-blocking: `seen` parts do not enforce the documented 4 MiB bound

Location: `src/core/code/gate/keep-sent.ts:180-195`.

D17.3 says the reads go “in parts of at most 4 MiB”. `partsOf` never splits one file's reads and only checks the bound when a part already has an entry. A single entry can exceed it. It also omits the array, separator and write-wrapper bytes from its accounting. The new test `test/daemon/keep-seen.test.ts` explicitly expects an oversized entry to remain whole.

Pure-function reproduction, with real default `SEEN_BYTES`:

```ts
import { partsOf, SEEN_BYTES } from './src/core/code/gate/keep-sent.ts';
const seen = [{
  ref: { project: '', path: 'test/a.test.ts' },
  add: Array.from({ length: 50000 }, (_, i) => 'data/' + i + '/' + 'x'.repeat(100)),
  direct: [], modules: [],
}];
const parts = partsOf(seen);
console.log(JSON.stringify({
  limit: SEEN_BYTES,
  parts: parts.length,
  bytes: parts.map(p => Buffer.byteLength(JSON.stringify({ kind: 'seen', seen: p }))),
}));
```

Output: `{"limit":4194304,"parts":1,"bytes":[5688994]}`.

This proves the size mismatch. It does not prove a refused socket request or a wrong stored result; the observed write is below the transport's 32 MiB limit. Non-blocking. One worker can split a large file's lists across entries bearing the same `ref` and account for the serialized envelope. The merge is additive. Test serialized sizes at the boundary and one file larger than the limit, preserving all three lists and their order.
