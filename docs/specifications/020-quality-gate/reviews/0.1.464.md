## Blocker

### B1. Proven: a dead Vitest file is later reported as still running

Locations: `src/runners/vitest/reporter.ts:156`, `src/runners/vitest/adapter.ts:748`, and `src/core/code/gate/collect.ts:223`.

Spec D3.4 says stderr names each file "still running past its estimate". Vision principle 2 requires current state: "An old result never gets to pose as the current truth."

`moduleQueued()` starts a file's timer through the new callback. Only `moduleEnd()` calls its returned end callback. A worker that dies before that event leaves the callback in `RunCollector.#running`. Neither `runEnd()` nor the adapter's run `finally` drains it. The gate closes `FileProgress` only after **all** runner lanes settle. A slower node:test lane therefore keeps the dead Vitest file's timer alive, and the CLI prints `Vitest is still running ...` after Vitest has returned `crashed`.

The real-run probe used a temporary copy of `test/fixtures/code/gate/lanes`. It replaced `test/b1.test.ts` with:

```ts
import { test } from "vitest";
import { b } from "../src/b.ts";
test("crashes", () => {
  b(1);
  process.kill(process.pid, "SIGKILL");
});
```

It called `collectEvidence` with changed paths `src/a.ts` and `src/b.ts`, the real CLI adapters, no stored durations, and a 12 s budget. The existing `n1/slow.test.ts` held the node:test lane until the deadline. Instrumentation wrapped Vitest's `fileStarted` callback and its returned end, wrapped `adapter.run()` to record its return, and recorded `overran`. All elapsed numbers are milliseconds from probe start.

Actual output, with unrelated quick node:test evidence omitted:

```json
{
  "trace": [
    ["started", "test/b2.test.ts", 904.016433],
    ["started", "test/b3.test.ts", 904.3132910000002],
```

There is no `ended` for b1. Almost ten seconds after its run ended, `overranText()` reports b1 as still running. The gate correctly keeps these files incomplete; the defect is the false live status.

**One-worker fix:** make adapter run settlement end every outstanding file-start callback, including crashes, rejected runs and cancellation without a module-end event. Drain callbacks idempotently so normal module ends still call each once. Keep the start history used by `notStarted`. Leave other lanes' timers active. A collector/adapter cleanup boundary is preferable to changing verdict logic.

**Done when:** a real Vitest worker dies beside a long-running node:test lane; its start hook ends once at run settlement; no later progress line names that Vitest file; the node:test file is still named once; the verdict remains incomplete and `--json` stdout remains one object. Keep a focused regression for callback cleanup on abnormal run settlement. No policy or key-version change is required for a wording repair.

## Should-fix

### S1. Proven, non-blocking: a throwing node:test start or end hook leaks its acquired slot

Location: `src/runners/node-test/run/run.ts:211` and `:234`.

The start hook runs before the `try`. The end hook runs before `slot()` inside the `finally`. If either throws, the slot is never returned. This falls outside the normal gate callback behavior demonstrated here, so it is a hardening note, not a proven break of a row's done-when. The daemon gives neither hook.

A small probe called `runNodeTest` twice, each with a fresh `SlotPool(1)`, one file, `timeoutMs: null`, and `/does-not-exist` as the executable. The first start hook threw. The second returned an end hook that threw after the failed spawn. After each caught rejection, it asked the pool for another slot and immediately aborted that wait. A returned slot would have resolved to a release function before the abort; both waits instead returned null:

```text
Error: start hook threw
start next slot: null
Error: end hook threw
end next slot: null
```

**One-worker fix:** cover the start hook with the acquired slot's outer `try/finally`, and put the end hook inside a nested `try/finally` that always releases the slot. Preserve error propagation or report it explicitly. Add focused tests for both throws. This may share B1's hook-cleanup row, but need not block that repair.
