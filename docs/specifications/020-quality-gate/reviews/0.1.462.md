## Blockers

### B1. Proven: a busy store open aborts collection and loses the report

Location: `src/cli/code-gate-log.ts:72` (`openStore` is outside the `try` at line 77). Downstream: `src/core/code/gate/evidence.ts:142` awaits the keeper without catching it; `src/cli/code-gate.ts:227` catches the resulting collection error and returns the setup-error path.

D17.5 says: "past the wait the log is not kept, with a note". Row 020-40's done-when also requires "verdict, exit and JSON rules unchanged".

`openStore` can throw on a busy open, not just return `StoreOpenFailure`. For example, the gate can start with no store, run its tests, and reach log retention while another worktree's daemon is still initialising the common store. An uncommitted schema transaction leaves `user_version` at zero to this connection. `openStore` reaches `migrate`, whose write lock times out and throws. The log keeper catches busy failures of its own row write but not this earlier failure.

I reproduced the failing boundary using the real SQLite opener, without mocks. A temporary git repository had no worktree registration. A second `DatabaseSync` connection to `.git/squeal/store.sqlite` held:

```sql
PRAGMA journal_mode=WAL;
BEGIN IMMEDIATE;
CREATE TABLE starting(value TEXT);
```

A real temporary log folder contained `vitest.log`. I then called `runLogKeeper(root, { note, busyTimeoutMs: 50 }).keep(...)` with one failed run's file and that folder. The probe imported the candidate's source with `tsx`:

```text
$ pnpm exec tsx /tmp/squeal-462-open-probe.mts
{"rejected":true,"message":"database is locked","notes":[],"elapsedMs":53}
```

The 50 ms test setting scales down the same busy timeout used in production. The log callback rejects instead of returning `null` and issuing a note. The source call chain then rejects `collectEvidence` and `collectWithStores`; `gate` calls `fail`, emits no report on stdout and returns 2. Thus a completed failed-test run that should report `incomplete` / exit 3 becomes a setup error, and `--json` has no object.

**One-worker repair:** include store opening in the log keeper's handled failure path. Close only a connection that opened. A busy or failed open must produce one bounded log-unavailable note and return `null`. Add a regression that holds an initialisation or migration write lock before log retention and checks that the CLI still emits one JSON report with its original verdict and exit code. Keep the existing 2 s bound.

### B2. Proven: prune can remove the row before the copy creates an orphan log

Location: `src/cli/code-gate-log.ts:92` finishes the row before committing and closing; `src/cli/code-gate-log.ts:101` copies the folders afterwards. The existing deletion rule is `src/core/store/prune.ts:187` (`dropRuns`).

D3.5 requires the kept folder to be "named by a finished `runs` row of the main store, so the store's prune removes it". The brief explicitly requires the kept logs to be pruned.

A gate-only worktree has no `worktrees` row. Its finished log row has no referring result. Any repository daemon's next prune may therefore remove that row immediately, even while the gate is still retaining its log. Committing the row before copying prevents an orphan on an insert failure, but does not protect against this deletion between the two operations.

I ran a deterministic interleaving with the real store and prune. A temporary git repository had no worktree registration; its source folder contained `vitest.log`. The probe replaced only the `node:fs` copy boundary, synchronised the named builtin export, and ran `openStore(commonDir).prune({ now, retentionDays: 7, maxSizeMb: null })` immediately before calling the original `cpSync`. No store or prune result was mocked. This schedules a repository daemon's valid prune between the row commit and the first copy. The keeper and both prune calls were candidate code.

```text
$ pnpm exec tsx /tmp/squeal-462-log-probe.mts

{"pathReturned":true,"folderExists":true,"rowExists":false,"notes":[]}

```

The second prune used a time 30 days later. It still removed nothing: prune enumerates rows, not unnamed folders. The gate returns a log path with no owning row, and that folder is outside the retention mechanism. This is an executed interleaving, not an untested race claim. The external probes cleaned up their temporary repositories and restored the copy function.

**One-worker repair:** make completion of the copy conditional on the owning row still being present. For example, after the last copy, check the row and remove the copied directory and return `null` with a note if prune removed it. Handle errors of that check with the same cleanup guarantee. Copying must not hold a long SQLite write transaction. Add a deterministic prune-between-insert-and-copy regression that proves the keeper leaves either a row-owned folder or no folder. Preserve the pre-report finished-row requirement and the busy bound.
