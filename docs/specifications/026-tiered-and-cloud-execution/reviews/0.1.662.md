## Blockers

### B1 — proven: the scratch filter drops an input that the current result key retains

Changed location: `src/core/runner-host/remote/lane-proof.ts:128-130`, consumed by `lane.ts:818-828`.

Contract: row 026-38 says **“Proof drops exactly what the key drops”**. Spec 021 D11 requires the observed inputs' remote blobs to equal the revision's. Vision principle 2 forbids a result from posing as truth for different bytes.

`keptObservations` drops every differing ignored read below a directory in this run's `written`. That bound limits **new observed growth** in `scheduler/observed.ts`; it does not remove an input already retained from an earlier run. `WorktreeKeys` keeps shared observations and has already added that path to its effective closure. The lane's `runInputs` uses the runner's closure, which need not contain a prior filesystem observation. Thus the `expected` union does not rescue that path.

Concrete case and probe:

1. Git ignores `scratch/`. A prior read has added `scratch/input.json` to `WorktreeKeys` with local bytes `local\n`. Track it before `beginRun`; its current keyed closure includes the path.
2. The remote has `scratch/input.json` with bytes `remote\n`, created outside sync. The runner's static closure names only the test and its source.
3. The remote run reads that input. It also creates/writes a sibling output under `scratch/`, reporting `paths: ["scratch/input.json"]` and `written: ["scratch"]`. The read input itself is not rewritten by this run.
4. The new filter drops the input's mismatch as scratch. The lane returns the file completed after one remote run, with no resend or local fallback under `whenLost: "not-run"`.
5. At record preparation, the path is already in the keyed closure. There is no new growth or first-seen path. Local bytes did not move. The real `storeDecision` returns `store`, at `ran`, `current: true`; the key remains unchanged and still includes the input.

Observed proof output:

```text
remoteRuns=1 localRuns=0
storeDecision={kind:"store",at:"ran",current:true}
keyUnchanged=true keyKeepsPath=true
localBlob=40830374235df1c19661a2901b7ca73cc9499f3d
remoteBlob=9c998f7b995a7327177b38a90d1385170df2b94b
```

This accepts a remote result whose read bytes differ from the bytes named by its local key. The existing screenshot regression covers a fresh scratch path only and does not exercise a retained observation.

**One-worker repair:** make proof retention account for the actual per-reader keyed closure and retained observed inputs before applying the written-directory bound. Keep one owner for that decision; keep the intended exclusion of fresh scratch output and applied runtime files. Add a regression with a previously retained ignored input and a write to its parent directory. Unequal retained bytes must refuse only the affected file under `not-run`, or run that file locally under the default policy. Equal retained bytes must still pass. Do not prune shared observations to make the proof agree.

### B2 — proven: intent-to-add is lost, and the freshness hash cannot detect the loss

Changed locations: `src/core/runner-host/remote/providers/agent37/git-index.ts:25`, `:87-109`, `:43-44`; `bootstrap.ts:119-123` includes this hash in freshness.

Contract: row 026-39's outcome is **“The remote Git index matches the local staged index”**. Spec 026 D8.4 permits repository-reading tests remotely only when Git metadata is verified current.

`git ls-files -s` contains the mode, blob and stage, but omits the intent-to-add flag. `git update-index --index-info` therefore reconstructs a local `git add -N` entry as an ordinary staged empty blob. Both entries have the same `ls-files -s -z` bytes, so `INDEX_HASH` agrees and `gitKeeper.current()` returns true despite different staged semantics.

Real-Git reproduction through `gitKeeper` and fake SSH:

1. Commit a base file. Create a new nonempty file and run `git add -N -- <path>`.
2. Sync through the candidate's keeper. It returns true.
3. Local and remote `git ls-files -s` are equal, as the existing regression checks.
4. Local `git diff --cached --name-only` is empty. Remote output contains the new path as a staged addition. Local `git ls-files --debug` reports flags `20004000`; remote flags are `0`.
5. A second keeper sync makes no SSH call and still reports current. It cannot repair the difference because the hash omits it.

The probe's filename included a double quote, tab, newline and literal `$(not-executed)`. That exact path survived the transfer; this failure is semantic index loss, not shell path parsing.

The existing intent-to-add test compares only `ls-files`, so it passes while the staged diff differs. A repository-reading test that inspects staged changes can now get a different answer on the remote while the capability claims current metadata.

**One-worker repair:** include semantic intent-to-add state in the local/remote freshness comparison and preserve it in index transfer without changing tree-host-owned working files. Verify staged diff output as well as listing, including transitions between intent-to-add and an ordinary staged empty file. Keep coverage for renames, stages 1–3, weird paths and zero SSH calls for a genuinely unchanged index. Until unsupported state is faithfully transferred, do not advertise it as current.
