## Should-fix

### S3 residual. Proven, nonblocking: the coverage lookup depends on a 256-file diagnostic ledger

Location: new `src/core/code/coverage/runtime.ts:97` through `:99`. Relevant existing contract: `src/core/scheduler/unknown-files.ts:20` and `:83`.

D9.2 requires storing admitted coverage through the normal local store path. The repair finds an alternate-machine result only if `readUnknownFiles` still holds that file's entry. That collection is a bounded diagnostic history: `recordUnknownFiles` retains only the newest 256 entries. Its omission does not establish that a file changed or that its admitted result is absent.

Concrete case: a worktree is keyed to the remote machine, and 257 files finish locally during fallback. The scheduler stores each result only under its executed machine's key and marks the current remote key unknown. After the diagnostic history drops the oldest entry, the new lookup returns no key for that file. Coverage awaiting its result cannot use the admitted executed-key result and is dropped after its result waits. A sufficiently long coverage mapping queue can also lose an older lookup when later unknown-file entries displace it. The original machine-key isolation remains correct.

The final probe used `claimRepo(257)` and the real `side` scheduler with `RUN_MISSING`. Its environment named a synthetic `freebsd/riscv64` remote; its local reports were untagged, taking B1's new local default. After `scheduler.start()` and `quiet()`, assertions confirmed:

- all 257 files ran exactly once;
- each file had an executed-key stored result belonging to this worktree, with a key different from its current remote key;
- the unknown-file ledger contained 256 entries;
- `mainStoreResultKey` returned the correct executed key for 256 files and `undefined` for one, without any edit.

Fix in one coverage/key integration worker: record the admitted `(worktree, runId, testFile)` to actual result-key association, including the current-key guard, where the scheduler knows it. Make the coverage lookup independent of the capped diagnostic history. Preserve admission, run/worktree identity and re-key protection. Add a regression above 256 files that stores coverage for every admitted file under its executed key and rejects coverage after re-keying. Removing the edit guard or merely increasing the diagnostic cap does not settle the contract.
