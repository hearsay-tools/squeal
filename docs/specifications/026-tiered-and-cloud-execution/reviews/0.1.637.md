## Blocking findings

### B1: channel-loss reports bypass the new automatic recovery matcher

**Proven, high priority.** `src/core/runner-host/remote/lane.ts:836` preserves a named crashed reply in `cutShort`. The new matcher at `src/core/runner-host/remote/daemon-lane.ts:183` accepts only `remote <target> unreachable|refused`. The new daemon callback at `src/core/daemon/daemon.ts:957` passes that matcher to `requeueUnknown`.

A real proxy-channel loss produces `the vitest runner host exited (signal SIGKILL)`. The lane returns this string unchanged after its reconnect attempt also loses the host. It contains neither the remote nor the policy. A later successful reconnect can call `onRecovered`, but its predicate rejects these files. Their unchanged `unknownKey` remains set. This defeats 026-30/026-32's goal of healing outage files automatically and also omits the required run-loss context for #278.

The focused probe used the existing real lane fixture:

```ts
const s = await setup({
  whenLost: "not-run",
  remoteRun: async (_root, _hang, _options, kill) => {
    kill();
    return new Promise(() => {});
  },
});
const lost = await s.lane.run([REF], background());
expect(isRemoteOutageReason(lost.failure ?? "")).toBe(true);
```

Actual output: `end: "crashed"`, no completed files/results, failure `the vitest runner host exited (signal SIGKILL)`; matcher returned **false**. This exercises the proxy, not a synthetic already-normalized report. The old `cutShort` behavior becomes a blocker at this wave's new recovery seam.

**Repair:** normalize proven channel loss at the remote lane boundary, retaining the original cause, target and policy. Keep timeouts and genuine test crashes distinguishable; do not broaden the matcher to every runner crash. Add a lane-to-scheduler recovery test that loses both initial and retried channels, reconnects later, then proves those same-key files run and become current.

### B2: automatic recovery uses a 256-file diagnostic sample as the complete set

**Proven, high priority.** `src/core/scheduler/scheduler.ts:1015` reads `readUnknownFiles`, and `:1020` skips each ledger file absent from that map. The existing diagnostic recorder caps it at 256 (`src/core/scheduler/unknown-files.ts:20`, `:83`).

The focused scheduler probe created 257 files with `catchUpRepo`/`catchUpSide`, one shared source, `hostSlots: 1`, `tierSize: 512`, and `RUN_MISSING`. All passed first. After editing the shared source, a wrapped runner returned a crashed, empty report with `remote box unreachable; not run here (whenLost "not-run")` for every file. The probe then restored the runner, invoked `requeueUnknown` with the matching predicate, and waited for quiet.

Actual output:

```text
unknown records 256 current 0
recovered 256 remaining 1
AssertionError: expected 256 to be 257
```

The remaining file cannot match a subsequent recovery call either: its reason was dropped from the sample. This matters directly to the roughly 2,000-file incident this wave addresses. The literal stored-entry algorithm in 026-32 is implemented, but that algorithm cannot meet the wave's recovery goal at this size. The capped recorder itself is pre-existing; the new dependency on its completeness is the break.

**Repair:** keep complete, key-qualified recovery causes for the active ledger, separate from the bounded display sample, or use another complete authoritative source. Preserve the same-key, nonblocked, nonqueued guards and exact cause matching. Amend the brief's data-source assumption. Test at least 257 matching files plus unrelated timeout/crash files, and assert all matching files become current while unrelated files remain unknown.

### B3: the diagnostic parser does not accept this wave's enriched run-loss message

**Proven, medium priority.** Producer: `src/core/runner-host/remote/lane.ts:854`. Consumer: `src/cli/remote-outage-text.ts:202`. The run regex requires `unreachable; not run here` with nothing between those clauses. The new producer inserts `during the run of N files (reason)`.

This exact producer string returned `null` from `reasonOutage`:

```text
remote box unreachable during the run of 1 files (the host ended); not run here (whenLost "not-run"); waits retry once box reconnects or run squeal retry
```

Without a surviving summary/note, the selected file's direct evidence cannot create the required named-wait `Remote:` context. `sideOutageText` at `remote-outage-text.ts:187` also fails to add proof recovery. The raw reason may still appear through other renderers; this finding concerns the shared diagnostic contract and required context/recovery, not a claim that every command becomes silent. Unit fixtures mainly exercise the older message shape and miss the producer/consumer mismatch.

**Repair:** support the current enriched format while retaining old persisted formats. Test the exact lane-produced string as the only evidence across named wait, timeout text, retry where applicable, and proof. Assert the remote, original reason, policy and supported recovery, with unknown/not-comparable unchanged.

### B4: an unrelated runner's remote outage is presented as a selected local file's blocker

**Proven, medium priority.** `src/cli/remote-outage-text.ts:69` accepts the last remote lane note from any runner. At `:79`, that note substitutes for missing direct evidence. `waitOutage` at `:165` only checks whether any selected file is noncurrent. It does not establish that this outage explains that file.

The focused helper probe supplied:

```ts
{
  summary: "command box: unreachable (the host ended); background runs of node-test; planning remote; environment match-local",
  notes: [{
    at: 1, revision: 1, topic: "remote-lane:node-test",
    text: "remote box unreachable since 2026-11-26T00:00:00.000Z (the host ended); 3 files not run",
  }],
  reasons: ["timed out after 60 s"],
}
```

`outageOf` returned `remote: "box"`, `state: "unreachable"`, reason `the host ended`, and the note's timestamp, instead of null. A named local Vitest timeout can therefore gain a line saying nothing runs here in the remote's place and suggesting recovery when node:test reconnects. `proof-green.ts:207` also computes one outage for a whole blocked-file batch and applies it to each file; mixed causes need per-file handling.

This violates 026-31's unchanged non-remote output requirement and #278 research's explicit warning against attributing unrelated outages. It does not produce a false pass, but it gives the wrong cause and recovery.

**Repair:** require selected-file or applicable current listing evidence before using a lane note as the blocker. Use notes to enrich an established cause, with runner/project scope when available. Keep separate global remote visibility from claims that it explains a selected file. Test mixed runners, mixed proof files, local timeouts and active remote outages together. Preserve local bytes and unrelated unknown details.

## Nonblocking note

Wave 12 requirement 026-30.3 says to return without invoking `m.syncGit`. The implementation intentionally retains the provider's local Git-state read, and its exit tests cover no subsequent remote write. No shutdown hang from that read was demonstrated, so this is not blocking. Either move the guard before the read, or record the narrower read-only exception in the brief/status contract.
