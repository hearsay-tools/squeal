## Blockers

### B1. Proven: the daemon's actual exit path does not abort acquire in flight

Changed boundary: `src/core/runner-host/remote/machine-share.ts:183` and `:414`. Caller: `src/core/runner-host/remote/daemon-lane.ts:437`. Provider check: `src/core/runner-host/remote/providers/agent37/index.ts:157`.

The row's O1 requirement is: “daemon exit aborts agent37 acquire and deletes any instance created mid-abort.” The added controller aborts only inside `share.release()`. The existing `withRemoteRelease` caller first awaits the runner's `close()`. A remote lane's close awaits its `connecting` promise, which includes the provider acquire. Thus the acquire finishes before the new abort fires. The daemon has an earlier wait too: `src/core/daemon/daemon.ts:1535` awaits `#starting` before reaching runner close. Remote planning can hold that startup on the same acquire.

Focused reproduction:

1. Configure an eager Agent37 Vitest lane with the mock API and fake SSH, `bootstrap: "tree-sync"`.
2. Hold the mock's `beforeCreate` promise after `POST /v1/instances` arrives.
3. Call `withRemoteRelease(remote.wrap(...), remote).close()`.
4. Let the mock create finish after close has begun. Await close.
5. Assert the mock holds zero instances and received a DELETE.

Actual output:

```text
calls: POST /v1/instances
       GET /v1/instances/mock000001
       POST /v1/instances/mock000001/sleep
instances: [["mock000001", "sleeping"]]
tracked: [{"id":"agent37:eu:vm:mock000001","status":"detached"}]
log: Agent37 instance mock000001 created (eu vm)
AssertionError: shutdown must abort acquire and delete the fresh instance:
expected 1 to be +0
```

No DELETE occurs. The fresh instance remains billed for disk. The new direct-provider tests pass because they abort a test-owned controller; they do not test the daemon-to-share signal boundary.

**One-worker fix:** provide a synchronous begin-exit cancellation path from the daemon before it awaits startup or lane close. Pass that signal to the machine share/provider independently of final release. Preserve final release's wait for active work and cleanup. Keep a create response observable long enough to obtain its id and delete it. Also propagate cancellation through inspect and SSH/bootstrap work: `index.ts:196` and `:202` currently call `ensureNode` and `ensureGitTree` without the request signal, so those steps continue until their deadlines even after a direct abort. Add an integration regression for SIGTERM during held create and during held bootstrap. Require DELETE and zero fresh instances; retain the existing normal sleep-on-exit behavior for an acquired machine.

### B2. Proven: ordinary note retention can remove the active remote's only status record

Changed boundary: `src/core/status/remote-status.ts:21` and `src/core/runner-host/remote/daemon-lane.ts:228`.

D12.1 and the row require plain status to show `Remote:` whenever a lane is configured/active. The summary now exists only as a daemon note. `src/core/notes.ts:64` keeps the last 20 notes globally. It can evict the latest summary even when no newer summary exists. `remoteOf` then returns no remote field, and `remoteLines` prints nothing. The daemon writes the summary on changes and suppresses unchanged lines, so later ordinary notes do not restore it.

A read-only probe seeded one `remote-lane:summary` note, appended 20 untagged runner-failure notes through `withNote`, then read through `readDaemonNotes` and `remoteOf`:

```json
{"before":{"remote":"command cmd:lan-1: awake; background runs of vitest; planning remote; environment match-local"},"retained":20,"after":{}}
```

This uses the actual persistence and read functions. Repeated runner planning errors are one concrete producer of untagged notes (`src/core/scheduler/context.ts:82`). No remote configuration removal or state change is needed. The remote line disappears solely because diagnostic history filled up.

**One-worker fix:** preserve the current remote summary independently of diagnostic-ring eviction, or give its latest entry a retention guarantee. Keep explicit clearing when the remote is removed. Add a status regression that appends more than `MAX_PERSISTED_NOTES` unrelated notes and still renders the active remote's provider, machine, state and modes. Verify that removing the remote clears it after the same history churn. The finding is the new reliance on the ring as authoritative state, not the pre-existing bounded-note implementation.
