## Remaining blocker

### B1. Abort still leaves an Agent37 connection being opened

**Proven, blocking.** `src/core/runner-host/remote/providers/agent37/api.ts:124`, `:181`; `providers/agent37/net.ts:123`, `:212`.

The brief requires the background prune to stop at exit and abort its HTTP calls. The repair passes `signal` into `Agent37Api.remove`. But `#call` awaits `openEndpoint` without a signal. It checks abort only after that operation returns. `openEndpoint`, proxy CONNECT and the TCP/TLS readiness waits have no cancellation input. A proxy that accepts CONNECT but does not answer keeps its request, socket and referenced 60-second timer alive after the prune has returned.

The probe used the actual built-in Agent37 provider and a loopback HTTP proxy. The proxy accepted CONNECT for a dummy HTTPS API host and sent no answer. After CONNECT arrived, the probe aborted the prune, awaited its result, then waited another 200 ms. Actual output:

```text
B1_CONNECT_ABORT {"aborted":true,"connectSeen":true,"openSockets":1,"records":1}
```

The probe had to destroy the proxy socket to clean up. No external host or real API key was used. The added regression waits for an already-sent DELETE over plain HTTP, which has finished connection setup. It therefore proves that phase cancels, but does not cover this earlier phase. The command-hook cancellation repair works for its reported case.

**Repair size:** carry the optional signal through connection setup, proxy CONNECT and TCP/TLS readiness. On abort, destroy the operation's actual request/socket, clear its deadline and reject. Keep the uncertain machine record and start no later release. Add a regression that aborts while a real loopback proxy withholds its CONNECT response; cover a pending TLS handshake through the same cancellation owner. Do not replace this with another promise race.

## N1 decision and new defect in its repair

### Scope is checked on the snapshot, but not before the queued release

**Proven, nonblocking note.** `src/core/runner-host/remote/prune.ts:107`, `:123`, `:144`; `machines-store.ts:92`.

The accepted decision is partly implemented: `recordOf` writes hostname plus mount namespace; startup passes that scope; initial selection skips foreign records; live legacy records are claimed; manual prune still visits foreign records and prints their scope. These branches have current passing tests. `releaseOnce` records its acquired machine in this process's scope before acting on it.

The new automatic-prune filter is not checked again after an await. `stale` rereads the current record but compares only `id`; it ignores the current `scope`. Conditional forgetting also compares only the id. A record that moves to a foreign scope before its turn can therefore still be released and erased by the old scope's prune.

Probe: track A and B in `host-a mnt:[1]`; hold A's release open; start an automatic prune with that scope; replace B's record with the same machine id and key but scope `host-b mnt:[2]`; finish A. This models another namespace recording or claiming the same machine while the first prune waits. The provider is fake and records its calls. Actual output:

```text
N1_FRESH_SCOPE {"released":[["cmd:a","host-a mnt:[1]"],["cmd:b","host-a mnt:[1]"]],"remaining":[]}
```

B is released using the old snapshot even though its current record is foreign, and its new record is forgotten. The fixed-snapshot foreign-record test does not cover this transition. This stays a note under the bounded re-review rule; it does not reopen the closed different-id replacement proof in B3.

**Repair size:** apply the automatic scope predicate to the freshly read record before each release. Use the fresh record's path and scope. Preserve a record whose ownership changes during the provider call by checking the relevant identity and scope inside the registry write lock. Keep manual prune's explicit cross-scope behavior. Add the queued foreign-scope transition and an in-flight scope-change regression.
