## Blockers

### B1. Proven: an excluded local Vitest instance stores a current pass under the remote key

Locations: `src/core/scheduler/record-tier.ts:164` and `:170`; caller boundary `src/core/runner-host/remote/daemon-lane.ts:223` and `:375`.

D10.2 requires: "Local native results (darwin) and remote results (linux) coexist in the same store under distinct keys and never masquerade as each other (vision principle 2)."

The new storage guard acts only when `executedCoreOf` returns a core. An untagged report falls through to `storeFile` under the currently keyed environment. The lane tags its own local fallback and direct branches correctly, but `createDaemonRemote.wrap` returns `spec.here` unchanged when the selected tier set is empty. `vitestOver` uses that route for a local slow/group/beside instance excluded from the configured remote lanes. Planning still comes from the fast lane, which can attach the remote core to the whole Vitest project's environment.

Concrete case: a macOS worktree uses `environmentMode: "remote-key"`, a Linux remote, and `lanes: ["background"]`. The fast lane keys the project to Linux. A slow or named-group instance runs locally, returns no execution core, and gets stored as a current Linux result. The result can then be reused by a real Linux run or CI import consumer. This is a new invalid assumption in the changed recording path, reached through an existing caller.

The probe used actual `createDaemonRemote` and `vitestOver` wrappers with the real scheduler/store fixture. It dispatched `slow:vitest` at the adapter seam while the fast environment named a synthetic `freebsd/riscv64` remote. Assertions passed for all of: remote platform on the stored worktree descriptor; no `executedCore` on the local report; a stored result under that remote key; and one current passing check. The synthetic platform makes the wrong-machine result visible on this Linux review host too.

Fix in one key-isolation worker: give untagged local reports a local machine identity at the recording boundary, or ensure every local producer is tagged, including instances returned when a remote tier is excluded. Do not infer remote execution merely from the project's key. Add regressions through `vitestOver` and the scheduler for remote background plus local slow, group and beside tiers. Assert no result or current pass under the remote key, and a result under the executed local key.

### B2. Proven: a failed slow-machine deletion loses ownership of a billable instance

Location: `src/core/runner-host/remote/machine-share.ts:326`, especially `:330` and `:335` through `:339`.

D11 permits at most one fresh-instance retry. The wave brief also requires lifecycle safety. D7.3.4 keeps machines tracked so removal can stop disk billing.

On the replacement path, `checkDisk` clears `machine` before awaiting `release("worktree-removed")`. It catches and logs any deletion failure, then unconditionally calls `forgetMachine` and throws `FreshMachine`. The next start can acquire a second machine. The first remains alive but has no state record and no in-memory owner. `releaseOnce` sees `machine === null` before replacement, or only the replacement afterwards. Neither daemon exit nor `squeal remote prune` can find the first instance.

This occurs when Agent37's DELETE returns a transient error, or a managed command provider's release hook fails. The probe made acquisition succeed and deletion reject with a simulated HTTP 503. It asserted: one tracked record before the check; `FreshMachine` afterwards; zero tracked records; `current() === null`; and only one release call, `worktree-removed`, even after `share.release()`. The path drops ownership despite explicit evidence that removal did not complete.

Fix in one machine-lifecycle worker: retain the original machine and its record until deletion succeeds. If deletion fails, refuse the lane and retain a recoverable owner rather than starting a replacement that overwrites its record. Preserve the one-replacement bound. Add failed-delete, shutdown-during-delete and successful-replacement cases. Verify that every acquired instance is either confirmed removed or remains tracked for cleanup.

## Should-fix

### S1. Proven, nonblocking: refused disk measurements are not cached per incarnation

Location: `src/core/runner-host/remote/machine-share.ts:303` through `:342`.

D11.1 says "Once per machine incarnation at connect". Only skipped, healthy and warning verdicts set `diskPassed`. A refused static machine, or the second refused managed machine, keeps no cached verdict. Each queued lane start and later reconnect probes the same incarnation again. The retry is bounded, so this does not cause an acquire loop, but it repeats the expensive 20-sync check and can change a refusal without a wake or new incarnation.

Fix alongside B2: cache the full verdict, including refusal, by machine incarnation. Reuse the refusal, rather than marking it passed. Add a two-lane refused-machine test that counts one probe and keeps both lanes refused; wake/loss must invalidate the cached verdict.

### S2. Proven, nonblocking: an absent source path passes remote coverage validation

Location: `src/core/runner-host/remote/coverage.ts:99` through `:104`.

The new decoder promises to drop a record that names a path outside the root. Its `find` predicate detects a non-string path, but an absent `source.path` yields `undefined`, which is also `find`'s no-match return value. The following `outside !== undefined` check therefore accepts it. A record with `sources: [{ blob: "a", lines: "", covered: "", functions: [] }]` and no path reached `shareRecord` and returned an object in the probe. A null source can pass the same path check and then throw while sharing it.

Valid host-generated records have paths, so this establishes a malformed-wire boundary defect, not a demonstrated traversal or false stored result. Existing tests cover an absolute path and `../`, but not an absent path.

Fix in one coverage worker: use an explicit invalid-path index or boolean, validate source shape, and convert sharing/validation failures to a dropped-record diagnostic. Test missing/null source paths and malformed source entries alongside traversal cases. A bad coverage record must not reject an otherwise proven test report.

### S3. Proven, nonblocking: other-machine results have no coverage result-key lookup

Locations: new `src/core/scheduler/record-tier.ts:191` through `:207` and its existing consumer `src/core/code/coverage/runtime.ts:63` through `:75`, wired by `src/core/daemon/daemon.ts:1023`.

The new `storeOtherMachine` correctly stores a tagged fallback under its executed key and leaves the current keyed row unknown. The writer's production `mainStoreResultKey`, however, searches only the current `testFileKeys` key. It cannot find the result under `ownKey`. Thus local coverage from a fallback while keyed remote is dropped after its result waits. The reverse case also drops mapped remote coverage when a daemon was keyed locally during an outage and the remote returns before a planning refresh changes that key.

This loses coverage; it does not put coverage under the wrong machine's key. Normal runs whose executed core equals the keyed core use the existing lookup correctly. The new remote-coverage test supplies a synthetic `resultKey` callback that always returns a per-file key, so it does not test this production seam.

Fix in one coverage/key integration worker: expose the actually stored result key for `(runId, testFile)` to the coverage writer, including an admitted other-machine result. Keep the result/proof requirement and edit protection. Add a real scheduler plus `mainStoreResultKey` plus `CoverageWriter` test asserting coverage under the executed key and none under the mismatched current key.

## Note

### N1. Plausible, nonblocking: wake-time Git refresh is outside the new run lease

Locations: new lease owner `src/core/runner-host/remote/machine-share.ts:282` and `:395`; call path at `:248`; existing provider `src/core/runner-host/remote/providers/agent37/machine.ts:185`.

The carried cross-lane scenario is covered: `refreshGit` waits for active leases, new runs wait for its writer, and runs share a read lease while Git is unchanged. `finally` releases a run's lease; an aborted refresh can leave its wait without writing. Static hosts with no `syncGit` get a no-op lease. The new attached tests pause one run and verify that a second lane cannot refresh until it ends, and verify two concurrent runs on unchanged Git.

One related route remains outside that owner. A lost channel sets the shared machine `awake = false`. A later `reach` calls `machine.wake`, whose Agent37 implementation refreshes Git directly, without `writeGit` or `leaseFree`. If only one lane lost its channel while another still runs, a local commit followed by reconnect could move Git under the surviving run. Ordinary coordinated sleep cannot take this route while a lane is busy. No concurrent reconnect reproduction was run, so this is a note, not a claimed false stored result or blocker.

Follow up in one focused lifecycle/lease worker: hold a run on lane A, lose lane B's host, commit locally, and reconnect B. Assert stable Git during A or a discarded result. If confirmed, make the shared lease the owner of every Git mutation, including wake, and retain abort/shutdown coverage.
