## Blockers

### B1. Proven: fake SSH shares the daemon's capacity pool and deadlocks on a four-CPU host

Location: `test/e2e/spec-026-remote-fixture.ts:56` and `:59`; failures at `test/e2e/spec-026-remote.test.ts:155` and `:206`.

`withRemote` changes HOME but keeps `repo.env.XDG_RUNTIME_DIR` in the fake remote environment. `fakeSshAt` changes HOME again when it runs a remote command, but leaves that runtime directory intact. Both the local daemon and fake remote runner hosts therefore use the same `slowSlotDir` and capacity lock files. They do not model two machines.

On the clean four-vCPU sandbox, both full-checkpoint cases got four results and then stopped making progress. A snapshot of the shared pool showed:

```text
local daemon: want=3, grant=3, cores=0.01, background=0
remote runner-host: want=1, grant=0, cores=0, background=0
```

The daemon holds all three default host slots while the remote waits for one before it can complete the local request. Increasing a timeout cannot release those slots. Both cases failed after the 120-second command deadline. Exact-candidate Node 24 CI reproduced both failures with the same two files pending. Giving only fake SSH its own runtime directory made both cases pass in 15.68 s on the same sandbox.

Fix for one test worker: give the fake remote its own private runtime directory and export it in the generated fake SSH command. Keep the local daemon's runtime directory unchanged. Keep one remote pool shared by that fake machine's lanes. Do not solve this by raising host slots, skipping the cases or increasing deadlines. Verify the two cases on four CPUs and retain the remote planning and zero-local-host assertions.

### B2. Proven: the lifecycle case asserts a completed baseline without waiting for it

Location: `test/e2e/spec-026-remote.test.ts:75` through `:90`.

The test starts with pathless `status --wait`, edits one source, waits for that source's selected test and runs the manual group. It then reads `status --full` without waiting and requires all six test files to be current. Those requests do not establish that the remaining baseline and slow work has finished. An edit can cancel an unfinished backlog tier and leave unrelated files queued for its quiet window.

This failed on exact-candidate Node 24 CI at line 90. The manual group completed, but the immediately following snapshot said:

```text
Known failures: 0; not current: 3 of 6 test files (3 queued)
Queued: 3 test files: slow: slow/wait.test.mjs,
  test/strings.test.ts, test/upper.test.ts
the vitest lane waits for quiet ... 20 s after the last edit ...
```

That is an honest intermediate product state, not evidence that remote execution broke. The new test treats it as a failure. Its pass on the quieter sandbox does not settle this race.

Fix in the same test worker: wait for the full set of fixture results that the next assertion and coverage read require, including the slow file and cancelled/requeued baseline importers. Use a bounded result predicate or an explicit fixture checkpoint after the per-lane actions. Preserve the separate edit and group assertions. Do not use a fixed sleep or relax “all six current” to “no known failures”. Re-run the lifecycle case under CI load after B1's isolation fix.
