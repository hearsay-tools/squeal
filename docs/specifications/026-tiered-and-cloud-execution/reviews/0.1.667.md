## Blockers

### 1. B1: an unreadable store is treated as proof that no daemon uses the machine

**Proven. Blocking.** Locations: `src/core/runner-host/remote/prune.ts:146`,
`src/core/runner-host/remote/prune-unused.ts:68` and `:99`.

D12.5 permits deleting a tracked awake/sleeping machine only when its
worktree has **no live daemon**. The new destructive path uses
`liveDaemonRecorded` as that proof. Its existing reader,
`recordedDaemon` in `src/core/daemon/ensure.ts:141`, returns `null` for a
store-open failure or exception. Thus an unreadable or busy store becomes
`false`, rather than an unknown state. Both the selection and final
recheck accept that answer.

Reproduction:

1. Track a same-scope sleeping machine whose `lastUsedAt` is 25 hours old.
2. Open a real store connection. Write its worktree row with a fresh
   daemon heartbeat, 5-second heartbeat interval and a 30-hour-old start.
3. Confirm `liveDaemonRecorded(root) === true`. A control prune keeps it.
4. Make only `.git/squeal` unsearchable with `chmod 000`. The worktree
   directory and the separate machine registry remain accessible. The
   original store connection remains open and can still read its daemon.
5. Run the automatic prune with its default liveness reader.

Actual output:

```text
freshHeartbeatBefore: true
controlKept: true
livenessWhenUnreadable: false
releases: [["cmd:unreadable", "unused"]]
recordsAfter: 0
originalConnectionStillHasDaemon: true
```

This also covers the long-lived daemon risk: a readable, fresh heartbeat
protects a machine that slept for 25 hours, but a store-read error removes
that protection and deletes its remote disk. The old helper itself is
outside this range; its new use to authorize destruction is the defect.

**Worker-sized fix:** give prune a liveness read that distinguishes
confirmed absence from an unreadable/busy/failed read. Keep and explain
unknown records at both checks. Preserve the existing Boolean helper's
behavior for unrelated callers if needed. Add a test through the real
reader with a fresh daemon record and an unreadable store, plus a readable
long-lived sleeping-daemon control. Do not replace this with another mock
that always returns `true` or `false`.

### 2. B2: reuse after `current()` can delete a live daemon's machine and erase its new record

**Proven. Blocking.** Location: `src/core/runner-host/remote/prune.ts:187-197`.

The row's done-when says: "a reattach between read and release keeps the
machine." `current()` reads status, timestamps and liveness without any
exclusion shared with daemon acquire/reuse. The provider release follows
after that check. Another process can reattach the same machine in
between. After the release, `forgetting` checks only id and scope, so it
also removes the newly updated record when the daemon reused the same id.

Deterministic reproduction used the provider's `reattach` seam to schedule
a separate Node process after `current()` and before `machine.release()`:

1. Track a same-scope detached machine, detached for 25 hours, with no
   recorded daemon. Start prune with its real default liveness reader.
2. In the provider seam, run that child process. It uses real `openStore`
   and `updateMachine` to register a fresh daemon heartbeat and update the
   same machine record to `awake` with a new `lastUsedAt`. This is the
   registry/store state that a successful daemon reattach writes.
3. Return the recording machine from `reattach` and let prune continue.

Actual output:

```text
liveAtRelease: true
recordAtRelease: [{id: "cmd:reattach", status: "awake"}]
releases: [["cmd:reattach", "unused"]]
recordsAfter: 0
outcomes: ["released"]
```

There is no registry or daemon lifecycle lock across this interval. The
child demonstrates a legal cross-process interleaving, even though the
parent has no `await` between its check and call. Agent37's release now
turns this call into `DELETE /v1/instances/<id>`. Its network operation
also leaves a longer interval in which acquire can race with deletion.

The candidate's reattach tests wait behind an earlier machine's release,
then change the record **before** this machine's `current()` call. They
test that recheck, but do not cover this later interleaving.

**Worker-sized fix:** coordinate the final decision and provider deletion
with daemon acquire/reuse through one shared lifecycle exclusion or claim.
An acquire must not reuse a machine selected for deletion, and a live
owner must exclude deletion. Recheck under that protection, then forget
only the claimed record/version. Comparing timestamps only at forgetting
would preserve the record but would still delete its machine. Another
unlocked liveness check would leave the same race. Add the cross-process
reattach test after the final selection, including reuse of the same id.

## Should-fix

### 3. N1: a legacy awake record needs a second automatic prune after scope claiming

**Proven behavior. Nonblocking migration note.** Locations:
`src/core/runner-host/remote/prune-unused.ts:56-65` and
`src/core/runner-host/remote/prune.ts:170`.

For an old awake/sleeping record with no scope, `unusedCause` requires
strict equality with `context.here`, so the first automatic prune does
not select it. Only afterward does prune write this host's scope. The
probe's first run returned `unused: 0` and kept the now-scoped awake
record; the second returned `unused: 1` and released it. With no later
daemon start or manual prune it remains tracked and keeps billing.

The amended crash rule specifically names own-scope records, so this
conservative migration delay is not a blocker. Consider evaluating a
successfully claimed legacy record in the same invocation, with the same
liveness guard, and test an old **awake** scopeless record. Keep the
manual prune's stricter foreign/unknown-scope behavior.
