## Blockers

### B1. Proven: deferral is global, so an eager runner wakes a deferred runner

**Location:** `src/core/scheduler/deferred-keying.ts:50`,
`src/core/scheduler/scheduler.ts:670`.

D1.1 defines eagerness per runner. D1.2 forbids background calls to a deferred
runner. The implementation instead uses `CHECK_RUNNERS.every(...)` as one switch
for the composite adapter. One eager node:test or pytest group makes the whole
baseline and refinement eager, including manual-only Vitest.

The independent scheduler probe sets Vitest `unit` to `manual`, node:test to
`edit`, and one configured node:test entry. `runnerKeyingDeferred(policy,
"vitest")` is true while `keyingDeferred(policy)` is false. A start through
`catchUpSide` calls the Vitest fixture's `environment`, `testFiles` and `closure`.
In the real daemon, the composite fans these calls to its members. This retains
the host cost D1 was meant to remove in a mixed repository.

**Repair scope:** one D1 worker. Enforce deferral at each runner boundary for
baseline and background calls. Keep owed invalidations and wake state per runner.
An explicit request for an eager group's files must not wake unrelated deferred
runners. Add mixed Vitest/node:test and Vitest/pytest tests, not only predicate
tests and an all-deferred fixture.

### B2. Proven: a fresh named wait cannot wake deferred keying

**Location:** `src/core/scheduler/scheduler.ts:961`.

D1.4 explicitly includes a named `status --wait <path>` needing runner
resolution. The new wake only occurs after a non-empty `testFiles` list reaches
`promote` or `focus`. A fresh deferred start has no listing. The CLI cannot
select those files, so it cannot send that wake. Its sync/readers path does not
open the runner either.

The real CLI probe starts the manual-only fixture, waits for ping, and asks
`status --wait 2500 test/math.test.ts`. It exits 3, says the daemon has not listed
test files, and leaves zero runner hosts. The subsequent explicit group run
opens the runner and succeeds. This is a missing wake path, not a slow test.

**Repair scope:** one D1 request worker. Let a named-path resolution request wake
the relevant deferred runner before selecting/promoting files. Keep ordinary
unnamed status and background sync cheap. Test a first-ever named test wait and
a first-ever named source wait with no stored listing, plus a new test added
after a deferred start.

### B3. Proven: an unseen included path still spawns debug-files before lint

**Location:** `src/core/lint/provider/oxlint/provider.ts:127` and `:274`.

D3.2 says to lint target paths directly and use `--debug files` only when the
lint report accounts for fewer files than requested. `inputs()` still calls
`linted()`, which runs debug-files for every path absent from the per-path memo.
The new conditional fallback in `lint()` does not remove this earlier spawn.

The probe warms the config and `src/a.js`, then runs the normal
`refresh -> inputs -> lint` pass on included `src/b.js` under unchanged config.
It records `debug-files`, then `lint`, where D3 requires just `lint`. No ignore,
unsupported extension or changed config is involved. The shipped spawn test

**Repair scope:** one oxlint worker. Make the pass account for target files from
the actual lint report before requesting ignore classification. Preserve keys
and ignored-file semantics. Test a new included path after a warm config, a
config change, and the fewer-files fallback with its exact call order.

### B4. Proven: lint --base does not constrain the lint request to changed paths

**Location:** `src/cli/run-group-base.ts:96` and `:220`.

D4.3: a lint group runs its linters on changed paths matching the group's rules.
Both text and JSON paths instead request the whole pending lint group. The
computed paths are printed but never sent to lint request intake.

Source inspection and `test/cli/run-group-base.test.ts:253` agree: the test
expects exactly `{ type: "run-group", group: "lint" }`, with no paths. If an
unrelated file has pending lint, `run lint --base main` also lints that file and
can return its failure. This defeats the new narrow command's scope.

**Repair scope:** one run/lint request worker. Carry the merge-base changed paths
through daemon intake and lint selection. Preserve ordinary whole-group runs.
Test one changed matching file, one changed nonmatching file, and an unrelated
pending failing file; the last must neither run nor affect this request's verdict.

### B5. Proven: --base --json omits final per-file verdicts

**Location:** `src/cli/run-group-base.ts:170`.

D4.4 requires selected-file verdicts: passed, failed, not-finished, and reuse
versus execution. After waiting, `testJson()` projects the original covered-file
request record into `selected[].state`; it does not project the wait's final
file states. A successful real run returns `state: "queued"` for its completed
file, as the output above shows. The `current` count is also the request's initial
count. These can be useful request facts, but they do not supply the promised
per-file verdicts. A partial wait cannot identify which queued files finished.

The projection also keys both stored states and failures by path alone. Two
Vitest projects listing the same test path can therefore share a failure flag
even when only one project failed.

**Repair scope:** one CLI reporting worker. Keep initial disposition as an
explicit request/provenance field. Add final per-file verdicts from a consistent
current snapshot, keyed by project and path, and retain not-finished/unknown
when the deadline or read prevents a verdict. Test fresh success, a partial
timeout, current reuse, and two projects sharing a test path.

### B7. Proven: remote sleep never closes the daemon's remote channels

**Location:** `src/cli/remote.ts:106`.

D12.4 requires closing idle remote SSH channels before asking the provider to
sleep. The command only reattaches a provider object, calls its hook, and writes
`status: "sleeping"`. It never contacts the active daemon. The lane retains its
ready host and channel; `machine.wake()` runs only when `machines.reach()` is
called from the connection factory (`daemon-lane.ts:113`, `:169`).

For a command hook that suspends a VM while preserving its SSH session, the next
run uses that cached ready channel instead of waking the VM. It can hang or
fall back after timeout. A hook that relies on closed connections to permit
sleep also receives none of the required channel cleanup. The standalone hook
tests do not cover this daemon/CLI boundary. The command also marks a static SSH
machine sleeping after its specified no-op sleep, although the host stays on.

**Repair scope:** one remote lifecycle worker. Route sleep through the owning
daemon when it is live. Close idle remote channels first, retain busy work
honestly, then invoke the provider and record the resulting state. Ensure the
next run reconnects through wake. Preserve direct provider control when there is
no daemon, and do not claim that a static no-op changed the machine's state.
Test channel-close/hook ordering and the next run with a retained fake channel.

## Should-fix notes

### S1. Plausible: concurrent machine-file writers can lose another worktree

**Location:** `src/core/runner-host/remote/machines-store.ts:92`.

Each daemon reads the shared file, changes its own record, and replaces the
whole file without a cross-process lock. Two writers reading the same old view
can overwrite each other's additions or removals. Atomic rename prevents partial
JSON, but not lost records. An orphaned managed machine could then escape prune.
No concurrent-process reproduction was run, so this is not blocking. Before
managed providers ship, use a locked read/modify/write or a transactional store
and test two writers from separate processes.

### S2. Plausible: remote adapter construction bypasses D1's deferred start

**Location:** `src/core/runner-host/remote/daemon-lane.ts:106`.

The new acquisition factory is passed to the existing `withRemoteLane`, whose
constructor immediately calls `connect()` (`lane.ts:393`). Thus scheduler-level
deferral does not prevent a configured remote's acquisition or connection at
daemon construction. A successful connection's environment comparison can also
ask the local runner. This may restore the runner-host cost under a manual-only
policy. The combined remote/manual-only case was not run, so it remains a note.
Add that integration case while repairing D1, and make remote acquisition lazy
where the moment policy requires it.
