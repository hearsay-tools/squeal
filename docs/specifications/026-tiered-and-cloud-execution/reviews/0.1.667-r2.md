### B2: closed, the registry claim decides reuse versus deletion

**Proven fixed.** `machines-store.ts:93` claims use under the registry
lock. `machine-claim.ts:60` checks identity, status, timestamps and
liveness under that same lock before changing status to `deleting`.
`machine-share.ts:290` takes the use claim before acquire or wake.

Both winning orders were checked independently:

| Interleaving | Actual result |
| --- | --- |
| Prune selected an old machine; a separate process registered a fresh daemon and claimed the same id before its delete claim | The child returned `awake`. Prune kept that machine with `it was used again`. Its record remained awake. Only an earlier, removed-worktree machine was released. |
| Prune claimed deletion first; a daemon reached the machine before the old release finished | Real `shareMachine.reach()` found `deleting`, completed that machine's release and acquired `cmd:new`. The old prune released only the old id. The new awake record survived. |

Thus the old seam after an unlocked `current()` no longer allows a
successful same-id reuse followed by deletion. After the atomic delete
claim, a daemon must acquire a replacement instead. `updateMachine`
cannot turn a `deleting` record back into an owned machine, and
`forgettingClaim` cannot erase the different replacement id. Agent37's
tracked-state lookup also excludes `deleting`.

The candidate tests cover a separate-process use claim, a delete claim
that wins first, a later prune recovering an unfinished delete, and a
real shared-machine acquire after a stale deleting record. Abort still
propagates to claims and provider calls. An unfinished claim remains
tracked for recovery.

## Nonblocking note

### 1. N2: the final synchronous liveness read uses a 100 ms busy timeout while holding the global registry lock

**Proven mechanism; ordinary-load impact unverified. Nonblocking.**
Locations: `src/core/runner-host/remote/machine-claim.ts:71-84`, `:101`,
and `src/core/daemon/ensure.ts:181-195`.

`claimForDelete` calls `stillUnused` inside the registry edit callback.
That callback calls the synchronous store reader with its default
`busyTimeoutMs = 100`. The async registry retry does not make this work
asynchronous: the daemon event loop and other registry writers must wait
while this reader runs. The timeout is per SQLite busy operation, not a
deadline for all filesystem and store work.

The bounded probe held an EXCLUSIVE lock on a rollback-journal store,
then called the real claim and liveness reader. Output:

```text
underRegistryLock: true
defaultBusyTimeoutMs: 100
claimResult: "its worktree's daemon could not be read"
status: "detached"
```

This proves the busy-read path is safe for deletion. It does not measure
normal WAL contention or prove a production latency regression. Repeated
old records can add synchronous waits at selection, and a final busy read
also occupies the global registry lock.

**Small follow-up:** consider a zero-busy-timeout liveness read for prune,
especially inside the claim. Busy would still mean unknown and keep the
machine. Add a busy-store claim test and compare the relevant boat.dev
benchmark cells before making a latency claim. Keep the atomic record
claim; do not move a final ownership check outside it without preserving
the exclusion that closes B2.
