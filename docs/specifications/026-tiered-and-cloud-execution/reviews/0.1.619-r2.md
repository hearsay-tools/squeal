### B3. Closed: reuse and later lane runs refresh Git metadata

`ensureGitTree` compares local and remote HEAD, the current symbolic branch or detached state, and tags. A changed state sends missing objects and updates refs plus the HEAD-derived index without overwriting synced files. Unknown remote history gets a full bundle; unchanged state avoids a second bundle. `gitKeeper` tracks the reached state and marks refresh failure as not current.

The typed `RemoteMachine.gitCurrent` / `syncGit` seam keeps this provider logic out of the lane. `MachineShare.refreshGit` reads local state before each eligible run's split and serializes required remote refresh with host starts. `daemon-lane.ts` uses freshness for the repository capability. Failed refresh leaves configured repository readers local. Wake also refreshes Git state. Existing providers without the optional methods retain their capability behavior.

Current real-Git tests cover a new commit, added/moved/deleted lightweight and annotated tags, amend, branch switch, detached HEAD, unrelated history, HEAD-derived index equality, and preserved dirty files. Attached-daemon tests cover a later commit/tag, no SSH when unchanged, failed refresh routing readers locally, recovery, and no SSH after release. This closes the prior reuse/attached-session scenario. Concurrent runs have the narrower unresolved risk in N1.

## Should-fix

### S1. Proven, nonblocking remainder: stdin can close before bridge listeners exist

Locations: `src/core/runner-host/remote/providers/agent37/tunnel.ts:81`, `:189`, and `:206`.

The repair bounds a silent upgrade, handles stdin end/close/error during that upgrade, bounds a normal close handshake, and removes bridge listeners/timers on its terminal paths. The current new tests establish those cases. The early-close test closes stdin only after the server receives the upgrade request.

The remaining window is earlier: `runTunnel` awaits `openEndpoint` before `bridge` installs stdin listeners. If stdin is destroyed during that await, its close event is lost. A later successful upgrade clears `upgradeTimer`; no close event remains to start `closeTimer`. The tunnel can stay open with no SSH input.

One local probe used production `runTunnel` and the existing local TLS/WebSocket helper. It started the tunnel, immediately destroyed its `PassThrough` input while connection setup was pending, and raced completion against 600 ms. Output from `pnpm exec tsx /tmp/squeal-619-r2-probe.mts` (exit 0):

```text
{"inputClosed":true,"upgrades":1,"connectMs":200,"closeMs":100,"afterMs":600,"result":"pending","failures":[]}
After server cleanup: 0
```

Fix in one transport worker: observe input termination before awaiting connection setup, and check `destroyed`/`readableEnded` when handing the socket to the bridge so an already emitted event cannot be missed. Close any socket obtained after input termination. Add a test that closes stdin during setup and asserts completion plus socket/listener cleanup without server intervention. This retains the prior nonblocking classification: transport cleanup is incomplete, but the probe proves no false stored test result.

## New repair risk

### N1. Plausible, nonblocking: one lane can refresh Git while another lane's test runs

Locations: `src/core/runner-host/remote/machine-share.ts:273`, `providers/agent37/bootstrap.ts:130`, and `lane.ts:415` under that remote directory.

Refreshes share the queue used for host starts. Active remote runs do not hold that queue. With two lanes on one machine, a commit followed by a run on lane B can update HEAD/tags/index while a repository-reading test on lane A is in progress. The metadata update also uses separate ref, HEAD and index commands. Blob proof checks file inputs and does not establish a stable Git state for that run. A test that reads Git twice could therefore observe different metadata within one execution.

The attached tests use sequential runs and do not settle this case. No concurrent reproduction was run, so this is **plausible**, not a blocker or a claim of a false result. A focused follow-up can pause a repository-reading run on one lane, request refresh on a second lane, and assert a stable Git state or a discarded result. If confirmed, add a shared run/refresh lease or a Git-state check to result proof behind the provider seam. Do not serialize unrelated static-host runs merely to handle this provider capability.
