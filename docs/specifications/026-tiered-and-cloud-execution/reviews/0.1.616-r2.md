## Should-fix notes

### S1. Proven, still open: a fresh empty lock lets another writer enter

**Location:** `src/core/runner-host/remote/machines-store.ts:127`, `:159`.

The repair adds a lock, but exclusive create and owner-text publication are two
operations. A contender can read the empty file between them. Its parsed pid
is invalid, so `takeOverStale()` removes this fresh live lock immediately.
Atomic replacement still cannot prevent a lost read/modify/write.

The two-process probe enforces this valid schedule with short filesystem-call
pauses. It changes no filesystem return values:

1. A creates the lock with `openSync(..., "wx")`. Pause before it writes owner
   text, leaving the real empty file on disk.
2. B sees the empty lock, removes it, creates its own, and reads the empty
   machines file. Pause after that read and before its edit/write.
3. A resumes, writes its owner into its now-unlinked descriptor, reads the
   same empty machines file, writes record A and returns successfully.
4. B resumes with its earlier read, writes record B and returns successfully.
   Final records are only B. A's managed machine is no longer tracked.

The repository's unforced two-writer test passes, but does not force this
initialization window. The original lost-record concern is therefore not
closed. It remains a should-fix note, as in the first review.

**Repair scope:** one machine-store worker. Treat a fresh uninitialized lock
as busy, and reclaim stale locks without deleting a replacement owner's lock.
Use a lock mechanism that covers acquisition through final rename. Add a
deterministic two-process test with the schedule above, then keep the existing
concurrent-write and abandoned-lock tests.

### N1. Proven repair regression: mixed-runner restart retires deferred files

**Location:** `src/core/daemon/composite-gate.ts:46`, `:57`.
Consumer: `src/core/scheduler/bootstrap.ts:163`.

D1.3 requires stored-graph re-keying without opening a deferred runner. The
vision requires preserving known evidence and distinguishing unknown state
from a pass. The new gate holds its listing and environment only in a WeakMap.
After a daemon restart, a shut member has no cache and returns successful empty
arrays. With an eager node:test group beside manual Vitest, the scheduler runs
the ordinary baseline. That baseline treats Vitest's empty contribution as a
complete listing and retires its prior files and known checks as deleted.

The independent restart probe above proves the loss, including removal of an
existing failure from the worktree view. Its global result storage is not
proved deleted, but status can no longer show those known checks. The failure
disappears without a passing observation or a source deletion. A fresh named
request may rediscover the files; ordinary status before that has lost them.

The new mixed-runner tests start with an empty store and reuse the same gate
after explicit work. They do not exercise this boundary. This is a new defect
in the repair delta, recorded as a note under the bounded re-review rule.

**Repair scope:** one per-runner keying worker. Preserve each deferred member's
stored listing and closures at startup, with unknown/stale validity where its
environment is unverified. Carry an incomplete/deferred listing explicitly so
baseline and structural relisting do not retire that runner's stored files.
Keep the eager runner active and make zero deferred host calls. Add a restart
test with a stored deferred failure and an eager neighbor; assert that the file
and prior failure evidence remain visible, then that an explicit request
catches up normally.
