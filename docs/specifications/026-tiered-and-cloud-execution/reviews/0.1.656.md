## Blockers

### B1. Proven: command checks run before the setup that supplies the commands

Location: `src/core/runner-host/remote/connect.ts:202`, `:206`, `:218`, `:223`; setup is called later at `:352`.

D13.1 makes the project script prepare the remote machine before the dependency install. D13.2 keeps files here when the command is missing on that machine. These two features must work together on a fresh machine.

The connect probes commands before sending the tree or calling setup. A global requirement can therefore refuse the remote before setup gets to install it. A per-file requirement does allow setup, but the connect returns the old missing-command answer even after setup has installed the command.

The probe used a fixture SSH home with its own bin directory on PATH. The setup script wrote an executable `squeal-review-656-required-tool` into that directory. It connected through the candidate's copied `plugins/claude-code/dist/cli/squeal.mjs`:

```text
array requirement:
  tests need squeal-review-656-required-tool; not found on PATH there
  toolInstalled: false
per-file requirement:
  toolInstalled: true
  commands.files: [{ glob: "test/*.test.ts",
    missing: ["squeal-review-656-required-tool"], differing: [] }]
```

The array case cannot bootstrap at any retry. The per-file case falsely says the installed tool is missing and keeps its files here until another connect.

Fix: with setup configured, probe the prepared machine after setup succeeds. Feed that result into both refusal and file routing. Preserve setup before install and global refusal before tests start. Add combined fixture tests where setup supplies an array command, a `"*"` command, and a per-file command on the first connect.

### B2. Proven: a historical success mark is treated as the machine's current setup

Location: `src/core/runner-host/remote/remote-setup.ts:70` through `:81`.

D13.1 says: "A mark on the machine ... per machine ... holds the SHA-256 of the script's content. At each connect an equal mark means ready; a different or absent mark runs the script again."

One permanent file per content hash does **not** meet that rule. It records that content once succeeded, not which content last prepared the machine. This is observable on an ordinary revert of the same script at the same path:

1. Script A writes `A` to a machine state file. Setup runs.
2. Edit it to B, which writes `B`. Setup runs.
3. Restore A's exact bytes. Setup skips it because A's old mark still exists.

The probe's `ran` answers were `[true, true, false]`. The machine state remained `B`. D13 requires the third run because the last successful setup was B. Cross-worktree reuse of equal content remains useful, but cannot establish current state after another content has run.

Fix: keep the machine's latest successful content hash in an atomically replaced mark, with a common lock for its comparison and update. Replace it only after exit 0. Add A/B/A and cross-worktree tests; the current tests instead assert that two historical marks remain.

### B3. Proven: a policy reload can send files remote without their required check

Location: `src/core/runner-host/remote/lane-commands.ts:31` through `:42`; `CommandsThere` in `commands-there.ts:39` records checked names but no version-check identity.

D13.2: "No remote result is stored for a file whose command is missing or differs there."

The lane reads the live policy, but it finds missing-command facts by the old glob and treats a checked command name as sufficient evidence for any new requirement. Two public-interface probes returned `{ globs: [], text: null }`:

- Connect with `{ "test/old/**": ["chrome"] }` while `chrome` is missing. Reload to `{ "test/new/**": ["chrome"] }`. The old answer still knows the command is missing, but the new glob has no entry in `there.files`. The files now go remote without their command.
- Connect with `{ "test/web/**": ["git"] }`. Reload the same glob to `[{ "command": "git", "version": "--version" }]`. Only presence was checked. The new version requirement is nevertheless treated as satisfied. Changing the version argument has the same identity problem.

`daemon.ts` reloads the policy without replacing the remote lane. Its live getter reaches this route, so this is the actual reload boundary, not an unreachable helper state. The lane then submits these files to the ordinary remote result path.

Fix: retain command facts independently of globs, with version facts identified by command and argument. Apply the live policy to those facts. A known missing command stays missing when a glob moves; an unmeasured version requirement stays local and is named until checked. Add lane tests that replace the policy object after connect, then run the affected files and assert no remote run or result for them.

### B4. Proven: a per-file version check also applies to plain-name requirements

Location: `src/core/runner-host/remote/commands-there.ts:72`, `:77`, `:88`, `:100`.

D13.2 says: "A plain name does no version check." Only matching files should stay here; the rest should go remote.

`versionsOf` stores differences by command name. `commandsThere` then applies a difference to every occurrence of that name, including entries without `version` and entries with another version argument.

The probe used a present command in both forms:

```json
{
  "test/plain/**": ["git"],
  "test/versioned/**": [{ "command": "git", "version": "--version" }]
}
```

Different version output produced `differing` entries for **both** globs. The plain-name files were kept here despite requiring only presence. If the plain-name entry is under `"*"`, line 72 turns the subset's difference into a refusal of the whole remote.

Fix: look up version results only for an entry that requests that exact command and argument. Preserve plain-name presence checks. Add a test with plain and versioned globs sharing a command, another with plain `"*"`, and one with two different version arguments. Coordinate this interface change with B3.

### B5. Proven: routing all files here before a lazy connect prevents the connect

Location: `src/core/runner-host/remote/lane.ts:1263` through `:1269`, with `lane-commands.ts:30`.

Before a connect answers, keeping per-file requirements local is conservative. It must still allow the connection to start. The existing lane contract connects a non-eager lane at its first eligible run; D13's remote preparation and routing cannot happen if the lane never connects.

With `eager: false`, `whenLost: "local"`, no `awaitConnect`, and `{ "test/**": ["git"] }`, every file is split here before `remoteTier` can call `ready`. The new early call to `ready` is conditional on waiting. No connect ever starts when all subsequent runs contain only these files.

The probe called the real `withRemoteLane` three times with one matching file and a counting local adapter/connect callback:

```text
backgroundRuns: 3
connects: 0
localRuns: 3
report: { state: "not connected" }
```

A newly created per-pass lane can likewise fail to wake a sleeping machine: it has no command answer, and `daemon-lane.ts` sets no `awaitConnect` while the shared machine is asleep. Non-eager lanes also arise through deferred runner keying. The added test covers `awaitConnect: true` only.

Fix: start or advance the eligible connection before an all-local provisional split can return. Under the local fallback policy, the first run may still proceed here without waiting. Keep backoff, cancellation, and the existing wait behavior. Test repeated all-matching runs on a non-eager lane and a sleeping lane; a healthy connect must eventually route them remote.
