## Verdict

**FAIL: five proven blockers, one plausible nonblocking note, no nits.**

The new background caller exposes unsafe deletion decisions and synchronous work on the daemon event loop. Racing a release promise with abort does not cancel the release. The existing happy-path tests do not exercise these boundaries.

## Blockers

### B1. Exit abort leaves the provider request running

**Proven.** `src/core/runner-host/remote/prune.ts:72`, `:98`; wired from `src/core/daemon/daemon.ts:644` and `:1768`.

The brief requires: “stops at the daemon's exit (abort the HTTP calls; do not hold the exit).” `until()` only resolves its own promise on abort. `machine.release("worktree-removed")` receives no signal. The built-in Agent37 release calls `api.remove(id)` without one. Its HTTP request and referenced 60-second timeout remain active.

Probe: use the actual Agent37 provider against a loopback HTTP server that accepts DELETE and sends no response. Start a prune, wait for DELETE, abort, and await the prune result. After another 150 ms the server still has one live connection and has seen no request close, although the prune returned `aborted: true`. Destroying the test socket is necessary to clean up. The CLI's existing two-second forced-exit timer can mask this leak; it does not satisfy HTTP cancellation. The fake never-settling promise in the added test owns no socket or timer, so it cannot detect this failure.

**Fix:** add an optional release signal through the provider seam and propagate it to Agent37 DELETE and command-provider hooks. Abort must close the actual operation, start no next release, and keep the uncertain record for a later prune. Cover cancellation with a real loopback socket or child hook, not only a pending promise.

### B2. An inaccessible worktree is treated as removed

**Proven.** `src/core/runner-host/remote/prune.ts:57` and the new `src/core/runner-host/remote/machine-share.ts:458` branch.

D12.5 authorizes deletion when the worktree path no longer exists. `existsSync()` also returns false for access failures. The new automatic start and exit paths turn that uncertainty into `worktree-removed`, which destroys an Agent37 instance and forgets its record.

Probe as an unprivileged user: create `restricted/live`, track its machine, set the parent directory mode to `000`, then prune with a fake provider. The provider receives one destructive release and the registry becomes empty. Restore the parent mode: `live` still exists. No worktree removal occurred. The same predicate in `releaseOnce` makes an ordinary daemon exit destructive in this case.

**Fix:** use one conservative presence check at both call sites. Distinguish a confirmed missing path from permission, I/O and other unknown errors. Keep and report an uncertain record; do not issue a destructive release. Add an unprivileged access-error regression for both prune and `releaseOnce`.

### B3. A stale prune can erase the record of a replacement machine

**Proven.** `src/core/runner-host/remote/prune.ts:57`, `:70`–`:73`; the called `forgetMachine` matches only provider and worktree id.

The brief requires concurrent prunes to be safe and a still-existing worktree's record to remain untouched. Missing paths are collected once, before any awaited release. No path or current-record check runs when each later release starts. A successful old release then forgets whatever machine currently occupies that provider/worktree key.

Probe sequence:

1. Track removed worktrees A and B. Pause A's release after the prune takes its snapshot.
2. Recreate B's path and replace its record with machine `cmd:b-new`, retaining B's provider and worktree id.
3. Complete A's release.

The prune releases old `cmd:b` and removes `cmd:b-new` from the registry although B's directory exists. The new machine was never released and is now untracked. Worktree reuse really keeps this key: `src/core/fs/git-layout.ts:56` derives the worktree id from the real path. If the recreated daemon reuses the tracked old instance instead, the stale prune can delete the instance it has just woken.

**Fix:** check current path presence and record identity immediately before a destructive release. After completion, forget only the exact machine record that was released, with the identity comparison inside the existing registry write lock. Preserve a replacement that arrived during the remote call. Cover recreation before B's turn and replacement during an in-flight release. Ordinary duplicate deletes and 404 handling do not settle either race.

### B4. The background prune waits synchronously on the global write lock

**Proven.** `src/core/runner-host/remote/prune.ts:73`, called in the daemon event loop by `src/core/daemon/daemon.ts:646`.

The brief requires that this work “never delays start or any run” and never holds exit. `forgetMachine()` uses the existing synchronous registry lock. Contention calls `Atomics.wait()` repeatedly for up to 10 seconds. A background promise does not move this work off the daemon event loop. Runs, startup continuation, timers and exit handling all wait behind it; an abort cannot interrupt that synchronous loop.

Probe: track a removed machine, hold the registry lock with a live owner, and let a separate Node process unlink it after 400 ms. Start a 10 ms timer and prune with an immediately successful fake release. The timer fired after 439 ms on one run and 449 ms on another. The current lock timeout permits a much longer pause.

**Fix:** give the background caller a nonblocking, abortable registry-update path. It can defer or retain an already-deleted machine's record when the lock is busy. Keep write serialization and exact-record comparison; do not remove the existing lock or add an unrelated cross-process prune lock. Test timer responsiveness while another process holds the write lock and abort during that wait.

### B5. CLI test daemons still run user-global release hooks

**Proven.** `src/cli/daemon.ts:55` unconditionally enables pruning. The opt-out at `src/core/daemon/daemon.ts:643` protects direct `startDaemon()` tests only.

The changed CLI is also what fixture hooks launch. The Claude Code branch of `test/e2e/harness.ts:180` gives its fixture only a private runtime directory. `test/e2e/plugins.ts` calls `runNode`, whose environment in `test/harness/bundle-helpers.ts:128` retains the real HOME. These CLI daemons therefore read the user's `remote.json` and `remote-machines.json` and can run unrelated configured release hooks. Separately, `test/daemon/helpers.ts:186` replaces the config directory but keeps HOME and the state directory, so its CLI daemons can still read the real machine registry.

Probe: make a private HOME stand in for the user's HOME, put a command-provider lane and an unrelated removed-worktree record in its default user config/state paths, and start the shipped CLI daemon for a local fixture with the same HOME-preserving, runtime-only environment. The release hook writes a marker and the user-global record disappears. The fixture repository needs no remote lane. The probe used only a harmless marker hook; no real user's files or cloud machines were touched. A configured hook that deletes cloud resources reaches the same invocation.

**Fix:** isolate HOME, `XDG_CONFIG_HOME` and `XDG_STATE_HOME` in every helper that can start a real CLI daemon, including shipped-plugin fixtures. Keep the production startup behavior. Add a CLI-level sentinel test proving a fixture cannot read or change a separate user registry or run its release hook. The added direct-daemon opt-out test is insufficient.

## Should-fix and design inputs

### N1. Registry paths have no filesystem-namespace provenance

**Plausible, nonblocking.** `src/core/runner-host/remote/prune.ts:48`–`:57`.

The automatic prune scans every repository's records in the selected user state file. A daemon in a container or another mount namespace can share that file while a host worktree path is absent from its filesystem. It would classify the host's live worktree as removed. Likewise, explicitly sharing `XDG_STATE_HOME` between environments does not establish that their path namespaces match. The registry has no host or namespace field that rules this out. No cross-namespace execution experiment was run, so this is not a sixth blocker.

The coordinator should settle which filesystem scope an automatic prune may trust. A permission-aware stat fixes B2, but cannot by itself distinguish a removed host path from a path not mounted here. Skip records with unknown ownership/scope unless there is evidence that their path namespace is this daemon's. A different HOME alone selects a different default registry; explicit shared XDG state is the relevant boundary.

## What fits

- The CLI and daemon share one prune implementation. Normal success, failure, empty and dry-run CLI text and exit-code branches retain their prior formatting. The only intended list-text addition is the orphan count; JSON remains unchanged. Existing relevant CLI tests have current passing results.
- The prune is not awaited by startup or shutdown. Errors from its import, provider and registry paths reach logs. The unresolved promise itself does not delay start; B1 and B4 concern actual handles and synchronous work.
- On abort, the loop starts no later record and retains the in-flight record. An eventual rejection has a handler. Retaining an uncertain release is appropriate.
- Agent37 DELETE already treats 404 as success. Duplicate forgetting is harmless when the record has not been replaced. The existing registry write lock prevents ordinary lost updates. B3 is an identity race, not a reason to add a global prune lock.
- `releaseOnce` correctly requests `worktree-removed` and forgets on success when the root is genuinely gone. A release failure retains tracking. B2 concerns the evidence used to decide that the root is gone.
- A symlink to an accessible live directory satisfies `existsSync`. Normal machine records use the canonical worktree root, so removing an alias does not by itself make that canonical root disappear. Access errors and namespace uncertainty remain separate concerns.
- No result-key or schema change was found.

## Inputs for the repair wave

Keep B1 and B4 separate: cancelling HTTP does not make synchronous lock acquisition interruptible. Apply the same conservative presence rule to automatic prune and `releaseOnce`. Combine that rule with fresh record checks and conditional forgetting for B3. Keep production CLI output stable while isolating test environments for B5.

Required regression cases: pending real DELETE closed at abort; inaccessible live worktree retained at start and exit; recreated path skipped; replacement record retained during an old release; event-loop timers and exit responsive under registry-lock contention; fixture CLI unable to invoke another user's release hook. Use affected results and targeted checks only. Full-suite CI must be resolved before release; the current failed shard is not overridden by this review's passing targeted evidence.
