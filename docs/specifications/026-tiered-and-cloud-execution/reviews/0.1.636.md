## Should-fix

### S1. Proven, nonblocking: failed deletion loses tracking of the old VM

Location: `src/core/runner-host/remote/providers/agent37/index.ts:212`.

Scenario: a user changes the template while an instance is tracked. The API returns HTTP 503 for `DELETE`. `reuse` swallows the error and returns `null`. Acquire creates a replacement. Its normal recording replaces the old provider/worktree entry (`machines-store.ts:81`), so the old instance remains alive but `remote prune` can no longer find it. Disk charges continue until manual cleanup; compute may also continue until auto-sleep.

Proof: a throwaway local HTTP server returned 503 on DELETE and successful creates; fake SSH ran the normal bootstrap in a temporary directory. The probe called public `provider.acquire`, then `recordMachine(recordOf(...))` for each acquisition, as the machine owner does. Actual output:

```json
{"live":["probe1","probe2"],"tracked":["probe2"],"oldUntracked":true}
```

The probe used no cloud service and was removed. This is nonblocking because Wave 11 requirement 3 explicitly mandates `await api.remove(tracked.instanceId).catch(() => {})` followed by replacement. The candidate implements that decision exactly. This is a follow-up to the design, not a missing implementation requirement.

Suggested one-worker fix, after amending that requirement: let deletion failures stop replacement and keep the old record for retry. Treat 404 as successful absence, as `api.remove` already does. Add a test where DELETE returns 503: no POST follows, the old record remains, and the caller receives a useful error. Existing successful replacement and legacy reuse tests must still pass.
