## Blockers

### B1. Proven: shared connect work can start a host after machine release

**Locations:** `src/core/runner-host/remote/machine-share.ts:175`, `:183`, `:213`;
`src/core/runner-host/remote/daemon-lane.ts:245`, `:278`;
`src/core/runner-host/remote/lane.ts:506`.

Row 026-11 requires one machine, "released once on daemon exit", with channels
and the ControlMaster closed before lifecycle release. The new shared connect
queue outlives that boundary. A lane's `close()` changes its state but does not
wait for its connecting promise. `share.release()` neither drains the queue nor
prevents later `reach()` or queued host starts.

A probe through the real `createDaemonRemote()` API used eager Vitest and
node:test, a fake provider, and a held first `startHost`:

1. Both lanes request connection. Vitest acquires the machine and pauses inside
   its host start. node:test waits in the shared serial queue.
2. Close both lanes, then call `remote.release()`, as the daemon wrapper does.
   Machine release returns while Vitest's start is still pending.
3. Let the first host start finish. Its closed lane closes that host, but the
   queued node:test operation now calls `startHost` after machine release.

Actual call order:

```text
acquire, start-vitest, release, daemon-close-returned,
close-vitest, start-node-test, close-node-test
```

With real transport the late operation can open SSH and its ControlMaster
after the final close, or wake a machine the release hook just slept. No
second release follows it. This is a new shared-queue failure schedule.

The same owner also has an early-acquire variant: delay `provider.acquire()`,
call `share.release()` while `current()` is null, then resolve acquisition.
Actual output was `calls: [acquire-start, release-returned]`, `awake: true`,
with an `awake` machine record and no release hook. The `released` flag
prevents an idle timer from rescuing it. The old single-lane implementation
also lacked an acquisition drain; the new shared owner must settle the whole
queue rather than carrying that gap into several lanes.

**Repair scope:** one remote lifecycle worker, owning `machine-share.ts`,
`daemon-lane.ts`, `lane.ts` and their tests. Make shutdown stop new queue work,
settle/cancel in-flight acquire and wake operations, and close every host that
was started before the final ControlMaster close and single provider release.
Do not treat a lane's closed state as proof its connect work has ended. Add
both held-start/two-lane and held-acquire tests. Assert no host start, wake,
channel or awake record can appear after release completes.

### B2. Proven: stale install-lock takeover removes a replacement live owner

**Location:** `src/core/runner-host/remote/tree-host.ts:224`, especially `:232-240`
and unconditional cleanup at `:249`.

D8.1 puts multiple hosts on one tree. The new lock says "one host at a time
installs". Its stale takeover reads an owner, then removes the lock directory
without checking that the directory still belongs to that owner. Two waiters
on a dead host can therefore install together. Its unconditional final
removal can also remove a successor's lock.

A deterministic two-process probe used real `createTreeHost().install()`, a
fixture `files.json` and package lock, and a fake `npm ci` that waited on a
signal file. A wrapped filesystem read paused at a real call boundary; it
changed no filesystem return values:

1. Seed `install.lock/pid` with a nonexistent pid.
2. A reads that dead pid. Pause A before returning the read to the lock code.
3. B sees the dead owner, removes the directory, takes the lock under B's pid,
   and enters its fake install. Keep that install running.
4. Resume A. A uses its earlier dead pid, removes B's live lock, takes it and
   enters a second install while B still runs.

Actual output:

```text
{"overlappingInstalls":true}
[{"role":"a","result":{"ran":true,"command":"npm ci"}},
 {"role":"b","result":{"ran":true,"command":"npm ci"}}]
```

Both processes exited 0. Real installs can remove or rewrite each other's
`node_modules` and shared install record. The machines-store lock fixed by
026-18 is a different lock and does not protect this remote tree.

**Repair scope:** one remote tree worker. Give install acquisition, stale
replacement and release an ownership-safe protocol. Re-check ownership under
serialized takeover and remove only the lock held by that installation.
Keep package-manager work inside that ownership interval. Add this forced
two-waiter takeover test, with the second install unable to enter until the
first releases, plus dead-owner and empty-owner recovery. Existing log-retention
and single-host install tests should stay green.

### B3. Proven: a revision-0 baseline cannot detect a later HEAD-only change

**Location:** `src/cli/status-stale.ts:80-85`.

D2.4 requires checking whether "HEAD moved or tracked/untracked files modified
since the last recorded revision" and printing the no-daemon notice. On a
fresh unchanged worktree, the initial scan can leave no revision row and no
head-move record. `recorded` is then null, so the new `moved` expression can
never be true. A commit that changes only HEAD has no stat change to rescue
the notice.

A real-process probe used the built candidate CLI, a temporary Git repository
with an initial commit, manual Vitest, complexity/coverage disabled and
`unusedExitMinutes: 0.05`:

```text
node <candidate-cli> start
# Let the edit-free daemon exit at its 3-second bound.
git commit --allow-empty -qm head-only
node <candidate-cli> status
```

The probe compared HEAD before/after and checked the text. Actual result:

```json
{"oldDaemon":{"state":"down"},"headChanged":true,"notice":false,"firstLine":"Revision: 0"}
```

The daemon had stopped cleanly. The new HEAD received no notice. The shared
staleness reader has the same missing baseline for code and lint. Current
tests cover a disk edit at revision 0, and a HEAD move after a nonzero revision;
neither covers this combination.

**Repair scope:** one daemon/status worker. Persist the HEAD observed by the
initial pass, including revision 0, and use that observation for no-daemon
comparison without inventing a content revision. Add a real-daemon test that
starts and stops without edits, moves HEAD without changing file bytes, and
gets the notice naming revision 0 from status/code/lint. Keep an unchanged
revision-0 worktree silent and preserve the existing read-only JSON contracts.
