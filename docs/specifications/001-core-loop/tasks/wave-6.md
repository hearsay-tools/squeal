## 001-47 interactive consumer liveness (defects 8 and 10)

Scope. Defect 8: Claude Code 2.1.288 runs no SessionEnd on an interactive exit after a typed prompt, so the main agent's consumer stays registered until the 12 h expiry (D10) and the worktree's daemon cannot idle-exit. Defect 10: Claude Code runs no Stop after the user interrupts a turn, so after an interrupt no waiter is armed until the session ends.

Contract (decided, do not re-open). An interactive main agent's liveness is its waiter: while a waiter runs it holds the consumer's waiter lock (`src/harness/claude-code/waiter-lock.ts`, an exclusive SQLite lock the OS drops on SIGKILL, and Claude Code kills the waiter with 137 at every exit). The lock file stays behind after a kill. So in the daemon's expiry pass (D10, `src/core/daemon/lifecycle.ts`, `expireConsumers`), a consumer whose waiter lock file exists, is not held (a fresh lock attempt succeeds), and that has not been seen or delivered to for `WAITERLESS_EXPIRY_MS` = 10 minutes is expired, and its lock file removed. Every other consumer keeps the 12 h rule; `-p` sessions and subagents never have a lock file, so nothing changes for them. The lock path and the lock test must live in one place that both the harness and the daemon import (move or re-export them under `src/core/`; the daemon must not import from `src/harness/`). A waiter that exits by its own timeout releases with `remove: false` today, which leaves an unheld lock file behind for a session that is still alive: make sure the next arming (Stop, or the re-arm below) comes well within 10 minutes of that, or have a timed-out waiter touch the consumer (`last_seen_at`) on exit so the 10 minutes start from there; pick one and say which.
Defect 10: re-arm the waiter on `UserPromptSubmit` (add the event to `plugins/claude-code/hooks/hooks.json` with the same `waiter.mjs` `asyncRewake` entry as Stop). The existing per-consumer lock makes a second waiter exit at once, so arming on every prompt is safe. If UserPromptSubmit also needs to register a consumer that expired while the session sat idle, do it through the existing registration path and inject the registration only when it carries known failures (the Stop rule); a new handler or entry bundle is fine if the waiter alone cannot do this.

Done when: a test with a real store shows a consumer with an unheld waiter lock file and last seen 11 minutes ago expired by the expiry pass, and one with a held lock, one without a lock file, and one seen 9 minutes ago kept; a test drives the daemon's real expiry timer with a short interval through the same path; recorded `UserPromptSubmit` hook JSON (add `test/harness/recorded/user-prompt-submit.json`, shaped like the other recordings) arms a waiter for a registered consumer with no waiter and exits at once when a waiter already holds the lock; a plugin manifest test asserts the new hooks.json entry.

## 001-48 forked-agent SubagentStop (defect 9)

Scope. Claude Code runs a forked agent after every interactive turn (the `prompt_suggestion` fork, lessons Surprise 6). It fires SubagentStart and SubagentStop, so every attended turn registers and unregisters one more consumer, and with `stop.blockOnKnownFailures` on and a current failure its SubagentStop is blocked: the fork makes another API request, and since a block keeps a subagent going its consumer is not unregistered until SessionEnd. A fork is not a consumer: it never reads Squeal output and never acts on it.

Contract. Recognise a fork from its hook input, not from timing. First find what the input carries: the dogfooding run's evidence is in lessons.md (A4, A5); Claude Code's subagent hook input carries `agent_type` beside `agent_id`; confirm against Claude Code's hooks documentation and, if you can, a real `claude` session with `--debug hooks` on a scratch repository (never on this repository's store). Parse the field you need in `src/harness/claude-code/input.ts`. Treat as a fork every agent type in one named set (`prompt_suggestion` plus any other internal fork type you find documented or observed; list the evidence for each in a comment). For a fork: SubagentStart does nothing (no registration, no daemon spawn beyond what SessionStart already did, no output); SubagentStop never blocks, delivers nothing and unregisters nothing it did not register (a stale consumer of that agent id from an older build may be unregistered); hooks fired inside a fork (PostToolBatch, PreToolUse) do not register it either; check `post-tool-batch.ts` and `pre-tool-use.ts` and, if they need a change, ask the coordinator first, because those two files are not in your ownership yet. A real subagent with an unknown or missing agent type keeps today's behaviour.

Done when: recorded fork JSON (`test/harness/recorded/subagent-start-fork.json` and `subagent-stop-fork.json`, shaped as Claude Code sends them) drives `session-start` and `stop` in a new `test/harness/forks.test.ts` with policy `stop.blockOnKnownFailures` on and one failure current: no consumer row exists after either hook, SubagentStop returns no block and no output; the existing subagent tests in `test/harness/stop.test.ts` stay green and one asserts a real subagent with the same policy is still blocked.

Owns: `src/harness/claude-code/hooks/stop.ts`, `src/harness/claude-code/hooks/session-start.ts`, `src/harness/claude-code/input.ts`, a new helper module under `src/harness/claude-code/` for fork detection if you want one, `test/harness/stop.test.ts`, `test/harness/forks.test.ts`, `test/harness/recorded/subagent-start-fork.json`, `test/harness/recorded/subagent-stop-fork.json`, `test/harness/recorded/README.md`.
