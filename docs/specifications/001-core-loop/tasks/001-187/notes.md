# 001-187 notes: held heals, grown-key re-runs, the preload stopgap, persisted re-runs

Seam map for whoever continues (builds on `tasks/001-170/notes.md` and `tasks/001-171/notes.md`).

- **B1, held after a heal.** `storeResults` (`src/core/scheduler/store-results.ts`) reads the key's rows after the write; for each other worktree it heals, when `heldFailure` holds them there it upserts that worktree's `test_file_keys` row `pending: "queued"` (only when it was `null`) and adds `{ testFile, key }` to `meta` `held-files:<worktree>` (`src/core/scheduler/held.ts`), in the heal's transaction, before the sink refresh, so the receiving states read `pending`, not `stale`. The receiving daemon takes the row (`takeHeldFiles`) in `Ledger.confirmHeld`: at the start of every `handleBatch` (watch or interval), at the start of `queueFullSuite`, and drops it at the start of `baseline` (its lookup finds the held file as a miss anyway). `confirmHeld` touches the file, nulls `resultKey` when it is the held key and queues the file unforced at `priorityOf`; a file running at the key, or moved off it, is only touched.
- **B2, the stopgap.** `unresolvedPreloads(context, project)` (`src/core/scheduler/growth.ts`) is the predicate: the project's `nodeTest.observedPreloads.<project>` meta row lists a path that `WorktreeKeys.environmentFiles(project)` (new accessor, `keying.ts`) lacks. `storeResults` still writes the rows, then returns before `recordFlips` and the heal. 003-43 can reuse the predicate.
- **B3.** `recordTier` (`tiers.ts`) calls `holdsNewFailure` for a grown file too (`growth !== undefined`, stored at `storeKey`), and pushes `{ key: storeKey }`; the grown file's results become current through `settle` after, and `queueReruns` runs after that. Discarded and first-seen runs `continue` before this point and never count.
- **S1.** `src/core/scheduler/rerun-memory.ts`: `meta` `reruns:<worktree>`, one `{ testFile, key, pending }` per file. `queueReruns` now returns what it queued and sets `FileState.rerunPending` (new, additive); `recordTier` writes them (`rememberReruns`). `endRerun` clears pending when a forced run at `rerunKey` stores (`recordTier`) or when `Ledger.settle` sees the file's key move off `rerunKey`; there the forced queue entry is removed so the new key runs as an ordinary miss. `restoreReruns` at the end of `baseline` restores `rerunKey` for every listed file, queues a pending re-run forced while the file is still at its key (not under lookup-only, not slow), ends the others, and prunes unlisted files. `Ledger.discard` takes `forced` and keeps it while the key did not move, so a discarded re-run is not lost to its own lookup.

Edits in files 001-184 also touches (`tiers.ts`, `ledger.ts`): `queueFullSuite` first line `ledger.confirmHeld()`; `recordTier`'s `storeResults` block (B3, `endRerun`), the `discard` call, the `queueReruns` line; `Ledger.settle` (the `rerunPending` drop before the `isForced` check), `Ledger.confirmHeld` (new), `Ledger.discard` (`forced`).

Known gaps, not fixed here:

- B2 withholds only the heal and the note. The row under the incomplete key is still replaced, so a later refresh of the other worktree's file at that same key (its row made dirty without a key change) can still read the pass. In practice its key moves first, when its observed-growth refinement keys the preload. 003-43 closes it.
- `confirmHeld` runs at batches, so a held file waits for the receiving daemon's next watch batch or reconciliation pass (30 s when idle) or `run --all`. Its row reads `queued` meanwhile. A receiving worktree with no daemon keeps that row until its next daemon's baseline rewrites every row.
- A `run --all --force` entry for a file whose re-run is dropped by a key move loses its force too: `settle` cannot tell the two apart. The new key is a miss unless another worktree stored it.
- Per-worktree `meta` rows (`held-files:`, `reruns:`) are not removed with a worktree, like `failure-keys:`.
- No test drives `Ledger.settle`'s in-daemon drop of a pending re-run on a key move (the restart test drives the baseline's). Ordering an edit between the queueing and the start of the re-run needs a hook the harness does not have.
