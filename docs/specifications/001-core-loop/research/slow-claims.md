## 1. The skill is offered, never chosen

- Every Claude cell's `system/init` event (48 of 48, both runs) lists `squeal:squeal` among 19 skills, with `Skill` among the tools and the plugin loaded as `squeal@inline` 0.1.123/0.1.124. In those 48 sessions, the tool calls were Bash 425, Edit 295, Read 88, Grep 43 and Write 15, with Skill 0. One haiku session called a nonexistent tool named `Squeal` (0.1.123 t3-tax r1). No Read touched `skills/squeal/`. *verified by experiment (recorded sessions)*
- Claude Code 2.1.296's Skill tool says: "When the task at hand is one a listed skill covers, call this tool first", and lists skills in a system-reminder ("The following skills are available for use with the Skill tool"). *read in source code (installed bundle, `claude.exe` strings)* The eval's tasks are features ("group thousands with commas"). Squeal's description ("Use when about to run tests (vitest, npm test) or to check whether a change broke something") names a step inside the task. The primer injected before the prompt already says how to check results and says "do not run Vitest". So a compliant agent is never "about to run tests", and a non-compliant one (haiku ran Vitest itself in 9 of 9 misses) uses Bash directly. *inferred*
- The primer and the registration header never mention the skill (rendered by the shipped SessionStart hook). *verified by experiment*
- Codex 0.160.1 rollouts show a `<skills_instructions>` block of 5 skills. Squeal is the only relevant one, listed with its `SKILL.md` path. The base instructions say: "If your current task would benefit from a skill, but is not explicitly invoked by the user, use reasonable judgement to apply relevant skill instructions… Do not use a skill based solely on keywords". Loading is a `cat` of the path. Luna's and sol's base instructions differ overall, but their "When to use a skill" section is identical (same hash). Luna loaded the skill in 8 of 24 sessions, sol in 24 of 24 (TREND, five runs: 29/60 and 60/60). *verified by experiment (recorded rollouts)*
- Eval pin: Claude runs `claude -p … --setting-sources project --plugin-dir <pin> --allowedTools <list>`, and the list has no `Skill`. The Agent SDK in the same bundle appends `Skill` to `allowedTools` when skills are enabled. Its permission text says a plugin skill without a `Skill(<name>)` rule "needs approval each time". So a Skill call in the eval would likely be refused in `-p`. This did not cause the 0 (no call was attempted), but a variant must point at the file, which `Read` may open. *read in source code (bundle); inferred (refusal)*
- Not determined: whether Claude Code truncates the listed description under its listing budget in `-p`. The `skill_listing` attachment is not in `stream-json`.

## 2. What changes the claim: a slow trigger, not the skill

Per graded session, both judged runs (68 sessions where `current-before-claim` applied: 48 met, 20 missed). A trigger is a `squeal run --slow` or `squeal run --all` command anywhere in the session. Met over sessions:

| Model | Skill loaded | `run --slow` | `run --all`, no `run --slow` | neither |
|---|---|---|---|---|
| haiku | 0 of 18 | 3 of 3 | 6 of 6 | 0 of 9 |
| sonnet | 0 of 17 | 6 of 6 | 6 of 8 | 0 of 3 |
| luna | 6 of 15 | 5 of 6 | 4 of 4 | 0 of 5 |
| sol | 18 of 18 | 17 of 17 | 1 of 1 | none |
| all | 24 of 68 | 31 of 32 | 17 of 19 | 0 of 17 |

- All 20 misses had the slow tier pending (19) or running (1) at the claim. All 48 met sessions had it current. The board says 18 of 20; the difference is the counting method (this file reads the last `Slow tier:` line). *verified by experiment (recorded sessions)*
- A trigger decides it in every model: `run --slow` 31 of 32 met, `run --all` 17 of 19, neither 0 of 17. The 21 current Claude sessions used `run --slow` (9) or `run --all --wait` (12), both named in the header ("`squeal run --slow` runs them now", "`squeal run --all` requests one"), never the skill. `run --all --wait` polls the checkpoint with no bound, and the checkpoint includes slow files (`src/cli/run.ts` `ended`, 004 D8). *verified by experiment; read in source code*
- `run --slow` alone does not get there. Its `--wait`, and `status --wait`, return "on quiet" while the slow file runs. Both luna and sol got `Returned on quiet … at revision 1 after 0.5 s; 2 checks pending in all` with `Slow tier: … running`. `commands.md` documents it: "slow files … do not hold it". Sol was current because it went on reading `commands.md` and ran `run --all`. A model following the skill's step 3 to the letter ("Done when its first line says Returned on quiet") claims while the slow tier runs. *verified by experiment (recorded sessions); read in source code*
- SKILL.md has no step to run the slow tier before a claim. It only says when slow files run. Step 4 allows a claim with checks pending if they are named ("say what is still pending"), which `current-before-claim` scores as missed. 8 of the 20 misses named the pending slow tier or their own run of it. *read in source code (skill); verified by experiment*
- 14 of the 20 misses (every Claude miss) had a completed full own `npx vitest run` after the last edit, and every one of their claims was true. That run includes the slow file. The miss is "evidence not Squeal's", not "evidence stale". Whether that is the right expectation while Squeal cannot answer is the 006 coordinator's question (see Open questions). *verified by experiment (timelines)*
- Correlation, not cause: within luna, a skill load went with `run --slow` (5 of 6 against 1 of 9). But Claude reached `run --slow` and `run --all --wait` with no skill, and sol mostly read only SKILL.md, whose text does not ask for it. Sol's 100% load and 100% current both look like diligence. *inferred*
- Variants written, not run (`evals/variants/`; patches checked with `patchPlugins` on a scratch copy, 13 bundles each, every patched bundle passes `node --check`, primer rendered by the patched SessionStart hook in both harnesses):
  - `skill-file`: the primer adds "Before you run tests or say the task is done, read Squeal's skill: <absolute path to skills/squeal/SKILL.md>", resolved from the bundle's `import.meta.url`. Same load channel in both harnesses, skill text unchanged. This isolates "loading the skill".
  - `slow-step`: the primer's slow sentence adds that `status --wait` does not wait for slow files and that, before a claim while the slow-tier line is not current, the agent runs `squeal run --all --wait` (Codex: "the CLI's `run --all --wait`", the primer's existing fallback for a long CLI path). Skill untouched. This isolates "the step in the primer".
  - `stop-slow`: policy `stop.requireSlowSuite: true`, today's end-of-turn block.
  - Run each with `run-baseline.mjs --variant <name>`. Reading: if `skill-file` moves Claude's `current-before-claim` and `slow-step` does not, the skill matters. If `slow-step` moves it and `skill-file` does not, the primer is the channel.

## 3. Telling a headless session apart

- Claude Code sets `CLAUDE_CODE_ENTRYPOINT` to `sdk-cli` whenever the process is non-interactive, and keeps an inherited value (`cli` becomes `sdk-cli` when non-interactive). `CLAUDE_CODE_SESSION_ATTENDED` comes from an internal check that returns true for interactive runs. *read in source code (bundle)* This Cezar worker, a long-lived multi-turn session with Squeal active, has `sdk-cli`/`0` and runs as `claude --input-format stream-json --output-format stream-json …` with no `-p` (`/proc/$CLAUDE_PID/cmdline`). The eval's subject runs `claude -p "<prompt>" …` with no `--input-format`. The Agent SDK always passes `--input-format stream-json`. So: *verified by experiment (own process; eval command in `evals/lib/session.mjs`)*
  - one-shot = entrypoint not `cli`, and the harness process's argv has `-p` or `--print` and no `--input-format stream-json`. The harness process is already found by 001 D9's walk. Reading its `/proc/<pid>/cmdline` adds one read.
  - also one-shot: entrypoint `claude-code-github-action` (a value in the bundle), or `CI` truthy with a non-interactive entrypoint. *read in source code; inferred for `CI`*
  - interactive never has `-p`, so this cannot fire there. A stream-json SDK session (Cezar, SDK apps, the SDK's one-shot `query()`) reads as not one-shot: a false negative, no wait. macOS has no `/proc`, so nothing is decided and nothing waits.
- Codex hook stdin carries `transcript_path` (002-01's logs). The rollout's first line is `session_meta` with `source` and `originator`. On this host, read only, top-level threads: `codex_exec`/`"exec"` in 69 of 69, `codex-tui`/`"cli"` 11, Cezar's app-server `"vscode"` 6,503 (plus probes), subagents an object. `"exec"` never appears outside `codex exec`. Hook processes get no `CODEX_*` variables (002-01). *verified by experiment (host rollouts, 0.160.1)* The format is undocumented (handlers.ts already says so), so a missing file or field must read as not one-shot.

## 4. What a bounded slow wait at Stop costs

Probe `probes/slow-claims/stopwait.py`. A scratch copy of `evals/ledgerline`, its slow file `test/slow/ledger.test.ts`, and `slow.maxLoadPerCpu` raised so the guard stays out. It runs this worktree's SessionStart, UserPromptSubmit, Stop and SessionEnd bundles with `-p`-shaped env (`sdk-cli`, `0`), edits `src/money.ts`, and polls `status --json` every 200 ms. Load 17 to 73 on 24 CPUs. *verified by experiment*

| Stop moment | Trials | Stop to slow-current |
|---|---|---|
| after the edit's fast results (the usual claim moment) | 5 | 27.0 to 28.2 s: about 14 s pending with no activity, then a 12.5 s run |
| while the edit's fast work still ran | 4 | 13.2 to 14.2 s: the slow file starts within 1 s of the fast tier's end |

(Two "immediate" trials read status before the edit became a revision and are discarded. Three earlier trials had a faulty settle check. Raw lines are in `stopwait-run1.jsonl` and `stopwait-run2.jsonl`.)

- The 14 s: slow work waiting on a consumer in a turn is looked at again only every `SLOW_RECHECK_MS` = 15,000 (`src/core/scheduler/slow-tier.ts`). A silent Stop's `endTurn` writes the idle state to the store and sends no nudge (`src/core/delivery/turn.ts`, `src/harness/shared/stop.ts`). Interactive sessions pay the same delay before the slow tier starts at a pause. *read in source code; verified by experiment*
- The fixture's slow file: 170 recorded runs in the retained cells, wall median 12.3 s, p90 12.4 s, max 13.6 s. Eval cells: median 68 s, max 115 s, against a 900 s cell deadline. *verified by experiment (cell stores)*
- This repository's `test/e2e` (10 files; not declared slow in `squeal.config.json`, so these are fast-tier runs, 2026-10-06 to 2026-10-11, at this host's working-day load). Per-file sums of check durations: lifecycle 40 s median (p90 83), policy 63 (108), slow-vitest 51 (84), worktrees 30 (104), slow-node-test 28 (83), node-test 22 (87), transitions 16 (51), shipped-plugin 11 (36), plugin-copy and torn-status under 1 s. Tiers of 4 e2e files: 92 runs, median 63 s, p90 106 s, max 292 s. So a full slow tier at `slow.maxParallel` 4 is about 1 to 2 min at the median and 3 min at p90. 004's research measured 71 s plain and 84 s at low priority at lower load. *verified by experiment (store)*
- The load guard (004 D3) applies to every trigger, explicit requests included (`#waitForCapacity` in `next`): at 1-minute load per CPU above 1.0 a slow file waits up to `slow.maxDeferMs` (600 s) per pass. At this host's usual 45 to 70 on 24 CPUs, a Stop wait would mostly wait for the guard. The eval starts cells only below the CPU count, so its fixture rarely meets the guard. *read in source code*
- Hook budgets: every Squeal Stop hook has `timeout: 2`, in both plugins. A wait needs its own Stop entry with a long timeout, as the waiter has (3600). The existing 2 s hook stays as it is, so an interactive Stop never waits on a bug. Codex runs all matching hooks concurrently, and Claude Code runs a Stop's hooks in parallel. *read in source code (hooks.json); read in 002-01*
- The claim comes before Stop. A wait that passes silently leaves a claim made on pending evidence: it removes false passes on slow failures, not stale claims. Only a Stop that speaks, or a step before the claim (§2), changes the claim. *inferred*
- With 004-29's drain: the drain stays for what the wait did not finish (bound reached, killed session). After a finished wait it finds nothing pending. The wait relies on the idle trigger, so it needs the nudge first or it pays the 15 s. With 004 D9: "Stop never waits for slow files" holds for interactive sessions, where the waiter wakes the agent. For a one-shot session, D9 and goal 4 need an amendment, since no next prompt comes and the drain's results reach nobody (the eval's 20 misses). *inferred*

## Recommendation for Squeal

Board rows, column shape `Task | Status | Scope | Done when`. Numbers are the coordinator's to assign.

| Task | Status | Scope | Done when |
|---|---|---|---|

One worker: `src/harness/shared/stop.ts`, the daemon's request handler, `src/core/scheduler/slow-tier.ts`, tests. | A scheduler test: idle consumer, slow file pending, nudge, the slow tier starts with no timer advance (red before); the probe shape gives Stop to slow-current within the file's run time plus 1 s. |

One worker: `src/cli/run-slow.ts`, `src/cli/status-wait*.ts`, references, tests. | A CLI test with a fake daemon: `run --slow --wait 60000` returns only once the queued slow file has a result, or on timeout (red before); `status --wait` unchanged for edits. |

| one-shot session detection | planned, after the human decides on the D9 amendment | `isOneShot(input, env, harness process)`: Claude by entrypoint plus harness argv (`-p`/`--print` without `--input-format stream-json`), the GitHub Action entrypoint or `CI`; Codex by the rollout's `session_meta.source == "exec"`; anything unreadable is false. One worker: `src/harness/shared/` (new module), `harness-process.ts` (cmdline read), tests on recorded inputs. | Tests: eval-shaped `claude -p` and `codex exec` inputs are one-shot; interactive Claude, a stream-json SDK session, Codex TUI and app-server rollouts, macOS (no `/proc`) are not. |
| a one-shot session's Stop waits for its slow tier | planned, after the two rows above | A second Stop entry (long timeout) waits, only in a one-shot session, for pending slow files up to a new `stop.oneShotSlowWaitMs`. Silent on pass. On a slow failure it blocks once with the failure. Amends 004 D9 and goal 4. The drain stays. One worker: hooks.json in both plugins, `src/harness/shared/stop.ts` or a sibling, policy key, tests. | Tests: a one-shot Stop waits and blocks on a slow failure; it returns at the bound with a note; an interactive or SDK Stop returns at once; the existing 2 s Stop is unchanged. |

Order: the two variants first (spend, the 006 coordinator's), with the nudge and the `run --slow --wait` rows beside them, since they are product defects whatever the variants say. Then the primer row, sized by the variants. The detection and one-shot wait rows wait for the human's D9 call. Do not chase Claude Code skill loading through the description: Claude Code's rule is task-level, and the primer reaches every session.

## Open questions

1. 006 (eval design): should `current-before-claim` count a completed full own run after the last edit, while Squeal cannot answer (slow pending, no wait that holds), as met? 14 of 20 misses are that case, with true claims. And should step 4's "say what is still pending" claim count as met?
2. Silent or speaking pass after a one-shot Stop wait: speaking costs one model turn per session but lets the agent restate a claim made on pending evidence.
3. Does Claude Code truncate a plugin skill's description in its listing? The listing attachment is not in `stream-json`. Not determined.
4. Whether a `Skill` call in the eval's `-p` would be refused (inferred from the bundle, never attempted).
5. The `-p` argv rule is from Claude Code 2.1.296 and Codex 0.160.1. Both signals are undocumented, so they need a check on each upgrade, as `CLAUDE_CODE_SESSION_ATTENDED` already does.
6. Load-confounded: the Stop-wait trials ran at load 17 to 73 on 24 CPUs and the e2e numbers at working-day load; there is no calm-load figure.
