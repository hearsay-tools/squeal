# 001 Core validation loop

Stage: draft for review. Evidence: the four documents under `research/`. Decisions that span specs: ADR 0001, 0002, 0003.

## Problem

Coding agents validate synchronously or not at all. They forget to run tests, run the wrong command, miss failures that were already there, and discover at the end of a task that an early edit broke something a later edit built on. Watch-mode tools exist for humans but not in a form an agent harness can consume: event-driven, revision-aware, machine-readable, and honest about what has and has not been checked.

Squeal v1 proves the interaction model from `docs/vision.md`: push transitions, pull state. One test ecosystem (Vitest), one harness (Claude Code), one repository with any number of git worktrees.

## Goals

Each goal is testable.

1. An agent editing a Vitest project learns about a `PASS -> FAIL` transition within one tool call of the result being known, inside the same turn, without running tests itself.
2. The matching `FAIL -> PASS` arrives the same way. Nothing arrives for `PASS -> PASS` or for a failure that is still failing with the same diagnostic.
3. Everything the agent is told is true at the moment it is told: a delivered state is the current known state, labelled with the revision it was validated at and whether the current revision is still pending for that check.
4. A new worktree of a repository that already has a baseline inherits every result whose inputs are byte-identical, without running them, and reports them as inherited.
5. `squeal status` answers, for the current worktree and revision: known failures, counts of checks current, pending, stale and unknown, whether a full-suite run exists for this revision, and whether the daemon is alive.
6. No Squeal hook ever blocks the agent for more than its configured timeout (2 s default), and a dead or hung daemon degrades to "status unavailable", never to a stall.
7. One shared store per repository serves several worktrees and several agents at once without lost writes or corruption.

## Non-goals

- Per-test closures from runtime coverage. V1 closures are per test file and static.
- Runtime file reads, environment variables and network as dependency inputs. The closure is declared incomplete by construction.
- Any check type other than Vitest tests. pytest is the second runner, in a later spec.
- Any harness other than Claude Code. The adapter interface is kept harness-neutral; other adapters are later specs.
- Background re-verification of inherited passes. Recorded as an open question.
- Dashboards, remote or networked stores, distributed workers.
- Idle wake-up in Claude Code `-p` mode. Not possible without blocking the agent (research, claude-code-integration §4).
- macOS verification. The design accounts for macOS findings from source and docs, but nothing in v1 was run there.

## Design

### D1. Workspace, repository, store

A **worktree** is one git working tree: the nearest ancestor of a path that is a git top level. Every worktree has its own daemon, revision counter, Vitest instance and file hash cache. A directory below a worktree root that contains its own `.git` entry is another worktree, or a clone or submodule, and is opaque to the parent: never watched, never validated.

A **repository** is the set of worktrees sharing one git common directory. The **store** is `<git-common-dir>/squeal/`. In a normal repository that is `<main worktree>/.git/squeal/`, so it lives in the main worktree, is never watched, and cannot be committed. Layout:

- `store.sqlite`: the shared database (D8).
- `locks/<worktree-hash>.sqlite`: one exclusive-lock database per worktree, the daemon singleton (D10).
- `runs/<run-id>/`: full runner output per run, referenced from results, pruned with them.

Hook scripts resolve the common directory without spawning git: if `<root>/.git` is a directory, that is it; if it is a file, follow its `gitdir:` entry and then `<gitdir>/commondir`. The daemon uses `git rev-parse --path-format=absolute --git-common-dir` and records the result.

The unix socket for liveness is `<runtime dir>/squeal-<worktree-hash>.sock`, never under the worktree, because socket paths are limited to 104 bytes on macOS and nested worktree paths exceed that. Without a runtime directory, or when that path would pass the bind limit, it lives in `/tmp/squeal-<uid>`, the per-user directory D10's temp directory also uses, created mode 0700 and checked for owner and mode, never a fixed name in a shared directory. It is never under the inherited `TMPDIR`, which another tool may reap and which differs between the processes that start hooks, so the daemon, every hook and the CLI compute one path. Hooks and the CLI pick the socket by one rule: the one recorded in the store first when its heartbeat is fresh and a daemon answers there, else the computed one.

### D2. Watcher and revisions

The watcher sits behind one internal interface with two backends: chokidar 5 on Linux, @parcel/watcher on macOS. The Linux choice is the only backend that passed every correctness scenario in research; the macOS choice avoids per-file descriptors and reports dropped events. Node's recursive `fs.watch` is excluded: it loses writes after an atomic save.

Watcher events are hints. Each debounced batch (100 ms quiet, 500 ms maximum) is reconciled: every reported path is re-stat'ed and, if `mtime`, `size` or inode changed, re-hashed with the git blob hash. Paths whose hash is unchanged are dropped. If anything remains, the worktree's **revision** increments by one and the revision records the changed paths with old and new hashes, the time, `HEAD`, and whether the tree is dirty. A revision is never created by a touch or a no-op save. Creating a revision never waits on the runner: the store work (revision row, stat cache, content re-key, queued phases) completes within the debounce window even while a tier is running, and the runner-dependent refinement is queued behind the tier separately and applied without holding the revision path. The last revision whose refinement was applied is recorded, and headers, status and every wait treat a revision ahead of it as pending, so a test file added during a tier is never reported as nothing pending.

Ignore rules come from git, in three layers: at watch time, exclude `.git`, nested worktree roots, and the output of `git ls-files --others --ignored --exclude-standard --directory`; at batch time, run the paths through one `git check-ignore --stdin`, except a path beyond a symlinked directory below the root, which git refuses and can never track: it takes the class of the outermost link above it, which git accepts. The link's subtree is ignored when git ignores the link's own path or would ignore a directory at that path (a linked `node_modules` under `node_modules/`, which never matches the link itself, a file to git); the second is asked as `L/` through one `git check-ignore --no-index --stdin` with the worktree's git directory against a scratch work tree under the daemon's temp directory (D10), reused, holding only copies of the `.gitignore` files above the link, so `info/exclude` and `core.excludesFile` apply too. Any other symlinked directory is a project directory: its descendants are candidates, the watcher watches its target and reports each event under the link's path, and every reconciliation pass walks it, since git status never lists what is behind a link; links inside it are not followed, and a link to the root or above it, or to another repository, is not observed. A batch git refuses anyway is split until the path it names stands alone and counts as ignored, so one path never fails the batch (tasks 001-111 and 001-118, `lessons.md` defect 21, `reviews/wave-11f.md` B1). Recompute the watch-time list when any `.gitignore` changes or a `.git` entry appears under the root. Gitignored files that appear in a known closure (generated code) and the installed-dependency lockfile that the environment hash reads are added to the stat cache and watched individually, so a change to them creates a revision like any other input, even though the ignored tree around them is not watched; the installed lockfile is read and watched through a linked `node_modules` the same way. A test file is never keyed while any of its closure paths is untracked by the stat cache.

A reconciliation pass runs every 30 s when idle and on daemon start: `git status --porcelain` plus a re-stat of every file in the hash cache. Anything the watcher missed becomes a revision then. This bounds the damage of a lost event to latency, never to a false "current".

### D3. Fingerprints: file hashes, environment hash, check keys

Results are keyed by what produced them, never by where or when. The commit SHA, revision and worktree are provenance, stored beside each result and shown to agents, never part of the key. (ADR 0002; research, result-fingerprinting-prior-art R1 to R4.)

- **File hash**: the git blob id of the bytes on disk, `sha1("blob <len>\0" + bytes)` (SHA-256 in `objectFormat=sha256` repositories). It is read from the git index only when git reports the file clean and no `eol`, `text` or `filter` attribute applies to it; otherwise the bytes are hashed. One definition everywhere.
- **Environment hash**, per Vitest project per worktree: Squeal version and runner-adapter version, Vitest and Node versions, platform and arch, the resolved Vitest config, the contents of the config file and its `configFileDependencies`, the closure of every `setupFiles` and `globalSetup` entry, the installed dependencies every test file can load (below), and allow-listed environment variables. Policy-declared `inputs` enter closures, not the environment hash, so they are never counted twice. npm's hidden lockfile `node_modules/.package-lock.json` stands for the install only while npm itself would trust it: every package folder in the `node_modules` hierarchy (the root's and each listed workspace's, recursively) is listed in it, every folder it lists exists, and none is newer than it, workspace links compared with `lstat` and never followed. Otherwise the fingerprint hashes the package folders instead (each folder's path and its `package.json` name and version, each link's path and target), so an install that bypassed the file still re-keys, and one daemon note, recorded once each time it changes and not again by a later daemon start that finds it unchanged, names the first unlisted, newer or missing folder of each kind (tasks 001-104, 001-105, 001-109).
- **Installed dependencies** (tasks 001-105, 001-109; scheme B of `research/per-package-keys.md`). The *whole fingerprint* hashes the installed lockfile metadata under `node_modules` (or the package folders, above) plus `patches/`. While npm's hidden lockfile is trusted, the environment hash holds only the lockfile closure of what every test file of the project can load, plus a hash of `patches/`: the runner (`vitest`, looked up from the project root, with its peers, so `vite`); the installed packages the setup and `globalSetup` closures import; the bare imports and literal `require`s of the config file and its `configFileDependencies` (the config's plugins); and the packages the resolved config names by string, looked up from the project root: the `environment`'s package (`vitest-environment-<name>`, or `jsdom`, `happy-dom`, `@edge-runtime/vm` for the builtins), every reporter given as a package name, and the packages of the paths Vitest resolves `snapshotSerializers`, `runner`, `snapshotEnvironment` and `diff` to. Each test file's key adds the sorted `location@version#integrity` set of the lockfile closure of the installed packages its closure's project files import in one hop, without those already in the environment. Those packages are the package entries Vite resolved, the specifiers Vite left bare, the targets of literal `require("x")` calls found by a scan of each project file's source on disk, cached per transform as D4's rule 3 scan is (Vitest's module runner gives every module a `require` that no transform dependency lists), and the environment package a `@vitest-environment` or `@jest-environment` docblock of the test file names, looked up from the project root. A package is found as Node finds it: from the directory of a package entry Vite resolved (`<dir>/node_modules/<name>/…`), or of the importer for a bare or required specifier, then each parent directory, closed over `dependencies`, `optionalDependencies` and `peerDependencies`. A name that does not resolve keys as absent, so its install re-keys; a workspace link keys as its location, since its files are project files in the closure; a package with no runtime file (only declarations, the manifest and documentation; `.json` and `.ts` count as runtime) keys as a constant and is not expanded, so `@types/node` re-keys no file that keeps its own segment, unless a project file imports the package's own `package.json`, which keys its version; an entry outside the worktree is left out, as no install of this worktree holds it.

  A test file keys by the whole fingerprint instead, so every lockfile change re-keys it, in exactly these cases: (1) a project file of its closure imports `child_process`, `worker_threads`, `cluster` or `module`; (2) a project file's source calls `require.resolve`, `createRequire` or `import.meta.resolve`, or `require(` with anything but one string literal (the scan above); (3) its closure reaches a file under `node_modules` that belongs to no package, such as Vite's pre-bundled `.vite/deps_ssr`; (4) its package set holds an *opaque* package, one whose own code references `child_process`, `worker_threads`, `cluster` or `module` as a module specifier (`require`, `import`, `from`, `getBuiltinModule`, a `node:` string, or for the first two any string literal), found by a scan of the package's code files, nested `node_modules` left out, once per installed version (`location@version#integrity`) and kept in memory for the daemon's lifetime; (5) the runner reports no packages for it (`node:test` until spec 003's 003-22). A process, a thread or a hand-made resolution can load a package no import names, and only these cases see one. The environment hash holds the whole fingerprint, and no test file adds anything, when the hidden lockfile is stale, for every other lockfile format (pnpm's `lock.yaml` and yarn's are not read yet), when the runner reports no environment packages, when the setup closures or the config files meet case (1), (2) or (3), or when an environment package other than the runner's and the config file's own imports is opaque: the runner and the config's plugins drive the run in Vitest's process and no test file imports them, and `vite`, `vitest` and common plugins (`@tailwindcss/vite`) reach these builtins by design. Accepted misses of scheme B, each a key that can hold through a bump that changes a result: a package loaded in-process by a package without declaring it (an undeclared `require`, a computed `import()`), a `node_modules` path built by hand and read with `fs`, a package that the runner or a config plugin starts in a child process or worker, and, under a running daemon, a package folder added below the root `node_modules` without rewriting the hidden lockfile, which re-keys only at the next start; one added at the top level re-keys before the next tier, since the check before every tier (D5) lists the root `node_modules` entries and reads the environments again when they moved. A closure restored from the store at bootstrap carries no packages (`test_files` stores paths only), so it keys by the whole fingerprint until the runner resolves it again on a miss (D5). On `cezar`, between the main checkout's install read as-is and a fresh `npm ci` of `origin/main`, 265 of 632 test files keep their key, none of them falling back; 310 fall back through cases (1) and (2) (306 reach `child_process`, two more call `import.meta.resolve`) and 57 through case (4) (`commander`, `es-toolkit`, `import-meta-resolve` and `marked` in 56 `web` files, `cross-spawn` in one `server` file); read under npm's rule, the main checkout's lockfile is stale (one unlisted folder) and none keeps its key. Keying all 632 files costs 64 ms on a warm scan cache; a daemon's first keying scans the 177 packages the test files' segments reach and costs 0.39 s; scanning all 555 installed packages costs 0.75 to 0.84 s (load 7 to 42; `tasks/001-105/notes.md`).
- **Check key**, per test file: `sha256(envHash, projectName, relative test path, installed-dependency segment, sorted (path, fileHash) over the closure)`. The segment is the test file's package set above, the whole fingerprint for a file that falls back, or empty when the environment hash holds the whole fingerprint. All tests in a file share its key.
- **Closure** of a test file: the test file, its transitive static and dynamic project imports from Vitest's transform graph (D4), its snapshot file path whether or not the file exists, for every unresolved import the target path and its resolution candidates (each configured extension and `index` file), any policy-declared `inputs` globs that match, and, while policy `observe.runtimeInputs` holds, the project paths the file's runs were observed to read, stat, list, load or execute (D4), shared per project across worktrees and merged (task 001-132; research, observed-runtime-inputs). The observed set is one map per project from test path to paths, in `meta` under `observed.<project>`, written in one transaction that merges and never prunes, so a read that disappears over-runs and never misses; a worktree reads it when it first keys a project's files and again before it records a tier. A listed directory enters as its listing path (`dir/`, the root `./`) and hashes as its sorted entry names among the files the watcher tracks (a file, or a subdirectory holding one), so an add or delete below it re-keys the file. A path git ignores is dropped, since the watcher does not track it (`web/dist` on `cezar` is such a read). Absent paths hash as absent, so the key changes the moment such a file appears, incrementally and at bootstrap. `node_modules` is excluded from the closure and covered by the installed dependencies above. Every closure carries `complete: false` in v1; status reports the closure method as "static imports plus declared inputs" (task 001-132 left that text as it was, observed reads included).

Incremental maintenance follows Bazel, Nx and the git index: a stat cache `path -> (mtime, ctime, size, inode, hash)`, a reverse index `path -> test files`, and re-computation only of the keys that reference a changed path. Adding or deleting a file re-resolves closures of test files that import from the affected directory, because module resolution can change without any closure file's content changing. Most such test files are also reported by the runner's `affected` (D4) or by an absent resolution candidate in their closure; only the `package.json` rule reports the importers of a directory whose `package.json` was added, deleted or edited, because the manifest is in no closure and in no module graph. It re-resolves every closure with a path below that directory, since the entry the manifest names, or named, may lie below it (`"main": "lib/entry.ts"`) (tasks 001-72, 001-79). The root `package.json` re-resolves every closure, since its `imports` and the package imported by its own name can resolve anywhere (001-81).

### D4. Vitest runner adapter

One `createVitest('test', { root, watch: false, reporters: [squealReporter], update: 'none', includeTaskLocation: true })` per worktree, then `standalone()`. Vitest's own watcher is never used. The adapter exposes, through the runner interface that later adapters will implement:

- `invalidate(paths)`: calls `invalidateFile` for each changed path. An add or delete also invalidates the cached transforms it can make wrong, and only those, because a transform holds each import as Vite resolved it and an unresolvable specifier verbatim. On delete: every module that imports the deleted path. On add, every module with (1) an import whose target has the added path among its resolution candidates (D3: each configured extension, `index` with each extension, the TypeScript twin of a JavaScript extension), whether the import was unresolved or resolved to a candidate the added path now shadows; (2) an unresolved import that is not relative, which is an alias, `tsconfig` `paths` or a package specifier, since Vite turns every import it resolves into a `/…` or `/@fs/…` URL; (3) `import.meta.glob` or a template-literal dynamic import in its source, which Vite expands from the files on disk at transform time, found by a regex over the source on disk (not the emitted code) cached per transform, one path for every project because Vitest does not pass a plugin given at `createVitest` to a project with its own Vite server; the scan covers a dependency Vitest inlines from `node_modules` (an externalized one has no cached transform), and a module with no source on disk, a virtual module served by a plugin's `load`, counts as expanding; (4) a resolved import under a directory the added path now shadows, which covers a directory resolved through its own `package.json`. An added, deleted or edited `package.json` also stales every module with a resolved import under its directory, because the directory, or the package imported by name, may now resolve to another entry. Of the edits, only a manifest edit takes this path, so a plain edit costs what it did (001-79). It also stales every module under that directory that has an import, since a subpath import (`#x`) resolves through the `imports` of the module's nearest manifest. Vite caches the package data it read, so each such manifest goes through `pluginContainer.watchChange`, the hook Vite's own watcher calls, in every environment; for an added manifest that hook drops nothing, so the nearest-package lookups at or below its directory are also dropped from Vite's internal `packageCache` (001-81). An edit that changes only fields no resolver reads (`scripts`, `version`, `description`, `keywords`, `author`, `contributors`, `license`, `repository`, `bugs`, `homepage`, `funding`, `private`) against the ones recorded when the instance last saw that manifest stales nothing; every other field counts, so a field named in `resolve.mainFields` or read by a plugin re-resolves when edited (`reviews/wave-9c.md` B1); the first edit after a start has none recorded and stales as above. On the cost fixture, `affected` after that first edit of `src/gen/package.json` costs 0.73 to 1.03 s, about 40 percent of the cold walk, and after a later `scripts`-only edit 17.6 to 20.4 ms against 28.4 to 38.2 ms after a plain edit (001-81, three local runs on a loaded machine, cold 2.2 to 2.4 s). So does an added path that a `package.json` in an ancestor directory below the project root names as its `main` or `module`, up to resolution candidates and a trailing slash: while that entry was missing, Vite resolved the directory to its `index`. A string `exports` or `exports["."]` is matched the same way, defensively: with `exports` present Vite does not fall back to `index`, so the import was unresolved and rule 1 already stales its importer (`reviews/wave-7.6.md` N2). A module Vite soft-invalidated still counts, because it is re-served with its old resolutions; that reads Vite's internal `invalidationState`, checked once per instance, and a Vite without it falls back to invalidating every cached transform with one note. Calls `clearSpecificationsCache()` when a path matching a test glob was added or removed; recreates the instance when the config file or one of its dependencies changed (about 50 to 200 ms). Invalidating every transform instead cost 5 to 6 s on the next `affected` on a 516-file repository (`lessons.md`, defect 11). On a 1,000-module, 205-test-file fixture (`structural-cost.test.ts`), `affected` right after an add costs 15.7 to 17.4 ms locally against 12.6 to 15.6 ms after a plain edit and 0.92 to 1.0 s cold (001-60, five runs); on CI (GitHub Actions run 37579065539, the code of `ae24aaf`) 20.5 ms against 17.6 ms warm, 20.5 ms after an edit and 1.9 s cold on Node 22, and 18.7 ms against 15.0 ms warm, 18.3 ms after an edit and 1.8 s cold on Node 24. The add carries a fixed part the warm walk does not, re-globbing the test files and transforming the new file, so only `affected` after an add under a quarter of the cold walk is asserted. The add's own `invalidate` costs 5 to 8 ms, and 18 to 21 ms the first time, when it scans the source of every module (tasks 001-53, 001-56, 001-60).
- `affected(changedPaths) -> test files`: the `related` walk (`config.related` plus `getRelevantTestSpecifications()`), which transforms without executing and costs about 100 ms cold and 2 ms warm on 50 files. Squeal adds what Vitest's walk misses: all test files of a project when a setup file, its closure, `globalSetup`, or the config changed; the owning test file when a `.snap` changed.
- `closure(testFile) -> paths`: from the same transform graph, plus the additions in D3. With them the installed packages and Node builtins the closure's project files import in one hop (`RunnerClosure.packages`): the package entries the walk reaches and stops at, the specifiers Vite left bare and the literal `require` targets of the source scan, with the importer's directory, and the test file's docblock environment, with the project root; a load no specifier names, or a file under `node_modules` in no package, is reported as the builtin `module`. `environment()` reports the same for the setup and `globalSetup` closures and the config files, plus the packages the resolved config names by string, and marks the runner and the config files' imports as `RunnerPackages.runner` (`RunnerEnvironment.packages`, tasks 001-105, 001-109).
- **Observed runtime inputs** (task 001-132; research, observed-runtime-inputs F1 to F4). While policy `observe.runtimeInputs` holds, every worker carries one CommonJS recorder (`src/runners/observe/recorder.cjs`, in each plugin's `dist/observe/`), a `--require` preload delivered through `createVitest`'s `env` option, which Vitest spreads into the workers of every project in both pools: `--require <recorder>` ahead of the daemon's own `NODE_OPTIONS`, and the recorder's settings in `SQUEAL_OBSERVE`. A project whose config sets `env.NODE_OPTIONS` gets the recorder ahead of its value. Neither enters the resolved config of D3, which Vitest copies the option into for a root project. The recorder wraps `fs` (sync, callback and promise forms), `ChildProcess.prototype.spawn` (every async spawn, `exec`, `execFile` and `fork`), `spawnSync`, `execSync`, `execFileSync` and the `Worker` constructor, registers a `module.registerHooks` resolve hook, and records a process's entry point and the existing files a spawn's arguments name. It changes no call's arguments or result except a child's env: at each spawn and Worker it puts `--require <recorder>` into the child's `NODE_OPTIONS` and its settings into `SQUEAL_OBSERVE`, whatever env the caller passed (`env: {}` and an allowlisted env too), so grandchildren are recorded; an error of its own is swallowed. It attributes an event by `__vitest_worker__.filepath` in a worker and by the test file its parent passed in a child or thread, keeps only paths under the worktree outside `node_modules`, `.git`, its own directory and the temp directory (unless the worktree lies inside it), and writes them batched: each process appends the paths new to it once per event-loop turn that found any, at exit, and before it sends its parent a message, since Vitest stops a fork with SIGTERM and a thread with `terminate()` and neither runs an exit hook. `run()` returns, per completed file, the paths it read, stat'ed, loaded or executed and the directories it listed, less the paths the run wrote and the directories it only stat'ed (`RunReport.observed`). While observing, the environment's adapter version carries the recorder's version, so a pass stored before observation runs once more. With the policy off, or a build with no recorder file, nothing is observed and keys are as before. Spec 003 decision 3 ("not observed past the spawn") is reversed for this recorder's reach; the node:test runner adopts the shared recorder in a row of spec 003. Not seen, and left to `inputs` (D11): what a non-Node child reads (a shell script's `cat`), native file access (`node:sqlite`), Vitest's own process (`globalSetup`, plugins, a computed `import()` Vite loads), an async `--loader`'s own thread, ignored paths and paths outside the worktree. On `cezar` (640 files, three full suites each way), a file's time with the recorder over its time without is 0.97 at p50 and 1.50 at p90, `web`'s jsdom files paying about 150 ms each at p50; 150 files observe paths beyond their snapshot, 4 per file at p50 and 787 at most; no file failed only with the recorder outside one run under contention (`tasks/001-132/notes.md`).
- `enumerate(testFile) -> check ids`: `parseSpecifications`, static, about 35 ms for 50 files. `test.each` appears as one templated entry until the file has run.
- `run(testFiles) -> results`: `runTestSpecifications`. Results come only from the reporter hooks `onTestCaseResult`, `onTestModuleEnd` and `onTestRunEnd`, never from the cumulative `TestRunResult`, which includes stale modules. File-level errors (import or syntax failures) become a `fail` for every check previously known in that file plus one file-level check. `process.exitCode` is reset after each run.

Check identity is `(project name, relative test path, fullName)`. When two tests in one file share a `fullName`, the second and later ones carry their source line as a suffix. Vitest's positional ids are used only within one run. Stack paths are relativized before storage. Per-run floor is 110 to 350 ms even for one file, so changes are batched per revision and runs are issued in tiers (D5).

### D5. Scheduler and result validity

Validity is per check, not per run. A stored result is **current** for a check in a worktree at a revision when its key equals the key computed for that check at that revision. Otherwise the check is **stale** (an older result exists under another key) or **unknown** (no result at all). **Pending** means a run that will produce a result for the current key is queued or running.

On each new revision the daemon:

1. invalidates changed paths in the runner and updates the stat cache and reverse index;
2. computes the affected test files and recomputes their keys;
3. looks each new key up in the store. A hit is promoted to current for this worktree with its provenance intact. No run is needed. This is the inheritance path for new worktrees and the de-duplication path between worktrees that have identical files;
4. orders the misses: checks whose last known state is `fail` (including inherited failures), then test files that import a changed path directly according to the runner's module graph, then transitively affected files, then never-run files; within a class, shortest last known duration first, so a slow integration file never delays the edited module's own unit test. A file's duration is the whole file as the runner reports it (Vitest: the module's collection, setup files, hooks and tests), not only its test cases. Work an edit caused, a test file whose closure a revision changed, that a revision added or edited, or that the runner reports as a direct importer, runs ahead of the baseline, an environment change, `run --all` and files re-queued after a discard or a crash, at the next tier boundary; within each of the two groups this order stands, and a queued file an edit reaches joins the first group until it runs. After four tiers in a row of the first group only while the second waited, the next tier is the second group's, so edits that keep the first group full still move the backlog by one tier in five (task 001-107). An environment input is in no closure, so the files an install or a config edit re-keys stay in the second (`lessons.md`, defect 19; on 200 queued failing files after a config edit, the edited module's test file ran fifth, before 195; task 001-100);
5. runs them in tiers of a configurable size (default 4 test files). Between tiers it re-plans against the latest revision. While the queue holds no work an edit caused, a tier is the backlog's and takes every queued file up to `runner.backlogTierSize` (default 200) and up to 300 s of last-known file durations, or half of `runner.timeoutMs` when that is less, summed as if the files ran one after another. The budget limits the files' last-known run time, not the tier's wall-clock time: a file with no known duration counts 0, the first file is always taken whatever its duration, a file may run slower than it last did, and a tier cut short by the run deadline or a cancel gets the runner's grace before it is forced (below and D12); no hard wall-clock cap exists (review wave 12b, S1) (`lessons.md`, defect 25: 559 tiers of 4 took 4.6 h where the project's own run took 514 s; task 001-124). A tier with any work an edit caused in the queue, including the backlog's turn after four tiers of the first group, is never cancelled by a new revision. A backlog tier in flight is cancelled by a revision whose content re-key queues work an edit caused, that adds or deletes a path (only the runner part, which waits for the runner, finds what it reaches), or that changes an input of the tier (its results would be discarded); an edit no test file reaches lets it finish. The cancel is the runner's own (Vitest's `cancelCurrentRun`, forced after 1 s, the instance dropped when its workers do not stop, as on a timeout, D12): the files whose module ended before the cancel keep their results under the stability check below, the rest go back to the queue uncounted, still forced when `run --all --force` queued them, and the edit's tier runs next. A daemon that exits still lets its tier store (D10), so a departure waits for the running backlog tier however long it takes; the budget bounds only its files' last-known run time. On 200 one-module test files after a config edit, the backlog ran in one tier in 10.8 s against 9.7 s for a direct `vitest run`; with tiers of 4 it took 18.0 s in 50 tiers against 7.0 s in a second measurement; an edit that landed after 23 of them completed cancelled the tier and ran its test file first in a tier of 4 (task 001-124, a host at load 72 on 24 CPUs). A runner that cannot cancel (node:test, spec 003) runs its part of the tier to the end.

Steps 1 and 2 are split so that the store never shows a revision whose classification lags: the revision row, the stat cache flush, the content re-key of every test file referencing a changed path, their `queued` pending phase and the refreshed known states are written in one transaction. The runner-dependent part (invalidation, affected set, re-resolved closures) refines keys afterwards; for structural changes the possibly affected files, or every file of the project when the set is unknown without the runner, are marked `queued` in that same first transaction.

A runner call that fails is a state, never a skip: when environment, invalidation or closure resolution fails for a project, every test file of that project becomes `unknown` at this revision with the runner's message as the reason, one factual line is delivered, and a note is persisted for status. A failed test-file listing keeps the previous list; checks are never retired because a listing failed. A run whose runner cannot load modules is a runner failure too, never a test result (`lessons.md`, defect 12): an ENOENT under the instance's own temp directory (Vitest copies transformed modules there for its forks pool), or an error raised by Vite's module runner whose message and stack name no project file (an installed file read while `npm ci` replaces it), ends the run `crashed` (D12), so its files become `unknown`, nothing is stored under a key, one line is delivered, the run's note is persisted for status, and the instance is recreated before the next runner call. A test file's own errors stay a `fail`: an import of a missing module or package names the importing file, a syntax error is raised by the transform, and a module that throws while imported is the top frame. The instance is also recreated when an installed lockfile (D3) appears or changes, with `vitest/node` imported again from the worktree (one that disappears ends the daemon, below), so a worktree registered before its dependencies were installed stops running its parent's Vitest after the install. A Vitest at the same resolved path keeps the module already imported; a new Vitest version there needs a daemon restart. An unkeyed or `unknown` file is always work to do: baseline and `run --all` include it, and a checkpoint containing one ends `abandoned`, never `completed`.

A worktree without its own dependencies is not validated (`lessons.md`, defect 18; tasks 001-100, 001-107). When the root `package.json` declares dependencies (`dependencies`, `devDependencies` or `optionalDependencies` not empty, or `workspaces`, whose packages only an install links) and nothing is installed for it, the daemon makes no runner call for any runner: it reconciles the stat cache and records revisions, with nothing left for the runner, but lists, keys and runs nothing. The test files an earlier daemon listed are `unknown` with the reason "no dependencies are installed in this worktree", one note is persisted, and `meta` holds `awaiting-install.<worktree>` = `true`, the one source of this state: every header says "No dependencies are installed in this worktree; Squeal lists and runs no tests until an install." in place of D6's install sentences, so the registration header says it and nothing else is pushed. Installed means an installed lockfile of D3's list at the root (one above the root does not count), and a lockfile a repository commits is not one on its own: `bun.lock` and `bun.lockb` count only beside the root's `node_modules`, `.pnp.cjs` and `.pnp.js` only beside Yarn's `.yarn/install-state.gz`, and `yarn.lock`, `pnpm-lock.yaml` and `package-lock.json` are not on D3's list. With none at the root, the root is installed when every workspace that declares dependencies has an installed lockfile of its own; while some have one and others not, `meta` holds the missing workspaces and the header says "No dependencies are installed at this worktree's root or in a, b, c and N more". A daemon that died while waiting left the flag: the next daemon clears it at its start before it decides again, and a header with no daemon live does not say it. Every reconciliation pass looks for the installed lockfile again, as it does for one that moved, and so does `run --all`; the pass that finds it runs the baseline. A `run --all` while still waiting records its checkpoint `abandoned` at once, never `completed`, and no header counts a checkpoint as a listing or a full suite while the wait holds. The paths revisions changed during the wait are edits to the baseline: a miss whose closure they touch, or that they added or edited, runs first. So are the paths no runner saw change before the daemon started: those of its start revision and of every revision after the refined one (D2), which a daemon that exited at a reinstall stored and never refined (task 001-113). A manifest that is missing, does not parse or declares nothing validates as before, which a `node:test` project with no dependencies needs (spec 003). Only a daemon's start waits. When the install goes while the daemon runs (a reinstall: `npm ci` removes `node_modules` before it installs), at the root or in a workspace that declares dependencies, the daemon stores nothing more and exits (D10), so no runner instance outlives an install and the next daemon waits with none open (tasks 001-107, 001-113; `reviews/wave-11c.md` B1, B2, decided by the human). It finds this on a revision that changes an installed lockfile or the root `package.json`, on every reconciliation pass, and on the check before every tier: the open checkpoint is abandoned, the queue and the runner parts not applied yet are dropped, the tier in flight records nothing, the revision stays unrefined, and one note says "dependencies were removed under a running daemon (a reinstall); this daemon exits and the next session starts a fresh one". A tier whose run overlapped a change of the install that left it installed stores nothing and its files are re-queued, uncounted and still forced when `run --all --force` queued them: before and after the run the daemon compares the names of the `node_modules` entries (dot entries left out, since npm 7's `ci` empties the directory and keeps it, and Vite creates `.vite` in it) and the stat of `package.json` and of the installed lockfile, at the root and, while the root holds no install, in every workspace that declares dependencies, so an install restored with identical content is caught too.

After each tier, every closure path of the tier's test files is re-stat'ed. If any hash differs from the inputs of the key the tier ran under, that file's results are discarded as unreliable and the file is re-queued. A result is stored only under a key whose inputs were stable for the whole run.

A completed file whose run observed paths its closure lacks (D3, D4; task 001-132) takes them into its closure and the shared observed set first, and the stability check covers them too: a file path against the stat cache, since the tier's snapshot did not hold it, and against the revisions during the run; a listing against the revisions during the run, each add or delete counting for every listing above it. Its results are stored under the key that includes what it read, never under the key it ran under, which lacks it, so its first run neither runs twice nor leaves a result that a worktree with other contents of those paths could inherit. When an edit moved its key during the run, nothing is stored. A listing is not compared with the disk after the run: an add the watcher has not reported yet re-keys the file at the revision that reports it.

Explicit checkpoints: `squeal run --all` queues every test file whose key has no result, or every test file when `--force` is given. On daemon start in a worktree, the baseline is a lookup (step 3 for all test files) followed by a run of the misses, or lookup only, per policy.

### D6. State, transitions and delivery views

The store holds the latest result per `(check id, key)` and the history needed for provenance. For each worktree and check the daemon derives the **known state**: `pass`, `fail`, `skip` (skipped or todo in the runner; counted separately, never a failure, never notable in a delta), `unknown`, with `current | stale | pending` validity, the revision and commit it was observed at, its origin (`own` or `inherited from <worktree> at <commit>`), duration, location, a concise failure summary, and a **diagnostic fingerprint** (normalized first error line plus source location; normalization removes times, durations, addresses, UUIDs, hex identifiers of 16 or more characters and temp or cache directory paths, so a re-run of the same failure never reads as a changed one).

A **transition** is recorded, per worktree, whenever a new result changes a check's known state in the ways the vision lists: first-seen fail, `pass -> fail`, `fail -> pass`, `fail -> fail` with a changed fingerprint, runner-crash to `unknown`. The file-level check of a test file records `pass` whenever the file loads, so a fixed import or syntax error closes with `fail -> pass` like any test. A check retired while the last state told to a consumer was `fail` is delivered once to that consumer as resolved, worded as no longer reported by the runner, so a renamed or deleted failing test never leaves an open failure in an agent's view. Transitions are the audit log. Agents never read them directly.

Delivery is a diff against a **consumer view**. A consumer is `(worktree, session id, agent id or "main")`. Its view is the state and fingerprint last told to it for each check. On registration the view is seeded with the current known state of every check, so pre-existing and inherited failures are reported once in the registration header as known failures, not later as transitions. Failures first observed by the baseline run after registration are delivered once, in a batch labelled as found by Squeal's run at start. At delivery time the daemon or hook computes the delta between the view and the current known states, keeps only notable differences (the transition kinds above, evaluated between what was told and what is known now), writes the result into the view, and returns the delta. A pass never told to anyone is written into the view silently. A check that broke and recovered between two deliveries produces nothing.

Every delivered message carries a header: daemon liveness when no daemon is validating (since when, and that results are as of the last revision it reached), delivered once per consumer when liveness changes; the worktree's current revision and the paths changed since the revision this consumer was last told about in a delivered header or its registration, a union over the revision records after it (the current revision's paths when it is the one last told; at most three, then "and N more"), how many checks are current, pending, stale and unknown at that revision, how many test files have produced no check yet and in which class they are (a never-run or unkeyed file counts as unknown, a queued one as pending), and whether a full-suite checkpoint completed for it. Delivery and status derive these from one shared header reader; check names are printed and parsed by one shared formatter so that a name an agent was told round-trips into `squeal why`. Failures come first, each in full: its change and that Squeal's run saw it at revision N (at start for the baseline; in another worktree at a commit when inherited, with the revision it was inherited at), and whether its test file's closure holds a path changed in this worktree after the consumer's registration revision, kept in `meta` ("touches files changed here since this session started: a, b, c and N more" or "none of the files changed here since this session started are in its imports"; the lines name changes in the worktree, anyone's, not the session's alone; inherited results are read against this worktree's changes). The closure is the stored one only when this worktree wrote it or the worktree that wrote it has this worktree's current key for the test file; otherwise, or when no closure is stored, or no registration revision was recorded, neither line appears. The registration revision is the worktree's revision when a consumer that is not registered registers, recorded with the start time of the live daemon when that daemon has written its bootstrap marker (`meta`, after `bootstrap`) and the consumer registers at its start (SessionStart other than `compact`, SubagentStart); no hook waits for the marker. A registration that follows the session's tool calls (PostToolBatch, UserPromptSubmit, Stop, SessionStart `compact`) may hold their edits in its registration revision, so it records no start time. A `start` revision is the stat cache's bootstrap only: what changed while no daemon ran, with any edit made before the bootstrap read the file. The change feed's own reconciliation at daemon start is an `interval` revision, so an edit made while the daemon starts is counted. No `start` revision is the agent's: a failure whose closure holds a path changed by a `start` revision after the registration revision, or by the one the registration revision is when the registration recorded no start time (it came before the start scan), gets neither line (a daemon spawned at SessionStart, or restarted while the consumer stays registered). A start scan also hashes the files it has no hash for without a revision (every file of a new worktree, a file created while no daemon ran), so "none of the files changed here" appears only while the daemon whose marker was there at registration is the one recorded; otherwise a failure gets "touches files changed here" when it applies and no line else. A consumer still registered keeps its registration revision when it registers again (`resume`, `compact`). A consumer that unregisters or expires parks it for 12 hours; the same session and agent registering again takes it up, with the revisions made while it was not registered left out, and keeps the daemon start time only when that daemon is still the live one. A test or hook timeout adds the one-minute load average the runner recorded on its error as the result came in. Up to five recoveries are listed one by one; above five they collapse into one summary line ("31 checks recovered (FAIL -> PASS)") and the shorter, in lines, of the recovered list and the list of checks still failing ("still failing: 2" and their names), ties to the still-failing list; a list of more than five names is grouped by test file with counts, ten files and then a count of the rest, when that takes fewer lines than the names. Checks no longer reported by the runner collapse the same way. A header beside a failure says once that no dependencies are installed when the daemon has hashed the worktree's files and no installed lockfile is among them, so failures that cannot find a package are expected until an install; otherwise, a header whose changed paths include an installed lockfile whose newest change among them wrote it (not deleted it) says the results follow a dependency install. A header says at most one of the two. The message is capped at 10,000 characters; overflow is summarized by count with a pointer to `squeal status`. Wording is factual, never imperative: hooks carry no user authority and models do not follow instructions in them (research, claude-code-integration §2).

### D7. Status

`squeal status` and `squeal status --json` read the store directly and need no daemon. Every status read, each `--wait` poll and each poll of Stop's wait (D9) is one read transaction, so it sees one committed state of the store and never pairs a new revision with the previous revision's states. `squeal status --wait <ms>` blocks until nothing is pending at the current revision or a new transition is recorded, then prints the snapshot; it replaces polling with `sleep`. Without a validating daemon nothing pending can finish, so it never reports quiet then: it returns with an outcome of its own, "no daemon has validated since <time>; results are as of revision N", also in the JSON payload. When the daemon has not yet listed the worktree's test files, headers and status say so instead of presenting zero counts as complete. The dirty flag is the one observed at the last revision and is labelled with that revision; when no daemon is validating it is reported as not known. The snapshot contains: worktree root, revision, `HEAD` and dirty flag, daemon liveness and last heartbeat, known failures with fingerprint and location, counts of current / pending / stale / unknown checks, how many current results are inherited and from where, whether a full-suite checkpoint completed for this revision and at which revision the last one completed, the closure method, store schema version, and the latest persisted daemon notes (runner failures, dropped watcher events, tier pump stopped), kept bounded per worktree in `meta`. A checkpoint is one `run --all` or baseline request; its tiers are separate runs that reference it. The human rendering is a separate formatter that reproduces the vision's example. `squeal why <check>` prints the full history and provenance of one check and the path to its last run log.

`squeal remove [--config]` takes Squeal out of a repository. It asks the daemon of every worktree the store records to stop, at the socket `locateDaemon` picks, and takes every daemon lock under `locks/`, waiting a few seconds (5) for each; a lock still held then makes it exit 1, naming the worktree, with nothing deleted. Holding the locks, it deletes the temp directories of the repository's daemons (D10), then `<common-dir>/squeal/`, since finding them needs the repository id: `/tmp/squeal-<uid>/tmp/<key>/` and those moved aside, only while `/tmp/squeal-<uid>` passes the daemon's private-directory check, and the `/tmp/squeal-<uid>-<key>-*` fallbacks, for the key of every recorded root. A path it cannot delete is listed under what remains with its error code, the rest is still deleted, and it exits 3. `--config` also deletes `squeal.config.json` at the worktree root, saying when the deletion is a change to commit; without it the config stays and the output says the next session starts Squeal again. It prints what it removed and what remains (the plugin, the kept config, the `squeal.config.json` of every other worktree git lists, each of which starts Squeal again there), and on a repository with no store says there is nothing to remove and exits 0.

### D8. Shared store

SQLite through `node:sqlite` (Node 22.13 or later; `--disable-warning=ExperimentalWarning` until Node 24 is the floor). WAL mode, `synchronous=NORMAL`, a busy timeout on every connection, short `BEGIN IMMEDIATE` write transactions, schema version in `user_version` with transactional migrations. Research measured 0 lost writes and 0 corruptions under 4 writers, 4 readers and 20 hard kills, with 0.45 ms median reads; JSON lost 75% of updates without a lock and was about 500 times slower with one.

Tables: `worktrees`, `revisions`, `file_hashes`, `test_files` (with the newest closure path list, stored once per test file), `test_file_keys` (the key each worktree computed per test file at its current revision, plus pending phase), `checks`, `results` (keyed by check and key, with a last-used time advanced on every lookup hit), `checkpoints` (one per `run --all` or baseline request, referenced by its tier runs), `runs`, `known_states` (the derived state per worktree and check, written by the daemon so hooks and status classify validity without one), `transitions`, `consumers` and `consumer_views`, `meta`. Failure text is deduplicated by exact text; the fingerprint is a separate derived column. Results under one key are shared by every worktree with that key: the newest run from any worktree replaces the stored outcome, and another worktree's known state follows when it next refreshes that file. Accepted in v1. Crashes and timeouts are never stored as results under a key: an `unknown` under a key would be inherited as a hit. Nor is a runner-environment failure (D5) stored as a `fail`: a `fail` under a key is inherited by every worktree with that key as an ordinary failure, which no code of theirs causes (`lessons.md`, defect 12).

Pruning: keep every result whose key is current in any live worktree plus the newest result per check on the main worktree; drop other keys after 7 days and everything owned by removed worktrees; when `store.maxSizeMb` is set (no cap by default), a size cap evicting least recently used results as a backstop; drop `checks` rows that no result, known state, view or transition references. Checks that disappear from a test file are retired from `known_states` and every consumer view; the file-level error expansion uses the checks of the file's previous key, never every check ever seen. Expected steady state for 5,000 tests at 50 revisions a day is about 40 MB.

A daemon that finds a `user_version` newer than it understands exits and leaves a status entry saying so. Hooks reading a newer schema report "status unavailable, store version newer than this Squeal".

### D9. Claude Code adapter

Shipped as a Claude Code plugin in this repository (ADR 0003). `squeal init` adds the marketplace and the `enabledPlugins` entry to project settings and writes `squeal.config.json` if absent. It never writes raw hook commands into user-owned settings.

Plugin contents:

- `hooks/hooks.json` with every hook `timeout: 2` and scripts under `${CLAUDE_PLUGIN_ROOT}`:
  - `SessionStart`: ensure the daemon (D10), register the consumer, inject the status header followed by the primer. After spawning a daemon it waits up to 750 ms for the daemon's heartbeat, never for its start scan (D6). With source `startup` or `resume` it first unregisters every other consumer of the session id, since that earlier run is gone; after `compact` the same run goes on, so it keeps every consumer and a registered main agent's view, and says only the primer, which compaction dropped. In a repository that has no store yet, SessionStart only spawns the daemon and injects the primer, and the first UserPromptSubmit (interactive) or PostToolBatch registers and injects the header. The **primer** is a short paragraph, the one place a hook tells the agent what to do, as decided by the human: Squeal runs the Vitest tests; do not run Vitest to learn whether edits broke something; results arrive with the next tool call, so keep working, and `squeal status --wait` only when a result is needed before the next step; run tests yourself only without a validating daemon, with unknown results, or when the repository's own gate requires it; Squeal does not cover typecheck, build or other suites. The registration is capped so that it and the primer stay within 10,000 characters. If interactive (`CLAUDE_CODE_SESSION_ATTENDED=1`, undocumented, guarded), arm the idle waiter.
  - `PostToolBatch`: deliver the delta for this consumer. Primary push channel. PostToolBatch and Stop also ensure the daemon when the recorded heartbeat is older than two intervals, a store read with no socket cost on the hot path. When that finds no daemon validating and starts none (one holds the lock and does not answer, D10, or there is no CLI to spawn), a batch whose tool calls may have changed files (any tool but the harness's known read-only ones, so a custom editing tool counts, or calls the harness does not name) adds one line at that boundary, every time, beside the liveness told once (D6): "Not validated: no daemon has validated since <time>; any change this call made has no result.", worded so a call that changed nothing is not said to have edited (`reviews/wave-11f.md` S1, S2) ("no daemon is running" when none ever heartbeat), so silence never reads as no failures (`lessons.md`, defect 22). A batch whose daemon the hook just spawned adds nothing: that daemon's start scan validates the edit. Verified to reach the model before its next step in the same turn; budget 80 ms p95 (about 50 ms Node start plus a store read).
  - `PreToolUse` on every tool: before the call runs, a registered consumer left idle goes back in a turn, in one small transaction, so a turn another Stop hook continued is a turn again from its first tool call. On `Edit`, `Write` and `NotebookEdit`: when policy `interrupt.onRegression` is on and the consumer's delta contains an undelivered regression, deny once with the regression entries as `permissionDecisionReason`, phrased as facts plus one sentence stating that the edit was not applied and can be re-issued. A regression is a `pass -> fail` of a check this worktree had seen pass, its own result or an inherited one, also when only unknown results (a runner crash between runs) came between the pass and the failure, which every delta reads as `pass -> fail`. A first-seen failure never denies, a baseline finding or a test file the agent just wrote alike; it is delivered at the next tool boundary. A worktree waiting for an install runs nothing, so no pass can be seen there and nothing denies (`lessons.md`, defect 17); a tier whose run overlapped a change of the install stores nothing (D5), so `npm ci` under a running daemon denies nothing either (task 001-107). The hook reads regressions through a peek that marks only those entries delivered, so recoveries and first-seen failures are not consumed by a denial and the same regression never denies twice. Recoveries never deny. Default on; the model reads the reason and continues in the same turn, but treats it as an obstacle rather than advice, so wording is a dogfooding item.
  - `Stop`: speak only with news, because any Stop context starts another model turn: a delta, a first registration that carries known failures, or a policy block. A main agent's Stop that says nothing ends the turn: its consumer becomes idle and records the test files pending at that moment, each at the key it is pending at (plus any with a difference not yet delivered, and, while the runner part of the revision is pending, checks first observed later, up to that revision); one that speaks keeps the turn going. A recorded file stops being waited for once its result at that key lands, told or not, or its key moves on, so an edit made after the turn, by the user or another session, does not wake the agent. On a worktree shared by sessions, the files pending at Stop include those another session's edits queued, so one session can be woken by a result of another's edit. Optionally wait up to `stop.waitMs` (capped at 1,500 ms by the 2 s hook budget) for pending checks of the current revision. `stop.blockOnKnownFailures` blocks only on failures that are current at this revision; failures whose re-run is pending are named as pending, never as existing. `stop.requireFullSuite` reads the checkpoint state. Re-arm the idle waiter if interactive.
  - `SubagentStart` and `SubagentStop`: same as SessionStart and Stop for the consumer `(session id, agent id)`, and SubagentStop unregisters that consumer afterwards, since a finished subagent can receive nothing more. Subagent context is isolated from the parent's in both directions, so each gets its own view. Claude Code's internal forked agents (prompt suggestions, `/btw`) are not consumers: they send SubagentStop, and no SubagentStart, with an empty `agent_type`, so a subagent event with an empty `agent_type` registers nothing, never blocks and delivers nothing. A SubagentStop whose consumer has no registration is treated the same way: a real subagent is registered by SubagentStart or its first PostToolBatch, so one that arrives unregistered ran no tool, and under `claude --agent <name>` a fork reports `<name>` and is caught only by this rule. PostToolBatch and PreToolUse ignore forks too.
  - `UserPromptSubmit`: re-arm the idle waiter, because an interrupted turn runs no Stop; Claude Code 2.1.291 also runs it for a turn the waiter wakes. Record a registered consumer as heard from, put it in a turn, and deliver its undelivered delta as context on the prompt: what the waiter did not wake the agent for, or everything since an interrupted turn. In an interactive session with no registration (a store created after SessionStart, or a consumer expired while idle), ensure the daemon, register, and inject the registration: context on a prompt starts no extra turn.
  - `SessionEnd`: unregister the consumer.
- Harness process: every registration records the process the hook runs under, the nearest ancestor of the hook that is not a shell or launcher (`sh dash bash zsh ksh mksh fish env nohup timeout`, at most four hops), as `(pid, /proc/<pid>/stat start time, PID namespace)` in `meta` beside the consumer, overwritten by each registration, so `claude --resume` moves the session to its new process (`research/harness-process-liveness.md`). Under Claude Code that is the process `CLAUDE_PID` names in every case recorded; the hooks walk rather than read the variable, so no Codex bundle names it (spec 002 D4). Without `/proc` (macOS), or when the walk fails, reaches pid 1, `systemd` or its hop limit, nothing is recorded and the consumer keeps the 12 hour expiry (D10); `ps -o lstart` was not taken, since one-second resolution against a 99,999 PID space buys little. About 30 µs per registration.
- Idle waiter: one `asyncRewake` hook per session, started by SessionStart, UserPromptSubmit and Stop, with a per-consumer lock so only one runs. It blocks on the daemon until the consumer is idle and has a non-empty delta about the test files it recorded when its turn ended, prints only those entries to stderr and exits 2, which wakes an idle agent in about 40 ms; the wake puts the consumer in a turn. Every other difference waits for the next prompt or tool boundary. Each consumer has a turn state, no timer: a session starts idle and waiting for nothing; UserPromptSubmit, a wake or a tool call (PreToolUse before it runs, PostToolBatch after the batch) puts it in a turn, the tool call correcting an idle state that a Stop which was not the last word (another Stop hook blocked) or a failed UserPromptSubmit left, though a result that lands between such a Stop and the continuation's first tool call can still wake the waiter; a registration by UserPromptSubmit, PostToolBatch or Stop is in a turn in its own transaction; only a silent Stop makes it idle, so after an interrupted turn (no Stop) it stays in a turn and nothing wakes it. The state lives in `meta`, one row per worktree, beside the told liveness; a `consumers` column would need a schema step that every older hook and daemon sharing the store reads as "store version newer". A waiter message written mid-turn lands only at the next tool boundary, after PostToolBatch has delivered the same news with a newer header, so the waiter never speaks in a turn (`lessons.md`, defect 14). It is never armed in `-p` mode, where `asyncRewake` blocks the agent. Its `timeout` is explicit and long; expiry is silent, records the consumer as heard from (D10), and the next prompt or Stop re-arms it.
- `skills/squeal/SKILL.md`: described by its trigger, the agent being about to run tests (vitest, npm test) or to check whether a change broke something. Its body is steps first: keep working and read the reports; on a FAIL, `squeal why` from the report's last line; wait with `squeal status --wait` only when a result is needed before the next step, results arriving with the next tool call by default; claim only what status shows; run tests yourself only in the primer's cases. It says a header names the files changed since the last report, not the cause. Counts, commands and policy keys are reference in `skills/squeal/references/`, reached by pointers that name when to read them. Every pointer to `squeal status --wait`, in the skill and the primer, states the next-tool-call default first.
- `bin/squeal` so the CLI is on the Bash tool's path.

Every hook script: dependency-free Node using `node:sqlite` and `node:net`; passes the CLI bundle it ships to the daemon-ensuring helper, so a plugin-only install can start a daemon; reads the store directly for deltas and status; uses the socket only for liveness and nudges with a 100 ms timeout; exits 0 with no output on any internal error; enabled plugins fire in every repository, so in a repository without `squeal.config.json` and without a store the script exits in a few milliseconds. PreToolUse and PostToolBatch, which fire per tool call, run Node only after a POSIX `sh` test, with no `git` or other process, finds Squeal from `$CLAUDE_PROJECT_DIR` or else the hook's working directory: `squeal.config.json` there or at the nearest ancestor with a `.git` entry, or a `squeal` entry in that worktree's common dir (the `.git` directory, or for a `.git` file its `gitdir:` and then that dir's `commondir`). Otherwise the command exits 0 with no output, budget 10 ms p95.

The adapter interface implied by Claude Code, Codex, Pi and OpenCode is three operations: `onToolBoundary(consumer) -> delta | none`, `waitForDelta(consumer) -> delta` where the harness can wake an idle agent, and `status()`. Nothing in the core depends on Claude Code.

### D10. Daemon lifecycle

A hook that finds no live socket spawns `squeal daemon <root>` detached (`detached: true`, `stdio: 'ignore'`, `unref()`), about 70 ms, and returns without waiting. The daemon takes `BEGIN EXCLUSIVE` with `locking_mode=EXCLUSIVE` on `locks/<worktree-hash>.sqlite` before opening the store, so losers never run the integrity check, and holds it for life. Losers exit. The lock is released by the OS on any death, so no pid file exists and pid reuse cannot fool it. A daemon that holds the lock but neither heartbeats nor answers (stopped, hung) has a socket that accepts and never replies: once its heartbeat is past grace (two intervals) it counts as down, and a hook whose ping times out spawns nothing, since a new daemon could not take the lock (`lessons.md`, defect 22). The winner unlinks a stale socket, binds its own, records the path and a heartbeat in the store, then: opens the runner, runs reconciliation, performs the baseline lookup, starts the watcher. While the worktree has no installed dependencies (D5) it opens no runner and performs no baseline until the install, so the first runner call after it imports Vitest from the worktree's own `node_modules`. A daemon that starts clears a waiting flag a killed one left before it decides again (D5). A daemon unlinks its socket on exit only while the path still holds the socket it bound, since a daemon at a root another repository or a fresh clone took over shares the path with the newcomer's.

The daemon itself holds nothing inside its root or inside the temp directory of the hook that started it, so a harness can remove the root under it. It is spawned with `<common-dir>/squeal/` as its working directory, and `squeal daemon`, however started, moves there. Once it holds the lock and has opened the store, it empties `/tmp/squeal-<uid>/tmp/<key>/` and sets `TMPDIR`, `TMP` and `TEMP` to it, the one addition to the environment it inherits (D11); the socket path is derived before that, from the environment hooks share. That temp directory lies outside every repository, as the `os.tmpdir()` of a test under `vitest run` does, so a test that makes a temp directory sees the same thing under the daemon; it is never the inherited `TMPDIR`, which another tool may reap. The key hashes the repository id and the root. The id is a random value the first daemon of a repository writes to `<common-dir>/squeal/repository-id` and every later one keeps, so a repository that takes a path another just left, or one cloned again in place, never shares the temp directory of a daemon still running there: their locks differ, and the key must be no wider than the lock. `/tmp/squeal-<uid>` must be a directory of the user's own with mode 0700, as the socket directory outside `XDG_RUNTIME_DIR` must (D1); when it is not, the daemon uses a fresh `/tmp/squeal-<uid>-<key>-XXXXXX` of its own instead and persists one note saying why. The daemon removes its temp directory when it exits, after the runner closed and before the lock goes; one that died leaves it to the next daemon of the key, which moves it aside under the lock and removes it in the background, so its size never delays the socket. Runner calls run with the root as working directory, because Vitest starts its test workers in the daemon's, configs and tests resolve relative paths against it, and loading the project's config anywhere else can change results (goal 3); the daemon returns to `<common-dir>/squeal/` when none is in flight. A process the project's tools start during a runner call inherits the root and may hold it until the daemon exits: esbuild's service, which Vite 6 and 7 start for every TypeScript transform, lives as long as the daemon. `git worktree remove` still succeeds, the daemon then exits (below) and the service with it; a harness that refuses to remove a directory any live process holds must run `squeal stop` first. A main worktree's store lies inside its root, so all of this holds for linked worktrees only.

The daemon exits when its root is deleted, when `<common-dir>/worktrees/<name>` disappears, when the store schema is newer than it understands, 3 s after its last session is gone, when a hook newer than it asks it to step down, after a configurable idle period (`daemon.idleExitMinutes`, default 60 minutes) when it never had a registered consumer (started by `squeal start`), or with code 0 and reason `reinstalled` when its install goes while it runs (D5, task 001-113): it persists the reinstall note, shuts down in the order below and clears its record, so the next hook finds no daemon and spawns a fresh one, which waits for the install or, once it is there, runs the baseline with a new runner instance. "Its last session is gone" (`lessons.md`, defect 24, the human's rule): a daemon that had a consumer of its worktree exits, with reason `sessions-gone` and one note, once none was registered for 3 s, counted every 250 ms and from the latest departure every unregister stamps in `meta`, so a session that registers and ends between two counts counts too; the 3 s absorb `/clear` and `/resume`, and a registration within them keeps the daemon. "A hook newer than it" (`lessons.md`, defect 26): every hook that reads a fresh heartbeat (SessionStart, a registering UserPromptSubmit, and PostToolBatch and Stop from the store read they already make) compares its own bundled version with the recorded `worktrees.daemon_version`. It sends `step-down` with its version over the socket only when both are plain `major.minor.patch`, the daemon's is strictly older, and every consumer of the worktree registered from another session recorded a version at least the hook's own. Each registration records the registering hook's Squeal version beside the consumer in `meta`, as it records the harness process; a consumer registered without one, by any hook from before task 001-130, counts as older, and the asking session's own consumers are left out, since they run the asking plugin. So while a session of an older plugin is registered nothing is asked and the daemon serves on; once those sessions leave, the next newer hook asks. An older hook therefore never takes the boundary after a step-down and starts a daemon older than the one that left (review wave 12b, B1). The daemon, checking the same order, exits with reason `superseded` and one note naming both versions. An equal or newer daemon answers and keeps running, so a downgrade replaces nothing. A daemon from before the request answers "unknown request type", and the hook sends `stop` instead. At most two round trips of the 100 ms budget, only for an older daemon; its heartbeat stops with its timers, so hooks stop asking within two intervals. The hook whose request the daemon accepted owns the handover: it spawns its own CLI's daemon at once as `squeal daemon <root> --await-lock 120000`, which retries the lock every 10 ms for up to 2 minutes instead of losing it at once, then starts as any daemon does, so a current daemon serves without another boundary. While it waits it exits as a loser when the store records a daemon other than the one it first saw, or one at least as new as itself, never the older one it replaces (another spawn won the lock), or when the root is gone; when the wait ends with the lock still held it persists one note and exits with code 0 and reason `lock-wait-timed-out`, and the next boundary spawns once the lock is free. Hooks that ask again while the old daemon stops each spawn a successor, and all but the lock's winner exit. Accepted limit (`reviews/wave-12c.md` B1, human, 2026-10-08): a hook from a release before 0.1.34 starts its own daemon without any version check, so if it takes the freed lock before the successor does (the successor descheduled at that moment), its older daemon serves. It does so only while that older plugin's session is registered, which is the case in which no step-down is asked anyway; once those sessions leave, the daemon exits within 3 s and the next newer hook starts a current one. SQLite has no blocking lock, so a daemon spawned in the moment between the old daemon's release and the successor's next retry could still win; the successor already retries while the old daemon shuts down, and another hook spawns only after it reads no record and finds no socket, both cleared just before the lock goes. Until it exits the old daemon holds the lock: hooks find it alive (stopping) and spawn nothing, and a daemon spawned without the wait loses the lock and exits. A tier in flight finishes and stores its results, then the daemon exits; the queue behind it is left to the next daemon. A session that starts while that tier finishes finds a daemon stopping and is served by the successor. On each heartbeat the daemon drops every consumer of its worktree whose recorded harness process is gone: its stat file missing, its start time different (the PID was reused) or its state `Z`; a process in another PID namespace is not judged. A dead process ends every session it hosted, a live one proves nothing about a given session, so SessionEnd and the expiries below stay. A consumer that has not been delivered to or heard from for 12 hours is expired, the backstop for a consumer with no recorded process (an older hook, macOS). An interactive main agent's liveness is its idle waiter: Claude Code runs no `SessionEnd` on an interactive exit after a typed prompt, but it kills the waiter, whose lock the OS releases while the lock file stays. A consumer whose waiter lock file exists and is held by no waiter, and that has not been delivered to or heard from for 10 minutes, is expired and its lock file removed. A waiter that ends on its own timeout records its consumer as heard from, so the 10 minutes start then. Status reports "no daemon running since <time>" when the heartbeat is older than its interval, or with the last heartbeat once a daemon stopped and cleared its record.

### D11. Policy

`squeal.config.json` at the repository root, committed, all keys optional. One loader serves daemon and hooks and never throws: unknown keys and wrong types are reported as problems, the defaults apply for those keys, the daemon persists one note and keeps running, and a revision that changes the file reloads it and re-keys what `inputs` and `env.allowlist` touch. Keys:

- `interrupt.onRegression` (default `true`), `stop.blockOnKnownFailures` (`false`), `stop.requireFullSuite` (`false`), `stop.waitMs` (`0`).
- `baseline.onStart`: `"lookup-then-run-missing"` (default) or `"lookup-only"`.
- `inputs`: extra closure globs for fixtures read at runtime that observation cannot see (D4), either a list applied to every test file or a map from test-file glob to input globs so one runtime read does not re-key the whole suite.
- `observe.runtimeInputs` (`true`): the runner records the project paths each test file reads, spawns or loads at run time and they join its closure (D3, D4; task 001-132). `false` keys by static imports and declared `inputs` alone, the keys of before. A revision that changes it re-assembles every closure, reads the environments again and recreates the Vitest instance, whose workers' env is set when it is created.
- `env.allowlist`: environment variables included in the environment hash.
- `runner.tierSize` (`4`), `runner.backlogTierSize` (`200`, the most files a backlog tier takes under D5 step 5's time bound), `runner.timeoutMs` per run (`600000`, because a synchronous loop in a test worker cannot be stopped by the runner's own test timeout). Runs go one at a time; no key sets how many run at once.
- `daemon.idleExitMinutes` (`60`), `store.retentionDays` (`7`), `store.maxSizeMb`.

Squeal loads Vitest from the project under validation, resolved from the worktree root and imported lazily by the runner adapter, never from its own installation; a project without Vitest is a runner failure state, not a crash. Squeal runs only the project's own Vitest configuration inside the worktree. It never runs arbitrary commands, never writes to the worktree beyond what Vitest itself writes (`update: 'none'` prevents snapshot writes), and inherits the environment of the hook that started it, with only the additions D10 makes (`TMPDIR`, `TMP` and `TEMP` point at its own temp directory) and, while observing, the recorder's `NODE_OPTIONS` and `SQUEAL_OBSERVE` in the test processes (D4).

### D12. Error handling

- Runner crash, or an unhandled error Vitest cannot attribute to a test file: the run is untrusted, every check in the tier becomes `unknown` at this revision, one transition is recorded, one factual line is delivered. Run timeout: files whose module ended before the cancel keep their results; the rest of the tier becomes `unknown`.
- Config change: instance recreated; all checks of the project re-keyed through the environment hash.
- Watcher backend error or dropped-events signal: full reconciliation pass; a note in status.
- Store unreadable or corrupt: `integrity_check` on daemon start; on failure the file is moved aside, a fresh store is created, status says the baseline was lost.
- Dead daemon: hooks still serve status and deltas from the store; status says the daemon is down and since when.
- Hook internal error: exit 0, no output. The daemon has no log file in v1; persisted notes in the store are the record, and a daemon that dies during start writes a note before any step that can throw after the store opens.
- Several Squeal versions on one store: newer schema wins; older daemons exit (D8).

## Testing

- **Core, pure functions, Vitest**: blob hashing including the attribute rule, environment and check key derivation, closure assembly, revision batching and reconciliation, validity classification, transition rules, consumer view diffing including the break-and-recover case, message formatting and the 10,000-character cap, status derivation.
- **Runner adapter, fixture projects**: affected-set computation including setup-file and snapshot additions, invalidation cases (import change, test file add and delete, config change), result extraction including file-level errors, the post-tier stability check.
- **Store**: concurrent writers and readers, kill-during-write, migration from an older `user_version`, pruning.
- **Hook scripts**: recorded hook JSON in, JSON out, for every event; a latency test asserting the p95 budget; behaviour with no store, with a newer schema, and with a dead daemon.
- **End to end, fixture repository with two worktrees**: edit a source file and assert exactly one `PASS -> FAIL` delivery, then exactly one `FAIL -> PASS`; break and recover between deliveries and assert silence; create a second worktree and assert its baseline is a lookup with zero runs and inherited provenance; modify one file in the second worktree and assert only its affected checks run.
- **Manual**: dogfood on this repository with Claude Code interactive and `-p`, recording delivery latency, duplicate rate, and how the model reacts to a PreToolUse denial.

## Open questions

Owner is the coordinator unless noted.

1. Inherited passes: current at once, or `stale` until confirmed in the background as Wallaby does? Trades latency against stale-result escape rate. Decide after first dogfooding data. Dogfooding (`lessons.md`): a second worktree of this repository inherited 760 of 760 results with 0 runs, baseline 1.1 s instead of 138 s. The only stale-result escape seen was an own result under a closure that cannot see a runtime file read; inheritance would copy such an escape but does not cause it. Proposed: keep inherited results current, and spend the effort on closure completeness (per-test-file `inputs`).
2. Decided 2026-10-06: the environment hash uses the full Node version. A patch release re-keys every file once; a missed native behaviour change would be worse.
3. PreToolUse denial wording and whether default-on survives dogfooding. Dogfooding (`lessons.md`): 4 denials in 2 of 18 editing sessions; the model re-issued the denied edit every time, never stalled or looped, and read the failure from the denial text, once reading the failing test in the same step as the re-issue and then fixing it. Cost: one extra tool call per denial. 2 of the 4 were transient mid-refactor failures. Claude Code prefixes the reason with "PreToolUse:Edit hook error:" without misleading the model. Proposed: keep default on and the current wording.
4. Decided 2026-10-06: accepted as a known risk. The wrapper in `src/runners/vitest/related.ts` is the only call site, the peer range pins Vitest to the majors the wrapper was tested with, and a Vitest upgrade re-runs the adapter tests before the range widens.
5. Decided 2026-10-06: the 30 s reconciliation pass stays and covers events lost across sleep; the first pass after wake re-stats every tracked file. Not measured on macOS.
6. Long tool calls delay delivery until they end (19 s observed). Whether to ship a plugin `monitor` is deferred to the dogfooding report. Dogfooding (`lessons.md`): during a 15 s Bash call the idle waiter took the delta 246 ms after the result and Claude Code queued it as a task notification until the call returned, 8.5 s later; a monitor's output would wait at the same boundary (inferred, not tested). The longest tool calls agents made were their own waits for pending checks (`sleep 20; squeal status`). Proposed: no monitor in v1; consider a blocking `squeal status --wait`.
7. macOS: fd usage of chokidar, parcel rename behaviour, socket limit, lock release, and whether the prebuilt @parcel/watcher binary loads with install scripts disabled. Needs a macOS run before any release.
8. Decided 2026-10-06: accepted. The cache is gitignored by convention, invisible to the watcher, and shared with the project's own Vitest runs, which keeps warm starts warm.
9. Recovery from `unknown` is silent and the fingerprint includes line and column, so a line inserted above a failing assertion reads as a changed failure. Both are spec-conformant; measure how agents react during dogfooding. Dogfooding (`lessons.md`): after a broken Vitest config was fixed, 18 recoveries from `unknown` were silent, the header's counts carried them, and the agent pulled status anyway; one `UNKNOWN -> FAIL` was delivered. A line shift was delivered as a changed failure and the agent called it a line shift and did nothing. The noisy case was a random temp path in the first error line, a changed failure on every re-run. Proposed: keep both behaviours; normalize UUIDs and temp paths in the fingerprint.
