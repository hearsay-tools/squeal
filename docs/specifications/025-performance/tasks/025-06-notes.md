# Row 025-06 notes: D6, SQLite hot-read optimizations

## Changes

1. **Code store complexity counts (D6.1).** `CODE_INDEXES` gains `states_non_pass`
   (`states (worktree_id, measure, outcome) WHERE outcome != 'pass'`). `CodeStateRepo.countNonPass(worktreeId, measure)`
   returns `{ fail, pending, unknown }` (new type `CodeNonPassCounts` in `src/core/code/store/types.ts`, additive).
   It names `INDEXED BY states_non_pass` only when the repo's open found the index in `sqlite_master`
   (the same `indexesIn` check as `states_failing`), else the same query without `INDEXED BY`.
   `codeStatusOf` uses it for `over` and `unknown` and no longer reads the passing states.
2. **`relevantStates` (D6.2).** `STORE_INDEXES` gains `known_states_non_pass`
   (`known_states (worktree_id, check_id) WHERE outcome != 'pass'`). The read is now a `UNION` of three
   check-id lookups (non-pass states, the consumer's view, births after the mark), then `CROSS JOIN known_states`
   by key and `JOIN checks`, in the same `ORDER BY`. It checks `sqlite_master` for the index on every call
   (one small read), because a test or another opener can drop or add it between calls; the code store
   repo checks once per open, as before.
3. **`resumeTurn` (D6.3).** Returns before `store.transaction()` when `store.consumers.get(consumer) === null`.
   The check inside the transaction stays, for a consumer removed between the read and the lock.
4. **`checksByFile` (D6.4).** Pushes into the per-file array instead of copying it per state.

No `SCHEMA_VERSION`, `CODE_SCHEMA_VERSION`, `KEY_FORMAT_VERSION` or `RECORDER_VERSION` change.

## Plans (`EXPLAIN QUERY PLAN`, read in the new tests)

- `countNonPass`, indexed: `SEARCH states USING INDEX states_non_pass (worktree_id=? AND measure=?)`.
  Without the index the plan does not name it (`test/code/states-index.test.ts`).
- `relevantStates`, indexed: `SEARCH known_states USING INDEX known_states_non_pass (worktree_id=?)`,
  `SEARCH consumer_views USING COVERING INDEX sqlite_autoindex_consumer_views_1 (worktree_id=? AND session_id=? AND agent_id=?)`,
  `SEARCH state_born USING COVERING INDEX sqlite_autoindex_state_born_1 (worktree_id=?)`,
  then `SEARCH s USING INDEX sqlite_autoindex_known_states_1 (worktree_id=? AND check_id=?)` and
  `SEARCH c USING INTEGER PRIMARY KEY`, with a temp B-tree for the `ORDER BY`.
  Without the index the first lookup is `SEARCH known_states USING INDEX sqlite_autoindex_known_states_1 (worktree_id=?)`:
  still a search of the worktree's states, no table scan.
