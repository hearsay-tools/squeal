# Row 025-10 notes: write slicing guided by the 025-09 write-wait data (D10)

Worker `c9b9d0b1`, 2026-11-24. Base: `main` at `957897ae3` (after `0.1.628`).

## What changed

1. **Zero-row prune slices** (`f5576e8b7`; `src/core/daemon/sliced-prune.ts`, `src/core/store/prune.ts`, `prune-keyed.ts`, `prune-checkpoint.ts`, `prune-vacuum.ts`).
   - `PruneSlice` is `() => unknown`. A slice that returns exactly `false` took no write lock or wrote nothing. Any other value, `undefined` included, counts as a write. Type change: `() => void` became `() => unknown`. Every old slice still type-checks, and the code store's slices (`src/core/code/store/*`, not owned here) keep their pause.
   - `SlicedPrune` follows a `false` slice with one `setImmediate` turn, not the `turnGapMs` pause. The socket and the heartbeat still run between slices. The busy retry moved to `#slice` (complexity of `run`: 21 → 17).
   - `false` slices: `deleteByKey`'s key reads, and its deletes whose recheck kept every row; `removeWorktree` slices for a worktree that is not gone or a batch that removed 0; `dropRuns`, `dropPrunable` and `evictToCap` batches that removed 0; `checkpointAfterWrites` slices that did not move `total_changes()` or the page count. The WAL checkpoint slice keeps its pause, as row 022-08r intends.
   - The two expiry steps (`expireReplaced`, `dropFallenUnknownRuns`) now read first, outside the write lock (`writeIf`). They take the write lock only when a replaced failure is past the cutoff, or when any unknown-run record exists. The write decides again under the lock. A prune of a store with nothing to prune now takes **no** write transaction (before: 2 per prune).
   - Prune safety rules are unchanged: `isGone` recheck under the lock, `hasIndexes`, `BUSY_SLICE_MS` retry, the corruption `fault` handler.

2. **The start's lookup commit in slices** (`d985114e7`; `src/core/scheduler/ledger.ts`, `bootstrap.ts`).
   - `Ledger.commitInSlices(options, run?, slice = WRITE_SLICE_FILES)`: a commit that records a refined revision is split by `sliceDrained` into write transactions. Each slice except the last holds at most 200 dirty files: their key rows and their applied results, in order. The last slice holds the rest (removals, re-key marks, unknown marks, unknown-file entries, retired checks, setups, runners, runtime applications, `recordRefinedApplied`) in `commit`'s order. One `setImmediate` turn separates two slices. `run` is the caller's busy retry per slice.
   - A file goes ahead only when no removal, unknown mark, unknown-file entry or retired check of the commit names it. Its re-key mark (a lookup hit at the file's key always discharges one) stays in the last slice. Those marks write only the edit records in `meta` (`recordRekeyed`, `recordMoves`), which no sink call reads. A move left open until the last slice only keeps an edit's wait waiting.
   - The baseline's `commitFirst` (lookup-only, before the recheck) and `commitLast` (under `retryWhileBusy`, per slice) use it. Each `commit` without a refined revision, and each other commit, is still one transaction.
   - Type changes: `Drained` is exported, and `sliceDrained` is new; both are for tests. `commitFirst` is now async.

3. **Scoped sink reads** (`5d200d17e`; `src/core/state/sink.ts`, by agreement with coordinator `0266d2c5` on 2026-11-24).
   - Before this change, every sink call began with `begin(worktreeId)`, which listed **every** known state and **every** key row of the worktree inside the write transaction. On a worktree of 1,000 files × 10 checks, one `knownStates.list` took 26 ms and a 30-file file-scoped list took 1.2 ms. A tier commit makes 2 to 3 such calls. This was the cost behind `#write < #record` (28–122 rows written, 250–369 ms held, `stress@0.1.626`).
   - Now `applyResults` reads the rows of its results' files, and `markUnknown` and `refresh(testFiles)` read the rows of the files they name. Each scope is deduplicated and padded to a power of two with its last file, so the connection's unbounded statement cache holds at most about a dozen shapes per read. Past `SCOPED_MAX_FILES = 1024` files, as for `setupOutcome` (it runs only at a setup's failure or its first pass after one) and a whole `refresh`, the call reads the worktree's rows as before.
   - Exactness: every check a call asks about belongs to a file it names. A refresh reads the results under each named file's key, and those results are that file's checks, because a key hashes its file's project and path (`keyFromSegments`) and a run's results are stored per file. `test/state/sink-scoped.test.ts` runs the same 14 calls on two stores, one whose reads ignore the file list (the sink before this row), and requires equal states, transitions and returns for both worktrees.

4. **Validity case** (`c73f811af`; `test/keys/validity/case.ts`, `harness/prune.ts`, `cases/prune/slices.ts`). `prune.ts` and `sink.ts` are in the key-format validity bundle. The read-first expiry steps run their write callbacks only when an expiry is due, so no case ran those lines. The `prune` kind takes `meta` rows now and reports them after the prune. A new case has an expired replaced failure beside a kept one, and a fallen unknown-run record. `test/keys/key-format.test.ts` passes, 12 of 12, with no version raised. The validity rules also decided item 3: a new `setupOutcome` line had no case, so it keeps its whole-worktree read. An out-of-scope fallback in `prior` could never be reached (see the key invariant above), so it was removed instead of given a contrived case.

## Invariants kept

- **Revision coherence (D5 review B2): `reconcileBatch` stays one transaction.** The coordinator agreed on 2026-11-24. The new revision row, the changed paths' `file_hashes`, the content re-key, the `queued` phases and the refreshed known states commit together. Readers never see a new revision whose classification lags. A split would have to write either the revision first (a reader sees revision N+1 with files still `current` at their old keys: a false pass) or the classification first (key rows at a revision the store does not hold; after a crash, a hash the next pass treats as already seen, so the change is lost). The only part outside the revision transaction is still D5's flush of unchanged-file stat updates. What this row cuts there is the read cost: the commit's `sink.refresh` of up to 1,024 re-keyed files now reads only their rows (item 3), not the whole worktree's.
- **Start-commit coherence: no half-written baseline reads as settled.** Each slice ahead moves the refined revision to `refined - 1` when the stored one covers `refined`, inside its own transaction, after `recordMoves`. `header.ts` (`runnerPartPending`), `isRefined` readers (`reader.ts`, `look-again.ts`) and every wait treat the revision's runner part as pending until the last slice. That slice records `refined` in the same transaction as the rest of the commit. The end state is the same as one transaction's.
- **Crash between slices:** the refined revision stays one below. The next start's `scan` reads that revision's changes as unseen. That is conservative: it never treats them as applied. Under `lookup-only` only a start that resumes a rest queues them. The key rows written ahead are rewritten by that start's baseline.
- **Busy refusal (row 011-126):** a slice refused by a busy store wrote nothing. When `run` gives up (the scheduler closed), every part from the refused one on is put back, in order, so the next commit writes each once.
- **Interleaving:** the baseline runs inside the scheduler lock (`#start`, `#catchUp`), and it already awaited runner calls between its two commits. So the turns between slices let in only work that never takes that lock: hook writes from the front desk, and other daemons.
- **`startTier` / `recordTier`:** no in-memory mutation moved out of a transaction. `endTier`, the queue, `warmUp`, `yields` and the withholds must change only after `BEGIN IMMEDIATE` succeeded, so a busy refusal changes nothing (row 011-126). The claim checks and `#heldNow` are read at lock time as before. Their lock time fell because of item 3. Measured on this host at a load average of about 11, with the same fixture (1,000 files × 10 checks), one 30-file tier commit went from 33–36 ms to 3.1–3.5 ms.
