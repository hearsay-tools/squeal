# 025-11 notes: status counts known states by SQL (D11)

## What changed

`squeal status` (`buildSnapshot`, `buildSnapshotWithReads`), a named wait's end read and `readVerdict` without `reads` no longer call `store.knownStates.list(worktreeId)`. They read `WorktreeStates`, a count of the worktree's known states:

- `groups`: states counted by check kind, validity, outcome and, when current, origin. The header's validity counts, `inheritedCount`, `importedCount`, the breakdown's outcome counts and `inherited.sources` fold these.
- `files`: per test file (`testFileId`), two tallies (`all`, which includes a global setup's state at the file's path, as `checksByFile` grouped it; `checks`, without setup states). Each tally has a count, counts by validity and outcome, and whether a state runs. Each file also has the oldest and newest `observedAt` of its current states, and its pending states by check kind and stored phase. Every per-file class (`classOf`), lane class, slow pending count, phase and `testFilesWithoutChecks` count reads these.
- `notable`: the states that fail, the unknown states and every global setup's state, in `knownStates.list` order. Only these are read one by one: a failure (`withRecorded`, verdict failures), an unknown check's reason, and a project's setup (`setupsOf`, `unknownReasons`). On a passing worktree it holds only the setups, also when every state is pending after an edit.

Seams:

- `src/core/store/status-reads.ts` (new, outside the key-format bundle, as `view-seed.ts` is): `readWorktreeStates` (one read transaction: `stateCounts` plus `notableStates`), `stateCounts` (one `GROUP BY` on the stored columns, folded in JS), `notableStates`, `importCountsByFile` (read only while the store holds an import), `importCountsOf` (the same counts from a list), and `originOf` (a copy of `repos/states.ts`'s `toOrigin`, which stays in the bundle).
- `src/core/state/file-class.ts`: the `WorktreeStates`, `FileStates`, `StatesTally`, `StatesGroup` and `PhaseCounts` types, `worktreeStatesOf(states)` (the same counts from a list), `classOf(row, tally)` (`fileClassOf`'s rule over a tally), `phasesOf`, `notCurrentOf`.
- Every rule now has one body, written over `WorktreeStates`. The functions that took `KnownState[]` keep their signatures and call `worktreeStatesOf` first: `readHeader`, `headerPart`, `countNotCurrent`, `fileClassOf`, `classifySlowFiles`, `classifyGroupFiles`, `readSlowTier`, `readGroupTiers`, `readImports`, `unknownReasons(...).of`. Callers outside this row (`delivery`, `harness/shared/stop*`, `cli/checks.ts`, `cli/retry*.ts`, `state/required.ts` and others) are unchanged.
- New entry points over `WorktreeStates`: `readHeaderOf`, `headerPartOf`, `classifySlowFilesOf`, `classifyGroupFilesOf`, `readImportsOf`, `UnknownReasons.ofCounted`.
- `WorktreeReads.states` is now `WorktreeStates`. `standingsOf` and `readVerdict` without `reads` call `readWorktreeStates`. `outstanding.ts` and `cli/wait/named.ts` needed no change: they pass `reads` through. A named wait's polls already read by file (`readClasses`). Its end read now lists no whole worktree.

## Type changes

- `WorktreeReads.states`: `readonly KnownState[]` changed to `WorktreeStates`. Only this row's files build or read it.
- Changed signatures (callers are only inside this row): `laneCounts`, `readLane`, `groupLaneCounts` take `WorktreeStates`. `laneCounts`' `classify` is a `LaneClassifier`. `pendingPhasesOf` and `unknownTestFilesOf` take `WorktreeStates`.
- Removed: `laneChecks` in `slow.ts` (no caller left).
- Additive: everything else listed above.

## Decisions the spec did not settle

- **`inherited.sources` counts a global setup's inherited state.** The brief said to leave setup checks out. The old code counted them in `inherited`, but not in the header's `inheritedCount`. Byte equality wins, so the new code counts them as before. A product change to leave them out is a one-line change in `inheritedSources` (`snapshot.ts`).
- **One scan, no index.** The counts read every state of the worktree, so no index helps them. `known_states_non_pass` is not used: `notableStates` also needs unknown states that pass and every setup, which that index does not hold. Nothing creates an index, so an older store or a read-only open reads alike.
- **Group by stored columns, not expressions.** A first version used two queries with about 25 `SUM(CASE ...)` columns. It took 53 ms on 20,000 states, which is more than `knownStates.list` (48 ms). One `GROUP BY` on the 9 stored columns, with the per-file tallies folded in JS, takes about 23 ms in SQL and 26 to 28 ms in total.
- **A wrapped store.** `connectionOf` does not know a `Proxy` of a store (the e2e probe, `torn-read.test.ts`). Then `readWorktreeStates` and `importCountsByFile` count from `knownStates.list`. The counts and the read transaction are the same. The `try`/`catch` follows `store/covered-files.ts`.
- **`readHeader`'s default** still lists every state when a caller passes none (`harness/shared/stop.ts`, `cli/retry-unlisted.ts`). That is outside status, and `test/presence/reads.test.ts` pins the order of the header's reads.

## Timing probe (not the benchmark)

`buildSnapshot` on a worktree of 2,000 listed files with 10 current, passing checks each (20,000 states). Each run makes 12 calls in one process; the median and minimum of calls 3 to 12 are shown. The old tree is the `git archive` export of `957897ae3`, the new one this row's final code. Runs alternate old and new. Node v26.13.0, 16 CPUs (`nproc`), host load average 7 to 10 from other work.

| run | old median (min) | new median (min) | old first call | new first call |
| --- | --- | --- | --- | --- |
| 1 | 88 ms (79) | 47 ms (39) | 149 ms | 73 ms |
| 2 | 87 ms (75) | 44 ms (41) | 143 ms | 73 ms |
| 3 | 85 ms (81) | 41 ms (39) | 153 ms | 72 ms |

On this worktree, `stateCounts` takes 26 to 28 ms, `notableStates` 3 ms, `testFileKeys.list` 2 ms and `knownStates.list` 45 to 54 ms (medians of 10 calls). The time still grows with the number of states: SQLite sorts every state for the `GROUP BY`. A flat cost needs counts kept at write time, which would change the schema. That is outside this row.
