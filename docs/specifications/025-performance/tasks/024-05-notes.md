# Row 024-05 notes: SQLite write lock holds and connection tuning (D5)

## What changed

1. `src/core/store/open.ts`
   - Every connection gets `CONNECTION_PRAGMAS`: `cache_size = -16384` (16 MiB) and `temp_store = MEMORY`.
   - An open with `create: false` that finds `user_version === SCHEMA_VERSION` skips `PRAGMA page_count`, skips `switchToWal` when `PRAGMA journal_mode` already reads `wal`, and skips `migrate`. A file that is not in WAL is still switched.
   - New option `managedCheckpoint?: boolean`: `true` sets `wal_autocheckpoint = 0` on that connection only.
   - `inspectConnection` also returns `cacheSize`, `tempStore` and `walAutocheckpoint` (additive).
   - `SCHEMA_VERSION` is unchanged and `results_by_failure` is untouched.
2. `src/core/daemon/idle-checkpoint.ts`
   - `passiveCheckpoint(db, walPath, minBytes = PASSIVE_CHECKPOINT_BYTES)`: runs `PRAGMA wal_checkpoint(PASSIVE)` only outside a transaction and only when the `-wal` file exists and holds at least `minBytes`.
   - `checkpointPassively(db, walPath, everyMs = PASSIVE_CHECKPOINT_MS)`: an unreferenced 15 s interval. It stops by itself once `db.isOpen` is false and also returns a stop function.
   - `IdleCheckpoint` and `truncateWal` (the quiet `TRUNCATE`) are unchanged.
3. `src/core/daemon/open.ts`: `openStoreFile` passes `managedCheckpoint: true`. After the store file is verified, `openDaemon` starts `checkpointPassively` on the daemon's connection. The daemon's lifecycle code (`lifecycle.ts`, row 024-04) is not changed.
4. `src/core/store-process/writer.ts`: the writer connection gets `CONNECTION_PRAGMAS` and `wal_autocheckpoint = 0`. `CheckpointingWriter` extends `GuardedWriter`. After each `write`, outside its transaction, at most once every `WRITER_CHECKPOINT_MS` (1 s), it runs `passiveCheckpoint` on `code.sqlite`. `writer-thread.ts` needed no change, because `openWriteConnection` returns the subclass.
5. `src/core/store/repos/results.ts`: `RESULT_TOUCH_INTERVAL_MS = 3_600_000`. `byKey(key, usedAt)` with `usedAt > 0` runs `UPDATE results SET last_used_at = ? WHERE key = ? AND last_used_at < ?` with `(usedAt, key, max(0, usedAt - RESULT_TOUCH_INTERVAL_MS))`. `usedAt === 0` stays read-only.
6. `src/core/scheduler/batch.ts`: `WRITE_SLICE_FILES = 200` and `flushStatsAhead`. When a batch has more than 200 stat-cache updates for paths that no change in the diff names (the stat moved, the bytes did not), `reconcileBatch` writes those first, in 200-path transactions, with one `setImmediate` turn between two transactions. The revision transaction then carries only the changed paths' updates. A batch with 200 or fewer such updates is written as before, in one transaction and with no added await.

## Decisions the spec did not settle

- **Passive checkpoint threshold: 4 MiB, not 8 MiB.** The daemon and the store-process writer no longer checkpoint at commit. The connections that still do (hooks, CLI) reach SQLite's default auto-checkpoint at 1,000 frames, which is about 4 MiB at 4 KiB pages. With an 8 MiB threshold, those hook commits would run most checkpoints, inside the hook budget. At 4 MiB, the daemon's 15 s pass usually runs first.
- **WAL size is measured as file size.** `journal_size_limit` keeps the file at its largest size, up to 64 MiB, after the WAL restarts. So after the file first grows past 4 MiB, every 15 s pass runs a PASSIVE checkpoint. When no new frames exist, that checkpoint copies nothing and calls no fsync, so the cost is negligible.
- **No slicing in `startTier`, `TierRecords.#write` or `recordTier`.** The coordinator approved option A on 2026-11-22. The reasons:
  - `startTier` is synchronous, and its callers are outside this row: `tier-start.ts:118` and `slow-tier.ts:720`.
  - The heavy rows of a tier record are the ledger's buffered commit (`ledger.ts`) and `recordFile`/`putMany` (`record-tier.ts`), not this row's files.
  - A record committed in parts breaks the busy-retry contract. `#written`/`#prepared` rerun a whole record after a busy store gives up.
  - Slot records share one ledger commit.
  - At the default `backlogTierSize` of 200, a threshold of more than 200 files never triggers for a tier.
  - `record.ts` and `tiers.ts` are unchanged.
- **The results touch keeps the brief's single `UPDATE`.** A no-row `UPDATE` still takes the write lock for a moment. `test/store/repos.test.ts` ("a hit still writes") depends on that. A read-first gate (`SELECT` the row and update only when it is stale) would also remove that lock. That change is a candidate for a later row.

| `Ledger.commit` | 3 | |
| Heartbeats (`beat`) | 3 | |

Follow-up candidates:

1. **Prune slices.** They are most of the count. They hold the write lock while they scan, and they write nothing. Candidates: scan outside the write transaction and delete by rowid, or bound each slice by time. No wave-1 row owns `prune.ts` or `sliced-prune.ts`.
2. **Tier records.** Slice inside `ledger.ts` and `record-tier.ts`, with per-slice progress kept across busy retries, and with a slice size below `backlogTierSize`. Measure the size on the bench.
3. **`startTier`.** Make it async in `tier-start.ts` and `slow-tier.ts` before it can yield between slices.

The 16 MiB page cache and the end of commit-time checkpoints should already shorten the "0 rows" and "32 rows" holds. The wave's paired benchmark will show whether they do.
