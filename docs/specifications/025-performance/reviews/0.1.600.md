## Blockers

### B1. Proven: the recorder can attribute an old symlink target to a later test file

**Location:** `src/runners/observe/recorder.cjs:68`, `:111`, `:209`. Row 024-04, D4.4.

**Contract:** “Recorded outputs must be byte-for-byte identical”; “zero key-format change.” The vision requires facts tied to the code actually observed.

The cache lives for the whole worker process. It does not expire when the current test file changes or a symlink is replaced. The existing per-test-file `seen` set does not make this safe: a new test file gets a new `seen` set but reuses the previous file's realpath answer.

**Reproduction:** create `a.txt` containing A, `b.txt` containing B, and `link -> a.txt`. Run the following body under the recorder, with `SQUEAL_OBSERVE` naming the temporary root and output directory, and no fixed `file` setting:

```js
const fs = require('node:fs');
const path = require('node:path');
globalThis.__vitest_worker__ = { filepath: path.resolve('first.test.js') };
const first = fs.readFileSync('link', 'utf8');
globalThis.__vitest_worker__ = undefined;
fs.unlinkSync('link');
fs.symlinkSync('b.txt', 'link');
globalThis.__vitest_worker__ = { filepath: path.resolve('second.test.js') };
const second = fs.readFileSync('link', 'utf8');
console.log(first + ' ' + second);
```

The unset attribution simulates a change between files. Inspect `f` in the output rows for `second.test.js`. The probe extracted `recorder.cjs`, `fs.cjs`, `spawn.cjs` and `preloads.cjs` from each exact commit into separate temporary directories and used `NODE_OPTIONS=--require <recorder>`.

Actual output:

```text
base:      actualReads="A B", secondFileObserved=["b.txt","link"]
candidate: actualReads="A B", secondFileObserved=["a.txt","link"]
```

The candidate reports A as an input although the second test read B. The stable-symlink test and key-format hash test do not exercise this case. The row notes acknowledge stale targets but do not make the changed recorder output conform to D4.

**Repair:** one observer repair row. Reuse a resolved path within one observation/load, or invalidate it before a later observation can see a changed symlink. Do not retain an unchecked target across test-file boundaries or filesystem mutations. Preserve the saving across `f`/`m`/`d` of one load. Add a recorder integration test for the sequence above. Keep both version constants unchanged only once output equivalence holds.

### B2. Proven: the old-schema status branch writes and masks busy migration errors

**Location:** `src/core/status/open.ts:154` through `:163`. Row 024-02, D2.4.

**Contracts:** “without running write pragmas, migrations, or WAL checkpoints on close”; “Preserves every failure classification,” including timeout/busy retry. Wave 1 requirement 5 says `withStatusStore` must never write.

For an older schema, `openReadOnly` closes its read-only handle and calls `openStore`, which can migrate and checkpoint. The new `test/status/open-readonly.test.ts:73` explicitly expects this write. The exception is not in D2 or the amendment log.

There is also a new error-path defect. If that fallback throws, the catch closes the same read-only handle again. Node throws `ERR_INVALID_STATE: database is not open`, replacing the original failure. A busy store is then reported as unreadable, without its requested retry.

**Reproduction on the clean build:** create a temporary git layout with `.git/HEAD`, and a database at `storePaths(commonDir).database`. On a raw `DatabaseSync` connection, run:

```sql
PRAGMA journal_mode=WAL;
CREATE TABLE old_store (x);
BEGIN IMMEDIATE;
```

Leave `user_version` at 0. While that connection holds the lock, call:

```js
withStatusStore(root, { busyTimeoutMs: 20, busyRetryMs: 80 }, () => 'read');
```

Control: `openStore(commonDir, { create: false, busyTimeoutMs: 20 })` throws `database is locked`.

Actual status output:

```json
{"schemaVersion":1,"available":false,"reason":"store-unreadable","message":"status unavailable, store unreadable: Error: database is not open","elapsedMs":21}
```

This is a lock held by a writer, not an unreadable database. The requested 80 ms retry was bypassed.

**Repair:** one status-open repair row. Keep the status path read-only for old schemas too. If their tables cannot be read, return an honest unavailable result and leave migration to a writer. Clear ownership of a raw handle after closing it, so cleanup cannot replace the original error. Add coverage for an old-schema store beside a writer and for no file/WAL changes on old-schema status reads. If migration during status is intentionally retained, obtain a D2 amendment and still fix the double-close and busy classification.

### B3. Proven: the scheduler slicing implementation leaves the large changed-file and tier writes whole

**Location:** `src/core/scheduler/batch.ts:69`, `:120` through `:130`. Row 024-05, D5.3. Required but unchanged paths: `src/core/scheduler/record.ts:319`, `src/core/scheduler/tiers.ts:182` and `:457`.

**Contract:** “at most `WRITE_SLICE_ROWS` (e.g. 200 files per slice)” when recording large batches, reconciling large batches and marking large tiers running, with event-loop yields between slices. Dependent revision/header markers must follow the file rows.

`flushStatsAhead` slices only paths absent from `diff.changes`. Every changed path is explicitly retained for the single transaction at line 70. For an ordinary bulk edit of 450 source files, the candidate therefore slices none of those 450 updates. Neither tier start nor tier record implements the required slicing.

**Probe:** call the exported `flushStatsAhead` on a valid diff with 450 distinct changed paths and one new-hash cache update per path. Count calls to a fake store's `transaction`. It returns:

```json
{"changedFiles":450,"updatesLeftForSingleRevisionTransaction":450,"sliceTransactions":0,"sameDiff":true}
```

Source inspection confirms those returned updates go straight to `commitBatch` inside one transaction. `startTier` still loops over all files under one transaction. `TierRecords.#write` and `recordTier` still enclose the whole result record. This finding is the missing D5 behavior, not a claim that this probe measured a hold longer than 250 ms.

The worker notes explicitly say these paths were not sliced and cite coordinator approval for option A. The candidate's spec and amendment log still require them. The board's narrower description does not resolve that discrepancy. `write-slices.test.ts` covers only unchanged-content stat updates, so it does not verify the row's full contract.

**Repair:** one scheduler repair row with ownership of the actual commit owners and their async callers, including `ledger.ts` and `record-tier.ts` if needed. Bound the changed-file reconciliation, tier-start and tier-record writes. Retain per-slice progress across busy retries. Publish dependent markers only after their rows commit. Add targeted tests for more than 200 changed files, tier start/record, a busy retry after a committed slice, and interruption before the final marker. Alternatively, narrow D5 through an approved spec amendment and name the deferred work explicitly; do not claim the current candidate implements the written D5.3.

## Should-fix

### S1. Proven, non-blocking: coverage batches use two transactions, while D3 says one

**Location:** `src/core/code/store/coverage.ts:139` through `:148`. Row 024-03, D3.3.

D3 says “Write each batch's records in a single `code.sqlite` transaction.” The implementation writes parts in one transaction, waits for them, then writes manifests in a second. This preserves the existing store-process requirement to read back generated part ids and still coalesces many files per batch. No correctness failure was found here.

Align D3 and the amendment log with this two-phase contract, including its `sent()` barrier and the rule that manifests never precede their parts. A later worker must not remove that barrier to match the current wording.
