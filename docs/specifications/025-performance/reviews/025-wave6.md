## Should-fix

### S1. Proven ineffective wait; plausible timing failure: complexity completion reads the wrong shape

`test/harness/work-per-call.test.ts:114` casts CLI status to a delivery-header
shape and waits for absent `code.counting`. CLI `CodeStatus` instead always
reports `code.pending` (`src/core/status/code-status.ts:54` and
`src/core/types/code-delivery.ts:230`). A status object with `pending: 55` and
`files: 55` already satisfies the candidate predicate. Thus the wait provides
no completion barrier.

The normal test passed on Node 22/24/26, with equal counts. No normal-run flake
was observed, so the race is **plausible, nonblocking**. On a delayed count,
hooks can read the counting path or its completion transition mid-sequence,
instead of the settled quiet state the committed limits describe.

**Fix:** consume the actual status type and require a completed count
(`pending === 0`, with evidence that the expected fixture files were admitted).
Check the CLI exit status too. Prove that a pending snapshot does not release
the wait, then retain the Node matrix. Do not add a fixed sleep or loosen limits.

### S2. Proven: every counted call leaks its scratch directory

`test/harness/work-per-call-helpers.ts:46` creates `/tmp/sq-work-*` outside
all registered fixture/build cleanup paths. `readWork` reads but never removes
it. A successful helper probe left one directory and one JSON file. The three
successful test runs left **30 directories**, ten per run. The reviewer removed
only these task-owned directories after reading them. No test daemon, runner
host or store process remained from these runs.

**Fix:** remove each counter directory in guaranteed cleanup after reading its
records, on success and error. Clear the timer on spawn failure and propagate
record-reading failures through the returned promise. Keep fixture-daemon
cleanup before fixture-directory removal.
