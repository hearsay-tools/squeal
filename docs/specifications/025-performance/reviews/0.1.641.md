## Blockers

### B1. Proven: builtin named exports stop following `syncBuiltinESMExports`

Location: `src/harness/builtins.ts:42` (`builtinSource`).

The review brief requires each builtin import form to behave as before,
including live bindings. Row 025-16 also requires unchanged hook output.
The virtual module exports each function as a constant read once. Calling
Node's `syncBuiltinESMExports()` later updates Node's real ESM namespace,
but cannot update these private constants.

A scratch entry imported default and named `node:fs`, namespace prefixless
`fs`, and literal dynamic `import("node:fs")`. It replaced
`fs.readFileSync`, called `syncBuiltinESMExports()`, and compared each imported
function with the replacement. Both builds used the same entry and esbuild
options; only the candidate build enabled `builtinsPlugin()`.

```text
                       named   namespace   dynamic
without the plugin     true    true        true
with the plugin        false   false       false
```

Before the replacement all identities passed. The same probe passed default
module identity, `promisify(execFile) === execFile[promisify.custom]`,
`new EventEmitter() instanceof require("events").EventEmitter`, and
`require("fs") === fs` in both builds. This isolates the regression to live
bindings rather than call wrappers or class construction.

This is a real repository contract: `src/core/lint/provider/rooted.ts:74`
and `observe.ts:75` patch builtins and synchronize exports after module
evaluation. They are included in routine Node builds. The probe proves the
import behavior break; it does not claim an end-to-end incorrect lint result.
The new bundle test does not exercise this case.

Fix scope: one builtin-transform worker. Preserve synchronized named,
namespace and literal-dynamic imports, with regression tests for mutation
after module initialization. Preserve function/class identity and custom
promisification. Rebuild the routine bundles and rerun the affected hook
checks. Do not implement function call wrappers that lose those identities.

### B2. Proven: builtin namespace generation depends on the build host's Node

Location: `src/harness/builtins.ts:33` (`Object.keys(mod)`).

Row 025-16 done-when: "a scratch build is byte-identical on Node 22.19 and
24.x." Enumerating the building Node's builtin exports violates it when a
namespace escapes static property analysis. The CLI contains such a use:
`src/runners/node-test/graph/resolver.ts:1` passes its `fs` namespace to
`enhanced-resolve`. Dynamic `fs/promises` and `node:module` namespaces also
retain complete export lists.

Built all Claude Code Node entries into two scratch directories using the
candidate's exported `bundleOptions`, the same installed esbuild, and
respectively Node `v22.19.0` and `v24.21.0`. Results:

```text
cli/squeal.mjs   DIFFERENT   5286839 bytes   5286950 bytes
other 14 .mjs entries       byte-identical
```

The Node 22 output includes `F_OK`, `R_OK`, `W_OK`, `X_OK`; the Node 24 output
instead includes `Utf8Stream`, `mkdtempDisposableSync`, and the promise API
`mkdtempDisposable`. Sorting stabilizes order, not membership. A namespace
also exposes the build host's API surface when run on another Node version.

CI independently reproduces the operational failure: Node 24 rebuilds all
five CLI bundles with different `openAsBlobSync` and `node:module._debug`
membership, then fails the required clean-build check. A local Node 26 pass
does not override that red CI result.

Fix scope: the same builtin-transform worker. Make namespace handling
independent of the building Node while preserving the runtime's supported
exports. Add coverage where the full namespace escapes, rather than only
known named imports. Compare the full Node bundle set across Node 22 and 24,
regenerate the runtime manifest, and obtain passing exact-SHA drift CI.

### B3. Proven: adding the plugin breaks the synchronous E2E build caller

Location: `src/harness/build.ts:199` (`plugins: [builtinsPlugin()]`), called
by `test/e2e/spec-026-build.ts:50`.

Shared `bundleOptions` previously worked with esbuild's `buildSync`.
esbuild rejects plugins in its synchronous API, even when the plugin's
callbacks are synchronous. `buildPluginDist` still passes these options
directly to `buildSync`, so its callers can no longer construct the shipped
test runtime. This is the changed module's existing caller, not a new test
expectation or an unrelated pre-existing failure.

Exact-SHA CI fails loading both `test/e2e/spec-026-tiered.test.ts` (Node 22
shard 1) and `test/e2e/spec-026-remote.test.ts` (shard 4):

```text
Error: Build failed with 1 error:
error: Cannot use plugins in synchronous API calls
  Object.build test/e2e/spec-026-build.ts:50:39
```

A minimal local `buildSync(bundleOptions(<scratch-outdir>))` reproduces the
same error immediately. No E2E suite was run locally. These suites are
excluded from Squeal's coverage, which explains why the eight affected checks
do not cover this failure.

Fix scope: one test-build worker. Move the shared E2E plugin build to
esbuild's asynchronous API and adapt its preparation/callers to await it.
Keep its cache/input observation and shipped-bundle options. Do not drop the
plugin only for these tests, which would make them exercise a different
runtime. Verify both named suites load and run, then require their CI shards
to pass on the repair candidate.

- **Policy freshness:** `config-file.ts` reads text before looking up its
  cached parse. `policy.ts` reuses a settlement only for that exact load.
  A same-process probe returned `100`, then `200` after a same-length edit
  with the old timestamp restored, then `300` after same-length atomic
  replacement with that timestamp. Unchanged text reused identity. The
  existing tests also cover missing, malformed, removed and separate-root
  files. No stale-policy regression was found.
- **Stop freshness:** a two-connection probe without triggers returned the
  same list while unchanged. A reader transaction kept its original pass
  snapshot after the writer committed fail, then returned fail immediately
  after the transaction ended. A wrapped own-state write invalidated the
  list and returned pass. The targeted test covers the armed marker path,
  external commits and fakes with no connection. No reachable stale Stop
  path was found. Hooks do not write known states through an unwrapped repo.
- **Frozen counts:** the new WeakMap caches only frozen arrays. Store lists
  decode fresh state objects, and `KnownState` and its consumers are read-only.
  A marker change replaces the list, so it replaces its counts. Mutable
  arrays still count afresh. No production mutation of a kept element or
  returned count was found. `Object.freeze` itself is shallow; this conclusion
  depends on the existing read-only contract.
- **Status builder removal:** every harness use of delivery was checked.
  No hook, Pi worker or OpenCode bridge path calls `delivery.status()`.
  Delivery invokes `options.status.build` only inside that explicit method.
  CLI status uses its separate reader. The throwing placeholder is unreachable
  on current hook paths. Claude Stop shrinks from 760,034 to 667,097 bytes;
  PreToolUse from 695,556 to 596,155 bytes across this range.
- **Build boundaries:** the new require banner obtains the real
  `createRequire(import.meta.url)` and keeps dependency resolution rooted at
  the bundle. The fixed Codex adapter dist is unchanged. OpenCode's Bun
  plugin keeps separate build options and native imports; it has no
  `getBuiltinModule` transform or require banner. Its committed bundle is
  not byte-unchanged: its sole delta is the requested bridge cache helper.
- **Compile-cache environment:** bridge tests pass for unset, user-set,
  empty, HOME/XDG and proxy-carry cases. An independent composition probe
  passed the actual `bridgeStart` environment through
  `withoutOwnCompileCache` and `dropOwnCompileCache`: own cache plus mark
  disappeared; user cache, including an empty value, remained. Node-test
  and pytest use the former path; Vitest drops the own cache before starting
  its user workers. Launcher and key-format tests are current/pass.
- **Latency coverage:** warmed runs still start fresh Node processes for the
  process hooks. They retain runtime work in the timing window and the 80 ms
  budget. Markers match a daemon-served store. They omit the unserved-store
  path, and a warm cache omits first-install/disabled/unwritable-cache costs;
  the retained direct diagnostics expose those startup costs for three
  harnesses. Antigravity asserts delivering output; Pi asserts a real answer,
  including its fresh-worker case. Codex intentionally measures runtime
  bundles with an adapter-like cache, as this brief allows. OpenCode keeps
  both sides warm for its relative margin; S1 concerns reporting only.
