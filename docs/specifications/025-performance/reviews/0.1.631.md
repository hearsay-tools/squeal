## Blockers

### B1 — Proven: fixture cleanup kills an independent process that only names a fixture path

Files: `test/harness/codex/cache-fixture.ts:122`, `:126`, `:143`, `:172`.

The new ownership test accepts any process whose cwd lies under the fixture, or whose command line contains an argument with `${dir}/`. Neither proves fixture ownership. Only the test process and its immediate parent are excluded.

A separate diagnostic process, such as `tail -f <fixture>/logs/daemon.log`, has a foreign HOME and can run outside the fixture directory. It still matches the argument rule and receives SIGKILL from `CodexMachine.end()`. The same applies to an independently opened shell inside the temporary directory. This breaks the review's explicit requirement to kill only fixture processes, and the row's scope of stopping the daemon and its surviving children.

An isolated probe used the real `codexMachine` factory without building a plugin. It started an independent Node observer with foreign HOME, cwd `/tmp`, and a fixture log path as a data argument. After the observer printed `ready`, the probe called `m.end()` without supplying any PID. Actual output:

```text
OBSERVER {"exit":[null,"SIGKILL"],"fixtureHOME":false,"fixtureCwd":false,"fixtureLaunch":false}
```

No host process was used in this proof. The process was created only inside the sandbox.

**One-worker fix:** remove cwd and arbitrary argument substrings as sufficient ownership evidence. Use the fixture's exact unique HOME for orphan discovery and tracked fixture process identities/descendants where needed. Keep exclusions before every signal. Add a regression test proving a foreign-HOME observer that names a fixture path survives, while the fixture's detached writer and store process end. Preserve the bounded wait, zombie handling and removal retries.

### B2 — Proven: a standing UNKNOWN record still causes a zero-row write transaction

Files: `src/core/store/prune.ts:115`, `:153`; contract: `tasks/wave-3.md:37` and `:48`.

The brief says that when a prune slice has nothing to delete it must "skip acquiring a write transaction". The new read guard checks whether any unknown-run record exists. A record whose UNKNOWN still stands passes that test. `writeIf` then opens the write transaction, although `dropFallenUnknownRuns` keeps every record and returns zero.

This is a normal stable state after a runner failure. Every prune keeps taking an unnecessary SQLite write lock. Returning `false` avoids the pause but does not avoid the lock.

A real-store probe registered one live worktree, inserted one UNKNOWN check at revision 3 with summary `runner failed`, and recorded a matching unknown-run entry with the same file, revision and reason. It ran every `pruneSlices` callback with `maxSizeMb: null`, counting transactions with `observeWrites`. Actual output:

```json
{"writes":1,"counts":{"resultsRemoved":0,"runsRemoved":0,"checkpointsRemoved":0,"checksRemoved":0,"worktreesRemoved":0},"unknownRuns":1,"allFalse":true}
```

The committed no-op test covers passing states only, so it misses this case.

**One-worker fix:** make the read-only preflight detect a fallen unknown-run record, rather than any record. Retain the under-lock standing check before mutation. Add a standing-UNKNOWN fixture to `test/daemon/sliced-prune-idle.test.ts` and assert zero transactions and zero pauses. Also retain a fallen-record case that proves real deletion still occurs. Rerun the prune validity corpus and key-format gate; do not raise a version to bypass it.

### B3 — Proven: the shipped-launcher change breaks CI recording in the `ff-ci` benchmark

Files: `bench/run-cell.mjs:89`, `:534`; caller: `bench/run-all.mjs:55`.

When the plugin has `bin/squeal`, the new selection sets `cliCmd` to that launcher and `cli` to an empty array. Most calls now use `cliCmd`. The `ciImport` recording call still uses `NODE` with `[...cli, "ci", "record", ...]`.

Every current shipped plugin has the launcher. Thus `ff-ci` runs `node ci record ...` in the upstream checkout. Node tries to load an upstream file named `ci`; no recording parts are produced, and export/import cannot exercise the intended CI reuse path. This breaks row `025-13`'s required shipped-path parity and a previously working benchmark cell.

A probe extracted the candidate's unchanged `ciImport` function, supplied the actual launcher-selection values and captured its `timed` calls. It executed only the resulting Node invocation, without running a benchmark or test suite:

```text
CI_RECORD {"code":1,"error":"Error: Cannot find module '/tmp/ci'","cmdIsNode":true,"argsStart":["ci","record"]}
```

**One-worker fix:** pass `cliCmd` to this `timed` call too. Test the record/export/import command construction with a plugin that has `bin/squeal` and one without it. The test must check the executable and argument list of the record call, not only inspect the source for a launcher string.
