# Research 025-22: the benchmark's Vitest cannot load Squeal's coverage provider

Brief: `bench-provider-brief.md`. Examined: Squeal 0.1.641 (`squeal--v0.1.641`, branch base `4a20b980e`), Vitest 5.0.3, Vite 8.3.8 and 8.4.0 (npm tarballs), Node v24.22.1, one boat.dev `default` sandbox ("AMD EPYC", 4 vCPUs) on 2026-11-26, deleted. Probes and logs: `probes/bench-provider/`.

**Verdict.** This is a product bug that a Vite release exposed. It is not a benchmark or sandbox fault. Vite 8.4.0 (published 2026-11-26 10:59:36Z) calls `pluginContainer.load(id, { withMetadata: true })` and reads `.code` on the result. Squeal replaces `load` with a one-argument wrapper (`src/runners/vitest/sources.ts:135`) that drops the second argument. When no plugin loads the file, Vite then gets `null` and throws `Cannot read properties of null (reading 'code')`. The provider is simply the first module that the daemon's Vitest loads. With coverage off, every test file fails the same way. The bench project installs without a lockfile, so it took Vite 8.4.0 after 10:59Z. CI uses the repository's lockfile, which pins Vite 8.3.2. The fix is to pass every argument on: one line in the product. Separately, the benchmark should pin Vite so that two versions are compared on the same dependencies.

## Findings

**Q1. The error.** On the sandbox, `repro-daemon.sh` reproduced the benchmark's log line exactly with 0.1.641 and a bench-shaped project on Vite 8.4.0. The same plugin started cleanly when the project pinned Vite 8.3.8 (`logs/2-daemon-start.log`). A copy of the bundle that wrote out each error's `cause` chain showed two layers (`logs/3-cause-chain.log`). Vitest wraps the cause as `Failed to load custom CoverageProviderModule from …` (`vitest/dist/chunks/coverage._yXj5zeb.js:27`, `{ cause: error }`). The cause is `Error: Cannot read properties of null (reading 'code')` thrown at `reviveInvokeError` in Vite's `module-runner.js`. The module runner rebuilds a server-side error from its message only. Vitest's transport returns the raw `Error`, and `Object.assign` does not copy its non-enumerable `stack`. A patch in Vitest's transport catch printed the server-side stack: `TypeError … at loadAndTransform (vite@8.4.0 …/chunks/node.js:19257:17)`, while fetching `/@fs/~/plugin-0/dist/coverage/provider.mjs` (`logs/4-vite-fetch-error.log`). All tagged verified by experiment.

Line 19257 is `if (loadResult.code == null)` after `const loadResult = await pluginContainer.load(id, { withMetadata: true })`. In 8.4.0, `EnvironmentPluginContainer.load(id, loadOptions)` returns `null` when `!loadOptions?.withMetadata` and no plugin loaded the file (`node.js:8729`). Vite 8.3.8 called `pluginContainer.load(id)` and checked for `null` (`node.js:20065`); it has no `withMetadata` anywhere. Vite 8.4.0's `index.d.ts:1455-1458` declares both overloads (read in source code, vite 8.3.8 and 8.4.0 npm tarballs). Squeal's `SourceStamps.attach` (row 001 D4, review wave-13 B2) does `container.load = async (id) => { await this.#stamp(reads, id); return load(id); }`, so Vite's options never reach the real `load` (read in source code, `src/runners/vitest/sources.ts:134-137`; bundle line 49564).

Proof that the wrapper is the cause. `probe.mjs` starts Vitest with Squeal's provider through Vitest's own API, without Squeal's Vite hooks. It loaded the provider and ran a test on both Vite 8.4.0 and 8.3.8 (`logs/1-plain-vitest-api.log`). `plugin-fix` changes only the wrapper to `async (id, ...rest) => … load(id, ...rest)`. With it, `squeal run --all` gave "21 passed (18 tests, 3 test files loaded)" with coverage on, on both Vite 8.4.0 and 8.3.8 (`logs/5-run-all.log`). Verified by experiment.

**Q2. The difference.** It is the installed Vite version, nothing else.

- `run-all.mjs` runs `pnpm install` on a `package.json` that pins only `vitest` and `@vitest/coverage-v8` at 5.0.3, with no lockfile. Vite is a peer of Vitest (`^6.4.0 || ^7.0.0 || ^8.0.0`), and pnpm installs the newest version that matches. The sandbox resolved `vite@8.4.0` (read in source code, `bench/run-all.mjs:212`, `bench/gen-project.mjs:55`, `vitest/package.json`; verified by experiment, `pnpm ls`).
- `npm view vite time`: 8.3.8 on 2026-11-11, 8.4.0 on 2026-11-26T10:59:36Z, now `latest`. The 9700X run built its template at 10:27:47Z (`run.log`). Both EPYC runs built theirs at 13:54:33Z and 17:11:23Z. The results keep no lockfile or Vite version, so it is inferred, not recorded, that the 9700X run had 8.3.8.
- CI installs from `pnpm-lock.yaml`, which locks `vite@8.3.2` (read in source code). So CI runs Squeal's tests on Vite 8.3.2.
- Ruled out by experiment on the sandbox: the pushed files (56 of 56 arrived, the provider among them), CPU (an EPYC sandbox passes with 8.3.8), Node (v24.22.1 in both), paths (`~/plugin-0` and the project layout as the benchmark has them).

**Q3. Users.** Coverage is on by default. With Vite 8.4.0 the daemon's Vitest cannot start, so "every check of this worktree is unknown". With coverage off, every test file has no result: "the Vitest instance failed to load modules and is recreated: Error: Cannot read properties of null (reading 'code')" (`logs/5-run-all.log`, first block). Both verified by experiment on the bench-shaped project. A user project gets Vite 8.4.0 from a fresh install, a lockfile update or a new project from today on. Only projects that run Vite 6 or 7, or that lock 8.3.x, stay out of it (inferred). How many users have updated is not determined: no source counts it.

The log line drops the cause in two places (read in source code). `createRecoveringRunner` builds `"<name> could not start: " + messageOf(cause)`, and `messageOf` reads `error.message` only (`src/core/daemon/runner.ts:148, 270-273`). The daemon runs Vitest in a runner host, and `errorOf` sends `{ message }` back over the socket (`src/core/runner-host/protocol.ts:246`). So the cause is gone before `messageOf` sees it (`logs/3-cause-chain.log`: the daemon side has depth 0 only). Even a logged cause would read only "Cannot read properties of null (reading 'code')", because Vitest's transport loses Vite's server stack. But that text says the file was found and the load itself broke, which would have pointed away from a missing file at once. The coverage-off path already shows this text, because `closeBroken` (`src/runners/vitest/broken.ts:56`) takes the run error's own message.

**Q4. The smallest fix.**

- *Product (needed):* in `SourceStamps.attach`, forward every argument, `async (id, ...rest) => { await this.#stamp(reads, id); return load(id, ...rest); }`, typed as `typeof container.load` so that both of Vite's overloads hold. `overload-check.ts` shows that `tsc` rejects the current one-argument wrapper against Vite 8.4.0's overloads (TS2322, verified by experiment). So bumping Squeal's locked Vite to 8.4.0 makes the typecheck name the line, and the existing Vitest adapter tests then run on the new `load` path. Verify the fix with: (a) the lockfile on Vite 8.4.0 and the affected adapter tests through `squeal status --wait`; (b) a unit test that the wrapper passes a second argument on and returns `load`'s value unchanged; (c) `repro-run.sh` with the rebuilt plugin on a sandbox.
- *Product (diagnostic):* append the `cause` chain's messages in `messageOf`, and carry them in the runner host's `HostError`. Then the note reads `… from <path>: Cannot read properties of null (reading 'code')`.
- *Benchmark:* add an exact `vite` to `gen-project.mjs`'s `devDependencies`, or commit a lockfile beside it, and write the installed `vitest`, `vite` and `@vitest/coverage-v8` versions into `meta.json`. Without that, an upstream release changes the benchmark between two runs of the same refs. The pin also keeps 0.1.640 and 0.1.641 measurable, because the product fix reaches only new versions. Verify with one `bench/boat-run.sh --cells ref` run whose cells pass correctness (inferred).
