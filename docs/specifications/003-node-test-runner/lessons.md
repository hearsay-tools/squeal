# 003 node:test runner: lessons

## Dogfooding on cezarion

Task 003-19, 2026-10-08. Squeal Codex plugin 0.1.31, installed and trusted in the real `~/.codex`, validated cezarion's node:test suites beside its Vitest suite while a Codex agent worked there. The agent was `codex exec` (CLI 0.160.1, `gpt-6.1-sol`), three sessions with no bypass flag. Cezarion was at `13351da8`, in a linked worktree of cezar with the config uncommitted, as the human decided (`status.md`, 2026-10-08). Node 24.21.0 only: cezarion's `engines` is `>=24.15.0`, so Node 22 was not exercised. Load average 3 to 27, other workers running. Scripts, prompts and trimmed logs: `research/probes/dogfood/`. Its README lists the rules followed and every source.

The worktrees are removed. Cezar's shared store `/home/agent/projects/cezar/.git/squeal/` still holds their rows and run logs: worktree `4ce39392decee992` (21,906 results, 253 runs), worktree `35edde0f88e9b723` (584 results, 10 runs), and the meta keys `nodeTest.observed.{test:unit,test:package,root:test:unit}` and `nodeTest.observedPreloads.root:test:unit`. They were not deleted.

### What the agent did

- **s1 used Squeal and ran no test itself.** It reported the two `PASS -> FAIL` in its next message: "Step 1 produced two Squeal failures during the harmless reads". After the fix, its `status --wait 60000` timed out on 3,536 pending Vitest checks. It then asked `squeal why` for the two new fixture cases and read "PASS, current, observed at revision 2". Final message: "I ran no tests myself because Squeal was validating in the background." It reached the CLI through the absolute path the primer now prints, so 002's defect 4 is closed.
- **s2 ran node:test itself, because of Squeal's own text.** At +16 s: "this file uses `node:test`, so I'll run it directly because Squeal only covers Vitest." It ran `node --import tsx --test packages/cezar/test/e2e/stop-child.test.ts` red, then green. Squeal's run for that edit came after the session had ended. Final message: "It uses `node:test`, outside Squeal's stated Vitest coverage."
- **s3 did the same, and Squeal was silent anyway.** At +30 s: "No new Squeal feedback has arrived. The relevant test uses Node's test runner, which Squeal doesn't cover, so I'll run it directly". The direct run failed as the task predicted; Squeal never ran the file. Final message: "the supplied Squeal instructions said its coverage was Vitest-only."

### False, late, repeated or missing

- **False:** two current passes on a broken input: `cursor-hang-stdin.test.ts` at r5 (s3) and `todo-task-text.test.ts` at r7 (P1). In both, the test reaches the edited file only through a spawned `node` or a `readFileSync`. Status said "Known failures: 0" both times. Nothing named those files as unkeyed (defect 6).
- **Late:** s1's `FAIL -> PASS` arrived 30 s after it was recorded, during a yielded command (defect 9). s2's result came 4 min 17 s after the edit and after the session (defect 2).
- **Repeated:** none.
- **Missing:** s3's deliberate break, never run. s2's new assertion was red only at r3, which no run covered; the agent saw it red only in its own run. That is correct for a superseded revision.

### Defects

Numbered from 1 for this spec.

1. **The primer and the skill tell the agent that Squeal covers only Vitest, so with node:test projects configured the agent runs node:test itself.** Harness text, `src/harness/shared/primer.ts:15` ("Squeal runs this repository's Vitest tests [...]; do not run Vitest [...]") and `plugins/{claude-code,codex}/skills/squeal/SKILL.md` lines 3, 10, 14 and 18 ("Squeal covers only the Vitest tests: run typecheck, build and other suites as the repository says"). s2 and s3 quote it as their reason. Goal 8 says the hooks work unchanged; their words do not. The text should name the configured runners, or say "this repository's tests".
2. **A revision's node:test work waits for any tier already in flight, even an unrelated Vitest tier of an older revision.** Core scheduler, 001 D5 with 003 D7. At r4 the edit touched only `test:package` files. Their run started 4 min 17 s later, after a 425 s tier of r2's Vitest re-runs (cezar's slow workflow tests). Until then even the runner part (affected, closures) stayed pending. A cheap node:test file sat behind minutes of unrelated work, and the agent finished without a report. Vision principle 4 ("fast, relevant checks come first") argues for running a new revision's direct files beside, or before, an older revision's transitive tail.
3. **A module loaded through `createRequire(<some file>)` is counted as a preload load, so editing it re-runs the whole project.** Adapter, D5's reachability. `release-finalization.test.cjs` and `recover-review.test.cjs` call `createRequire(path.join(root, 'package.json'))`. The recorder logs the edge with that `package.json` as its parent, and no test-file root reaches it (`unreached.mjs`). So `nodeTest.observedPreloads.root:test:unit` holds seven ordinary modules (`release-finalization.cjs`, `release-bump-pr.cjs`, `release-ci.cjs`, ...). P2: a comment in `release-bump-pr.cjs` re-ran all 36 files (47 s) instead of the three that load it: `release-bump-pr.test.cjs` and `recover-review.test.cjs` statically, `release-finalization.test.cjs` through `createRequire`. An over-run, never a stale pass. Fix direction: attribute a load whose parent is not a loaded module to the test file of that process, since one process runs one test file.
4. **Results stored before an observation never serve another worktree, so the first inheriting worktree re-runs every file with observed paths.** Adapter, D3 as designed ("the next run in that worktree corrects"), measured. Worktree 1's results for `resolve-browser-launch.test.ts` and `inline-contract.test.ts` sit under their pre-observation keys (`45299cc6`, `daef9f49`). Worktree 2 computed the post-observation keys (`1363357b`, `a9b67400`) and ran both. `observedPreloads` grew from four to seven paths after worktree 1's last root runs, which re-keyed all 36 root files. Result: 38 of 58 node:test files re-ran where goal 2 promises zero. Fix direction: when a run observes paths whose content at run time equals the current content, also store its results under the key that includes them.
5. **A second daemon starting on the shared store made the first daemon's scheduler hit `database is locked`, losing a tier for 57 s.** Core store, 001. At 09:13:07 worktree 1 noted "scheduler stopped running tiers: Error: database is locked". The tier begun at 09:12:12 never closed its run row (`ended_at` null), and the same four files ran again from 09:13:09. During the baseline, 1 of 94 status reads also failed with "store busy for more than 1000 ms". The store was shared with cezar's own Squeal daemons throughout.
6. **Tests that reach their input through a spawned process or a file read keep a stale pass, and nothing names them.** Repository config, with a missing note. Open question 3 leaves these to declared `inputs`, but `squeal init` seeds none and no note points at them. The adapter knows the signal: a closure of only the file and a manifest, as for the seven spawn-based files listed above. `todo-task-text.test.ts` reads its fixture through `readFileSync(new URL(<literal>, import.meta.url))`, a literal the parser could resolve. Declared inputs that would have caught r5 and r7: `packages/cezar/test/unit/cursor-hang-stdin.test.ts: ["packages/cezar/scripts/mock-cursor-hang-stdin.mjs"]`, `packages/cezar/test/unit/todo-task-text.test.ts: ["packages/cezar/test/fixtures/todo-task-text.json"]`.
7. **`squeal init` prints a template whose name collides with the entry it just seeded.** CLI, after `reviews/wave-2.md` N1's fix. The refused root `test:unit` gets the template name `test:unit`, the name of the seeded `packages/cezar` entry, so pasting the template as printed is rejected as a duplicate. `reviews/wave-2.md` expected the seed to be named `packages/cezar:test:unit`; it is plain `test:unit`.
8. **Test children that escape a run outlive the daemon in its process group.** Core, 001 D12, which kills process groups only at a deadline. Two `fake-dev-server.mjs --delay 600000` from a Vitest tier at 08:20:11 (cezar's preview tests) were reparented to `systemd --user`. They stayed in the daemon's process group 818133 for 57 min and survived `squeal stop`, and I terminated them. Cezar's tests leak them; Squeal neither reaped them nor said so.
9. **Under Codex, a `PostToolUse` is not delivered while a command yields to `write_stdin`.** Adapter limitation, 002 open question 5, now measured. s1's `FAIL -> PASS` was recorded at 08:49:09.75. The agent's `squeal status --wait 60000` yielded at 08:49:21.9, and two `write_stdin` polls completed at 08:49:28.5 and 08:49:33.5. None carried it. It arrived at 08:49:39.6, after the next `exec_command` completed. `squeal status --wait`, the command the primer suggests, is exactly such a command.
