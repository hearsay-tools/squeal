### 1. Rollback recovery and the C3 invariant

**Proven.** I archived the review base, linked the installed dependencies, and copied only the candidate's `one-write-path.test.ts` into that scratch tree. Running the two cases under “an observed path the record's rolled-back transaction did not store” produced:

The required subset passes both cases on the candidate. The injection throws at the first `meta.set(observedMetaKey(""), ...)`. The test checks that both the shared meta value and every result for the file are absent after rollback (`one-write-path.test.ts:195-197`). After the next record, it checks the stored path and current result, then restarts and inherits without a run (`:208-216`). Editing the observed path then runs the file. The second case restarts before another record, verifies that the fresh view lacks the path, and requires a new run before the result is current (`:222-234`). These assertions cover C3's additions (a) and (b).

The view may lead the store after rollback. The retained `#unwritten` entries make the next record repair the store. Results and `writeSeen` remain under the same outer transaction (`record.ts:341`, `tiers.ts:665`, `record-tier.ts:218`). A failed record commits neither its results nor its observed paths. The amendment describes that invariant, rather than claiming that rollback restores the view.

### 2. Union across connections and the shared writer

**Proven by test and source.** `observed.test.ts` now opens two independent store connections. Both views first read empty keys. B writes its paths, then A writes from its earlier view. Exact text assertions require the union in `observed.`, `observedDirect.` and `observedStartup.`. B then refreshes through its own connection and sees both paths. This test passes on both Nodes.

`SharedPaths.write` starts a store transaction before `meta.get` (`observed.ts:229-230`). `Connection.transaction` uses `BEGIN IMMEDIATE`, or a savepoint under the record's existing write lock. Thus its merge reads the stored value under the write lock. It does not use the cached `#read` value. `see` changes the view; `write` changes the store. Both stored shapes use the same `parse`, `merge` and `format` functions. The observed and direct facades use the map shape; the startup facade uses the list shape.

### 4. Refresh residue

**Proven pre-existing limit; outside the wave's repair.** `SharedPaths.of` calls `refresh` after a successful write resets `#read` (`observed.ts:199-200`, `:244`). That read merges the whole project's map and discards the list of grown entries. `WorktreeKeys.refreshObserved` later receives no entry to put into `#grownElsewhere` (`keying.ts:435-437`).

I ran the same small probe against separate archives of the candidate and review base. Each used two `WorktreeKeys` views over a scratch store and a module-load environment. Both keyed test files A and B. The second view stored `y.txt` for B. The first view stored `x.txt` for A, then called `observedOf(A)` before `regrowObserved()`. It changed the cached hash of `y.txt` and asked the key index to re-key that path. Both archives returned:

```json
{"observed":["y.txt"],"closure":["test/b.test.ts"],"grown":[],"changed":[],"keyUnchanged":true}
```

Thus B's observed view contains `y.txt`, but B's indexed closure and key do not. A result already current at that key can remain current: the key has not changed. This is a key-level proof, not a full daemon status reproduction. Another `setClosure(B)` repairs the closure. The existing first case in `observed.test.ts` also pins the read that consumes growth. The candidate does not introduce this limit; the base probe gives the same result. It does not block this review.

### 6. One write per record transaction

**Proven by the product call graph.** `RecordWriter.#write` calls `recordTier` once inside its outer transaction. `recordTier` records its files, then calls `endRecord` once. The sole product call to `WorktreeKeys.writeSeen` is `endRecord` (`record-tier.ts:218`). It writes startup views, then observed and direct views. Each facade holds one `SharedPaths` per project and meta key, and visits it once. `addObserved` now calls `see`, with no store write. No product caller uses `ObservedSets.add`.

Thus the same `SharedPaths.write` is not called twice in a record transaction. The concern in the notes is real for a future caller: a second write in one transaction could clear an unwritten entry that the first write stored, then lose it if the outer transaction rolls back. The present product call graph cannot take that path.
