The required subset passes this same test on both Nodes at the candidate. Two `WorktreeKeys` views share one store. Both key A and B before the other view records Y for B. This view records X for A, reads A, then regrows. The test requires Y in B's closure and requires an edit of Y to re-key B (`observed-regrow.test.ts:107-115`). ### 2. All product reads after a write

**Proven by source; covered by the regression and unchanged rollback tests.** `SharedPaths` has only two product users: `ObservedSets` and `StartupSets`. They own the observed map, direct map and startup list. No product caller uses `ObservedSets.add`; the product calls `see`, then the record's sole `writeSeen`.

| Read path | What happens between a write and the next refresh |
| --- | --- |
| `WorktreeKeys.setClosure` (`keying.ts:405-419`) reads `ObservedSets.of` | It may assemble from this view before foreign paths arrive. Its callers include bootstrap restore (`bootstrap.ts:150`), environment-gate changes (`keying.ts:307`), policy changes (`:356`, `:364`), declared-input changes (`:577`), revision closure resolution (`revision.ts:268`), and runner refinement (`refinement.ts:255`). No read consumes growth now. Refinement calls `regrowObserved` before applying runner closures (`refinement.ts:247`); a later explicit refresh still reports any foreign additions. |
| `addObserved` (`keying.ts:428-431`) calls `see`, then `setClosure` | It adds this run's paths to the view immediately. `recordCompleted` uses it only after preparation has refreshed the projects (`observed.ts:59`). Completed results use the grown closure's key (`record-tier.ts:152-166`). |
| `observedGrowth` reads `observedOf` (`observed.ts:93`) | It explicitly refreshes first (`:59`). It includes foreign paths absent from the closure in the stability check and hashes them before recording. |
| `#release` reads `ObservedSets.of` (`keying.ts:618`) | It decides which inherited extra paths to keep tracking. It stores no result. A retained closure also keeps a path through the reverse-index check (`:622`). |
| `heldBeyondInputs` reads `observedOf` (`edit-cut.ts:153`) | It classifies reached files for edit scheduling. It does not construct a result key. |
| `observedDirectOf` reads `directOf` (`edit-cut.ts:192`), and `markDirect` calls `see` | Direct marks control reach and order. They do not add a separate segment to the key. `ObservedSets.refresh` refreshes them too (`observed.ts:113`). |
| Startup `seeStartup`, `#withStartup` and `regrowStartup` | `seeStartup` adds to the view. Every startup `of` is in `#withStartup`, which calls `refresh` first (`keying.ts:290-298`). `regrowStartup` refreshes before it re-keys environments (`:464-468`). |

A local closure can temporarily omit a foreign path that the shared store already holds. This was already possible between explicit refreshes. The change does not turn such a read into a permanently missed re-run: it leaves the foreign additions available for the keying layer's refresh. The record refreshes before it stores observed results; the module-load refresh also runs through the daemon's timer and refinement. The changed code removes the path that silently consumed those additions. No examined caller requires the implicit read after a write. Extra paths from another branch can cause an over-run, as C3 permits.

This does not claim an atomic snapshot across daemons between asynchronous record preparation and the final write. The existing contract reads shared observations at first keying and before tier recording, not on every `of`. This review found no new missed-result path at that boundary.

The write still happens once per record transaction, after file results and before commit (`record-tier.ts:218`). The union, rollback, next-record recovery and restart assertions from 016-29 are unchanged and pass in `observed.test.ts` and `one-write-path.test.ts` on both Nodes.

**Proven exclusion by source.** This case creates a fresh fixture store and one worktree. The second-worktree case creates a different fixture. The first case has no other writer whose observed paths a shared-set write could merge. This worktree's own paths are already in its view when it writes them, so neither 016-29's deferred write nor this change can create foreign growth there. The CLI rewrite is a declared input of the slow file only. A shared-set write alone is not a file edit.

**Plausible cause: the new failure's normal forced retry starts after the test's run-count snapshot.** `storeFile` identifies a new failure (`record-tier.ts:201`), and `endRecord` queues its fast file once, forced (`:230`; `rerun.ts:86-110`). A same-key forced retry keeps the stored failure current (`state/derive.ts:67-73`). The test helper waits on check-level `counts.pending`, not file-level `testFileCounts.pending` (`test/e2e/harness.ts:383-394`). It can therefore accept a current fast failure while that retry is still queued or running.

`fastFirstThenSlow` resets `from` immediately before Stop (`slow-shape.ts:123`). If the retry has already started, its run row precedes that snapshot and the assertion passes. If it starts later, `ranSince` includes the fast file and the assertion fails even though no key changed. This fits the observed extra failing fast file and the passing rerun.

**Unverified historical attribution.** The failed CI assertion prints file names, not the fast run's key, forced flag or cause. Those logs do not prove which mechanism started that exact run. Five passing repetitions do not prove it either. The retry explanation is the most likely source path, not a claim that its historical cause was captured. This is pre-existing test behavior, outside the candidate's product fix.
