# Research brief: what the slow tier is for, and when its results can reach the agent

Use /researcher. Shape: research, read-only on the product. Decided by the human on 2026-10-18 (row 004-74): before changing D2's triggers, find out what Squeal's slow tier should be. The human's own framing, to weigh rather than to confirm: running slow files when the build is made makes sense, but not every e2e suite may depend on a build; "slow" may be the wrong name; build-dependent suites may be better run on request, as now, with better wording; the agent may need a baseline ready so that a later build does not re-run everything; and dropping slow-tier support so Squeal focuses on the fast lane is a real option. Run probes only when the one-minute load is below the CPU count.

Read first: 004 `spec.md` D2 (triggers, lanes), D5 (keys: a slow file is keyed by its declared artifact), D8, D9; `research/slow-suite-policy.md` (finding 3, why idle only) and `slow-suite-runtime.md`; `lessons.md` (the dogfooding defects); `research/issue-4-signals.md`; issues #3, #4, #5, #29, #35; the cezarion and this repository's `squeal.config.json` slow globs and inputs.

Questions, each with its evidence tag:

1. **What the slow suites test.** For this repository's `test/e2e` and cezarion's slow globs (`test:package`, the browser e2e): what each needs before it can run (a build, an install, a server, ports), and whether it tests the built output or the sources live (a dev server). Which are build-dependent, which are only slow?
2. **When agents build.** From the eval cells under `/tmp/squeal-evals-<uid>/` and dogfood transcripts named in `lessons.md` (read-only; never write under the real HOME), how often a session rebuilds mid-turn, at its end, or never; and whether its slow results were current when it finished.
3. **What a rebuild invalidates.** A slow file's key holds its declared artifact, so one rebuild re-keys every file declaring it. Could a narrower closure (the node:test recorder, the bundle chunks a browser spec loads) re-key only the specs a build changed? Measure on one real rebuild in a scratch worktree. This is the human's "baseline ready for the build" question: what can be reused after a build, and what must re-run.
4. **Mid-turn cost.** With slow files in their own lane today (D2), what running them mid-turn after an artifact change costs the fast lane (its latency at two loads), measured on a scratch worktree.
5. **The options.** For each, the evidence for and against and what it costs: (a) as now, pause and explicit triggers, with better wording; (b) run affected slow files when their artifact changes; (c) on request only, never automatic, with a kept baseline; (d) drop the slow tier and say Squeal covers fast tests only. Include the name ("slow", "e2e", "build", "artifact" tier) and the text an agent reads.
