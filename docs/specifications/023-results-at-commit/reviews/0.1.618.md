## Blockers

### B1. Proven: a recorded write path does not prove that the run made the name

Locations: `src/runners/observe/inputs.ts:100`; `src/core/keys/observed.ts:364`, `:385`, `:393`; `src/core/scheduler/keying.ts:972`. The unchanged recorder boundary is `src/runners/observe/fs.cjs:77`, `:243`.

Wave 38 requires: "an ignored name the user (or any process outside Squeal's test runs) puts into a listed folder still separates keys, before or during a run." This candidate violates that hard limit.

`wroteOf` copies the recorder's `written` set. Most fs wrappers fill that set **before** calling the real operation. It includes failed writes and successful calls that change nothing. For example, an exclusive `writeFileSync` that throws `EEXIST`, or recursive `mkdirSync` of an existing directory, still names the path in `ObservedInputs.wrote`. `Listings.wrote` then treats the current entry as output if the cached earlier names lacked it. It also marks ancestor names when the run only wrote a child.

One real-adapter scheduler proof establishes the wrong answer:

1. Track `test/fixtures/listed/a.json` and one unchanged folder-reading test. Seed its existing observed listing, so this is not a first-seen run.
2. Start the run with only `a.json` present. The test signals readiness and waits on a gate outside the worktree.
3. From the probe process, create ignored `test/fixtures/listed/user-dir`. The recorded test did not create it.
4. Open the gate. The test lists the folder, then calls recursive `mkdirSync` on `user-dir`, then asserts that the earlier listing has two names. The mkdir is a no-op. The assertion passes.
5. The report claims `user-dir` in `wrote`. The core excludes it and stores the pass at the key from before its creation.
6. Remove `user-dir` from the probe process and reconcile one unrelated tracked edit. A fresh run would list one name and fail before its own mkdir could affect that listing. Instead, the key stays equal, no run starts, and the earlier pass stays current.

The fixture's critical ordering was:

```ts
const names = readdirSync(folder);
mkdirSync(join(folder, "user-dir"), { recursive: true });
expect(names).toHaveLength(2);
```

Actual scheduler output, with unrelated fields omitted:

```json
{
  "namesNow": ["a.json"],
  "beganKey": "c34ed515267601d0a81436959e29f0276ddefdc207c9e1d623c386b0d588eead",
  "keyNow": "c34ed515267601d0a81436959e29f0276ddefdc207c9e1d623c386b0d588eead",
  "before": 1,
  "after": 1,
  "state": { "outcome": "pass", "validity": "current", "origin": { "kind": "own" } }
}
```

The regression assertion failed with `expected 1 to be greater than 1`. This is a same-worktree false current pass. The retained 023-70 foreign-result refusal cannot prevent it.

Two cheap checks expose related holes in the same ownership rule:

- The real recorder reports `listed/user.log` in `wrote` after an exclusive write throws `EEXIST` and the run only reads the user's bytes. Feeding that report through `Listings.wrote` makes production `checkKey` equal the key without `user.log`.
- `beginRun` copies the names from the last listing read; it does not read disk. Create an ignored user directory after that read but before `beginRun`, then let the run write one child. The ancestor directory is excluded too. Its own creation happened before the run and outside it. This also gives equal production check keys.

**One-worker repair:** require evidence that the run actually created the entry being excluded. Do not treat a write attempt, a no-op mkdir, or a write below a pre-existing user directory as creation of that directory. Preserve conservative inclusion when ownership is unknown. A fresh run-start snapshot alone does not fix the during-run case. Carry any recorder-contract decision back to the coordinator before changing versions.

**Required regressions:** keep the gate ordering above, the failed exclusive write, and the stale-snapshot parent-directory case. User names must count at the next revision and after restart. Keep the intended own-output and second-reader stability tests.

### B2. Proven: a user replacement before report arrival becomes the run's output

Locations: `src/core/keys/observed.ts:393`; `src/core/keys/run-written.ts:53`, `:63`, `:89`.

Wave 38 also requires: "A run-written name that later a user edits or replaces must count again (it stops being 'the run's own')."

The stamp comes from the entry on disk when `wrote` processes the report. No write-time stamp or entry identity accompanies `ObservedInputs.wrote`. If the run creates `out.log` and the user replaces it before the report arrives, `RunWrittenNames.wrote` records the **user's** inode and timestamps. All later stamp checks succeed for that replacement, so the name stays excluded. The same risk applies when a path is already held: `has` deliberately ignores the current stamp, and another report can renew it without checking who replaced the entry.

The independent probe used this exact sequence:

```text
hash listed/ containing a.json; capture Listings.names()
run: create listed/out.log
user: remove out.log; create out.log with different bytes
report: Listings.wrote(before, ["listed/out.log"])
apply an unrelated revision; compute production checkKey again
```

Actual output was `{"scenario":"replace-before-report","names":["a.json","out.log"],"keysEqual":true}`. The assertion that the keys must differ failed. This is an ordinary replacement with a different inode and content, not a timestamp-collision theory. The committed replacement test changes the entry only **after** `Listings.wrote`, so it does not cover this order.

**One-worker repair:** compare the entry at report time with evidence from the run's successful creation/write, and keep the name when that evidence is missing or no longer matches. Do not establish or renew ownership from a report-time stat alone. Add replacement-before-report and overlapping-report cases alongside the passing replacement-after-report case. A key-format raise alone cannot fix collisions between two candidate runs.

## Should-fix

### S1. Proven: deleted whole directories keep their names, and the row has no size bound

Locations: `src/core/keys/observed.ts:412`; `src/core/keys/run-written.ts:38`, `:69`.

Deleting one held name from a readable directory reaches `visible` and drops it. Deleting the whole directory takes the `readdirSync` catch and returns before `visible`, so none of its held names are dropped. The cheap probe recorded one output, wrote the row, removed its whole directory, called `apply([])` and `write()`, and still read `{"listed":["run.log\\0<stamp>"]}` from the row. Its expected-empty assertion failed. A restart does not sweep those entries either.

There is also no entry or byte bound. Fresh retained log names accumulate for the worktree's lifetime. Every listing check stats each held present name, and each changed write sorts and rewrites the whole JSON row. Deleted or no-longer-listed directories can add historical state to that cost. Removing a worktree does remove the row correctly; that is a separate passing control.

**One-worker follow-up:** prune the row when a listed directory is gone, persist pruning through an appropriate write boundary, and choose a conservative entry/byte budget. When the budget is exceeded, count uncertain names rather than hiding them. Cover whole-directory deletion, restart, obsolete directory records and a long fresh-name sequence. No measured latency regression is claimed here.

### S2. Proven by source: run-start snapshots retain ended runs while any run stays in flight

Location: `src/core/scheduler/keying.ts:965` to `:978`.

Each `beginRun` copies the map of all hashed directories. `endRun` decrements only a count. No completed run's entry leaves `#namesAtRun`; the map clears only at a later `beginRun` that finds zero runs in flight. With a long run beside many short runs, retained snapshots grow with all runs begun during that overlap, rather than the number still in flight. Even an idle end retains the last batch until another run starts. Each snapshot also holds old directory-name sets alive.

**One-worker follow-up:** release the snapshot for the specific run when its report or cancellation no longer needs it. Carry the run number through cleanup. Bound the map by live runs and verify a held long run beside many completed short runs. This is a retained-state defect; no out-of-memory failure was reproduced.
