## Closed findings

### B1: component order in tracked symlinks

`src/core/commit/held.ts` now expands each symlink before consuming subsequent components. `..` pops the resolved prefix; it cannot erase an unresolved missing component, regular file or loop. Leaving the repository, absolute or empty targets, non-folder intermediate components and more than 40 link hops return false.

The original probe now returns:

```text

dangling-via-dotdot/file.txt: held false; disk ENOENT
file-via-dotdot/file.txt: held false; disk ENOTDIR

```

The shared `heldAt` interface is unchanged. Proof and the commit daemon still use that one rule. The expanded held tests pass, including valid in-tree parent traversal, ordinary directory links and the existing refusals. No separate proof or status exemption was added.

### B2: narrowed source-file waits after wide asks

`joinedCommit` identifies named source paths from the commit rows. Once setup is ready, `joinCommit` asks the commit daemon's read-only sync for their readers, within `askBy`. Those readers filter both retained asks and pending rows, feed the final source report, and determine the deduplicated wait refs. It queues no new ask.

The original source-file probe now calls the commit wait, observes completion and returns 0. Its report joins one file and no longer says nothing is queued while that file runs. The new regression also leaves the unrelated reader in the separate rest count and waits for only the named source's reader. Existing recorded-request and deadline tests pass.

The worker's deliberate scope rule is retained: a named source folder selects no readers through the exact reverse-index lookup. It can still select test files beneath that folder by path. The regression records this choice; this repair does not add recursive source-folder reader selection.

### B3: actual group and project limits in estimates

`workGroups` reads each side's own policy. The estimate applies `maxParallel`, gated tier size, low-priority width beside normal work and workers per file. The pool read now carries the configured repository project cap into both own demands. An unreadable tree's group limits are marked unknown.

The original real-scheduler probe now gives:

```text

poolWidth: 4
estimate: { files: 12, width: 1, seconds: 120, basis: "durations", known: 12 }
```

The call-level regression also passes through the report JSON: twelve ten-second serial files estimate 120 seconds times the load factor, with width 1. Tests cover multiple groups, workers per file and a shared group slot. The capped-project assertion returns `[1, 1]`; the separate uncapped control has the portability defect in T1.

Shared `maxParallel` arithmetic deliberately includes both sides' remaining work. It can err long for the side that finishes first. It does not observe every other worktree's shared-slot backlog. These are estimates from known work, not measured completion guarantees. The scheduler and D4.5 selection did not change.
