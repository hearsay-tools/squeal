## Blockers

### B1. Proven: normalizing a link target before resolving its components admits outside inputs

Location: `src/core/commit/held.ts:113`. Both `src/core/daemon/commit-start.ts:79` and `src/cli/status-at-run-select.ts:164` use this rule.

D4.9 says: "A file whose closure reads a path git does not hold reads `not comparable (needs <path>)` and is not run." V1 also explicitly requires refusal of links outside the repository, dangling links and loops.

`posix.join` and `posix.normalize` remove `component/..` before `holds` can inspect whether `component` is another link, a missing folder, or a regular file. Filesystem traversal must resolve that component first.

Reproduction in a temporary parent folder:

1. Track `repo/folder/held/file.txt` with `commit content`.
2. Track `repo/folder/bridge -> ../../outside` and `repo/outside-via-dotdot -> folder/bridge/../held`.
3. Create the outside folders `outside` and `held`, beside `repo`. Put `outside content` in the latter's `file.txt`.
4. Read `repo/outside-via-dotdot/file.txt` and ask `heldAt(repo, "HEAD").has("outside-via-dotdot/file.txt")`.

Actual results:

```text
disk: outside content
held: true
needsOf for that recorded read: null
```

The resolver instead reaches the tracked `folder/held/file.txt`. It certifies bytes that the filesystem does not read. This removes the refusal in both proof and status, and can admit a result whose outside input is not the commit's.

Three further targets, with tracked `held/file.txt`, also returned true: `gone/../held`, `regular/../held` where `regular` is a file, and `loop/../held` where `loop -> loop`. Actual reads failed with `ENOENT`, `ENOTDIR` and `ELOOP` respectively. Existing tests cover direct forms, but no intervening component followed by `..`.

**Worker-sized fix:** resolve components in filesystem order against git objects. Preserve unresolved `..` until preceding links have been expanded; verify directory traversal and reject a repository escape at the point it occurs. Keep the one shared rule for daemon and proof. Add all four cases beside the existing normal directory-link case.

### B2. Proven: a narrowed source-path wait drops its still-running reader

Locations: `src/cli/status-at-commit-ask.ts:109` and `src/cli/status-at-call-sides.ts:146`.

V4 requires a narrowed wait to wait for its own files. D7.3 says `--wait` "joins work already queued". The review brief explicitly excludes a done report while a named file still runs.

`narrowed` gets readers only from the retained asks' `readers[path]`. A prior wide ask named no path, so that map is empty. The pending-row fallback also filters only by test path. Neither discovers readers of a source path first named by the wait.

Reproduction with the existing status fixture:

1. One test imports `src/a.ts`; HEAD changes that source.
2. A wide `--run` queues the test at the commit. Its kept ask has the test in `files` and an empty `readers` map, as a real wide ask does.
3. Give the working-tree side a pass. Keep the commit row `running`.
4. Call `status --at <base> src/a.ts --wait 5000`.

The daemon's wait port was never called. The same report contained:

```text
test/a.test.ts: no result (running) -> pass (now: run in this worktree)
--wait: nothing is queued or running for these files at <base> or in the working tree
```

The command returned 3 immediately. JSON likewise counts zero joined commit files. With only the base version of `status-at-commit-ask.ts`, the same probe calls the commit wait, observes the test complete, and returns 0. This is a regression introduced by narrowing the retained asks.

**Worker-sized fix:** obtain the current named paths' readers from the commit daemon's index without queueing work. Use those refs for pending-row selection, the wait and report counts. Do not depend on what an earlier caller happened to name. Test source-file and source-folder waits after a wide ask, with unrelated queued files still pending.

### B3. Proven: the new estimate still ignores the daemon's actual concurrency limits

Locations: `src/cli/status-at-estimate.ts:75`, `:89` and `src/cli/status-at-call-run.ts:154`.

V2 requires the estimate to use "the real parallel limit the daemon applies". The new width uses only host slots and synthetic file-count demands. It never applies the files' group limits. It also discards the two own marks, including their project caps, then recreates them without `project`.

A real-scheduler probe used `heldSide` with eight host slots and a manual browser group with `maxParallel: 1`. Twelve queued files had ten-second durations. The scheduler ran one file, held by the fixture's gate. The estimate's two synthetic sides each wanted twelve files:

```text
groupMaxParallel: 1
actualRunningFiles: 1
estimatedWidth: 4
estimate: { files: 12, width: 4, seconds: 30, basis: "durations", known: 12 }
```

The group's serial stored-duration estimate is 120 s, before any contention. Increasing host slots widens the error without changing the group's one-file limit. The report presents the 30 s value without an uncertainty warning.

A separate config/mark probe set `capacity.hostSlots: 8` and a one-slot project cap. Both own marks carried that project. `resolveCapacity` returned `projectSlots: 1`, but `readPoolView` plus `widthsOf` returned `[4, 4]`. For 100 ten-second files the estimate was 250 s, although the project's pool permits cannot supply that assumed four-worker width.

**Worker-sized fix:** preserve the own daemons' capacity metadata and estimate work by the actual runner/group limits and shared group slots, per side. If a limit is not known, label the estimate uncertain instead of asserting this width. Extend the arithmetic tests with a serial group, multiple groups and a shared project cap. No scheduler behavior change is needed.

### B4. Proven: a narrowed wait can report another caller's selection count as its own

Locations: `src/cli/status-at-report-scope.ts:42` and `src/cli/status-at-call.ts:120`.

V8 requires the summary to say what this comparison covers and what "the change selects". D7.1 shares a commit daemon across every worktree and caller. Those callers can have different HEADs and diffs against the same commit.

For `--wait`, the call reads every kept ask. `selectsOf` simply takes the newest count, with no link to this caller's diff. It then renders that count as a fact about this call and its suggested command.

The four-test fixture had one test reading `src/a.ts` and three reading `src/b.ts`. This caller's HEAD changed only `src/a.ts`. The stand-in returned the valid kept-ask sequence of a shared daemon: this caller's selection count 1, then another worktree's selection count 4 for a diff that changes both sources. A narrowed `--wait test/a.test.ts --json` returned:

```json
"scope": { "paths": ["test/a.test.ts"], "files": 1, "selects": 4 }
```

The expectation of 1 failed with `expected 4 to be 1`. Text uses the same field and says "the change selects 4 test files". A later edit in the same worktree can cause the same problem without a second caller. The new test supplies only one constant count, so it cannot detect this mix-up.

**Worker-sized fix:** have the daemon count the current call's diff in a read-only query, or retain enough request identity to prove the count applies. A count with no matching identity must remain `null`, using the existing uncertainty text. Test two callers with different diffs and a later wait after HEAD changes. Keep `--wait` free of new run requests.

The real-scheduler test proves the next two tiers run the named folder's files. An unnamed call sends no `lead`.
- V4 counts a directly named test file separately from the remaining queue and preserves the scope in JSON. B2 concerns reader discovery, not that direct-path case.
- V2 handles equal-duration arithmetic, other daemons' host-pool shares, a load factor, missing durations and the explicit `a guess`/`time unknown` forms. B3 concerns missing effective limits.
- V6's two sides use the same `queuedSide` rule. A failed setup is excluded from that side's running count, and the opposite side's genuinely pending files receive the failure annotation. When both fail, each has its own setup line and neither contributes a running count. The new integration test covers commit-side failure with working-tree work pending; the mirror and both-failed forms were inspected, not independently run.
- V8's normal `--run` reads its own ask, and narrowed summaries name the file scope. JSON fields are additive, including `scope`, `run.paths`, rest counts, estimates and setup `elsewhere` counts. B2 and B4 identify incorrect values in otherwise additive fields.
- Existing changed tests discriminate the ordinary cases they describe. Their red-without-change claims in the worker notes were not all independently replayed. The independent base control for B2 did distinguish this regression.
