## Proven blocker

### B2 remains: recovery counts project identities, but the suggested worktree request expands paths

**Proven.** `src/cli/status-at-idle.ts:65` and `:73`; the request it describes uses `src/cli/status-at-call-sides.ts:82`. The false sentence is rendered by `src/cli/status-at-report-join.ts:45`.

The original B2 requires the recovery promise to match what its suggested `--run` queues. The repair fixes the original two-distinct-path case, but its new exact count uses a different selection unit from the real working-tree request.

`idleOf` builds `chosen` from `testFileId`, which includes project and path. Its `nowRuns` requires that exact identity. `queueBoth` instead takes every missing working-tree ref whose **path** appears in the commit selection. A test path listed by two projects can therefore queue both projects when the commit selects only one.

Reproduction through the CLI fixture and the real `choose()` function:

1. List `test/shared.test.ts` in projects `a` and `b`. Each project has a result at the commit and no working-tree result. Their commit closures can select only project `a` for the changed source path.
2. Run a wide `--run`. `choose()` returns `withResult: [{ project: "a", path: "test/shared.test.ts" }]`; its missing-file list is empty.
3. Join with wide `--wait`. The kept ask has the same change, no named paths and `allMissing: false`, so the repair accepts it as count evidence.
4. JSON reports `run.idle.now: 2` and `run.idle.queues.now: 1`. Text promises: `queues 1 of them; it does not select the other 1`.
5. Run the suggested wide `--run` again. The worktree request's wait set contains **both** project refs. The probe checked that project `b` was present and that the two unique requested identities totaled 2 before asserting that the reported count matched.

The probe failed at the final assertion: `expected 1 to be 2`. It did not fail on setup, selection or the actual request. This is the same recovery-truthfulness boundary as the prior B2, exposed by the repair's project-sensitive count.

**One-worker fix:** make the working-tree recovery count follow `queueBoth`'s path expansion over current-side refs. Keep the commit-side count project-sensitive. Prefer sharing the selection rule so the report and request cannot diverge. Preserve the same-change, same-paths, `allMissing: false` and older-daemon uncertainty checks. Do not change scheduling or broaden the commit selection to repair a report count.

**Required regression:** two projects share a test path; only one commit ref is selected; both current refs lack results. Execute the suggested command and compare its requested ref set with the promised count in text and JSON. Also cover a sibling that already has a current result: it must not be counted or queued. Retain the existing distinct-path and reverse-side tests.
