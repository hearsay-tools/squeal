## Blockers

### B1. Proven: the folder exemption admits a stored green pass from a different listing

Locations: `src/cli/proof-green.ts:159` and `:163`; the matching daemon rule is `src/core/daemon/commit-start.ts:88`.

D2 requires exact keys at the committed code version. D4.9 refuses an input git does not hold. D5.1 says the green side is never the current worktree's result. A tracked descendant proves that a folder exists; it does not prove its listing is the committed listing.

The new `held` filter drops every recorded folder with any committed descendant before D4.9 examines it. The daemon makes the same unconditional exemption. `Listings.hashOf` in `src/core/keys/observed.ts:330` hashes a tracked folder from tracked names. It omits ignored names. This older key limitation is material because the new exemption removes the refusal at this boundary.

Reproduction, using the existing fixture and `runGateFiles` helpers:

1. Base tracks `src/a.ts` exporting `value = 1`, `.gitignore` containing `node_modules/` and `*.log`, and `test/fixtures/a.json`.
2. HEAD changes `value` to 2 and adds this named test:

   ```ts
   import { readdirSync } from "node:fs";
   import { expect, it } from "vitest";
   import { value } from "../src/a";
   it("value", () => {
     expect(value).toBe(2);
     expect(readdirSync(new URL("./fixtures", import.meta.url)).length).toBe(2);
   });
   ```

3. In the caller only, write ignored `test/fixtures/extra.log`. Run `runGateFiles` for the named test with the normal shared store. It passes and records the folder read. `git status --porcelain` remains empty.
4. `passesAt(f, head, TEST)` returns false in a fresh checkout. The committed folder has one member.
5. Call `prove(f, { files: [TEST.path], base, case: "source" })` with the normal linked install and real in-process commit daemon.

Actual result:

```text
exit: 0
verdict: proven
red: fail, assertion, run
green: pass, store, stored: true, runs: 0
```

The green pass belongs to the caller's two-member folder. Committed HEAD fails. The clean install and whole-checkout check do not detect an ignored member that existed only in the result writer's tree.

Control: retain recorded folders in `greenNeeds` instead of applying the new `held` filter. The same probe returns exit 3, `not comparable`, reason `green side: needs test/fixtures/`. The control also deferred the early ask, but that change cannot explain B1: this case has a stored green result and no pending green ask.

**One-worker repair:** make both folder exemptions conditional on evidence that the listing is covered by the key and matches the commit. Refuse uncertain or extra names in the caller or installed checkout. Keep the clean tracked-folder case working. Do not treat one tracked descendant as sufficient evidence. Add regressions for stored caller results and generated ignored members in a tracked folder, including the root listing.

### B2. Proven: green runs before D5.2 has refused the proof

Locations: `src/cli/proof-green.ts:96` and `:109`, with the guard in `src/cli/proof.ts:198`.

D5.2 says an unchanged named test with unsettled changed files stops the proof: "the proof does not run". The candidate asks every pending green file before calling the body that applies that guard and chooses the case. The persistent daemon can therefore execute a test the proof refuses.

Reproduction:

1. Both commits hold the same named test. It imports `src/a.ts`, writes `ran.marker` beside the test folder when its body runs, and asserts `value === 2`.
2. Base exports 1; HEAD exports 2. An unrelated tracked `docs/info.md` also changes.
3. Keep `inProcessCommitDaemons()` alive across the call. Call `prove` with `source: ["src/a.ts"]`, leaving the docs path unsettled.
4. The proof correctly exits 3 with `changed files not named: docs/info.md` and `report.runs === 0`.
5. Wait for the named file through that same daemon's `wait` port. `ran.marker` exists in its commit worktree.

Actual probe output:

```text
STOP_PROBE 0 ...changed files not named: docs/info.md true
AssertionError: D5.2 says the stopped proof runs nothing:
expected true to be false
```

Control: remove the eager ask and ask only inside `open.run`. The stopped test writes no marker; the probe passes. This control isolates the cause, but moving the ask after red execution is not the proposed final design.

The same ordering also starts green work before a later case-choice usage error. For a red side that passes, the call can report green as not run while its previously queued run continues. The new `proof.test.ts` assertion reads only the report and does not establish that no daemon work ran.

**One-worker repair:** split selection from execution. Apply D5.2 and settle the case first. Ask green only for the admitted files, still before red execution if retaining the approved early order. Report queued, running, or completed green work truthfully when red does not need it. Test a persistent daemon and a real side effect; a zero report count alone is insufficient.

### B3. Proven: the new daemon fingerprint read is outside `--timeout`

Locations: `src/cli/proof.ts:70` and `:301`; reused reader `src/cli/status-at-call.ts:263`. Also inspect the new metadata reads in `src/cli/proof-green.ts:157` and `:158`.

The wave brief requires one deadline over every new daemon step. `greenDaemon` receives no deadline. It awaits `commitAllowlist`, whose `git show <HEAD>:squeal.config.json` has no timeout. This happens before `readyTree` starts enforcing the remaining time. `keptAlive` prevents an early process exit; it does not bound an operation.

Reproduction uses `proofCommand` directly with `timeoutSeconds: 1`, a normal two-commit fixture, and `NO_DAEMONS`. A temporary `git` wrapper delays only the new configuration read:

```sh
if [ "$1" = show ] && [ "${2##*:}" = squeal.config.json ]; then
  sleep 4
fi
exec <real-git> "$@"
```

All other git calls run normally. No test run or daemon setup causes the delay.

```text
BOUND_PROBE 3 4022 1
AssertionError: the daemon fingerprint's git show must share the 1 s bound:
expected 4022.037312 to be less than 3000
```

The call eventually reports budget exhaustion, but it first waits for the entire delayed operation. A stuck read can hold it indefinitely. The new `greenNeeds` path also performs three git tree reads through helpers with independent 30-second limits. Those reads do not receive the remaining proof budget; that second route was read in source, not separately timed.

**One-worker repair:** pass the original deadline into fingerprint preparation and the new folder checks. Bound each subprocess by the remaining time and stop when none remains. A timed-out allowlist read must yield a budget answer, not silently become an empty allowlist and a different daemon fingerprint. Add coverage for the fingerprint read and post-setup tree reads, alongside the existing held-install test.

## Nonblocking note

### N1. Plausible: asking first does not establish that green finishes or records inputs first

Location: `src/cli/proof-green-run.ts:122`.

The early ask can remain useful after B2's guard. It is not an execution barrier. Green and red use different execution paths and can contend for permits. `sideOf` accepts any records at the live key before it examines `row.pending`. If row 023-47 leaves a red record at a shared pre-run key while green is still pending, ordering the asks alone does not establish the record's origin.

No delayed-green reproduction of that interleaving was run. This is not another blocker or a claim that ordinary valid-key reuse is wrong. Preserve the known gate defect as a separate row. Do not describe early queue order as a general proof against that defect; test a delayed green run if the fix relies on it.
