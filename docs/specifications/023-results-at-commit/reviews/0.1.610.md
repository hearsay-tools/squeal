## Blockers

### B1. Proven: a named wait falsely says it released a manual group's file

Locations: `src/core/state/groups.ts:154` and `:157`; `src/core/state/group-text.ts:73` and `:182`; `src/cli/status-wait-groups.ts:58`.

The vision requires status to distinguish queued work from work still held. Row 023-67 must report an actual run request. Membership in a published promotion batch does not prove that request occurred. A plain named `status --wait` also makes a batch through `promoteRequest`, which changes queue order but does not release a manual group's lane.

Reproduction uses the real scheduler, store, header reader and production text formatters:

1. Start `heldSide` with one `test/browser/a.test.ts`, owned by a `manual` browser group. Write that same group policy for the header reader.
2. Edit its imported `src/a.ts`. The file is pending and held. The runner has zero calls.
3. Call `scheduler.promote([ref], 60000)`, the named wait's operation. Wait for the scheduler's rest. The runner still has zero calls.
4. Read `readHeader`, `groupTierLines` and `groupsQuietText`.

The header invents `requested: 1`. The group line says:

```text
browser: 1 test file; 1 queued by a request (`squeal status --at <commit> --run` or `squeal run browser <path>...`). Squeal runs them now; `squeal run browser --wait 60000` waits for its result.
```

The wait text also says `a request queued the pending ones: Squeal runs it now`. No such run request was sent. The file remains held. The suggested command would actually release it, but the new text describes that command as only waiting. An agent can keep joining work that will never start.

The probe fails at the assertion rejecting `Squeal runs them now`, after checking the zero runner calls. In the control, only `groups.ts` comes from the range's base. The same probe passes and both formatters retain `only on request`. The candidate's normal tests publish synthetic promotion rows as if every batch were a run request; they do not test this real scheduler distinction.

**One-worker fix:** publish evidence of an actual lane release or narrow run ask, tied to its file and key. Derive `requested` from that evidence. A named wait's promotion alone must not count. Do not make a plain wait run a manual group to make the sentence true. Keep the new text for actual `--at --run` and narrow group requests, including partial groups and live-daemon filtering.

**Required regression:** use a real scheduler to compare a manual file after a named wait with the same file after an actual narrow run request. Test the hook JSON, plain status and `status --wait` through their real formatters. Only the second case may say a request queued it and it runs now.
