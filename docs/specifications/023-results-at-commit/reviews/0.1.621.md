## Blockers

### B1. Proven: an earlier queued snapshot makes a current-key run read as stale

Location: `src/cli/status-at-estimate-stale.ts:39` to `:46`; caller `src/cli/status-at-call-run.ts:173`.

Row 023-84 requires: “a run at the current key reads as today.” The new reader does not read the current key row. It treats membership in its `queued` argument, plus any open run of that file, as proof that the run started before its inputs changed.

Those facts come from different reads. `readAfter` saves the per-file state before `queuedRun` calls `sideWaits`, which opens the store again. The daemon can start the queued file at its unchanged current key between those reads. The file is then running at the current key, but the earlier queued list still names it. The run start's transaction cannot make these separate reader snapshots atomic.

The independent probe uses the queued-waits fixture and production `sideWaits`. It retains the call's queued list, starts a run of `B1`, and writes its same key row as `pending: "running"`. It verifies that row before calling the reader. No input or key changes. The reader returns:

```text
the commit worktree's run of test/b1.test.ts to end:
that run started before its inputs changed (running for 0 s),
so its result will not count, and the file runs again after it
```

This is a false statement about a valid run. The committed current-key control does not cover the seam: it supplies `running` before the report's first read, so the file never enters `queued`.

**One-worker repair:** establish the queued key row, matching lane activity and open run from one consistent store read before making the stale claim. Reject the claim when the current row is running or has settled. Keep the existing text when staleness is proved. Add the queued-snapshot-to-current-run case through the report path, plus a real K-to-K-prime run control. Do not compare run revision alone: unrelated edits can move it without changing this file's key.

### B2. Proven: the new text says a free group slot is in use

Location: `src/core/state/slow-text.ts:37` to `:40`; group caller `src/core/state/group-text.ts:111`; retry callers `src/core/retry/text.ts:119` and `:158`.

The vision requires an honest snapshot. `slot: "held"` records what the scheduler found at its last attempt. The formatter turns that observation into the present claim `(in use)`. The other process can release the permit before this daemon's next recheck. The waiting daemon remains live, so the output does not say “last reported”.

The independent probe reuses the two real schedulers from `slot-pairs.test.ts`, with one permit and a 30 s recheck. The commit side holds `a`; the tree asks for `a,b,c` and publishes `slot: "held"`. Release `a`. The commit side yields and publishes `slot: "turn"`. Before the tree rechecks:

```text
heldPermits({ group: "browser", permits: 1, ... }) = []
browser: 3 test files; 3 pending,
waiting for the browser group's slot (in use).
```

The probe verifies the free permit through production `heldPermits`, then passes the tree's actual published activity to production `groupTierText`. Its assertion against `(in use)` fails. The same shared helper supplies retry and hook text. With the default recheck this gap can last 15 s. It also occurs if the holder exits.

**One-worker repair:** keep the exact slot-versus-pool distinction, but word `held` as the last observed refusal, or omit `(in use)`. A present-tense occupancy claim requires a live permit read. Do not restore the old slot-or-pool hedge for new daemons. Keep that hedge for older daemons without `slot`.
