## Blockers

### B1. Proven: a foreign folder result arriving after selection bypasses the refusal

Locations: `src/core/daemon/at-asks.ts:305`, `:310`, `:321`; `src/core/daemon/commit-start.ts:101`; `src/cli/status-at-commit-rows.ts:116`.

Row 023-70 requires: “a stored result must pass D4.9 before the commit side uses it.” The accepted decision permits a folder read only for a result the commit worktree wrote. The new check covers only results already present when `choose` builds `stored`. A result can arrive later while the selected file waits on another worktree's claim or the group's slot. The scheduler can inherit that result. The report reads it through `resultsAt`, with only the refusals captured by the earlier ask. Nothing checks the arriving result's writer.

The independent probe uses two real daemons, the real store, a manual group with one shared slot, and the production status command:

1. Commit A has `test/fixtures/a.json`. Its test lists that folder and expects two names. A pristine A has one name and fails this assertion.
2. Commit B adds only an unrelated tracked file. The test and its inputs are unchanged. A previous observed-read record names `test/fixtures/`; neither current key has a result yet. This is a normal state after an earlier run at a different key.
3. The caller at B has an ignored `test/fixtures/extra.log`. Start its narrow run first. The test waits 15 s before its assertion, so its claim and group slot stay held.
4. During that run, call `status --at A test/lists.test.ts --run`. The probe confirms the commit ask reached `queued` while its key still had zero stored results. The commit folder itself matches the tracked listing, so the initial run refusal permits it.
5. The caller's pass arrives. The commit side reads that foreign pass at the shared key.

Actual command result, with fixture identifiers omitted:

```json
{
  "exit": 0,
  "selectedBeforeResult": true,
  "at": { "state": "pass", "origin": { "kind": "own" } },
  "now": { "state": "pass", "origin": { "kind": "own" } },
  "counts": { "pass -> fail": 0, "fail -> pass": 0, "unchanged": 1, "unknown": 0 }
}
```

The probe fails on `expected 'pass' to be 'not comparable'`. It first confirms that selection preceded the stored result and that the caller passed. The commit and caller read exactly the same key. This is a false comparison, not merely a stale queued label.

The candidate's new stored-result test passes. It seeds the result before making the ask, so it cannot catch this ordering.

**One-worker fix:** make result admissibility apply when the commit side accepts or reads the result, including a result that arrives after selection. Use that result's provenance and the commit daemon's closure facts. Keep the accepted refusal for a foreign folder result. Do not certify the foreign run from the commit folder's current names, or treat queue membership as proof that the commit worktree ran it.

**Required regression:** preserve the arrival ordering above. The call must return `not comparable` and exit 3 under the chosen policy. Keep the existing pre-stored foreign-folder refusal, clean stored-result reuse, and own-commit-folder positive controls. Cover a join of an already queued ask as well, since a new request must not be needed to make the read honest.

### B2. Proven: the new full-pool tests use the real CPU ceiling and fail before asking the named file

Location: `test/scheduler/named-slot-wait.test.ts:139` to `:146`.

The row's proof must exercise a named request against a full pool. The wave's done-when includes passing targeted checks. Both new full-pool cases instead fail on an ordinary four-CPU sandbox:

```text
AssertionError: expected 3 to be 8
test/scheduler/named-slot-wait.test.ts:145:63
expect(other.acquire(200, "fast", 1, "backlog")?.grant).toBe(8);
```

The scheduler fixture supplies a synthetic CPU count and disables live host readings. The competing `createPermitPool` supplies only `hostSlots: 8`. Its background ceiling therefore uses the actual CPU count and the default 75% share. Four CPUs admit three background workers. The assertion fails before either named request runs. On a larger host it can pass by accident.

A temporary copy of this test adds only `cpus: 64, host: null` to that competing pool. All three cases then pass, including both full-eight-permit cases. Product code and the original test remain unchanged. This control supports the worker's claim: the named browser file runs despite a full pool, and the shared slot hands over as the existing rule requires. It does not justify the failing candidate test.

**One-worker fix:** give every participant in this pool test the same explicit CPU and host inputs, or fill and verify the pool through another deterministic arrangement. Keep the assertion that the competing background work actually holds every configured permit. Do not weaken it to accept a partially filled pool. Rerun the unchanged committed test on a small host.

### S1. Proven by source: wait codes do not prove the new occupancy claims

Location: `src/cli/status-at-estimate-waits.ts:115` and `:118`. Nonblocking: the source and formatter overclaim are clear; this review did not measure how often an agent sees the transient cases.

The slot text says “which another daemon holds.” `SlowTier.#takeSlot` also publishes the same `for: "slot"` activity when it yields one turn to a marked waiter. In that branch it does not attempt to acquire the slot; the slot can be free. The existing publisher documents both meanings.

The pool text says all N shared permits “are held by other work.” A pool refusal can also come from a project limit or an admission rule. The published activity records only `for: "pool"`, with no occupancy count. The configured slot count cannot prove that all those permits are held.

Use “the browser group's slot” and “capacity from the shared worker pool” unless the publisher also records the claimed holder or occupancy. Keep “time unknown.” This preserves useful reasons without reconstructing facts the daemon did not publish.
