# 023-84 notes: a named file behind its own stale run (round 11, AA4)

Row 023-84, wave 40, 2026-11-24. Brief: `wave-40.md`. Base: main at 0.1.619.

## Cause

Round 11, s1b-03 at 312 s, read: "1 of 1 queued at d8abcfe46, waiting for the browser group's run of packages/web/e2e/thread-scroll.e2e.ts to end". That run was the commit side's own run of the same file. It started at 243 s, at a key the file no longer had (AA1). Its result did not count, and the file ran again from 407 s. The line was true, but it did not say why the wait would not end with that run.

## Change

`staleRunWait` (`src/cli/status-at-estimate-stale.ts`, new) is called from `sideWaits` → `waitOf` (`status-at-estimate-waits.ts`) for each group of a side's queued named files. It returns a wait only when the daemon records all three of these facts:

1. the group's lane publishes `running` with the file among its paths;
2. the store holds a run of the file open (`store.runs.inFlight`);
3. the file's key row reads `queued`. The call passes only files that are queued and not started.

A run at the file's current key marks the row `running` in the same transaction that publishes the activity (`SlowTier`, review wave 2 B1). So a queued row beside an open run of the same file is a run at an older key.

The text, in the per-file line and in the estimate:

`waiting for the commit worktree's run of <path> to end: that run started before its inputs changed (running for 40 s, about 57 s left), so its result will not count, and the file runs again after it`

- The side's name comes from the call's two sides (`the commit worktree`, `the working tree`).
- The time left is the lane's stored duration (`lastDurationMs`) less the time run. It shows only from 1 s up. Without a stored duration, only "running for N s" shows.
- With several such files, the line names them all and says "their inputs" and "the files run again".

## Decisions the brief did not settle

- **The open run is required.** The lane's activity alone can be old news (it is republished only on lane decisions). Without an open run in the store the line reads as before.
- **Paths, not base names**, as 023-77's holder line.
- **"running for N s"** is added beside "about N s left", as in 023-77's holder text, so the time left has its base.
- **Only the call.** The hook and `status` show no per-file wait, so nothing changes there.

## Review 0.1.621 repair

**B1** (review 0.1.621): the stale-run line could call a run at the file's current key stale. The call's `queued` files come from its first read of the store (`readAfter`). `sideWaits` read the lane activity and the open runs later, in another read. The daemon could start the queued file at its current key between the two reads.

- `sideWaits` now reads every fact of every side's wait in one read transaction (`readTransaction`).
- `staleRunWait` reads the named files' key rows again in that transaction. A file reads stale only when its row is `queued` at a key now, its lane publishes a run of it, and the store holds a run of it open.
- Why this proves an older key: the ledger marks a row `running` only while its tier runs the file's current key (`Ledger.#syncPhase`, "a key an edit moved during the run is not running"), in the transaction that starts the tier and publishes the activity. A run records no key of its own, so the row is the record that the two keys differ. The run's revision is not compared (an unrelated edit moves it).
- A row that reads `running`, or settled (no `pending`), is no stale run. The text is unchanged when the run is stale.

Tests (`test/cli/status-at-queued-waits.test.ts`):

- **K to K′**: the run starts with the row at `old-…` `running`, then an edit moves the key (row `queued` at the current key). The line reads the stale text.
- **Race through the report path**: `readMainStore` is wrapped (`vi.mock`). Before the call's wait read, the daemon marks `b1` `running` at its unchanged key. The line no longer says "will not count". Red without the fix: it read the stale text, as the reviewer's probe did.
