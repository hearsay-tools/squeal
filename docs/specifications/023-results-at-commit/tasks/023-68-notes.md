# Row 023-68 (X3) notes: both sides run the selected files in one order

Wave 32, worker A, brief `tasks/wave-32.md`. Spec D7.3; round 8 X3 (`../lessons.md`, "Round 8 (023-63)"). Branch `cez/3f115c68`, base `fbbd232bc`.

## Cause

One `status --at --run` call asks two daemons for the same files: the commit daemon (one ask; `AtAsks`, one request per group) and the working tree's daemon (`status-at-call-sides.ts`: the change's and the named files first, then the commit daemon's selection). Each daemon formed a batch of the request's files, but ordered the batch by its own rules (`RunQueue.orderedBatches` and, for a group's own lane such as `browser`, `sorted`): batch rank, then stored duration (a batch tier: longest first; a lane: shortest first, unknown last), then the order the file was first queued, then path. The two sides differ in all three inputs:

- Stored durations: each side's results become durations the other side reads, so a file one side ran moves in the other side's order.
- Queue order: the working tree's daemon had queued the browser files earlier (a manual group's files wait, "waiting for `squeal run browser`"), the commit daemon queued them at the ask.
- The two sides' requests listed the files in different orders (the commit daemon's rows order; the working tree's own rows order).

In round 8 s1-03 the commit side ran `activity`, `artifact-project-links`, `automations-github`; the working tree `agent-browser-tabs`, `assistant-*`, `automations-disabled`, `chat-code-fence`, `command-palette`. No browser file had both sides in any session.

## Change

- **Scheduler (spec 011 files, brief-owned).** A request with `at` (`NarrowRunOptions.at`, which both sides of a `status --at --run` call already send) forms a batch that keeps the request's order: `Promotions` records each file's place in the request (`places`), `PromotionRank.place` carries it, and `RunQueue` sorts by it right after the batch's rank, before duration and queue order, in batch tiers (`orderedBatches`) and in a group's lane (`sorted`). Other batches (named waits, `squeal run <group> <path>`) keep their order as before. No protocol field: the order is the request's `paths` order, and `at` already reaches the scheduler on both daemons (`narrowOptionsOf`). The doc of `NarrowRunOptions.at` in `src/core/types/scheduler.ts` says so (a comment change only).
- **One order for both sides.** `atOrder` (`src/core/daemon/at-asks.ts`): the files the call names by their own path first, in the call's order, then the others by path and project. The commit daemon's ask queues `atOrder(named, chosen)`; the working tree's side queues its first files and the commit daemon's selection in `atOrder` too (`status-at-call-sides.ts`).

So within one group the two sides start the same files in the same order, within what each group's limits allow.

## Decisions the spec did not settle

- **Path order after the named files.** The brief allows any deterministic order the call sends. Path order needs no data from either side, and both daemons can compute it alone, so no order list travels in the protocol. Longest first (a tier's end waits for its longest file) would need durations both sides read alike, which is the input that made them differ.
- **Only `at` requests keep their order.** Named waits and `squeal run <group> <path>` keep longest first (row 011-268), since only a call that asks both sides gains from one order.

## Limits

- Inside one tier the runner may still reorder files: Squeal sets no Vitest sequencer, so Vitest orders a run's files by its own cache (failed first, then duration, then size), and each worktree has its own cache. When a group runs one file a tier, or both sides form the same tiers, the order holds. For squawk's browser group (`fileParallelism: false`) round 9 will show which.
- The working tree sends two requests (the change's and the named files, then the commit daemon's selection). Each is in `atOrder`, so a file of both lists keeps the first request's place unless the second leads (a narrowed call); then the selection, also named files first, ranks first. The commit side sends one. Across requests the two sides can still differ for files of the first request that are not named (in round 8, the new test file only).
- The order does not make the sides run at the same speed: a side that runs faster still has more results. It only makes the first results of each side the same files.
