## `owner`: gone, the covered-files id replaces it

The brief left the choice open. `owner` (on `NarrowRunOptions` and `RunGroupPathsRequest`) had two uses: the take-back's key and the key of the `at` flag (`AtRunRequests`). With the take-back gone, the key only groups a call's flags for removal, and nothing removes them by key now. The flags end when their files ran or after the hour, whatever the key. So `flagAccepted` keys each accepted request by its covered-files id (a random id when an old scheduler gives none), and `owner` is removed from both types, from the CLI's `NarrowCall` and from the commit daemon's narrow runs (`at-asks.ts`). The commit daemon's own `CommitAskRequest.owner` (the ask's identity for `commit-read`) is a different field and stays.

Compatibility: the parser ignores an `owner` an older CLI still sends (`test/daemon/narrow-lead.test.ts` checks it). A newer CLI sends none; an older daemon then keys by the covered-files id, as it did for a request without one.

Kept as the brief says: `lead`, the `at` flag and the `SQUEAL_RUN_GROUP` token (T3).

## Repair: review 0.1.596 B1

The manual e2e's step 2 and 3 expectations were written without a run, and two were wrong. The product is unchanged; only the test changed.

- `run.again`: a call with a finite wait always names the call that waits again (`queuedRun`, `status-at-call.ts`), even when every file is known. Both calls have a finite wait (300,000 ms given, then the 100,000 ms default), so the test now expects `waitAgain("HEAD~1", paths)` and checks that it ends with the paths and the default wait. It also expects `retry: null`: nothing came back late to queue again. `running: 0` and `known` equal to `files` still say nothing runs.
- Origin: a file whose key changes at the parent has only the commit daemon's result, so its commit-side origin stays `commit`. The unaffected file has the same key on both sides; the shared store answers with whichever valid result it holds, this worktree's (`own`) or the commit daemon's (`commit`). The test now checks the equal key and accepts either origin for that file.

- The commit side's count: the unaffected file shares its key with the working tree, so this worktree's daemon can store it before the commit daemon reads the parent. `commit.files` is then the changed files alone, else every existing file, and `known` equals it either way. One run saw 2 of 3 in the Squeal case; the review's run saw 3.
- The kit's cleanup check (`checkoutsLeft`, `at-commit-kit.ts`) read `commit-places/` as a repository's checkout folder. That folder holds the commit worktree registrations (D7.4). A registration outlives its worktree on purpose: the next count drops one whose folder is gone (review wave-22 B3). The check now reports a registration only when its folder is still there.
- The stop calls print their output in the assertion message. One run's `stop --at <parent>` in the second repository case exited 1 with no text recorded; the later runs passed it.
- Step 2's checks moved to `checkQueued`, which keeps the test body under the complexity limit.

The run on a boat.dev sandbox (both repository cases, through the stops and the back-at-the-parent step) is in the worker's report to the coordinator.
