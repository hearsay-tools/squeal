# Row 023-76 notes: what a run listed in a folder

Wave 36, worker A, brief `tasks/wave-36.md`. Review `reviews/0.1.611-rereview.md` N1. Spec D4.9, D7.3. Branch `cez/7bc99c10`, base `f40b98202`.

## Cause

`Listings.hashOf` (`src/core/keys/observed.ts`) hashed a directory that holds a tracked file by its tracked names only. A run that listed an ignored name there (`extra.log`) and a run that did not got one key. The caller's pass and the commit's failure then shared that key. The store keeps one record per test and key, so the commit's failure replaced the caller's pass, and `status --at` read "fail -> fail, unchanged" (N1). Row 023-70 hid the same gap at the commit side with an own-worktree rule: a folder reader's result counted at the commit only when the commit worktree wrote it.

## Decision: the listing goes in the key

The brief offered two places for the record: in the key, or beside the result with a lookup that refuses a mismatch.

- **In the key (chosen).** `Listings.hashOf` now hashes every name on disk with the tracked names (their union), and reads the names on disk again at each revision (`apply`), as it did before for directories with no tracked file (row 016-24). Two runs that saw different listings get different keys, so neither result replaces the other, and every reader (the daemon's state, `status --at` on both sides, `proof`, `why`) keeps reading by key with no new rule. With equal names on disk, the hash equals the hash of the commit's tree (`namesHash` of the tracked names), so a working-tree result keyed over a clean listing is found at the commit's key.
- **Beside the result (rejected).** The store keeps one row per check and key (`INSERT OR REPLACE`, primary key over check and key). To keep two listings apart, the listing would join that primary key: a schema change, and every reader that pools records by key (`stateOf`) would need a filter. More code, more places to forget.

**Old keys.** A release before this row stored results at keys with tracked names only, also from runs that listed ignored names. A clean commit computes the same tracked-names hash, so it could find such a result. To prevent that, a listing path's key segment carries a mark (`encodeSegment` in `src/core/keys/check-key.ts`, `"names on disk "` before the hash). Every key that holds a listing moves once; a key with no listing keeps its value.

- I did not change `namesHash` itself: the CI hook (`src/runners/ci-runtime/evidence.cjs`) computes the same hash in its own copy, and CI reuse compares the two. A changed `namesHash` broke `test/runners/vitest/ci-evidence*.test.ts`. The segment mark leaves raw listing hashes as they are.
- **No `KEY_FORMAT_VERSION` raise.** The validity alarm asks for a raise only when keys are equal and outputs differ. Here every changed key differs (`verdict.ts`, `outputsEqual` is true when keys differ), and the mark makes sure no key of this release equals an earlier one that holds a listing. Tests that read no folder keep their keys and results (`test/keys/check-key.test.ts` checks this against the earlier encoding).
- **Cost of the re-key.** In this repository's store, 236 of 1,538 test files list a folder; each runs once again after the release. In the main checkout, 3 of 610 listed directories hold ignored names now (`.tmp` in three fixture folders); their readers stop sharing results with a clean commit, which is the point.
- **Cost per revision.** `apply` now reads every listed directory on disk at each revision, not only the ones with no tracked file. 610 directories took 5.5 to 6.7 ms here.

## The relaxed commit rule (row 023-70)

With the listing in the key, a result at the commit's key ran over the same names the commit worktree has on disk. The commit worktree's own listing must equal the commit's tracked names, or the file is refused by D4.9 (`needs`, row 023-64, unchanged). So a result at the commit's key counts at the commit whoever wrote it. I removed the own-worktree rule completely:

- `src/core/daemon/at-asks.ts`: `listings` and `ownResult` ports, the folder part of `storedRefusals`, `ownOnly`, `storedReason`.
- `src/core/daemon/commit-start.ts`: the two ports.
- `src/cli/status-at-commit-rows.ts` and `src/cli/proof-green-run.ts`: the `ownOnly` filters. Proof keeps its own rule for `runs: 1` (a queued file counts as this command's run only when the commit worktree wrote it).

CI imports. Row 023-70 also refused imported results of folder readers. An import is keyed by the commit tree's names (`transfer-rekey.ts`), but CI reuse admits it only when its evidence certifies each input (018 D9, D33). For a listing, the hook's read-time evidence is the hash of the names the run listed, compared with the commit tree's hash. So an imported result at the commit's key also ran over the commit's names; I do not refuse it. A reviewer may want to confirm that certification covers every listing path an import carries.
