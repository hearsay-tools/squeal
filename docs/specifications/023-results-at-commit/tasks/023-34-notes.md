## What each item does

- **T5.** `status --at … --wait` prints one line and exits 2: `squeal status: --at takes no --wait; --run waits up to --timeout (300 s)`. `parseAt` returns `AT_NO_WAIT`; `main.ts` prints it without the help.
- **T4.** The commit side runs first, so before the working tree's turn the call knows which selected files the gate ran and did not keep (`unkept`, `status-at-run-unkept.ts`). The working tree runs those files through the gate in a child, never through the daemon: the daemon's answer gives no outcome for a file it does not keep. The gate's answer gives the outcome (`unkeptNow`), and the working tree's side reads it when the store has no result (`withUnkept`). Both sides then read `pass -> pass (this run, not stored)`. Nothing is stored. Files the daemon ran and did not keep go through the gate once in the last pass. The gate path moved to `status-at-run-now-gate.ts`.
- **T1, cannot fit.** Without `--timeout` and without `--all-missing` (`RunArgs.fitCheck`), the commit side's selection is checked before it runs (`clearlyOver`, `status-at-run-fit.ts`). The check fails in two cases. Case 1: R4's estimate is above the 600 s cap. Case 2: no file has a stored duration, and the files are more than `width × floor(budget / 20 s)` (`roundsHold`; 165 at width 11 and 300 s). In both cases neither side runs. The report gives the rule, R4's line and the forcing call (`--timeout <budget>`). The coordinator chose this rule.
- **T1, take-back.** Each narrow run records the files it queued itself under its covered-files id (`TakeBacks`, `src/core/scheduler/take-back.ts`). Files already queued or running are not recorded. The request's own promotion is recorded too. At the call's end, its daemon files first get the rest of the budget (`giveBack`, `status-at-run-give-back.ts`). Then `take-back {coveredIds}` takes out every recorded file that has not started. Four kinds of file stay: a running file, a forced file, a file an edit queued again (recent), and a file another promotion holds (`Promotions.heldElsewhere`). The report gives three counts: taken back, still running, and kept queued. An older daemon answers "unknown request type"; the report then keeps today's line "their runs go on in the daemon".

## Known limits

- **Two cases where later named files do not run first.** After a take-back, an earlier call leaves nothing queued, except in two cases. (1) The one tier that was running at the take-back: by the coordinator's choice it is not cancelled, so a narrowed call can wait for it to end. (2) An earlier call that still runs at the same time, for example a call the harness moved to the background. The later call's batch then ranks after the earlier one, because batches rank by request order. The fix is a later row (the coordinator, 2026-11-21): a narrow run of test files the caller named ranks first (`promotions.ts`, `narrow-run.ts`).
- **A request the daemon had not taken by the deadline** has no covered-files id, so it cannot be taken back. Its files can still be queued after the call ends.
- **The cannot-fit check** reads the commit side's selection only. When the commit side has all its results and the working tree lacks many, the working tree's files go to the daemon, and the take-back at the end limits them.
