# Row 023-67 (X2) notes: the hook names files that an `--at --run` queued

Wave 32, worker B, brief `tasks/wave-32.md`. Spec D7.3; round 8 X2 (`../lessons.md`, "Round 8 (023-63)"). Branch `cez/a2cf10c6`, base `fbbd232bc`.

## Cause

A group at `manual` (or `commit`) keeps its files queued but held: they run only when a request asks for them (`heldUntilAsked`). The group line (`src/core/state/group-text.ts`) read only the store's pending rows and the group's activity. With no activity yet, every pending file read as "waiting for `squeal run browser`. Squeal runs them only on request", also after `status --at … --run` had asked for them. Which files a request asked for lived only in the daemon's memory (the lane's asks).

## What the store already holds

A narrow request (`squeal status --at <c> --run` on the working-tree side, `squeal run <group> <path>...`) puts its selected files in a batch (`promoteNarrow`). The live daemon publishes its batches in the `promotions` meta row (`publishPromotions`), and a batch lives until its files settle. `publishedBatches` reads it, and drops a row written before the live daemon started. So the hook can tell a requested file from a held one without a new write: a queued file of a held group in a published batch was asked for.

## Change

- `GroupTierState.requested?` (additive): at `commit` and `manual`, the pending files in a batch the live daemon published. `groupTiersOf` (`src/core/state/groups.ts`) reads it once per header.
- The group line (`group-text.ts`):
  - all pending files requested: `browser: 97 test files; 97 queued by a request (`squeal status --at <commit> --run` or `squeal run browser <path>...`). Squeal runs them now; `squeal run browser --wait 60000` waits for their results.`
  - some: `…; 2 queued by a request (…), 1 pending, waiting for `squeal run browser`. Squeal runs the requested ones now, the other pending ones only on request; …`
  - none: as before.
  - While a file of the group runs, the daemon publishes the group's activity, and the line reads as before (`pendingText`).
- The hook (`src/core/delivery/slow-told.ts`): `groupKind` gains `"queued"`, so a group last told as waiting for `squeal run` is told again when a request queues it. A delivery title reads "browser group queued".

## Decisions the spec did not settle

- **The commit is not named.** The brief's example is "97 queued by `squeal status --at <short commit> --run`". The daemon's batch row does not say which request made it, and naming the commit needs a new write: the call writing a meta row (the store is read-only in the call today), or the daemon keeping the request's origin in its batch row (scheduler, worker A). The line names both requests that queue such files instead. If round 9 shows agents need the commit, that is a follow-up row.
- **`squeal status --wait` text.** `src/cli/status-wait-groups.ts` (not in this row's ownership) still words a held group "Squeal runs them only on request"; its run text comes from `groupRunText`, which now says "waits for" when every open file is requested. Not changed.
- **A named wait on a manual file.** A plain `squeal status --wait <path>` also forms a batch. If it names a manual group's file, the line now says "queued by a request" although that wait does not run it. Not seen in any round; left.

## Review 0.1.610 repair (B1)

**Cause.** `requested` counted a queued file of a held group in any published batch (`publishedBatches`). A plain named wait (`squeal status --wait <path>`, `Scheduler.promote`) also forms a batch, which orders the queue but releases no file of a `manual` or `commit` group. So after a named wait the line said "1 queued by a request … Squeal runs them now" while the file stayed held. This was the case the first notes left ("A named wait on a manual file").

**Evidence now.** A narrow request (`squeal run <group> <path>...`, and `squeal status --at <c> --run` on the working-tree side, which sends the same `run-group-paths` request) adds asks to its group's lane (`SlowTier.narrow`, a `CommitAsks`), each at the file's key. That ask is what releases the file (`#trigger`). The scheduler now publishes those asks:

- `src/core/scheduler/narrow-asks-row.ts` (new): the `narrow-asks:<worktree>` meta row, `{ at, asks: [[testFileId, key], ...] }`; an empty list drops the row. `publishedNarrowAsks` takes no row older than the live daemon's start. The row is registered in `WORKTREE_META_ROWS` (`src/core/types/store.ts`, one line, coordinator agreed in request 9dfd6256), so `WorktreeRepo.remove` drops it with the worktree (covered by `test/store/worktree-meta.test.ts`, which iterates every entry).
- `CommitAsks` takes an optional change callback; `add`, `prune` and the new `clear` call it only when an ask came or left. A lane's `narrow` set calls `LaneLoop.narrowChanged`, and the scheduler writes every lane's narrow asks (`GroupTiers.narrowAsks`), stamped like the promotions row (`CalendarSteps.stamp`).
- A re-key or an end drops the ask from the row at the next ledger commit: `ledger.ends.committed` now also calls `GroupTiers.pruneNarrow`. Before, a busy lane pruned only at its next decision, so a re-keyed queued file kept its old ask in the row while the lane ran another file. A retired lane clears its asks.
- `requestedOf` (`src/core/state/groups.ts`) counts a pending file only when the row holds its `testFileId` at its current key. A named wait's batch counts for nothing. Text (`group-text.ts`, `status-wait-groups.ts`, delivery) is unchanged: it reads `requested`.

A plain wait still runs no manual file (asserted: zero runner calls).

## Tests (repair)

- `test/status/group-requested-scheduler.test.ts` (new), the reviewer's regression on a real scheduler: one `manual` browser file, edited and held. (1) After `promote` (a named wait), zero runner calls; plain status (`createStatusBuilder` + `formatStatus`), the PostToolBatch hook (`createDelivery` + `formatDelta` + `additionalContext`, read back from its JSON) and `status --wait` (`groupsQuietText`) all say it waits for `squeal run browser` and "only on request", and none says "queued by a request", "a request queued" or "runs … now". Then a narrow run request for the same file (already in the wait's batch) runs it, and the texts say "Squeal runs them now" and the hook's title "browser group queued". (2) A narrow run request alone: the same "runs now" texts. Red without the change: case (1) fails at the plain status line (the batch read as a request).
- `test/scheduler/narrow-asks-row.test.ts` (new): a named wait publishes no ask; a narrow request for two files publishes both at their keys; an edit that re-keys the queued one drops its ask while the running one's stays; the row is gone when the run ends. Red without the commit-time prune (the re-keyed ask stayed).
- `test/status/group-requested.test.ts`, `test/delivery/group-requested.test.ts`: seed the asks row instead of a batch. New case: a named wait's batch alone, and an ask at a key the file left, read as waiting. Red without the change.

The line names a request as "queued by a request" only while a requested file is queued with no group activity. Once the lane runs it, the line shows the run, and the second sentence says "Squeal runs them now". In the real scheduler the queued-and-asked state is short (the narrow request wakes the lane), so the regression checks the "runs now" sentences, not the "queued by a request" clause.
