# Row 023-39 notes: the daemon's commit mode (D7.2)

## Where it lives

- `src/core/daemon/commit-mode.ts`: the rules. `commitModeOf` decides the mode, `commitPolicy` gives the policy, `commitCheck` is the idle and cap check, `removesAtExit` says which exits remove the worktree, and `NO_WATCH`, `NO_CODE_PASS` and `COMMIT_FEED_TIMINGS` are what the daemon uses in place of the watcher, the code pass and the interval pass.
- `src/core/daemon/daemon.ts`: `DaemonOptions` extends `CommitModeOptions`. That type has `commitMode` (explicit), `commitWorktrees` (023-38's functions) and `commitTimes` (for tests).
- `src/core/daemon/lifecycle.ts`: `TimerContext.commit`. When it is set, `commitCheck` replaces the idle check.

## The seam to 023-38 (agreed through the coordinator, 2026-11-21)

`CommitWorktrees` stands for 023-38's `src/core/checkout/commit-worktree.ts`:

| Seam | 023-38 function | When the daemon calls it |
|---|---|---|
| `read(root)` | `readCommitWorktree(root)` | at start: a marker turns commit mode on |
| `claim(root)` | `claimCommitWorktree(tree)` | once, after registration, with the daemon lock held |
| `remove(root, note)` | `removeCommitWorktree(root, { note })` | at exit: after the socket closes, before the daemon lock is released |

- Until the integration, the default is `NO_COMMIT_WORKTREES`: no marker is read and nothing is removed. **The integration must wire the default**: in `startDaemon`, `options.commitWorktrees ?? <023-38's functions>`, or a default in `commitModeOf`. Without this, `squeal daemon` in a commit worktree runs as a normal daemon.
- `remove` runs from the daemon's own live process. The marker still names that pid, so `removeCommitWorktree` must not refuse it as a live owner. The daemon's working folder is not under the tree, and its runner hosts are closed before the call.
- A `superseded` exit (step-down for newer hooks) does not remove the worktree, because its successor serves the same tree. Every other exit removes it.

## Decisions the spec did not settle

1. **The policy stays the file's, except a lookup-only start.** `complexity.enabled: false` would turn coverage off (`coverageOn` needs both keys). The coverage options are part of Vitest's environment key. So the commit daemon's results would land at keys that D2's keyer and the user's daemons never read, which breaks D7.1. Lint and complexity are instead skipped in the daemon: no lint providers are passed on, and the code pass is `NO_CODE_PASS`. Coverage records are still written, at the commit's keys.
2. **No watcher.** The change feed gets a backend that reports nothing, and its interval pass is set to the 3 h cap. `status --wait` and `run --all` still ask for their own pass (`DaemonLoop.reconcile`).
3. **Activity** for the 10 min idle exit is what it is for every daemon (a request, a nudge, a request's ended file), plus a queued file or a running tier at each check.
4. **The cap** is the new exit reason `lifetime-cap`. Queued files are left in the queue. Since review wave-22 B2, the cap cancels the tier in flight as `squeal stop` does (see the repair below); before, the shutdown waited for it, without limit.
5. The shared CI reader and the daily full check still run as in every daemon. Nothing in D7.2 excludes them.

## Open question 4 of `research/run-wait-model.md`: answered

A queue waiting for a pool permit counts as activity. A tier that the pool refuses leaves its files queued (`scheduler/tier-start.ts` `act`: `WAIT_FOR_CAPACITY` returns before `startTier` dequeues anything). `Scheduler.queued()` then is above 0, and `commitCheck` counts that as activity. Tests: `test/daemon/commit-mode.test.ts` and `commit-timers.test.ts`.

A `--wait` call reads the store and is invisible to the daemon. It waits only while its files are queued or running, and those count as activity.

## Type changes (additive)

- `DaemonExitReason` gets `"lifetime-cap"`.
- `DaemonOptions` extends `CommitModeOptions`.
- `TimerContext.commit?: CommitLife`.
- `IdleGc.running()`: the number of tiers that run now.

## What 023-40 needs to know

- Start the daemon in the commit worktree as any daemon is started. With the seam wired, the marker turns on commit mode. `commitMode: true` is the explicit option for an in-process start.
- The daemon serves `run-group-paths` and `--wait` unchanged. Nothing runs at start (lookup-only), so a call must send its narrow requests.
- After an idle exit or a cap exit, the tree is gone. A later call must create the worktree again through `ensureCommitWorktree`.

## Repair after review wave-22 (B2, S1, N1 second location)

- **B2, the cap is enforced.** The timer's `shutdown` callback in `daemon.ts` calls `#cancelTiers("stop")` for `lifetime-cap` before `#shutdown`. So the cap takes the stop path: `#stopRequested` is set, the loop closes with `cancel`, no tier starts, and after `CANCEL_GRACE_MS` (2 s) the daemon's marked children are stopped (`stopMarked`). Then close, removal and lock release run as before. The scheduler cause is `stop`; no new `CancelCause` was added. Regression: `test/daemon/commit-cap.test.ts`, a real in-process daemon in explicit commit mode with `runner.timeoutMs: null` and one requested test that waits for a release file. Without the fix the daemon did not exit within 20 s of the cap (`reason: null, removed: []`); with it, it exits with `lifetime-cap` in about 2 s, the test's process is gone and `remove` was called, and the release file was never written.
- **S1, the removal report.** `CommitWorktrees.remove(root, note)`: the default passes `note` to `removeCommitWorktree`. The daemon passes its log (`options.log`; `squeal daemon` writes it to the daemon log file, which outlives the store closed before removal). The idle and cap texts no longer say the worktree is removed. After the removal, the exit text gets `; the commit worktree is removed` when the root is gone, and `; the commit worktree is not removed (<root>): the sweep removes it later` when it is still there (an error, or another live owner). The daemon reads that fact from the file system after the call, so a fake and the real function are judged the same way. Regression: `test/daemon/commit-removal.test.ts`; without the fix, neither note reached the log.
- **N1, `commit-timers.test.ts`.** Each step waits for one whole lifecycle check that began after the clock moved (`checked()`, counted in `requestProgress`, which every check calls before its idle decision in the same synchronous turn). With the fixed sleeps, a lagging check made the assertions check nothing: with checks every second and the queue-is-activity rule removed, the old file passed 4 of 4; the new one fails the queue test.
- **Type change:** `CommitWorktrees.remove` takes a second parameter, `note`. New export `removalText` in `commit-mode.ts`.
