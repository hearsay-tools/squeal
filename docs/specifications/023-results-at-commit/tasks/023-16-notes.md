| `at-keys-walk.ts` | `withKeyer`, `withCheckout`, `CheckoutFailed`, `KeyingOptions`, `CheckoutOptions` | the gate's keyer in a checkout |

`KeyAt` is `{ key, stored }` or `{ notDetermined: { reason, detail } }`. Reasons: `absent` (the commit, or the side's test version, lacks a named file; no checkout for it), `unlisted` (no adapter in the checkout keyed it), `checkout`, `install`. `stored` is the main store's `results.byKey(key, 0)` for that file, read-only; empty for no result.

`KeysAt` gives `commit`, `files`, `failure` (why the checkout gave no keys, when it could not be made or installed; with no named files, `files` is then empty), `checkoutMs` (the checkout's whole time; `null` only when every named file is absent at the commit) and `store` (false when the store could not be read).

## Flow

The human dropped the fast path on 2026-11-17, after three reviews (`reviews/wave-5.md`, `wave-5-rereview.md`, `wave-5-third.md`) found it reused the current key at commits that resolve an import otherwise: a file beside a folder index, a configured extension, a folder manifest's deeper `main`, a retargeted folder symlink. No rule over git objects proved resolution equal.

1. Named files the commit's tree lacks (`git ls-tree`) read `absent`, with no checkout.
2. `withCheckout` sweeps the checkouts of dead owners (D6), makes the checkout at the commit, and runs the install.
3. `withKeyer` opens the gate's `openKeyer` (exported from `src/core/code/gate/stored.ts`, with `readStores`, `Keyer`, `Keyed`, `Stores`; no behaviour change) in the checkout: the adapters load the configs there and the keyer walks each named file's closure fresh over a scratch store. With no named files, it keys every file the adapters at the commit list. Each key is looked up in the shared store read-only. The checkout is removed in `finally`. No daemon, no `test_file_keys`, no shared write; the user's tree is not read beyond git.
4. Review wave-5 B3: the default install reports its process group (`InstallOptions.started`), which the checkout's marker records (`CheckoutMarker.group`, `recordGroup`). `removeTree`, which both removal and the sweep run, stops that group first (`stopRecordedGroup`): when its leader still lives, or the leader's pid is free while the group has members. A SIGKILL between the spawn and the record leaves the group unrecorded (re-review N1, nonblocking).

The comparison with the current tree (D3) needs the current keys; that is 023-06's, from a running daemon or the gate's keyer in the worktree.

## Decisions the spec did not settle

- Adapters come from the caller (`KeyingOptions.adapters`, the CLI's `daemonAdapters`): nothing under `src/core` imports a runner.
- The policy of each tree is read as a daemon there reads it (`readPolicy(tree)`), with no coverage override (the gate's `storedFiles` forces `coverage.children`; these keys do not).
- Default files: those the adapters list at the commit.
- The install's default budget is 300 s (`installTimeoutMs`); D4's whole-run budget is 023-07's.
- Side keys: a test version from a commit is written from its blob into a temporary folder and copied in with `copyIntoCheckout`; `tests: null` copies from the worktree. Only the named files are copied: D5.2's helper copy and import refusal are 023-08's.
