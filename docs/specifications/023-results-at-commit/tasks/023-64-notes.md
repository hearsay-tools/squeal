## Cause: the brief's premise did not hold

The brief assumed a lone run at the commit that missed V1's symlink hold. The evidence says otherwise:

- In squawk at the round's parent commit, `.ai/ast-grep/rules/` is a plain tracked folder (`git ls-tree`); no symlink is on its path.
- The reason `needs .ai/ast-grep/rules/` ends in `/`: it is a listing path, a folder read (`listingPath`). D4.9 refused every folder read by design since review 0.1.597 B1 ("Clean tracked-folder reads now refuse too"; `reviews/0.1.597-rereview.md`).
- No lone run took place. The narrowed call's ask ran D4.9 in `AtAsks.choose` (`src/core/daemon/at-asks.ts`). By then the working tree had run `lint-ast-grep-1/2` and recorded the folder read, so the commit daemon's closure index held it, and the ask refused both files. `status-at-commit-rows.ts` shows any ask's refusal before a stored result, so the result the commit batch stored for them read `not comparable` too.
- In the other 9 sessions the first ask chose the files before any run had recorded the read, so they ran in the batch and compared.

So the defect was timing: the same file at the same commit was refused or compared depending on whether its folder read was recorded before the ask chose it.

### Rule text, for the spec (D4.9, the commit daemon)

> A file whose closure reads a path git does not hold at the commit reads `not comparable (needs <path>)` and is not run. A path under a tracked symlink is held as the link resolves at the commit's tree (row 023-48). A folder read (`<folder>/`, `./` for the root) is held when the commit worktree, the folder resolved through links on disk and inside the worktree, lists exactly the names the commit tracks in that folder: its files, its links, and its subfolders that hold a tracked file. A name the commit does not track (ignored, untracked, or written by the install) or a tracked name missing on disk refuses the file. The check runs in the commit daemon only; proof's green side and the in-call D4.9 check (`needsOf`) still refuse every folder read.

Why it is sound: a listing's key hashes the names the commit tracks (`Listings.hashOf`). When the names on disk are exactly those, the commit daemon's own run reads the commit's listing, so its result is the commit's. Review 0.1.597 B1's case, a stored result from a listing with an extra ignored name, still refuses, because that name is on disk in the commit worktree only when the install wrote it there, and then the listing differs.

## Which wins, a refusal or a stored result (the coordinator's question 2)

`status-at-commit-rows.ts` (`state`) reads an ask's refusal before any result. After this change:

- A folder whose names on disk equal the commit's: no ask refuses the file, whenever its read was recorded. A result the commit batch stores reads as the commit's result.
- A folder with an extra or missing name: an ask that knows the read refuses the file, and the refusal wins over a result stored at the commit's key, because that result was run on a listing that is not the commit's.

Left open: an ask that chose a file before any run recorded its read cannot refuse it, so a file that lists a folder with an install-written name runs once in the commit batch, and its result stands until a later ask refuses it. Making that strict needs the run's recorded reads to be checked after the run, before the result is read as the commit's (for example, `status-at-commit-rows.ts` asking the commit daemon for each result's `needs`). Not done here; a candidate for round 9 or later.
