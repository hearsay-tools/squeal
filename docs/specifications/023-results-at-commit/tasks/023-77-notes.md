# 023-77 notes: a file waiting for the shared slot names its holder (round 10, Z1)

Row 023-77, wave 36, worker B, 2026-11-24. Brief: `wave-36.md`, "Worker B". Base 0.1.611.

## Change

- **The record.** The slot's lock file records its holder: pid, worktree and since (row 011-58). It now also records the files the holder runs, with each file's stored duration (`SlowSlot.holding`, row 023-78, `023-78-notes.md`). The lane writes the files right after its tier starts, while it holds the slot.
- **The read.** In a narrowed `status --at --run` call, when a side's lane publishes that its files wait for the group's slot (`activity.for === "slot"`), `slotHolder` (`src/cli/status-at-estimate-holder.ts`, new) reads that group's permit files: `heldPermits` over `maxParallel` files in the slot directory as the daemons name it (`slowSlotDir`, the host config's `capacity.groupSlotScope`, the worktree's Git common dir from its store row).
- **The text.** The per-file line: `<path>: 1 of 1 queued at <c>, waiting for the browser group's slot, which the working tree's run of <path> holds (running for 40 s, about 57 s left), …`. The estimate: `Still to run, at <c>: 1 test file, time unknown: waiting for the browser group's slot, which … holds (running for 40 s, about 57 s left); it starts when that run ends`. With several files of the side waiting, it reads `the first starts`. The holder is `the commit worktree` or `the working tree` by the call's two sides, else `another worktree`.

## Rules (review 0.1.611 S1: claim only what is recorded)

The call names a holder only when every held permit belongs to one process, and that process:

- runs (`pidRuns`);
- is another worktree's, not the waiting side's own;
- recorded its files with the stamp of the holder row it holds. An older release's take, or a record older than its permit, has no files (`holdingOf`).

Otherwise the line reads as in 0.1.611: `waiting for capacity (the browser group's slot)`. This covers no permit held (a one-turn yield with the slot free), several holders, a dead holder and an older release's holder. The time left is the longest stored duration of the holder's files less the time held. It is shown only when every file has a stored duration and at least 1 s is left. Otherwise no time is shown.

The read is cheap (the coordinator's condition 4). It happens only for a side whose published wait is the slot, and only in a narrowed call (as 023-71's waits). It opens that group's `maxParallel` permit files, no per-file scan.

## Decisions the brief did not settle

- **Where the holder is read.** The waiting side's daemon could republish its wait with the holder in the activity. Instead the call reads the slot's record live. That needs no change to `SlowTierActivity` (`src/core/types/status.ts`) or its parser. A lane's wait is republished only every 15 s, so a holder in it could be up to 15 s old. Status and hook deltas also do not change with each holder.
- **"It starts when that run ends"** is in the estimate line only. The per-file line keeps one clause per side, separated by commas. The claim holds for the waiting side's lane: at the handover the holder yields one turn to a marked waiter (spec 004 D2). A third worktree's fresher mark could take the turn first. That is rare, and the brief's wording was kept.
- **Paths, not base names.** The holder's files are named by their recorded relative path, as the per-file lines name them.
