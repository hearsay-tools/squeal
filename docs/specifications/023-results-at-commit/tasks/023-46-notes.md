# Row 023-46 notes: a daemon's start skips the walks the store already proves

Row 023-46 (wave 24). Goal: a commit daemon serves within seconds of its install, not after the import walk over every test file (`023-40-measure.md`: about 25 s of a 31 s start on 4 vCPUs).

## Where the walk runs

A daemon's start is `scan` then `baseline` (`src/core/scheduler/bootstrap.ts`). In `baseline`:

1. Every listed test file with a stored closure list (`store.testFiles`, the newest list any worktree wrote) is keyed from that list. No runner call. Files without one (`unresolved`) are walked at once (`resolveClosures`).
2. The first lookup reads results at those keys.
3. **The recheck.** Every miss keyed from a stored list is walked again (`resolveClosures` -> `runner.closure` -> `importClosure` in the runner host, a Vite transform of every file the closure reaches), keyed from its own closure and looked up once more. The comment says why: "A miss will run, so it is keyed again from this worktree's own closure". A list another worktree wrote can belong to other file contents.

In the measured runs the store had no results (fresh store, lookup-only worktree daemon). Every file missed, so the recheck walked all 2,105 files: the 25 s. The worktree daemon at HEAD had already walked the same files a minute before. HEAD and HEAD~1 differ in 45 files, so most of those walks give the same closure at the same key.

## The rule

A recheck walk is skipped when its answer is already proven: **the store holds a walk of the same test file at the key the stored list gives here** (`test_file_imports` row at `(project, path, key)`).

Why this is exact (D2: keys stay the daemon's own keying):

- A `test_file_imports` row is written only by a real walk (`storeClosures` -> `recordImportGraph`), at the key that walk's closure gave, after `trackUntracked` (`import-edges.ts`: "One key's walk is one walk").
- A key covers the environment hash, the project, the test path, the installed-dependency segment and every present closure path with its bytes (`checkKey`, `keyFromSegments`). Equal keys mean equal environment, equal present closure paths and equal bytes. A walk reads only those bytes and the existence of the resolution candidates (which the closure lists), so it returns the same closure here. The key it gives is the key already computed. The recheck would key the file at the same key and find the same miss.
- This is the rule the start already uses for a lookup hit ("A hit is safe with another worktree's closure list: equal contents import the same files", B1), and the rule `closureTrust` uses for delivery ("a key covers every closure path and its content"). Results are reused across worktrees on the same rule.
- A stored list carries no per-file packages. Where packages are keyed per test file (scoped mode, task 001-105), its key takes the whole fingerprint and never equals a walked key: no row matches, and the file is walked as before. In this repository the keys are equal (probe below), so the rule applies.
- When anything differs (another observed set, other globs, an untracked path, another environment), the key differs and the file is walked as before. The rule can only skip a walk whose key it already has. It never changes a key.

What the skipped file keeps: its closure from the stored list, marked as a stored closure, as a lookup hit's is. What the recheck wrote to the store is still written: the closure rows (`store.testFiles`, now by this worktree) in one `storeClosures` call. The walk row at that key is already there.

## Scope: every daemon

The rule is in `baseline`, which every daemon runs: commit daemons and worktree daemons. The coordinator accepted this (2026-11-21): no visible change, the same trust rule as lookup hits. A worktree daemon whose misses have stored walks at their keys starts faster too. Existing tests with a fake runner store no walk rows (their closures report no `imports`), so they walk as before.

Not changed: the unresolved walk (no stored list at all, for example a fresh store where the worktree daemon has not walked yet, or both daemons starting together), runtime-selected files, and misses with no walk at their key. At a commit near HEAD, the remaining walks are the files the diff reaches, which `--run` selects and runs anyway.

## Seam with 023-40c: selection in the commit daemon

023-40c selects D4.5's files in the commit daemon. It must not call the runner's `affected` (`src/runners/vitest/affected.ts`): Vitest's `relatedSpecifications` transforms every test file and its imports, the same 20 to 25 s walk, at the first request. Select from the key index instead (coordinator, 2026-11-21: "never runner.affected in the commit daemon"). No `Scheduler.keyFiles` is added: the start keys every file eagerly. Absent means "the start pass keyed everything", as agreed.

The functions, all on the scheduler's `SchedulerContext` and `Ledger` after the start committed (`baseline` returned; `Scheduler.readers` waits on the lock):

| Need | Call | Covers |
|---|---|---|
| Test files whose closure holds a changed path | `context.keys.index.reverse.referencing(changed)` (also through `Scheduler.readers(paths)`) | imports at any depth; the snapshot path; every resolution candidate of an unresolved import (a file added since the commit); the manifests `#` and workspace imports read (023-14); declared `inputs` (they are in the assembled closure); observed paths |
| Changed test files themselves | `ledger.recentOf(changed)` (the above plus every listed file whose own path is in `changed`) | a test file the diff changed |
| A project's config, setup and global setup files | `context.keys.environmentFiles(project)` for each project; a changed path among them selects every file of that project | 020 D3.1's "every file of a project whose config or setup changed" |

Exactness conditions:

- After the start, every keyed file's closure is its own at this tree: a lookup hit (B1), a proven miss (the rule above), or a walked one. So the reverse index answers for this tree, as it does for a worktree daemon's edits.
- A file with no key (`ledger.file(ref)?.key === null`: its closure call failed, or a project's listing failed) is not in the index. Treat it as selected, or report it as not keyed; never as unaffected.
- `changed` is relative to the root. The commit worktree has the user's layout, so `git diff --name-only <c>..HEAD` plus the working tree's changes can be used as given.
- A changed path that is a test file's own path but not listed at the commit (a test file new since the commit) is not at the commit; it belongs to the working-tree side.

### 023-40c's later additions (coordinator, 2026-11-22)

- **node:test incomplete-closure lists (T2).** Not affected. The node:test adapter builds its static graph over every listed test file when the project opens, and `graph.incompleteClosures()` reports from that graph (`adapter-project.ts`, `notes()`), whatever closures are asked. Also, only the Vitest adapter's closures carry `imports`, so only Vitest files have walk rows and can be proven: node:test and pytest files are asked of their runner at every start, as before.
- **`Scheduler.closureReads(picks)` (D4.9).** It reads the key index's paths. A proven file's closure is the stored list, as a lookup hit's is. Its present paths and their bytes are a walk's (equal key). Its absent paths can differ from a fresh walk's in one case: the stored list was walked where an import resolved, and here its target is absent, so the list names the target but not the target's other resolution candidates (other extensions, `index` files), which a fresh walk would list. Then a candidate that exists untracked in the caller's worktree is not picked, and a diff that adds such a candidate does not select the file. A lookup hit keeps a stored list in exactly this way today; the rule adds no new kind of case. At the commit, such a file imports a missing file (its run fails to load).

## Round 4: review wave-23-third B2 (the human 2026-11-22: "Tighten it"; option B, coordinator 2026-11-22)

**Defect.** An equal key proves a stored list's present paths and bytes, not its absent paths. The start keys from the newest list any worktree wrote. When that worktree resolved an import to a file absent here (`src/foo.js`), its list lacks the candidates a walk here probes (`src/foo.ts`). The list still keys at the key of A's unresolved walk, so the shortcut kept the wrong closure. The "absent paths" caveat in "023-40c's later additions" above was this defect.

**Rule now** (`proven-walks.ts`). A miss is proven, and not walked, only when the store holds a walk of the file at the key K computed here, and one of these holds:

1. **No unresolved path** (`unresolvedHere`). No path of the list keyed here hashes `null` in the hash source the key index keys with (the stat cache through `gitEntryByKind`). The test file's default snapshot path (`<dir>/__snapshots__/<name>.snap`) is the one exception. Listing paths (`dir/`) never hash `null`: an absent directory lists as `ABSENT_LISTING`.
2. **The writer walked it at K** (`writerWalked`). The stored row (`test_files`) has every path in the list keyed here. Its writer (`updated_by`) holds K for the same project and path in `test_file_keys`. No stored walk row of the file (`test_file_imports`, every key) names a path that is absent here, as a walked module or as a static or dynamic import target.

Everything else is walked, as before row 023-46.

**Why 1 is complete.** `checkKey` keys each closure path as `path\0hash\0`, and a path whose hash is `null` adds nothing (`encodeSegment`). Absent paths are left out, not keyed as `null`. So with no absent path, the key holds every listed path with its bytes. The default snapshot path depends only on the test path, which the key holds, so every walk at the key lists it alike.

**Why 2 is exact.** The key is `sha256([KEY_ENCODING, environment hash, project, test path, dependency segment, runtime?, ...segments])`. The segments are the present paths, in closure order, with their hashes. A writer key equal to K therefore means the same environment hash (config, setup, versions), the same project and test path, the same dependency segment, and the same ordered present paths with the same bytes. Let R be the stored list and I the list keyed here (R plus this worktree's declared inputs, observed reads and glob folders, so R ⊆ I). Take a path P in R that is absent here. If P had been present at the writer, its segment would be in the writer's key and missing from K. So P was absent at the writer too. The writer's walk therefore saw exactly the existence and bytes this tree has for every path of R, under the same environment and dependencies. A walk depends only on those, and D3 makes it list every path it probes (imports, the snapshot path, every resolution candidate of an unresolved import, the manifests `#` and workspace imports read). So a walk here gives R. Extra paths in I only widen the reverse index.

**Where `updated_by` or the writer's row can be stale, and what covers it.**

- **The writer's commit window.** `storeClosures` writes the list and its walk rows in one transaction. The writer's key row is written later, at its ledger commit (`ledger.ts`, `testFileKeys.upsertMany`). In between, and for good if the writer dies there, the row holds its previous key. If that previous key equals K, the argument above fails for the new list. This is B2 again: B's list after it gained `src/foo.js`, with B's row still at A's K. The walked-path guard covers it: the new list's walk row names `src/foo.js`, absent here, so the file is walked. Not covered: in that window, a path the new walk read that is not a module (a manifest, a declared input, an observed read), present at the writer and absent here, while the writer's previous key equals K. Also not covered: another worktree's walk of the same file prunes the writer's fresh walk row before the writer commits its key (the prune keeps only keys held in `test_file_keys`). Both need the window, a key equal to the previous one, and a non-module change, or two writers of one file in one window.
- **`updated_by` is the newest writer of the row**, of any worktree, a commit worktree included. The row and the key row are read by the same project and path, so another project cannot match. A writer whose tree is gone keeps its last committed key row, and the argument holds for the list it committed. A list proven here is written again as this worktree's, holding K (`storeClosures`), so the next reader's writer test sees a list proven for K.
- **A list rewritten after the start keyed it.** If the new row is not within the keyed list, the writer test fails and the file is walked. If it is within the list, the argument holds for the new row, and the keyed list only adds paths.
- **Runners without walk rows** (node:test, pytest) are never proven, by either rule.

**Why clause 2 was added: the cost of clause 1 alone, on this repository's store** (the newest list per file against this worktree's files; read-only script, not committed). Of 2,135 lists, 1,395 hold an absent path other than the snapshot, mostly files another branch's tree had. The old rule would rarely have found a walk at the key for those. Several absent paths are the same in every worktree: the `package.json` lookup chain (`src/package.json` in 596 lists, `src/core/package.json` 595, `test/package.json` 384) and the `.postcssrc*` config candidates (383). With clause 1 alone, those files would be walked at every start. Clause 2 keeps them proven whenever the list's writer is keyed at K, as the worktree at HEAD is for the files a commit near HEAD did not change. No benchmark was run (no build in this repair).
