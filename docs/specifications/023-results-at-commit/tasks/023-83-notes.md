# 023-83 notes: the first browser pair, and what a slot wait waits for (round 11, AA2)

Row 023-83, wave 40, 2026-11-24. Brief: `wave-40.md`. Base: main at 0.1.619.

## Cause

Round 11: the commit side started its browser runs at 56 to 84 s, and the working tree at 94 to 178 s. The working tree then followed the commit side's latest file (6 of 6). That follow rule came from row 023-78 (`followPartner`). The slot's lock file recorded only the last holder's files, so a follower that came late saw only the leader's latest file. The leader's first file was paired last.

## Change

- **The slot keeps every file a holder ran.** `recordHolding` (`src/core/slow/slot-holding.ts`) now also appends to a `ran` table in the permit's lock file: worktree, project, path and when. The same transaction writes the `holding` row. The table keeps the newest 256 rows. `partnerRuns` reads the runs of the other worktrees from the last 3 hours (`RAN_FRESH_MS`, a commit daemon's longest life, D7.2). It lists each file once, at its first run, the first run first. It reads with the `immutable` URI and takes no lock, as `lastHolders` did.
- **The follower takes the leader's first file.** `followPartner` (`src/core/scheduler/slot-follow.ts`) goes through those runs in order. It puts first the first file that this side's `status --at --run` request holds and that is free to run now. "Free to run now" means queued here, so this side has no result for the file at its key. The rules from 023-78 do not change: a named file of a leading batch stays first, the order changes only among the files that may run now, and nothing waits.
- **A slot wait records why.** `SlowTierActivity`'s waiting variant has a new optional field, `slot?: "held" | "turn"` (`SlotWait`, `src/core/types/status.ts`):
  - `held`: the lane tried every permit and each one was taken (`acquireSlowSlot` returned none, or `slowSlotHeld` was true).
  - `turn`: the lane gave its turn to another worktree's marked waiter (a yield, or a drain).

  The lane publishes it in `#waitAtSlot`, and the parser (`toSlowActivity`) keeps it. Status, the hook and `squeal retry` then name the slot: `waiting for the browser group's slot (in use)`, or `… (its turn went to another worktree that waits for it)`. A daemon of an earlier release publishes `slot` without the field. That `slot` keeps today's hedge, because before row 011-291 a daemon published `slot` for a pool wait too. `pool` was already exact (row 011-291).

## Alternation

The 004 D2 handover already alternates the slot. A holder between files that finds another worktree's fresh waiter mark skips one turn. The new test "pairs the commit side's first file first and alternates the turns after a late start" passes on the base for alternation. Only its pair order is red there. I found no code path where a side that waits at the slot with a fresh mark loses two turns in a row. I did not change the rule. Review 0.1.621 S1 later found one (an extra pass after a yield); the fix was dropped, see "S1: strict alternation dropped" below. Round 11's runs of 2 to 4 turns by one side have no recorded cause. The round's data do not show what the waiting side's lane published at each handover. The code has three paths where a side that wants the slot leaves no fresh waiter mark, so the holder takes the next turn too:

- **The pool.** The lane takes the slot, the pool refuses a permit, and the lane lets the slot go. It publishes `pool` and leaves no mark. Three sessions shared one pool.
- **Fast work first.** A lane that waits for the groups it follows publishes `fast` and leaves no mark (spec 019 D1). The commit side's lint runs from the second call (s1-04 at 107 s) are one case. They do not overlap the consecutive turns of s1-05 (126 and 157 s) or s1b-02 (269 and 272 s).
- **A lane not asked for 30 s.** The mark is fresh for 30 s (`SLOT_WAITER_FRESH_MS`). A lane refreshes it on each recheck (15 s). A lane that is not asked in that time, for example during a long busy-store wait, loses its mark.

Round 12's hook and store copies can now tell `slot: held`, `slot: turn` and `pool` apart. The first two paths can then be separated. A fix that keeps a pool-refused side's mark would cost the holder up to one 15 s recheck per turn while the pool stays full. That would slow a side that is in effect alone, which the brief forbids. So this row does not make that change without evidence.

The 15 s gap: after a yield, the slot stays free until the waiter's next recheck, at most `SLOW_RECHECK_MS` (15 s). This fits s1b-02's 15 s delay. A shorter recheck for a marked waiter is a later decision (load). It is not part of this row.

## Decisions the brief did not settle

- **"A result or a run"**: the record holds runs under the slot. A partner's result that came from no run here (imported, or from an earlier session older than 3 h) is not in it, so such a file is not followed. It runs in this side's own order.
- **Order by the leader's runs, not by the follower's queue.** "The earliest file in the request's order" is read as the leader's run order. The follower's own queue can put the change's own files first (023-68's separate request), and then its order is not the request's. The leader runs in the request's order (023-68), so in the usual case the two orders are the same.
- **History bound**: 256 rows per lock file and a 3 h window. A run older than that does not steer the order.
- **Words**: `(in use)` for `held`, and `(its turn went to another worktree that waits for it)` for `turn`. The `status --at` call keeps its own words (`waiting for capacity (the browser group's slot)`, with 023-77's holder). It never said "not known". `status --wait` prints no lane wait words, so it has nothing to change.

## Review 0.1.621 repair

### B2: "(in use)" only from the permits as they are now

The lane published `slot: "held"` at its last try. The words said `(in use)` until its next recheck (15 s by default), also after the holder let the slot go or exited.

- The lane now publishes where its slot is with a slot wait: `slotAt: { dir, permits }` (`SlotAt`, `src/core/types/status.ts`). It is only in the store.
- `liveActivity` (`src/core/state/slow.ts`), the read behind status, the hooks and `squeal retry`, calls `slotNow` (`src/core/state/slot-now.ts`). It tests the permits then (`heldPermits`) and drops `slotAt`:
  - every permit held now: `in use`, "the browser group's slot (in use)";
  - published `held`, a permit free now: `free`, "(taken at its last try, free now)";
  - published `turn`, a permit free now: stays `turn`;
  - no `slotAt`, or the folder cannot be read: the published value stays. `held` then reads "(taken at its last try)", never "in use".
- `SlotWait` is now `"held" | "turn" | SlotNow`, `SlotNow = "in use" | "free"`. Only readers write the last two. The parser keeps all four and `slotAt`.
- An older daemon's bare `slot` keeps the hedge. `status --at` keeps its own words with 023-77's holder read.

### S1: strict alternation dropped (the human, 2026-11-24)

Review 0.1.621 S1 showed that the 004 D2 handover does not keep the turns strictly alternating. A side that gave its turn takes the slot again on an extra pass (a nudge, a run's end) before its partner's recheck: `commit:a, commit:b, commit:c`. The first repair (commits `046feeffc`, `e358185dd` on the 0.1.621 repair candidate) made a waiter's mark name its wait, `<worktree>\n<pid>.<random>\n`, and kept a lane that yielded yielding while that wait was open. The re-review (`reviews/0.1.621-rereview.md`) failed it on two points:

- **B1**: the mark's contents were the wait's identity, but a refresh rewrites the file in place (`writeFileSync` truncates first). A daemon that reads the mark between the truncation and the write sees a new wait and takes the slot again.
- **B2**: an older daemon writes only `<worktree>\n`, so each of its waits has the same identity. The new side kept yielding to an older partner after that partner's turns had ended, and stopped its own progress while the older daemon took turn after turn.

The human chose (2026-11-24) to drop the turn-taking change, keep the slot handover as it is on main, and keep the rest of the repair. Strict alternation (wave 40's "a side does not take the slot twice in a row while the other side waits for it") is not delivered by this row. It is left for a new row. That row must be designed with older daemons sharing the slot in mind: an identity that a refresh cannot change, and a bounded rule for marks without one. 0.1.624 is wave 40 rebased onto main 0.1.622 without the two commits; `newSlotWait`, `slotWaiters`, `waiterRuns`, `#yieldedTo`, `test/scheduler/slot-turns.test.ts` and `test/slow/slot-waiters.test.ts` are gone, and `test/daemon/idle-gc-daemon.test.ts` and `src/core/slow/slot-files.ts` are as on main.

## Re-review 0.1.621 repair (B3)

### B3: a malformed permit that no process holds is no proof of use

`heldPermits` counts a permit file that neither a lock test nor SQLite can read (no database) as held, `unreadable`, so the slot stays conservative. `slotNow` counted it as proof that the slot was in use: a `held` wait with such a file and no holder read "(in use)".

- `HeldPermit` has a new optional field, `unknown?: true`: the lock test failed, so whether a process holds the permit is not known. A permit whose lock test finds it held (with a missing or malformed holder row) has no `unknown`.
- `slotNow` reads `in use` only when lock tests find every permit held. When every permit counts held but some are `unknown`, the published value stays: `held` reads "(taken at its last try)", `turn` stays `turn`. A permit free now still reads `free`.
- Slot enforcement does not change: `acquireSlowSlot` and `slowSlotHeld` still treat a malformed permit as taken.

Tests (red without the fix, each read "(in use)"):

- `test/status/slot-at-kit.ts` gains `malformed`: the permit file is "not a database", held by no process. Cases through the live read and the text: `group-lines` (status), `slow-tier` (status, the slow slot), `group-requested` (the hook), `retry-holds-group` (retry).
- `test/state/slot-now.test.ts`: two permits, one held by another worktree and one malformed: `held` stays `held`, `turn` stays `turn`. Controls: one held and one free reads `free`; both held reads `in use`.
- `test/slow/slot-holders.test.ts`: the no-database permit carries `unknown`; the held permits with a missing or malformed row do not.
