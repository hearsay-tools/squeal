# 023-78 notes: both sides take the shared slot file by file (round 10, Z2)

Row 023-78, wave 36, worker B, 2026-11-24. Brief: `wave-36.md`, "Worker B". Base 0.1.611.

## Cause

The handover already alternates the slot. A browser group's `maxParallel` slot is one per repository, shared by the working tree and its commit worktree (`023-71-notes.md`). Spec 004 D2's handover gives it to the two sides in turn: a holder between files that finds another worktree's fresh waiter mark skips one turn (`SlowTier.#takeSlot`, `othersWaitingForSlot`).

What each side ran in its turn was the first file of its own queue, and the two queues can differ:

- The working tree queues the change's own files in a request of their own before the commit daemon's selection (`023-68-notes.md`, "Limits"), so its batch order is not the commit side's.
- A side that starts later (the commit worktree installs and keys first) is behind the other.

`test/scheduler/slot-pairs.test.ts`, first case, reproduces round 10 on the base: the commit side runs a, b, c and the working tree c, a, b. No slot turn compares a file.

## Change

- **The slot records what its holder runs.** `SlowSlot.holding(files)` (new, `src/core/slow/slot.ts`) writes a `holding` table into each held permit's lock file: the holder row's pid and `since`, and the files (project, path, stored duration). The lane calls it right after its tier starts (`SlowTier.#launch`). The record outlives the hold: the lock file keeps its last holder. `src/core/slow/slot-holding.ts` (new) writes and reads it.
- **The side that takes the slot follows its partner.** `followPartner` (`src/core/scheduler/slot-follow.ts`, new), called from `SlowTier.#candidates` for a group with `maxParallel`: among the files that may run now, the file another worktree last ran under the slot goes first, when a `status --at --run` request queued it on this side (its batch keeps a request order, `PromotionRank.place`, row 023-68).

The result: the leader runs a file, the partner runs the same file next, then the leader runs its next file. Every two slot turns compare one file.

## Decisions the brief did not settle

- **Who leads.** The brief says the commit side's run, then the working tree's. The rule here has no fixed leader: the side that takes the free slot first leads, and the other side follows. The pairs still arrive in the leader's order. A fixed leader would need the working tree to give way to the commit side even when it holds nothing. That is a wait, and the brief forbids slowing a side whose partner has nothing queued. In the usual case, both sides got the same request order (row 023-68), so the leader's order is the request's.
- **Where the record lives.** The record is in the permit's lock file, beside the holder row (`takePermit`), not in the store and not in a new file. Row 023-77 reads the same record for the holder line. It is a table of its own, `holding`, stamped with the holder row's pid and `since`: an older release takes the permit, rewrites only the holder row, and leaves `holding` as it was. A stamp that differs is an earlier holder's record and is not read (`holdingOf`). A lock file with no `holding` table reads as a holder with no files.
- **Named files first.** A file of a leading batch (a call that named it, row 023-34) stays ahead of a partner's file that no call named on this side. Under the leading rank, a partner's file of the same or an earlier batch is followed.
- **No wait, ever.** `followPartner` only reorders the files that may run now. A partner with nothing queued, a partner whose daemon is gone, or a partner that ran a file this side was not asked for changes nothing. This side runs its own order at once (the coordinator's condition 3).
- **Reading cost.** `lastHolders` opens the group's `maxParallel` permit files, read-only through SQLite's `immutable` URI. It runs only when at least two files may run and one of them is in a `status --at --run` batch.

## Type changes (additive)

- `SlowSlot.holding(files)`: a new method. `noSlot` (a group without `maxParallel`) does nothing.
- `PermitRecord` (`kind: "holder"`) gains optional `files`.
- New: `SlotFile`, `SlotHolderRecord`, `recordHolding`, `holdingOf`, `lastHolders`, `readRecord` in `slot-holding.ts`. `immutableUrl` moved there from `slot.ts`; its one other user, `src/core/ps/work.ts`, imports it from there (a one-line change outside the brief's list).

Repair worker, 2026-11-24. Review `reviews/0.1.612.md`, S2.

**Decision (coordinator, kept as implemented).** The leader is whichever side takes the free slot first, not the commit side. The follower runs the file the other worktree last ran under the slot (its latest holder record), when its own `status --at --run` request holds it. The brief's order (the commit side's run, then the working tree's, in the request's order) holds in the usual case, where the commit side starts first and both sides got the request's order (row 023-68). A fixed leader would make the working tree wait when it holds the free slot and the commit side has nothing ready; the brief forbids that wait. The rule has no request or partner identity: it follows any other worktree's latest record.

**Accepted limit.** A partner that queues late follows the leader's latest file, then runs its own order. The files the leader ran before the partner came get the partner's run last.
