# Rows 023-48 (V1) and 023-50 (V3) notes: what the commit side holds and runs first

Wave 28, worker A, brief `tasks/wave-28.md`. Spec D4.9 and D7.3. Base: main at 0.1.598 (`22be8a3c4`). Branch `cez/56684c4a`.

## 023-48, V1: a path under a tracked symlink is held at the commit

Cause. `git ls-tree -r` lists a tracked directory symlink as one blob (mode 120000) and nothing under it. Both D4.9 checks asked `committedBlobs(...).has(path)`, so `.agents/skills/a/SKILL.md`, read through the link `.agents/skills/a -> ../../.ai/skills/a`, was "not held". The file exists in the commit worktree through the link, so the check named it: `not comparable (needs .agents/skills/a/SKILL.md)`.

Change. `src/core/commit/held.ts` (new): `heldAt(root, commit, timeoutMs)` gives the commit's blobs and `has(path)`. `has` is true when the commit lists the path, or when a prefix of the path is a tracked symlink whose target, read from the link's own blob at that commit and joined with the rest of the path, is held in turn. Not held: an absolute target, a target that leaves the repository (`..` past the root), a target the commit does not hold, a file prefix (`plain.txt/x`), a loop or a chain of more than 40 links. A folder read through a link (`…/a/`) stays a folder, which is no blob, so it still reads `needs <folder>` (review 0.1.597 B1). The link targets are read with one `git cat-file --batch`, only when the commit has links; both git calls share the one timeout (review 0.1.597 B3).

Both sides use it, with the same rule:

- The commit daemon's `needs` (`src/core/daemon/commit-start.ts`): at the commit (the tree's HEAD) and at the caller's HEAD (the "generated input" test).
- `needsOf` (`src/cli/status-at-run-select.ts`), which serves proof's `greenNeeds` (`proof-green.ts`), proof's temporary-checkout side (`proof-side.ts`) and `refuse` of `status --at --run`. `status-at-run-select.ts` is not in the brief's ownership list; `needsOf` lives there, so the fix is there. No sibling row owns it in wave 28.

Tests.

- `test/commit/held.test.ts`: `heldAt` over a repository with a directory link, a link to a link, `..` inside the tree, a link out of the tree, an absolute link, a dangling link and a loop; `needsOf` with no reason for a read through the link and the path for a read that leaves; the batch parser with a missing object and multibyte content. Red on the old rule (2 of 3 fail).
- `test/cli/status-at-commit-refused.test.ts`, "row 023-48 (V1)": a real commit daemon; a test reads `.agents/skills/a/SKILL.md` through a tracked link; the first run records the read; the next commit's daemon runs it (`pass`). Red on the old rule: `not comparable`.

Not done, for whoever continues:

- Round 6 also says these 2 files had no result in the working tree, and round 5 called them "not stored (read paths first seen during the run)". That is the working-tree daemon's keying of an observed read under a symlink, not D4.9. Not investigated here.
- Keys computed in the CLI from git objects (`at-keys.ts`, `status-at-commit.ts`, `status-at-commit-rows.ts`) still read `committedBlobs`, so a path under a link has no blob there either. The commit daemon keys from its checkout on disk, so `status --at --run` does not depend on them.

## 023-50, V3: files under a named folder lead the commit daemon's queue

Cause. `AtAsks.#take` (`src/core/daemon/at-asks.ts`) queued `chosen.named` with `lead` and `chosen.rest` without it. `choose()` puts only a file named by its own path in `named`; a file under a named folder (and a reader of a named source path) is in `rest`. A narrow request without `lead` forms a batch that cannot take a file out of an earlier batch (`Promotions.add`, row 023-34), so the folder's files stayed in the earlier wide call's batch, at its place.

Change. In a call that names paths, `#take` queues every chosen file with `lead`, in one request per group, named files first, then the rest in row order. One request matters: a later leading batch ranks first, so two requests would put the rest ahead of the named files. A call that names no path leads nothing, as before. `choose()` and its return are unchanged (the coordinator: worker B adds `selects` there), so the selection is unchanged: a named folder narrows and forces no file (D4.5 at the commit; the existing test says so).

The working-tree side already sends `lead` for every request of a narrowed call (`status-at-call-sides.ts`, `call.lead`); nothing changed there.

Tests.

- `test/daemon/at-asks.test.ts`: a call that names a file, a folder and a source path asks one leading request per group, named file first; a call that names none sends no `lead`. Red on the old code.
- `test/daemon/at-asks-lead.test.ts`: a real scheduler with a held runner, one file a tier. A wide batch of 8 files runs shortest first; an ask that names the folder of the two longest files runs them next, after the tier in flight only. Red on the old code (the next runs come from the wide batch).

Not done: V3's proposal also says "if a running batch cannot yield, say so in the report". The tier in flight is not cut (row 023-34); the report texts are worker B's.
