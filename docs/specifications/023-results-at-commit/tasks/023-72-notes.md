# Rows 023-72 and 023-74 (Y2) notes: a requested file re-keyed before it runs is left held

Wave 34, worker B, brief `tasks/wave-34.md`. Spec D7.3; round 9 Y2 and 023-67's rest (`../lessons.md`, "Round 9 (023-69)"). Branch `cez/42ac8fe0`, base `d5065ea6b`.

## Cause (not the brief's hypothesis)

The working tree's request did not leave the files out; the scheduler dropped them after it took them.

- A narrow request (`squeal run <group> <path>...`, and the working tree's side of `status --at --run`, which sends the same request) releases a held group's file (`manual`, as squawk's `browser`) by an ask in its lane, `SlowTier.narrow`, a `CommitAsks` kept at the file's key at the request.
- `CommitAsks.prune` drops an ask once its pending file has neither the asked key nor a run at it. So a requested file re-keyed before its turn lost its ask, stayed pending and held, and never ran. The hook (023-67's line) then read it, correctly by its data, as "pending, waiting for `squeal run browser`".
- What re-keyed the files in round 9: the commit daemon ran `activity.e2e.ts` and `agent-browser-tabs` first. Their runs grew the shared observed reads (`observed.<project>`, merged across worktrees). The worktree's daemon reads that growth and keys a file whose observed set grew elsewhere again (`KeyIndex.regrowObserved`: "so a key this worktree holds a result under takes the paths"). Their asks at the old keys left.
- This explains the three signs together: the files the working tree left "queued" were the ones the commit side ran first; they were the 2 with a stored duration (the commit side's results); and the hook's "2 pending, waiting for `squeal run browser`" (s1-01).
- An agent's edit after a `--run` call re-keys the same way, so every requested file the edit reaches was dropped too.

The working tree's selection in the call (`queueBoth`, `takenBy`, `withoutNow`) and the 023-68 order were not the cause.

## Change (the coordinator agreed the scheduler edit, request 70b1f635)

- `src/core/scheduler/commit-asks.ts`: a second constructor argument, `follow` (default `false`). With it, `prune` moves the ask of a pending file with a key to that key instead of dropping it. An ended file (no phase), a file that left the ledger or has no key still drops its ask. The change callback runs on a move, so the narrow asks row is written again at the new key; no ask is kept at an old key, so 0.1.610's rule (status counts an ask only at the file's current key) stands.
- `src/core/scheduler/slow-tier.ts`: the lane's `narrow` asks follow (one line). 019's commit asks (`asks`) keep their rule: an edit before the commit's run leaves the file to the next commit.
- Order: a promotion batch keeps a file's place by `testFileId` while the file is queued or running (`Promotions`), so a re-keyed file keeps its 023-68 place.
