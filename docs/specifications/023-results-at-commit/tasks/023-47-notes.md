# Row 023-47 notes: a rewritten first-seen input is not kept at the shared pre-run key

Wave 27, brief `tasks/wave-27.md`. Base: main at 0.1.597 (`0f38f516f`). Branch `cez/9753aef6`.

## Cause

The gate's keep rule was not at fault. It never saw the read.

- The runtime recorder records reads (`paths`) and writes (`written`) per test file. `observedInputs` (`src/runners/observe/inputs.ts`) left every path the run wrote out of its reads (spec 001 D3: "less the paths the run wrote"). That rule keeps a scratch file the run writes and reads back out of its key.
- The repro test reads the tracked `data/a.txt` and, at commit A, rewrites it. So its report named no `data/a.txt`. The keeper saw no growth, and decided "store at the key it ran under": the key from before the run, which A and HEAD share (`8a87c5ed` in 023-42's probe). No read was merged, so the key never moved.
- Probe: one line of debug output in `keepDecisions` over the `it.fails` case. The observed paths were `test/__snapshots__/a.test.ts.snap` and `test/a.test.ts` only; the decision was `{ kind: "store", at: "ran" }`.

## Fix

1. The runner names the files a run read and also wrote, created or removed: `ObservedInputs.rewritten` (an additive, optional field). They stay out of `paths`, as before. The recorder keeps no order, so a file written and then read back is named too.
2. `inputsOfReads` (`src/core/scheduler/observed.ts`) keys the `rewritten` files that git tracks as reads (`trackedRewrites`, `src/core/scheduler/rewritten-reads.ts`: one `git --literal-pathspecs ls-files -z --cached` call, and none when no file has a rewrite). An untracked or ignored file the run wrote and read stays out, as before.
3. Nothing else changes. The existing rules act on the read: it joins the file's growth; it is first seen or it moved during the run, so the record and the keeper keep nothing; the read is merged into the shared observed rows, so every later key covers it. `inputsOfReads` is shared by the daemon's record, `squeal code`'s keeper and the gate's `--parts`, so all three get it.

The key format does not change. The recorder's version does, if the human agrees (below).

## Cost: tests that go to the completion barrier

A test that rewrites a tracked file it read with the same bytes now reads as "touched", and the completion barrier withholds it, as it already withholds a rewritten closure input. In the daemon it re-runs once, then reads unknown.

Measured by a grep, not a run: writes in `test/` and `src/` whose path comes from `import.meta.url`, `__dirname`, `process.cwd()` or a repository root. No test in this repository rewrites a tracked repository file from its own process. Every hit copies from the repository into a temporary folder, or is test source inside a fixture string that runs in a temporary repository. So 0 tests here.

## Review 0.1.598 repair (B1, N1)

- B1: `rewrittenOf` left out a path that is a directory after the run. A tracked file the run read, removed and replaced with a directory was then named nowhere, and the keeper stored the run at the key from before it. The observer now names every project path the run read and wrote, whatever stands there after the run. The core's `trackedRewrites` keeps a path only when `git ls-files` names it exactly, so it keys a path git tracks as a file and drops a directory (tracked files below it do not match), an untracked path and a removed directory.
- The recorder already named a stat'ed directory the run removed (for example `rmSync(dir, { recursive: true })`) before this repair; the core drops it in the same way. A directory the run only listed is in `listed`, not `paths`, and is never named.
- Cost: a run that stat'ed a project directory and created or removed it now names it too, so its batch can make the one `git ls-files` call where before it made none.
- Tests: `test/runners/observe/rewritten.test.ts` (file to directory named; listing-only directory not), `test/ci/inputs-here.test.ts` (the replaced file keyed; tracked, removed, untracked and ignored directories not), `test/code/gate/keep-rewritten.test.ts` (the reviewer's keeper probe: 0 results at the key the run ran under, the read merged; 1 result without the fix).
