# 023-45: a slow file in the fast pass of `slow-node-test.test.ts`: worker notes

## Cause

The slow e2e scenarios (`test/e2e/slow-shape.ts`) run under the default `slow.trigger`, `"continuous"` (004-80, 2026-10-18). Under it a slow file starts once the fast work is done and the latest revision is `slow.quietMs` (3000 ms) old, mid-turn or not (`momentHolds`, `src/core/scheduler/slow-trigger.ts`). The scenario asserts the `"idle"` rule: in a turn, after an edit and a CLI rewrite, the slow files stay pending until Stop or `squeal run --slow` (`slow-shape.ts` lines 113 and 120). So the check passed only while it ran within 3 s of the edit's revision. When the fast pass and the settle took longer, the slow tier started, and its first file, `cli.test.ts`, entered `ranSince`. `cli.test.ts` is first because `slow.rank` `"tokens"` matches the rewritten `cli.mjs` to it. Under load a tier holds one file, so only it ran.

This is a test race, not a product defect: a slow file that starts mid-turn 3 s after the edit is the continuous trigger's rule. 004-80's notes (decision 2) pinned the idle-semantics tests to `slow.trigger: "idle"`; these e2e scenarios were not pinned then.

## Evidence

- The margin, measured before the fix on this host (load 15 to 16, 3 runs, 6 cases): from the edit to the `settleFast` return 818 to 892 ms, to the check after the hook (line 120) 937 to 1022 ms. The 3 s window leaves about 2 s; a loaded CI shard can spend it.
- Forced delay, before the fix: a 5 s wait added after `settleFast` (line 112) made the test fail in both plugin cases, 2 of 2, with `cli.test.ts` and `package.test.ts` in `ranSince`. The same wait with `trigger: "idle"`: 2 of 2 pass.
- CI logs (the coordinator's search, 433 job logs with this case, split by whether the commit contains 7591bf996, v0.1.586): the claude-code case's own duration, p50, Node 22 shard 10.0 s before (n=267) and 13.1 s after (n=8); Node 26 8.7 s and 14.1 s (n=91, n=10); Node 24 about 10 s both. The failures: 2 of 366 before, 4 of 28 after. Longer cases leave less of the 3 s margin. Which change in 0.1.586 made the case slower is not identified; the CI logs carry no daemon notes, and the test is now independent of it.
- Unflagged runs pass through `withRunGroups` (`src/core/daemon/run-groups-watch.ts`) unchanged, and the take-back and lead-batch changes (`promotions.ts`, `queue.ts`, `narrow-run.ts`) touch narrow runs only, which this scenario does not make. No 0.1.586 path starts a slow file in a turn under `"idle"`.

## Fix

`SLOW_TUNING` in `test/e2e/slow-shape.ts` adds `trigger: "idle"`. Its users: `slow-node-test.test.ts`, `slow-vitest.test.ts` (both scenarios, both plugins) and `ps.test.ts`'s slow fixture (no consumer, so idle holds at once; its comment already says "on idle"). No assertion changed. The continuous trigger keeps its scheduler tests (`test/scheduler/slow-continuous.test.ts`).

## Repetitions

Host: 16 vCPUs, one-minute load 18 to 21 from other sessions during the runs.

- Before the fix, continuous trigger with timing probes only: 6 runs, 12 of 12 cases pass on this host (margin above); the CI rate is the baseline (4 of 28 since 0.1.586).
- Before the fix, 5 s forced delay: 1 run, 2 of 2 cases fail.
- After the fix, 5 s forced delay: 1 run, 2 of 2 cases pass.
- After the fix: `slow-node-test.test.ts`, `slow-vitest.test.ts`, `ps.test.ts` once: 13 of 13 pass. `slow-node-test.test.ts -t "fast tests first"` sequentially: 10 of 10 runs pass (20 cases, both plugins).
