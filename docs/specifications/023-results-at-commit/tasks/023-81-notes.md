### Proposed rules (sent to the coordinator; Step 2 waits for the reply)

**A. Row 023-81 as briefed: names a recorded run wrote stay out of listing keys.** A listing hashes the tracked names and the names on disk, less the worktree's *run-written names*. A name `n` in folder `D` is run-written when all three hold:

1. `n` was not on disk in `D` when `D`'s names were last read before the run (`Listings` keeps the names, not only their hash);
2. a recorded run wrote, created or renamed `D/n` or a path below it (the recorder's `w` set; a new additive field `ObservedInputs.created`, the first name below each listed or written folder);
3. its stat stamp (inode, size, mtime, ctime) still equals the stamp taken when the run's report arrived. A user's edit or replacement moves the stamp, and the name counts again.

The names and stamps are kept per worktree in the store (one `meta` key), so a restart keys the same way; a name gone from disk leaves the set. A name no recorded run wrote counts as today: one written by the user, by Squeal, by the runner's main process, or by a runner without the recorder (pytest, node:test children outside it). This replaces `Listings.ran`, which acknowledges every name on disk at a run's end when one test lists the folder (and so also another process's name: review 0.1.612 B1's next-revision case). N1 holds: a name the user adds before or during a run is not run-written. Limits: a revision during the run sees the run's name before its report and moves the key; the report then moves it back to the stored key. A test whose result depends on another test's leftover output in a listed folder keeps its key; that order dependence goes unseen. Cost: it fixes the rare shape above, not the re-runs round 11 measured. It needs two call-site edits in `src/core/scheduler/` (`keying.ts` `listedByRun`, `observed.ts`), outside this row's ownership.

**B. For the re-runs round 11 measured (outside this row's ownership).** An absent path first read during a run certifies the run when it is still absent at the run's end, git does not ignore it, and no revision or touched input during the run names it: the watcher reports a create of a path git does not ignore, so "absent" has evidence from the whole run. An ignored absent path still re-runs, as today. Here it would remove 48 of 48 `first-seen` re-runs in this repository's fresh store and 2 of 2 per side for squawk's lint files. To check first: whether a create and delete within one run reach the touched set. Code: `src/core/scheduler/observed.ts` (`firstHashedDuringRun`), and the store decision.

## Step 2

### B: stopped at condition (i)

The watcher can miss a create and delete within one run. `diffCandidates` (`src/core/revision/reconcile.ts`) compares what is on disk when the daemon reads a candidate with the stat cache. A first-seen path is in neither cache state (no hash, no recorded absence). If it is gone when the daemon reads it, the diff has no change and no `set` update, so `touchedUnchanged` names nothing, no revision holds it, and `Tier.changes` stays empty. A scratch test (run, then removed) showed it: a path created, stat'ed by the watcher's `statCandidates` while present, then removed before `diffBatch` gives `changes: []` and `touchedUnchanged(...): []`, and the same with the watcher's stat taken after the removal. So B would certify a run that read a file that existed only during the run, which condition (iv) forbids too. No product change was made for B. Re-runs it would have saved, measured before (Step 1): 48 of 226 folder-listing test files in this repository on an empty store, and squawk's `lint-ast-grep-1/2` once more on each side.

**For a later row.** Certify an absent first-seen path from the recorder's own read outcome, not from the watcher: the recorder sees each call the test makes, so it can report that the read returned `ENOENT`. With that, and the path still absent at the run's end, the run read "absent" and the result keyed with the path absent is right, whatever happened between. It covers a create and delete before the read too, which the watcher cannot see. A path the run read while present and that is gone at the end stays first-seen (condition iv), as does a path whose reads disagree. It needs a recorder output change (a `RECORDER_VERSION` question) and the store decision in `src/core/scheduler/store-decision.ts`.

### A: names a recorded run wrote stay out of listing keys

Commit `ee5aae135`.

- `RunWrittenNames` (`src/core/keys/run-written.ts`): per directory, the names a recorded run wrote, each with the stamp it had at the run's report (inode, size, mtime, ctime). One `meta` row per worktree (`run-written:<worktree id>`, owner `scheduler/keying`), stored in the record's transaction with the other observations (`writeSeen`), each entry `name\0stamp` read through `readSharedEntries`. `visible` drops a held name that is gone or no longer has its stamp, so the user's edit or replacement counts again.
- `Listings` (`src/core/keys/observed.ts`) keeps the raw names it last read per directory. It hashes the names on disk less the visible run-written ones (tracked names always count). `wrote(before, paths)` holds a name as run-written when a path the run wrote stands at it, the directory was hashed when the run began (`before`), the name is not tracked, and it was absent then or already run-written. `ran` is gone.
- `WorktreeKeys` (`src/core/scheduler/keying.ts`) copies `Listings.names()` at `beginRun`, per run number. `wroteByRun(paths, run)` replaces `listedByRun`, called from `observedGrowth` (`src/core/scheduler/observed.ts`) for each reported file.
- `ObservedInputs.wrote` (additive, `src/core/types/runner.ts`): every project path the run wrote, created, renamed (both ends) or removed, from the recorder's existing `w` set (`src/runners/observe/inputs.ts`). The recorder itself is unchanged.
