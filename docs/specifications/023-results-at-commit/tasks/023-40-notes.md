# Row 023-40 notes: `status --at --run` on the daemons (D7.3, D7.4)

Row 023-40a. What the coordinator, row 023-41 and the review need to know.

## The call now

`src/cli/status-at.ts` parses and locates as before. With `--run` or `--wait` it hands over to `daemonCall` (`src/cli/status-at-call.ts`):

1. **Keys and selection.** The commit side is keyed in a temporary checkout as before (D2): `commitSelect` (`status-at-select.ts`) runs the same keyer and D4.5's `selector` while the adapters are open, then the checkout is removed. Nothing runs in it. So the keys the call compares at are D2's by construction, and the at-keys tests are unchanged. A checkout that git's rules or the install changed queues nothing at the commit; its files stay `not comparable`.
2. **Commit side** (`status-at-queue.ts` `commitQueue`, `status-at-daemons.ts`): `ensureCommitWorktree` with the commit's own `env.allowlist` (read from `<commit>:squeal.config.json`, which the commit daemon reads) and `daemon.maxCommitDaemons` as `limit`; its notes, the "waiting for a place" line included, go to stderr. A daemon that answers in the tree is reused; else one starts as `squeal start` starts one (`startCommand([tree])`, its output dropped). The call then polls the marker until the daemon's claim (at most 60 s), as 023-38's notes ask. Then one `run-group-paths` request per group of the tree's own policy, with `at`, the call's `owner` and `lead` when the call names paths.
3. **Working-tree side** (`worktreeQueue`): the selected files with no result now (R1's rule) go to this worktree's daemon, started with `squeal start` when none answers, one request per group, the same flags.
4. **Wait.** Both sides at once, each as `run <group> --wait` waits (`runWait`, group wait over the file list). The bound counts from the call's start: 100,000 ms by default with `--run`, `--wait <ms>`, a bare `--wait` until done. A request is asked for at least 10 s even after the bound, so it is recorded; a request recorded and not taken by then counts as `queued`.
5. **Read again** (`status-at-after.ts`). The commit side is read at the call's own keys; a result whose worktree is the commit worktree reads origin `commit` ("run in the commit's worktree"). A file still without a result says why from the daemon's records: still queued or running (`pending`), its project's setup failed (`not run`, `setup: "<group>: <text>"`, R3's line as before), its run kept no result (`not determined`), or the daemon stored it at another key (`not determined`, named; D7.1 says this cannot happen, so it is reported, never mixed). The working tree's side is `nowSide` again with the same reasons.
6. **Report** (`status-at-report-queued.ts`). D3's text is unchanged; the run's lines are new: `--run: queued N test files with no result at <c> in its commit daemon (its worktree <tree>); K have a result now`, R8's not-selected line, `--run, now: …`, setup and problem lines, a side whose daemon could not be reached reads `not queued: <why>`, and Q7's line last while anything runs: `N still running at <c> (its worktree), M in the working tree; their runs go on in the daemons. squeal status --at <given> <paths> --wait 100000 waits for them; squeal ps shows them.` JSON: `run` is the new `QueuedRun` (`mode`, `waitMs`, `usedMs`, `commit`, `notSelected`, `now`, `again`), so the report version is now `squeal-status-at/2`.
7. **`--wait` without `--run`** (`status-at-join.ts`): finds the commit worktree for this commit and environment (`find`), joins the files of the call that its daemon has queued or runs, and the working tree's pending ones; asks nothing, starts nothing.
8. **Exit codes** as D1: 0 every file known on both sides, 3 some file still running, unknown or not comparable (and a failed checkout or an unmatched path, as before), 2 usage or setup error (`--timeout` included).

`--timeout` is a usage error in one line (`AT_NO_TIMEOUT`, exit 2): `--at takes no --timeout; --run waits up to --wait <ms> (100000 by default) and its runs go on in the daemons after it`. It replaces row 023-34's `AT_NO_WAIT` line.

## The config key: `daemon.maxCommitDaemons`

A whole number of at least 1, or `null`; absent (the default) means 023-38's memory-derived ceiling. Why this name: the existing caps are `max<Thing>` (`stop.maxHolds`, `slow.maxWorkers`, `slow.maxParallel`, `store.maxSizeMb`), and the `daemon` group already holds the daemon's lifetime keys. The thing a user counts is commit daemons, one per commit worktree. It is optional in `Policy` and absent from `DEFAULT_POLICY`, so every test that builds a policy or compares the defaults stays as it was. It is read from the caller's worktree (`readPolicy(root)`), since the ceiling is the caller's wait. Listed in the skill's `references/policy.md` (all three copies). There is no README config table.

## Decisions the spec did not settle

1. **Keys from the temporary checkout, not from the live commit daemon.** Research Q4 suggests reading a live commit daemon's keys instead of keying again. The brief asks that the commit side's keys equal D2's and that the at-keys tests stay green, so this row keeps the keying and reads the daemon only for pending and setup states. The real-daemon test shows the daemon's result found at the call's key. Cost: each `--run` call still makes one temporary checkout and keys (about 6 s for one file, 50 s for all, D2). A later row can read the daemon's keys when one serves the commit.
2. **The commit daemon starts after the keying, only when the selection has files for it.** Starting it beside the keying would save time on a first call, but would start a 1 GB daemon for calls that select nothing.
3. **The wait counts from the call's start**, so a call ends near 100 s plus the report, under Claude Code's 120 s tool limit (T6), whatever the keying took.
4. **Origin `commit`.** A result the commit worktree stored reads "run in the commit's worktree" in this call. Without `--run` a result from a commit daemon still reads "run in worktree <id>"; the worktree's id is fixed by its folder, so a later row can name it there too.
5. **The working tree's daemon is started with `squeal start`**, which also clears a `squeal stop` mark and ends command holds, as `squeal start` does. The brief says "as `squeal start` does"; the coordinator may prefer a start that keeps the stop mark.
6. **`--wait` alone joins only what the daemons list as pending.** A request a commit daemon recorded and has not taken yet (its lookup pass still runs) is not seen as pending, so such a file is not joined. A second `--run` call joins it instead (the queue shares the files).
7. **A file with no result whose daemon ran it and recorded nothing** reads `no result` (unknown). Only a failed setup or an unknown summary gives a reason.

## B2

Repair of review wave-23 B2 (recorded requests joinable). It replaces decision 6 above: `--wait` alone now also joins a narrow request a daemon recorded and its scheduler has not taken yet.

- **Daemon side** (spec 011 files, coordinator-approved). `PingResponse.recorded` is an additive field: each `run-group-paths` request the socket's request map holds that the scheduler has not taken, failed or answered unknown (`groupRequests().recorded()`), with `requestId`, `group` and `paths`, oldest first. The field is absent when there are none, and from an older daemon. Whole-group `run-group` requests are not listed: they name no files to join. The ping answer moved into `pingAnswer`, so `createHandlers`' switch does not grow (it was 49 already).
- **CLI side** (`status-at-join.ts`, `joinBoth`). For each side (the commit worktree that `find` returns, and the user's worktree), the call's files with no result there are joined when the daemon lists them pending (as before) or when a recorded request selects them: the same group, and a request path equal to the file or a folder above it (`selects`). Each such request is followed by `run-group-status` (`joinRequestAt`, then `takenRequest`, as `run <group> --wait` follows its own request) until it is taken, failed or the call's deadline. Then the side's wait covers its files. At the deadline, a request that is still recorded keeps its files `queued`, so Q7's line prints and "nothing is queued" does not. It asks nothing and starts nothing.
- **Interface.** `AtDaemons extends RecordedJoins` (`recorded?`, `joinRequest?`, both optional, so stand-ins are unchanged); `realDaemons` wires them over the daemon's socket. The `status-at-daemons.ts` and `status-at-call.ts` edits were agreed with the coordinator: each is in its own commit.
- **Not matched.** A recorded request whose paths are source files (`squeal run <group> src/x.ts`) selects its test files only once the scheduler takes it, so the join cannot see which files it covers before then. `status --at --run` always sends test file paths, so Q7's follow-up is covered.
- **Tests.** `test/daemon/run-group-paths.test.ts`: ping lists two held narrow requests, not the whole-group one; it drops each as it is taken or failed. `test/cli/status-at-join-recorded.test.ts`: real handlers on real sockets for both daemons, with the scheduler held. A first `--run` leaves both requests recorded. Then Q7's exact `--wait 100000` call is observed asking `run-group-status` for both requests while they are held (barrier), waits for them, then their files; it queues no run, exits 0, and never prints "nothing is queued". At `--wait 0` the files stay queued with Q7's line. Without the join (recorded list forced empty), both tests fail: the first call ends at once with "nothing is queued". The deadline case does not check that Q7's line is last: the stale `--run` advice after it is S2.
