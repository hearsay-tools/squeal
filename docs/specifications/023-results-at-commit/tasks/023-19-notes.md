## P3: `--run` at its budget

**Cause, diagnosed.** In r2 the clone's store was empty, so the gate had no stored duration. The gate's `chunksFor` (row 020-59) then makes one chunk, so the 1,338 files ran as one Vitest run. The gate keeps a run's files only once that run ends (its keeper hears a run when it ends). The run, its coverage mapping and its close took more than the budget plus the parent's 60 s grace on a host at load 58. The parent killed the group. The child had written no answer, and the run never ended, so nothing was kept or reported. The same loss happens to any run that cannot end in time: the regression test makes one with a Vitest `globalTeardown` that holds the gate's close.

**Fix.** `--run` runs its selection in batches of whole paths (the gate runs a path under every project that lists it), one gate child each:

1. Size. The first batch is one round of files at once (Vitest's width, `availableParallelism() - 1`), or, with stored durations, the paths whose estimate over that width reaches the batch's aim. The aim is a fifth of the budget, at least 20 s. After one batch size, the next is sized from the time per path, the child's start included. After two sizes, a least-squares line through (paths, seconds) gives a fixed start per batch and a cost per path (`costOf`); the next batch aims at the larger of the aim and four times the start, so the start costs at most a quarter of a batch. No number is tuned to this host: the width comes from the CPU count, the rest from the budget and the times measured. JSON `run.batches` gives each batch's paths and seconds.
2. Time. Each child's gate gets the time left minus a margin (`stopMargin`: a tenth of it, 5 s to 60 s). The parent stops the child's group at the end of the time left (`stopAfterSeconds`), not 60 s after it. No batch starts with less than 1 s for its gate.
3. Read back. A batch that answered is read back at once (023-18 D1: at the key the gate kept each file at). A batch the parent stopped has no answer. Its files are read at the key from before the run: the gate keeps a run's files as that run ends (row 020-59's early writes), and a chosen file's key held no result when it was chosen, so a result there is this run's. A file with no result there reads `not run (budget)`. The files of batches that never started read `not run (budget)`. A child that failed for a reason of its own (no command to start it, for example) stops the batches; the files left read that reason.
4. Estimate. Before the first batch, D17.1's estimate is told when `--all-missing` is given (as before), or when the selection is large for this machine and budget: an estimate over half the budget left, or, with no stored duration, more files than run at once. Without `--all-missing` the line adds how to narrow it: `to narrow it, name test files or folders: squeal status --at <commit> <path>... --run`.

**Default budget: 300 s.** Claude Code's longest Bash call is 600 s; at 600 s r2's call moved to the background and the agent lost the answer. The budget covers the checkout, the install, the keying and the run. Outside it are the current side's keying (no daemon, or P5's late files: about 50 s for every file of this repository), the checkout's removal and the report, all slower on a loaded host. Half of the call leaves that room. A selection that does not fit ends with the rerun line, and the next call finds the kept files in the store.

## P4: source paths

A path that selects no test file listed on a side (and that the side's tree holds) is a source path there. It selects the test files whose closure holds it (exact path, as `squeal status <path>` does):

- At the commit: `narrowedOrAll` does not narrow the checkout's listing when a path is a source path, so every listed file is keyed and each key's `loads` is read. This costs the full keying (about 50 s for 1,919 files here) only when a source path is named.
- Now, with a daemon: the daemon's stored closures through `storedReaders` (the code `squeal status <path>` uses). With no daemon: every listed file is keyed in the working tree and its `loads` read.

The report holds the union of both sides. A path that selects nothing on either side, and that the commit or the working tree holds, is not a file row: the text says `no test file's closure holds <path>, at <commit> or now`, the JSON lists it in `unmatched`, and the exit code is 3. A path that exists on neither side, or that a failed checkout could not answer, keeps the earlier behaviour (a row in the default project: `absent`, or `not determined`).

"The daemon lists no such test file" now appears only when the working tree's own keying does not list the file either ("no runner lists it").

## Decisions the brief did not settle

- **Source path selection is the union of both sides**: the files whose closure at the commit holds the path, and those whose closure holds it now. The brief names the commit's closure; the union adds a test that only reads the path now, which is the usual case for a new test of a changed source (r1's `active-run-write-index.test.ts`, `absent` at the commit).
- **Exact path for closures**, as `squeal status <path>` does; a folder of sources only selects test files below it by path.
- **A path that selects nothing exits 3.** The question about that path has no answer.
- **P5 falls back per file, not for the whole side**, when the daemon lists some files: the daemon's states stay for what it lists. A file neither the daemon nor the commit lists (and no path names) is not reported: finding it would key every file in the working tree.
- **A stopped child's files read `not run (budget)`** when their key holds no result, so the rerun line includes them. This applies to `squeal proof` too, through the shared `outcomesOf`, but only past its budget plus 60 s (proof passes no `stopAfterSeconds`), and its forced sides read nothing from the store.
- **Batches are sized in paths**, not files; a path listed under several projects counts once.

## Review wave-13 re-review repair (B2, completion record)

`reviews/wave-13-rereview.md` failed `cand/0.1.564` (`7827ce934`) on B2 alone. The newest-key store lookup lost the stopped run's own pass when a run in a linked worktree had meanwhile stored a newer result for the file at another key. A completed file that the gate did not keep (coverage off) read `not run (budget)`. The human chose "A: repair once more" (2026-11-19). This replaces the B2 repair above. The fix is in `bb1d93838`.

**Completion record.** Each `--run` batch child keeps a record of its own work in the run's folder (`<checkout folder>/at-run-record.json`). The child writes it whole each time it grows: a new file, then a rename, so a stop leaves the last whole record. The checkout's removal deletes it, and `runInChild` removes any old one before each child. It holds:

- `runs`: each run's file outcomes, per runner and path, as that run ended (`GateFileRun`); a rerun's outcome replaces the first run's.
- `kept`: per project and path, the key the keeper wrote the file at.
- `notKept`: per path, the keeper's reason for not keeping a completed file.

The gate tells these through additive hooks:

- `CollectOptions.ended`, from `lanes.ts` at each run's end;
- `KeepOptions.decided`, from the keeper after each queue step, each early pass and the last pass;
- `StoredOptions.decided`, `storedFiles`' last parameter and `runGateFiles`' `progress` option carry them.

A listener that throws costs only its own record.

**Reading it.** A child that gave no answer (stopped at the budget, or ended otherwise) is read from its record through the same path as an answer (`outcomesOf`):

- A kept file reads at its own kept key, as 023-18's D1 reads an answer.
- An unkept file reads its outcome with the gate's reason. With coverage off: `the gate keeps a result only with coverage on`.
- A completed file the keeper had not decided on yet reads its outcome, not stored, with `the run was stopped at the budget before the gate decided whether to keep it`.
- A file with no outcome in the record reads `not run (budget)` after a stop; after another ending, not determined with the child's error.

A child that answered is read from its answer: the answer is the record's final form, written at the end. No store lookup by the newest key and no provenance search is left. So a concurrent `--run` in a linked worktree that shares the store cannot change what a stopped run reports about itself.
