# Row 023-70 notes: a stored result passes D4.9 before the commit side uses it

Wave 34, worker B, brief `tasks/wave-34.md`. Spec D4.9, D7.3; review 0.1.610, "outside this wave". Branch `cez/42ac8fe0`, base `d5065ea6b`.

## Cause

`AtAsks.choose` (`src/core/daemon/at-asks.ts`) put a file with a result stored at its live key into `withResult` and skipped it before it applied D4.9 (`refusals` ran over `first` and `rest` only). `status-at-commit-rows.ts` then read the stored result as the commit's. The reviewer's case: the caller's run of `test/lists.test.ts` lists `test/fixtures/` with an ignored `extra.log` in it, so it passes; the key of a folder read hashes the names git tracks there (`Listings.hashOf`), not the names the run saw, so the pass is stored at the key the pristine commit has, where the file fails.

## Decision: not comparable, not "run again" (the coordinator agreed, request 47cad2c0)

- **Run again** would need the scheduler to run a file that is current at its key (a narrow request skips current files, `narrowAnswer`), and it would store a second outcome at the same shared key. `stateOf` pools every record at a key (any fail wins), so the working tree and other worktrees that share the key would read that outcome too.
- **Not comparable** keeps the store as it is and says why. It matches 023-64: a folder read is held only when the commit worktree's own run read the commit's listing.

## Rule

A result stored at the commit's key counts as the commit side's only when D4.9 holds for the tree that ran it:

1. A path git does not hold at the commit (the commit daemon's `needs`) refuses a stored file as it refuses a file to run. Before, stored files were never checked.
2. A folder read holds only for a result that the commit worktree wrote. A result that any other tree wrote (the caller's worktree, another worktree, an import) is refused with `needs <folder>/: its stored result ran in another worktree, whose listing of it is not recorded`. The coordinator's condition: judge the result by the listing its run saw. No record holds that listing (result records and the observed map hold paths only; `Listings` hashes tracked names), so the rule refuses.

Refused stored files leave `withResult`, so the working tree's side does not queue them because of the commit side, as with files refused before a run.

## Change

- `src/core/daemon/at-asks.ts`: `choose` collects the stored candidates (`StoredAt`), applies `needs` to them, and asks the optional port `storedNeeds` for folder reads that another tree ran (`storedRefusals`, `storedReason`).
- `src/core/daemon/commit-start.ts` (worker A's file, agreed in request 47cad2c0): `storedNeeds` reads each stored file's result writers (`store.results.byKey`), keeps the files whose results another worktree wrote, and returns their first folder read from `closureReads`.

## Type changes (additive)

- `AtAskPorts.storedNeeds?`, `StoredAt`, `storedReason` (exported from `at-asks.ts`).

## Review 0.1.611 repair (B1)

Worker of the repair, 2026-11-23. Review `reviews/0.1.611.md`, B1.

**Cause.** The check ran once, in `choose`, over the results stored when the ask selected. A file queued with no result could get one later from another worktree (the caller's narrow run held the group's slot and its key is shared); the commit's scheduler then had nothing to run, and `status-at-commit-rows.ts` read that pass as the commit's.

**Rule now (one rule, two points).** A file whose closure lists a folder holds only a result the commit worktree wrote, whenever the result arrives.

1. `choose` asks the new port `listings(refs)` for every chosen file (to run or stored) and `ownResult(ref, key)` for the stored ones. A stored file with a folder read is refused unless the commit worktree wrote a result at its key. Before, one foreign record beside the commit's own refused it; now the commit's own record holds.
2. Every chosen file with a folder read that is not refused goes into the ask's `ownOnly` (with `storedReason(listing)`). The reader (`rowsSide`) reads those files' records filtered to the commit tree's writer; if none is the commit's and another worktree's exists, the file reads `not comparable` with that reason (exit 3). The kept ask carries `ownOnly`, so a `--wait` that joins it, or any later read, applies it without a new request.

The judgment uses the result's writer (`provenance.worktreeId`) and the commit daemon's closure facts (`closureReads` with `listedDirectory`), not the commit folder's current names and not queue membership.

**Type change (additive).** `CommitAskState.ownOnly?: readonly CommitRefusal[]` in `src/core/types/commit-ask.ts` (outside the repair's listed ownership; needed to carry the fact from the daemon to the reader). `AtAskPorts.storedNeeds` is replaced by `listings?` and `ownResult?`.
