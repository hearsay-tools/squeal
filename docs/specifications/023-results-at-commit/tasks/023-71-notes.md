# 023-71 notes: a named file that waits at the commit (round 9, Y1)

Row 023-71, wave 34, worker A, 2026-11-23. Brief: `wave-34.md`, "Worker A". Base 0.1.610.

## What held the file: not the pool, not the shared slot

The brief's part 3 assumed that the named file waited for a pool permit. The code says it cannot:

- A named file of the `tests` group is in a batch. A batch's tier that the pool refuses goes on at once as an edit's tier, with no grant (`src/core/scheduler/tier-pass.ts`, the `refused` branch, row 011-308).
- A named file of a configured group (squawk's `browser` group: `at: manual`, `maxParallel: 1`, `maxWorkers: 1`, `priority: low`) is a narrow ask of its lane on both sides (`status --at --run` sends `run-group-paths` with `at` and, when it names paths, `lead`). `SlowTier.#explicit` is true for it, so the lane skips the load guard, and a pool refusal does not stop it: the tier runs without a grant (`src/core/scheduler/slow-tier.ts`, `#explicit` and `#select`).

The second suspect was the group's `maxParallel` slot. Its scope is the repository (`capacity.groupSlotScope` default), keyed by the repository id in the Git common dir. The commit worktree is a `git worktree add` of the same repository, so the working tree's daemon and the commit daemon share one browser slot. Other sessions' clones have their own ids, so the slot is not shared across sessions.

`test/scheduler/named-slot-wait.test.ts` proves both with two real schedulers in one repository (a main worktree and a linked one, one store, one pool, one slot directory):

1. The working tree holds the browser slot with an unnamed file. The commit side queues every browser file, then a narrowed call names one (`lead`). When the working tree's file ends, the named file takes the slot before the working tree's next file (the handover of spec 004 D2: a holder that took the slot last yields one turn to a marked waiter, and the named file leads the waiter's queue).
2. Every pool permit is held by another daemon's background tier (`acquire(200, "fast", 1, "backlog")`, 8 of 8). The named file still runs, on an idle host and at a load of 5 per CPU.

All three cases pass on the base without a change. So no pool rule was added (the coordinator's reply to request 1692ec67: "No pool rule unless the test shows the pool"). Nothing in `src/core/scheduler/` or `src/core/capacity/` changed.

## The likely hold: the narrow ask dropped by a re-key

`CommitAsks.prune` drops an ask once neither the file's key nor its run in flight is the asked key. A file of a `manual` group whose ask went has no trigger left: it stays queued, and only `squeal run <group>` runs it. That matches round 9: the commit daemon had "1 pending" and no test process for up to 930 s, and used 12 s of CPU in 15 minutes. Worker B found the same drop for 023-72/74 and changes `commit-asks.ts` so a pending file keeps its ask across a re-key (coordinator's note, 2026-11-23). Not proven for Y1 here: round 9's data has no daemon log, and the re-key's cause at the commit is not reproduced. Round 10 should check that the named browser file starts at the commit within one browser file's time.

## What changed (parts 1 and 2)

- **State.** `QueuedSide.queued` (new, optional): the call's files on a side that are queued and not started (`pending: "queued"`). `running` keeps its meaning, queued or running. The named line: `<paths>: 1 of 1 queued at <c>[, waiting for <reason>], …`; with some started, `1 of 2 running and 1 queued at <c>…`. The Q7 line: `<n> running and <m> queued at <c> (its worktree), …` when any is queued. Worker B's `status-at-report-narrow.ts` and `status-at-report-queued.ts`, by agreement (request 1692ec67), in their own commit.
- **Reason.** `QueuedSide.waiting` (new, optional), only from what the side's daemon publishes for the lane of each queued file's group (`readGroupActivity`): `the <g> group's slot, which another daemon holds`; `a free test process: the shared worker pool's N permits are held by other work` (N is `capacity.hostSlots`); `the host load to drop`; `the work the <g> group runs after`; `the agent to pause`; `the <g> group's run of <path> to end`. A group that publishes nothing (the default `tests` group; a lane on hold, behind runner work, or with its ask dropped) gives no reason: the line says only `queued at <c>`. Several groups with different waits join with `; `. `src/cli/status-at-estimate-waits.ts`.
- **Estimate.** A narrowed call's side whose every named file still to run is queued and not started gets `SideEstimate.waiting` (new, optional) and no time: `1 test file, time unknown: waiting for capacity (<reason>)` for a slot or pool wait, `not started, waiting for <reason>` for another published wait, `not started yet, and the daemon does not say what holds it` with none. A wide call is unchanged: its queue ahead is in its estimate.

Only narrowed calls read the waits (one read of the main store per call). `readMainStore` in `status-at-estimate-named.ts` is `runsInFlight`'s store read, shared.
