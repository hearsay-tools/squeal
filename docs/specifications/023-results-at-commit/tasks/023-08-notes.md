## Flow

The human, 2026-11-18, after the re-review ("A: clean checkout"): the green side is always keyed in a temporary checkout at committed `HEAD` after its frozen install, exactly as the red side is keyed, then read from the store at that key, and run there only without a result. Proof never reads the working tree, its daemon or its keyer.

1. Locate the worktree, `--base` and committed `HEAD`; named paths relative to the root.
2. Green checkout (`withSide`, side `HEAD` over `HEAD`, `listed`): the runners there list the named paths with their projects; each is keyed, refused (D4.9) or read from the store at its key. A named path no runner lists at `HEAD` reads `not comparable (no runner lists it at <head>)` on both sides.
3. While the green checkout is open:
   1. Case: `--case`, or `defaultCase` per file over the diff `base..HEAD` and each file's closure in the green checkout; files that need different cases, or no case, are a usage error (exit 2).
   2. Red side (`runSide`) in a checkout of its own: `sideKeys` at the code version with the named files and `testSideCopies` (test-side paths the test version holds otherwise) copied in. The install, then the whole-checkout check against the side's expected tree. Per keyed file: `missingImport` → `not comparable (imports <path>, absent at <code>)`; D4.9 `needsOf` → `not comparable (needs <path>)`; a stored result at the key (checkout unchanged) → read; else run. Runs go through `runInChild` with `store: changed === null`, read back by `outcomesOf`.
   3. Green runs, in its checkout, the files whose red side failed on assertions alone and that it holds no result for.
4. Failure evidence (review wave-8 B1 and its re-review): a stored run's failures are read at the file's own key for its own project (`resultsAt`, `endOfRecords`). The gate's answer is by path; an unstored run (coverage off, or a changed checkout) takes its failures from it only when every project that ran the path failed with the same evidence (each test's errors: name, message, stack, diff, code, causes, phase; a timeout's load aside) (`sharedFailures`). Otherwise the file reads `not comparable (its N projects failed with different failures, ...)`, `from: run`, and counts as run. A path's timeout counts only when every project's run of it was stopped.
5. Dirty: any path `git diff HEAD` or the untracked list holds gives one line that the proof is of committed `HEAD`, naming up to five paths. It changes nothing else.
6. Verdict per file, report (with each side's own checkout time), exit (`proofExit`).

The two sides never share a checkout: in the `source` case their code versions differ, and in the `test` case the red side's checkout holds the base test files over `HEAD`'s code, another expected tree than `HEAD`'s. The red checkout opens and closes inside the green one's lifetime.

One budget (`--timeout`, 600 s) over the whole call: each side's run gets what is left; each install gets `min(300 s, left)`.

## Decisions the spec did not settle

- **Test side.** Runners do not give their include globs, so a path is test-side when it is a named test, lies in a folder named `test`, `tests`, `__tests__`, `spec`, `specs`, `__mocks__`, `fixtures`, `__fixtures__`, `__snapshots__` or `testdata`, or has a test file's name (`*.test.*`, `*.spec.*`, `*_test.*`, `test_*.py`). A helper in another folder (for example `src/test-utils.ts`) counts as code.
- **Copy set.** Every test-side path the test version holds otherwise than the code version, not only those the test loads: the closure at the test version is only known after keying in the checkout, and a file the test does not load changes neither its key nor its run. Test-side paths the test version lacks are not deleted from the checkout.
- **Missing source import.** A code-side path in the closure in the side's checkout that the code version lacks and the test version holds. Resolution candidates both versions lack are no import.
- **Assertion.** An error whose class name is `AssertionError` or whose code is `ERR_ASSERTION`, with no `phase` and no recorded `loadAverage`. A failed test is an assertion only when every error it recorded is one; a failure with no recorded error is not. A missing named export fails inside the test as a `TypeError` in Vitest (probed: `(0, __vite_ssr_import_1__.b) is not a function`), so it reads `red for another reason`; so does a fix for a crash (the old code throws `TypeError`). Kinds: `import` (phase `load`), `setup`, `hook` (`after-tests`), `timeout` (a recorded load average; absent on Windows, where a timeout reads `error`), `error`.
- **Red side not finished** (budget stopped it): `red for another reason`. **Not started** for want of budget: `not comparable (not run (budget))`. A failed node:test `prepare`: `red for another reason`.
- **Green side** is keyed for every file; it runs only after a red side that failed on assertions alone. For every other red verdict it is shown only when the store held its result (else `green: not read`). The second call of a proven file reads both sides with no run.
- **Green checkout failure** (it could not be made or installed): no case is decided and no red side is made; every file reads `not comparable` with the checkout's reason, case `not decided`.
- **Exit.** 3 outweighs 1 when files have both (an unknown answer, as D1).
- **Default case per file**; files that need different cases are refused with a usage error asking for `--case` or separate calls.
- **Dirty tree**: any tracked change, staged change, deletion or untracked (not ignored) file gives the line; both sides are committed versions in checkouts, so an installed `node_modules` that differs from the committed lockfile cannot reach either side (re-review B2).
- **Unstored projects of one path** (review wave-8 B1 and re-review): they share failure evidence only when it is the same; with coverage off or a changed checkout and projects whose failures differ in any shown way, each reads `not comparable` on every call. Each project's own text would need the gate to answer by project.
- **A named test not committed at `HEAD`** reads `not comparable` (absent at `HEAD`) in the source case, with the dirty line: commit it first.
- The run count is the files that ran, summed over both sides.
