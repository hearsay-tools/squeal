# Row 023-60 (W3) notes: a named file inside a running batch at the commit

Wave 30, worker A, brief `tasks/wave-30.md`. Spec D7.3; round 7 W3 (`../lessons.md`, "Round 7 (023-56)"). Branch `cez/bd82ba48`, base `534e2b20c`.

## Cause

A call that names a file queues it with `lead` (rows 023-34, 023-50): the file leaves its earlier batch for a new leading batch (rank below 0). When the file is already **running** in the commit daemon's batch tier (round 7: about 65 files at the grant), nothing changes for it. `rankToBeat` takes the least rank among the tier's unfinished files, which is now the named file's own rank, so no wait beats it, and the yield check answers `named`. The file's result lands from the run's report, when the whole tier ends: 250 to 420 s in round 7, while the call said "about 3 s".

Reproduced with a real scheduler before the change: a 40-file batch tier at 4 workers, the named file current only at the tier's end (14.8 s against its own 1.5 s).

## What the runners allow

- Only Vitest reports each file's end during a run (`RunOptions.fileEnded`, `onTestModuleEnd`). node:test and pytest do not.
- No runner gives a file's results before the run's report. The scheduler stores a file only from the report, after the completion barrier and the stability check (`storeDecision`). Storing per file as it ends would change the runner interface and the store path for every runner.
- node:test and pytest keep a batch's files in edit-sized tiers or slots (`batchFiles`: `backlogSlot`), and their runs ignore a cancel. The wide batch tier, and so W3, is a Vitest case.

So the fix is the "lead" mechanism, done with the existing yield: cut the tier.

## Change: the cut (scheduler, coordinator-approved, request 5659a672)

`src/core/scheduler/lead-cut.ts` (new), called from `decide` in `decide-yields.ts`, right after the supersession and backlog cancels. A tier yields (`"yield"`, the existing cancel) when all of these hold:

- It can be cut: it has a cancel, and it is no slot, turn, slow or focused tier.
- It holds no file an earlier yield cut (the `marks`). The cut marks every unfinished file of the tier, the leading ones too, so a leading batch is cut for at most once, and the tier that runs the cut files later is never cut again.
- Files of the least-ranked **leading** batch (rank below 0) are in it, beside unfinished files outside that batch.
- Its work left exceeds those files' own time by more than `YIELD_REMAINDER_MS` (30 s). Work left (`workLeft`): its files run at the grant's width, so the whole tier takes the longer of its longest file and its summed durations over the width; less the time it ran; at most its unfinished files' sum over the width; at least its longest unfinished file's time left. A file with no stored duration counts 0, as `remainder` counts it.

After the cut: the tier's ended files keep their results (a cancelled Vitest run completes the files whose module ended); its other files go back to their batch, so they keep their place ahead of the backlog; the leading batch ranks first and runs next, alone. The history records the yield as `to: "promoted"`.

**Effect for everyone.** Only calls that name paths form leading batches: `status --at <c> <path>... --run`, on both sides (the commit daemon's ask, `at-asks.ts`, and the working tree's narrow requests, `status-at-call-sides.ts`); nothing else sends `lead`. A plain `status --wait`, `squeal run <group> <path>`, a wide call, a backlog tier and a batch tier with no leading file are not cut by this rule. The work run again is bounded by the tier's in-progress files, at most its grant (in round 7, a few files against about 65 that waited).

## Change: the named file's time (CLI)

`src/cli/status-at-estimate-named.ts` (new): `runsInFlight` reads each daemon's runs in flight since its start from the main store (read-only); `namedRun` finds, for a narrowed call's files still running, the newest run in flight that holds one beside a file outside the call, and its time left (the same rule: summed stored durations over the side's width, times the load factor, less its run); `namedRunText` writes `test/store/open.test.ts runs in a batch of 65 test files started 98 s ago; its result comes when that batch ends (about 4 min)`.

Wiring in worker B's files, by agreement, its own commit: `SideEstimate.batch?` (additive) and its text appended to `sideText`; `estimateOf` sets it for a narrowed call and counts at least the batch's time left in `seconds`. JSON: `run.estimate.{commit,now}.batch` (`named`, `files`, `startedAt`, `ran`, `seconds`). The basis rule is unchanged.

So the estimate is true both ways: when the cut runs the file alone, its run holds only the call's files and its own time stands; when the tier is not cut (within 30 s, or cut once already), the line names the batch and its time left.

## Tests

- `test/daemon/at-asks-running.test.ts`: a real scheduler as a commit daemon (lookup-only; durations stored by another worktree), `AtAsks` over it, a wide ask's batch tier of 40 files at 4 workers. (1) A narrowed ask's file is current within its own 0.5 s plus 5 s while the tier is held; the tier is cancelled, the next run is the file alone, the other 39 keep their batch place and run next. (2) The four files that ended before the cut keep their results and do not run again. (3) A request without `lead` does not cut. (4) A tier whose work left is within 30 s of the file's own is not cut. (5) Two leading calls in a row: the second, inside the cut batch's next tier, does not cut it. Cases 1, 2 and 5 fail without the rule.

- `test/cli/status-at-estimate-named-call.test.ts`: `status --at <c> <file> --run --json` with a stand-in commit daemon whose batch run is in flight: `estimate.commit.batch` is set and `seconds` counts it; with the file running alone, no `batch`. Fails without the wiring.

## Decisions the spec did not settle

- **Cut, not a second run beside.** Running the named file again beside the batch would leave one file in two tiers at one key; the ledger keeps one `runningKey` per file, and its end handling assumes one tier.
- **Leading batches only.** A non-leading named wait on a file inside a backlog tier is unchanged (W3's calls lead).
- **The estimate's seconds** is at least the batch's time left when a named file runs inside one, so the headline time is not "about 3 s" while the result waits minutes. The brief asks for a true estimate; the coordinator asked for additive wiring, and this is the one non-text change in it.
