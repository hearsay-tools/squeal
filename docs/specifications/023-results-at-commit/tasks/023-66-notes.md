# Row 023-66 (V2) notes: the call's measured rate is per group

Wave 32, worker B, brief `tasks/wave-32.md`. Spec D3 and D7.3; round 8 V2 (`../lessons.md`, "Round 8 (023-63)"). Branch `cez/a2cf10c6`, base `fbbd232bc`.

## Cause

`estimateSide` (`src/cli/status-at-estimate.ts`) took one rate per side: the call's results on that side (`measured.done`) over the call's time, applied to every file still to run there. In round 8 s1 the 14 results were unit files. The 96 files left were browser files, which run one at a time at 30 to 135 s each, so "about 11 min for 96 test files, at this call's rate there (14 results in 98 s)" was off by a factor of 5 or more.

## Change

- `status-at-call-run.ts` passes each side's finished files (`done`) to `workGroups` beside the files still to run.
- `workGroups` (`status-at-estimate-groups.ts`) counts them per group by the side's own policy. Each `WorkGroup` gets its `name` and `done` (additive fields). It also returns `doneIn`, per side the result count of a file's group.
- `byGroup` (`status-at-estimate-rate.ts`, new) estimates each group still to run alone when the call measured results on the side and counted them per group:
  - its own rate, when at least `MEASURED_LEAST` (10) results arrived in it;
  - else its own stored durations under V2's rules (`tooFew`), with its own median for a file without one, at its own width;
  - else time unknown.
  The side takes its longest group's time, unknown when any group's is unknown.
- `groupedSeconds` and `groupWidth` moved from `status-at-estimate.ts` to `status-at-estimate-rate.ts` (the estimate file was over 300 lines).
- The named file's batch (row 023-60) is timed at the rate of that file's group (`groupBatch` in `status-at-call-run.ts`). `namedRun` is unchanged (worker A owns it this wave): the call asks it once to find the batch, then again with the group's rate.

## Text

- One group left, rated by its own results, with no results elsewhere: as before, `about 12 min for 100 test files, at this call's rate there (14 results in 98 s)`.
- One group left, rated, with results in other groups too: `… at this call's rate for the tests group (12 results in 98 s)`.
- One group left with no rate of its own: `96 test files, time unknown: none has a stored duration and this call measured no rate for the browser group (0 of its 14 results there in 98 s were that group's)`. With too few stored: `time unknown: too few runs stored (3 of them have a stored duration) and this call measured no rate for the browser group (…)`. With enough stored: the stored-durations text as before.
- Two or more groups left: `30 test files, time unknown, by group: tests: about 3 min for 20 test files, at this call's rate for the tests group (12 results in 98 s); browser: 10 test files, time unknown: …`. With every group known: `about 10 min for 30 test files, by group: …`.

## Type changes (all additive)

- `WorkGroup.name?`, `WorkGroup.done?`.
- `SideFiles.done?`.
- `workGroups` returns `SideGroups` with `doneIn` beside `groups` and `unknown`.
- `SideEstimate.basis` gains `"groups"`; `SideEstimate.group?`, `.elsewhere?` (`{ done, own, seconds }`), `.groups?` (`GroupEstimate[]`). JSON `run.estimate.commit` and `run.estimate.now` carry them.
- New `GroupEstimate` (a `SideEstimate` with `group`).

## Decisions the spec did not settle

- **Per-group only after a measurement.** A join (`--wait` alone) and a call that measured no result on a side keep the whole-side estimate. Per-group parts appear only when the side has a rate from some group, because only then can a rate be applied to the wrong group.
- **A side whose tree is gone** (its limits not read) has one group and no per-group count: the side's rate, as before. It has one group only, so the rate cannot cross groups.
- **Groups run beside each other.** With per-group parts, the side takes its longest group; the pool share over all groups is not added (the measured rates already hold it). The whole-side path keeps it.
