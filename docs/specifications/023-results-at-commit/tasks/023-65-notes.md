# Row 023-65 (W3's rest) notes: cut a named file out of a batch whose time is unknown

Wave 32, worker A, brief `tasks/wave-32.md`. Spec D7.3; round 8 W3 (`../lessons.md`, "Round 8 (023-63)"); row 023-60 (`tasks/023-60-notes.md`). Branch `cez/3f115c68`, base `fbbd232bc`.

## Cause

W3's cut (`src/core/scheduler/lead-cut.ts`) compares the tier's work left with the leading files' own time. A file with no stored duration counts 0 in both. On an empty store (round 8 s2-01, 03, 05: 21 of the batch's 200 files had a stored duration) the work left was a few seconds, so the 30 s margin was never passed, and the named file waited for the whole batch. s2-05 ended without its result.

## Change (scheduler)

In `leadCut`, after W3's rules (a cancel, no slot, turn, slow or focused tier, no file an earlier cut marked, files of the least-ranked leading batch beside files outside it):

- When the tier's stored durations are too few to estimate (`tooFewStored(known, files)`, where `known` counts the tier's files with a stored duration), the tier is cut when more than `UNKNOWN_CUT_FILES` (20) of its unfinished files are outside the leading batch. The time rule does not apply then.
- Otherwise the time rule stands as before.

`tooFewStored` is the call's `tooFew` floor (`src/cli/status-at-estimate.ts`: fewer than 1 in 5 files known, or fewer than 10 known and fewer than half). The scheduler cannot import the CLI, so the floor is written twice. A test checks that the two agree for every count up to 220 files. So the tier the call reads as "time unknown" is the tier this rule cuts.

W3's rules are kept: at most one cut per batch (the marks), never a re-cut of the tier that runs the cut files, and only tiers that can be cancelled and are no slot (node:test and pytest keep a batch's files in slots, so this is the Vitest case).

### Why 20

The count is of unfinished files outside the leading batch, not of all the files the batch holds: a batch of 200 with 3 files left is not worth a cut. A batch tier runs at the grant's width, at most about 12 workers on the machines this has run on. 20 files are then at least two rounds, so without the cut the named file waits at least one more round of files whose length is unknown. A cut costs at most one round: the tier's files in progress run again. At or under 20 the call keeps its existing line, "its result waits for the batch that holds it … (time unknown …)", which is true.

## Change (CLI text; by agreement, requests 353abdfe and 6de8442b)

The brief asks the call to say that the file runs on its own. `namedRun` and `namedRunText` (`src/cli/status-at-estimate-named.ts`, worker B's file; the coordinator gave these two functions to this row for the wave) and one condition in `ownText` (`src/cli/status-at-estimate.ts`), in their own commit (subject "023-65 text"):

- `namedRunText` writes `test/store/open.test.ts runs on its own (about 3 s)`, or `(time unknown: it has no stored duration)`. With several named files: `… and 2 more named test files run on their own (…)`.
- `ownText` no longer says "its result waits for the batch that holds it" for a lone run.
- JSON: `run.estimate.<side>.batch` is set with `alone: true` for a lone run (additive). Before, it was absent.

Not done, and why: the coordinator asked for "cut out of a batch of 200 test files". The call reads the runs in flight only (`store.runs.inFlight`), and the cut ends the batch's run, so the call cannot see the batch the file came from. That needs a store query for runs ended since the daemon's start, which is outside this row. The side is already named at the start of the line (`Still to run, at <commit>: …`), so the text does not repeat the commit.
