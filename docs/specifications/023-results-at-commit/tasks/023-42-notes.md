# Row 023-42 notes: `proof`'s green side on the commit daemon

Wave 26, brief `tasks/wave-26.md`. Spec D7.6. Base: main at 0.1.596 (`8831b2890`). Branch `cez/3d833979`.

## What changed

A green side with no condition and no repeat (`--env`, `--without` and `--repeat` absent; `--case dependency` always has a condition) no longer keys in a temporary checkout at HEAD. `proof` now:

1. Makes the commit worktree at HEAD with no install, and starts its daemon when none serves it (`AtDaemons.commit`, the same call `status --at --run` makes, D7.1). It is the same worktree `status --at` uses, so either command reuses it.
2. Reads the daemon's setup (`commit-read`) every 250 ms until it is `ready`, `failed` or `changed`, or the deadline.
3. Reads each named path's rows of that worktree from the shared store (`daemonKeyed`, `proof-green-rows.ts`): every project that lists the path, its live key, the results stored at that key, and its stored closure. The case choice, the stop's marks and D4.9 read that closure. A closure holds for the row when the daemon wrote it, or when its writer's current key for the file is the same key (the `storedReaders` rule).
4. A file with a stored result is read, not run (D5.1). A file with none is asked of the daemon at once, by its own path, with no change (`askGreen`, `proof-green-run.ts`). This happens before the red side runs. The call waits for the run only when the red side decides (`readGreen`): it waits for the file, then reads it again at its live key.
5. The red side and P9's control run are unchanged: each runs in its own temporary checkout. A green side under a condition, or repeated, stays in its temporary checkout as before (`withSide`).

Files: `src/cli/proof-green.ts` (the flow), `proof-green-rows.ts` (rows and closures), `proof-green-run.ts` (the ask and the read), `proof.ts` (`withGreen` chooses; `greenDaemon` builds the commit worktree's input as `status --at` does: the commit's own `env.allowlist`, `daemon.maxCommitDaemons`).

Reuse only, with no behaviour change: `readUntilQueued` and `Read` (`status-at-commit-ask.ts`), `keptAlive` (`status-at-now-ask.ts`) and `commitAllowlist` (`status-at-call.ts`) are exported.

## One deadline

The proof's `--timeout` (`deadline`, `performance.now()`) is turned into epoch ms once (`by`). The worktree add, the daemon's start and socket wait (`AtDaemons.commit` with `deadline: by`), each setup read, the ask, its reads and the files' wait end by `by`. Each pending wait is wrapped in `keptAlive`. If the setup is not done by `by`, every named file reads `not run (budget)`. If a run is not done by `by`, that file reads `not run (budget)`. Either way the report prints the rerun line with a longer `--timeout`, and the daemon goes on. The rerun reads the result. Tested: the daemon's install held by a barrier, `--timeout 6`: exit 3, `reason: budget`, `notRun: 1`, the rerun line, in under 10 s.

## Refusals (D5.5)

- **Whole-checkout check.** The daemon's setup `changed` (git's checkout rules, or the install, changed a tracked path): every named file reads not comparable with `changedText` ("install changed the checkout: <path>"). Nothing is keyed, so the red side does not run. In 0.1.596 the green side ran in a changed checkout and was not stored, and the verdict still came out. That behaviour now applies only to the red side and to conditioned green sides (the brief: "they answer not comparable").
- **A failed setup**: not comparable, "the commit daemon's setup at <c> failed: <its text>". In 0.1.596 the reason was "install: exit 1"; now the daemon's own text follows it.
- **D4.9**: the call checks each row's stored closure with `needsOf` against the commit worktree. The daemon refuses a file it was asked to run (`refused` in the ask). Either refusal reads `needs <path>`.

## Decisions the spec did not settle

1. **Dirty HEAD: no change in what users see.** The green side is the committed HEAD. The commit worktree is checked out from the commit, so the working tree's uncommitted changes never reach it. The report keeps 0.1.596's line, "This proves the committed HEAD <h>, not the uncommitted change to <paths>". Nothing is refused and nothing is read from the working tree. Test: `proof-green-daemon.test.ts`, "proves the committed HEAD when the working tree changes the code the test loads" (the worktree's `src/a.ts` is HEAD's blob).
2. **The early green ask** (the coordinator kept it, request `d710c888`). Asked after the red run, the daemon read the red run's result as green's in `proof-mutated.test.ts`. That test rewrites an input the key did not cover yet. Under 0.1.596's order, the red run was kept at the key HEAD's file has before its first run, and the green side read "not green". Asked first, the green run records the read. The red run's key then differs, and the gate does not keep the red run. Cost: one green run also when the red side passes or fails for another reason. That run is stored, so a later proof shows "green: pass, stored result" where 0.1.596 printed the "not run" line. `proof.test.ts` keeps the "not run" line's check on a fresh repository.
3. **A stored green failure is read as it is.** 0.1.596 ran again a stored failure that does not record where in the test it happened (`reusable`, review wave-14 B2). That rule matters for the red side's evidence. On the green side any failure is "not green", and the daemon does not run a file that has a result. So the green side reads every stored result.
4. **Observed folder reads.** The daemon's stored closure holds the reads Squeal observed, such as `test/fixtures/` or `./`. The checkout keyer's closure never held them. D4.9 read such a folder as a path git does not hold. The proof side (`greenNeeds`) and, coordinator-approved, the commit daemon (`commit-start.ts`, the `needs` port) now hold a folder when the commit tracks a file under it. `status --at --run` had the same false refusal. Its test, `status-at-commit-refused.test.ts` "row 023-42: runs a file whose recorded reads list a folder the commit tracks", fails without the fix with `not comparable`.

## Investigation: a side reading the other code version's result (the coordinator; issue #264)

Test: `test/cli/proof-shared-key.test.ts`.

- **`--source`, the product file read at run time or imported: not reproduced.** Over 4 calls each (2 plain, one with `--env`, one plain after it) the verdict is always `proven`, with red failing from A's code. Mechanism, from a probe:
  - Before any run, both commits give the runtime-read test the same key (`79c61271`).
  - Each run is kept at the key taken after it, and that key covers the file the run read: A at `6d9af29c`, HEAD at `14731293`.
  - So nothing is ever stored at the shared key from before the run, and neither side reads the other's result.
  - The imported case has different keys from the start (`37a899cf`, `518d360b`).
- **A real wrong-result path, narrower: a test that rewrites an input it reads for the first time.**
  - (a) Unconditioned sides are stored, and so is P9's control run under a condition.
  - (b) The control run of such a test is kept at the key the file has at both commits before any run (`8a87c5ed`). The input it read is not recorded: after the proof, A and HEAD both still key `8a87c5ed`.
  - (c) So HEAD's key holds A's failure for every reader at HEAD. A temporary checkout at HEAD reads `stored=[fail, pass]`. Plain `status --at`, `proof`'s sides and a worktree daemon at HEAD key it the same way (D2). It persists, because no later run records the read.
  - The repro is the `it.fails` case. It is the known defect "rewritten first-seen input kept at the pre-run key", the board row the coordinator adds beside #264.
  - The cause is the gate's keep rule for a first-seen input that changed during the run (spec 020 and 018 code). It is outside this row, and not fixed here (the coordinator: "Do not fix the gate").
