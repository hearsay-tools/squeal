# One-step installation for a fixed Codex wrapper

Use one fixed plugin with a bundled fallback runtime and a Squeal-owned external runtime updater; do not require a second plugin.

Row 002-28 / wave 3 R3. Researched 2026-10-27 on Linux, Codex CLI 0.164.0, Node 24.21.0. Source tag `rust-v0.164.0`, commit `6aaac694803004a63c6f393d153c96d22521a6b9`. Read both prior reports and `tasks/stable-wrapper-design.md`. This is a recommendation, not an approved design or a product change. Only scratch homes and harmless fixtures were used. No model request or real release install was made.

## Supported mechanisms and their limits

**Read in source code, 0.164.0.** `RawPluginManifest` contains identity, skills, MCP servers, apps, hooks, interface and extensions. It has no dependency resolver or lifecycle-script fields. `RawAgentPluginManifest` also has no dependency field. `install_resolved_plugin` materializes one source, calls the store, enables that plugin and records telemetry. The store validates its name/version and replaces its cache root. None of these paths runs the plugin's code. The npm path packs and unpacks one archive; it does not run `npm install` or resolve its package dependencies. Bundled dependency bytes may travel in the archive, but that is packaging, not installation of a second plugin.

**Read in official docs, fetched 2026-10-27.** The build guide states: “Codex downloads the package without running lifecycle scripts.” Its onboarding section says: “When users run setup, it invokes the skill in a new conversation”. This does not guarantee setup before a model turn. MCP launch is a server lifecycle, not a general plugin installation contract. No dependency/bootstrap guarantee was found there either. These live docs can describe newer clients; versioned source and the installed binary decide the 0.164.0 findings.

**Verified by experiment, 0.164.0.** A local marketplace exposes `probe` and `required-runtime`. The first plugin declares candidate `dependencies` and `scripts.postinstall` fields, plus npm package dependencies and postinstall. `plugin add probe@install-probe` succeeds, installs only `probe`, runs neither marker script and does not run its SessionStart bootstrap. After explicit approval, `thread/start` followed by `thread/archive`, without `turn/start`, still does not run SessionStart. Acceptance of unknown JSON fields is not support.

**Read in source code, 0.164.0.** `core/src/session/turn.rs:340` awaits `run_pending_session_start_hooks` before ordinary sampling. A stopping result returns from the turn. `hook_runtime.rs:127–180` dispatches the pending startup/resume source and records its context. Thus a synchronous approved startup hook can prepare runtime bytes before the first ordinary model request. It cannot prepare them at `plugin add` or at `thread/start` alone. No complete first-turn boundary was run in this research.

**Read in official docs / inferred.** Command hooks have configurable timeouts; most default to 600 seconds, while SessionEnd/Interrupt cap at 3 seconds. Squeal currently sets 2 seconds for startup. Do not put an unbounded network download in that budget. A timeout is not proof of successful installation or a reliable denial. A handled bootstrap failure can return `systemMessage`, `additionalContext` and `continue:false` from SessionStart. The source handles stopping before sampling. Shell replay verifies the output shape only, not the actual stopping behavior. Trust-disabled hooks cannot report their own absence; Codex's hook warning and explicit setup/status checks remain necessary.

## Recommended one-step flow

The following is an **inferred custom proposal**, not built-in Codex dependency management. It replaces the two-plugin D7 proposal; the coordinator must amend the spec before implementation.

1. Publish one hook-owning `squeal` plugin. Freeze its entire contents, including manifest, bootstrap, declarations, skill entry points and a known-good seed runtime. On the first approved SessionStart, use a valid external runtime if present; otherwise publish a complete copy of the seed outside the plugin root and use it. Direct `/plugins` installation or `codex plugin add squeal@hearsay` then needs no second plugin. Hook approval and repository setup remain explicit existing steps; “one-step” describes component installation, not bypassing those steps.
2. Have `install.sh` provision the current runtime through the same installer before reporting success. Have setup check runtime readiness as well as plugin presence and trust. Today `install.sh` installs the plugin and prints `squeal setup`; it does not provision this proposed runtime. Setup's `readHarnesses` also checks the current single plugin, so neither existing path already implements the split.
3. Make `squeal update` own runtime updates, independent of the wrapper's version. Today it calls `codex plugin marketplace upgrade hearsay`; upgrading a byte-identical wrapper cannot supply new runtime bytes. A release artifact must carry the runtime version and provenance. Stage it, validate its identity/integrity and required files, then publish atomically. Preserve the usable version on failure. Codex still approves wrapper changes; Squeal verifies runtime releases under an explicitly disclosed update policy.
4. Keep tool-boundary hooks local. If automatic runtime freshness is required for direct-install users, add a bounded update check at session startup with a persisted retry interval and one updater lock. Start this only after a valid runtime is available, or keep it outside the hook via the explicit updater. A background check must not delay the first usable seed or change the running session. This is additional custom behavior, not proven here. No fetch per tool call.
5. Pin each session to a complete runtime version, including its skill files, daemon recorder and reporters. Retain versions in use. Keep one owner of every hook during migration; remove the old hook declarations rather than installing both. A fixed skill can direct the agent to the retained runtime's skill; changing a bundled skill would invalidate wrapper trust. Pinning, migration and cleanup remain unimplemented.

The deciding tradeoff is seed size and age versus cold-start reliability. A tiny downloader-only wrapper is smaller, but a direct install followed by first use offline cannot validate. A frozen seed gives that path usable bytes, although it may be old. It must remain compatible with the supported Node/platform and runtime protocol; a seed or bootstrap repair is a wrapper update requiring fresh approval. There is no guarantee that a fixed seed works forever. If shipping a seed is rejected, state that direct first use needs network and stop with an explicit repair message on failure. Do not claim all requirements are satisfied by a downloader alone.

| Route / failure | Proposed behavior |
| --- | --- |
| Direct install, first use offline after plugin acquisition | Copy and run the seed; state its actual version. No latest-version claim. |
| Installer/setup route | Provision runtime first, validate it, install/check the one wrapper; report incomplete setup on failure. |
| External runtime missing | For a new session, recover from a compatible seed. A session with a missing pinned version reports failure; it does not silently switch. |
| Update interrupted or offline | Keep the valid selected runtime. Report update failure separately from validation status. |
| Seed absent/corrupt, unsupported Node, unwritable data directory | Emit a clear validation-unavailable diagnostic through the stable entry point where execution remains possible; fail setup/status. Handle startup failure before the hook deadline. Do not use silent exit 0. |
