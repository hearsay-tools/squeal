## B3. Proven blocker: empty mapping lines bypass the parser's line bound

Locations: `src/core/code/coverage/own-map.ts:123` (separator handling), `src/core/code/coverage/own-map.ts:113` (the only generated-line position check), and `src/core/code/coverage/sourcemap.ts:39` (decoder allocation).

Contract: approved task `015-95.md` says, “Invalid transformed evidence is unread” and “Keep parsing bounded”. D8 says malformed or unsupported transform evidence leaves the source unread. Implementation notes document a 250,000 generated-line limit. The final review brief explicitly requires bounded decoding/mapping.

`validMappings` checks the current generated line only in `end()`, which runs for a nonempty segment. A semicolon increments `line` without checking its bound. Empty lines therefore pass even after the supplied generated line lengths are exhausted. They also bypass `MAX_SEGMENTS`. The shared decoder then pushes one new array per semicolon before mapping begins.

This is an observable allocation and validation failure, not an inferred crash. A 250,005-character mapping for a one-line script is admitted and produces 250,002 decoded line arrays, exceeding the documented 250,000-line limit. `ownRecord` accepts it as readable coverage instead of listing the source unread. The 16 MiB string cap still applies, but permits roughly 16 million empty mapping-line arrays. No large allocation, out-of-memory failure or daemon crash was attempted or claimed.

Small deterministic reproduction, after the ordinary build, with no fixture files or disk-map reads:
