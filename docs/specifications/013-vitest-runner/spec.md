## Scope

The Vitest adapter implements `RunnerAdapter` (011 C14) over one warm `vitest/node` instance per worktree and lane. It decides what Vite's module graph says about a change, what a test file's closure and packages are, how a run is issued and read, which Vitest-specific inputs enter a key, and how the recorder and the child marker reach Vitest's workers. When a tier runs, what happens to its results, and what a key means are 011's (C3, C4, C11). Excluded: the recorder's own code and form rule (011 C12, C10); the install-detection rule (011 C11); node:test's and pytest's use of the same contracts (003, 007).

## Design

### V1. Instance and adapter version

<!-- 001 spec.md@cdd72a91 lines 79 (D4) -->
One `createVitest('test', { root, watch: false, reporters: [squealReporter], update: 'none', includeTaskLocation: true })` per worktree, then `standalone()`. Vitest's own watcher is never used. The adapter's version (`VITEST_ADAPTER_VERSION`; `NODE_TEST_ADAPTER_VERSION` for spec 003's runner) is in each of its projects' environment hashes (D3), so a bump re-keys this runner's checks and no other's. Each version sits alone in its runner's `version.ts`, which the D3 guard exempts, so bumping it re-keys that runner's checks and leaves `KEY_FORMAT_VERSION` and every other runner's keys alone (task 001-203, review wave 13m S1). The guard covers the rest of every adapter, so a change to its code bumps `KEY_FORMAT_VERSION` and re-keys every runner; an adapter bump alone is for a change to one runner's results that no guarded source shows (task 001-199). The adapter exposes, through the runner interface that later adapters will implement:

**A closed instance is emptied** (amended 2026-10-21, the human, row 013-06, `research/vitest-close-leak.md` 3 and recommendation 1). Rolldown's native resolve plugin holds Vite 8's callbacks as GC roots (rolldown/rolldown#10887). Their closures reach the config's plugins, whose hooks close over the instance, so a closed `Vitest` stayed reachable with all it held: on cezar, 110 to 114 MiB of heap per recreate. After each awaited close, the adapter deletes the own properties of the closed instance, its logger, its projects with the root one, its Vite servers and their environments. The awaited closes are a recreate, the adapter's own close (also the slow pass's, 004 D2), a broken instance's and a rejected run's (V8). The adapter gathers these objects before the close, because the close clears `vitest.vite` when no listed project is the root one (a root config that selects only separate project configs). It leaves plugin objects alone, since a config may import one that the next instance shares. A rejected close leaves every object whole, and an error while emptying is dropped. The emptied shell stays reachable through the plugins, but its module graphs are collected (on cezar, 7 to 15 MiB stay per close). An instance in `abandon`, whose close is not awaited, is never emptied; nor is a failed start's, which built no module graph (0.36 to 0.72 MiB, `tasks/013-06/notes.md`).

### V2. Invalidation

<!-- 001 spec.md@cdd72a91 lines 81 (D4) -->
- `invalidate(paths)`: calls `invalidateFile` for each changed path. An add or delete also invalidates the cached transforms it can make wrong, and only those, because a transform holds each import as Vite resolved it and an unresolvable specifier verbatim. On delete: every module that imports the deleted path. On add, every module with (1) an import whose target has the added path among its resolution candidates (D3: each configured extension, `index` with each extension, the TypeScript twin of a JavaScript extension), whether the import was unresolved or resolved to a candidate the added path now shadows; (2) an unresolved import that is not relative, which is an alias, `tsconfig` `paths` or a package specifier, since Vite turns every import it resolves into a `/…` or `/@fs/…` URL; (3) `import.meta.glob` or a template-literal dynamic import in its source, which Vite expands from the files on disk at transform time, found by a regex over the source on disk (not the emitted code) cached per transform, one path for every project because Vitest does not pass a plugin given at `createVitest` to a project with its own Vite server; the scan covers a dependency Vitest inlines from `node_modules` (an externalized one has no cached transform), and a module with no source on disk, a virtual module served by a plugin's `load`, counts as expanding; (4) a resolved import under a directory the added path now shadows, which covers a directory resolved through its own `package.json`. An added, deleted or edited `package.json` also stales every module with a resolved import under its directory, because the directory, or the package imported by name, may now resolve to another entry. Of the edits, only a manifest edit takes this path, so a plain edit costs what it did (001-79). It also stales every module under that directory that has an import, since a subpath import (`#x`) resolves through the `imports` of the module's nearest manifest. Vite caches the package data it read, so each such manifest goes through `pluginContainer.watchChange`, the hook Vite's own watcher calls, in every environment; for an added manifest that hook drops nothing, so the nearest-package lookups at or below its directory are also dropped from Vite's internal `packageCache` (001-81). An edit that changes only fields no resolver reads (`scripts`, `version`, `description`, `keywords`, `author`, `contributors`, `license`, `repository`, `bugs`, `homepage`, `funding`, `private`) against the ones recorded when the instance last saw that manifest stales nothing; every other field counts, so a field named in `resolve.mainFields` or read by a plugin re-resolves when edited (`reviews/wave-9c.md` B1); the first edit after a start has none recorded and stales as above. On the cost fixture, `affected` after that first edit of `src/gen/package.json` costs 0.73 to 1.03 s, about 40 percent of the cold walk, and after a later `scripts`-only edit 17.6 to 20.4 ms against 28.4 to 38.2 ms after a plain edit (001-81, three local runs on a loaded machine, cold 2.2 to 2.4 s). So does an added path that a `package.json` in an ancestor directory below the project root names as its `main` or `module`, up to resolution candidates and a trailing slash: while that entry was missing, Vite resolved the directory to its `index`. A string `exports` or `exports["."]` is matched the same way, defensively: with `exports` present Vite does not fall back to `index`, so the import was unresolved and rule 1 already stales its importer (`reviews/wave-7.6.md` N2). A module Vite soft-invalidated still counts, because it is re-served with its old resolutions; that reads Vite's internal `invalidationState`, checked once per instance, and a Vite without it falls back to invalidating every cached transform with one note. Calls `clearSpecificationsCache()` when a path matching a test glob was added or removed; recreates the instance when the config file or one of its dependencies changed (about 50 to 200 ms). A run whose `runTestSpecifications` rejects closes its instance, also when it rejects during a timeout's or an edit's cancellation and whatever value it rejects with (task 001-389), and the next call starts a new one: Vitest marks a project's `globalSetup` done before it runs it, so a kept instance would run every later file with no setup (task 001-382, `research/cezar-e2e-setup.md`). Invalidating every transform instead cost 5 to 6 s on the next `affected` on a 516-file repository (`lessons.md`, defect 11). On a 1,000-module, 205-test-file fixture (`structural-cost.test.ts`), `affected` right after an add costs 15.7 to 17.4 ms locally against 12.6 to 15.6 ms after a plain edit and 0.92 to 1.0 s cold (001-60, five runs); on CI (GitHub Actions run 37579065539, the code of `ae24aaf`) 20.5 ms against 17.6 ms warm, 20.5 ms after an edit and 1.9 s cold on Node 22, and 18.7 ms against 15.0 ms warm, 18.3 ms after an edit and 1.8 s cold on Node 24. The add carries a fixed part the warm walk does not, re-globbing the test files and transforming the new file, so only `affected` after an add under a quarter of the cold walk is asserted. The add's own `invalidate` costs 5 to 8 ms, and 18 to 21 ms the first time, when it scans the source of every module (tasks 001-53, 001-56, 001-60).

### V3. Affected, closure, enumerate

<!-- 001 spec.md@cdd72a91 lines 82-83 (D4) -->
- `affected(changedPaths) -> test files`: the `related` walk (`config.related` plus `getRelevantTestSpecifications()`), which transforms without executing and costs about 100 ms cold and 2 ms warm on 50 files. Squeal adds what Vitest's walk misses: all test files of a project when a setup file, its closure (an unresolved import's resolution candidates included, D3), `globalSetup`, or the config changed; the owning test file when a `.snap` changed.
- `closure(testFile) -> paths`: from the same transform graph, plus the additions in D3. With them the installed packages and Node builtins the closure's project files import in one hop (`RunnerClosure.packages`): the package entries the walk reaches and stops at, the specifiers Vite left bare and the literal `require` targets of the source scan, with the importer's directory, and the test file's docblock environment, with the project root; a load no specifier names, or a file under `node_modules` in no package, is reported as the builtin `module`. `environment()` reports the same for the setup and `globalSetup` closures and the config files, plus the packages the resolved config names by string, and marks the runner and the config files' imports as `RunnerPackages.runner` (`RunnerEnvironment.packages`, tasks 001-105, 001-109).

- `enumerate(testFile) -> check ids`: `parseSpecifications`, static, about 35 ms for 50 files. `test.each` appears as one templated entry until the file has run.

### V4. Runs, results and check identity

<!-- 001 spec.md@cdd72a91 lines 86 (D4) -->
- `run(testFiles) -> results`: `runTestSpecifications`. Results come only from the reporter hooks `onTestCaseResult`, `onTestModuleEnd` and `onTestRunEnd`, never from the cumulative `TestRunResult`, which includes stale modules. File-level errors (import or syntax failures) become a `fail` for every check previously known in that file plus one file-level check. A hook error inside a `describe` lands on that suite, not the module; the adapter reads every suite's own errors after the module's, so it fails the file-level check as a file-level hook does, and the suite's tests keep the `skip` Vitest reports; an empty `describe` fails its file as Vitest does without `passWithNoTests` (task 001-360). `process.exitCode` is reset after each run. The file-level check records the file's whole time, the module's diagnostic parts summed (environment, preparation, collection, setup files, its tests and hooks), not the time outside its tests; a file's estimate is the larger of that and its tests' sum, so a result an older release stored, which kept only the remainder, reads at least its tests' sum (amended 2026-10-21, row 013-03, gh-62: one cezar file showed 3.5 s for a 112 s run; the scheduler's estimate already summed every result, so the yield rule read the whole file before). The adapter reports each module's end to the scheduler as it happens (`RunOptions.fileEnded`, row 011-54); a throw there is logged and ends nothing.

<!-- 001 spec.md@cdd72a91 lines 92 (D4) -->
Check identity is `(project name, relative test path, fullName)`. When two tests in one file share a `fullName`, the second and later ones carry their source line as a suffix. Vitest's positional ids are used only within one run. Stack paths are relativized before storage. A stored error keeps its `code` and its `cause` chain, outermost first, three links of message and code, each message's first line capped at 200 characters and each code kept whole (task 001-361). Per-run floor is 110 to 350 ms even for one file, so changes are batched per revision and runs are issued in tiers (D5).

### V5. Bytes Vite read, touched files, the optimizer

<!-- 001 spec.md@cdd72a91 lines 87-88 (D4) -->
- **Bytes Vite read** (task 001-146). A cached transform holds the bytes on disk when Vite read them; a key names the bytes the watcher hashed (D2). A revert and its restore inside one debounced batch leave a path's hash unchanged, so no revision names it and `invalidate` never sees it, while a transform read in between keeps the reverted bytes: every later run executed them under a key naming the restored ones (evidence-001-146: a rebase reverted and restored `src/cli/run.ts` within a second, and 7 FAILs from the old module were stored as current). Each Vitest instance wraps the `load` of the plugin container of every environment of every project server, so each project file Vite loads is stamped: its stat, then the hash of its bytes, before any plugin or Vite reads it. The root server, an inline project sharing it and a project with its own config file, which has a Vite server of its own that a plugin given to `createVitest` never reaches, are stamped alike (review wave-13 B2, task 001-151); a container is wrapped when the instance is created and again before each check, and what it cached before that counts as moved. Stamps are kept per container, not per path: two servers (two projects with config files of their own) each cache a file from their own read, and one server's later read of restored bytes must not hide another's transform of transient ones (review wave-13b B2, task 001-154). Within a container they are kept per module ID, each with the project file it names: a query variant (`mod.ts?variant`, `?raw`, `?inline`) is a module of its own, cached from its own read, and so is a `\0` ID that names a project file once its `\0` and query are set aside; one variant's later read must not stand for another's (review wave-13c B1, task 001-157). A virtual module, whose ID names no project file, is checked through the project files its plugin declared it read (`addWatchFile`, which Vite records as imports without a transform of their own): each is stamped at the first check after the load if it changed before the load began, and otherwise counts as moved since; a moved one invalidates the virtual module. What a plugin reads without declaring it is invisible to Vite's own watcher too and is not checked. `invalidate` and every `run` first check each container's cached modules against that container's own stamp for that module ID, and invalidate in every project, every module that names it included, each file whose stat moved since a stamp (or is racy, D3) and whose bytes no longer hash the same, or which is gone; a cached module of a project file with no stamp (cached before its container was wrapped, or by any path besides the container's `load`) counts as moved, whenever it was read; the disk is read once per file per check, however many containers cached it. After a run, a file the run read whose bytes moved since makes the test files of the run that import it not completed, all of the run's files when none imports it in the module graph (a computed `import()`); the scheduler records them `unknown` with the reason (D5). Vitest's `fsModuleCache` serves a transform from its own copy on disk without the container's `load`, so the adapter turns it off (`fsModuleCache: false` among `createVitest`'s options, which Vitest hands to every project as a CLI override), whatever a config says: such a transform would have no stamp and count as moved at every run (task 001-157). What a Vitest instance reads once is checked too: its config files, which Vite bundles itself and no container loads, are stamped before `createVitest` reads them (the last instance's config files and the scripts at the root; a config file not stamped then is trusted only if it changed more than the racy window before) and checked at every check above; its global setup, which runs once per instance, is stamped like any module, but a moved one is not undone by invalidating it. Either leaves the instance unsure: the next call replaces it once, and a run under an instance still unsure makes all its files not completed, with that reason. A closure fetched while such a window was open may describe the reverted bytes until the file's key moves, unless the restore reached the runner as a touch (below). The inventory of what holds a project file's bytes is `tasks/001-157/notes.md`.
- **Touched files** (task 001-159; reviews wave-13 to wave-13d; narrowed 2026-10-20 by the human, row 013-01, gh-33, D1 to D3: `tasks/013-01/design.md`). Four reviews each found one more cache that can keep a project file's transient bytes when it changes and changes back within one batch: a virtual module's declared input with a transform of its own, processed CSS holding what it `@import`ed, and the dependency optimizer's bundle of a source reached through an alias. All have the same trigger: a touch no revision names (D2). Each but the optimizer, off since task 001-176, records its read in the module graph of the environment that cached it: the declared input as an import of the virtual module, the `@import`ed file as an import of the stylesheet (013-01, Vitest 5.0.3 on Vite 8.3.2). So a touch counts for an instance only when the instance could have read the path. It counts when a module of some environment names it, in Vite's file index or by its ID with any `\0` and query set aside. It counts too when it is an input the instance reads once and holds outside any module graph: a config file or one of its dependencies, a file of a global setup's closure, an installed lockfile the instance started with, or a `package.json`, `tsconfig*.json`, `jsconfig*.json` or `.env*` file under the root. Any other touch, such as build output no test file loads through Vite, withholds nothing and keeps the instance. On 0.1.224 a same-bytes `tsc` rebuild of 804 `dist` files no Vitest file loaded withheld every file of the run in flight, and a second one left them `unknown`. An `invalidate` naming a touch is heard when it is called, not behind the run in flight. A run under the instance when a counting touch is heard makes some of its files not completed, with a reason naming the counted paths. These are the files whose import graph in their own project reaches a module of a counted path. When none of a project's files reaches it (a computed `import()`, a setup file, `vi.importActual`, a `__mocks__` file), all of the run's files in that project, if its environments hold a module of the path. When the path is an input read once, all of the run's files. It reports the completed ones as withheld (`RunReport.withheld`); the scheduler stores none of them and re-queues them, counted toward its discard limit, at which they are `unknown` (011 C4; amended 2026-10-17, task 011-06). A counting touch replaces the instance at the next call of either lane, and every project's and environment's transforms and module graph and the global setup's state go. A touch that does not count is sorted again at each call and forgotten once every call in flight when it was heard has returned: a transform records the files it read only when it completes. A same-bytes write in place truncates first, so a reader can see an empty file (013-01: 14 to 25 of about 40,000 reads during three `tsc` rebuilds). When only Vite's read falls in that window, the stamp re-hashes equal bytes and only the touch counts it. A path the run itself wrote counts like any other (review wave-13e B1, task 001-168): writing its bytes proves nothing about which bytes a cache served the run. So a test that rewrites, with its own bytes on every run, a file it loads through Vite or that its key names, is never stored and ends `unknown` at the discard limit. The remedy is to write outside the worktree, or under a path git ignores that no `inputs` entry names and no test file imports. An instance with a browser-mode project, whose client environment can still bundle, counts every touch, as before. A touch of a file a plugin read without declaring it counts as its edit does: it is not checked. Declaring the file does not help: a declared file is in the key, and the completion barrier counts its touch (review wave-13f N1). No project counts as recreated: the touched bytes are the bytes they were, so the environment and the listing are too, and a listing then could hash a file added since ahead of its own batch, which would then name no revision. The closures that name a touched path are fetched again from the new instance, replacing one fetched while the transient bytes were on disk. A slow instance (spec 004 D2) hears a touch at once as well. Touches queued behind runner work that has not started wait as one call. The stamps above stay the fast path: they cover a run that read transient bytes before the touch was heard. A touch whose batch reaches the scheduler only after the run ended is caught by the completion barrier (D2, review wave-13e B2, task 001-168): before a tier is recorded, every input its keys name (closure, declared inputs, observed paths, environment files) is re-stat'ed against the stat cache as it stood when the tier was selected, and a path written since whose bytes hash as before withholds the test files whose keys name it, as a content change discards them, their files `unknown` with a reason naming the path (D2 of row 013-01); the path is then reconciled, so the runner hears the touch before its next run. A touch reconciled after the tier was selected counts even when the runner heard it before the run began: withholding on any touch over a run's interval is the conservative rule. Nothing from a withheld run is stored, so no shared row names it for a lookup or another worktree. A path no key names (an undeclared `@import`ed stylesheet) is outside the barrier, as an edit of it is outside the key; only a touch the runner hears during the run withholds for it. Cost: a recreate and a cold transform of every closure, once per batch with a counting touch; none for a batch whose touches no instance could have read. An agent's ordinary edits cause none (an atomic save's temp file is not a touch); a no-op save from an editor, `touch`, a git branch round trip, a stash push and pop, a reset and back, or a build rewriting committed output each cause one (`tasks/001-159/notes.md`).

  **The dependency optimizer is off** (reviews wave-13d S1 to wave-13f, task 001-176; decided by the human 2026-10-09). Vite's dependency optimizer bundles what `deps.optimizer.*.include` names, a project source reached through an alias included, into files under `node_modules/.vite` that no plugin container loads, so no stamp, touch or key names the bytes a bundle holds. Six reviews found it running other bytes than a stored result's key: a bundle of transient bytes kept across a restart, by a project with its own config file too (wave-13e B3, wave-13f B3), one built when the instance started, before the first key scan read the disk (wave-13f B4), and one an ordinary edit of the aliased source left in place (wave-13f S1). So every Vitest instance Squeal makes, fast and slow, initial and replacement, runs without it, in every environment of every project, whatever a config says; Vitest leaves it off by default, and neither this repository nor cezar turns it on. No `createVitest` option reaches it everywhere: `test.deps` is not among the CLI options Vitest hands a project with its own config file, and Vite's inline config (`forceOptimizeDeps`, 001-168's rebuild at every start, now gone) reaches the root server only. Vite builds each environment's optimizer with its server and its resolver decides then that one exists, so after `createVitest` and before anything loads, the adapter empties every optimizer's metadata (`optimized`, `chunks`, `discovered`, `depInfoList`), which Vite reads at each resolve and load, and sets each project's `deps.optimizer.*.enabled` to false, which the workers read. Nothing then resolves to a bundle: an import goes through the plugin container and is stamped like any module. Vitest builds only optimizers that do not discover imports (`noDiscovery`) outside browser mode, so the emptied metadata stays empty; a browser-mode project's client environment discovers imports and can bundle again, and is not covered. The bundles a start still builds are never read, so the start costs what it did with the optimizer on. A config that turns the optimizer on gets one note, once per daemon, in `squeal status` and in the registration header, naming the projects and saying why: a test that passes only with the optimizer can fail under Squeal and pass in `vitest run`.

### V6. Environment inputs and packages

Vitest's inputs to the environment hash are listed inside 011 C3's environment-hash bullet: the resolved Vitest config, the config file's contents and its `configFileDependencies`, the closure of every `setupFiles` and `globalSetup` entry with the resolution candidates of its unresolved imports, the packages the resolved config names by string, the reporters given as packages and the environment package. They reach the core as `RunnerEnvironment.files` and `RunnerEnvironment.packages` from `environment()`, and a test file's packages as `RunnerClosure.packages` from `closure()` (V3). How packages become a key segment, and when a file falls back to the whole fingerprint, is 011 C11; this adapter's part of that rule is what it reports: the package entries Vite resolved, the specifiers Vite left bare, the literal `require` targets of the source scan with the importer's directory, and the docblock environment with the project root.

### V7. Runs and the runner part: the gate

<!-- 001 spec.md@cdd72a91 lines 112 (D5) -->
What the Vitest adapter's calls exclude (task 001-150; `src/runners/vitest/gate.ts`). Two queues per instance: runs, one at a time (Vitest serializes them itself), and the runner part (`invalidate` without a recreate, `affected`, `closure`, `enumerate`, `testFiles`, `environment`), one at a time; a call of one overlaps a call of the other, so a node:test-only revision's runner part, which the composite fans out to every adapter, no longer waits for a Vitest run. Exclusive: what replaces or closes the instance, a start, a recreate (an `invalidate` naming a recreate trigger or a lockfile, policy `observe.runtimeInputs` moved), dropping a broken or hung instance after its run, and `close`. An exclusive section waits until neither queue is inside a call and holds both until it returns, so a recreate asked during a run waits for that run, and the next run waits for the recreate; the call that asks gives up its own place first, so a run and the runner part asking at once queue rather than wait on each other. The project list is written only there. `config.related`, the one field a call writes and a run resets as it ends (Vitest's `runFiles` `finally`), stays with `affected`: a related walk that finds it reset by a run ending meanwhile, and so may have answered every test file, is answered by the adapter's own walk instead. 001-146's check of the bytes a run read stays whole: the runner part's own check during a run drops the transforms it finds moved before the run's check would see them, so it logs what it found with when Vite read it, and the run's check after it ends names those it loaded too (`SourceStamps`), and an `invalidate` during a run checks before it drops anything, and first keeps the stamp of every module it may drop, each declared input of a virtual module included, which the run's check compares with the disk for those read since the run began, so a transform dropped while the bytes it read were still on disk, then restored, is still seen (task 001-264, review wave-13af B2). Measured by `test/runners/vitest/overlap.test.ts` with a worker held mid-run: every runner-part call answers; a recreate and a run asked after it complete in order after the held run; a module that moved and was invalidated by the runner part still drops the held file. The related walk transforms only the test files Squeal lists: a file `vitest.exclude` or `vitest.excludeProjects` leaves out is never loaded into the instance unless a listed file imports it, so its edits during a run withhold nothing (amended 2026-10-21 on the human's acceptance, 011-82 row B; task 001-146's fallback withheld every finished file of a run when an excluded test file the walk had loaded moved).

### V8. Runner failures and the failed start

A runner call that fails is a state, never a skip: the rule and its consequences are 011 C4's paragraph on it. This adapter's cases in that paragraph: a run that rejects before any test file reports (a `globalSetup` that throws) is a failed start, its instance closed and the next call starting a new one, because Vitest marks a project's `globalSetup` done before it runs it (V1); an ENOENT under the instance's own temp directory, or a Vite module runner error whose message and stack name no project file, ends the run `crashed`; the instance is recreated when an installed lockfile appears or changes, with `vitest/node` imported again from the worktree; a Vitest at the same resolved path keeps the module already imported, and a new version there needs a daemon restart. 011 C13's first two bullets state the untrusted-run and config-change rules; the setup check a failed start feeds is 011 C5.

### V9. Policy and capacity

<!-- 001 spec.md@cdd72a91 lines 209 (D11) -->
- `vitest.excludeProjects` (`[]`; decided by the human, 2026-10-14, task 001-349): names of Vitest projects Squeal never runs, an exclude list so a project added later runs by default. A repository whose own test script selects projects (cezar's `npm test` runs four of its five, leaving browser e2e to `npm run test:e2e`, which boots what they need) lists the rest here; setup proposes the difference (spec 005). An excluded project is never validated, keyed or counted; `squeal status` and the start's delivery name each entry as not run, excluded by `squeal.config.json`, a plain name as the project (`project "e2e"`) and a pattern as a selector (`projects matching "E*"`), and an edited file only an excluded project's tests read is uncovered under `delivery.uncoveredEdits`. Names match as Vitest's `--project` does (`*` a wildcard, case ignored, a name also covering projects nested under it), since the list joins that filter as `!name` entries. Vitest's `project` option replaces a config's own `test.project` filter, so Squeal passes that filter with them, read by resolving the config once before the instance: the key only narrows what Vitest would run. A name matching no project, the config resolved with its own filter cleared so a project that filter drops still counts, is reported as `"vitest.excludeProjects[<index>]" names no Vitest project ("<name>"); it is left out`, and the rest of the list applies. Changing the list recreates the Vitest instance; a remaining project re-keys only when its environment's inputs change (D3). Every project's config files are in each project's environment, so excluding a project with its own config file re-keys the others once, and excluding an inline project re-keys none of them. Excluding every project is a runner failure. `slow` stays separate: a slow file runs in the slow lane, an excluded project never runs.

**Note.** 001 listed this key between `delivery.uncoveredEdits` and `daemon.idleExitMinutes` in the policy list that is 011 C10. The list there says it is this spec's.

Two more rules of 011 C10 are this adapter's to implement. The runner ceiling (C10 Capacity, "Runner ceiling"): each backlog or checkpoint tier's workers come from its grant under the project's own resolved `maxWorkers`, at least 2 unless the project set 1, and the warm instance is resized before each run, never recreated. The loading rule in C10's last paragraph: Vitest is loaded from the project under validation, resolved from the worktree root and imported lazily, never from Squeal's own installation; only the project's own configuration runs inside the worktree; `update: 'none'` prevents snapshot writes; the workers' environment additions are the recorder's and the child marker's (V10).

### V10. Recorder and child-marker delivery

The recorder (011 C12) and the child marker (011 C13, the process-reaping bullet) reach Vitest's workers through `createVitest`'s `env` option, which Vitest spreads into the workers of every project in both pools: the recorder as `--import` of its `file:` URL, or `--require` where C10's Fidelity rule says so, ahead of the daemon's own `NODE_OPTIONS`, with its settings in `SQUEAL_OBSERVE`; and `SQUEAL_DAEMON_CHILD=<token>:<lane>`. Neither enters the resolved config 011 C3 hashes. `fsModuleCache` is off so that every transform goes through the stamped `load` (V5).
