## Should-fix

### S1: the matcher counts object identities instead of occurrences on removal

**Proven; non-blocking.** `src/core/lint/transition.ts:61` and `:67`.

`unmatched` records consumed findings in a `Set<LintFinding>`, then filters the original array by object identity. If the same object occurs twice in `before`, consuming one occurrence marks both as matched. The fingerprint correctly detects the loss of one finding, but the transition names no removal.

At the exact candidate, a Node 24 throwaway probe called the exported functions with:

```ts
const f = {
  rule: "no-undef", message: "'report' is not defined.", severity: "error",
  line: 1, column: 1, lineHash: "same",
} as const;
lintTransition([f, f], [f]);
// Actual: { kind: "fail-changed", added: [], removed: [] }
lintTransition([f, { ...f }], [f]);
// Actual: { kind: "fail-changed", added: [], removed: [f] }
```

The probe also confirmed that the two fingerprints differ. D2 keeps duplicate findings and says that the match's count remains right. That helper invariant does not hold for repeated object references.

This is not a blocker for the implemented flow: `eslintFindings` constructs one new object per message, and reading findings from stored JSON also constructs distinct objects. The replay uses those distinct objects and passes. No production caller of `lintTransition` exists yet. The defect needs object reuse by a future caller or test fixture.

One-worker fix: track matched array positions or occurrence counts, instead of a set of objects. Add a regression for `[f, f] -> [f]` and for the same input through the second matching stage. This needs no schema or public type change.
