## B1-R. Proven: old states can be certified by a newer cursor from another committed snapshot

**Locations:** `src/core/lint/surface/named.ts:75` and `:76`; `src/cli/wait/named-lint.ts:86`.

The repair correctly rejects a saved result when the cursor it reads is behind. It does not read the state and cursor from one snapshot. `namedLintOf` first lists the states, then reads the cursor and other metadata. `readNamedLint` calls it directly, without `access.store.read(...)`. The named wait's main-store transaction does not protect this separate lint-store connection.

The original contract still fails: a named wait must wait for the named files' current lint. Spec D2 defines pending as "while Squeal has not linted the current bytes"; vision principle 2 forbids an old result posing as current truth. Here the file bytes stay equal, but the config changed, as in B1's required control.

**Deterministic proof:** a throwaway test used two real connections to the same WAL lint store. It reused `lintedRepo("pass")`, `stateOf` and `keyedAt` from the candidate's new fixture:

1. Seed the old pass and cursor 3. Request revision 4. Keep B's bytes equal to the judged blob.
2. Read the old state list on connection R.
3. Before R reads its cursor, commit one transaction on connection W: B becomes `pending`, and its tool's cursor becomes 4 under a new environment.
4. Resume the candidate's `namedLintOf` on R. It reads cursor 4, accepts the old state and matching blob, and returns `done: 1`, `outcome: "pass"`.

The probe wrapped only R's `states.list` method to insert W's transaction immediately after the actual SELECT returned. It did not fake SQL results or change product code. A daemon in another process can commit between those same two statements. The writer changed state and cursor atomically; the reader lost that relationship.

Core of the probe:

```ts
const list = reader.states.list.bind(reader.states);
reader.states.list = (id, filter) => {
  const oldRows = list(id, filter);
  if (!keyed && filter?.tool === "eslint") {
    keyed = true;
    writer.transaction(() => {
      writer.states.upsertMany([stateOf(repo.mainId, B, "pending")]);
      keyedAt(writer, repo.mainId, 4, "new-config");
    });
  }
  return oldRows;
};
```

The test called `namedLintOf` with revision 4, `Buffer.from(B_TEXT)` as its byte read, and `[B]` as the named files. It required `done: 0`, `pending: 1`. It ran the same interleaving again with only the call enclosed in `reader.read(...)` as a control.

## What the repair settles

- Without an interleaving writer, the original old-pass probe now waits for the edit's failure. A cursor behind a config change keeps even equal-byte results pending through the deadline.
- The byte check applies to both pass and fail outcomes. Missing provenance or different bytes cannot count as done on the ordinary read path. An unchanged file's older judged result remains valid once its tool's cursor is current.
- The deadline test confirms the lint field stays pending while tests give the settled verdict and exit code 0. Off tools give unknown with a reason. Lint disabled still omits the field. Missing or unreadable stores have explicit `unavailable` output; busy reads are retried before the deadline. Existing held-state handling remains in `fileOf` after freshness is established.
- The JSON change adds `waits: "keying"` and optional `lint.unavailable`. It preserves the existing counts and the repository-wide lint payload. `printNamed` carries the new object through its existing additive lint field. The real-formatter eval parser checks still pass.
