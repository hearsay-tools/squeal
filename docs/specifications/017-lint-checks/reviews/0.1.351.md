## Blocker

### B2-R3. Proven: a first-seen unlisted rule can store old findings under its new bytes

`src/core/lint/pass/unlisted.ts:62` treats a first observation as unchanged unless a revision names the path. `src/core/lint/pass/session.ts:141` opens and refreshes the worker before that first observation. At `session.ts:214`, the pass also awaits the install fingerprint between the worker's refresh and the first `Unlisted.look`. The rule may change during that interval. The pass records its new hash without refreshing the worker that loaded the old code. Later looks see the same hash, so later passes cannot detect the mismatch.

This is the worker notes' stated first-look limit, verified by a concrete interleaving. D4 requires a new worker for changed local rule code. D5 keys findings by the hashes of the config closure. Vision principle 2 says an old result cannot pose as current. The stored result here describes the old rule at the new rule's exact key and is shared as current. Disclosure in the notes does not amend those contracts.

Reproduction with the real provider and pass:

1. Populate the `ts-config` fixture through `fixture(tree, "ts-config", undefined, ["rule.ts"])`. All ordinary files are listed. Only `rule.ts` is on disk outside the listing. Its local rule reports `before`.
2. Create the normal real-provider pass. Supply this install-fingerprint callback to force a concurrent edit at the existing await boundary. It returns the same fingerprint used by the second root:

   ```ts
   let edits = 0;
   const after = readFileSync(rulePath, "utf8").replace('"before"', '"after"');
   installed: async () => {
     if (edits++ === 0) writeFileSync(rulePath, after);
     return "install-1";
   }
   ```

   The callback changes no provider answer. The worker has already loaded the actual old rule. This forces an edit between that read and the pass's first disk sample, without a timing guess. It proves the interleaving, not its frequency.
3. Nudge the first pass and await idle. It stores **`["before", "inline before"]`**, `stale: false`, with `keyed: 1, hits: 0, linted: 1`. On Node 24 its key is `e5f476cdd8bbe08bfd737df1ad688c7e1161bc5657a2614024f81cf97e12707d`.
4. Fresh `eslint -f json src/a.js` on that same disk reports **`["after", "inline before"]`**.
5. Write a README-only revision and nudge again. The stored findings remain `before`, `stale: false`. The next pass does not repair them.
6. Create a second fixture root on the same lint store and fingerprint. Write the rule with `after` before opening its worker. Its pass returns **`keyed: 1, hits: 1, linted: 0`** at the first root's exact key, with **`["before", "inline before"]`**. The second root's worker has loaded `after`, but the shared hit prevents linting.

The same proof passes on Node 22; its key is `a23f6c8cf5441f20aaabb353c7c65f37bc6ac929954dee47034a09f79bc36d8b`. Node majors correctly separate keys. Both roots within each major share the wrong answer.

Fix scope, if the human authorizes another repair: one pass/session row plus a real-provider regression. Synchronize a newly discovered unlisted input before trusting its first sample as the worker's bytes. For example, a first-seen config/closure input can require its D4 refresh; a first-seen program input can require the walk/feed contract. Keep the bounded settling loop and refuse storage when synchronization cannot be established. Test the edit after initial worker refresh, the next nudge and a clean second root. Existing version-2 lint results can contain this wrong association, so an authorized repair must also prevent their reuse. No shared test-key encoder change is needed.
