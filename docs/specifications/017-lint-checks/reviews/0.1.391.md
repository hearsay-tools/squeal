## Blockers

### B1. Proven: normalizing user text hides a different finding

Location: `src/core/lint/fingerprint.ts:19`, used at
`src/core/lint/transition.ts:28` and `:48`.

D2 requires a transition for `fail` to `fail` when the fingerprint changes,
with the findings added and removed. The review brief explicitly requires that
normalizing `line N` never merge two different findings. The new regex treats
any occurrence of those words as a source location, including an import's name.

Reproduce with installed ESLint 10.13.0 and this config:

```js
export default [{
  rules: { "no-restricted-imports": ["error", "line 1", "line 2"] },
}];
```

Open `eslintProvider` with the fixture root and the candidate's committed
`plugins/claude-code/dist/cli/lint-worker.mjs`. Refresh once. Lint `a.js` first
with `import "line 1";\n`, then with `import "line 2";\n`. Feed the returned
finding sets to `lintFingerprint` and `lintTransition` from the candidate.
The built-in rule returns:

```text
before: no-restricted-imports: 'line 1' import is restricted from being used.
after:  no-restricted-imports: 'line 2' import is restricted from being used.
lineHash before: 3451e720462a28bd
lineHash after:  8b33a6e7ffe0e35f
fingerprint before: 91bf29abc4946045
fingerprint after:  91bf29abc4946045
lintTransition(before, after): null
```

This is a different prohibited import, not a moved diagnostic. The agent loses
the changed-finding news. The line-hash matching stage cannot help: the equal
fingerprint returns before matching, and the fallback matching also normalizes
the text. A literal `line N` can collide with a numbered phrase too.

**One-worker fix:** normalize only known location fields or known rule message
templates. Keep arbitrary diagnostic data intact. A narrowly scoped handling of
the observed exhaustive-deps message is sufficient for L5; do not globally
rewrite user text. Add the real built-in restricted-import regression alongside
the moved exhaustive-deps and upgrade cases. The restricted import edit must
record `fail-changed`, with one added and one removed finding. Keep the seven-edit
replay and unchanged-upgrade cases quiet.

### B2. Proven: the JSONC reader corrupts an extends path and misses a key input

Location: `src/core/lint/provider/oxlint/configs.ts:153`, consumed by
`configFacts` at `:82` and `:93`.

D11 requires "the root config and its `extends` closure" in the key. Research Q2
names that closure as a necessary input. The comment promises that strings are
kept as they are. The final trailing-comma regex runs over strings too.

Reproduce with real oxlint 1.90.0 linked into a scratch root:

```text
.oxlintrc.json:       {"extends":["./configs/base,}.json"]}
configs/base,}.json:  {"rules":{"eqeqeq":"error"}}
a.js:                export const f = x => x == 1;
```

Open `oxlintProvider`, call `inputs(["a.js"])`, then lint the on-disk text.
Change only `configs/base,}.json` to `{"rules":{"eqeqeq":"off"}}`, refresh
at `instance` level, call `inputs` again and lint again.

Actual output:

```text
configFiles: [".oxlintrc.json"]
closure: ["configs/base}.json"]
inputs before and after:
  config: {"chain":[["",".oxlintrc.json"]]}
  wholeProgram: false
held before and after:
  .oxlintrc.json: 0b1f6524818a25607af0aff7a0eb8a1a5c9a342d
sameReportedKeyInputs: true
before: eslint(eqeqeq): Expected === and instead saw ==
after: findings: []
```

The native tool reads the valid path containing the comma. The provider reports
the nonexistent path without it. The actual base is absent from `configFiles`,
`closure`, `program` and `held`. Its native read is not observed by the preload.
The file blob, tool/install, environment, reported config and all reported input
blobs stay the same while the fresh tool changes from fail to pass. The future
pass cannot make a sound key from this report. Oxlint is not wired into the pass
yet, so this proves a provider-contract failure, not an already-stored false pass.

**One-worker fix:** remove trailing commas only outside JSON strings, in the
same lexical pass that handles comments, or use a suitable JSONC reader. Preserve
strings and token boundaries. Add a real-provider regression with this extends
path and with a comma before `]` inside a string. Require the real base path and
blob in the reported inputs and require its edit to change the key. Retain the
existing comments, trailing commas, native-only replay and JS-read checks.

## Should-fix notes

### N1. Plausible: the directory patch is partial

Location: `src/core/lint/provider/worker.ts:30` and
`src/core/lint/provider/wraps.ts:98` and `:160`.

The worker now reports the root from `process.cwd()`, and wrapped reads/opens
resolve relative paths there. Other relative calls such as `statSync`,
`existsSync` and `readdirSync` still use the real daemon directory. A resolver
that probes before reading can therefore take a different branch from the CLI.
The new cwd test covers resolved reads and bare relative reads, not those calls.
The worker notes correctly disclose this limit.

No published plugin reproduction was established here. D5 already names an
existence-only boundary, and local rules outside the observer are also a named
limit. This is not a blocker. A follow-up should exercise a real resolver's
relative probes before promising that every process-relative operation runs
from the root. If needed, keep the path redirection in one owner.

### N3. Plausible: Vite+ configs fall outside the input discovery

Location: `src/core/lint/provider/oxlint/configs.ts:12` and
`src/core/lint/provider/oxlint/config-set.ts:54`.

Research Q1 states that `VP_VERSION` selects `vite.config.*`. The provider keys
that variable but its config names only include the four oxlint names. A root
containing only a Vite config takes no `--print-config` path and can leave
`javascript` false, so its lint runs would have no preload. That can omit the
config and the files it imports or reads, as well as miss type-aware detection.

This is a source-level risk, not a verified real Vite+ run. Before 017-15 uses
this provider for such a root, add an actual Vite+ fixture and discover/observe
its config, or explicitly return off/unknown for that mode. Do not infer support
from the current test that merely checks that `VP_VERSION` is echoed.
