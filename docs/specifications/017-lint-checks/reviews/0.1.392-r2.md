## The first candidate's CI wait-test failure

Read with `gh run view 41369888037 --log-failed`, filtered to the named test:

```text

status --wait <path> reads the selected files' states, and every state only at its end
```

**Judgment: a timing-sensitive poll-count assertion, not evidence of a
wave-5 lint-read regression.** The concrete causal checks are:

- `git diff ee85e1270 HEAD -- src/cli/status-wait-paths.ts src/cli/status-sync.ts src/cli/status-wait.ts test/cli/wait-reads.test.ts` is empty.
- `repoWith` seeds test states without a policy file. Lint defaults off.
  `lintStoreSource.policy()` returns null, so this fixture opens no lint store.
- In `status-wait-paths.ts:325`, `buildSnapshot` runs only after the outcome
  is decided. The lint status read is inside that final snapshot. It cannot
  add an earlier poll to the count that failed.
- The unchanged loop tests the deadline before its read transaction
  (`status-wait-paths.ts:242`), then sleeps for the remaining fractional
  milliseconds (`:361`). `pollPause` can also wake on a sync answer. An early
  timer or a read crossing the deadline can add a terminal read. The existing
  test comment and `test/cli/wait-clock.ts` already describe differing timer
  and `performance.now()` clocks. There is no strict six-read product bound.

The precise sequence of the seven CI reads is **unverified**: that log has
no timestamps per poll. Timing is a plausible explanation, not a claim to
have reproduced that CI schedule. The same file is current and passing in
Squeal at this candidate. That local pass does not erase the known old CI
failure or replace the new exact-head CI run. No poll-count threshold was
