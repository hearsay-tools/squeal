## Decisions the spec did not settle

1 to 4 were agreed with the coordinator on 2026-10-26; 5 to 9 are this row's choices; 10 to 13 are the wave 1.5 repair (R2), 12 and 13 at the coordinator's decision; 14 to 18 are the wave 1.6 repair (R3), from its brief.

1. `inputs()` rejects with an `Error` whose message is D9's reason when the config does not load, the worker fails or the provider is off.
2. The computed config's JSON has the project root (and its real path) written `<root>`. A typed config holds `tsconfigRootDir` as an absolute path on ESLint 9 and 10, so without it no typed file's key is shared between worktrees (goal 7).
3. The third worker failure (timed out, threw, exited) within 10 minutes turns the provider off; that call resolves `{ off: "the ESLint worker failed 3 times; <reason>" }`. `refresh("instance" | "thread")` and `open()` clear the off state and the count. An earlier failure gives every file of that call `unknown` with the reason (D9: the part's files), and the next call starts a new worker. A failure while no call is in hand (a plugin's late timer) counts too.
4. `refresh()` reports `program` and the tsconfigs in `closure` before any lint. A `tsconfig.json` under the root (outside `node_modules` and dot folders) counts when one of its files gets a typed config from `calculateConfigForFile`, which applies ESLint's own `files` and ignores; `project` as paths names its tsconfigs instead. `lint()` adds what it learns (accumulates per thread).
5. `lint()` feeds typed files and the given program files ESLint does not lint to TypeScript's project service, by the config's own parser (`parseForESLint`), before it lints, when the call holds more than one of them; a typed file alone is parsed first only when it is outside the known program, to learn its program. Tested with `projectService`; `project` (typescript-estree's own programs) is not. A fed file ESLint does not lint gets no entry in `results`. A file that is neither linted nor in the program reads `unknown: ESLint does not lint this file`.
6. A file a rule throws on reads `unknown: ESLint failed on this file: <first line>`; the worker lives on. A parse error is a finding with `rule: null` (D9).
7. A plugin's 0 ms timer that throws fails the call it was set in: the worker waits one timer turn before it answers.
8. The worker runs with `execArgv: []`, the daemon's environment plus `TSESTREE_SINGLE_RUN=false`; a plugin's stdout and stderr are read and dropped.
9. Off reasons: `no ESLint installed in <root>`, `ESLint <major> is not supported`, `eslintrc configs are not supported; ESLint 9 and 10 read eslint.config.*` (ESLint 9 with `ESLINT_USE_FLAT_CONFIG=false`), `the ESLint worker's script is not built`, and (B2) `the ESLint worker cannot see which files <config> loads`.
10. **B2, the closure of a TS config.** ESLint 9 and 10 load `eslint.config.ts` with jiti (`createJiti(…, { moduleCache: false })`), which reads each module with `fs.readFileSync` and resolves none through Node, so the resolve hook saw nothing. The worker wraps `fs.readFileSync` and records each absolute path read while `calculateConfigForFile` runs (the only call that loads a config; `configOf` and the refresh probe go through it). Reads at other times (TypeScript reading the program, rules reading files) are not recorded. jiti's file cache is off in the worker (`JITI_FS_CACHE=false`, the worker's own `process.env`): its cache files, in the temp folder, would enter the closure and differ between worktrees. Each config file ESLint uses (`findConfigFile(path)`) joins the closure, the root one and nested ones. When that config file is in neither the resolved modules nor the recorded reads, the worker answers `off` with the reason above, for any call; the host stops the thread and stays off until a refresh above `none`. Node's own type stripping (`ESLINT_FLAGS=unstable_native_nodejs_ts_config`) goes through the resolve hook. Tested: `test/lint/provider/ts-config.test.ts` (ESLint 10 and 9 with jiti, ESLint 10 with type stripping, and a worker whose reads are hidden).
11. **B3, the program before any lint.** `refresh()` walks from each relevant tsconfig's root files: `preProcessFile` gives each file's module specifiers, `/// <reference path>` and `/// <reference types>`; `resolveModuleName` resolves each specifier in both import modes where the resolution kind reads modes (Node16, NodeNext, Bundler), since the walk does not tell an `import` from a `require`; automatic type directives are resolved from the tsconfig's folder. JavaScript files add JSDoc `@import … from` and `import("…")` types by a pattern. The walk follows every file outside `node_modules` (a package's own imports are the install's). On this repository's tsconfig the walk gives exactly TypeScript's own program outside `node_modules` (2216 files, 10 of them outside `include`); `units.test.ts` compares the two on a small tree too. A full `ts.createProgram` was measured and not used: 4.5 s wall, 7.8 s CPU and 850 MB here (2.3 s, 4.9 s and 610 MB with `noLib` and empty package files).
12. **A later walk reads again only what may have moved.** A walk from nothing costs about 0.2 s of CPU per refresh here, past goal 9's 60 ms per edit. `ProgramReader` keeps each file's specifiers by its stat (mtime, ctime, size, inode) and, per tsconfig, each file's resolved targets with the paths its resolutions read: the folder of each target and of each of TypeScript's `failedLookupLocations`, and each `affectingLocations` manifest, outside `node_modules` (an install is a thread refresh). `Watch` stats every such path at the start of a walk; a changed one makes the results that read it stale until they are made again. A folder whose mtime moved and whose entries kept their names, kinds and link targets (an editor's save by rename) makes none stale. A tsconfig is parsed again when it, a config it extends or a folder its `include` glob reads (each wildcard folder, and below a recursive one every folder but `node_modules` and dot folders) changed. A state younger than 1 s is unsure: it equals no later one, so that path is read again at the next walk, as git treats a racily clean file; file times tick coarsely, and a change between a read and the stat after it must not pass. A failed resolution that does not say where it looked is resolved at each walk. `units.test.ts` compares each later walk with a walk from nothing after an import of a file outside `include` is added, an import is removed, a file and a folder appear where an import failed, an imported file is removed and a file is added under `include`; another test counts that a save by rename parses nothing and resolves only the saved file, and another that an edit in the same tick as the walk is seen. Turning the folder check off fails the first test.
13. **The pass reads the program again after a module file's edit** (`ProviderSession.ready`, `src/core/lint/pass/session.ts`, the one pass change of this row). When the changed paths include a file with one of D5's module extensions (`MODULE_EXTENSIONS`) and the refresh level is `none`, the pass calls `refresh("none")` before keying, so the keys of that pass hold an edit's new import. The install fingerprint is read only at open and at a thread refresh, as before. `test/lint/integration/b3.test.ts`, second test: two worktrees on one lint store, each with a daemon pass kept open, both make the same edit importing `src/gen.ts`, a file outside the listing whose return type differs between them; the second must lint and find `no-floating-promises`. Without the change it reads the first worktree's pass at the same key. `test/lint/pass/pass.test.ts` now expects a `none` refresh at each `.js` edit. Decision 15 now holds this rule (`refreshOf`).
14. **One owner for the key inputs outside the listing** (`Unlisted`, wave 1.6). The inputs are the config files, the closure and the program's files, those under `node_modules` left out (the install fingerprint holds them). A generated or git-ignored file makes no revision, so each pass reads every such input on disk (its git blob) before any lookup, and the pass's keys take that blob: `Keyer.inputBlobOf` for the closure in each key and the environment cursor (B2-R), and the program segment's files outside the listing (B3-R). A missing input reads `null`, which the closure keys as no segment and the program segment as `-`, so it is keyed apart from an existing unlisted file; the shared encoder `check-key.ts` is unchanged. The keyer still keys and lints only listed files (`blobOf`). An input first seen is recorded, not counted as moved: the worker read it a moment before. A path the revisions name that has left the listing counts as moved at first sight.
15. **What a moved unlisted input refreshes** (`refreshOf`). A config or closure file: D4's level, as a listed one (`instance` for a config file, `thread` for the rest); the environment cursor moves with its blob, so every file is keyed again with no transition. A program file whose bytes moved or appeared: `refresh("none")`, so its new imports enter the program before keying, and the next lint call feeds it, hits included (`Ready.feed`). A program file gone, unlisted or deleted from the listing in the revisions: a new thread. TypeScript's project service, which typescript-estree keeps per thread with no file watchers, keeps what it read; `refresh("none")` gave the deleted file's old finding (`unlisted.test.ts`, the deleted case). A listed module file in the revisions still reads the program again (decision 13).
16. **The pass looks again after each refresh** (`ProviderSession.ready`). A refresh may bring new inputs, which are read for the keys, or race an edit, which moves an input again. Up to three refreshes run; inputs that still moved end the pass with `Moving`: nothing is keyed, the refresh they call for is left due for the next pass, the moved program files are kept to feed, and the pass looks again 1 s later.
17. **A config keying feeds its changed program files too.** A new instance (a config edit) keeps the worker's TypeScript service, so a program file changed in the same revisions must be fed, as in an edit keying.
18. **`LINT_KEY` is `squeal-lint-key/2`**, the round's one key-version change: version-2 provider keys stored by the 0.1.348 candidate omit the unlisted inputs' bytes. `PROVIDER_VERSION` stays 2. The listing is read at most once per pass (`onePass`) and shared with the keys: an input check looks paths up one by one for the first 64, then reads the listing whole, which the program segment reads anyway.

## What the next rows must know

- **The pass calls `refresh("none")` after a module file's edit** (decision 13), and above `none` as D4 says. `refresh("none")` walks the program again (the cost above) but finds the relevant tsconfigs once per instance.
- **Each pass reads the unlisted key inputs on disk** (decision 14). An edit to a git-ignored file still makes no revision, so no pass runs until something nudges one (review `0.1.348-r2` N2); the next pass sees it before any lookup.
- **A deleted program file restarts the worker** (decision 15), listed or not: a listed one deleted in a revision has left the listing, and the revision names it. A thread start costs the config's load and the first typed lint's program; dogfood states how often agents delete program files.
- **Changed typed program files must be in a lint call**, hits included: `lint()` is the only way to feed the project service, which reads a file it never opened from disk once and never again.
- **`configFiles` holds the root config only.** ESLint 10 reads nested `eslint.config.*` per directory; the pass should treat any path named `eslint.config.{js,mjs,cjs,ts,mts,cts}` as a config file (`instance`), as the replay's `levelOf` does. A nested config already loaded is in `closure` too, so check the name first.
- **`packages` are absolute package folders** (real paths), for 011 C11's identities; a loaded file outside the root and outside `node_modules` stands as its own path.
- **`program` is the complete program at the last refresh** (decisions 11 and 12), plus what a lint learns from the project service. A lint report does not walk again.
- **An added file costs more than goal 9 allows on a program this size** (the table above): the `include` glob runs again. Cutting it means TypeScript's internal `matchFiles` per changed folder, or the pass telling the provider which paths changed; neither is built.
- **The first typed lint builds the program** inside the 5 s per-file guard. On a large program that may time out; dogfood states it (`guardMs` is an option).
- **Not covered:** a data file a config reads with an API other than `fs.readFileSync` (`fs.promises.readFile`, `fs.readFile`) while it loads; a project file only a package imports (the walk does not follow `node_modules`); tsconfig project references (the walk follows sources, as a project service does); a file system that does not move a folder's mtime when an entry is added or removed (some network mounts), where decision 12 keeps a stale resolution; a memory cap (`resourceLimits`) on the worker; the cost of the relevance scan, which calls `calculateConfigForFile` on each file of a tsconfig until a typed one; an unlisted input that changes between the worker's read and the pass's first look at it (decision 14 records the first look), which is seen only at its next change.
- **Squeal re-runs the provider and integration tests on a worker edit** since `776cc07a9` (a `squeal.config.json` `inputs` entry for the bundled worker's sources and fixtures).
- **Dist drift until the build:** a change to `src/core/lint/**` makes `test/harness/plugin.test.ts`, `test/harness/codex/plugin.test.ts`, `test/harness/opencode/package.test.ts` and `test/harness/pi/package.test.ts` fail until `npm run build` (the coordinator's step).
