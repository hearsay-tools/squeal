## Blockers

### B1. Plain Jest recognition does not prove that Jest selects the configured config

**Proven on Jest 29 and 30.** `src/runners/jest/describe.ts:83`, `:122`. Consumer: `src/harness/shared/deny.ts:153` (`resolveTestFiles` followed by the current-result denial).

Spec 028 D6.3 adds plain-Jest recognition to the existing opt-in denial contract. That contract's response says: "Squeal holds current results ... for the ... test file ... it runs" (`test-command-reason.ts`). The vision requires trustworthy state and provenance. Results under another Jest config do not establish the requested command's result.

`jestHere()` checks the working directory, but never checks the config Jest discovers there. `direct()` then accepts paths and associates them with the policy project. A valid policy can select a non-default config, or set `cwd` separately from its config directory. Plain Jest can consequently execute the same file under different globals, transforms or setup files.

Reproduction, in a temporary directory with one installed Jest and one listed file:

```js
// jest.config.cjs: what a plain Jest command discovers
module.exports = {
  testEnvironment: 'node', testMatch: ['<rootDir>/*.test.cjs'],
  globals: { FLAG: 'direct' }
};
// policy.jest.cjs: same options, but globals: { FLAG: 'configured' }
// a.test.cjs
test('same test file', () => expect(FLAG).toBe('configured'));
```

Policy project: `{ name: 'app', config: 'policy.jest.cjs', include: [], exclude: [], args: [], env: {} }`.
Read `commandContext(policy, root, root)`, recognize `jest --runInBand --ci a.test.cjs`, then resolve it against `[{ project: 'app', path: 'a.test.cjs' }]`.

```text
Jest 29 and Jest 30:
recognized: { runner: "jest", project: "app", paths: ["a.test.cjs"], ... }
resolved files: [{ project: "app", path: "a.test.cjs" }]
Jest with --config policy.jest.cjs: exit 0
plain Jest with the recognized arguments: exit 1
  Expected: "configured"
  Received: "direct"
```

Once Squeal holds current passes from its configured run, the existing denial path can stop the failing direct command and present those passes as its evidence. The feature is opt-in, but the evidence is still wrong when enabled.

**One-worker fix:** require proof that Jest's automatic config selection from the command directory is the policy project's config. Fall through for a custom config, an ambiguous config search or a root multi-project wrapper that does not match the configured project. Keep `--config` and shell/Nx fallthrough rules. Add both-major regressions with two configs selecting the same file but producing different outcomes, including an explicit policy `cwd`.

### B2. Setup drops valid inline projects from a root projects array

**Proven on Jest 29 and 30.** `src/cli/jest-seed.ts:169` through `:174`; root wrapper is discarded at `:87`.

Spec 028 D1.2: "If a root config defines a non-empty `projects` array ... `squeal setup` expands it into explicit `JestProject` entries and does not register the root wrapper as a project." It specifies resolution through `readConfigs`. There is no amendment limiting this to string entries.

The seed reads the wrapper through `readConfig`, takes `global.projects`, and explicitly skips every object entry. A normal Jest multi-project config can therefore produce zero Squeal projects, despite selecting tests successfully in both supported majors.

Reproduction:

```js
// jest.config.cjs
module.exports = {
  projects: ['unit', 'integration'].map(displayName => ({
    displayName,
    rootDir: '.',
    testEnvironment: 'node',
    testMatch: [`<rootDir>/${displayName}/*.test.cjs`]
  }))
};
// unit/a.test.cjs and integration/b.test.cjs each contain one test.
```

The probe writes this config and both tests, then compares the installed Jest's `--config jest.config.cjs --listTests --runInBand --json` with `seedJest(root, trackedFiles, process.env)`.

```text
Jest 29 and Jest 30:
Jest exit: 0
Jest listed: ["integration/b.test.cjs", "unit/a.test.cjs"]
seed.projects: []
seed.notes:
  Jest config jest.config.cjs lists 2 projects: Squeal seeds each, not the config itself
  Jest config jest.config.cjs lists a project as an inline object;
  Squeal seeds projects from config files only: move it to its own jest.config file
  [same note for the second project]
```

The note exposes the limitation, but does not fulfill the approved expansion goal. The existing multi-project regression covers only file/directory entries.

**One-worker fix:** resolve root projects with Jest's `readConfigs` and retain a stable way to address each resolved project through discovery, execution and environment hashing. Preserve inline project options and their config dependencies without requiring edits to the user's Jest config. Add both-major setup/apply/run coverage for a root containing only inline projects and for mixed string/object entries. If support is to be deferred instead, that requires an explicit accepted scope amendment; this review cannot supply it.

### B3. The version bump leaves the release installer on 0.1.644

**Proven.** Changed `package.json:3`; consumer `install.sh:45`, with tag use at `:279` and archive selection at `:288`.

The requested bump is 0.1.644 to 0.1.646. The base agrees at 0.1.644, but the candidate changes the package and plugin versions without changing `SQUEAL_VERSION=0.1.644` in the installer. Process step 6a attaches the tagged commit's `install.sh` as the release asset. That asset would still request `squeal--v0.1.644` for the Codex runtime and use the old source archive for Pi, OpenCode and Antigravity.

The existing installer regression failed on the clean exact candidate. The independent git-object check above confirms this without relying on the remote test environment. This is a mismatch introduced by the changed package version, not a pre-existing installer defect outside the range. The passing version-bump script does not check installer equality.

**One-worker fix:** set `SQUEAL_VERSION` in `install.sh` to 0.1.646 with the candidate bump. Run the existing `test/cli/install-sh.test.ts` version assertion and relevant installer tests. No new product mechanism is needed.
