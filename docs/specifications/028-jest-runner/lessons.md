## Findings

- **F1. On a cold baseline every Jest file runs twice (product bug, reported to the coordinator).** One `squeal run --all --wait` at revision 0 made 470 file runs for 258 files: the 192 passing Jest files ran twice, the 10 failing ones three times (twice plus the failure confirmation), the 56 pytest files once (no environment). The second pass started at about 103 s, when the first had ended, inside the same checkpoint. The daemon noted "coverage: 128 completed test files got no record since this daemon started: 128 no-result (its run's result was not found at its key)": the first pass's results were stored under a key the checkpoint did not look up. This is why the cold baseline took 190.8 s against plain Jest's 104.8 s. Minimal reproduction, the end-to-end suite's 3-file fixture on Jest 29.7.0 and on 30.5.2: `squeal setup --yes --no-warmup`, commit, `squeal start`, `squeal run --all --wait` prints "3 test files, 0 already current, 3 run now", while the store's `runs` table holds 4 runs and 6 file runs, each file twice, the second about 0.7 s after the first. With a fresh store each time: `coverage.enabled: false` and `observe.runtimeInputs: true` gave 6 file runs; `coverage.enabled: true` and `observe.runtimeInputs: false` gave 3; both off gave 3. A second `run --all` finds every file current, so the cost is each file's first run (a cold baseline, a new test file, a worktree with nothing to inherit). Edits in steady state are not affected: the button edit made 78 runs plus 8 confirmations. The end-to-end suite does not assert one run per file yet, by the coordinator's decision, so it stays green on `0.1.651`.
- **F2. Jest coverage records are stored but reported as not measured (product bug, reported).** Jest runs write coverage records (the code store's `coverage` table had records for `packages/core/src/helper.js` in the fixture), but `RECORDING_RUNNERS` in `src/core/code/coverage/runtime.ts` lists only `vitest` and `node-test`. So the session start says "Coverage comes from Vitest and node:test runs only; functions that only Jest tests run read not measured.", `squeal code` says "4 files not measured: Jest gives no coverage", and CRAP and untested verdicts are never given for code only Jest tests reach. On the `saas-boilerplate` copy, status reported "1924 files unknown (712 because no test Squeal runs loads them, 1212 from a test file with no coverage record)". Spec 028 Goal 4 and D5.3 promise V8 coverage in `CoverageRecord`.
- **F3. The setup instruction block does not name Jest (product bug, reported).** `BlockRunners` in `src/cli/setup/block.ts` has no Jest field. In a Jest-only repository `blockText()` falls back to Vitest, so `CLAUDE.md` and `AGENTS.md` get "Squeal runs the Vitest tests after each edit ... If you have seen no SQUEAL message in this session, run `npx vitest run` instead." In `saas-boilerplate`, with two pytest projects seeded too, the block names only pytest: "Squeal runs the pytest tests after each edit".
- **F4. Peak memory of warm Jest workers (observation, reported).** Right after the 78-file edit the daemon's tree held 20 warm Jest workers using 10,324 MB in all (about 516 MB each), beside 17 Jest runner hosts at 1,980 MB: 13.1 GB for one worktree. Each worker stays below the recycling ceiling of D7.2 (`min(1024 MiB, 10% of host RAM)`), so none was recycled. They left on their own within about 5 minutes. On a 16 GB machine the peak alone would be most of its memory.
- **F5. 14 of 78 files ran again on the revert (open).** The revert restored the exact baseline content, yet 14 files ran instead of taking their stored pass (`profile`, `home`, `header`, `sidebarLogo`, `editProfileForm` in `webapp`; `subscriptions`, `editSubscription`, `subscriptionPlanItem`, `editPaymentMethodForm`, `stripePaymentMethodSelector` in `webapp-finances`; `crudDemoItemList`, `crudDemoItemDetails`; `document`; `actionLogExportReady`). Only one of them was among the failing files. The cause was not found in this session; it may share F1's key mismatch, since those stored passes came from the baseline's double run. A later no-change `run --all` found all 202 files current.
- **F6. The 10 baseline failures are the repository's own.** Each fails the same way under plain Jest without Squeal: 8 `webapp-sso` files with "Configuration error: Could not locate module react-markdown mapped as ... node_modules/react-markdown/react-markdown.min.js" (the shared `webapp-api-client` setup file reaches `webapp-core/src/utils/mentions.tsx`, and `webapp-sso`'s `moduleNameMapper` points at a file that is not installed), and 2 `tools` files with `ts-jest` type errors (`TS2741` and `TS2554` in `executors/setup/executor.spec.ts`, `TS2305` in `generators/webapp-lib/generator.spec.ts`). Squeal's failure line for the `webapp-sso` files shows only the headline "Configuration error:" with the location `mentions.tsx:3:1`; the line that names the missing module is not in it. Minor.
- **F7. Minor setup notes.** The setup plan's warm-up estimate said "runs all 56 test files": it counted the pytest files and left out the 202 Jest files. The seeded `packages/backend` pytest `exclude` lists `**/__pypackages__/**` twice.
- **What worked as the spec says.** Discovery skipped the empty root config and seeded the 17 package configs without Nx (D1.2). Results matched plain Jest exactly: 202 files, 808 passed, 4 skipped, the same 10 failed files (D4, D5). The `webapp-core` edit selected files in 12 packages through workspace imports and the shared setup file, and left the others current (D3). The `ts-jest` `.d.ts` edit re-keyed and failed exactly the one test file whose type check reads it, and its revert took the stored pass (D3.2). `squeal stop` left no Squeal, runner host or warm worker process (D7).

## End-to-end suite (`test/e2e/spec-028-jest.test.ts`)

One test per Jest major, on Jest 29.7.0 and 30.5.2, against the plugin's `dist/` built by `buildPluginDist` with the Jest runtime copied in (as `spec-027-docker.test.ts` does), a real daemon and the plugin's hook bundles. The fixture is `saas-boilerplate`'s shape in small: an empty root `jest.config.mjs` above `packages/core` and `packages/app`, whose test imports the core helper by its workspace name through a `node_modules/@mono/core` link. Each test:

1. runs `squeal setup --yes --no-warmup` with a `PATH` holding only `git` and asserts both package projects are seeded and the root config is skipped with its note;
2. runs a foreground `squeal run --all --wait` (3 files, 6 passing checks);
3. edits the core helper and asserts `squeal status --wait 60000 <helper>` selects the two importing files across both packages, fails both, and keeps the third file current; the revert passes them again;
4. with `testCommand.denyWhenCurrent: true`, runs the SessionStart hook and then PreToolUse: `jest test/alone.test.js` from `packages/app` is denied with the current-results reason, and `jest test/alone.test.js | tail`, `pnpm nx run app:test` and the same `jest` command again run;
5. checks that Jest runner hosts and warm Jest workers sit below the daemon, runs `squeal stop`, and waits until every process below the daemon is gone.

`TMPDIR=/tmp pnpm exec vitest run test/e2e/spec-028-jest.test.ts`: 2 tests passed in 15.6 s.
