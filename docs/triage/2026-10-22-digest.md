## A. Squeal's own runtime goes while a daemon uses it

Rows: gh-72, gh-70. Related: 005-73 (done), 011-32 and 011-34 (W1 of wave 12, running), 011-66 (planned), 005-75 (W2 of wave 12, running).

Facts. gh-72 is reproduced on 0.1.238 with a synthetic deletion (`011-core/research/issue-72.md`). After `rm -rf` of the daemon's plugin directory, the daemon stays alive and keeps scheduling. A child that a running test spawns fails with `ERR_MODULE_NOT_FOUND` for `<plugin>/dist/observe/recorder.cjs`, gh-70's exact error, and Squeal stores a current product FAIL. Every later tier crashes with `[vitest-pool]: Worker forks emitted error.` before a test body runs; its 4 files read UNKNOWN and leave the queue. `squeal retry` refuses the false FAIL without `--reason`. `stop`, `start` and `run --all --wait` through another copy of the CLI give 6 of 6 files current and 0 failures. gh-70 (0.1.235 to 0.1.236, 12 false worker-wait failures) was not reproduced (load 61.24) and shows the same child error. #72's second report (2026-10-21, 0.1.245 to 0.1.247) found the CLI path gone and no daemon running; the agent found the new CLI with `rg` and ran 5 files by hand. That session started before 005-73's launcher existed.

Read in spec: C9 lists the exits of a daemon, and its own runtime going is not one of them. The nearest rules are for the project's install. The daemon exits with reason `reinstalled` when the install goes (C9), and a tier whose run overlapped an install change stores nothing and its files are re-queued (C11). The step-down of 011-30 to 011-34 starts only when a newer hook asks, so a deletion with no newer hook leaves the old daemon serving.

Left after 005-73 (`005-agent-adoption/tasks/005-73-notes.md`, "Open after this row"): a daemon that a CLI spawns from the plugin cache, for example `squeal start` through `~/.local/bin/squeal`, or the first hook before any copy exists. The next Codex upgrade deletes that runtime. Claude Code keeps an old version for 14 days and while a live session holds it (`005-agent-adoption/research/plugin-cache-cleanup.md`), so the risk there is small.

Overlaps. 011-32 and 011-34 (W1) make one successor per handoff and let `start` finish it; a daemon that exits for a missing runtime needs that `start`. 011-66 re-queues, once, the files of a tier that crashes while its daemon stops; the store-nothing rule below is the same once-only re-queue at the same seam. 005-75 (W2) moves the launcher's plugin lookup into the CLI entry, the seam that the cache-started daemon needs.

Recommendation. Merge gh-70 into gh-72: both keys stay, and gh-72 carries gh-70's evidence. Approve two rows:

1. One 011 row, in one brief with 011-66, after W1. Before each tier, the daemon checks that its own module directory exists. When it does not, it starts no tier, leaves the files queued, persists one note that names `squeal start`, and exits as `reinstalled` does, so the next boundary or `squeal start` runs the installed runtime. A tier during which the runtime went stores nothing and re-queues its files once, as C11 does for an install. So a missing recorder is never stored as a product FAIL, and no queued file becomes UNKNOWN.
2. One 005 row, after 005-75. A daemon that a CLI spawns from the plugin cache runs from a kept copy of its version, as a SessionStart daemon does since 005-73.

Cost. Row 1: one C9 sentence and one C11 sentence; the daemon's tier start, its exit and the tier's store step; three tests in the shape of `011-core/research/probes/issue-72/probe.sh`: a deletion during a live tier (no FAIL stored, the files queued), a deletion with queued work (no tier starts, the note names `squeal start`), and a start through another copy (every file current). ## B. A named wait behind a tier whose estimate is wrong

Row: gh-73. Related: 011-51 and 013-03 (done), 011-99 (running), 011-103 slice 6 (planned).

Facts. On 0.1.238 a promoted named wait stayed behind a 4-file tier because "its estimated remainder was 0 s, not over 30 s". The tier started at 17:49:57 (UTC+2), the wait printed that line at 17:51:36, and the requested file started at 17:52:31, 2 min 34 s after the tier. Not reproduced (load 27.62). The issue's guess, a short duration from a transform failure, is not established.

Read in source: a tier yields when its largest last-known duration less its elapsed time exceeds 30 s (`src/core/scheduler/yields.ts:114-115`, `remainder` at `:211-214`). An unknown duration counts as 0. So a tier that has run past its estimate never yields. The estimate is the newest result's duration, whatever its outcome (`src/core/scheduler/ledger.ts:379`, `durationOf` in `src/core/scheduler/files.ts`), so one short failed run replaces a long pass's estimate. 013-03 shipped in 0.1.242, after the report. On 0.1.238 a file's duration could be a fraction of its wall time (gh-62), which alone can give a 0 s remainder (inferred).

Overlaps. 011-99 (running) changes scheduler tests. 011-103 slice 6 makes one `remainderSeconds` and takes the "30 s" text from `YIELD_REMAINDER_MS`, on the lines this row changes: `src/core/status/next-step.ts:67` and `src/core/status/standing-groups.ts:40`.

Recommendation. Approve one 011 row, in one brief with 011-103 slice 6, after 011-99. Amend C4 step 5: a tier that has run 30 s past its estimate yields as one whose remainder exceeds 30 s does, once per file and key as today. A promoted wait then waits at most the tier's estimate plus 30 s and the cancel. Under this rule the reported tier passed the bound at 17:50:27, so the wait would have been served from 17:51:36 at the latest, not at 17:52:31 (inferred from the issue's times, if the estimate was 0 s). Do not change how the estimate is taken: the queue order, the backlog budget and the edit cut read the same `durationMs` (`ledger.ts:172` and `:193`, `src/core/scheduler/edit-cut.ts:130`), so that change reaches further than the wait.

Cost. One C4 sentence; `#decide` in `yields.ts`, one standing kind for an overrun and its text in `next-step.ts` and `standing-groups.ts`; three tests beside `test/scheduler/tier-yields.test.ts`: a tier with a 0 s estimate and one with a stale-short estimate yield to a promoted wait within the bound, a tier within its estimate keeps today's rule, and a second yield at the same key does not happen. No evals parser reads the yield line (searched `evals/lib` and `evals/bin`). No key change.

## C. The run behind an UNKNOWN

Row: gh-74. Related: 011-77 (planned), 011-04 and 011-59 (done), gh-72 (group A).

Facts. On 0.1.242 two browser test files went PASS -> UNKNOWN with `Worker forks emitted error`. `squeal why` showed `Run log: unknown, no stored result, or several, fit the known state` and no run id. Not reproduced (load 52.58). The cause of the worker exit is unknown.

Read in source: an UNKNOWN known state keeps the crash text in `summary` but no run id (`KnownState`, `src/core/types/state.ts`), so `why` prints the `unidentified` gap (`src/core/status/format-why.ts:315`). C7 forbids storing a crash as a keyed result, so the run cannot ride on a result row.

A possible link to group A, inferred and not verified: 0.1.242 was released at 18:15:07Z (`gh release list`), and the two transitions came at 18:20:33Z and 18:22:37Z. gh-72's probe saw the same `Worker forks emitted error` in every tier that started after the daemon's runtime was deleted. The run log that would decide it is what this row keeps.

Overlaps. 011-77 makes prune keep the runs and logs of replaced failures and makes `why` list older failures: the same prune step and the same `why` text.

Recommendation. Approve one 011 row, dispatched in 011-77's brief as a second commit. When a check reads UNKNOWN, the run that produced it is recorded beside the known state, never as a keyed result, so C7 holds. `why` names that run, its worktree and revision, the worker's error and the log, also when newer results are passes. Prune keeps that run and its log while the UNKNOWN stands. A missing log names one reason: pruned, never written, or recorded by a daemon older than this row.

Cost. One C6 sentence and one C7 sentence; the run id stored with the UNKNOWN (a store column or a `meta` record, the brief's choice), `markUnknown`, prune, `format-why.ts` and one additive `why --json` field; the issue's four tests, including across worktrees and across a daemon restart. No key input changes (inferred).

## D. Regression notices on an edit

Row: gh-71. Related: 002-12 and 011-75 (done). W1 owns `src/core/delivery/` in this wave.

Facts. On 0.1.236 under Codex, with `interrupt.onRegression: true`, a guard edit for `ResizeObserver is not defined` was denied with 91 changed checks, and the same edit ran when sent again. Not reproduced (load 24.36). This is the specified behaviour.

Read in spec and source: the deny-once contract is in every harness, not in Codex only: 001 D9 (`Edit`, `Write`, `NotebookEdit`), 002 D3 and D8 (`apply_patch`), 008 D3 (`edit`, `write`, `apply_patch`) and 009 D3 (`edit`, `write`). All go through `denyOnRegression` in `src/harness/shared/deny.ts`, whose reason is `formatDelta` (`src/core/delivery/format.ts:244`). `interrupt.onRegression` defaults to `true`. 001 D9 says the model "treats it as an obstacle rather than advice": the deny is how a regression gets the agent's attention. `formatDelta` writes one block per failing check up to the 8,000-character cap, then "Not shown: N more changed checks"; nothing groups checks with one error and location. The evals grade a deny as its own kind (`evals/lib/grade.mjs:267`). With `interrupt.onRegression: false`, `denyOnRegression` returns before its peek (`deny.ts:57`), so the edit runs and the entries arrive at the next delivery.

Recommendation. Split the issue. Approve the grouping as one 011 row, after W1: `formatDelta` puts failing checks with the same first error and location in one block, with their count and one `squeal failures` command. Every harness's notice and deny reason get it. Hold the change to the deny-once contract until the grouping ships and a report shows that the retry still costs. Answer #71 now: `interrupt.onRegression: false` lets every edit run and delivers the regression at the next tool call.

Cost. Grouping: one C5 sentence; `format.ts`; tests that 91 checks with one error give one block with their count, that mixed errors give one block each, and that `squeal failures` and `why` still give every check's evidence; the evals parsers round-tripped through the real `formatDelta`. The contract change, if approved instead: amendments in 001, 002, 008 and 009; `deny.ts` and four harness output shapes; the evals' deny grading; and a measurement that agents still act on a regression when nothing stops the edit.
