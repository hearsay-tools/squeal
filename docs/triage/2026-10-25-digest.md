**Read in source and spec (0.1.309).**

- gh-94: `SPAWN_WAIT_MS = 10_000` (`src/cli/start.ts:26`, comment: "A spawned daemon binds its socket in about 100 ms; a loaded machine gets more"). When `served` is false, `start` prints the message and returns 1 (`:70-72`). `served` (`:232-244`) probes every 50 ms with a 100 ms probe timeout. It returns true once the daemon answers and the store records it (011-111). At the deadline it returns whether the last probe answered. `ensureDaemon` spawns the daemon detached and returns `"spawned"` without the child's pid (`src/core/daemon/ensure.ts:186-197`). So `start` cannot tell a daemon that is still starting from one that exited. `commands.md:122` in both plugins documents "Exit 0 once a daemon answers, 1 otherwise". The spec does not name the 10 s (011-111's entry in `011-core/status.md`: "the 10 s spawn bound unchanged"). `start.ts` has not changed since 2026-10-23. Hooks already have a starting state: `startingSince` (`src/harness/shared/ensure.ts:338`).
- gh-93: `src/harness/codex/handlers.ts:116` maps both a block and news to `decision: "block"`. In `src/core/delivery/delivery.ts:220-229`, a liveness or hold change alone is news. 001-224 has an exception for the edit line only: "news at Stop costs a continuation, so the edit line only rides on other news". 002 D3: "news at Stop always costs a continuation". 011-73 (2026-10-23): "a hold change at Stop is news, as a liveness change is (C8)". Changes to these files since 0.1.296 are a refactor (016-16) and 011-200's late-feed line, not the Stop rule.
