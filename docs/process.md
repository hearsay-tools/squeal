# How work happens in this repository

The operating model is the one from mega.dev's "autonomous product development", run with Cezar as the orchestrator. This file is the entry point for any coordinator session. Humans own `vision.md`, `styleguide.md` and this file; agents maintain everything else.

## Files that carry context

| File | Owner | Purpose |
| --- | --- | --- |
| `docs/vision.md` | human | Why Squeal exists. Every feature passes its decision filter. |
| `docs/styleguide.md` | human | Code, naming, spec and agent-work conventions. |
| `docs/process.md` | human | This file. |
| `docs/board.md` | coordinator | Current and planned tasks, grouped in waves. Workers never edit it. |
| `docs/specifications/NNN-*/` | coordinator and workers | One folder per feature: `spec.md`, `status.md` (stage and amendment log), `research/`, `reviews/`, `tasks/`, `lessons.md`. |
| `docs/decisions/` | coordinator | ADRs for decisions that span specs. Supersede, never edit history. |
| `docs/triage/` | coordinator | Dated digests of the board's Triage rows: themes, overlaps, one recommendation per group. Decision inputs, never normative; the decision lives on the row. |

## Roles

- **Coordinator**: the Cezar parent session. Reads the human's intent, runs research, writes the spec, keeps the board, dispatches waves, integrates worker commits, folds reviews back into the spec. Never writes product code itself beyond integration fixes.
- **Researcher**: one worker per research topic. Read-only on the product; writes one findings file under `research/` with every finding tagged `verified by experiment`, `read in official docs`, `read in source code` or `inferred`. Throwaway probes live under `research/probes/`.
- **Worker**: one worker per board row. Disjoint file ownership from the other workers of its wave. Test first. Final message lists decisions the spec did not settle and any type change.
- **Judge**: one per fan-out question. Reads two or more findings files and names where they diverge; the output is the spec input, never an average.
- **Quality**: one per stretch of landed work, after a spec ships or about ten rows. Proposes drop candidates, board rows and small slices; edits nothing.
- **Reviewer**: one per wave. Changes no code. Labels every finding proven, plausible or unverified; only a proven break blocks. Writes `reviews/wave-N.md`: verdict, verification output, blockers, should-fix, nits, what fits, and inputs for the next wave.

## The loop for a feature

1. **Intent.** The human states the goal. The coordinator writes back its understanding and asks only the questions that change the design.
2. **Research first.** Open questions become researcher tasks run in parallel. Nothing is designed from memory when an experiment is cheap.
3. **Spec.** The coordinator writes `spec.md` from the findings, with numbered design sections (D1, D2, ...) that tasks and reviews cite. The human reviews it before any code.
4. **Board.** The spec is decomposed into waves of worker-sized rows, each with scope and a testable done-when. Wave 0 is the scaffold and shared interfaces; later waves build on reviewed interfaces.
5. **Wave.** Workers run in parallel with disjoint ownership. The coordinator verifies each tree (lint, typecheck, tests) in the worker's own worktree, cherry-picks or fast-forwards, runs the combined checks, pushes the result as a candidate branch `cand/<version>` (branch CI runs on it), and lands it on main only after its review passes (step 6), then retires the workers. Docs commits (board, research, review files, spec text the human approved, eval results) land directly. A landing that changes the plugin bundles raises the patch version in `package.json` in the bundle commit, so different builds never share a version in the environment hash or in step-down; CI fails it otherwise. Before each landing the coordinator reads the CI result of main's last landing; a red run blocks the next landing until its cause is fixed or is a board row the human has seen. Landing on main ships nothing: installed plugins come from the hub (step 6a).
6. **Review.** A reviewer, pinned to the candidate's exact SHA, gates every product landing (`src/`, tests, `evals/` code, plugin bundles, versions): nothing reaches main before its review passes (human, 2026-10-15). A first-round FAIL gets a coordinator repair on the candidate and a narrow re-review; a second goes to the human. After a PASS the candidate is rebased onto main: when the commits since are docs only it lands as is; when they touch code, the version raise and key re-pin are redone as its last commit, the gate re-runs, and a re-review covers only the files they share. A candidate holds its version until it lands or is abandoned, and the coordinators announce claims to each other. Blockers become a fix wave (N.5) before the next wave starts; should-fix items fold into the next wave's briefs; every accepted deviation becomes a dated amendment line in `status.md` and an edit to the spec section.
6a. **Release.** After a wave's review passes (or when the human asks), the coordinator releases through the hub `hearsay-tools/marketplace` (marketplace `hearsay`): pick the reviewed main commit, whose `npm run build` shows no drift; `claude plugin tag plugins/claude-code --push` creates `squeal--v<version>`; in the hub, set both Squeal entries' `ref` to that tag and `sha` to its commit, run `claude plugin validate .`, commit `squeal <version>` and push. Then publish the tag as the latest GitHub release with the tagged `install.sh` as its asset: `git show squeal--v<version>:install.sh > install.sh` in a scratch directory, then `gh release create squeal--v<version> install.sh --latest --title "squeal <version>" --notes "<the reviews that cover it>"`. The README's install command fetches `releases/latest/download/install.sh` (human, 2026-10-14). Before tagging, run `npx vitest run test/keys/key-format.test.ts`; if it fails, the key-relevant sources changed since the last release: bump `KEY_FORMAT_VERSION` in `src/core/keys/key-format.ts`, pin the hash the failure prints under the new version, and land that first. A release that ships an unbumped change could reuse results whose meaning changed. Release between Codex sessions: Codex deletes the previous version's directory at once. The findings behind this step are in `specifications/001-core-loop/research/release-hub.md`. Two coordinators share the hub. Each releases its own reviewed waves, never while the other's release is in progress: first send the other a one-line "releasing X from <sha>" and wait for an ack or 10 minutes. A release takes the newest main commit whose whole content is reviewed, or accepted unreviewed by the human, and the hub commit names the reviews that cover it. No eval runs before a release, and none gates one (human, 2026-10-19: the evals were the slowest step of the release cycle while the friction reports waited on fixes already on main). After the GitHub release, the releasing coordinator closes every issue whose row this release ships for the first time, each with a comment naming the row, the version it landed in and the release (human, 2026-10-19). An issue the release fixes only in part gets that comment, names the row that holds the rest, and stays open.
6b. **Evals.** The evals run on their own cadence, not per release (spec 006 D7): with every `/quality` scan, and whenever the human asks; that is the whole cadence (human, 2026-10-19). Until the human says otherwise, they run on Sonnet and Sol only (`--models claude-sonnet-5-5,gpt-6.1-sol`), Haiku and Luna left out (human, 2026-10-19). Each run takes one commit (the latest release tag unless asked otherwise), each session started only below the host's CPU count in load, never two eval runs at once:
   1. The atomic tier: `node evals/bin/run-baseline.mjs --atomic --commit <tag> --models claude-sonnet-5-5,gpt-6.1-sol`, 220 short sessions (11 scenarios, 2 models, 10 repetitions). Commit its results file and the regenerated `evals/results/ATOMIC.md`.
   2. An alarm (a false pass or a forbidden edit) goes to the human at once. A flag (a model's measure fell against the previous release with an atomic run, at one-sided Fisher p < 0.01) is first re-checked by an atomic run on that release's commit (`--commit <its tag>`). If the drop still shows against that run, it goes to the human, who decides whether it becomes a row and whether the next release waits for it.
   3. Only when the atomic tier raised nothing: the long baseline, `node evals/bin/run-baseline.mjs --commit <tag> --models claude-sonnet-5-5,gpt-6.1-sol` (three repetitions, 24 sessions). It calibrates the judge first when this Claude Code version has no passing calibration (minutes, under a dollar; it stops before any session if no model passes). Commit its results file, any new `evals/results/judge-calibration-*.json` and the regenerated `evals/results/TREND.md`.
7. **Proof.** The last waves are an end-to-end suite that runs the product the way it ships and a dogfooding report written to `lessons.md`, which resolves the spec's open questions with evidence. The spec moves to `shipped` when its goals hold in dogfooding with no blocker.

## Issue triage

A new GitHub issue first passes CI intake (`.github/workflows/issue-intake.yml`, spec 010 D12): Jev picks at most one type and one `area-*` label, closes a duplicate of an open issue once `ISSUE_INTAKE_CLOSE_DUPLICATES` is `true`, comments on a likely duplicate of a closed one, and marks every issue left open `needs-triage`, also when intake fails. That label starts one `/coordinator` triage session through the cockpit's automation (human, 2026-10-16; on `needs-triage` since 2026-10-17), which replaces it with `triaged`; adding it by hand re-triages an issue. It is documentation only: no product code, no edit to any `spec.md`, `status.md` or skill, and at most one `/researcher` for a reproduction bounded to about 20 minutes, skipped when the one-minute load average is above the CPU count. The reproduction's findings go to the owning spec's `research/issue-<N>.md`, its throwaway probes under `research/probes/issue-<N>/`. The session works from `origin/main`, checks the board for the issue number and symptom and the open issues for duplicates, and writes one row under the board's `## Triage` section (created by the first row), keyed `gh-<N>` with no spec number: the coordinator who approves the row assigns a number from the board on main and moves it into its spec's section. Numbers allocated from a local board copy collided across parallel sessions on 2026-10-16, which is why triage never allocates one. The row names the issue, the research file, the spec sections it touches, the reproduction and duplicate verdicts, and the decision the human must take. It lands on main as a docs commit (rebase onto `origin/main`, push, one retry), after which the issue gets a `triaged` label and a comment with the row key. Creating the row authorizes nothing: it is dispatched only once the human approves it.

**From row to work** (human, 2026-10-17; the split proposal's rule 1). A Triage row moves through `proposed`, `approved`, then the ordinary `planned`, `running`, `review`, `done`, or `dropped`. Only the human approves: a dated `approved (the human, YYYY-MM-DD[, scope])` written into the row's status, in the board or as a decision the coordinator records there the same day. Before a batch of decisions the coordinator may write a digest under `docs/triage/<date>-digest.md` that groups the open rows by theme, names overlaps to merge, and gives one recommendation per group; the human decides per group, and the decision is recorded on each row, never only in the digest. An approved row is taken by the coordinator of its owning spec, who allocates its number from the board on main, moves it into that spec's section, writes its brief with a stopping condition, and dispatches it under the wave rules above; the issue gets a comment naming the number. A `dropped` row keeps its key in the Triage table with the dated reason, and its issue gets the reason as a comment and is closed. Two rows the human merges keep both keys, one row carrying the other's evidence. An expansion found while a row runs becomes a new `proposed` row, never a widening of the running one.

## Test runs on a shared host

This project's sessions share one host with other coordinators, their workers and reviewers, evals and every worktree's Squeal daemon (human, 2026-10-15). A worker's full-suite verdict is `squeal run --all --wait`, which re-runs only what has no current result; `npx vitest run --maxWorkers=4` only when Squeal is unavailable, no daemon is validating or the checkpoint is abandoned, and it says which. Every independent full run (a reviewer's, a coordinator's gate) takes the host's turn, one at a time: `flock /run/user/$(id -u)/squeal-full-run.lock npx vitest run --maxWorkers=4`. A coordinator lands finished rows as one bundle, one gate per release. It has no fixed limit on how many workers and reviewers it runs at once (human, 2026-10-21, which lifted the limit of 3 set on 2026-10-15). A file that fails a loaded gate and passes alone is named, with the load, in the landing note. Eval runs keep their own turn (step 6b).

## Procedures

Each role's step-by-step procedure is a skill, so an agent loads only its own: `.claude/skills/{coordinator,worker,reviewer,researcher,judge,quality}/SKILL.md`, mirrored under `.agents/skills/` for other harnesses. This file describes the model; the skills carry the steps.

## Provenance

The model is mega.dev's "autonomous product development", whose reference implementation is [overment/limen](https://github.com/overment/limen). Limen injects vision and styleguide into every role and selects a short role preamble per spawn (`templates/<role>.md`, overridable per project); its roles are coordinator, worker, reviewer, researcher, judge and quality, and all six are skills here, rewritten from limen's preambles and shop manual on 2026-10-06 with our additions marked *(Squeal)*. Left out, with reasons: the picture role (an architecture map; no map exists here yet), the keeper role (fixes ticket front matter and board links that limen's strict check enforces; our board has no such check), team groups (several coordinators on one feature; one coordinator per spec is enough at this size), and Herdr tab mechanics (Cezar's cockpit is the window). Limen's research fan-out of two models plus a judge is the human's call here, because it is spend.
