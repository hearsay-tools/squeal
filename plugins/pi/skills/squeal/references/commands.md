# Commands

`squeal --help` lists every command and flag. This file says what their output means.

## squeal status

Prints the current state of this worktree, its verdict first. It reads the store and needs no daemon.

```text
Revision: 187
Known failures: 0; not current: 27 of 290 test files (3 running, 24 unknown), 3 tests (3 running)
Affected checks: 47 passed (40 tests, 7 test files loaded), 3 running (3 tests), 0 queued
Full-suite checkpoint: none completed since revision 170 (the counts are for revision 187; `squeal run --all` requests one)
Outstanding:
  3 test files in the vitest tier of 3 test files running since 12:04:20: test/cart.test.ts, test/money.test.ts, test/tax.test.ts; no command runs them sooner (a running tier is not interrupted)
  24 test files never run at their inputs, nothing queued them (the baseline is lookup-only): test/api.test.ts, test/auth.test.ts, test/billing.test.ts and 21 more; `squeal retry <test file>...` runs each once, `squeal run --all --wait` runs all 27 test files not current here
More: `squeal status --full` adds the worktree and daemon
```

`Known failures: 0` with test files not current means "no known failures yet": the current revision is not fully validated. The skill's step 4 says what to claim from it. When slow files are among the checks running and queued, `Affected checks` names them, a few by path and the rest by count, and `squeal run --slow --wait 60000`, which waits for their results.

`Outstanding:` groups the test files that are not current by what holds them, and each group ends with the command that advances it, or says that none does and why: no daemon validates (`squeal start`), files never run or stale at their inputs (`squeal retry <test file>...`, or `squeal run --all --wait` for all of them), a running tier, a queue, another worktree's run of the same inputs, a pending retry, a checkpoint in progress. It shows at most six groups and three paths a group, and counts the rest. Slow files the `Slow tier:` line counts are not repeated there. Run a group's command only when you need that result now; results still arrive with your next tool call. With every test file current, there is no `Outstanding:` block.

`More:` names what `squeal status --full` adds after it: the worktree and daemon, the results inherited from other worktrees and where from, each test file without a result with its reason, and Squeal's notes. `squeal status --notes` is `--full` with each note listed on its own line.

`squeal status --json` gives the same snapshot as a versioned JSON object; its `outstanding` field holds the groups, each with what holds it (`standing`) and all of its `files`.

After a plugin upgrade, the older daemon hands over to the newer release's: it stops what it runs and lets go of its lock, and one successor takes the lock, usually within seconds. Meanwhile nothing validates, and status says so: the first `Outstanding:` group reads `the daemon is handing over from 0.1.255 to 0.1.256 since <time>; results are as of revision N; 0.1.256 serves once the old daemon's lock frees`, and `--full`'s `Daemon:` line says the same (`stopping since <time>` when no newer release claimed the handoff). Keep working; results arrive once the successor serves. Past 130 s the line adds `past its 130 s bound` and ends `` `squeal start` finishes it ``. With `--json`, `daemon.stopping` holds `from`, `since`, `overdue` and, for a handoff, `to` and `boundAt`; `daemon.state` stays what the heartbeat says.

In a Codex or Pi shell, status adds a line starting `Codex:` or `Pi:` when no Squeal consumer of this session is registered in this worktree: Squeal's hooks or Pi extension do not run in the session, or have not registered it yet. The line names the step that enables them (trusting the hooks, installing the Pi package); tell the user, and leave the step to them.

## Waiting for pending checks

Results arrive with your next tool call, so by default keep working. Only when you need a result before your next step, for example before saying the task is done, run `squeal status --wait 60000`. It replaces `sleep` and polling.

It returns once the test files your edits re-keyed since Squeal last told you something have their results (a pass, a failure, a skip, or unknown with a reason), or as soon as one of their checks changed (a new failure or a recovery), and at the latest after the given milliseconds; then it prints status as `squeal status` does (`--full` adds the same detail), and last the line saying why it returned. An edit to an environment input (the Vitest config, a setup file, the installed lockfile) re-keys every test file, and a pytest project's config or a sync of its environment every file of that project, so its wait holds for all of them. A baseline, a backlog, slow files and other worktrees' work do not hold it, and other checks' changes do not end it: the line counts them, and the `Outstanding:` block above it says what else is not current. When slow files are not current, a quiet line says so and names `squeal run --slow --wait 60000`, which waits for their results, joining a slow file already running.

Its last line says why it returned, with the revision and the time waited, then the worktree's known failures and its checks running and queued:

- `Returned on quiet`: none of the test files your edits re-keyed is pending; while other test files are not current, it adds `this wait does not hold for the rest of the worktree`. Quiet says no result your edits owe is outstanding, not that they passed: read the outcome in the snapshot it prints.
- `Returned on news`: a check of those files changed; read it as you would a SQUEAL message.
- `Returned on timeout`: some of those files are still pending, and the line says how many. Wait again, or say so; a timeout is no reason to run those files yourself.
- `Returned without a daemon: no daemon has validated since <time>; results are as of revision N`: nothing gets validated, so results are as old as that revision, whatever the files hold now. Run `squeal start` and wait again, or run the tests yourself. The wait starts no daemon.

While the daemon hands over, the wait goes on and its line says `the daemon is handing over from 0.1.255 to 0.1.256 since <time>, so the wait went on`. A handoff that takes longer than 130 s returns ``Returned without a daemon: the handoff to 0.1.256 did not finish within 130 s; `squeal start` finishes it``; a named wait says the same after `Named test files have no verdict:`.

The exit code is 0 in all four cases. Keep the limit below your shell tool's own timeout. On a busy host give it `120000`: at load 100 to 170 on 24 CPUs, an edited file's result took 1 to 16 s at the median and up to 51 s. A daemon from an older release names no files: the wait then returns when nothing at all is pending, or on any check's change. With `--json`, stdout is the snapshot with a `wait` field (`outcome` is `quiet`, `news`, `no-daemon` or `timeout`; `edit`, when the daemon named the files, holds `since`, the first revision of the window, `testFiles`, `pending` and `otherTransitions`) and the line goes to stderr.

Results for particular files also arrive with your next tool call; when you need them first, name them: `squeal status --wait 60000 <path>...`. Name the files you just changed when the wait above would hold for many more (after an edit to an environment input, or other edits that re-keyed most of the suite), or a test file your edits did not re-key, which the wait above does not hold for. A test file's path selects only that test file, even when other test files import it or read it; any other path, such as a source file, selects every test file that imports or reads it, as far as Squeal's record for this worktree knows. The wait returns when every selected file has a result at the current revision, or at the deadline. A selected slow file is held for like any file, since it runs after the fast tests; under `slow.trigger: "idle"` one that waits for a pause or `squeal run --slow` is not held for: the verdict line names it, and a wait that selects only such files returns at once without a verdict (exit 3). It prints the revision line, then the files it selected and their failures in full, and last their verdict, `Named test files at revision N: no known failures; ...` or `Named test files have no verdict: ...`, which counts the files still pending by what holds them, then the worktree's known failures and what in it is not current; `--full` prints the worktree's status first. Without a verdict, one line per class comes before it (`Pending:`, `Current:`, `Stale:`, `Unknown:`), and each pending file says what holds it, with a bound when one is known: its run in a lane, a tier running before it, another worktree's run of its key, the slow tier, or a revision not listed yet; a test file named by its own path that the wait moved ahead of other queued work says `queued, promoted`, also when the wait times out. A test file named by its own path that is stale or unknown with nothing queued gets one run asked, as `squeal retry <file>` does, and the wait holds for it as pending: ``Run asked: <file> was stale with nothing queued, so this wait asked its one run at these inputs, as `squeal retry <file>` does.``; a wait that times out before that run ends adds `; the run is pending`, and until the daemon queues it the file reads `run asked by this wait; the daemon has not queued it yet`. It asks no second run at the same inputs, none for a file another worktree is running at its inputs, and none for the files a source path selects. It exits 0 with every selected file current and passing, 1 with a known failure among them, and 3 without a verdict (a file pending at the deadline or unknown, no daemon). Without a verdict, the line says which revision the passes it lists ran at, that a later pass is not reported and a failure arrives with a later tool call, and ends with the command to wait again. After exit 3, run the same wait again before you report a result. A path that selects nothing is named beside that verdict, `no test file's closure holds <path>`, and leaves no clean one: the wait still holds for the files the other paths select, and exits 1 with a known failure among them, else 3. When no path selects a file, it exits 3 at once with `No verdict: no test file's closure holds <path>`; name the test file itself instead. Any other path that is not a listed test file gets a line after `Selected:`, `Not a listed test file: <path>; it selects the N test files that read it`. One with a test file's name that no runner here lists reads `Not run by Squeal: <path> ...`: Squeal does not run it, the test files that read it are not it, and with them passing the selection has no verdict (exit 3); run that test with the repository's own command. Other files' work and changes do not affect it. With `--json`, stdout is the snapshot with a `selection` field, and the lines go to stderr: `selection.code` is the exit code and `selection.result` the same as a word, `pass`, `fail` or `none`; with `none`, `selection.reason` names what holds the verdict: `no-daemon`, `lapsed`, `on-hold`, `paused`, `focused`, `unsynced`, `unlisted`, `pending`, `not-current`, `not-run` or `unmatched`. Gate on `selection.code` or `selection.result`, never on a file's `state`: `current` says a result is up to date, not that it passes. `selection.testFiles` lists each selected file with its `state` (`current`, `pending`, `stale` or `unknown`) and, when known, its `verdict` (`pass`, `fail` or `skip`), `selection.unmatched` the paths that select nothing, and `selection.paths` each named path with its `kind` (`test-file`, `source`, `not-run` or `unmatched`) and how many test files it `selects`. `selection.asked`, present only when the wait asked a run, lists each such file with `pending`, and once its run ended its `outcome` (`passed`, `failed`, `unknown` or `cancelled`). The same payload is also under `wait`, as before.

Results for some checks of a large test file arrive with your next tool call too, after the file's whole run; when you need them first, add `--check <text>`, repeatable, to the named wait: `squeal status --wait 60000 test/api.test.ts --check 'rejects a bad token'`. It selects the checks of each test file named by its own path whose name within the file holds a text; a name copied from a FAIL line, with its `<path> > ` prefix, selects the same checks. The daemon runs them first, alone, and the wait returns with their outcome, each failure with its first error and location: `Focused: 2 checks of test/api.test.ts at revision 4, run alone in 1.2 s; not the file's verdict.`, or `No check of test/api.test.ts holds "<text>" at revision 4 (the run collected 30 checks).` when the text matches nothing, and last `Focused: 1 of 2 selected checks failed; no verdict for the file yet: ...`, which names the wait for the file. It exits 1 when a selected check failed, else 3: a focused pass says nothing of the file's other checks, so say the file passes only after its own run. A focused result is a first run, not re-run, and never a known failure: `squeal status` shows it on a `Focused (not counted):` line while the file waits for its own run, and `squeal why <check>` below the known state. A file already current answers as the named wait does, with the selected checks named from its result. A source path selects no checks, so `--check` with source paths only is a usage error (exit 2). A slow file and a node:test file run whole, and a daemon older than `--check` says `this daemon (Squeal <version>) runs whole files only`: the wait then waits for the file's run. With `--json`, `selection.outcome` is `focused` and `selection.focused` lists each file's selected checks. Without `--wait`, `squeal status <path>... --check <text>` shows the focused outcome stored now and asks for nothing.

`squeal status <path>...` without `--wait` answers the same question now, without waiting for pending files, whose results arrive with your next tool call. It asks the daemon whether its pass over your edits is stored, for at most 750 ms, then prints the same lines, its last `Named test files at revision N: ...` with a verdict or `Named test files have no verdict at revision N: ...` without one. When the daemon has not stored that pass in time, the line says `the daemon has not stored its pass over the latest edits` and gives no verdict, since an older result may not hold your edits; a daemon that cannot answer at all gives none either (`the daemon did not answer its sync`): wait with `squeal status --wait 60000 <path>...`. It exits as the wait does, 0, 1 or 3. Unlike the wait, it does not move a named test file ahead of other queued work. With `--json`, stdout is the snapshot with the same `selection` field, whose `outcome` is `snapshot`, so one filter on `selection.testFiles` reads both forms; the payload is also under `named`, as before, and the lines go to stderr.

## Red/green: checking that a test catches the bug

To show that a test fails without your fix and passes with it, let Squeal run it rather than running it yourself. Results would arrive with your next tool call anyway; here each step needs its result before the next, so wait after each edit:
```sh
# 1. Revert the fix, then:
squeal status --wait 60000   # Returned on news: the test's PASS -> FAIL
# 2. Restore the fix, then:
squeal status --wait 60000   # Returned on news: FAIL -> PASS
```
Each edit is its own revision, so the first wait reports the revert, not the fix: the result is the FAIL the test had before your fix, often looked up from the store at once since the reverted files are the same bytes, so that wait may return on quiet instead of news. Quiet says no result your edits owe is outstanding, not that it passed: read the outcome in the snapshot the wait prints. The test catches the bug when it is listed under `Known failures` after the revert and gone from it after the restore; listed as passing after the revert, it does not. For one test of a large test file, name the file and add `--check '<test name>'` to each wait: it returns at that test's own first run, before the file's, which still decides.

## squeal why

`squeal why '<check name>'` prints the history and provenance of one check and the path to its last run log, which holds the full output; SQUEAL messages carry only the first error line and its location. A FAIL report ends with the command for its first failure:

```text
Full output: squeal why 'src/math.test.ts > math > adds'
```

Use a name exactly as a SQUEAL message or `squeal status` printed it. Any unique part of the name also works.

When the result shown ran at a revision older than the current one, a `Changed since revision N:` line lists each path changed after it, with the revisions that changed it (at most 20 of each). Those changes are what the result has not seen; at the current revision the line is absent.

Its `Run log:` line names the `vitest.log` of the run that produced the result shown, from the worktree it was inherited from when it was. That file holds the run's `console` output, but it covers every test file of that run, not only this check. To see only this check's test file's lines, add `--include-logs`:

```sh
squeal why 'src/math.test.ts > math > adds' --include-logs
```

It prints at most 200 of them and says how many there were. A log Squeal has pruned is reported as pruned; the result's errors are still in the store.

## squeal failures

`squeal failures [<test file or directory>...]` lists this worktree's stored failing results, newest first, each with its check, run and first error line, and says how many there are. `--check <text>` keeps the checks whose name holds the text, `--error <text>` the failures whose error holds it, and `--all-worktrees` adds other worktrees' failures. Each edit that re-runs a failing check stores one more failure of it; `--per-check` lists each check once, at its newest failure. It lists 20 by default, `--limit <n>` more, and `--limit all` every one. When a report groups checks that failed with one error and location, the group ends with the command that lists each of them, and any other check in those files that failed with that error:

```text
Full list: squeal failures tests/components --error "ReferenceError: ResizeObserver is not defined" --per-check --limit all
```

## squeal code

With `complexity.enabled` (see `policy.md`), `squeal code` lists every function over the complexity threshold, newest first by the revision it went over: its location, its complexity (CC) with the decision points by kind, and that revision. It reads the store and needs no daemon.

```text
Complexity: 2 functions over 20
  src/core/scheduler/tiers.ts:120  selectTier  CC 23 (if 12, logical 6, optional-chain 4), over since revision 14
  src/core/ledger.ts:40  Ledger.settle  CC 31 (if 20, case 10), over since revision 3
Not judged:
  src/big.ts: 600 KiB, over the 512 KiB limit (complexity.maxFileBytes); its functions are not counted
```

`squeal code <path>...` lists every function of those files or directories, over the threshold or not. `--changed` keeps the functions whose state changed since this session registered, the ones a message counts as `and N more complexity changes`. `--told` keeps the functions over the threshold that this session was told about as `FAIL` or `STILL FAIL`, the ones a message with test news counts as `Code: 2 functions over 20 that this session was told about`, sent once per change of the standing summary; in a shell whose session is not registered in the worktree, it lists those told to any session that is. The two do not combine. The files not judged follow the functions, with why: too big, not parsed (the functions in a parse error are not judged), or not counted yet. With complexity off it says so and exits 1. `--json` gives a versioned object: `functions`, each with `path`, `qualifiedName`, `occurrence`, `line`, `outcome`, `complexity`, `threshold`, `decisions` and `changedAt`, and `files`, each with `path`, `reason` and `size`; with `--told`, `told` names whose messages it read, its `scope` `session` or `worktree`. With coverage on (see `policy.md`) and paths, each function also has `coverage`: `crap` with its `outcome` and `value`, and a `reason` when the outcome is `unknown` or `pending`, and `uncovered`. A function whose CRAP is not judged yet reads `pending`, never no CRAP; the text line ends `CRAP pending: <reason>`. With `coverage.children` (see `policy.md`), what the processes and worker threads a test starts run counts too, as a lower bound, and the words say so. A file that only such a process runs is judged from the test file that starts it while `observe.runtimeInputs` is on (the default); with it off, it reads `not measured`.

`squeal status` counts them in one line under the test lines, `Complexity: 62 functions over 20, 2 since this session started; squeal code lists them.`, and `--json` adds them as `code`. In a shell that names no session, the line counts since the oldest session registered in the worktree, and says so.

## squeal code --base

`squeal code --base <ref> [<path>...] [--test <file>...] [--group <name>...] [--parts <dir>...] [--timeout <seconds>] [--exceptions <file>] [--json]` is a one-shot check of the code a branch changed, before a pull request or in CI. Unlike `squeal code` without `--base`, it runs tests: with no daemon and no session, for up to `--timeout` seconds in all, whole seconds, default 600. It needs neither `complexity.enabled` nor `coverage.enabled`. It keeps what it runs in the repository's stores, so a second run on the same bytes runs only what the first did not complete.

It judges every JS/TS function that changed between `git merge-base <ref> HEAD` and the working tree: untracked files, nested functions and test callbacks included. A function moved with the same body is not a change, nor is a test callback whose occurrence number moved because a same-named one was added before it. Removed functions are not judged. A function a changed line touches but that is not judged is left out, with why: `unchanged`, its body is as it was at the merge base (a new test title, a reindent), or `moved`, its body is at the merge base in another function of a changed file (a move, a rename or a copy). The verdict line ends with their count, for example `7 left out as moved or unchanged; --json lists them.`, and says nothing when there are none. It selects the test files that load a changed file, the changed test files and the `--test` files; `--test` takes the files after it, so paths go before it. The limits are `complexity.threshold` and `crap.threshold` in `squeal.config.json` as it is at the merge base, so a branch cannot loosen its own check, and equality passes. Paths keep the functions in those files or directories.

Of the test files that load a changed file and the changed test files, only those of a check group in scope run (`checks` and `gate.groups` in `policy.md`, both read at the merge base). By default every test group whose moment is not `"manual"` is in scope, so with no `checks` every test file is. `gate.groups` names the groups in scope instead. `--group <name>...` adds groups for one run, `"manual"` ones included; it takes the names after it. A name that is not a test group at the merge base is a usage error. `--test` files run whatever their group. A selected test file outside the scope does not run and starts no setup, but Squeal reads which files it loads. A function whose evidence from the files that ran passes reads `pass`, and its JSON row lists the files left out in `loaders.leftOut`. One whose CRAP is over the limit reads `incomplete` with the gap `left-out`, since more coverage could lower it. A CC over the limit stays a `violation`. The verdict line names each group that did not run, for example `browser (manual) did not run: 100 test files load changed code; add --group browser to run them.`

Each selected test file's results and coverage come from the first of these that holds them for the bytes in the working tree now:

1. The parts `squeal ci record` wrote in CI, in each `--parts <dir>`, which takes the directories after it. A Vitest test file is taken from them when it is in exactly one part, that run's coverage records came from Squeal's coverage provider, or from the project's own V8 provider that `ci record` read, at this Squeal's versions, and it recorded what its tests read, and every file it imported or read at run time had the bytes then that it has now, and that run had the environment the gate's Vitest has here: the same Node, platform, Vitest version, resolved config and allow-listed variables, and it wrote no snapshot (Vitest's snapshot update mode was "none", as with CI set). A part whose project ran in another environment or could write snapshots, or that holds none, gives nothing for its files, with a note on stderr that names the difference. A test file that failed there is taken with its failure, with or without a coverage record. The parts of an older format, of other coverage versions, of a run where `ci record` made no coverage records, or whose records came from another collector give nothing, with a note on stderr that says why; so does every part when `coverage.children` is on at the merge base, since `ci record` does not measure child processes. A `--parts` directory that is missing or holds no part, or a part that does not read, is a setup error. The parts are only read.
2. The repository's stores, which its daemons and this command fill: a test file with results and a coverage record at the key a daemon in this worktree gives it. A daemon that runs is not asked.
3. A run of the test file here, with Squeal's coverage. Every other selected test file runs.

stderr counts what did not run, for example `2 of 3 selected test files read from the parts`.

Each test file it runs to completion is written to the stores at that key, with its results and coverage record, as a daemon writes it: the next `--base` run on the same bytes reads it, and so does a daemon, which then does not run it. A test file that did not finish, was left out, did not run because of its `prepare`, or came from the parts is not written. Nor is one whose files changed during the run, or that read a file at run time that its key does not name yet; a daemon names such a file once it has run that test. With no store yet, the first write creates it. While a daemon runs in this worktree, nothing is written, with one note on stderr. When another process holds the store's write lock for 10 s, the files not written by then are not kept, and a note on stderr says how many. It reads and writes the stores only when `coverage.enabled` and `complexity.enabled` are on in the working tree's `squeal.config.json`, as a daemon there stores coverage records; otherwise every selected test file runs and nothing is kept.

Before the first run, stderr gives each runner's estimate of the files left to run, from the durations the stores hold for them at any commit, for example `Vitest: 1283 test files to run here, up to 11 at once: about 1590 s from the stored durations of 1213 (the others at their median)`. With no stored duration it says the time is unknown. When the estimate is over what is left of the budget, the line ends with the ways out: a longer `--timeout`, paths that narrow the changed files, fewer check groups (`gate.groups` at the base, `--group`), or CI's results with `--parts`. The estimate is advice: the run starts anyway, and the verdict does not read it. The stored durations are from this host's daemon runs, under its load at the time. The runners run one after another, the one with the smaller estimate first (with no stored duration at all, the one with fewer test files), so a large Vitest selection does not leave a few quick node:test files unrun; stderr lists the runners in that order.

Each runner gets its files grouped by changed file: first the test files that load the changed file whose loaders took the least stored time (or are fewest, with no stored time), then those of the next one. So a changed file that a few tests load completes before one that every test loads, which within a short budget may not complete. Test files whose imports Squeal cannot read run last.

Each changed function reads one state:

- `pass`: CC and CRAP at or under the limits, from a coverage record of every test file that loads its file. A pass can also be proven from some of them, since more coverage only lowers CRAP.
- `violation`: CC over the limit, whatever its coverage, or CRAP over it.
- `skipped`: its file matches `coverage.exclude` (see `policy.md`) and CC is at or under the limit. It gets no CRAP, never counts as pass, and does not block.
- `accepted`: a violation an entry of `--exceptions` covers. It keeps its measured scores, names the entry, and does not block.
- `incomplete`, with its gap: `not-counted` (in code that does not parse), `no-loader` (no test loads its file), `not-finished` (a test file that loads it did not finish in the budget), `no-record` (no coverage record of its file's bytes now), `not-joined` (its coverage could not be matched to it), `test-failed` (a selected test failed), `skipped` (a test file that loads it skipped a test), `left-out` (a test file that loads it is in a check group this run left out), or `not-prepared` (a test file that loads it did not run: its node:test entry's `prepare` failed, timed out, or is declared only at the head; see `nodeTest[].prepare` in `policy.md`). A function never gets a CRAP from 0% coverage because no test loads it.

With `coverage.children` at the merge base (see `policy.md`), the runs also measure what the processes and worker threads the tests start run, as a lower bound. A file that only such a process runs is loaded by no test file, so name the test that starts the process with `--test`. A coverage file of a process that cannot be read is dropped alone, with a note on stderr, never a gap: a lost process only lowers coverage, so it cannot turn a violation into a pass.

```text
Code gate: violations. 3 changed functions against origin/main (merge base 1f097649): 1 violation, 1 incomplete, 1 pass.
  src/math.ts:5  deep  CC 21 over 20, coverage 0%, CRAP 462 over 30: violation
  src/orphan.ts:1  lonely  CC 1: incomplete: no test loads its file
JSON report: squeal code --base origin/main --json
```

The verdict line comes first, then each function that is not `pass` with its gap or measure, then each changed file that could not be counted (over `complexity.maxFileBytes`, not parsed, or not a regular file), each exception that applied to no function, each test file with failed tests and each test file that did not finish, and last the command for the JSON report. The verdict is `violations` when one function is a violation; else `incomplete` when one is incomplete, a changed file was not counted or a selected test failed; else `pass`, which `accepted` functions do not prevent. The exit code follows it: 0 pass, 1 violations, 3 incomplete, and 2 on a usage or setup error, such as a ref that names no commit, a `--test` file no runner lists, a `--group` name that is not a test group at the merge base, an `--exceptions` file that cannot be read or parsed, or `--changed` or `--told` with `--base`. So a CI step can tell "fix the code" from "the evidence is missing". Problems in `squeal.config.json` and the runners' notes go to stderr, never to stdout. CRAP is rounded in the text only.

`--exceptions <file>` reads exceptions: a JSON object with `format` `squeal-code-exceptions/1` and `entries`, each with `path`, `qualifiedName` and `bodyHash` (the changed function at the head), `measure` (`complexity` or `crap`), `kind` (`inherited` or `approved`), `value` (the highest accepted value), `issue` (a URL), `approver` and `baseCommit` (the merge base it was accepted against). Squeal does not decide who may approve: the caller, for example CI code from the base commit, builds the file from evidence it checked, never from a file or label on the branch alone. An entry applies only to the changed function with its path, name and body hash, when its `baseCommit` is the merge base. An `inherited` entry holds when the function was already over at the merge base and did not get worse, as Squeal counts the base: for `complexity`, the base CC is over the limit and the head CC is at most the base CC, which is at most `value`; for `crap`, the head CC is at most the base CC and the head CRAP at most `value`. An added function has no base, so nothing is inherited. An `approved` entry holds when the head value is at most `value`. No entry covers missing evidence: an incomplete function stays incomplete, and a function whose CC an entry covers still needs complete coverage evidence for its CRAP. A test file the scope left out is not missing evidence: an entry can cover a function whose only gap is `left-out`. A function over an entry's `value` stays a `violation`, and the line says why its entry does not cover it:

```text
Code gate: violations. 2 changed functions against origin/main (merge base 1f097649): 1 violation, 1 accepted.
  src/math.ts:5  deep  CC 23 over 20, coverage 100%, CRAP 23: violation; inherited complexity exception does not cover it: CC is over the base's 21
  src/parse.ts:12  parse  CC 22 over 20, coverage 100%, CRAP 22: accepted: inherited complexity exception, https://github.com/acme/app/issues/41
JSON report: squeal code --base origin/main --exceptions exceptions.json --json
```

`--json` gives the `squeal-code-gate/1` report: `versions` (Squeal, the counter, the coverage provider and record, the quality policy); `base`, with the ref, the merge-base commit and the `policy` read there, `coverageChildren` `true` in it when `coverage.children` is on, and `gateGroups`, the `gate.groups` it used or `null`; `head`, with the commit, whether the tree was `dirty` and each changed path with its blob; `budget`; `scope`, with the `groups` in scope (each `name`, `at` and `from`: `default`, `gate.groups` or `--group`) and each group left out that owns a test file in `leftOut` (`name`, `at`, its test `files`, the ones `selected` that did not run, and `add`, the flag that runs it); `functions`, each with `path`, `qualifiedName`, `occurrence`, `line`, `bodyHash`, `change` (`edited` or `added`), `complexity`, `coverage`, `crap`, `state`, `gap` and `loaders` (the test files that load it, `expected` and `measured`, and `leftOut` when the scope left one out), and with `--exceptions`, `exceptions` when an entry names it: each `entry`, its `outcome` (`covers`, `not-needed`, `incomplete`, `over-value`, `worse-than-base`, `not-over-at-base` or `not-at-base`) and the `baseComplexity` Squeal counted; `omitted`, each function left out, with `path`, `qualifiedName`, `occurrence`, `line`, `reason` (`unchanged` or `moved`) and, for `moved`, `base`, the `path`, `qualifiedName` and `occurrence` of the first function at the merge base with its body, sorted by path and name; `uncounted`; with `--exceptions`, `exceptions.unused`, each entry that applied to no function with `why` (`base-commit`, `body-hash` or `no-function`); `runs`, per runner the test files `selected`, `completed` and `notFinished`, the `failed` tests, `from` when one of them did not run here (each selected test file with where its evidence came from: `run`, `store` or `parts`), `estimate` when a file was left to run here (`seconds`, `null` when no duration is stored, the `files` it covers, the ones `known` with a stored duration, and `width`, the most that run at once) and `durationMs`, with `coverage.children`, `children`: the coverage files of the processes and threads the tests started that it `read` and `dropped`, and for node:test, `prepare` when an entry's `prepare` ran or was due: each `project`, `command`, `outcome` (`passed`, `failed`, `timed-out` or `not-at-base`), `exit`, `durationMs` and the selected files it kept from running in `notRun`; `verdict` and `counts`. Its only times are `createdAt` and the run durations, so the same inputs give the same report; `estimate` reads the stores and the host's CPU count too.

## squeal reach

`squeal reach` says what one edit of each file re-runs, from the stores. You ask for it; no message pushes it. It needs no daemon, runs no test, and writes nothing. Use it when you want to know why an edit re-runs much of the suite, or which change would cut that. Every number is relative to this repository's own suite, recorded seconds and edits.

```text
Reach: what one edit of each file re-runs, of 1490 test files and 6696 s recorded.
Edits: 1523 from 2026-10-06 to 2026-11-07, every worktree's watch revisions in which HEAD did not move, of files this worktree has.

Files, by avoidable seconds per edit, then seconds re-run:
  1. src/core/state/slow.ts
     re-runs 85% of the suite: 959 test files, 5692 s; 6 edits in the window re-ran 34152 s
     coverage: loaded only 41%, called 29%, not loaded 25%, outside the test's process 5%; avoidable 3700 s
     paths: barrel 80%, runtime read 20%
     gateway: barrel through src/core/state/index.ts, for example test/a.test.ts → src/core/state/index.ts → src/core/state/slow.ts
     suggestion: import src/core/state/slow.ts from its own path in the files that use it, or split src/core/state/index.ts

Files, by seconds re-run over the window's edits:
  1. src/core/state/slow.ts: 6 edits re-ran 34152 s, 5692 s each; avoidable 3700 s; rank 1 above
```

The first part ranks files by their avoidable seconds per edit: the seconds of test files that load the file through their imports, or through the setup files that run in each test's process, but call none of its functions, or do not load it at all. Setup reached from the config or a global setup file runs outside the test's process, and its seconds are never avoidable. Where coverage cannot tell (coverage off, or a runner such as pytest that gives no records), the seconds on import paths count instead, and the entry says `on import paths with called unknown`. Then it ranks by the seconds one edit re-runs. Files that share a gateway and the same test files are one entry, such as `11 files in src/core/types/ through src/core/types/index.ts`. Each entry gives the share of the suite, the edits in the window, the coverage split (`called`, `loaded only`, `not loaded`, `unread`, `no record`, `outside the test's process`, `unknown`; `unread` also means the record cannot tell the file's top level from a function that starts with it), the path kinds (`setup`, `declared input`, `child process`, `runtime read`, `direct`, `barrel`, `test helper`, `transitive`, or `import` while import chains are not stored), the gateway with one example chain, and one suggestion. The gateway is that of the route with the most avoidable seconds, when the file has one. A suggestion is evidence and an option, not an instruction: a barrel's file that exports no runtime value can leave the tests' closure with `export type *`; a test helper is worth splitting only when some test file that loads the file through it never calls it, so with none there is no suggestion. When the module that imports the file also imports many of its sibling modules, such as a factory that loads every runner, and a barrel or helper comes before it on the chain, the entry names it as a `second gateway` with its own suggestion, which counts the test files that load the file through that module and never call it; when every one of them calls it, there is no such suggestion. Tests that start the program from source (`child process`, `runtime read`) get a note when their seconds outweigh the import seconds: Squeal re-runs them by design, and their seconds are never avoidable. A second, short list ranks the same entries by the seconds the window's edits re-ran, with each entry's rank in the first list; with no edits recorded yet, as in a repository that just installed Squeal, it says so in one line and ranks nothing. The last part ranks test files by avoidable pair-seconds: a test file's seconds times the source files it loads on import paths and never calls (`avoidablePairSeconds`), with the direct import that brings in most of the uncalled files.

`squeal reach <path>...` gives those files or directories in full: each path kind and gateway with its test files, their seconds and coverage, and one chain. Each list lists 10 entries and says how many more there are; `--limit <n>` lists `n`. In the named view, it bounds the routes of each file and the test files of each route the same way. `--json` gives every entry in a versioned object (`v`, `history`, `suite`, `window`, `coverage`, `absent`, `files`, `byEdits`, `testFiles`, `named`, `proposals`), or `--limit` entries when given. The lists hold only paths this worktree has: files of other worktrees or commits that tests read at run time are left out, and one line counts them (`absent`). Edits count only the paths this worktree has.

While no daemon has listed this worktree's test files, the whole answer is a proposal: `squeal start`, which lists them and looks up the results stored for their inputs in any worktree of the repository; under the default `baseline.onStart` it runs no test. With test files listed and no recorded result, the whole answer is `squeal warmup`, how many test files it runs, and its cost, about one run of the whole suite. Test files with no recorded seconds are left out of every share, and the report counts them. With coverage off, `called` reads `unknown`: the path kinds are only a proxy. The report then proposes the `squeal.config.json` key and `squeal warmup`, with the cost: every Vitest and node:test file runs once more, and each later run takes about a tenth more CPU. When some test files have no coverage record at their current inputs, it gives their share and names them: `squeal retry <test file>...` runs once each one that has no result at its inputs; a current result is re-run only by `squeal run --all --force`, which re-runs every test file, about one run of the whole suite. It never starts a run or changes the configuration. Exit 0 with an answer, the proposal included; 1 when there is no store; 2 on a usage error.

## squeal run --all

Queues every test file that has no result for the current files (`--force` queues all of them). Completion shows in the full header (at registration and Stop) and `squeal status` as `Full-suite checkpoint: completed at revision <current>`. Policy `stop.requireFullSuite` can require one before you stop.

`--wait [<ms>]` waits until the checkpoint ends, or at most `<ms>`, and gives its verdict as its first line, then the start line and status. Exit 0: it completed with every test file current, no known failures, and the worktree still at its revision (`Checkpoint <id> completed at revision 9: no known failures; 290 test files, 284 already current, 6 run now`). Exit 1: it completed with known failures, tests and test files that did not load counted apart. Exit 3: Squeal has no verdict (`Checkpoint <id> has no verdict: ...` or `No verdict: ...`): no daemon, the checkpoint abandoned, the deadline passed with files pending (the checkpoint goes on in the daemon), a test file without a current result, or an edit recorded a newer revision. On 3, wait again, or run the test command yourself.

## squeal run --slow

Asks the daemon to run the repository's slow files (`slow` in `squeal.config.json`: end-to-end and other suites too slow to run after every edit) as soon as no fast work of an edit is pending (background work such as a baseline does not hold them back). They also run on their own after the fast tests (under `slow.trigger: "idle"`, only while you are idle), and when your last session ends the daemon runs them before it exits; ask when you need their result now, for example before saying slow tests pass. It prints how many slow files it queued at which revision, or that there are none to run (none declared, or all current at this revision). Their results arrive with your next tool call, so by default keep working; `--wait <ms>` waits after the request as `squeal status --wait` does, and also until every slow file it queued has its result (one already running counts: the wait joins its run instead of starting another), then prints status, and last the line saying why it returned. Whether it is needed before saying the task is done is the repository's policy, read off the end of the `Slow tier:` line (the skill's step 4): `Stop waits up to … for them or holds the agent …` means it is, once you change a file, and Stop keeps you going at most `stop.maxHolds` times in one turn (the line ends `once` at the default 1, else `up to 3 times in a turn`); any other ending means it is not, and a claim that slow tests pass still needs the line to say every slow file is current. That last line says `the N slow files run --slow queued have their results`; on timeout it says how many of them are still pending and their paths, so say so, or wait again. A change of one of their checks (a slow failure) ends it early, as news. Exit 1 means no daemon runs, or the daemon predates `run --slow` (restart it with `squeal stop` then `squeal start`). With `--wait`, exit 3 means it has no verdict: the wait returned without a daemon, or timed out with a slow file it queued still pending; say so, or wait again.

## squeal run <group> <path>...

Runs now only the test files of group `<group>` (`checks` in `policy.md`) that the paths select, whatever the group's moment, `"manual"` included. Use it where the primer says no test group runs after each edit: there no message between edits is not a pass. A test file's path selects that test file. Any other path, such as a source file, selects what an edit of it runs first, among the group's files: its namesakes (`src/parse.ts` selects `parse.test.ts`), or with none the test files that import it directly, then the `runner.tierSize` shortest of its other direct importers. A selected file that is current does not run again; its result counts. The group's other files keep waiting for its moment or `squeal run <group>`: a narrow run never makes the group current, and Stop still waits for every file of a group at `"stop"`.

It prints what the paths select, such as ``Group e2e at revision 12: these paths select 2 test files; 2 queued, which run now.``, then, when there are any: the group's other test files that read the paths and what they wait for; each other group with test files the paths select, with its own command, ``Group unit has 1 test file these paths select: `squeal run unit src/parse.ts` runs it.``; and the paths that select no test file of any group. With `--wait <ms>` it then waits for the selected files only and gives their verdict first, ``Selected test files of group e2e completed at revision 12: no known failures; 2 test files, 2 queued by this request``, then status. Exit 0 when every selected file is current and passing, 1 with a known failure among them, 3 without a verdict: a file pending at the deadline or without a current result, no file of the group selected, or a path that selects nothing while the others pass. A lint group takes no paths (exit 2): run `squeal run <group>`. A daemon older than this command runs nothing and says it predates narrow runs; `squeal stop`, then `squeal start`, starts the installed version.

## squeal start

Starts this worktree's daemon, or finds it running, then prints status. It also ends every `squeal hold` of the worktree and names the commands that still run. Exit 0 once a daemon answers. A daemon it starts has 30 s to answer: past that, while its process runs, `start` says the daemon is still starting, names `squeal status`, and exits 3. That is no failure: the daemon goes on starting, and `squeal status` says when it serves. Exit 1 when the daemon's process ended without an answer, or no daemon could be reached or started. A daemon that stops or hands over is never called alive: `start` asks it to stop, starts the successor when no hook has, and waits up to 90 s, as `squeal stop` does, for a daemon of its own release or later. Then it prints `Squeal daemon started for <root>, after the 0.1.255 daemon handed over in 2.4 s` and status, and exits 0. Past 90 s it exits 1 and names what still holds the lock: the old daemon's process and the processes it started. Tell the user, and run the tests yourself meanwhile.

## squeal stop

`squeal stop [--until-start] [root]` stops a worktree's daemon, this one's or the one at the root you name, and waits until the daemon and every process it started are gone. Run it before you delete a worktree. Exit 0 once they are gone or when no daemon ran; exit 1 when one still runs past its bound, and the output names it. A path that is not a worktree's top level stops nothing and exits 1, so it never stops the checkout around it. A root that is already deleted still names its own daemon: the stop asks only the daemon that served that path, and says that it and its processes stopped (exit 0), which still run (exit 1), or that this cannot be told (exit 1). With no daemon there it stops nothing: exit 0 when the repository's store still records that worktree, as it does after its daemon exited, and exit 1 when no store it can read does, as for a mistyped path. It reads the store of the checkout the path was inside and of the checkout you run it from, so run it from the same repository. A hook starts a daemon again at the next edit; `--until-start` keeps it stopped through edits and Git operations until `squeal start`. `--until-start` on a path that does not exist is refused (exit 1): there is no worktree to hold yet.

## Holding a new worktree before its agent starts

A hold covers only its own worktree: `squeal stop --until-start` in your worktree does not hold a worktree you create for another agent. To create one whose validation is held from its agent's first hook, as an orchestrator does, take these steps in this order:

1. Create the worktree, for example `git worktree add <child root>`. A stop before the worktree exists is refused.
2. Run `squeal stop --until-start <child root>`, from any directory. It held the worktree when it exits 0 and writes nothing on stderr; a line on stderr means the stop could not be recorded, and a hook may start a daemon. The stop is recorded in the repository's store, or, with no store yet, only when the child has a `squeal.config.json`; with neither, no hook starts a daemon there, but if a `squeal.config.json` arrives later, stop the child again before its agent starts.
3. To check it, run `squeal status --json` in the child root: `daemon.stopped` and `daemon.untilStart` are `true`. Status starts no daemon.
4. Start the agent's session in the child. Its hooks start no daemon, and no edit or Git operation starts one. Its tests are not validated, and its session start and status say that the daemon is stopped until `squeal start`.
5. To end the hold, run `squeal start <child root>`, or `squeal start` in the child. It starts the daemon, which validates the child's changes.

A stop after the agent's session has started does not hold its first validation: its first hook may already have started a daemon.

## squeal hold

`squeal hold [--max <duration>] -- <command> [args...]` runs the command with this worktree's validation on hold, for a long gate the repository asks you to run yourself, such as `squeal hold -- npm run gate`, or a manual run across edits, such as a browser test you reproduce by hand. Use it instead of `squeal stop`, which your next edit ends. The daemon cancels the Vitest runs it can (a node:test or pytest file in flight finishes), starts no other, and still records each edit as a revision and queues its work. It also closes the slow tier's Vitest instance, so a project's `globalSetup` teardown frees what it holds, such as a test environment and its lease, while your command runs; the next slow tier runs the setup again. When the command exits, the queued work starts, with no further edit. The hold also ends after `--max` (default `3h`; `90s`, `30m`, `2h`, `1d` are durations), when its processes are gone, or at `squeal start`, which ends every hold of the worktree and leaves their commands running. An edit does not end it, and `squeal stop` stops the daemon and leaves the hold: the next daemon starts on hold. It prints one line on stderr when the hold begins, then the command's own output. It exits with the command's exit code, `128 + n` when a signal `n` ended it, and 127 or 126 when the command could not start; SIGINT, SIGTERM and SIGHUP reach the command. Two holds at once end when the last command exits. Without a store (no daemon ever ran here) it runs the command and says that nothing is on hold. Between separate gate steps, wrap each step; validation runs between them. For a session that wants no validation at all, `squeal stop --until-start` keeps the daemon stopped through edits and Git operations until `squeal start`.

## squeal remove

Takes Squeal out of the repository: stops the daemon of every worktree, then deletes the store and the daemons' temp directories. `--config` also deletes `squeal.config.json`. Run it only when the user asks to remove Squeal. Exit 1 means a daemon did not stop and nothing was deleted; its output names the worktree. Exit 3 means it deleted what it could, and the paths it could not delete are listed under "Still there" with their error codes: tell the user. It prints what remains: the plugin, the config when kept, and the `squeal.config.json` of every other worktree, where the next session starts Squeal again. A deleted config that git tracks is a change to commit.

## squeal init

Sets Squeal up in a repository; the user runs it, or asks you to. `squeal init --harness codex --trust` shows the Squeal hooks Codex has not trusted and asks the user whether Codex should trust them. Never answer that question for the user, and never add `--yes` unless the user asked for it: trusting hooks lets them run code in every Codex session.
