# Squeal

Under Pi `squeal` is not on the PATH: wherever this skill and its references say `squeal`, run the command the SQUEAL messages name, the Node that runs Pi with `--disable-warning=ExperimentalWarning "<package root>/dist/cli/squeal.mjs"`, the package root being the directory that holds `skills/squeal/`. The last line of a FAIL report names it too.

Squeal runs this repository's tests in the background after every edit. It reports only changes, in messages that start with `SQUEAL ·`: a check that went `PASS -> FAIL`, `FAIL -> PASS`, or failed differently. It covers the checks `squeal checks` lists from `squeal.config.json`: the Vitest tests, the node:test tests of the `nodeTest` projects, the pytest tests of the `pytest` projects, and the slow test files `slow` marks; a test file you add that matches them is picked up too. Typecheck, build and anything else the repository checks are yours to run.

## Steps

1. **Learn this repository's checks first.** Run `squeal checks` once. It lists every check Squeal runs here: what it covers, when it runs (after each edit, between your turns, at Stop, when you commit, or only on request) and the command that runs it now. A check that does not run after an edit is yours to start, through Squeal: `squeal run <check> --wait 60000`, not by hand. Before a pull request, a test check that runs only on request needs only the test files your branch's changes select: `squeal run <check> --base <ref> --wait` (`<ref>` is the branch you merge into); it says which of the check's other files it did not run, and those wait for `squeal run <check>` or CI. Its last line names what Squeal does not run here (typecheck, build, other suites): those are yours to run.
2. **Keep working, and read the reports.** Results arrive with your next tool call, as SQUEAL messages. No message means nothing changed, not that everything passes; where `squeal checks` shows no check that runs after each edit, nothing ran: use `squeal run <check> <path>... --wait 60000`. Running the test files beside your edit to learn sooner duplicates what Squeal is already running. Done when you have read every FAIL in every SQUEAL message that arrived.
3. **On a FAIL**, read its first error line and location. When they are not enough, run the message's last line, `Full output: squeal why '<name>'`, for the full output and history. Squeal re-runs a new failure once on its own, but not one from a forced run (`squeal run --all --force`, `squeal warmup`, a re-run), one already re-run at the same inputs, a slow file's, nor any when more than eight eligible test files fail anew in one tier; a passing re-run arrives as a PASS with the line `Flaky: FAIL -> PASS under the same tracked inputs`. So rather than re-running such a failure yourself to see whether it is flaky, let that re-run answer. After your fix the recovery arrives as `FAIL -> PASS`. Done when each FAIL is fixed or you can say why it stays.
4. **A failure you did not cause** (its report says it was recorded before your edit, or it comes from host load or a stopped service): do not run the tests yourself to check it. Ask Squeal to run it once more: `squeal retry <file> --reason load`, or `--reason environment` once the service runs again; then `squeal status --wait 60000 <file>` and claim from that result. Never retry past a failure your change could have caused.
5. **Wait only when you need a result before your next step**; otherwise results arrive with your next tool call. For files you just changed, `squeal status --wait 60000 <path>...` gives the verdict of the test files they select. Before saying the task is done, run `squeal status --wait 60000`, or `--wait 120000` on a busy host: it returns once the test files your edits affect have results, or one of their checks changed, but not for slow files (step 6); `squeal run --all --wait` is a full-suite checkpoint. Done when the last line gives a verdict, `Returned on quiet` or `Returned on news`; on a timeout, wait again.
6. **Before you say the task is done, make the evidence current.** Where `squeal.config.json` marks slow test files, the header's second line starts `Slow tier:`. If the last one says `Stop waits`, they are required once you edit: while one is not current, run `squeal run --slow --wait 60000`. Without `Stop waits`, say how many are not current. Claim slow tests pass only once it says every slow file is current. Done when no check of your edits is pending, the slow tier is current or counted, and every claim about tests matches a line of `squeal status`. When a check stays pending after you waited again, say it is pending: `Known failures: 0` beside test files that are not current means "no known failures yet".
7. **Run tests yourself only** when a header says no daemon is validating, Squeal's run left a result unknown, or the repository's own gate (CI, a pre-commit hook, the task) requires a run; while Squeal is still starting, use step 5's path wait instead. A SQUEAL line `No result for <path>: no test Squeal runs reads it` means the same for that file: run whatever tests it yourself. Done when what `squeal checks` says Squeal does not run has run as the repository says; a gate the repository requires is still yours to run.
8. **Results at another commit, and red proofs.** To compare with an earlier commit, run `squeal status --at <commit>` (`--run` fills both sides: it queues the runs in the daemons and waits up to 100 s (`--wait <ms>`); what still runs goes on); to compare a changed test file with its old version: `squeal status --at <base> <file> --run`; `proof` answers a different question. To show a test fails without a committed fix, `squeal proof <test file> --base <commit>` (`--env`, `--without` for a hidden dependency, `--repeat` for a flaky one). Both work in a temporary checkout and leave your tree alone: do not stash, check out or copy old files into it.

## Reading a header

The registration and Stop's report say ``Known failures: 0; 40 of 43 test files are current (run on the files as they are now), and `squeal status` counts the rest.``, after a line naming the files changed since your last report: what changed, not what caused a failure, which may be any earlier edit or none of yours. Other SQUEAL messages carry those files and how many of the test files your edits affect have not run yet; `squeal status` has every count.

## Reference

- `references/reports.md`: when reports arrive and what every header count and line means: pending, stale, unknown, inherited, `git-ignored`, the slow tier, no daemon validating. Read it when a header says something the steps do not cover.
- `references/commands.md`: what `squeal checks`, `squeal status`, `squeal why` and `squeal run` print, what the last line of each wait means, what a path selects, and red/green: through the wait for an uncommitted fix, `squeal proof` for a committed one. Read it when a command's output is not what step 5 or 6 expects, or before a red/green check.
- `references/policy.md`: an edit denied after a regression, a Stop that keeps you going or waits for the slow tier, and every key of `squeal.config.json`. Read it when Squeal denies an edit or blocks a stop, or before changing the config.
